## IDE

**IDE（Integrated Development Environment 統合開発環境）**は現代のプログラマーが最も頻繁に接触するツールで、コンパイルツールを提供するだけでなく、通常以下の機能も含む：

- テキストエディタ：コードを記述し、構文の色分けにより可読性を高める
- インテリセンス：コードの一部を入力するだけで全コードを提示し、開発者のコード記述速度を向上させる
- デバッガ：プログラムの実行ステップを定点で実行し、プログラムの誤りロジックを迅速に発見しやすくする
- 美しいインターフェース：各種ボタン、パネル、メニュー、ウィンドウなどのコントロールが整然と配置され、操作がより便利になる
- パフォーマンス分析：CPU使用率、メモリ消費量などプログラムの各種パフォーマンスを分析するツールを提供
- プロジェクト管理ツール：ソースファイル、画像、動画、サードパーティライブラリなどプログラムに関連するすべてのリソースを管理する
- ...

現在主流のC++ IDEは以下の通り：

- [Visual Studio](https://visualstudio.microsoft.com/zh-hans/)：マイクロソフトが提供するIDEで、多くの人から「宇宙一のIDE」と尊称されている。容量は大きいが、Windowsシステム下での開発の第一選択肢である。

## ビルドツール

前のセクションでは、Visual StudioのCLコンパイラを使ってC++のコンパイルフローを簡単に説明した。実際のプロジェクト開発では、プロジェクトが単一のソースファイルだけで構成されることはほとんどない。これは大量のコンパイル命令を記述する必要があることを意味するが、幸いにも命令を**makefile**ファイルに記述し、**make**ツールを通じてビルドできる。しかし、ここには非常に深刻な問題が存在する：

> Windows下の命令をLinuxに置くと、認識されないのだ~

是的、makefileは直接オペレーティングシステムの命令を呼び出すが、各システム間の命令には差異が存在するため、多くのクロスプラットフォームプロジェクトビルドツールが登場した。例えば：

- [cmake](https://link.zhihu.com/?target=https%3A//cmake.org/)：現在主流のクロスプラットフォームビルドツール
- [qmake](https://link.zhihu.com/?target=https%3A//doc.qt.io/qt-6/qmake-manual.html)：Qtが提供するビルドツールで、現在Qtは全面的にCmakeに移行し、qmakeは維持されなくなった。
- [nmake](https://link.zhihu.com/?target=https%3A//docs.microsoft.com/en-us/cpp/build/reference/nmake-reference)：Visual Studioの組み込みツールで、Makefileに記述されたコンパイルリンクステップを実行する。
- [xmake](https://link.zhihu.com/?target=https%3A//xmake.io/)：国人が開発したLuaベースの軽量クロスプラットフォームビルドツール。
- UBT：Unreal EngineにおけるC#ベースのビルドツール

大部分のC++初学者にとって、プロジェクトのビルドは多くの場合IDEのグラフィカルインターフェースを直接使用し、操作ボタンをクリックしてソースファイルを追加することだろう。例えばVisual Studio：

![image-20230113082804541](../../../00-C++/Resources/image-20230113082804541.png)

グラフィカルインターフェースは使用しやすいが、いくつかの欠点も存在する：

- IDE自体がクロスプラットフォームをサポートしていない場合、そのプロジェクトファイルもクロスプラットフォームできないため、他のプラットフォームではコンパイルできない
- 異なるシステムでは異なるビルド設定が存在し、グラフィカルインターフェースでは静的な設定しかできず、自動化されたビルドロジックを実現できない
- グラフィカルインターフェースで設定されたプロジェクトファイルは、ファイルパスやシステムが変更された場合、以前のリンクが失われる可能性がある
- ライブラリの管理が混乱しやすく、かつ非常に煩雑...

> そうは言っても、筆者は早期にビルドツールを使用せず、純粋なグラフィカルインターフェースでプロジェクトを記述しても何の問題もなかった（技術力不足が原罪だ）
>
> グラフィカルインターフェースの使用を放棄する主な原因は：
>
> - プログラムのコンパイル前に、プロジェクト内の一部のファイルを「前処理」してからC++コンパイラに渡す必要がある（QtのMocを模倣：[XObject](https://github.com/Italink/XObject)）
> - プログラムのコンパイル前に、いくつかのスクリプトや命令を実行する必要がある。例えば、シェーダーコードを事前にバイナリファイルにコンパイルする

上記の**多くのビルドツールの中でどれを選ぶべきか？**

### CMake

なぜCMakeなのか、それは非常に強力だからか？いいえ、それは主な原因ではない。最も根本的な原因は：**大部分のオープンソースコミュニティがCMakeをビルドツールとして使用している**ため、他のサードパーティライブラリを容易に導入できるからだ。

多くの人がCmakeが難しいと不満を言うかもしれない。その構文はクソのようだが、実際に難しいのはCmakeではない。プロジェクトの規模が大きくなると、ビルドロジックは必然的に複雑になる。どのビルドツールも主体的なロジックはほぼ同じで、核心的なビルド文は数行だけである。多くののはいくつかのビルドオプション、クロスプラットフォーム設定、自動化スクリプトなどだ。一つのビルドツールを理解すれば、他のものは簡単に理解できる。

CMakeを使用してプロジェクトを管理する主なメリットは以下の通り：

- CMakeは各プラットフォームのIDEプロジェクトファイルを生成できる
- CMakeを使用してロジックコードを記述し、自動化されたビルドを完成させ、各プラットフォームのビルドの詳細に適応できる
- サブプロジェクト（ライブラリ）の管理が容易
- プロジェクトファイルは依存関係分析を行い、コンパイル速度が非常に速い

初学者にとって、一般的にCMakeGUIの使用とCmakeListsの基本構文を習得するだけで十分だ。

#### CMake GUI

CMake GUIは**親切な**グラフィカルインターフェースで、コマンドライン操作に代わることができる。

Cmakeをインストールした後、CMake GUIのデスクトップショートカットを作成することに注意してください。

![image-20230108215228112](../../../00-C++/Resources/image-20230108215228112.png)

CMakeプロジェクトをビルドしたい場合は、直接CMake GUIを開く：

- CMakeLists.txtをウィンドウにドラッグし、`Where to build the Binaries`（バイナリのビルド先）を設定する。筆者は通常ソースディレクトリの後に`/build`を追加する。

- `Configure`をクリックするとポップアップウィンドウが表示され、生成したいIDEプロジェクトファイルといくつかのコマンドラインパラメータを選択する。

  ![image-20230108220004147](../../../00-C++/Resources/image-20230108220004147.png)

- `Finish`をクリックすると、調整可能な設定オプションが表示され、説明に従って調整できる。

- 再び`Generate`をクリックすると、対応するIDEのプロジェクトファイルが生成される。

- 最後に`Open Project`をクリックすると、対応するIDEで直接プロジェクトが開かれる。

> Qt CreatorやVisual Studioなど、一部のIDEは直接CMakeList.txtを開くことをサポートしている。Visual Studioについては、筆者はCMake GUIの方式でVSのプロジェクトファイル（`*.sln`）を生成することを推奨する。



#### CMakeList基本構文

CMakeは難しくない。ただプロジェクト情報を設定するだけ：

``` cmake
project(${ProjectName} VERSION 0.1 LANGUAGES CXX)
```

Cmakeの最小バージョンを制限する：

``` cmake
cmake_minimum_required(VERSION 3.5)
```

元の【手動でボタンをクリックしてソースファイルを追加する操作】は以下に置き換えられる：

``` cmake
add_executable(${TargetName} *.h *.cpp ...)				//実行ファイルを作成
// add_library(${TargetName} STATIC *.h *.cpp ...)		//静的ライブラリを作成
// add_library(${TargetName} SHARED *.h *.cpp ...)		//動的ライブラリを作成
```

他のライブラリを導入したい場合は以下を使用：

``` cmake
target_link_libraries(${TargetName} PRIVATE ${LibraryName})  
//PRIVATEは${TargetName}だけが${LibraryName}のコードにアクセスできることを意味する
//PUBLICは${TargetName}を導入した他のライブラリも${LibraryName}のコードにアクセスできることを意味する
```

Includeパスを追加したい場合は以下を使用：

``` cmake
target_include_directories(QEngineEditor PRIVATE ${IncludeDir}) 
```

ローカル変数を操作したい場合は直接以下を使用：

```cmake
set(VarName "This is String")
messgae(Warning ${VarName})  // ${}で変数を囲んで読み取る。ここではVarNameの値を出力する操作
```

サブディレクトリを追加したい場合は以下を使用（サブディレクトリとはCMakeLists.txtを持つパスを指す）

``` cmake
add_subdirectory(${Subdir})
```

基礎的な操作はこれだけである。ある設定や機能が合理的であると感じれば、それは大概率存在する。インターネットで検索したり、公式サイトで調べたりすれば出てくる。ビルドファイルの変更は頻繁ではないので、主体的なロジックを知っていれば十分だ。

ビルドツールは実質的に大差なく、何を使っても構わない。それらの使用は難しくないが、关键は各種プラットフォームとフレームワークの詳細な設定である。これは避けられない。

CMakeの使用については、インターネットに多くの優れたチュートリアルが存在するが、筆者は公式ドキュメントを読むことを推奨する：https://cmake.org/cmake/help/latest/guide/tutorial/index.html

## パッケージ管理

Pythonを使用したことがある人は、パッケージ管理ツールである`pip`を使用したことがあるだろう。

`pip install ...`を使用してpythonにサードパーティライブラリを迅速にインストールできる。

C++のパッケージ管理は常に混乱している。自分のプロジェクトにサードパーティライブラリ（例えばOpenCV、ffmpeg...）を導入したい場合、公式ウェブサイトからダウンロードする必要がある。もしCMakeでビルドされたソースコードであればまだ良いが、ライブラリファイルであれば、コンパイルタイプがDebugかReleaseか、動的ライブラリか静的ライブラリか、MDかMTか、32ビットか64ビットかに注意する必要がある...

多くの人はライブラリのインストール時に各種設定に苦労したことがあるだろう。今、ついに大家を救うツールが登場した —— [Vcpkg](https://github.com/microsoft/vcpkg)

> VcpkgはWindows、Linux、MacOS上でCおよびC++ライブラリを管理するのを助ける。

その使用方法については以下を参照：

- https://github.com/microsoft/vcpkg/blob/master/README_zh_CN.md

## バージョン管理

その日、筆者はバージョン管理のない時の恐怖を思い出した...

筆者が早期に学習していた時は、バージョン管理ツールについて何も知らなかった。普段は問題を解くだけで、コード量はせいぜい百行程度で、小さなプロジェクトを書いても千行程度だった。後にプロジェクトの規模が大きくなり、Featureのコード変更が比較的大きくなったため、着手する前にソースコードをコピーしてバックアップしておく習慣を身につけた。新しいコードに「莫名其妙」な、修復不可能なエラーが入るのを防ぐためだ。

早期のこの方法には特に問題はなかった。しかし、ある日筆者がコードを書き込んでバックアップを取らなかった。約一週間のコード変更が非常に多く、一日調べても原因が見つからず、頭が破裂しそうになった。後に仕方なく、以前のバックアップから再び書き直し、少しずつ追加し、少しずつテストした。約三日間かかってやっと問題を修復し、進捗を回復した。

その三日間、筆者は毎日が長く感じ、一行一行の馴染みのあるコードを見ながら、小心翼翼に再び書き直し、一度は諦めたくなったが、自分自身に耐えて坚持するよう説得し続けた...

それでも筆者は新しいものを理解する時間を浪費することを嫌い、その時間を**コードを積み上げる**ことに費やしていた。

後に、筆者は一位の兄貴に出会った。彼は辛抱強く筆者のプロジェクトの瑕疵を指摘し、プロセスの不規範さを指摘し、苦口婆心でGitを紹介してくれた。筆者はついに彼に打ちひしがれ、使用してみることを決心した。これを使用して現在まで続けている。現在の筆者が以前の自分を評価すると、ただ二文字 — バカ — だけだ。

### Markdown

> Markdownは一種の[軽量マークアップ言語](https://baike.baidu.com/item/轻量级标记语言/52671915?fromModule=lemma_inlink)で、創始者はジョン・グルーバー（John Gruber）である。人々が読み書きしやすい[純粋テキスト形式](https://baike.baidu.com/item/纯文本格式/9862288?fromModule=lemma_inlink)でドキュメントを記述し、その後有効な[XHTML](https://baike.baidu.com/item/XHTML/316621?fromModule=lemma_inlink)（またはHTML）ドキュメントに変換することを許可する。この言語は電子メールに既に存在する多くの純粋テキストマークアップの特性を吸収している。
>
> ——《百度百科》：https://baike.baidu.com/item/markdown/3245829

なぜMarkdownを使用するのか？

筆者のブログはすべてMarkdownで記述されている。使用してきた感想は以下の通り：

- **記述速度が速い** ：Markdownの構文に慣れると、ドキュメントの記述速度が非常に速くなる
- **操作が簡単で、認知負担が小さい** ：いくつかの「不合理な」機能を制限し、ドキュメントのロジックが線形であることを保証する。それでドキュメントを書くのは一種の享受だ。
- **汎用性が高い** ：多くのウェブサイトがMarkdownのサポートを提供している。それは本質的に純粋テキストであるため、他のウェブサイトはその構文を解析してプレビューできる。また、テキストであるため、ドキュメントのバージョン管理も容易になる。
- **美しい** ：markdownはドキュメントの構造だけを記録し、多くの美しいサードパーティのスキンテーマが存在する。

Markdownを何で書くのか？

Markdownエディタは多く、一部のブログサイトは直接サポートしている。ローカルでは、筆者が見た多くのものはVS Codeを使用するか、狂拽酷炫、天下无敌、宇宙第一のMarkdown神器である：
