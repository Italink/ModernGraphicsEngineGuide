# 편집기 아키텍처

저자가 최근 몇 년 개발 중 대부분의 코드 축적을 엔진 편집기에 쏟았으므로, 여기 몇 가지 경험을 정리하여 참고로 제공합니다. 이 문서는 다음과 같은 차원에서 편집기 설계를 분석합니다:

- 디자인 미감
- 사용자 경험
- 리플렉션 기반 편집기 아키텍처
- 성능 최적화

## 디자인 미감

디자인 미감은 대부분 개발자가 부족한 부분입니다. 왜냐하면 그들은 코드에 매우 많은心思를 쏟기 때문에, 정교한 인터페이스를 만드는 방법을 고심하려는 사람이 적기 때문입니다.

물론, 그들은 디자인을 이해하는 뇌를 갖고 있지는 않지만 아름다운事物을欣賞하는 눈은 있으므로, 적절한 참고 자료만 있으면 개발자들은 빠르게 해당 효과를 복제할 수 있습니다.

대부분의 소프트웨어 개발 팀에는 전문 UI 디자이너가 있으며, 그들은 주로 UI의 다음 사항에 집중합니다:

- 타이포그래피
- 색조
- 아이콘
- 레이아웃

저자가 사용한 일부 소프트웨어 시스템 중 일부는确实上述几点을考虑하여 정교한 인터페이스 효과를 만들었지만,往往 UI의 **컴포넌트화 설계**를 무시하여 다음과 같은 문제를 유발합니다:

- 사용자가 소프트웨어의 사용 규칙을 빠르게建立할 수 없어, 큰 인지 부담이 발생합니다.
- 소프트웨어 코드의 조직 구조를破坏하며, 컴포넌트화 설계가 우수한 UI는 인터페이스에서 코드의 계층 구조를看出할 수 있지만, 규칙이 혼란한 인터페이스는 그 코드도往往一团糟입니다.

Unreal Engine을 예로 들면, 그 컴포넌트화 설계가 매우 직관적입니다:

![image-20230629110339347](../../../02-EngineTechnology/Resources/image-20230629110339347.png)

사용자는 인터페이스上各个组件元素의职责을理解하고掌握하기만 하면, 많은 경우 튜토리얼이나 문서를借助하지 않고도举一反三地操作할 수 있습니다.

UI 디자이너는大多 UI 효과에专注하기 때문에, 그들에게 코드 아키텍처에适用于하는 컴포넌트화 설계를制作하게 하는 것은往往比较困难합니다. 따라서 이方面의内容에 대해 개발자가思考,讨论,引导하고 "아니오"라고 말하는 법을学会해야 합니다.

UI 디자인上的一些概念和风格에 대해, 여기 더详细한 참고 자료가 있습니다:

- [All Time Design - UI Style Guide](https://alltimedesign.com/ui-style-guide/)

## 사용자 경험

사용자 경험에 대해, 주로 다음을围绕합니다:

- 사용자의 인지 부담 감소: 인터페이스 레이아웃, 라벨 명명,操作上一些常識和规范을遵循
- 취소, 재실행 지원: 일부 잘못된操作을快速修正할 수 있게 함
-合理的操作反馈: 일부操作을执行할 때,日志, 대화 상자, 진행률 표시줄, 알림 버블, 상태 표시줄...을 사용하여 사용자에게操作的执行状态를告知
-及时的状态备份或保存:意料之外的崩溃导致大量工作数据丢失를避免
-可配置的操作方式: 사용자가 단축키, 레이아웃方式,操作风格等을自定义할 수 있게 함

사용자의 인지 부담 감소에 대해, 여기非常完善한 문서가 있습니다:

- [O3DE - Component Card UX Pattern](https://docs.o3de.org/docs/tools-ui/ux-patterns/component-card/)

- [O3DE - Component Card Error Handling](https://docs.o3de.org/docs/tools-ui/ux-patterns/error/)

취소 재실행에 대해,它是一个代码设计的问题입니다.通常情况下,我们会在设计模式层面备忘录模式和命令模式을使用하여撤销重做功能을实现합니다. 이는 Qt中对应的结构是 **QUndoCommand** 和 **QUndoStack** 이며,其中 **QUndoCommand** 的核心定义如下:

``` c++
class QUndoCommand
{
    virtual void undo();
    virtual void redo();
    virtual int id() const;
    virtual bool mergeWith(const QUndoCommand *other);
}；
```

使用时,我们会 QUndoCommand를派生하고, 함수를覆写하여 undo和redo的操作行为을实现한 후,具体的Command를 UndoStack中에推入합니다.

여기简单的代码示例가 있습니다:

``` c++
#include <QUndoCommand>
#include <QUndoStack>
#include <QDebug>

class QAssignCommand : public QUndoCommand {
public:
	QAssignCommand(int* ptr, int dstValue)
		: mValuePtr(ptr)
		, mSrcValue(*ptr)
		, mDstValue(dstValue) {}
protected:
	virtual void undo() override {
		*mValuePtr = mSrcValue;
	}
	virtual void redo() override {
		*mValuePtr = mDstValue;
	}
private:
	int* mValuePtr = nullptr;
	int mSrcValue;
	int mDstValue;
};

int main(int argc, char** argv) {
	QUndoStack stack;
	int value = 0;
	stack.push(new QAssignCommand(&value, 1));
	qDebug() << value;		//1
	
	stack.undo();
	qDebug() << value;		//0
	
	stack.redo();
	qDebug() << value;		//1

	stack.beginMacro("Merge");	
	stack.push(new QAssignCommand(&value, 2));
	stack.push(new QAssignCommand(&value, 3));
	stack.endMacro();
	qDebug() << value;		//3

	stack.undo();
	qDebug() << value;		//1

	return 0;
}
```

它的实现思路比较简单하지만,也有一些比较难处理的点이 있습니다:

- Command中操作对象如果在其他地方被销毁了,但Command还存在于Stack中,如果此时执行撤销重做,可能会导致程序的崩溃

이러한 문제에 대해,我们主要可以通过以下几个方案去解决합니다:

-撤销重做操作的指令가操作对象的生命周期를完全覆盖하지 않았는지考虑

- Command에有效性验证을增加
-序列化을使用하여对象를保存和重建

Unreal Engine中,对象系统 기반의撤销重做机制 —— **Transactional**을提供합니다.

任意 `RF_Transactional`标识를携有的UObject实例에 대해,如下代码를使用하여撤销重做을实现할 수 있습니다.

``` c++
GEditor->BeginTransaction(FText::FromString("Assign Value"));	//事务开始

MyObject->Modify();												//初始状态保存
MyObject->ValueProperty = 123;									//属性修改

GEditor->EndTransaction();										//事务结束
```

UObject的GC가对象延迟回收을 가능하게 하므로,我们无需操作对象生命周期的问题을考虑합니다.它的实现原理에 대해,详见:

- [CSDN - UE4 编辑器(UObject)的Undo撤回系统Transactional](https://blog.csdn.net/qq_29523119/article/details/96778797)

状态保存에 대해,大家都程序突然崩溃或者电脑突然关机的情况을遇到한 경험이 있을 것입니다.这个时候如果及时的保存工作数据를 하지 않았다면,几小时的工作成果가打水漂해야 합니다.而这个时候,如果程序이保存或备份的辅助手段을提供한다면,意外来临时自己을救一命할 수 있습니다~

而这种手段一般是指自动保存입니다.用户가手动点击하여工作数据를保存하는 것 외에도,我们还可以特定时机去自动保存或备份工作数据를 할 수 있습니다.就比如:

-用户가某个界面을关闭时保存进行
-定时自动保存
-程序崩溃时保存（`SetUnhandledExceptionFilter`函数을使用하여程序崩溃时的系统回调을设置可）

上述手段可以尽可能的工作数据丢失的风险를减少합니다.当然,一些保存性能损耗不大的数据,比如小型配置文件에 대해,就可以直接操作完执行后立即保存을 할 수 있습니다.

## Meta思维

Meta思维은现代工业软件开发过程中极大的便捷度를提供할 수 있으며,一劳永逸的代码扩展方式를提供할 수 있습니다.

> Meta思维에 대한 연상 단어로는: `求导`, `高阶维度`, `上帝视角`, ...
>
>详见: [[ 知乎 ] bus waiter- 谈meta](https://zhuanlan.zhihu.com/p/406257437)

假如写代码를盖房子比作한다면,我们考虑的是如何房子를盖好하는 것이고, Meta层面에서我们考虑的是如何自动盖房子的机器를构建하는 것입니다. Meta思维은我们을一个工程问题에서另一个으로转换시킵니다.虽然难度有所上升하지만,只要方法得当하다면,它能无可比拟的收益를带来합니다.

저자가一些自研引擎和软件를接触한 바,只要 **自研引擎编辑器** 相关的话题가涉及되면,下面基本就是骂声一片~~~

究其原因,无外乎:

-界面简陋
-用户体验差

而大部分开发者的想法是:

- "并不是不能做好,只是要做好得花很多时间,会很麻烦,没必要浪费时间,将就能用就行了."

当然,这种想法는一些小工具来说无可厚非하지만,一些高频使用的工具에 대해依旧是这样的态度对待한다면,那对使用人员来说就是一场痛苦的折磨...

저자는 Qt上数十万行代码的积累을 가지고 있지만, Unreal Engine上只数万行的代码를使用했을 뿐더러,更多更完备的功能을做出었습니다.并且 Unreal Engine中,界面风格和用户体验的需求는非常容易满足的입니다.这很大程度得益于 Unreal Engine 的 " **基础建设** " 입니다.

游戏引擎中, Meta理念 기반의架构가比比皆是합니다.而在这其中最有用最强大的无疑是 —— **리플렉션 기반 편집기 아키텍처**

相信大家都一些参数调节面板을见过을 것입니다.比如:

![image-20230628222459585](../../../02-EngineTechnology/Resources/image-20230628222459585.png)

代码层面에서,这些可配置参数往往具体的数据结构에对应합니다.它可能是这样的:

``` c++
struct Options{
	bool 			Option0;
    int 			Option1;
    string 			Option2;
    vector<string> 	Option3;
};
```

大部分开发者는数据结构`Options`에针对하여手动编写代码去编辑面板을创建합니다.而 Meta层面에서,我们会这类复杂结构를进一步拆解합니다.因为 C++中的基本类型은有限적이며,开发者所创建的类型也只是那些基础类型을按照一定层次组织起来的 것입니다.我们完全可以成员变量的类型에根据하여控件를创建하고, `Options`的结构에根据하여控件的布局를组织할 수 있습니다.简而言之,也就是 **类型 기반控件, 结构 기반面板** 입니다.

由于我们需要运行时数据结构的相关信息를获取해야 하므로,因此就必须 **리플렉션** 을依靠해야 합니다.此外,数据结构组织往往是树状的因此我们会 GUI框架中的`TreeView控件`을使用하여控件面板을组织합니다.

여기简单的伪代码가 있습니다:

``` c++
class Options: public Object{		//数据结构, Object는对象系统的基类
    OBJECT_ENTRY()					//OBJECT_ENTRY는 리플렉션系统的入口宏
    
   	PROPERTY()	bool 			Option0;	//PROPERTY宏을使用하여属性를 리플렉션
    PROPERTY()  int 			Option1;
    PROPERTY()  string 			Option2;
    PROPERTY()  vector<string> 	Option3;
};

class DetailView: public TreeView{
public:
	void setObject(Object* object){											
        clearTreeView();
        for(auto metaProperty: object->metaObject()){						//MetaObject에根据하여对象所有的属性를遍历
            Widget* widget = generateWidgetForType(metaProperty.type());	//类型에根据하여控件를生成
            widget->bind(Object,metaProperty);								//控件를 리플렉션的属性와绑定
            this->addRow(widget);											//控件를 TreeView中에添加
        }
    }
};
```

类型에 대해,我们主要以下分类에根据하여归纳합니다:

-基本类型: 逻辑, 数值, 枚举, 字符串
-复合类型: 类, 结构体
-容器类型:
    -连续（sequential）容器: list, array, vector, set, queue...
    -组合（associative）容器: map, hashmap...

这样的分类을通过하여,开发者只需要基本类型에 대해控件를制作하고,复合类型에 대해属性面板布局를组织하면 됩니다.而容器类型的编辑面板은往往内部元素类型에自动生成和组合的 것입니다.此外,为了能够开发者가随心所欲的基本属性를扩展하고对象的面板和布局를覆盖할 수 있게 하기 위해,一般会两个结构를提供합니다:

```C++
class IDetailCustomization{
public:
	virtual void CustomizeDetails(DetailsBuilder* builder) = 0;		//对象的调节面板을自定义用于
};

class IPropertyTypeCustomization{
public:
	virtual void CustomizeHeader(RowBuilder* builder) = 0;		//属性类型的 Header Row를自定义用于
	virtual void CustomizeChildren(DetailsBuilder* builder) {}	//该属性类型的 Child Row를附加用于
};
```

为了能够属性를管理하기 위해,还会 `IPropertyHandle`을派生합니다.它主要用作:

-多态을使用하여层次关系的组织을处理.
-属性设置和获取的唯一入口으로作为하여,撤销重做,变动通知,编辑器同步等相关功能을加入.

``` c++
class IPropertyHandle{
    void SetValue(Variant var);
    Variant GetValue();
    virtual Widget* GenerateNameWidget();		//属性的名称控件를生成
	virtual Widget* GenerateValueWidget();		//属性的值控件를生成
	virtual void GenerateChildrenRow(DetailsBuilder* builder);	//属性的子行를生成
};
```

如上结构的支撑를有了之后, DetailsView的创建过程可以简单看作是:

``` C++
map<typeid,IDetailCustomization*> GloabalDetailCustomizationMap;
map<typeid,IPropertyTypeCustomization*> GloabalPropertyTypeCustomizationMap;

class DetailView: public TreeView{
public:
	void setObject(Object* object){											
        clearTreeView();
        
        auto DetailCustomization = GloabalDetailCustomizationMap[object->metaObject()->type()];	
        DetailsBuilder builder(this);
        DetailCustomization->CustomizeDetails(&builder);
        /* 对象类型所对应的DetailCustomization을获取, CustomizeDetails를调用하면其所有的Property를遍历하고,
        IPropertyHandle을创建합니다.而 IPropertyHandle又会属性类型所对应的IPropertyTypeCustomization에根据하여,
        具体的属性调节控件를创建합니다.
        */
    }
};
```

实际的架构会上面的结构보다复杂一些하지만,只要核心思路를掌握하면实现起来并不困难합니다.此处简单版本的 Qt实现（Unreal Engine 的 DetailsView를参考）가 있습니다:

-代码: https://github.com/Italink/QEngineUtilities/tree/main/Source/Editor/Source/Public/DetailView
-示例工程: https://github.com/Italink/QEngineUtilities/tree/main/Samples/DetailViewExample

## 성능 최적화

计算机的计算资源는始终有限적이며,游戏引擎中性能消耗的大头毫无疑问是 Game입니다.因此我们需要尽可能的编辑器的性能损耗를降低하여它对 Game执行的影响를减少해야 합니다.

一般情况下,我们可以以下手段을通过하여编辑器的性能를优化할 수 있습니다（游戏内 UI也适用）:

- **美观追求를 위해高损耗的界面效果를 사용하지 마세요** :

  -尽可能界面动画和滤镜（模糊,阴影,拟态,毛玻璃,投影变换...）을使用하지 마세요.

  -高分辨率的图像资源를使用하지 마세요.

  -静态的 UI에 대해,尽可能已制作好的图像를使用하거나预先 RT（Bitmap）을绘制하세요.而不是 GUI框架을使用하여每帧实时绘制하세요.如取色器的调色板:

    ![image-20230629115539526](../../../02-EngineTechnology/Resources/image-20230629115539526.png)

- **界面重绘的时机를管控하세요** : 假如某个`操作A`가界面更新을触发하지만,有时候我们往往一帧中`操作A`를多次执行합니다.很显然我们没必须要一帧中多次界面를重绘할 필요가 없습니다.所以我们往往`操作A`中直接 UI를更新하지 않고,标识를设置하고 UI的`Tick`事件中标识에根据하여 UI를重绘합니다.就像是这样(伪代码):

  ``` c++
  class MyWidget : public Widget{
  private:
      bool bNeedRepaint = false;
  public:
      void setFont(...){				//字体를设置, 界面重绘을触发
       	bNeedRepaint = true;
      }
      
      void tick() override{			//UI的Tick事件을覆写, Tick时是否需要 UI를重绘检查
          if(bNeedRepaint){
              repaintUI();			//UI的重绘接口
              bNeedRepaint = false;
          }
      }  
  };
  ```

- **离屏绘制缓存和局部刷新를使用하세요** : 一些上帧图像复用性很高的 UI에 대해, UI를先一张 RT（Bitmap）上에绘制할 수 있습니다.每帧只要按需部分区域的 UI를更新即可.这种做法는图表, 画布相关的 UI上较为常见합니다.

- **主线程中高消耗的逻辑操作执行으로 UI阻塞를避免하세요** : UI的处理往往是主线程에位于합니다.如果一些主线程中逻辑操作的执行耗时가比较高다면,就会 UI的阻塞를导致합니다.这个问题을解决하기 위해主要两个方法이 있습니다:

  -逻辑操作中 UI系统的更新操作을插入하여强制 UI刷新.
  -逻辑操作을异步线程에放到执行하고,逻辑执行完毕后主线程中 UI相关的更新을执行.
