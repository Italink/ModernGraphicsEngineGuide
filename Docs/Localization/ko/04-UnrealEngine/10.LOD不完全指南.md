# LOD 불완전 가이드

전자 컴퓨터의 발명은 제2차 세계 대전 기간에 시작되었는데,当时 포격 및 탄도 계산이 점점 복잡해져 기존 계산 도구로는 요구를 충족시킬 수 없게 되었고, 이러한 문제를 해결하기 위해 과학자와 엔지니어들이 전자 컴퓨터 개발을 시작했습니다.

전자 컴퓨터의 출현과 함께 전자 게임도 생겨났습니다.

전자 게임의 발전 과정에서는 언제나 독창적이고 혁신적인 아이디어와 기술이 있었으며, 이는 하드웨어 개발자의 사고의 한계를 끊임없이 뛰어넘고 하드웨어 성능을 극한으로压榨하며 컴퓨터가 놀라운 방향으로 발전하도록 이끌었습니다:

- [지후 | 전자 게임의 전생, 금생과 미래 - 맥아트](https://zhuanlan.zhihu.com/p/206828303)

그리고 **LOD（Level of Detail）** 는 바로 이 발전 과정에서 나타나 지금까지 계속 사용되는 기술로, 그 목적은 다음과 같습니다:

- 서로 다른 **중요성（Significance）** 의 상황에서 서로 다른 정밀도의 전략을采用하여 자원 낭비를 최대한 줄이고 전체 시스템의 한계를 높이는 것입니다.

이러한 사고 전략은 게임 제작의 모든 면에 나타납니다.

## 모델

모델에서 LOD의 적용은 주로 모델에 여러 정밀도 수준의 저정밀 모델을 생성하는 것입니다. 가까운 거리에서는 고정밀 모델을 사용하고, 먼 거리에서는 저정밀 모델을 사용합니다.

실시간 렌더링 분야에 사용되고 일정 규모가 있는 3D 장면에서 프로그램의 프레임 속도를 보장하기 위해 모델 LOD 제작은 개발 팀이 피할 수 없는 난제입니다.

높은 시간과 인력 비용으로 인해 많은 독립 개발자와 소규모 팀이 복잡한 장면을 구축할 때 매우 많은 어려움에 직면해야 합니다.

UE의 가상 기하학 기술인 **Nanite** 가 등장하기까지는 장면 제작의 진입 장벽이 크게 낮아졌습니다.

Nanite는 모델 기하학의 중요성 정보를 분석하여 고품질 LOD를 자동으로 생성하며, 저장 공간을 더 적게 차지할 뿐만 아니라 매우 높은 성능으로 렌더링할 수 있어 기하학 렌더링의 미래라고 할 수 있습니다.

하지만 현재로서는 일부 특정 시나리오에서는 LOD를 완전히 포기할 수 없습니다:

- 현대 PC의 GPU 연산 능력은通常 여유가 있으며, 대부분의 중급 GPU로는 일반적인 복잡한 장면 렌더링을应付할 수 있지만, 모바일 기기, X Box, Switch 등 다른 플랫폼의 경우 높은 화면 요구 사항이 있는 프로젝트에 대해 현재 연산 능력은 대부분 겨우 충분한 수준에 불과하며, 더 나은 시각 효과를追求하기 위해 종종 극한 최적화를 위해 비교적 Hack적인 렌더링 메커니즘을定制해야 하며, 할당된 나머지 연산 능력으로는 Nanite의 운영을支撑하기 어렵습니다.
- Nanite의 모델 단순화 알고리즘은 식물과 같은 일부 특수한 모델 유형에서 아직 많은 최적화 공간이 있습니다. 만약 식물 밀도가 높고 범위가 넓은 복잡한 장면이라면 LOD를 사용하여 성능을 더 크게 압축할 수 있으며, 이는 이전 [문서](https://zhuanlan.zhihu.com/p/713731229)에서 언급되었습니다.

이전 대부분의 게임 프로젝트에서는通常 미술人员이 DDC 소프트웨어에서 LOD를 제작했으며, 미술人员은 모델 소스 파일을 제공하는 동시에 일정 규范에 따라 모델에 해당하는 LOD를 생산했습니다.

이러한做法는 현재来看 일정한 한계가存在합니다:

- 초기 모델 제작 프로세스는 비교적 "실용적"이었으며, 대부분의 경우 여전히 수동 모델링 방식만 사용할 수 있었지만,现在 많은 메시 처리 SDK가涌现했으며, 이들은 일반적으로 효과적인 모델 단순화 알고리즘을 제공하여 다시 모델링하지 않고도 고품질 LOD를 생성할 수 있습니다.
- 수동으로 LOD를 제작하는 것은通常 높은 비용이 필요하며, 팀 자체에 충분한 인력과 자원이 있으면还好지만, 아웃소싱 팀에 맡기면 이는 분명 큰 지출이 될 것입니다.
-任何 방법론都有一定适用条件，모델 제작도 마찬가지입니다. 일부 오래된 제작 업체 외에는 대부분의 팀이 게임 제작 초기阶段에 완벽한 제작 규范을制定하기 어려울 것이며,往往 개발 진행에 따라 많은 숨겨진 문제가逐渐浮现합니다. 그리고 미술 제작은 전체 프로젝트에서 비용 소모의 큰 부분을 차지하는데, LOD 제작의 경우 소스 모델이나 규范이 변경되면 이전에 제작한 "제품"이白费되므로,我们需要关注焦点를具体的 LOD 제작에서可迭代的 LOD 생산 파이프라인 구축으로 전환해야 합니다.
- 소스 모델은 미술人员이 제작하지만,他们往往 성능에敏感하지 않고 LOD에 대한认识도 깊지 않으며,无论怎么制作都很难满足 규范的 모델에面对할 때表现出的 것은 무措뿐입니다.

此时 기하학 처리, 그래픽 렌더링, 편집기 방향에 대해深入한了解가 있는 사람이程序化的方式로这些事务을包揽하면 팀의 제작 비용을不少节省할 수 있으며, 이러한 전문人员은一般적으로 **파이프라인 TA** / **엔진 파이프라인 엔지니어** 로定义됩니다.

### 제작 프로세스

LOD를 제작하기 전에 간단한 미리보기 레벨을搭建하는 것이 좋습니다. 간단한 편집기 도구를 통해 자동으로 배열하여 다음 목적을达成할 수 있습니다:

- 자산 목록 또는 자산 경로에 따라 미리보기할 모든 자산을确定합니다.
- 모델의 경계 구체 반경을间隔로 사용하여横向으로 배열합니다.
- LOD의 화면 크기를距离로 변환하여纵向으로所有 LOD를 배열합니다.
-生成된 모델에 화면 크기,距离,顶点 수,면 수 등关键信息를扩展显示합니다.

이러한视图下에서 모델의规格을更加直观地查看和管理할 수 있습니다:

![image-20241109114502541](../../../04-UnrealEngine/Resources/image-20241109114502541.png)

초기 LOD 제작 프로세스에서는一般적으로 모델과 카메라之间的 **距离** 를 LOD切换的判断标准으로 사용했으며,每隔一段距离마다一个 정밀도의 간소화 모델을切换했습니다.这种方式下我们可能会制作出这样的 **LOD 체인** :

![image-20241109115221157](../../../04-UnrealEngine/Resources/image-20241109115221157.png)

但很快有人发现距离를使用하는 것은 LOD之间的距离间隔을很直观地确立할 수 없습니다.因为有的 모델은 크고有的 모델은 작기 때문에,每个 모델에合适的 정밀도分布를保证하기 위해서는不同的距离间隔을评估해야 하므로,这个问题를解决하기 위해我们는另一个 매개변수인 **화면 크기（Screen Size）** 를引入했습니다:它는 **카메라距离** , **카메라의 투시 행렬** 및 모델의 **경계 구체 반경** 을综合评估하여一个数值를得到하며,模型의 화면 점유율로粗略하게当作할 수 있습니다.这是它的计算公式입니다:

``` c++
float ConvertDistanceToScreenSize(float ObjectSphereRadius, float Distance)
{
	const float FOV = 90.0f;								// 카메라 매개변수는统一确认할 수 있습니다
	const float FOVRad = FOV * (float)UE_PI / 360.0f;
	const FMatrix ProjectionMatrix = FPerspectiveMatrix(FOVRad, 1920, 1080, 0.01f);		
	const float ScreenMultiple = FMath::Max(0.5f * ProjectionMatrix.M[0][0], 0.5f * ProjectionMatrix.M[1][1]);
	return 2.0f * ScreenMultiple * ObjectSphereRadius / FMath::Max(1.0f, Distance);
}
```

我们는每次一定百分比의 화면 크기를缩减하여 LOD之间的间隔을确定하며,直接距离를使用하는 것보다更加容易합니다:

![image-20241109121834793](../../../04-UnrealEngine/Resources/image-20241109121834793.png)

可是,虽然 화면 크기를使用하는 것은确实 LOD之间的间隔을直观地设置할 수 있지만,不同 크기의 모델에 LOD 체인의距离间隔을统一하지 않으면视觉上产生的瑕疵가更加明显해집니다.

假如我们는 화면 크기固定百分比递减方式로 LOD를生成하면,不同 모델의 LOD 체인距离가不一致한 것을看到할 수 있습니다（这里瑕疵를看到하기 위해 의도적으로 LOD의 간소화幅度를很大게 조절했습니다）:

固定距离 기울기 LOD를使用하는画面变化가更加平缓한 것을看到할 수 있습니다:

![image-20241109135329103](../../../04-UnrealEngine/Resources/image-20241109135329103.png)

虽然 화면 크기를使用하는 것은确实 LOD之间的间隔을直观地设置할 수 있지만,引擎中大量使用 **距离** 来限制某些视觉效果（比如阴影,距离场光照...）因此,视觉效果를更加平滑地过渡하기 위해서는 다음 전략을使用하여 LOD를生成하는 것이建议됩니다:

-固定 LOD距离 기울기를使用합니다.
-경계 구체 반경에 따라 LOD의数量를确定합니다.
-화면 크기,顶点密度 및 모델 특징에 따라 간소화幅度를确定합니다.

上述의一些关键 매개변수는 프로젝트의迭代,复杂度의提升以及 플랫폼의 성능要求에 따라变化하므로,我们는直接手动으로 LOD를生成하지 않고可迭代的 LOD 생산 파이프라인을搭建해야 합니다.这样可以不断迭代和优化这条 파이프라인입니다.

常见的 간소화 모델生成 전략은 세 가지类别가 있습니다:

- **면 감소（Reduce）** :重要性에 따라一定 **간소화幅度** 를按照하여原有 모델의顶点 데이터를删减하여 간소화 모델을生成합니다.
- **재구성（Remesh）** :체적화 모델 알고리즘을通过하여一定 **체적 정밀도** 로 소스 모델을逼近하여 간소화 모델을得到합니다.
- **대체（Impostor）** :取巧的方式로 모델의视觉效果를保证하며,通常原有 모델의 기하학 구조를打破합니다.

目前大部分의 팀은这条 파이프라인을 DDC와 엔진之间에搭建하지만,目前来说虚幻 엔진은非常优秀的 모델 처리 인터페이스를提供하므로,我们는直接 엔진 측에 파이프라인을搭建하면实际的 게임 장면 환경과更好地结合하여更好的效果를生成할 수 있습니다.

## 재질贴图

재질의 경우 초기 일부 프로젝트에서는 모델 LOD를生成하는 동시에对应的 재질에 LOD를生成했습니다.虽然理论意义上 재질의 로직을 간소화하는 것은确实 성능 오버헤드를减少할 수 있지만, 재질 LOD는无疑 재질 집합의 크기를增加시키며带来的 성능提升은特别明显하지 않고,较复杂的管理方式也让这种做法在实际 프로젝트中很难推广합니다.

目前更多的关注点는贴图上面에 있으며, LOD의应用은 주로贴图에 **Mipmap** 을生成하는 것입니다.

大家는 **Mipmap（다단계渐远纹理）** 에 대해更多的认识는 모어 패턴 현상을解决하는 것일 것입니다:

![14568](../../../04-UnrealEngine/Resources/14568.gif)

- [지후 | 컴퓨터 그래픽스七：텍스처 매핑(Texture Mapping) 및 Mipmap 기술 - 손샤오뢰](https://zhuanlan.zhihu.com/p/144332091)

모어 패턴을解决하는 외에도 Mipmap은目前 UE中还有其他用处가 있습니다:

- **텍스처 스트리밍（Texture Streaming）** ：显存占用의压力를缓解하기 위해 UE는默认一定大小의 텍스처 스트리밍 풀을分配합니다（`r.Streaming.PoolSize`로配置）. 텍스처의重要性（카메라距离 및 텍스처 그룹 우선순위）에 따라 텍스처의某个 **MipLevel** 을流入하여整体的显存占用을尽可能降低합니다.这里는 텍스처 스트리밍에关于하는非常有价值的文章가 있습니다:
    - [지후 | UE4 Texture Streaming - mike](https://zhuanlan.zhihu.com/p/556620567)
    - [지후 |虚幻 엔진（UE4）对移动端 텍스처 자원（ASTC）的极致压缩处理总结 - Sparrowfc](https://zhuanlan.zhihu.com/p/566998709)
- **UI适配（UI Adaptation）** ：游戏은不同分辨率的运行环境에面临할 수 있으므로 UI贴图을缩小할 때 **다운샘플링（Downsampling）** 의紋素跨度过大导致贴图에鋸齒边缘이出现하며,动态调整位置的 UI의 경우明显的闪烁이出现할 수 있습니다.此时 UI贴图에 Mipmap을生成하면引擎은 `DDX(UV)` , `DDY(UV)`에 따라 UI贴图의哪一个 **MipLevel** 을使用할지确定합니다.

![image-20241115230952306](../../../04-UnrealEngine/Resources/image-20241115230952306.png)

我们는这里에서某个贴图의 Mipmap을单独特化할 수 있습니다:

![image-20241109194151209](../../../04-UnrealEngine/Resources/image-20241109194151209.png)

但最好的方式는贴图을不同的 **텍스처 그룹（TextureLODGroup）** 에分类하여每个 텍스처 그룹에统一的配置를采用하는 것입니다.这样多平台의 성능 튜닝을 할 때更加方便합니다.

UE 5中에서는此处에서不同 플랫폼下 텍스처 그룹의配置를统一设置할 수 있습니다:

## 지형

UE5의 지형运行 메커니즘은非常完善하며, 지형의 LOD는曲面细分의 정밀도를调整하여实现합니다.目前默认 8级 LOD를使用하며, LOD를修改하려면这些 매개변수를调整하면 됩니다:

![image-20241109210110173](../../../04-UnrealEngine/Resources/image-20241109210110173.png)

UE5.1之后 Nanite 지형을支持하며, 지형은非常标准化的 모델 데이터를拿到하므로 Nanite를开启한 후无疑更合理的 기하학组织을拥有하며, LOD相比通常更少的 삼각형과更保真的视觉效果를具有합니다:

![image-20241109211741424](../../../04-UnrealEngine/Resources/image-20241109211741424.png)

虽然 Nanite의 스케줄링 알고리즘은曲面细分相比复杂一些且网格 데이터를多一份占用하지만,镜头静止时 Nanite의 렌더링消耗은明显 LOD보다低으며,并且 Nanite는虚拟阴影에友好하므로 플랫폼 제한이 없다면 Nanite 지형이更好的选择입니다.

目前一些 프로젝트中에서는静态 메시를 지형으로使用하며,世界分区의 스트리밍과 HLOD를借助하여更好地性能平衡를得到할 수 있으며 지형编辑的限制가 없지만, 지형의主要优势는几张高分辨率（贴图의分辨率는远远小于 지형分辨率）的 Tile贴图으로一个很大的区域를平铺할 수 있어,相同视觉 정밀도的 지형을 모델로平铺出하는 것보다占用하는磁盘大小가远远小다는 것입니다.

## HLOD

上面提到的几种 LOD类型은主要单个 자산을针对하는 것인데, HLOD는 자산을合批之后再 LOD를制作하는 것입니다.

目前 HLOD는 UE中两种使用方式가存在합니다:

-普通 맵에针对하여该文档에 따라工具을利用하여 메시를合并하여 HLOD를生成할 수 있습니다:
    - [Epic Games | HLOD构建](https://dev.epicgames.com/documentation/en-us/unreal-engine/building-hierarchical-level-of-detail-meshes-in-unreal-engine)
-开放世界 맵에针对하여则是场景物体를分类하여 **HLODLayer** 를设置하여世界分区의 **메시单元（Grid Cell）** 에自动으로 HLOD를生成해야 합니다:
    - [Epic Games |世界分区为 HLOD构建](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---hierarchical-level-of-detail-in-unreal-engine)

这里는后面一种方式에 대해展开하여说하겠습니다.

因为 **世界分区（World Partition）** 은场景 메시를很多个单元으로划分하여 **스트리밍（Streaming）** 을通过하여关键的一部分区域（比如玩家周边）만加载하므로,程序执行的压力를有效缓解할 수 있습니다:

![image-20231128183116324](../../../04-UnrealEngine/Resources/image-20231128183116324.png)

但卸载된单元에 대해我们는仍然它가显示되기를希望하지만太大的性能 오버헤드를增加하고 싶지 않으므로,我们는单元内의物体에 HLOD를生成하여 스트리밍的加载范围를进一步缩减할 수 있습니다.因为 HLOD는 다음을做到할 수 있습니다:

- Draw Call减少
-图元组件数量减少,剔除效率提升
-远景的 기하학和贴图的 정밀도减少, 렌더링效率提升 및内存压力降低

但它同样也问题가存在합니다:

-一定的显示范围만扩大할 수 있습니다
-磁盘空间大小를增加시킵니다

目前 UE는四种基础的 HLOD生成 전략을提供하며,它们는 **静态 메시体 자산만针对** 하는 것인데,分别是:

-实例化：单元格内的物体를 ISM으로合并합니다
-合并：单元格内的物体를一个 메시로合并합니다
-간소화：单元格内的物体를合并之后 메시 간소화를进行합니다
-近似：单元格内的物体를合并之后 메시近似를进行합니다

它们는分别不同的 메시类别에适用于不同하며,假如这样的分区 메시를使用한다면:

| GirdName              | Cell Size | Loading Range | Priority | BlockOnSlowStreaming |
| --------------------- | --------- | ------------- | -------- | -------------------- |
| `MainGrid`（Default） | 12800     | 25600         | 0        | false                |
| `DeferGrid`           | 25600     | 25600         | -9       | true                 |
| `AdvanceGrid`         | 51200     | 51200         | 9        | true                 |
| `SmallGrid`           | 6400      | 19200         | -9       | false                |

依此可以以下几个大类로分합니다:

-지형面片：主要地表를补充하는一些静态 메시面片（非 지형组件）로 `AdvanceGrid`에分布하며, 지형块의大小는一般 25600이 될 수 있습니다. 지형面片의 경우 `51200`의 Cell에放在하여 기하학을合并하여 HLOD를生成하며, DrawCall 및图元组件数量를减少합니다.
-普通 모델：`MainGrid`에分布하며 `12800`의 Cell에放在하여 HLOD의生成方式는小物件를剔除하여合并后 간소화或近似生成 HLOD 간소화 모델하며,多个 HLOD级别를具有할 수 있습니다.
-식물：`AdvanceGrid`에分布하며 `25600`의 HISM으로 Partition을组织하여 `51200`의 Cell에放在하여 HLOD 전략은 HISM을合并하여 `51200`大小의 ISM으로退化为합니다.
-其他：一些自定义或动态的 렌더링组件（比如粒子,水体...）은尽可能远处显示를避免하며,通常这类物品는远处显示를 위해加载距离를扩大하고 LOD를做好하거나专属的 HLOD生成 전략을定制해야 합니다.

![image-20241116120055164](../../../04-UnrealEngine/Resources/image-20241116120055164.png)

## 특수 효과

**특수 효과（Niagara）** 는非常特殊的 렌더링组件로, GPU粒子는 **Computer Shader** 를使用하여粒子运动을模拟하며,模拟的数据를粒子 렌더러에交由 **间接 렌더링（Indirect Rendering）** 을执行합니다.

粒子的优化은主要模拟 로직의复杂度减少,发射器减少,裁剪, 재질 및 OverDraw优化에在于합니다.

LOD의主要应用은 Niagara가提供하는一些引擎内置 변수를在于합니다:

![image-20241116115756142](../../../04-UnrealEngine/Resources/image-20241116115756142.png)

通常我们는 LOD의距离에 따라粒子的数量及生命周期를动态调整하여粒子의 성능消耗을优化합니다.
