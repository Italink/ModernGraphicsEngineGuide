### 파티션

월드 파티션은 **오브젝트의 바운딩 박스**에 따라 해당 오브젝트가 어느 **그리드 레벨（Grid Level）**의 **셀（Cell）**에 속하는지 결정합니다.

예를 들어 월드 파티션 영역에 다음과 같은 오브젝트가 존재하고 빨간색 영역이 그들의 **바운딩 박스（Bound）**의 **수평 면적（Area）**이라고 가정해 봅시다:

![image-20231128100717690](../../../04-UnrealEngine/Resources/image-20231128100717690.png)

### 스트리밍

장면에 새로 생성된 Actor는 기본적으로 스트리밍에 참여합니다. 즉 언로드될 수 있으며 Actor의 디테일 패널에서 관련 조정을 할 수 있습니다:

![image-20231201112501518](../../../04-UnrealEngine/Resources/image-20231201112501518.png)

- **런타임 그리드** : 해당 Actor가 속하는 월드 파티션 그리드. None인 경우 **MainGrid**에 지정됩니다.
- **공간 로드됨** : 체크하면 해당 Actor가 월드 파티션 스트리밍에 참여하고, 체크를 해제하면 해당 Actor가 장면에서 항상 로드되어 스트리밍에 참여하지 않습니다.

월드 파티션의 스트리밍은 **스트리밍 소스（Streaming Source）**에 의해 트리거됩니다.

##### 스트리밍 최적화

월드 파티션은 기본적으로 스트리밍 최적화를开启하며 매 프레임마다 스트리밍 상태를更新하지 않습니다. 다음 구성을 통해 최적화 전략을 조정할 수 있습니다:

- `wp.Runtime.UpdateStreaming.EnableOptimization true` : 기본값은 true로 스트리밍 최적화를开启합니다.
- `wp.Runtime.UpdateStreaming.ForceUpdateFrameCount 0` : 기본값은 0으로 고정된 프레임마다 스트리밍 상태를更新하도록 설정할 수 있습니다.
- `wp.Runtime.UpdateStreaming.LocationQuantization 400` : 기본값은 400으로 이동 거리가 400보다 클 때 스트리밍 상태의更新를触发합니다.
- `wp.Runtime.UpdateStreaming.RotationQuantization 10` : 기본값은 10으로 회전 각도가 10보다 클 때 스트리밍 상태의更新를触发합니다.

### 코드 흐름

개발자에게 월드 파티션의 흐름을 깊이 이해하는 것은 전체 프로젝트를 통제하는 데 매우 중요합니다! 미술人员은 건너뛸 수 있습니다.

여기에서 주요 몇 가지 단계를挑出하여 설명합니다.

UE 월드 파티션의 핵심 구조는 **UWorldPartition**입니다.

它는 **AWorldSettings**에 저장되어 있으며 다음 방법을 통해获取할 수 있습니다:

``` c++
UWorldPartition* UWorld::GetWorldPartition() const
{
	AWorldSettings* WorldSettings = GetWorldSettings(/*bCheckStreamingPersistent*/false, /*bChecked*/false);
	return WorldSettings ? WorldSettings->GetWorldPartition() : nullptr;
}
```

Actor가 월드 파티션을 지원하는 주요한 점은 Actor 기본 클래스에 **편집기下**의 가상 함수가 추가되어 월드 파티션의 Actor 설명을创建하는 것입니다:

``` c++
class AActor: public UObject
#if WITH_EDITOR
	virtual TUniquePtr<class FWorldPartitionActorDesc> CreateClassActorDesc() const;
#endif
}
```

편집기中에서创建된 모든 ActorDesc는 **UWorldPartition**의`ActorDescContainer`에存储됩니다:

``` c++
class UWorldPartition final 
    : public UObject
    , public FActorDescContainerCollection
    , public IWorldPartitionCookPackageGenerator
{

	UPROPERTY(Transient)
	TObjectPtr<UActorDescContainer> ActorDescContainer;		//ActorDesc를存储하는 컨테이너，也被称为**MainContainer**

```

`ActorDescContainer`는 임시 변수로 직렬화에参与하지 않지만 패키징时存储됩니다:

``` c++
bool UWorldPartition::GatherPackagesToCook(IWorldPartitionCookPackageContext& CookContext)
{
	TArray<FString> PackagesToCook;
	if (GenerateContainerStreaming(ActorDescContainer, &PackagesToCook))
	{
		FString PackageName = GetPackage()->GetName();
		for (const FString& PackageToCook : PackagesToCook)
		{
			CookContext.AddLevelStreamingPackageToGenerate(this, PackageName, PackageToCook);
		}
		return true;
	}
	return false;
}
```

#### 파티션 

其中 **UWorldPartition**의 Actor 파티션 분할 전략은 `RuntimeHash`에 의해实现됩니다. 편집기下에서`RuntimeHash`는 맵启动时마다重新分할을进行하며 패키징时分할 데이터를烘培합니다:

``` c++
bool UWorldPartition::PrepareGeneratorPackageForCook(IWorldPartitionCookPackageContext& CookContext, TArray<UPackage*>& OutModifiedPackages)
{
	check(RuntimeHash);
	return RuntimeHash->PrepareGeneratorPackageForCook(OutModifiedPackages);
}

bool UWorldPartition::PopulateGeneratorPackageForCook(IWorldPartitionCookPackageContext& CookContext, const TArray<FWorldPartitionCookPackage*>& InPackagesToCook, TArray<UPackage*>& OutModifiedPackages)
{
	check(RuntimeHash);
	return RuntimeHash->PopulateGeneratorPackageForCook(InPackagesToCook, OutModifiedPackages);
}

bool UWorldPartition::PopulateGeneratedPackageForCook(IWorldPartitionCookPackageContext& CookContext, const FWorldPartitionCookPackage& InPackagesToCook, TArray<UPackage*>& OutModifiedPackages)
{
	check(RuntimeHash);
	return RuntimeHash->PopulateGeneratedPackageForCook(InPackagesToCook, OutModifiedPackages);
}

UWorldPartitionRuntimeCell* UWorldPartition::GetCellForPackage(const FWorldPartitionCookPackage& PackageToCook) const
{
	check(RuntimeHash);
	return RuntimeHash->GetCellForPackage(PackageToCook);
}
```

편집기下에서 오픈 월드 맵을启动하면`UWorldPartition::OnBeginPlay`가调用됩니다:

``` c++
void UWorldPartition::OnBeginPlay()
{
	TArray<FString> OutGeneratedStreamingPackageNames;
	GenerateStreaming((bIsPIE || IsRunningGame()) ? &OutGeneratedStreamingPackageNames : nullptr);

	// Prepare GeneratedStreamingPackages
	check(GeneratedStreamingPackageNames.IsEmpty());
	for (const FString& PackageName : OutGeneratedStreamingPackageNames)
	{
		// Set as memory package to avoid wasting time in UWorldPartition::IsValidPackageName (GenerateStreaming for PIE runs on the editor world)
		FString Package = FPaths::RemoveDuplicateSlashes(FPackageName::IsMemoryPackage(PackageName) ? PackageName : TEXT("/Memory/") + PackageName);
		GeneratedStreamingPackageNames.Add(Package);
	}

	RuntimeHash->OnBeginPlay();
}
```

其中`GenerateStreaming`函数는进一步`UWorldPartition::GenerateContainerStreaming`을调用하며该函数中 **MainContainter**에서 **递归搜索出所有的Containter和ActorDesc**합니다.

일부 ActorDesc는自己的Containter를持有합니다. 예를 들어 **FLevelInstanceActorDesc**就是一个特例입니다.它는 장면에放置된关卡实例이며主要的代码定义如下:

``` c++
class FLevelInstanceActorDesc : public FWorldPartitionActorDesc
{
public:
	FLevelInstanceActorDesc();
	virtual ~FLevelInstanceActorDesc() override;

	virtual bool IsContainerInstance() const override;
	virtual bool GetContainerInstance(const UActorDescContainer*& OutLevelContainer, 
                                      FTransform& OutLevelTransform, 
                                      EContainerClusterMode& OutClusterMode) const override;
protected:
	FTransform LevelInstanceTransform;
	ELevelInstanceRuntimeBehavior DesiredRuntimeBehavior;
	TWeakObjectPtr<UActorDescContainer> LevelInstanceContainer;  //关卡实例的ActorDescContai
private:
	void RegisterContainerInstance(UWorld* InWorld);
	void UnregisterContainerInstance();
};
```

所有的Containter和ActorDesc를搜集한 후 다음을调用합니다:

``` c++
bool UWorldPartitionRuntimeSpatialHash::GenerateStreaming(UWorldPartitionStreamingPolicy* StreamingPolicy,
                                                          const IStreamingGenerationContext* StreamingGenerationContext,
                                                          TArray<FString>* OutPackagesToGenerate);
```

该函数主体流程是:

- 장면中所有的网格配置를搜集합니다. (WorldSetting中만网格配置가 있는 것이 아니라 일부 Actor也提供합니다. 예를 들어 **ASpatialHashRuntimeGridInfo**는 현재 주로 HLOD에 사용됩니다.)

-所有的ActorDesc를遍历하며 ActorDesc中的 `런타임 그리드（RuntmeGrid）`配置에 따라对应 Grid 的 **FActorSetInstance**中划分합니다.

-每个Grid의 **FActorSetInstance**에 대해 다음을调用합니다:

  ``` c++
  FSquare2DGridHelper GetPartitionedActors(const FBox& WorldBounds, 
                                           const FSpatialHashRuntimeGrid& Grid, 
                                           const TArray<const FActorSetInstance*>& ActorSetInstances)
  ```

  该Grid中的所有Actor를具体的 **셀（Cell）**中划分합니다.

### 핵심 문제

월드 파티션（World Partition）을 통해 우리는 쉽게无缝加载的大世界를实现할 수 있지만 스트리밍的特性也很多限制를带来합니다.这往往需要开发商具有更加成熟的制作团队，并配备专业的引擎团队，在设计时充分考虑到世界分区的特性，并且 **需要专业人员来监管世界分区的流送策略** 。

##### 해결方案

엔진은该现象을缓解하는 데 도움이 되는 몇 가지 명령어를提供합니다:

- `wp.Runtime.RuntimeSpatialHashUseAlignedGridLevels` :网格级别的向上对齐를开启할지 여부.
- `wp.Runtime.RuntimeSpatialHashSnapNonAlignedGridLevelsToLowerLevels` :未对齐的物体를更低的网格级别에划分합니다.
- `wp.Runtime.RuntimeSpatialHashPlaceSmallActorsUsingLocation ` :바운딩 박스가 셀尺寸보다 작은物体는直接 Location을使用하여划分합니다.
- `wp.Runtime.RuntimeSpatialHashPlacePartitionActorsUsingLocation` :바운딩 박스가 셀尺寸보다 작은分区物体（植被，水体和地形）는直接 Location을使用하여划分합니다.

#### 로드 우선순위

월드 파티션 스트리밍的缘故으로 장면中的一些运动物体에异常이出现합니다.重力是其中最常见的:

![1232265272](../../../04-UnrealEngine/Resources/1232265272.gif)

上图中存在的问题是:

- 部分立方体가一个单元格中划分되어划分算法的局限性으로 인해地面가另一个单元格中划分되어地面所在的单元格가加载范围之内에 없기 때문에物体가直接地底로掉下去습니다.

还有其他情况也会触发这个问题:

- 월드 파티션的 스트리밍은 **逐单元（Cell）**进行되는데 **逐Actor**가 아닙니다.一个单元가 스트리밍 소스의加载范围之内에 있을 때该单元的所有Actor를 **异步**地 **加载（Loading**）합니다.这个加载顺序는无法保证하기 때문에先立方体를加载하고再地面를加载하는 경우 물리 Tick을执行하는 동안物体가地面로掉下去습니다.（这在场景压力比较大时更容易出现）

##### 해결方案

这个问题을解决하는主要思路是:

- 重力承载物体所在的 월드 파티션 그리드가更大的加载范围를具有하도록 합니다.
- 重力物体를重力承载物体보다加载优先级更低的 월드 파티션 그리드中移動합니다.

#### 데이터 지속성

월드 파티션에参与的Actor는数据持久性을具有하지 않습니다.加载之后的物体에修改를进行하고卸载时修改的数据는保存되지 않습니다.

比如这个例子: 월드 파티션中有一群浮空的立方体가加载之后重力로 인해地面로掉下去고卸载之后再加载하면立方体가之前的状态를正确的保存하여地面에落在 있습니다:

![123d23422](../../../04-UnrealEngine/Resources/123d23422.gif)

但控制台指令 `gc.ForceCollectGarbageEveryFrame 1`을开启하고再来看:

![123asd23422](../../../04-UnrealEngine/Resources/123asd23422.gif)

这时重新加载立方体하면立方体会回到起始位置입니다.

第一个示例让我们产生 物体修改能被保存 的错觉는加载范围를超出한单元格가立即释放되지 않고 `Unloaded Still Around`状态에处于하기 때문입니다.这样能保证下次加载的时候可以立即复用하고真正卸载单元格的时机는下次GC时입니다.

![image-20231129112140082](../../../04-UnrealEngine/Resources/image-20231129112140082.png)

##### 해결方案

这个问题은 스트리밍的特性导致합니다:

- 流入时资产를内存에加载하고流出时资产를卸载（销毁资源）하며资产的修改를保存하지 않습니다.

那是否意味着我们需要在流出时保存资产的修改？

- 很明显不需要합니다.除非永久性的修改를进行하고 싶을 때 즉 게임을重新打开之后之前的修改가还在 있고还原할 수 없을 때입니다.

通常情况下这种修改는一定作用域（生命周期）之内에维持됩니다.比如游戏을重新进入하거나关卡를重新进入하거나存档를重新打开之后这种修改는丢失되어야 합니다.

只不过现在我们想要的是 스트리밍이数据的丢失를导致하지 않는 것입니다.

那其实只需要:

- 这部分数据가 스트리밍에参与하지 않도록 즉数据를合理的作用域에存储하고 Actor中에存하지 않는 것입니다.

UE5.3中实验性插件 **LevelStreamingPersistence**를提供하여开发者가该问题을解决하는 데帮助를 줍니다.

![image-20231204160944855](../../../04-UnrealEngine/Resources/image-20231204160944855.png)

该插件는 **ULevelStreamingPersistenceSettings**를通过하여引擎中哪些属性需要持久性을配置합니다:

![image-20231211095416739](../../../04-UnrealEngine/Resources/image-20231211095416739.png)

월드 파티션 스트리밍单元时流出的单元中具有持久性的属性를以上配置에 따라保存하고流入的单元时之前的历史值를使用하여赋值합니다:

上面的重力问题을解决하기 위해只需要我们在`DefaultEngine.ini`中如下配置를增加합니다:

``` c++
[/Script/LevelStreamingPersistence.LevelStreamingPersistenceSettings]
Properties=(Path="/Script/Engine.SceneComponent:RelativeLocation",bIsPublic=False)
Properties=(Path="/Script/Engine.SceneComponent:RelativeRotation",bIsPublic=False)
```

**PropertyPath**를通过하여哪些属性를确定하는 것은非常宽泛的范围를得到합니다.比如上面的配置는所有场景组件的位置和旋转을序列化합니다.但并非所有场景组件都需要持久化합니다.该插件也一些委托를提供하여哪些对象需要序列化를进一步筛选합니다:

![image-20231211100646090](../../../04-UnrealEngine/Resources/image-20231211100646090.png)

其中 `bIsPublic`은该属性被保存的值가手动修改될 수 있는지 여부를决定합니다.스트리밍에 따라自动序列化되는 것뿐만 아니라其中操作的接口主要位于 **ULevelStreamingPersistenceManager**中:


####  런타임生成

월드 파티션 분할은编辑器中进行되며运行时生成（Spawn）的任何物体都不会参与世界分区的流送입니다.试想一个这样的情景:

-  장면中重力를具有하는小球을 Spawn했는데它가地面에落到고角色가该区域를远离하여地面가流出时小球가地底로掉下去습니다.

这显然不是我们想要的입니다.一般情况下场景中角色之外的所有常驻物体都应该在一开始就地图关卡中放置되어야 합니다.

但有时候确实存在一些特殊的需求:

- 一些场景物体可能运行时的事件依赖가存在하기 때문에必须运行时去 生成（Spawn）해야 합니다.

##### 해결方案

- 如果物体的位置가固定不变的 경우提前在场景中占位용 Actor를放置하여 Runtime时可配置的状态로 만들 수 있습니다.
- 如果物体가一定区域에位于하는 경우该区域에 **触发器体积（Trigger Volume）**를放置하여触发器逻辑를通过하여物体的生命周期를控制할 수 있습니다.触发区域的大小가 월드 파티션的加载范围를超过하는 경우触发器体积를加载优先级更高的网格中放置하고 스트리밍 소스 컴포넌트를添加해야 합니다.

#### 캐릭터 전송

월드 파티션中에서 캐릭터 전송（传送）时 스트리밍에一定时间이需要하기 때문에 캐릭터를直接目标位置에转移하면周边物体가还没有加载完成되어角色가重力로 인해直接地底로掉下去的情况가 발생할 수 있습니다.

##### 해결方案

针对这个问题我们需要目标区域에서预加载를进行하고加载完成을等待합니다.

- 方案一: 角色 Tick을关闭하고角色를目标点에传送하여角色自身를 스트리밍 소스로 하여周边区域的 스트리밍을触发합니다. **轮询（FTSTicker）**를通过하여目标区域加载完成时 Tick을开启합니다. 매트릭스 프레임워크下也相应的参考가 있습니다:

  ![image-20231129150658814](../../../04-UnrealEngine/Resources/image-20231129150658814.png)

- 方案二: 目标位置에 스트리밍 소스 컴포넌트를带有的 Actor를 Spawn하고 스트리밍을开启합니다.轮询을通过하여加载完成을等待하고完成后角色를传送过去합니다:

  ![image-20231129151231027](../../../04-UnrealEngine/Resources/image-20231129151231027.png)

### One File Per Actor

OFPA는 팀成员가同一地图的不同Actor를共同编辑할 수 있도록 허용합니다.

传统地图는 所有Actor를 World对应的资产包中存储하는데 UE的开放世界地图는 기본적으로 [ **一Actor一文件（One File Per Actor，简称OFPA）** ](https://docs.unrealengine.com/5.3/zh-CN/one-file-per-actor-in-unreal-engine/)를启用합니다.即每个Actor都对应一个文件입니다.

这些文件는项目Content目录下`__ExternalActors__`和`__ExternalObjects__`文件夹中的对应地图路径下存储됩니다.下图는名为`OpenWorld`的地图中的所有Actor를表示합니다:

![image-20231017111331540](../../../04-UnrealEngine/Resources/image-20231017111331540.png)

我们可以场景大纲中Actor的真实文件路径를获取합니다:

![image-20231017111622364](../../../04-UnrealEngine/Resources/image-20231017111622364.png)

通常情况下所有Actor는`__ExternalActors__`中存储되고`__ExternalObjects__`는一些UObject（非Actor）对象比如各类Setting大纲分组等를存储합니다.

### HLOD

월드 파티션的 스트리밍을通过하여全场景的性能压力를 스트리밍 소스의周边区域만关注하면 되는程度로缩减할 수 있습니다:

![image-20231129151341077](../../../04-UnrealEngine/Resources/image-20231129151341077.png)

游戏逻辑而言这种 스트리밍은固然一种优化이지만场景而言我们并不希望 스트리밍으로 인해远处的场景가卸载되는 것을 원합니다.而HLOD正是为了解决这个问题입니다.

**HLOD는 월드 파티션中远景를显示하기 위한 것**입니다.开放世界地图中它的使用方式는普通地图（UE4）的HLOD와 다릅니다:

- [언리얼 엔진中的 월드 파티션 - 分层细节级别 | 언리얼 엔진 5.3 문서 (unrealengine.com)](https://docs.unrealengine.com/5.3/zh-CN/world-partition---hierarchical-level-of-detail-in-unreal-engine/)

官方文档中也HLOD相应的细节描述가缺乏합니다.它的定位를了解하지 않는小伙伴에게 HLOD를滥用하기 쉽습니다.월드 파티션中HLOD를使用하는本意는:

-  **单元格（Cell）**中 **所有Actor**를一个低精度的 单元格模型代理로合并하여单元格가 스트리밍 소스의加载范围를超出时该简模를使用하여显示합니다.这样做远景를显示하는 동시에 렌더링消耗（低精度模型和材质를使用）를减少하고遮挡剔除的计算量（Actor的数量를减少）를优化합니다.

  ![image-20231129152538095](../../../04-UnrealEngine/Resources/image-20231129152538095.png)

  ![image-20231129153201753](../../../04-UnrealEngine/Resources/image-20231129153201753.png)

我们可以此处에서整个地图的 默认（缺省）HLOD层 配置를设置합니다.它는所有Actor에生效합니다:

![image-20231027163751104](../../../04-UnrealEngine/Resources/image-20231027163751104.png)

它的资产配置面板如下:

![image-20231027164043816](../../../04-UnrealEngine/Resources/image-20231027164043816.png)

- **层类型:** HLOD를生成하기 위해何种策略를使用할지 결정합니다.
    - **实例化** :对应模型最低级别的LOD를使用합니다.（如果是Nanite模型则会该LOD를使用하여新的Nanite数据를生成합니다.）
    - **合并** :分区内的静态网格体를一起合并합니다.
    - **简化** :分区内的网格体를合并하고合并网格体的基础上网格体简化를执行합니다.它는几何形状比较复杂的物体比如枝繁叶茂的树木에更适合합니다.
    - **近似** :分区内的网格体를合并하고合并网格体的基础上网格体近似를执行합니다.它는几何形体比较圆润的物体比如建筑石头에更适合합니다.
    - **自定义** :自定义HLOD生成策略를 사용합니다.

- **已空间加载:** 生成的HLOD是否需要 스트리밍을开启할지 결정합니다.开启하면该HLOD层에 대해 HLOD Grid를创建하고生成的HLODActor를这个Grid中放置합니다.
    - **单元大小:** HLOD Grid的单元大小를配置합니다.数值는最好是Main Grid单元大小的整数倍입니다.
    - **加载范围:** HLOD Grid的加载范围를配置합니다.数值는最好是Main Grid单元大小的整数倍입니다.
    - **父层:** 生成的HLOD简模에 대해父HLOD层를使用하여再处理하여更精简的HLOD简模를生成합니다.通常它는更大的加载范围를具有합니다.

注意事项:

- 매트릭스的场景物体多是棱角分明的建筑이며统一使用了 定制的 近似网格 策略입니다.场景가更复杂的物体种类（比如树木水体植被）를具有하는 경우更细化的处理策略를定制해야 합니다.这往往非常严格的资产管理策略作为支撑가 필요합니다.此外HLOD相关代码流程和UE所提供的网格处理算法를深入了解하는 것은开放世界项目的性能优化에非常有价值합니다.
- HLOD는一个网格的单元를一个简模로合并하는 것입니다.但如果一块区域가多个网格가存在하는 경우该区域가多个简模를生成하고不同网格之间的模型가合并되지 않습니다.因此通常情况下所有场景物体都应该该MainGrid中放置되어야 합니다.只需要MainGrid中的物体에 대해 HLOD를生成합니다.小型物件의 경우加载范围가更小的网格中放置하고 HLOD的生成에参与하지 않아야 합니다.

### 데이터 레이어

데이터 레이어는 UE 5가 오픈 월드为提供하는一项功能입니다.它的用法는大纲文件夹와类似합니다:

但文件夹와不同的是它还两项关键功能를提供합니다:

- 编辑器에서 맵을打开时默认该类别的Layer를加载하지 않을 수 있습니다.
- 运行时相关接口를通过하여 Layer를 加载和卸载할 수 있습니다.

为什么需要 데이터 레이어를使用하는가?

-  데이터 레이어를利用하여 场景物体를 **类别에 따라分层**하고 **区域에 따라分块**할 수 있습니다.这样的分类를通过하여 **编辑器全场景加载的压力를缓解**할 수 있습니다.多人编辑时各个人员가自己关注的区域를选择性地加载할 수 있습니다.这는大型场景管理和多人协作中至关重要합니다.它가处理되지 않으면场景制作流程混乱的开端가 될 수 있습니다.
- 编辑器下的分类能够 **后续的场景优化에有效的依据를提供**합니다.
-  데이터 레이어는 월드 파티션 스트리밍에参与的 **子关卡**입니다.

这里有一些建议가 있습니다:

- UE는只是引擎技术的供应商입니다.它는许多优秀的技术能力和通用编辑器를提供하지만一套标准的场景制作解决方案가存在하지 않습니다.这는研发团队가大量的试错成本을耗费하여技术的积累和选型을做해야 합니다.

- 人的力量가有限的 것을明白해야 합니다.因此资产制作时最好尽可能地程序化를采用하고管控流程上尽可能自动化를使用하여合适的量化指标를寻找到场景制作流程를可追溯可迭代하게 만듭니다:
    - Houdini和UE5的PCG框架:
        - [[UE5 PCG] 官方公开课:深入研究Electric Dreams环境项目](https://link.zhihu.com/?target=https%3A//www.bilibili.com/video/BV1y8411U7Hs)
        - [Electric Dreams PCG技术详解（一）——术语、工具和图表介绍](https://link.zhihu.com/?target=https%3A//mp.weixin.qq.com/s/mGWiPKvWU_NHTktIWA6LnA)
        - [Electric Dreams PCG技术详解（二）——沟壑、大型Assembly](https://link.zhihu.com/?target=https%3A//mp.weixin.qq.com/s/xHdnrFTkywF_7OjqOuALbw)
        - [Electric Dreams PCG技术详解（三）——森林、岩石和场景背景](https://link.zhihu.com/?target=https%3A//mp.weixin.qq.com/s/YWcd8l-VphNLrOlg3zkSzA)
        - [Electric Dreams PCG技术详解（四）——远景、雾气、自定义节点及子图表](https://link.zhihu.com/?target=https%3A//mp.weixin.qq.com/s/CWTUcRIBTXw8WvhX3jrcBw)
    - [언리얼 엔진自动化系统 | 언리얼 엔진 5.3 문서 (unrealengine.com)](https://docs.unrealengine.com/5.3/zh-CN/automation-system-in-unreal-engine/)
    - [程序化生成和深度学习 | EA工作室](https://www.bilibili.com/video/BV1yh411M7pA)  
    
- 开放世界场景的性能优化는单个资产的优化와 다릅니다.本身大量需要维护的资产가存在하기 때문에人力로维护하기很难합니다.所以应该尽可能宏观上一些统一的管理策略를寻求하고一些小的优化要求를舍弃하여更大的性能平衡를换取합니다. **场景资产的分类和隔离**를做好하는 것은非常非常非常重要합니다.它는性能优化的重要依据입니다.研发团队가不同的分类에 따라相应的LOD Group Texture Group和HLOD生成策略를制定할 수 있습니다.此外一些确实特化处理가需要的资产에 대해也特化的依据（白名单）를保留해야 합니다.

- 场景制作流程가混乱하지 않는前提는每个参与者가严格场景的制作规范를遵守하는 것입니다.因此研发团队가公共的文档仓库를建立하여场景规范를公布和迭代해야 합니다. 尽可能工具를依靠하고人工로校验하지 않아야 합니다.这样人为介入产生错误的概率를很大程度地减少할 수 있습니다.非要相关人员的手动工作量를增加해야 하는 경우也最精简的数据和流程를尽可能地评估해야 합니다.

- 开放世界的场景规范는极度游戏的玩法设计에依赖합니다.只有核心角色玩法를明确한 후开发团队가与之对应的 **场景规范**를制定하고 **性能优化指标**를确立하며相应的 **工具链**를制作할 수 있습니다. 왕국之泪을 예로 들면:

    - 角色的精力（游泳攀爬滑翔）机制에 따라地形高度坡度和水体的规范를定制합니다.
    - 通天术的技能要求에 따라地形规范를定制합니다.
    - 究极手余料建造倒转乾坤这些技能的特性에 따라其要求的可交互物件를制作합니다.
    - 武器（单手剑双手剑长枪盾牌箭）가余料建造를进行할 수 있습니다.对应的插槽上特性绑定를进行하여余料物品的规范를制定합니다.
    - 已知角色的状态类别에 따라不同的场景效果比如雷击着火寒冷炎热를制作하고为之相应的解决方案（服装 or 料理）를提供합니다.
    - 核心玩法设计规范와冲突가出现하지 않는前提下 左纳乌科技的玩法를制作합니다.

    这些规范에 대해引擎开发人员가类似如下的开发工作를进行할 수 있습니다:

    - `地形可攀爬高度` `水体可穿越区域` `通天术可使用区域` 的调试视图를定制합니다.（如果UE가源码를修改하지 않고插件的形式로调试视图를扩展할 수 있으면很舒服합니다.）
    - 各种特效场景效果的性能指数를验证하고效果与性能的平衡를调校하며相应的管理和验收工具를制作합니다.

- 编辑器工具에 대해这里有一些小建议가 있습니다:
    - 尽可能问题产生的起源를追溯해야 합니다.源头에서问题를解决하는成本가最低입니다.比如说 **资产创建时（AssetCreated）** **资产保存时（AssetSaved）** **Actor创建时（NewActorsPlaced）** ...
    - 可忽略的 **通知（Notification）**를使用하고 **对话框（Dialog）**로用户输入을强制阻塞하지 않아야 합니다.
    - 友好的用户体验를提供하고撤销重做批处理自定义를支持해야 합니다.

开放世界的 **底层玩法设计** 非常重要합니다.它는 **完备的充满取巧** 的 것이어야 합니다.某一效果를达成하기 위해不合理的模块를强塞하면后续的开发工作에 **毁灭性** 的打击를给할 것입니다.

- 各种预算（时间精力金钱算力）的上限를明确한 후 **资源的调度分配**를制定해야 합니다. **取舍是必然的** 입니다.
- 如果底层玩法设计가严谨하지 않으면整个 **制作流程가混乱甚至失控** 될 수 있습니다.玩法的堆叠에 따라开放场景的 **制作难度가指数级提升** 될 것입니다.一些 **取巧** 的设计를采用하여玩法内容를收敛하지 않으면 **制作成本가很容易飙升** 될 것입니다.

두 가지 예를 들면:

- 塞尔达中底层的系统化玩法를通过하여整个游戏的玩法体系를架起하고各种模板를套用하여各种玩法的扩充를完成합니다.开发者는 模板和系统化设计 가可管控的范围之内에 있는 것을保证하고艺术家和游戏创作者가这个 **限定范围之内** 去游戏内容的衍生를做하기 때문에项目的复杂度가体量变大에 따라急剧上升하지 않습니다.

- 黑神话中 오공은 72变 을通过하여各种精英怪로变成할 수 있습니다.这一玩法设计는研发团队가更多的制作成本을精英怪的设计当中投入할 수 있도록 합니다.
