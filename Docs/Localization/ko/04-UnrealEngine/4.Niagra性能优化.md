# Niagara 성능 최적화

**Niagara**는 **Unreal Engine**에서 제공하는 거의 무엇이든 가능한 파티클 시스템으로, 특정 효과를 제작하는 방법에 대한 훌륭한 온라인 튜토리얼이 많지만 Niagara의 사용 관리와 성능 최적화는 종종 효과 제작자들이 간과하는 경향이 있습니다.

저자가 오랫동안 이 문제로 시달려왔기 때문에 이 섹션에서는 관련 내용을 보충하여,小伙伴들이 이를 이해한 후 이러한 문제가 발생하는 것을 최대한 피할 수 있기를 바랍니다=.=。

## 사용

**파티클 시스템（Particle System）**은 3D 장면에서 효과를 풍부하게 하는 중요한 수단으로, 장면의 **메시（Mesh）**와는 다릅니다. 그显著한 특징은 다음과 같습니다:

- 파티클의 **수량**이 비교적 많음
- 파티클이 시간에 따라 **운동**함

이 두 가지 특징을 만족하지 않는 경우（즉 `수량이 적고` `정적`인 경우）, 제작자는 **MeshActor**를 사용할지 파티클을 사용할지 고려해야 합니다.

UE의 효과는 주로 다음 두 가지 유형으로 나눌 수 있습니다:

- **생성 효과**：`SpawnSystemAtLocation`과 `SpawnSystemAttached`를 사용하여 장면에 **동적으로 생성**되는 효과.
- **장면 효과**：**Actor 형태로 장면에 배치**되는 효과.

이 두 유형의 효과는关注重点과相应的管理措施가 다릅니다.

### 경계 상자

게임 엔진에서는 매 프레임 이미지의 렌더링 오버헤드를 줄이기 위해 일부 보이지 않는 객체를 제거하여 GPU 렌더링에 참여하지 않도록 합니다. 다음 그림과 같습니다:

![img](../../../04-UnrealEngine/Resources/CameraCulling.gif)

> 이 이미지는 다음 출처에서 가져왔습니다: [马克·加尔维斯 - 主页 (optus23.github.io)](https://optus23.github.io/)

만약 [3D视图变换](https://zhuanlan.zhihu.com/p/597152918)를了解한다면, 카메라 행렬을 통해 객체의 모든 정점을 계산하여 객체가 카메라 범위 내에 있는지 확인할 수 있다는 것을 알 것입니다.

![img](../../../04-UnrealEngine/Resources/viewing-frustum-_frustum.fit_lim.size_768x.gif)

하지만 한 객체는 수천 개의 정점을 가질 수 있으므로, 각 정점에 대해 계산을 수행한다면 게임 엔진은 PPT 플레이어가 될 수 있습니다~

이 과정을 단순화하기 위해 게임 엔진은 객체를 감쌀 수 있는 간단한 상자를 사용하여 객체의 정점 대신 카메라 제거 계산을 수행하는 편법을 사용합니다. 상자의 정점은 적지만 가시성 판단이 정확하지 않을 수 있지만, 이로 인한 성능 향상은 매우可观합니다.

> 논리적으로 이 상자를 볼 수 있다면 해당 객체가 보이는 것으로 확신할 수 있습니다.

![image-20231007172724563](../../../04-UnrealEngine/Resources/image-20231007172724563.png)

> 객체 경계 상자 표시: `ShowFlag.Bounds 1`

따라서 다음 점을明白해야 합니다: **엔진에서 객체가 카메라 범위 내에 있는지 또는 가려져 있는지 확인할 때, 일반적으로 객체 자체의 정점 정보가 아닌 객체의 경계 상자를 참조합니다.**

**정적 메시（StaticMesh）**의 경우, 정점은 모두 정적이므로 자산 생성 시 엔진이 자동으로 경계 상자 정보를 생성합니다.

하지만 효과의 경우 파티클이 동적이므로 경계 상자를 정적으로 생성할 수 없습니다.

UE에서 **CPU 파티클**의 경우, 엔진은 매 프레임 Niagara의 경계 상자 경계를 다시 계산합니다:

<img src="Resources/cpasd.gif" alt="cpasd" style="zoom: 67%;" />



하지만 **GPU 파티클**은 구현의特殊性（모든 파티클 데이터가 GPU에 있고 파티클 수가 매우 많음）로 인해 CPU 측에서 파티클의 경계 상자를 실시간으로 계산할 수 없으므로, 개발자는 **반드시** **고정 경계**를 설정해야 합니다. 즉 경계 상자의 크기를 수동으로 설정해야 합니다.

> GPU 파티클은 GPU 기반의 렌더링 파이프라인으로, 전 과정에서 CPU와의 상호작용이 거의 없습니다. 그래픽 렌더링 파이프라인 데이터는 대부분 CPU->GPU의 단방향으로 볼 수 있으며, GPU에서 데이터를 읽어올 수는 있지만 이 과정에는 일정한 지연이 발생하고 성능 비용이 매우 높습니다.）

Niagara에서 **파티클 발사체**의 경계 상자를 설정할 수 있습니다:

![image-20231007175720103](../../../04-UnrealEngine/Resources/image-20231007175720103.png)

- 효과의 경계 상자가 실제 운동 공간과 일치하지 않으면 잘못된 시각적 클리핑이 발생합니다:

### 생명 주기

**장면 효과**의 경우, 생명 주기는 장면이 Actor 수준에서 관리하므로 일반적으로我们가关心할 필요가 없습니다. 하지만 **생성 효과**의 생명 주기 관리에는我们가必须了解的细节가 있습니다:

**생성 효과**는 **UNiagaraFunctionLibrary**의 몇 가지 함수를 사용하여 생성되는 효과를指합니다:

``` c++
UNiagaraComponent* SpawnSystemAtLocation(const UObject* WorldContextObject,
                                         class UNiagaraSystem* SystemTemplate, 
                                         FVector Location, 
                                         FRotator Rotation = FRotator::ZeroRotator,
                                         FVector Scale = FVector(1.f), 
                                         bool bAutoDestroy = true,
                                         bool bAutoActivate = true, 
                                         ENCPoolMethod PoolingMethod = ENCPoolMethod::None,
                                         bool bPreCullCheck = true);

UNiagaraComponent* SpawnSystemAttached(UNiagaraSystem* SystemTemplate,
                                       USceneComponent* AttachToComponent,
                                       FName AttachPointName,
                                       FVector Location, 
                                       FRotator Rotation,
                                       FVector Scale, 
                                       EAttachLocation::Type LocationType, 
                                       bool bAutoDestroy, 
                                       ENCPoolMethod PoolingMethod, 
                                       bool bAutoActivate = true,
                                       bool bPreCullCheck = true);
```

**SpawnSystemAtLocation**은 지정된 위치에 파티클 컴포넌트를 생성하는 데 사용되고, **SpawnSystemAttached**는 다른 장면 컴포넌트에附着하는 데 사용됩니다. 생명 주기에 대해我们가主要关注해야 할 매개변수는 다음과 같습니다:

- **bAutoActivate**：자동 활성화 여부. true는 즉시 파티클 효과를 재생함을 의미합니다.
- **bAutoDestroy**：자동 파괴 여부. true는 파티클 재생 완료 후 컴포넌트를 파괴합니다.
- **bPreCullCheck**：사전 클리핑. true인 경우 생성된 파티클 시스템의 경계 상자가 시야 절두체 범위 내에 없으면 파티클 컴포넌트가 생성되지 않고 null을 반환합니다.
- **PoolingMethod**：풀 작업. 파티클 컴포넌트를 재사용하는 메커니즘. 값은 다음과 같습니다:
  - **None**
  - **AutoRelease**：자동 릴리스. 재생이 완료되면 자동으로 효과 풀에 저장하여 재사용합니다.
  - **ManualRelease**：수동 릴리스. **ReleaseToPool**을 수동으로 호출해야 해당 파티클 컴포넌트가 재사용됩니다.
  - ManualRelease_OnComplete：비공개 옵션. Niagara 내부 상태 제어에 사용되므로 사용하지 마십시오.
  - FreeInPool：비공개 옵션. Niagara 내부 상태 제어에 사용되므로 사용하지 마십시오.

#### 효과 풀

> 자세한 메커니즘은 다음 문서를 참조하십시오: [【UE4】特效池 - 知乎 (zhihu.com)](https://zhuanlan.zhihu.com/p/394772587)

##### 캐시 메커니즘

효과 풀의 목적은 주로 파티클 컴포넌트를 재사용할 수 있도록 하는 것입니다. 그 캐시 메커니즘은 다음과 같이 볼 수 있습니다:

- 생성 매개변수에 풀 작업（즉 `PoolingMethod != ENCPoolMethod::None`）이 포함된 경우, Niagara는 효과 풀에서 재사용 가능한 동일한 유형의 컴포넌트를 검색합니다. 있으면 이를 사용하고, 없으면 새 파티클 컴포넌트를 생성하고 사용 시간을 기록합니다.
- 새로 생성된 파티클 컴포넌트는释放되지 않습니다（**bAutoDestroy가 무효화됨을 의미합니다**）. 효과 풀에 저장되어 관리됩니다.
- **AutoRelease** 파티클 컴포넌트의 경우, 재생이 완료되면 효과 풀이 재사용 가능으로 표시합니다.
- **ManualRelease** 파티클 컴포넌트의 경우, **ReleaseToPool**을 호출하면 파티클이 재생 완료된 경우 즉시 재사용 가능으로 표시하고, 그렇지 않으면 풀 작업을 **ManualRelease_OnComplete**로修改하여 재생 완료 시 재사용 가능으로 표시합니다.

##### 정리 방식

**UNiagaraComponentPool**은定时清理 메커니즘을 가지고 있습니다. 두 가지 주요 매개변수는 다음과 같습니다:

- **GNiagaraSystemPoolKillUnusedTime**：기본값은 180입니다.
- **GNiagaraSystemPoolingCleanTime**：기본값은 30입니다.

위 구성에 해당하는 자동 정리 메커니즘은 대략 다음과 같습니다: UNiagaraComponentPool은 30초마다 180초 이상 재사용되지 않은 파티클 컴포넌트를 정리합니다.

> 실제로 Tick으로 정리하는 것이 아니라 매 재사용 시 정리하므로 30초가 아닐 수 있으며 편차가比较大할 수 있습니다.

World를切换할 때 **UNiagaraComponentPool**은 Cleanup을执行합니다.

**UNiagaraComponentPool::ClearPool(UNiagaraSystem* System)**을手动으로 호출하여 정리할 수도 있습니다.

#### 함정

- 풀 작업（**PoolingMethod**）이 있는 경우 **bAutoDestroy**가 무효화됩니다.
- 풀 메커니즘이正常工作的前提是 파티클 시스템이 재생을 완료할 수 있다는 것입니다. 다음을注意하십시오:
  - 파티클 시스템에 생명 주기가无限인 발사체가 없도록确保하십시오.
  - ResetParticles(true)를 호출하면 Complete에 도달하지 못합니다.
  - 확장 가능한 클리핑의 **클리핑 반응이休眠**인 경우, **클리핑된 효과는 재사용되지 않으며** **OnSystemFinished가触发되지 않습니다**（엄격히 말해 완료된 것이 아님）.
- 풀 작업이 있는 파티클 컴포넌트에는 **DestoryComponent를 호출하지 마십시오**. 풀의 파티클 컴포넌트는 World切换时 정리되거나定时 정리됩니다.
- **SpawnSystemAttached**에 풀 작업이 포함된 경우, 새로 생성된 파티클 컴포넌트의 **실제 소유자는 World이며附着된 컴포넌트가 아닙니다**. 파티클 컴포넌트는 **附着된 컴포넌트가 파괴되어도 파괴되지 않습니다**.
- **AutoRelease** 파티클 컴포넌트에 **ReleaseToPool을 호출하면 오류가 발생합니다**.
- **AutoRelease**도开启하지 않고 풀 작업도 없는 파티클의 경우, 생명 주기를严格하게 관리해야 합니다.

### 확장성

경계 상자를 설정하여 **시각적으로** 파티클을 제거할 수 있지만, 파티클 시스템은 일반적인 장면 객체와不同하여 **模拟 비용**도 있음을注意해야 합니다!

이것은 현재 많은 효과 디자이너가 Niagara를 사용할 때容易忽略하는 문제입니다. 많은小伙伴들은 파티클이 보이지 않을 때 파티클이停止한다고 생각하지만 실제로는 그렇지 않습니다. 여전히 다음을执行합니다:

![dasd](../../../04-UnrealEngine/Resources/dasd.gif)

생성 효과의 경우一定的 생명 주기를 가지므로 대부분의 경우模拟消耗가无关痛痒합니다.

하지만 장면 효과의 경우, 장면에布置된 NiagaraActor 수가过多하면整个程序에 큰影响를 미칩니다.

이 문제를解决하기 위해 UE는 **효과 유형（NiagaraEffectType）**이라는 자산을提供하여 Niagara System **模拟의 최적화 전략**을控制합니다.

![image-20231007193640734](../../../04-UnrealEngine/Resources/image-20231007193640734.png)

여기에서 NiagaraSystem이使用할 효과 유형을指定할 수 있습니다:

![image-20231007193928904](../../../04-UnrealEngine/Resources/image-20231007193928904.png)

이를 사용하여 다음需求을完成할 수 있습니다:

- 파티클 시스템의最远显示距离를限定합니다.
- 현재视口内显示的最大 파티클 시스템 수를限制합니다.
- 성능 예산에 따라 파티클 효과를调整합니다.
- 발사체 발사 수의缩放 계수를调整합니다.

구성 패널은 다음과 같습니다:

![image-20231007194409696](../../../04-UnrealEngine/Resources/image-20231007194409696.png)

시스템 및 발사체 확장성 구성을添加할 수 있으며, 각 구성은不同性能级别에서采取할 확장성 전략에对应합니다:

![image-20231007194552208](../../../04-UnrealEngine/Resources/image-20231007194552208.png)

매개변수의意义는 다음과 같습니다:

- 로컬 플레이어에 대해 클리핑 실행: 로컬 플레이어가生成、附着、创建한 효과를 클리핑할 수 있는지 여부.

- 更新频率: `仅生成`、`低`、`中`、`高`、`连续`

  **NiagaraEffectType**과 **NiagaraComponent**는 모두 **NiagaraWorldManager**에 의해管理됩니다. **NiagaraEffectType**은单独进行Tick하며,这里的更新频率는 **NiagaraSystem**의当前状态를检测하는频率를指합니다.频率가越高，클리핑 반응이越及时，但性能 오버헤드也越大합니다.

- 클리핑 반응: `摧毁`、`摧毁并清除`、`休眠`、`休眠并清除`

  清除는 즉시所有 파티클을杀死한 후 NiagaraSystem을剔除합니다.清除하지 않으면新 파티클이生成되지 않고已存在 파티클의 생명 주기가全部结束된 후剔除합니다.

  摧毁와休眠的区别는摧毁는直接 파티클을销毁하는 반면,休眠은只是 파티클을隐藏하고激活을等待하는 것입니다.

  장면 효과의 경우 장면에放置된 Actor이므로销毁后再生成되지 않으므로一般休眠으로设置합니다.具体的销毁和加载은大世界에 의해管理됩니다.

  생성 효과의 경우一般一次性生成되므로休眠으로设置하면内存을一直占用하므로一般摧毁로设置합니다.

  UE 5.3에서는 `暂停` 메커니즘이添加되었습니다.休眠과的区别는暂停은重新激活되지 않고 파티클의当前数据를保留（内存占用）합니다.

- 중요性处理器: `年龄`、`距离`

  重要性处理器는主로下方的 **最大系统实例**와有关합니다.最大系统代理는当前同类型 파티클 시스템의实例 수를多少个만允许할지决定하며,重要性处理器는 파티클排序的优先级를确定합니다.例如距离를目标으로 하여 10개의 파티클 시스템이 있고最大系统实例가 5인 경우, **NiagaraEffectType**은最近的 5개의 파티클 효과만保留합니다.

- 시스템 확장성设置

  **设置列表**，每添加一个设置项，该设置项이哪些环境下生效할지配置할 수 있습니다.

  ![image-20231007194731440](../../../04-UnrealEngine/Resources/image-20231007194731440.png)

  - 最大距离: 효과와当前 플레이어의距离에 따라 파티클을剔除합니다.

  - 클리핑代理模式: `已实例化渲染`，**已实例化渲染**를开启하면不可见的 파티클 시스템을创建하여其他所有被剔除的同类型 파티클 시스템이它를使用하여渲染합니다.这样可以大量的模拟 비용을避免합니다.

  - 最大系统代理:最大系统代理数.

  - 预算调整:一定的预算에 따라 파티클 시스템의 확장성 전략을调整합니다.
  - 可视性剔除:可视性에 따라剔除합니다.

> 具体的说明은编辑器面板의 Tooltip을参考하십시오.

### 발사체 수 관리

理想的情况는 두 발사체가使用하는 렌더러 매개변수가完全一致하면同一个 발사체를使用해야 한다는 것입니다.

因为 발사체의一个 렌더러는一条图形 렌더링 파이프라인에对应하며, 파티클 시스템은本质上图形 렌더링 파이프라인에 필요한实例化 데이터를处理하는 것입니다.

발사체가多一个就多一份 렌더링 데이터가增加되며,一个 파티클 버퍼를多维护해야 합니다.

只是 파티클의运动机制을调整하려는 경우,自定义 Module을通过하여扩展할 수 있습니다.

### CPU 파티클과 GPU 파티클界定

CPU 파티클:少量的 파티클 렌더링에适합합니다.数据가 CPU에位于하므로整个 장면的信息를获取할 수 있으며游戏逻辑과的交互가方便하고, 파티클间的事件通信,精准的物理碰撞을支持하며,动态地 경계 상자 경계를计算할 수 있습니다.

GPU 파티클:非常低的性能损耗를 가지며大量（十万级别）的 파티클 렌더링에适合합니다.

界定时首先考虑的维度는 파티클 수입니다. 파티클 수가非常少（例如几个或几十个）的 경우, GPU의调度 오버헤드를几个 파티클 위해增加할 필요가 없으므로最好 CPU 파티클을使用합니다.

수가一千을超过하는 경우,功能需求에 CPU 파티클의特性을用到是否需要하는지考虑합니다.需要하지 않는 경우优先 GPU 파티클을使用합니다.

파티클 수가非常多但 CPU 파티클의特性을使用해야 하는 경우,较低级别的代码维度에서 GPU 파티클의功能을扩展해야 합니다.

#### 问题及建议

- Unreal Engine 5.1版本之前 Niagara System은 **재컴파일 BUG**가存在합니다.表现效果는游戏中首次 파티클을生成时整个 파티클 시스템의 재컴파일을触发하는 것입니다.这是因为 Niagara System Editor에서资源保存을进行하여游戏模式下与不同的一些配置를存储하여 파티클 시스템의 HashID가不一致하여 컴파일 캐시의失效를引起하기 때문입니다.因此游戏环境中的 파티클 시스템의执行性能을评估해야 하는 경우,笔者는打包环境下测试를建议합니다.
- Unreal Engine은 Niagara에非常完善的配套工具을提供하지만大型团队而言易于使用하지만管理하기不易합니다.笔者는上述工具集的基础上进一步扩展하여自动化流程을增加하여宏观的 파티클 시스템管理을完成하는 것을非常建议합니다.
-材质 최적화,模型简化, Overdraw降低等一些常规的 렌더링 최적화는 Niagara에도同样适用합니다.

### 제작 최적화

亡羊补牢的过程中总结出来的 최적화经验은弥足珍贵합니다.它能让 제작人员逐渐地性能卓越的 파티클特效을制作하는 방법을了解하게 합니다.

以下는特效师의 제작 최적화를帮助할 수 있는一些心得입니다（主要 GPU 파티클에针对）.

#### 연산력 인지

`1920 x 1080`은当下电脑显示器의常见分辨率입니다.这代表屏幕上有将近 **两百万** 个像素点이 있으며,电脑이一帧图像를绘制하는 데至少两百万次의像素级别的数值处理를做해야 함을意味着합니다.目前一些中端硬件设备上一秒内成百上千张图像를轻易绘制할 수 있으며,这惊人的 연산력은图形处理单元（GPU）的高速发展에得益于합니다.中央处理单元（CPU）와不同的是 CPU는电脑的调度中心로架构가系统的方方面面을兼顾해야 하지만, GPU는剑走偏锋的做法로大量的计算单元을架构에塞入하여图形运算의需求를满足합니다.

> 当下尖端的消费级显卡 `GeForce RTX 4090`을 예로 들어七百六十多亿个晶体管,一万六千多个计算核心을具有합니다.

![GPU VS CPU](../../../04-UnrealEngine/Resources/format,png.png)

这个上限을清楚한 후我们는简单하게 `单个 GPU 파티클`을 `像素点`과对应할 수 있습니다.也就是通常情况下中端显卡也能轻松百万级别数量的 파티클 효과를模拟할 수 있습니다.

但需要注意的是百万级别는通常整个系统的上限이며我们는所有性能预算을 파티클 시스템에留给不可能합니다.因此一般情况下整体的 파티클 수가十万을超过하면整个 렌더링系统에性能压力를造成할 수 있습니다.

这十万 파티클을对应数量的`1x1`像素点으로平铺하면大约 `300x300`尺寸大小的图像에对应합니다:

![image-20231008104748978](../../../04-UnrealEngine/Resources/image-20231008104748978.png)

파티클 시스템의 **占屏面积**이 **平铺面积**에越接近则 OverDraw가越少므로性能이越好다는 것을意味着합니다.

####程序化内容生成

파티클 시스템은主要 **大量** **动态** 的物体를模拟하는 데 **适用**합니다.但一些特定需求下만我们는不得不 파티클 시스템을使用하여 **实时的模拟**을进行해야 합니다:

-可交互的动态效果制作
-无视觉死角的立体效果营造需要
-非常大数量的大范围集群

以上的使用场景을排除하면我们는通常 **静态材质烘培**을通过하여想要的表现效果를达到할 수 있습니다.

因此我们는 파티클效果制作时实时的模拟을进行하기 위해 파티클 시스템을使用해야 하는지认真审视해야 합니다.

如果要的话那么我们는再思考합니다: 파티클 시스템中某些实时计算的阶段을已经预制的静态数据로换成是否可以的지.

例如场景相关的特效制作时, 파티클的模拟은一些场景信息을输入으로需要할 수 있으며,这些场景数据的绝大多数情况下都是静态的입니다.我们는运行时에实时으로场景的相关信息을计算할必要가 없으며编辑器中静态으로这些数据를生成할 수 있습니다.这样较少的性能成本으로场景와高度融合的特效을制作할 수 있으며,这는 파티클 시스템 수가比较多的情况下提升이尤为明显합니다.

我们는 또한 Niagara上程序化内容生成（PCG）的 자산을制作할 수 있습니다:

- **Niagara System**의 **用户参数（User Parameters）**中 파티클 시스템所需要的场景数据를添加합니다（这里 `SpawnPositionArray`라는 변수를添加）:

![image-20231008115550644](../../../04-UnrealEngine/Resources/image-20231008115550644.png)

-新的 **Actor 蓝图**를创建하여 **NiagaraComponent**를添加하고 **Niagara System**을指定합니다.

-蓝图的 **BeginPlay**事件中我们在 Niagara中添加的参数를设置하고参数输入을 `提升为变量`（`Partcile Spawn Position Array`）:

  ![image-20231008114722968](../../../04-UnrealEngine/Resources/image-20231008114722968.png)

-蓝图中一个函数（例如 `CalcParticleSpawnPositionArray`라 부름）을添加하고 **Call In Editor**를勾选합니다.这个函数中场景信息을获取（性能을关心할 필요 없으며 Actor扫描,射线打... 가능）하여蓝图变量值（`Partcile Spawn Position Array`）을填充합니다:

  ![image-20231008115241436](../../../04-UnrealEngine/Resources/image-20231008115241436.png)

- Actor蓝图를 장면中放到하면细节面板中之前创建的函数이可点击的按钮으로变成될 수 있습니다:

  ![image-20231008115733236](../../../04-UnrealEngine/Resources/image-20231008115733236.png)

-按钮을点击하면对应的函数逻辑을执行할 것입니다.它将会执行并蓝图属性을填充하며,这些属性值은保存时序列化될 것입니다.正常游戏启动时 BeginPlay를执行하여这些数据를 Niagara에提交할 것입니다.

-之后 Niagara中相应的 Module을编写하여这部分数据를使用할 수 있습니다.

> 需要注意的是 `CalcParticleSpawnPositionArray`中直接 Niagara的参数值을设置하지 않고蓝图的变量属性序列化을借助하여场景数据를存储해야 합니다.
>
> 这是因为 Niagara参数设置函数（`NiagaraSet...`으로开头）은直接数据를 Niagara的数据处理器에上传하며存储를进行하지 않기 때문입니다.因此函数를通过하여 Niagara参数를设置하면 NiagaraSystem的细节面板上参数发生变化를不一定能看到합니다（有一部分属性类型은编辑器数据的返回同步을做了所以细节面板上变更를看到能）.
