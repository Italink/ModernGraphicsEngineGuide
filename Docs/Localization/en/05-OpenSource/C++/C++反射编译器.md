# C++ Reflection Compiler

- GitHub Repository: https://github.com/Italink/XObject

## Build

- Can be built directly using CMake (GUI)

## Brief Project Structure

- Core: Core module
  - 3rdParty: Third-party libraries
  - XHT: Code scanning tool
  - Test: Directory for module function test projects
  - XObject: Base class encapsulation

## Brief Logic

### Base Class XObject

XObject serves as the base class for all objects, providing operations such as serialization and reflection.

### Reflection

The library used for reflection is Rttr, an excellent C++ reflection library. It not only enables simple type information reflection but also provides a complete set of reflection processing interfaces:

- rttr::variant: Similar to stl::any but more powerful, offering numerous type information and conversion interfaces (e.g., an int-type variant can be directly exported as double, which invokes the int-to-double conversion interface; custom variant type conversion functions can be defined in rttr).
- Supports creating corresponding instances based on type names, with three creation modes (Type, Type\*, std::shared_ptr\<Type\*>).
- Metadata is used to append information, allowing many additional details to be added to properties via this feature.

XHT is used for code scanning (referencing QtMoc), completing automatic type registration through macro markers, which solves the problem of RTTR requiring manual registration function writing.

> XHT may seem dispensable—writing registration functions manually is certainly possible—but there are better reasons to use it:
>
> - Not only RTTR requires registration functions; other features involving adding attachments to types (such as serialization) also need them. For the current XObject, an h-file containing two simple classes would generate nearly a hundred lines of additional code via XHT. This code requires a fixed format and is tedious to write manually.
> - XHT is less error-prone; only generation rules need to be defined.
> - When the original class is modified, XHT automatically synchronizes changes to the additional code without manual intervention.

## XHT Working Mode

- XObject.h: Defines macros whose markers will be captured by XHT

  ```C++
  #define XENTRY(...) \
  public: \
      static XMetaObject* staticMetaObject(); \
      virtual XMetaObject* metaObject() override; \
      virtual rttr::instance instance() override { return *this; } \
      using base_class_list = rttr::type_list<__VA_ARGS__>; \
  	virtual void __intrusive_deserialize(Deserializer& deserializer) override; \
      virtual void __intrusive_serialize(Serializer& serializer) override; \
      virtual void __intrusive_to_json(nlohmann::json& json) const override; \
  private:
  
  #define XFUNCTION(...)
  #define XPROPERTY(...)
  #define XENUM(...)
  
  ```

XHT is a standalone command-line project with the following parameter format:

```
AxHeadeTool ${input_file} -o ${output_dir} 
Options:
-i include_dir: Include path for input files
```

This tool scans files, collects their symbol information, and generates new files. Refer to main.cpp for the processing flow.

### Customization Process

#### Define Keywords

XHT efficiently parses file content into symbol strings using a keyword lookup table. The table content is located in `Keywords.inl`, which is automatically generated by the `KeywordsGen` project. This project defines all keywords used in XHT.

```C++
static const Keyword pp_keywords[] = {...}   // Preprocessing keywords	
static const Keyword keywords[] = {
	{ "<", "LANGLE" },
	{ ">", "RANGLE" },
	...
	
	{ "XENTRY","XENTRY_TOKEN"},
	{ "XFUNCTION","XFUNCTION_TOKEN"},
	{ "XPROPERTY","XPROPERTY_TOKEN"},
	{ "XENUM","XENUM_TOKEN"},
	...
	};
```

Each keyword contains two parameters. Taking `{ "XENTRY","XENTRY_TOKEN"}` as an example: `XENTRY` represents the exact symbol in the code file, and `XENTRY_TOKEN` corresponds to the enumeration used in XHT. The enumeration definition is located in XHT's `Token.h` file:

```C++
#define FOR_ALL_TOKENS(F) \
    F(NOTOKEN) \
    F(IDENTIFIER) \
    ...
    F(XENTRY_TOKEN) \
    F(XFUNCTION_TOKEN) \
    F(XPROPERTY_TOKEN) \
    F(XENUM_TOKEN) \
    ...
```

Therefore, defining a keyword requires the following steps:

- Add a new keyword entry `{symbol, enum_element}` in the **KeywordsGen project**.
- Run the **KeywordsGen project** to automatically generate `Keywords.inl` in XHT's code directory.
- Define the `enum_element` in the `Token.h` file of the **XHT project**.

#### Write Collectors

There's no need to concern yourself with the **FileParser** process unless you need to handle include and macro-related operations. The only thing to note is the `bool parse(FileDataDef&, const Symbols&)` function in **SymbolParser**.

The main hierarchical structure of the switch in the parser is as follows:

- Top-level switch: Collects global file information
  - namespace: Collects namespace information
    - ...
  - class/struct: Collects class information
    - ...
  - ...

Checking the code reveals that the class contains `case AX_INVOKABLE_TOKEN` and `case AX_PROPERTY_TOKEN`.

Taking `XPROPERTY_TOKEN` as an example, its role is to mark variables in the following format:

```
XPROPERTY(GET getX SET setX)	// Where GET and SET specify the get and set functions for the variable 
int var;
```

Returning to **SymbolParser**, you can see that this case actually calls the function `parseAxProperty()`:

```c++
case XPROPERTY_TOKEN:
	def.propertyList.push_back(parseXProperty());
break;
```

The function definition is as follows:

```c++
void SymbolParser::parseXProperty()
{
    PropertyDef axVarDef;				// Define the data structure for Property
    next(LPAREN);						// Move to the next symbol and check if it's a left parenthesis
    while (test(IDENTIFIER)) {	    	// Check if it's an identifier (non-keyword)
        std::string type = lexem(); 	// Get the symbol string
        if (type == "GET") {			// Check if the obtained character is GET or SET
            next();						// Move to the next symbol
            axVarDef.getter = lexem();  // Save the symbol
        }
        else if (type == "SET") {
            next();	
            axVarDef.setter = lexem();
        }
    }
    next(RPAREN);						// Move to the next symbol and check if it's a right parenthesis
    axVarDef.type = parseType();		// Parse the variable type
    next(IDENTIFIER);					// Move to the next symbol and check if it's an identifier
    axVarDef.name = lexem();			// Get the variable name
    until(SEMIC);						// Move backward until a semicolon is matched
    return axVarDef;
}
```

All data structures are defined in the `DataDef.h` file.

Therefore, to complete information collection, the general steps are as follows:

- Define the data you want to collect in `DataDef.h`.
- Add a case in the appropriate place in `SymbolParser::parser`.
- Write a symbol parsing function, using the convenient methods provided by **Parser** to complete information collection.

  - Basic functions

    ```c++
    class ParserBase{
    ```

## Automatic Build

With **XHT**, files can only be processed manually via the command line. What if you want to automatically call **XHT** to process code files in a project?

This is implemented in the **CMakeLists.txt** of **XObject**:

```cmake
function(target_xht_warp PROJECT_TARGET INPUT_FILE_PATH)            
    get_filename_component(INPUT_FILE_NAME ${INPUT_FILE_PATH} NAME_WE)               # Get the filename without extension
    set(OUTPUT_FILE_PATH ${CMAKE_CURRENT_BINARY_DIR}/AutoGenFiles/XHT_${INPUT_FILE_NAME}.cpp)   
    add_custom_command(
        OUTPUT ${OUTPUT_FILE_PATH}                                                   # Specify the output file
        COMMAND XHT ${CMAKE_CURRENT_SOURCE_DIR}/${INPUT_FILE_PATH} -o ${OUTPUT_FILE_PATH}  # Command-line instruction
        MAIN_DEPENDENCY ${INPUT_FILE_PATH}                           # Specify dependencies; automatically invoke the instruction when the file changes
    )          
    set_property(TARGET ${PROJECT_TARGET} APPEND PROPERTY SOURCES ${OUTPUT_FILE_PATH})       # Add to the build target
    source_group("Generated Files" FILES ${OUTPUT_FILE_PATH})                                # File grouping
endfunction()
```

This function processes a single file, automatically generates additional code, and includes it in the project build.

Can we automatically call HeaderTool when certain symbols are detected in code files, similar to UE or Qt? The answer is yes. CMake provides the following function to check if code files contain certain symbols:

[ **check_cxx_symbol_exists** ](https://cmake.org/cmake/help/latest/module/CheckCXXSymbolExists.html)

However, this process is actually inefficient as it requires traversing the entire file. A better approach is to identify which files need HeaderTool processing via file extensions. The CMakeLists of XObject also provides the following function:

```cmake
function(target_xht_auto PROJECT_TARGET)
    get_target_property(TARGET_SOURCES ${PROJECT_TARGET} SOURCES)
    message(WARNING "FILES ${TARGET_SOURCES}")
    foreach(FILE ${TARGET_SOURCES})
        get_filename_component(FILE_EXT ${FILE} EXT)     
        if(FILE_EXT STREQUAL ".hxx")
            target_xht_warp(${PROJECT_TARGET} ${FILE})
        endif()
    endforeach()
endfunction()
```

#### Some Issues

##### Inheritance

Rttr uses templates to register reflection types. Inheritance handling is implemented via template metaprogramming (when a subclass calls a parent class function, it retrieves the parent class based on `using base_class_list = rttr::type_list<...>` defined in the subclass). Therefore, this definition must be written in the header file to ensure visibility to subclasses. This requires manually specifying the parent class again during reflection marking, like this:

```C++
class Base : public XObject {
	XENTRY(XObject) 					// Must specify the parent class here; otherwise, Rttr cannot determine the inheritance relationship
}
```

##### Pointer Decay

In Rttr, you cannot use a parent class pointer to call a subclass method. For example, the following code:

```c++
XObject* x = new Base;					// Base contains the print method
rttr::invoke(x,"print");				// Call fails because Rttr cannot determine the real type of x
```

XObject adds the following definition in the `XEntry()` macro:

```c++
virtual rttr::instance instance() override { return *this; } 
```

This provides a virtual function for XObject subclasses to obtain an rttr instance, avoiding the above pointer issue. The call looks like this:

```C++
XObject* x = new Base;
rttr::invoke(x->instance(),"print");	// Call succeeds
```

##### Registration Timing

The official approach is static registration, whose principle can be simplified as follows:

```c++
// Located in CPP
struct Register{
	Register(){
		// Perform RTTR type registration here
	}
};
static Register register;
```

Explanation: RTTR creates a struct in CPP, writes the registration function in the struct's constructor, and then creates a static instance to complete type registration.

This approach has the following main issues:

- Registration order is difficult to control.
- Registering all reflection types at once can cause program startup lag.

To solve this problem, XObject adds the **XMetaObject** class, whose structure is similar to the above `Register` (i.e., Rttr registration code is located in its constructor). The difference is that we do not directly create a static instance of XMetaObject in cpp, but instead implement it as follows:

```C++
class XObject{
	static XMetaObject* staticMetaObject(){
        static XMetaObject instance;
        return &instance;
    }
}
```

The static instance inside is only created when the `staticMetaObject()` function is first accessed. Additionally, since XObject uses XMetaObject as the only entry for reflection data, Rttr registration is automatically performed when using the reflection interface of that type.

Here's another detail:

When using a subclass reflection interface to call a parent class interface, you need to ensure the parent class has been registered.

To achieve this, XObject calls the parent class's `staticMetaObject` once in the constructor of the subclass MetaObject to ensure the parent class is registered in advance.

> ### Meta Object
>
> The above mentioned XMetaObject. Here's a brief explanation of how XObject uses it as the only reflection entry for a type.
>
> Reflection is mainly used for the following purposes:
>
> - Read/write properties and obtain property information (type, metadata, etc.)
> - Call functions and obtain function information (parameter information, etc.)
> - Create instances based on type names
>
> XMetaObject is type-related and instance-independent. It is only used to obtain reflection data. Part of its code is as follows:
>
> ```C++
> struct XMetaObject {
> public:
> 	XMetaObject();
> 	XObject* newInstance(std::vector<rttr::argument> args = {});	// Create instance
> 	rttr::property getProperty(std::string name);					// Get the property named "name"
> 	rttr::array_range<rttr::property> getProperties();				// Get all properties of the type
> 	rttr::method getMethod(std::string name);						// Get the method named "name"
> 	rttr::array_range<rttr::method> getMethods();					// Get all methods of the type
> };
> ```
>
> Calling functions is instance-related. To call a function, you must provide an instance. This operation looks like this:
>
> ```c++
> Base* base = new Base;
> XMetaObject* meta = Base::staticMetaObject();			// Get the static meta object of Base
> rttr::method method = meta->getMethod("print");			// Get information about Base's print function
> method.invoke(base);  									// Provide an instance when calling
> ```
>
> As we all know, a weakened pointer type cannot call static functions of the actual type, i.e.:
>
> ```c++
> XObejct *x = new Base;
> x->staticMetaObject();		// This will call XObject::staticMetaObject() instead of Base::staticMetaObject()
> ```
>
> To solve this problem, the `XEntry()` macro adds the following definition:
>
> ```C++
> virtual XMetaObject* metaObject() override { return staticMetaObject(); }
> ```
>
> Additionally, searching the type pool by type name in Rttr is expensive. To solve this problem, XMetaObject provides an additional virtual function for binding MetaObject to rttr::type:
>
> ```c++
> virtual rttr::type getRttrType() { return rttr::type::get<void>(); };	
> ```
>
> When XHT generates the Rttr registration function, it also generates the definition of this function, which returns a determined rttr::type.
>
> Based on the meta object interface, XObject also provides some instance-related reflection interfaces:
>
> ```C++
> bool setProperty(std::string name, rttr::argument var);		// Set property
> rttr::variant getProperty(std::string name);				// Get property
> rttr::variant invoke(rttr::string_view name, std::vector<rttr::argument> args = {});		// Call function
> ```

### Serialization

Serialization is not difficult if you write the serialization functions manually, but if you want automatic serialization, you face the following challenges:

- Serialization of custom types
- Serialization of complex types (containers)
- Deserialization of pointers
- Runtime error checking for deserialization

Different serialization purposes require different handling methods:

- Binary serialization has the best performance and memory efficiency, but its content is difficult to read.
- Non-binary serialization (e.g., xml, json, cbor) has an elegant storage structure and strong readability, but with relatively higher performance and memory overhead.

#### Binary

The library used for binary serialization is [BitSery](https://github.com/fraillt/bitsery), which supports serialization of complex types (containers) through some template operations.

To make a type support BitSery serialization, you only need to provide the template function `serialize(Serialize& s, type& o)`:

```C++
struct MyStruct {
    uint32_t i;
    std::vector<float> fs;
};

template <typename Serialize>
void serialize(Serialize& s, MyStruct& o) {	 // This template function can be used as both a serialization and deserialization function
    s(o.i);
    s(o.fs);
}
```

To serialize this object, simply:

```C++
using SerializeBuffer = std::vector<uint8_t>;		// Define the buffer type
using OutputAdapter = bitsery::OutputBufferAdapter<SerializeBuffer>;
using InputAdapter = bitsery::InputBufferAdapter<SerializeBuffer>;
using Serializer = bitsery::Serializer<OutputAdapter>;
using Deserializer = bitsery::Deserializer<InputAdapter>;

void main(){
    MyStruct myStruct;
    SerializeBuffer buffer;
    
    // Serialize: output myStruct to buffer
    bitsery::quickSerialization(OutputAdapter(buffer), myStruct); 
    
    // Deserialize: read data from buffer into myStruct
    bitsery::quickDeserialization(InputAdapter(buffer), myStruct);   	
}
```

##### Bypassing Templates

To avoid templates, XObject splits the serialization and deserialization functions, adding the following definitions in the **XENTRY()** macro:

```c++
virtual void __intrusive_deserialize(Deserializer& deserializer) override; 
virtual void __intrusive_serialize(Serializer& serializer) override; 
```

The function implementations are generated by XHT based on properties. Additionally, the parent class's serialization functions are called here.

> Template adaptation of Bitsery API is used here. The problem is that the inheritance relationship of types cannot be determined through templates.
>
> Fortunately, some definitions were added when implementing Rttr inheritance. These definitions can be used to easily determine whether a type is a subclass of XObject:
>
> ```C++
> template<typename T, typename std::enable_if< std::is_class<T>::value&& rttr::detail::has_base_class_list<T>::value>::type* = nullptr>
> void serialize(Serializer& serializer, T& ptr) {
> 	ptr.__intrusive_serialize(serializer);
> }
> 
> template<typename T, typename std::enable_if<std::is_class<T>::value&& rttr::detail::has_base_class_list<T>::value>::type* = nullptr>
> void serialize(Deserializer& deserializer, T& ptr) {
> 	ptr.__intrusive_deserialize(deserializer);
> }
> ```

##### Pointer Specialization

Since Bitsery does not support pointer serialization, specialized pointer serialization templates must be written.

Pointer types differ from original types in two ways:

- Pointers can be null; nullptr cannot be serialized.
- New instances may need to be created during pointer deserialization.

To solve these two problems, the following solutions are adopted:

- Write the pointer's type during serialization; write an empty type for null pointers. During deserialization, the type is always read first. If the type is not empty, serialization continues.
- Since the pointer type is written during serialization, new instances can be created via RTTR based on the type name. However, this requires ensuring the type has a registered parameterless constructor.

But for XObject, more work is needed—for x in `XObject* x = new Base();`, `std::remove_pointer_t<T>::type` cannot be simply used to obtain the original type. Therefore, for XObject types, the type needs to be obtained from the instance's metaObject. The core code is as follows:

```c++
template<typename T, typename std::enable_if<std::is_pointer<T>::value && !rttr::detail::has_base_class_list<rttr::detail::raw_type_t<T>>::value>::type* = nullptr>
void serialize(Serializer& writer, T& ptr) {
	std::string typeName;
	if (ptr != nullptr) {
		rttr::type type = rttr::type::get<rttr::detail::raw_type_t<T>::type>();		// Get the original type based on the pointer type
		typeName = type.get_raw_type().get_name().to_string();
	}
	writer(typeName);					// Write the type
	if (ptr != nullptr) {
		writer(*ptr);					// If the pointer is not null, write the data it points to
	}
}

template<typename T, typename std::enable_if<std::is_pointer<T>::value&& rttr::detail::has_base_class_list<rttr::detail::raw_type_t<T>>::value>::type* = nullptr>
void serialize(Serializer& writer, T& ptr) {
	std::string typeName;
	if (ptr != nullptr) {
		rttr::type type = ptr->metaObject()->getRttrType();							// Get the type from metaObject
		typeName = type.get_raw_type().get_name().to_string();
	}
	writer(typeName);					// Write the type
	if (ptr != nullptr) {
		writer(*ptr);					// If the pointer is not null, write the data it points to
	}	
}

template<typename T, typename std::enable_if<std::is_pointer<T>::value>::type* = nullptr>
void serialize(Deserializer& reader, T& ptr) {
	std::string typeName;				
	reader(typeName);					// Read the type
	if (typeName.empty())				// If the type is empty, return directly
		return;
	if (ptr != nullptr) {				// If the object pointed to during deserialization is not null, directly deserialize it
		reader(*ptr);
		return;
	}
	rttr::type type = rttr::type::get_by_name(typeName);		// Get the Rttr type
	if (!type.is_valid())
		return;
	rttr::variant var = type.create();							// Create an instance using Rttr
	if (!var.can_convert<T>()) {								
		return;
	}
	ptr = var.get_value<T>();									// If the instance is valid, deserialize it
	reader(*ptr);
}
```

##### Include Optimization

Bitsery is a **Header-Only** library. To avoid including all content in **XObject.h**, the core definitions are written in **SerializationDefine.h**, which XObject only includes. Other code is included in **SerializationBriefSyntax.h**, which XHT includes when generating additional code.

#### Json And Cbor

The library used here is [nlohmann json](https://github.com/nlohmann/json.git). The implementation here is somewhat hasty—it only completes serialization and not deserialization, and can only be used for debugging. The serialization functions are also generated via XHT. Naturally, new definitions are added in **XENTRY()**:

```c++
virtual void __intrusive_to_json(nlohmann::json& json) const override;
```

The handling method is similar to binary serialization.

Json serialization was initially intended to be done via reflection, as I did with Qt before. But when I actually implemented it, I found it wasn't that simple:

Using rttr, I can read an rttr::variant data. How can I automatically convert it to json data? It seems I can only do this:

```C++
rttr::variant property;
if(var.isType<int>()){
	json[propertyName] = property.get_value<int>();
}
else if(var.isType<double>()){
	json[propertyName] = property.get_value<double>();
}
else if(...){
	...
}
```

> A roundabout way to solve the problem...?

I always thought that IO operations on QVariant in Qt would automatically redirect to the corresponding type's serialization function.

But rttr::variant does not support this. So I looked up how QVariant does it to fill this gap.

I found that its approach is actually the same, but it uses a Map to store functions:

```c++
rttr::variant property;
json[propertyName] = FuncMap[property.typeId()](property);
```

For custom types, Qt declares that they need to be modified using the macro **Q_DECLARE_METATYPE**:

```C++
struct CustomType{};
Q_DECLARE_METATYPE(CustomType)  // This macro registers the meta type. If the type has a serialization function, it binds the function pointer to the type id.
```

RTTR registration does not support such operations, so for now, XHT is still used to generate json serialization functions.

### Editor

The Core module does not depend on the Editor module at all, while the Editor module uses reflection data from Core to create the editor.

I have written many editors before and made many attempts, mainly going through the following stages:

- **Editor as Core**

  - The early development goal was simple: I needed an editor of a certain type to achieve a certain effect, so I directly started designing the editor's UI and logic. The editor directly called methods of the effect class to edit effects, and sometimes even had to specifically ask the effect class to provide certain APIs for the editor. In the end, the original effect class was completely altered, editor and effect class code was scattered everywhere, coupling was very severe, and I had to be extremely careful when writing import/export interfaces.

- **Type Editor with Property as Core**: There were many transitional stages before this, but they are not worth mentioning. You can understand it through the following features:

  - Property as the editing target, with logically consistent read/write interfaces

    > When writing effect classes, editable properties should be reserved with corresponding read/write interfaces. When using these properties, their synchronization status should be ensured to correctly utilize data generated by editor serialization.

  - Editor widgets correspond one-to-one with data types

    > That is:
    >
    > Int types have int editing widgets, curve classes have curve editing widgets, tree structures have tree editing widgets...
    >
    > These widgets are very fine-grained. Complete editors are assembled from these small widgets.
