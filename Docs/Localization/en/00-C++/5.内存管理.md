## Basic Concepts

When data on a disk is used, the operating system loads it into memory. According to [Baidu Encyclopedia](https://baike.baidu.com/item/%E5%86%85%E5%AD%98/103614):

> Memory is an important component of a computer, also known as internal memory and main memory. All programs in a computer run in memory, and the performance of memory affects the overall performance of the computer. When computation is completed, the CPU sends the results back.

### Heap and Stack

A program (an `exe` file on Windows) is also a type of data. When it starts, the operating system pre-allocates two **fixed-size** blocks of memory for it, which serve as:

- **Stack**: Mainly used for function call execution
- **Heap (Memory)**: Used to store addresses of dynamically allocated memory during program runtime

> The size of the stack is fixed, while the size of the heap is implementation-specific and depends on the compiler used. The heap can be viewed as a chain storage of dynamically allocated memory addresses. Although the default pre-allocated size of the heap in MSVC is 1MB, the space used during runtime can exceed 1MB.

Different compilers and platforms have different default sizes. Taking MSVC on Windows as an example, execute the following program:

```c++
int main() {
    char arr[10000000];
    return 0;
}
```

Since we created or used memory in the stack that exceeds the pre-allocated size of the program, a Stack Overflow error will occur:

![image-20230203205039824](../../../00-C++/Resources/image-20230203205039824.png)

Execute the following program again:

```c++
int main() {
    for (int i = 0; i < 100000000; i++) {
        new int;
    }
    return 0;
}
```

Dynamic allocation will fail when there are no corresponding free memory blocks:

![image-20230203210759623](../../../00-C++/Resources/image-20230203210759623.png)

### Memory Fragmentation

In C++, we typically use `new`/`delete` to create and destroy dynamic memory. In reality, memory allocation interfaces vary across different operating systems. For example, Windows actually uses `VirtualAlloc`/`VirtualFree`, while Unix and Mac use `mmap`/`munmap`.

During program execution, frequent memory allocation and deallocation can lead to a large number of small, contiguous free memory blocks scattered among allocated memory. Due to the imperfection of the operating system's memory allocation algorithm, these **free memory blocks cannot be reused**, which are called **memory fragments**.

### Memory Alignment

Most CPUs do not read or write memory in byte units; they typically use 2, 4, 6, or 8 bytes as the memory access granularity, which helps improve memory I/O efficiency. For specific details, refer to:

- https://zhuanlan.zhihu.com/p/83449008

Memory alignment varies across different operations, hardware, and platforms. For developers, a lack of understanding of these "jargons" can easily lead to pitfalls, such as:

- Using SIMD requires 16-byte alignment.
- Buffers allocated on the GPU have minimum alignment offset restrictions.
- Vector alignment methods differ across different rendering APIs.

### Cache

Although memory has fast read/write speeds, the CPU operates even faster, causing the CPU to spend a long time waiting for data to be read and stored. To reduce the average time the CPU spends accessing memory, the computer storage system introduces the **CPU cache** component. According to [Baidu Encyclopedia](https://baike.baidu.com/item/CPU%E7%BC%93%E5%AD%98):

> In a computer system, the **CPU cache** (English: CPU Cache) is a component used to reduce the average time required for the processor to access memory.
>
> In the pyramid storage system, it is located at the second level from the top, second only to CPU registers. Its capacity is much smaller than memory, but its speed can approach the processor's frequency.
>
> When the processor issues a memory access request, it first checks if the requested data is in the cache. If it exists (a hit), the data is returned directly without accessing memory; if it does not exist (a miss), the corresponding data from memory is first loaded into the cache, then returned to the processor.
>
> The cache is effective mainly because program runtime exhibits locality (Locality) in memory access. This locality includes both spatial locality (Spatial Locality) and temporal locality (Temporal Locality). By effectively utilizing this locality, the cache can achieve a very high hit rate.
>
> From the processor's perspective, the cache is a transparent component. Therefore, programmers usually cannot directly intervene in cache operations. However, it is indeed possible to implement specific optimizations on program code based on cache characteristics to better utilize the cache.

On Windows, you can open Task Manager to view your computer's cache information:

![image-20230203213134642](../../../00-C++/Resources/image-20230203213134642.png)

When a program accesses a block of memory, it may load its surrounding area into the cache (since loading additional content has little overhead). If the next memory to be accessed has already been loaded into the cache (called a cache hit), the CPU does not need to access memory again, thereby improving speed.

This example code helps you understand the importance of the cache:

```c++
#include <iostream>
#include <chrono>
#include <vector>

class ClockGuard {			// Used to print the execution time of a scope
public:
    ClockGuard(const std::string& inDest)
        : mDesc(inDest)
    {
        mStartTime = std::chrono::steady_clock::now();
    }
    ~ClockGuard() {
        std::chrono::steady_clock::time_point currentTime = std::chrono::steady_clock::now();
        double durationNs = std::chrono::duration<double, std::nano>(currentTime - mStartTime).count();
        std::cout << mDesc << " Cost: " << durationNs << " Ns" << std::endl;
    }
private:
    std::string mDesc;
    std::chrono::steady_clock::time_point mStartTime;
};

const size_t bigger_than_cachesize = 10 * 1024 * 1024;
long* ptr = new long[bigger_than_cachesize];
void ClearCPUCache() {				// Attempt to clear the cache
    for (int i = 0; i < bigger_than_cachesize; i++) {
        ptr[i] = rand();
    }
}

int main(int argc, char** argv) {
    std::vector<int*> continuous(1000);		// Array with continuous memory
    std::vector<int*> dispersive(1000);		// Array with scattered memory

    for (int*& item : continuous) {
        item = new int;
    }

    const int spacing = 10000;	   		// Memory spacing; adjust this to observe cache effects
    for (int*& item : dispersive) {	   		
        item = new int[spacing];
    }

    ClearCPUCache();
    {
        ClockGuard guard("continuous");		// Assign values to continuous memory; high cache hit rate
        for (int*& item : continuous) {
            *item = 1;
        }
    }
    
    ClearCPUCache();
    {
        ClockGuard guard("dispersive");		// Assign values to scattered memory; low cache hit rate 
        for (int*& item : dispersive) {
            *item = 1;
        }
    }

    return 0;
}
```

### Hardware Acceleration

In addition to the cache mechanism, there are some "black magic" techniques in memory usage, such as the following code:

```c++
#include <iostream>
#include <chrono>
#include <vector>

class ClockGuard {
public:
    ClockGuard(const std::string& inDest)
        : mDesc(inDest) {
        mStartTime = std::chrono::steady_clock::now();
    }
    ~ClockGuard() {
        std::chrono::steady_clock::time_point currentTime = std::chrono::steady_clock::now();
        double durationNs = std::chrono::duration<double, std::nano>(currentTime - mStartTime).count();
        std::cout << mDesc << " Cost: " << durationNs << " Ns" << std::endl;
    }
private:
    std::string mDesc;
    std::chrono::steady_clock::time_point mStartTime;
};

const size_t bigger_than_cachesize = 10 * 1024 * 1024;
long* ptr = new long[bigger_than_cachesize];
void ClearCPUCache() {
    for (int i = 0; i < bigger_than_cachesize; i++) {
        ptr[i] = rand();
    }
}

int main(int argc, char** argv) {
    std::vector<int> src(100000);
    std::vector<int> dst(100000);

    ClearCPUCache();
    {
        ClockGuard guard("Copy");		// Ordinary C++ copy
        for (int i = 0; i < src.size(); ++i) {
            dst[i] = src[i];
        }
    }
    ClearCPUCache();
    {
        ClockGuard guard("Map");		// Memory copy
        memcpy(dst.data(), src.data(), src.size());
    }

    return 0;
}
```

In C++ syntax, you cannot write simpler code than `for (int i = 0; i < src.size(); ++i) { dst[i] = src[i]; }`, but using `memcpy` to do the same thing can significantly improve performance. This is mainly because `memcpy` uses assembly-level optimizations and is strongly related to hardware features:

- Implementation principle of memcpy on ARM64 architecture: https://blog.csdn.net/m0_46250244/article/details/115055101

As you continue learning graphics, you will encounter many similar operations on the GPU, so it is important to gain a deeper understanding of hardware architecture.

## Object Lifecycle Management

Modern program development involves a large number of objects. For objects allocated on the stack, they are automatically released when they go out of scope. However, for objects allocated on the heap, we need to manually manage their lifecycles. In C++, this means ensuring that `new` and `delete` are used in pairs. Ideally, it looks like this:

```c++
void Func() {
    Object* object = new Object;
    //...
    delete object;
}
```

But reality is often harsh. When logical branches or nested functions appear in the code, and the object's lifecycle is transferred, manually controlling its `delete` becomes difficult:

```c++
void Func() {
    Object* object = new Object;
    if (...) {
        // Do something 
        delete object;
        return;
    }
    else if (...) {
        // Do something 
        delete object;
        return;
    }
    else if (...) {
        // Do something 
        delete object;
        return;
    }
}
```

For this reason, we often need an automatic object lifecycle management strategy. Currently, there are two main approaches:

- Smart pointers
- Garbage collection

### Smart Pointers

Various C++ libraries often provide the concept of shared pointers. Their core idea is:

- Wrap the actual object pointer with an external object. By monitoring the construction, destruction, and copying of the external object, use a piece of public memory to record the pointer's reference count. When the reference count reaches 0, destroy the object.

A simple imitation is as follows:

```c++
struct SharedPtrRefData {
    uint refCount = 0; 
};

template<typename _Ty>
class SharedPtr {
public:
    SharedPtr(_Ty* rawPtr)						// Constructor
        : mRawPtr(rawPtr)
        , mRefData(new SharedPtrRefData)		// Create public memory
    {
        mRefData->refCount++;					// Increment reference count
    }
    
    SharedPtr(const SharedPtr<_Ty>& other) {		// Copy constructor
        mRefData = other.mRefData;				// Transfer public memory
        mRefData->refCount++;					// Increment reference count
    }
    
    ~SharedPtr() {								// Destructor
        mRefData->refCount--;					// Decrement reference count
        if (mRefData->refCount == 0) {	
            delete mRawPtr;						// Destroy the object
            delete mRefData;					// Destroy public memory
        }
    }
private:
    _Ty* mRawPtr;
    SharedPtrRefData* mRefData;
};
```

This structure is implemented in the following frameworks:

- C++ standard library: **std::shared_ptr**
- Unreal Engine: **TSharedPtr**
- Qt: **QSharedPointer**

Using `SharedPtr` ensures that the pointer object is not released when accessed. However, sometimes we may want a "shared pointer" **not to extend the object's lifecycle but to check if the object has been destroyed later**. Frameworks generally call this structure a **WeakPtr**, which corresponds to:

- C++ standard library: **std::weak_ptr**
- Unreal Engine: **TWeakPtr**
- Qt: **QWeakPointer**

Taking `std` as an example:

```c++
#include <iostream>

int main() {
    std::shared_ptr<int> sptr(new int);
    std::weak_ptr<int> wptr(sptr);
    if (const std::shared_ptr<int>& lock = wptr.lock()) {
        std::cout << "exist!!!" << std::endl;
    }
    else {
        std::cout << "not exist" << std::endl;
    }
    sptr.reset();
    if (const std::shared_ptr<int>& lock = wptr.lock()) {
        std::cout << "exist!!!" << std::endl;
    }
    else {
        std::cout << "not exist!" << std::endl;
    }
    return 0;
}

/*
exist!!!
not exist!
*/
```

In the simple `SharePtr` code above, when `refCount` is 0, both the object and public memory are destroyed. In reality, `SharedPtrRefData` contains two counters: `refCount` and `weakCount`. When `refCount` is 0, only the object is destroyed, not the public memory. This allows `WeakPtr` to still access the shared memory to check if the object exists. The public memory is only destroyed when `weakCount` also reaches 0.

For raw pointers, `delete` only destroys the object's memory, but the address pointed to by the pointer still exists. Improper management can lead to dangling pointers and memory leaks. `WeakPtr` solves this problem.

Another scenario: sometimes we want a `new`-created object to be destroyed when it goes out of scope, just like an ordinary object. For example:

```c++
class Example {
public:
    Example()
        : mObject(new Object)
    {}
    ~Example() {
        delete mObject;
    } 
private:
    Object* mObject;
};
```

In this case, we can use:

- C++ standard library: **std::unique_ptr**
- Unreal Engine: **TUniquePtr**
- Qt: **QScopedPointer**

> Qt's naming seems to better reflect its purpose.

The above code can be rewritten using `UniquePtr` as:

```c++
class Example {
public: Example()
    : mObject(new Object)
    {}
private:
    std::unique_ptr<Object> mObject;
};
```

Smart pointers can solve most problems in development, but they are not perfect. Here are some **notes**:

- When using smart pointers, try to `new` objects in constructors or `reset` functions. Avoid manipulating raw pointers outside smart pointers.

  ```c++
  
  ```
  
- Do not use `std::shared<int> sptr(this)`. If you want to create a shared pointer using `this`, the class of `this` must inherit from the template `enable_shared_from_this`.

- Excessive use of unnecessary `SharedPtr` can lead to waste. The original intention of using `SharedPtr` is to maintain the object's lifecycle. If you do not need the interface to transfer the object's lifecycle, you should not expose `SharedPtr`; instead, use `WeakPtr` or `RawPtr`.

- When using in a multi-threaded environment, ensure that the `SharedPtr` used is thread-safe to ensure the reference count works correctly.

Additionally, there are some **hidden dangers**:

- When using shared pointers, it is easy to overlook the lifecycle of captured parameters. If there are shared pointers internally, it can lead to memory leaks:

  ```c++
  #include <iostream>
  #include <functional>
  
  class Example {
  public:
      Example() {
          std::cout << "Create" << std::endl;
      }
      ~Example() {
          std::cout << "Destroy" << std::endl;
      }
  };
  
  int main(int argc, char** argv) {
      {
          std::function<void()> func0;
          {
              std::shared_ptr<Example> sptr(new Example);
              std::function<void()> func1 = [sptr]() {};	// Capture the shared pointer as a parameter
              std::cout << "---------0" << std::endl;
              // func0 = func1;		// Uncomment this line, and Example will be released between 1 and 2
          }
          std::cout << "---------1" << std::endl;
      }
      std::cout << "---------2" << std::endl;
      return 0;
  }
  /*
  The captured parameters of a lambda are released only when they go out of scope and are not referenced by any function.
  If the function is not destroyed or reset in time, the captured parameters will persist, leading to memory leaks.
  */
  ```

- `SharedPtr` has a circular reference problem:

  ```c++
  #include <iostream>
  
  struct B;
  
  struct A {
      ~A() {
          std::cout << "destruct A" << std::endl;
      }
      std::shared_ptr<B> mB;
  };
  
  struct B {
      ~B() {
          std::cout << "destruct B" << std::endl;
      }
      std::shared_ptr<A> mA;
  };
  
  int main() {
      {
          std::shared_ptr<A> a(new A);
          std::shared_ptr<B> b(new B); 
          a->mB = b;
          b->mA = a;
      }
      return 0;	// Objects cannot be released
  }
  ```

- The destruction of `SharedPtr` is immediate. Destroying a large number of objects at once in a large-scale system can cause lag.

### Garbage Collection

To address the flaws of shared pointers, some high-level languages and large frameworks provide a Garbage Collection (GC) mechanism, aiming to solve circular reference problems and implement delayed destruction.

> Due to C++'s features (historical reasons), introducing a poor GC mechanism into the C++ standard would only make it more chaotic. Therefore, GC in C++ is usually customized by frameworks, such as UE and Qt, which have deviated from the C++ standard. Netizens jokingly call them U++ and Q++.

Currently, the GC mechanisms the author is more familiar with include:

- Unreal Engine
- Qt, FBX SDK
- Lua

For developers, there are two main points to understand about GC:

- How to mark reference relationships between objects
- How to perform garbage collection

For some high-level languages like Java, C#, Python, and Lua, it is easy to monitor reference relationships between objects due to the virtual machine. In C++, reference relationships between objects can only be set manually or analyzed through reflection.

Qt uses `QObject` as the base class, and its memory collection is very simple:

```cpp
class QObject {
public:
    QObject(QObject * parent = nullptr);
private:
    QVector<QObject*> children;
    QObject *parent;
};
```

- `QObject` has a `parent` pointer and a `children` list. Destroying a `QObject` will also destroy its `children`.
- `QObject` also provides a `deleteLater()` function, which adds the object to an array. The object is destroyed after the event processing loop ends.

FBX SDK uses `FbxObject` as the base class, and a parent object must be specified when creating an instance:

```cpp
FbxManager* lManager = FbxManager::Create();
FbxIOSettings* lIOSettings = FbxIOSettings::Create(lManager, "");
FbxScene* scene = FbxScene::Create(lManager,"");
FbxSkeleton* skeletonNode = FbxSkeleton::Create(scene,"SkeletonRoot");
FbxCluster* rootCluster = FbxCluster::Create(skeletonNode, "");
```

- When the parent object is released, the child objects are also released.

The main memory collection structures of the above two frameworks are very simple. For loop problems, they detect when specifying `parent` and directly report an error if a loop occurs.

In contrast, UE's GC mechanism is much more complex. In UE, references are mainly built in two ways:

- UProperty (reflection): UE determines the reference relationship between two objects by analyzing the `Property` of `UObject`.
- FGCObject: An interface class for manually building reference relationships. Most frameworks in UE, such as UMG, Editor, Niagara, etc., derive from `FGCObject` to implement a set of GC reference management mechanisms. This allows developers to implicitly build reference relationships between objects when calling certain interfaces.

UE's collection method is relatively complex and will not be expanded here. Generally, it is only necessary to understand that it performs collection periodically and quantitatively.

### Cache

Although memory has fast read/write speeds, the CPU operates even faster, causing the CPU to spend a long time waiting for data to be read and stored. To reduce the average time the CPU spends accessing memory, the computer storage system introduces the **CPU cache** component. According to [Baidu Encyclopedia](https://baike.baidu.com/item/CPU%E7%BC%93%E5%AD%98):

> In a computer system, the **CPU cache** (English: CPU Cache) is a component used to reduce the average time required for the processor to access memory.
>
> In the pyramid storage system, it is located at the second level from the top, second only to CPU registers. Its capacity is much smaller than memory, but its speed can approach the processor's frequency.
>
> When the processor issues a memory access request, it first checks if the requested data is in the cache. If it exists (a hit), the data is returned directly without accessing memory; if it does not exist (a miss), the corresponding data from memory is first loaded into the cache, then returned to the processor.
>
> The cache is effective mainly because program runtime exhibits locality (Locality) in memory access. This locality includes both spatial locality (Spatial Locality) and temporal locality (Temporal Locality). By effectively utilizing this locality, the cache can achieve a very high hit rate.
>
> From the processor's perspective, the cache is a transparent component. Therefore, programmers usually cannot directly intervene in cache operations. However, it is indeed possible to implement specific optimizations on program code based on cache characteristics to better utilize the cache.

On Windows, you can open Task Manager to view your computer's cache information:

![image-20230203213134642](../../../00-C++/Resources/image-20230203213134642.png)

When a program accesses a block of memory, it may load its surrounding area into the cache (since loading additional content has little overhead). If the next memory to be accessed has already been loaded into the cache (called a cache hit), the CPU does not need to access memory again, thereby improving speed.

This example code helps you understand the importance of the cache:


## Object Lifecycle Management

Modern program development involves a large number of objects. For objects allocated on the stack, they are automatically released when they go out of scope. However, for objects allocated on the heap, we need to manually manage their lifecycles. In C++, this means ensuring that `new` and `delete` are used in pairs. Ideally, it looks like this:

```c++
void Func() {
    Object* object = new Object;
    //...
    delete object;
}
```

But reality is often harsh. When logical branches or nested functions appear in the code, and the object's lifecycle is transferred, manually controlling its `delete` becomes difficult:

```c++void Func() {
    Object* object = new Object;
    if (...) {
        // Do something 
        delete object;
        return;
    }
    else if (...) {
        // Do something 
        delete object;
        return;
    }
    else if (...) {
        // Do something 
        delete object;
        return;
    }
}
```

For this reason, we often need an automatic object lifecycle management strategy. Currently, there are two main approaches:

- Smart pointers
- Garbage collection

### Smart Pointers

Various C++ libraries often provide the concept of shared pointers. Their core idea is:

- Wrap the actual object pointer with an external object. By monitoring the construction, destruction, and copying of the external object, use a piece of public memory to record the pointer's reference count. When the reference count reaches 0, destroy the object.

A simple imitation is as follows:

```c++
struct SharedPtrRefData {
    uint refCount = 0; 
};

template<typename _Ty>
class SharedPtr {
public:
    SharedPtr(_Ty* rawPtr)						// Constructor
        : mRawPtr(rawPtr)
        , mRefData(new SharedPtrRefData)		// Create public memory
    {
        mRefData->refCount++;					// Increment reference count
    }
    
    SharedPtr(const SharedPtr<_Ty>& other) {		// Copy constructor
        mRefData = other.mRefData;				// Transfer public memory
        mRefData->refCount++;					// Increment reference count
    }
    
    ~SharedPtr() {								// Destructor
        mRefData->refCount--;					// Decrement reference count
        if (mRefData->refCount == 0) {	
            delete mRawPtr;						// Destroy the object
            delete mRefData;					// Destroy public memory
        }
    }
private:
    _Ty* mRawPtr;
    SharedPtrRefData* mRefData;
};
```

This structure is implemented in the following frameworks:

- C++ standard library: **std::shared_ptr**
- Unreal Engine: **TSharedPtr**
- Qt: **QSharedPointer**

Using `SharedPtr` ensures that the pointer object is not released when accessed. However, sometimes we may want a "shared pointer" **not to extend the object's lifecycle but to check if the object has been destroyed later**. Frameworks generally call this structure a **WeakPtr**, which corresponds to:

- C++ standard library: **std::weak_ptr**
- Unreal Engine: **TWeakPtr**
- Qt: **QWeakPointer**

Taking `std` as an example:

```c++
#include <iostream>

int main() {
    std::shared_ptr<int> sptr(new int);
    std::weak_ptr<int> wptr(sptr);
    if (const std::shared_ptr<int>& lock = wptr.lock()) {
        std::cout << "exist!!!" << std::endl;
    }
    else {
        std::cout << "not exist" << std::endl;
    }
    sptr.reset();
    if (const std::shared_ptr<int>& lock = wptr.lock()) {
        std::cout << "exist!!!" << std::endl;
    }
    else {
        std::cout << "not exist!" << std::endl;
    }
    return 0;
}

/*
exist!!!
not exist!
*/
```

In the simple `SharePtr` code above, when `refCount` is 0, both the object and public memory are destroyed. In reality, `SharedPtrRefData` contains two counters: `refCount` and `weakCount`. When `refCount` is 0, only the object is destroyed, not the public memory. This allows `WeakPtr` to still access the shared memory to check if the object exists. The public memory is only destroyed when `weakCount` also reaches 0.

For raw pointers, `delete` only destroys the object's memory, but the address pointed to by the pointer still exists. Improper management can lead to dangling pointers and memory leaks. `WeakPtr` solves this problem.

Another scenario: sometimes we want a `new`-created object to be destroyed when it goes out of scope, just like an ordinary object. For example:

```c++
class Example {
public:
    Example()
        : mObject(new Object)
    {}
    ~Example() {
        delete mObject;
    } 
private:
    Object* mObject;
};
```

In this case, we can use:

- C++ standard library: **std::unique_ptr**
- Unreal Engine: **TUniquePtr**
- Qt: **QScopedPointer**

> Qt's naming seems to better reflect its purpose.

The above code can be rewritten using `UniquePtr` as:

```c++
class Example {
public: Example()
    : mObject(new Object)
    {}
private:
    std::unique_ptr<Object> mObject;
};
```

- When using smart pointers, try to `new` objects in constructors or `reset` functions. Avoid manipulating raw pointers outside smart pointers.

### Garbage Collection

To address the flaws of shared pointers, some high-level languages and large frameworks provide a Garbage Collection (GC) mechanism, aiming to solve circular reference problems and implement delayed destruction.

> Due to C++'s features (historical reasons), introducing a poor GC mechanism into the C++ standard would only make it more chaotic. Therefore, GC in C++ is usually customized by frameworks, such as UE and Qt, which have deviated from the C++ standard. Netizens jokingly call them U++ and Q++.

Currently, the GC mechanisms the author is more familiar with include:

- Unreal Engine
- Qt, FBX SDK
- Lua

For developers, there are two main points to understand about GC:

- How to mark reference relationships between objects
- How to perform garbage collection

For some high-level languages like Java, C#, Python, and Lua, it is easy to monitor reference relationships between objects due to the virtual machine. In C++, reference relationships between objects can only be set manually or analyzed through reflection.

Qt uses `QObject` as the base class, and its memory collection is very simple:

```cpp
class QObject {
public:
    QObject(QObject * parent = nullptr);
private:
    QVector<QObject*> children;
    QObject *parent;
};
```

- `QObject` has a `parent` pointer and a `children` list. Destroying a `QObject` will also destroy its `children`.
- `QObject` also provides a `deleteLater()` function, which adds the object to an array. The object is destroyed after the event processing loop ends.

FBX SDK uses `FbxObject` as the base class, and a parent object must be specified when creating an instance:

```cpp
FbxManager* lManager = FbxManager::Create();
FbxIOSettings* lIOSettings = FbxIOSettings::Create(lManager, "");
FbxScene* scene = FbxScene::Create(lManager,"");
FbxSkeleton* skeletonNode = FbxSkeleton::Create(scene,"SkeletonRoot");
FbxCluster* rootCluster = FbxCluster::Create(skeletonNode, "");
```

- When the parent object is released, the child objects are also released.

The main memory collection structures of the above two frameworks are very simple. For loop problems, they detect when specifying `parent` and directly report an error if a loop occurs.

In contrast, UE's GC mechanism is much more complex. In UE, references are mainly built in two ways:

- UProperty (reflection): UE determines the reference relationship between two objects by analyzing the `Property` of `UObject`.
- FGCObject: An interface class for manually building reference relationships. Most frameworks in UE, such as UMG, Editor, Niagara, etc., derive from `FGCObject` to implement a set of GC reference management mechanisms. This allows developers to implicitly build reference relationships between objects when calling certain interfaces.

UE's collection method is relatively complex and will not be expanded here. Generally, it is only necessary to understand that it performs collection periodically and quantitatively.

Here is a simple mark-and-sweep algorithm. Its core is:

- Store all recyclable objects in an array.
- Store reference relationships between objects.
- Have a global root node. If other nodes have a reference relationship to reach this node, it means the node is reachable.
- During garbage collection, the game thread needs to be suspended to ensure no objects are in use.
- Traverse from the root node, mark all reachable nodes.
- Traverse the object array, destroy unreachable nodes.

A simple implementation is as follows (for more details, see: [Mark-and-Sweep: Garbage Collection Algorithm](https://link.zhihu.com/?target=https%3A//www.geeksforgeeks.org/mark-and-sweep-garbage-collection-algorithm/)):

```cpp
class ObjectBase {
public:
    typedef short ID;
public:
    ObjectBase();
    virtual ~ObjectBase();
    void addRefrence(ObjectBase * ref);     // Add object reference
    void removeRefrence(ObjectBase* ref);   // Remove object reference
private:
    friend class ObjectManagement;
    ID id;                      // Assign a unique ID to this object
    std::list<ID> refrence;     // List of referenced object IDs
};
```

> `short` is used here because it is only 2 bytes and can represent 2^15 (32767) numbers, which is sufficient for IDs.

To manage all `ObjectBase` objects, a global management object **GObjectManagement** is created. Objects are added to it during construction and removed during destruction:

```cpp
ObjectBase::ObjectBase() {
    GObjectManagement.AddObject(this);
}

ObjectBase::~ObjectBase() {
    GObjectManagement.RemoveObject(this);
}
```

The definition of `ObjectManagement` is as follows:

```cpp
class ObjectManagement {
public:
    ObjectManagement() {
        for (int i = 0; i < mObjects.size(); i++) {     // Initialize the ID stack
            mObjects[i].object = nullptr;
            mIdStack[i] = i;
        }
    }
    void AddObject(ObjectBase* obj) {       // Add an object
        if (obj != nullptr) {
            obj->id = allocId();
            mObjects[obj->id].object = obj;
            ++mCurrentNumberOfObject;
            mMaxIdOfObject = std::max(mMaxIdOfObject, obj->id);
        }
    }
    void RemoveObject(ObjectBase* obj) {    // Remove an object
        if (obj != nullptr) {
            mObjects[obj->id].object = nullptr;
            freeId(obj->id);
            --mCurrentNumberOfObject;
        }
    }
    void GarbageCollection() {              // Garbage collection
        MarkObjects(0);        // Assume node 0 is the global root node of the game; start traversal from it to mark reachable objects
        for (int i = 0; i <= mMaxIdOfObject; i++) {     // Simply traverse all objects and destroy unreachable ones
            if (!mObjects[i].reachable) {
                delete mObjects[i].object;
            }
            else {      // Restore state for the next reachability traversal
                mObjects[i].reachable = false;
            }
        }
    }

    void MarkObjects(const ObjectBase::ID& Id) {                // Depth-first traversal of all nodes
        ObjectBase* obj = mObjects[Id].object;
        if (obj != nullptr && !mObjects[Id].reachable) {        // Require the node to be unreachable to avoid loops
            mObjects[Id].reachable = true;
            for (auto& subId : obj->refrence) {
                MarkObjects(subId);
            }
        }
    }

private:
    ObjectBase::ID allocId() {                  // Allocate an ID from the top of the stack
        assert(mIdStackTop < mIdStack.size());
        return mIdStack[mIdStackTop++];
    }
    
    void freeId(ObjectBase::ID id) {            // Recycle an ID
        assert(mIdStackTop > 0);
        mIdStack[--mIdStackTop] = id;
    }

public:
    struct ObjectItem {
        ObjectBase* object;
        bool reachable = false;
    };

    static const int MAX_NUMBER_OF_OBJECT = std::numeric_limits<ObjectBase::ID>().max();

    std::array<ObjectItem, MAX_NUMBER_OF_OBJECT> mObjects;      // Create a fixed-size array of 32767 to store all objects
    
    std::array<ObjectBase::ID, MAX_NUMBER_OF_OBJECT> mIdStack;  // This fixed-size array simulates a stack to allocate and recycle IDs, ensuring IDs do not expand rapidly
    ObjectBase::ID mIdStackTop = 0;                             // Top index of the stack

    ObjectBase::ID mCurrentNumberOfObject = 0;                  // Current number of objects
    ObjectBase::ID mMaxIdOfObject = 0;                          // Maximum ID used in the program to reduce traversal count
};

// Global static object
static ObjectManagement GObjectManagement;
```

## Memory Scheduling Frameworks

The open-source community has produced many memory scheduling frameworks aimed at reducing memory fragmentation and increasing cache hit rates. Some well-known ones include:

### [mimalloc](https://github.com/microsoft/mimalloc)

mimalloc is a general-purpose allocator with excellent [performance](https://github.com/microsoft/mimalloc#performance) characteristics. It was originally developed by Daan Leijen for the runtime systems of the [Koka](https://koka-lang.github.io/) and [Lean](https://github.com/leanprover/lean) languages.

- **Small and consistent**: The library uses simple and consistent data structures, with approximately 8k LOC. This makes it very suitable for integration and adaptation to other projects. For runtime systems, it provides hooks for monotonic *heartbeats* and delayed release (for bounded worst-case time with reference counting).
- **Free list sharding**: Instead of a single large free list (per size class), each "mimalloc page" has many smaller lists, which reduces fragmentation and increases locality—things allocated in time are allocated close together in memory. (A mimalloc page contains blocks of a single size class, typically 64KiB on 64-bit systems.)
- **Free list multi-sharding**: A great idea! We not only shard the free lists per mimalloc page but also have multiple free lists per page. In particular, there is a list for thread-local `free` operations and another for concurrent `free` operations. Freeing from another thread can now be a single CAS without complex coordination between threads. Since there will be thousands of individual free lists, contention is naturally distributed across the heap, and the chance of contention at a single location will be low—much like randomized algorithms such as skip lists, where adding a random oracle eliminates the need for more complex algorithms.
- **Eager page reset**: When a "page" becomes empty (more likely due to free list sharding), the memory is marked as unused by the operating system ("reset" or "purged") to reduce (real) memory pressure and fragmentation, especially in long-running programs.
- **Security**: *mimalloc* can be built in secure mode, adding guard pages, random allocation, encrypted free lists, etc., to prevent various heap vulnerabilities. The performance penalty is usually around 10% higher on average in our benchmarks.
- **First-class heaps**: Efficiently create and use multiple heaps for allocation across different regions. Heaps can be destroyed at once instead of freeing each object individually.
- **Bounded**: It does not suffer from *bloat*, has bounded worst-case allocation time ( *wcat* ), bounded space overhead (about 0.2% metadata, up to 12.5% waste in allocation size), and no internal points of contention using only atomic operations.
- **Fast**: In our benchmarks, *mimalloc* outperforms other leading allocators ( *jemalloc* , *tcmalloc* , *Hoard* , etc.) and usually uses less memory. A nice feature is that it consistently performs well across a wide range of benchmarks. There is also good huge OS page support for larger server programs.

### [oneTBB](https://www.intel.com/content/www/us/en/developer/tools/oneapi/onetbb.html)

Intel® oneAPI Threading Building Blocks (oneTBB) is a flexible performance library that simplifies adding parallelism to complex applications across accelerated architectures, even if you are not a threading expert.

- **Specify logical performance, not threads**: The runtime library automatically maps logical parallelism to threads to most effectively utilize processor resources.
- **Target threads for better performance**: Focus on specific goals for parallelizing compute-intensive work, providing higher-level, simpler solutions.
- **Coexist with other thread packages**: It can seamlessly coexist with other threads, giving you the flexibility to keep legacy code unchanged and use oneTBB for new implementations.
- **Emphasize scalable data parallel programming**: oneTBB emphasizes data parallel programming rather than decomposing the program into functional blocks and assigning a separate thread to each block, allowing multiple threads to work on different parts of a collection. This scales well to more processors. As you add processors and accelerators, program performance improves.

### [jemalloc](https://github.com/jemalloc/jemalloc)

jemalloc is a general-purpose `malloc(3)` implementation that emphasizes avoiding fragmentation and scalable concurrency support. It is designed to be used as a system-provided memory allocator, such as in FreeBSD's libc library, and for linking to C/C++ applications. jemalloc provides many introspection, memory management, and tuning features beyond those of standard allocators.

### [tcmalloc](https://github.com/google/tcmalloc)

TCMalloc is Google's custom implementation of C `malloc()` and C++ `operator new` for allocating memory in C and C++ code. This custom memory allocation framework is an alternative to the frameworks provided by the C standard library (usually via `glibc` on Linux) and the C++ standard library.

- Performance scales with the degree of parallelism in the application.
- Optimized for C++14 and C++17, with slight differences from the standard while ensuring performance advantages (these are noted in the [TCMalloc Reference](https://github.com/google/tcmalloc/blob/master/docs/reference.md)).
- Allows extensions for better performance on certain architectures, as well as other behaviors such as metric collection.

- Performs allocation from the operating system by managing memory blocks of specific sizes (called "pages").
- Uses separate pages (or runs of pages called "spans" in TCMalloc) for specific object sizes. For example, all 16-byte objects are placed in "spans" allocated specifically for that size of object. Operations to acquire or release memory in this case are much simpler.
- Keeps memory in *caches* to speed up access to commonly used objects. Retaining such caches even after release helps avoid costly system calls if the memory is reallocated later.

In Unreal Engine, it implements a memory allocator base class **FMalloc** and derives the following subclasses. It uses `FMemory::Malloc`/`FMemory::Free` to call the memory allocator's interface, allowing switching between different memory allocators:

- **Ansi**: Standard C allocator, directly calling `malloc`, `free`, `realloc`.
- **Stomp**: Helps track problems caused by reading/writing during allocation, such as dangling pointers and memory out-of-bounds.

- **TBB**: Thread Building Blocks, a 64-bit scalable memory allocator provided by Intel.

- **Jemalloc**: Mainly used for Unix memory allocators.

- **Binned**: Binned memory allocator, mainly used for iOS.

  - **Binned**: The binned allocator divides a block of memory ( **Pool** ) into many slots of different sizes. For example, Binned divides 64KB into 41 different slots on PC and allocates free slots from the end forward.

  - **Binned2**: The Binned2 allocator supports thread-local memory allocation and does not need to lock every time. This can significantly improve performance during frequent small memory allocations and releases.

  - **Binned3**: Uses virtual memory addresses (logical memory addresses), which can be arranged to perform high-speed Pool Index searches, so that the target size Pool can be calculated from the memory pointer.

- **Mimalloc**: A general-purpose memory allocator superior to tcmalloc and jemalloc.

## Basic Library Optimization

At the application level of memory, there is much room for optimization in C++'s basic containers and algorithms, which brings us to the C++ STL library. It has many shortcomings:

- Some STL implementations (especially Microsoft STL) have poor performance characteristics, making them unsuitable for game development.
- STL is sometimes difficult to debug because most STL implementations use cryptic variable names and unusual data structures.
- STL allocators are sometimes painful to use because they have many requirements and cannot be modified once bound to a container.
- STL contains excessive functionality that may cause code to behave unexpectedly. It is not easy to tell programmers they should not use a certain feature.
- STL is implemented through very deep function calls. This leads to unacceptable performance in non-optimized builds and sometimes in optimized builds as well.
- STL does not support alignment of contained objects.
- STL containers do not allow you to insert entries without providing an entry to copy from. This can be inefficient.
- Useful STL extensions found in existing STL implementations such as STLPort (e.g., `slist`, `hash_map`, `shared_ptr`) are not portable because they do not exist in other STL versions or are inconsistent between STL versions.
- STL lacks useful extensions that game programmers find useful (e.g., `intrusive_list`), but they can be optimally implemented in a portable STL environment.
- The STL specification limits our ability to use it effectively. For example, an STL vector does not guarantee contiguous memory, so it cannot be safely used as an array.
- STL emphasizes correctness over performance, and sometimes you can achieve significant performance gains by reducing academic purity.
- STL containers have private implementations that do not allow you to manipulate their data in a portable way, but sometimes this is important (e.g., node pools).
- All existing versions of STL allocate memory in the empty version of at least some of their containers. This is not ideal and prevents optimizations such as container memory reset, which can greatly improve performance in some cases.
- STL compiles slowly because most modern STL implementations are very large.

> Excerpted from https://github.com/electronicarts/EASTL/blob/master/doc/Design.md

Its biggest shortcoming is:

- **STL emphasizes correctness over performance. In pursuit of academic purity, it does not take risks or take unconventional paths for performance.**

For example, many people know that when using `std::vector`, they should use `reserve` to pre-allocate memory to avoid memory reallocation due to expansion. For containers like `set` and `map`, it is also possible to pre-allocate node memory, which not only reduces the number of memory allocations but also ensures that container elements are contiguous in memory, greatly increasing cache hit rates during access.

If you compare STL and UE's memory allocators, you can find obvious differences:

- STL uses `Allocator` to allocate memory for new elements in the container.
- UE's `Allocator` reallocates memory for the entire container. UE's containers all support an expansion mechanism like `std::vector`.

To solve the above problems, many engines maintain their own basic libraries. Open-source solutions mainly include the following:

### [EASTL](https://github.com/electronicarts/EASTL)

EASTL is a C++ template library containing containers, algorithms, and iterators that can be used for runtime and tool development across multiple platforms. Its implementation is quite extensive and robust, with an emphasis on performance above all other considerations.

- EASTL has a simplified and more flexible custom allocation scheme.
- EASTL's code is easier to read.
- EASTL has extended containers and algorithms.
- EASTL has optimizations designed for game development.

Among the above points, the only incompatible difference with STL is the memory allocation situation.

### [foonathan](https://github.com/foonathan/memory)

foonathan also aims to solve the flaws of STL, but unlike EASTL, it does not attempt to change STL.

### [STL C++17 polymorphic memory source](https://www.rkaiser.de/wp-content/uploads/2021/03/embo2021-pmr-STL-for-Embedded-Applications-en.pdf)

Before C++17, memory allocation for STL containers needed to be done using `allocator`, which had the following main flaws:

- `allocator` is part of the template signature. Containers with different `allocator`s cannot be mixed.

  ```c++
  vector<int, allocator0> v0;
  vector<int, allocator1> v1;
  v0 = v1;  // Error
  ```

- `allocator` memory alignment cannot be controlled and requires passing a custom `allocator`.

- `allocator` has no internal state.

C++17 provides a new memory allocation method for containers ——` <memory_resource>`.

Its usage is as follows:

```c++
#include <memory_resource>
#include <vector>
#include <string>            
#include <iostream>

class CustomMemoryResource : public std::pmr::memory_resource {   // Custom memory_source
public:
    CustomMemoryResource() {}
private:
    virtual void* do_allocate(const size_t _Bytes, const size_t _Align) override {
        return ::operator new(_Bytes, std::align_val_t(_Align));
    }                                                                                                                                             
    virtual void do_deallocate(void* _Ptr, size_t _Bytes, size_t _Align) {
        ::operator delete(_Ptr, _Bytes, std::align_val_t(_Align));
    };
    virtual bool do_is_equal(const memory_resource& _That) const noexcept {
        return this == &_That;
    };
};
int main() {
    std::pmr::unsynchronized_pool_resource ms1; // Non-thread-safe pool allocator
    std::pmr::synchronized_pool_resource ms2;   // Synchronized pool allocator
    CustomMemoryResource custom_memory_source;  // Custom allocator
    char buffer[20];
    std::pmr::monotonic_buffer_resource mbr(std::data(buffer), std::size(buffer), &custom_memory_source);   // Monotonic buffer allocator, allocates memory from the buffer. Memory is released only when mbr.release() is called. If the buffer is exceeded, the upper-level allocator is used for allocation.
    {
        std::pmr::vector<std::pmr::string> vec{ &mbr };
        vec.push_back("Hello World");
        vec.push_back("One Two Three");
    }   // vec's memory is not released
    mbr.release();  // Memory in mbr is released at this point
}
```

From the above code, it can be seen that **MemoryResource** perfectly solves the problems of **allocator**. We only need to use containers from the namespace `std::pmr`.

How does it do this?

Taking `std::pmr::vector` as an example, find its definition:

```c++
namespace pmr {
    template <class _Ty>
    using vector = std::vector<_Ty, polymorphic_allocator<_Ty>>;
} // namespace pmr
```

It is very simple; it is just a `std::vector` using `polymorphic_allocator`. Finding its definition, you can see the following code:

```c++
template <class _Ty>
class polymorphic_allocator {
public:
    //...
    _NODISCARD __declspec(allocator) _Ty* allocate(_CRT_GUARDOVERFLOW const size_t _Count) {
        // Get space for _Count objects of type _Ty from _Resource
        void* const _Vp = _Resource->allocate(_Get_size_of_n<sizeof(_Ty)>(_Count), alignof(_Ty));
        return static_cast<_Ty*>(_Vp);
    }

    void deallocate(_Ty* const _Ptr, const size_t _Count) noexcept /* strengthened */ {
        // Return space for _Count objects of type _Ty to _Resource
        // No need to verify that size_t can represent the size of _Ty[_Count].
        _Resource->deallocate(_Ptr, _Count * sizeof(_Ty), alignof(_Ty));
        
private:
    memory_resource* _Resource = _STD pmr::get_default_resource();    
};
```

It is not difficult to find that it actually just calls the methods of `memory_resource` on the original `Allocator` interface.
