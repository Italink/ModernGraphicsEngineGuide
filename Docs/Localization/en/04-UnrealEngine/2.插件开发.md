Plugins exist independently of the engine and project code. They are the primary way to extend program functionality in UE.

Essentially, a plugin is a modular code design. Following this design reduces dependencies between code modules, making subsequent iterations and maintenance easier.

The standard file structure of a plugin in UE is as follows:

![image-20230525143413268](../../../04-UnrealEngine/Resources/image-20230525143413268.png)

-   `Binaries`: Stores compiled output files
-   `Content`: Stores the plugin's asset content
-   `Intermediate`: Stores intermediate files generated during compilation
-   `Resources`: Stores the plugin's resource files (e.g., icons) that are not UE assets
-   `Source`: Stores source code files and can contain multiple Modules

-   `*.uplugin`: The plugin's structural organization file

The basic content of `*.uplugin` is as follows:

``` c++
{
	"FileVersion": 3,				// File version
	"Version": 1,					// Version number
	"VersionName": "1.0",			// Version name
	"FriendlyName": "CustomPlugin",	// Alias
	"Description": "",				// Description
	"Category": "Other",			// Category
    "CreatedBy": "",				// Author
	"CreatedByURL": "",				// Author URL
	"DocsURL": "",					// Documentation URL
	"MarketplaceURL": "",			// Marketplace URL
	"SupportURL": "",				// Support URL
	"CanContainContent": false,		// Whether to include content directory
	"IsBetaVersion": false,			// Whether it is a beta version
	"IsExperimentalVersion": false,	// Whether it is an experimental version
	"Installed": false,				// Whether it is embedded
	"Modules": [					// Module definitions
		{
			"Name": "CustomPlugin",		// Module name
			"Type": "Editor",			// Module type
			"LoadingPhase": "Default"	// Loading phase
		}
        //,								// Other modules
        //{
        //	...    
        //}
	]
}
```

For configuration of these parameters, see:

These are the necessary files in a C++ plugin:

``` c++
// MyPlugin.h

#pragma once

#include "CoreMinimal.h"
#include "Modules/ModuleManager.h"

class FMyPluginModule : public IModuleInterface
{
public:

	/** IModuleInterface implementation */
	virtual void StartupModule() override;
	virtual void ShutdownModule() override;
};
```

``` c++
// MyPlugin.cpp

#include "MyPlugin.h"

#define LOCTEXT_NAMESPACE "FMyPluginModule"

void FMyPluginModule::StartupModule()
{
	// This code will execute after your module is loaded into memory; the exact timing is specified in the .uplugin file per-module
}

void FMyPluginModule::ShutdownModule()
{
	// This function may be called during shutdown to clean up your module.  For modules that support dynamic reloading,
	// we call this function before unloading the module.
}

#undef LOCTEXT_NAMESPACE
	
IMPLEMENT_MODULE(FMyPluginModule, MyPlugin)		// Define plugin entry point
```

UE calls `StartupModule()` when loading the plugin and `ShutdownModule()` when unloading the plugin.

The code workflow for plugin development is mainly:

-   In `StartupModule()`, call **core module function interfaces** or use **core module global singletons** to perform operations, or mount some logic to **core module entry points** for extensions.
-   In `ShutdownModule()`, clean up the operations performed in `StartupModule()`.

## Menu Bar and Toolbar Extension

During engine development, there are often requirements to extend the engine editor's menu bar and toolbar by adding a button to perform some convenient operations, like this:

![image-20220526100322912](../../../04-UnrealEngine/Resources/image-20220526100322912.png)

![image-20220526115630692](../../../04-UnrealEngine/Resources/image-20220526115630692.png)

In UE4, the main way to extend menus is through **FExtender**. In UE5, there is a new and easier way — **UToolMenus**.

**UToolMenus** is a singleton class. You can get the singleton instance with the following code:

``` c++
UToolMenus* ToolMenus = UToolMenus::Get();
```

In UE5, all extensible menu bars and toolbars call the function `UToolMenus::RegisterMenu` for registration `during initialization`:

```c++
UToolMenu* UToolMenus::RegisterMenu(const FName InName,
                                    const FName InParent = NAME_None,
                                    EMultiBoxType InType = EMultiBoxType::Menu,
                                    bool bWarnIfAlreadyRegistered = true)
```

![image-20230524155859423](../../../04-UnrealEngine/Resources/image-20230524155859423.png)

This function is used to register an extensible `ToolMenu`. The meanings of each parameter are as follows:

-   `InName`: The chain field used for registration, in the form of `LevelEditor.LevelEditorToolBar.User`. You can later use this field as a key to get the `UToolMenu`.
-   `InParent`: Specifies the parent of the tool menu.
-   `InType`: Specifies the type of the ToolMenu. This type determines how the menu can be extended. It can be one of the following values:
    -   `MenuBar`: Menu bar, supports extending menus
    -   `ToolBar`: Toolbar, can add tool buttons
    -   `VerticalToolBar`: Vertical toolbar
    -   `SlimHorizontalToolBar`: Horizontal toolbar, a slim version of the toolbar that aligns icons and text elements horizontally
    -   `UniformToolBar`:
    -   `Menu`: Menu, can add menu items
    -   `ButtonRow`: Buttons arranged in rows, with a maximum number of buttons per row. Similar to a toolbar but can have multiple rows.
-   `bWarnIfAlreadyRegistered`: Boolean value. If the field is already registered, a warning is issued.

When the menu needs to be `previewed`, the function `UToolMenus::GenerateWidget` is called to generate the `ToolMenu` control:

```c++
TSharedRef<SWidget> UToolMenus::GenerateWidget(const FName Name, const FToolMenuContext& InMenuContext)
```

![image-20230524154628869](../../../04-UnrealEngine/Resources/image-20230524154628869.png)

After the `ToolMenu` is registered, we can extend the menu content at any time before preview by calling the function `UToolMenus::ExtendMenu`.

``` c++
UToolMenu* UToolMenus::ExtendMenu(const FName InName)
```

![image-20230524160554125](../../../04-UnrealEngine/Resources/image-20230524160554125.png)

There are many extension references in the code above, and here is a simple plugin extension example:

``` c++
#pragma once

#include "Modules/ModuleManager.h"

class FCustomPluginModule : public IModuleInterface
{
public:
	virtual void StartupModule() override {
		// Add a callback to UToolMenus' startup when the plugin starts
		UToolMenus::RegisterStartupCallback(FSimpleMulticastDelegate::FDelegate::CreateRaw(this, &FCustomPluginModule::RegisterMenus));
	}

	virtual void ShutdownModule() override {
		// Remove UToolMenus' startup callback and reset some states
		UToolMenus::UnRegisterStartupCallback(this);
		UToolMenus::UnregisterOwner(this);
	}
private:
	void RegisterMenus() {
		FToolMenuOwnerScoped OwnerScoped(this);
		UToolMenu* Menu = UToolMenus::Get()->ExtendMenu("LevelEditor.LevelEditorToolBar.PlayToolBar");
		FToolMenuSection& Section = Menu->FindOrAddSection("PluginTools");
		FToolMenuEntry& MenuEntry = Section.AddEntry(
			FToolMenuEntry::InitToolBarButton(			// Add toolbar button
				"CustomToolbarButton",
				FUIAction
				(
					FExecuteAction::CreateLambda([]() {
						FMessageDialog::Open(EAppMsgType::Ok, NSLOCTEXT("CustomNs", "HelloWorld", "Hello World!"));
					})
				)
			)
		);
		MenuEntry.InsertPosition = FToolMenuInsert(NAME_None, EToolMenuInsertType::First);
	}
};
```

This code adds a button to the toolbar of the level editor main panel. When clicked, it pops up a `Hello World` dialog box:

### Undo and Redo

UObject has a transaction mechanism. If a UObject has the flag `RF_Transactional`, you can use the following code:

```C++
GEditor->BeginTransaction(NSLOCTEXT("NS", "Transaction", "Transaction"));       // Start transaction
Object->Modify();               // This operation stores the current state of Object in the transaction

SomeChange(Object);             // Modify some properties of Object

GEditor->EndTransaction();      // End transaction and commit the new state of Object
```

The above operation allows SomeChanged to be undone and redone.

> For details, see: https://blog.csdn.net/qq_29523119/article/details/96778797

In editor development, it is often necessary for an object or window to respond to changes (e.g., rebuild) when undo/redo is performed. UE provides the interface **FEditorUndoClient** for listening to undo/redo events. A simple code example is as follows:

```C++
class FUndoRedoListener: public FEditorUndoClient{
public:
    FUndoRedoListener(){
        if (GEditor)
            GEditor->RegisterForUndo(this);     // Register the listener at the appropriate time, not necessarily in the constructor
    }
    ~FUndoRedoListener(){
        if (GEditor)
            GEditor->UnregisterForUndo(this);   // Unregister
    }
protected:
    virtual void PostUndo(bool bSuccess) override{      // Called after the editor performs undo
        RebuildSomething();
    }
    virtual void PostRedo(bool bSuccess) override{      // Called after the editor performs redo
        RebuildSomething();
    }
};
```
