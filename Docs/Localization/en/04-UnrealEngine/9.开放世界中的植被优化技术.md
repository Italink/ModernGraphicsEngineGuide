In open natural scenes, the frequency and impact of performance issues caused by vegetation are often no less than those caused by lighting and special effects.

These asset-level optimizations and complex specialized methods often struggle to support the lush vegetation ecosystems in open scenes.

Therefore, this article will elaborate on some strategies and perspectives regarding vegetation optimization.

## Plant Asset Production

Most 3D modeling software can create plant assets, but in the game industry, **[Speed Tree](https://store.speedtree.com/)** is the mainstream vegetation production tool.

![image-20240808182351274](../../../04-UnrealEngine/Resources/image-20240808182351274.png)

Unlike common models such as rocks, items, and buildings, plants often have a large number of stems and leaves. Geometrically, this means plant models usually have a large number of dense vertices and faces, which brings very high rendering costs. Here is an example:

![image-20240808193318835](../../../04-UnrealEngine/Resources/image-20240808193318835.png)

- Such a not-so-lush tree has up to two million triangles. This huge amount of vertex data and numerous repeated draws will keep the GPU busy.

This method of using model geometry to represent plant structures is generally called **model trees/grass**. Usually, assets of this specification cannot be used in large quantities in game projects.

In existing game projects, plant assets are more often made using the **card/mask** method. By pressing some branches and leaves onto a texture sheet and inserting a large number of cards on the branches to show a lush appearance, this is a very clever production method. Although there are some flaws in the effect, the performance benefits it brings are very objective.

![image-20240808195330576](../../../04-UnrealEngine/Resources/image-20240808195330576.png)

The card method has long been recognized as the most efficient way for vegetation rendering in the game industry, but it also has some defects:

- Visual defects, easy to be exposed in close-up shots.
- Using mask materials, although the number of vertices is reduced, there is still a lot of OverDraw, and the shadow rendering cost is higher.
- Plant models lack vertex features of branches and leaves, resulting in loss of global illumination effects.

With the emergence of UE5's virtual geometry technology - Nanite, this situation has changed somewhat.

The advantage of Nanite lies in using a GPU-driven pipeline, which can quickly switch geometric details and timely cull invisible triangles, greatly improving vertex utilization (screen space ratio) without affecting the visual effect as much as possible.

![image-20240808202239795](../../../04-UnrealEngine/Resources/image-20240808202239795.png)

### The Downside of Nanite

The reason for the negative answer is not about the vertex data volume and video memory usage, because vegetation in the scene is usually drawn in an instanced way, especially in open world scenes. We are very concerned about the load balance of performance between partitions. Although a **single** model tree using Nanite may indeed have better performance, it will also hinder us from building a unified vegetation strategy with superior performance.

The following will elaborate on the problems of using Nanite from several aspects. The views may be somewhat subjective. If there are any mistakes, please correct them~

- Higher effect expectations, accompanied by more difficult performance balance control
- Unable to specialize model optimization strategies, and not the most performance-optimal model optimization processing method
- Static data with fixed precision gradients is easier to organize into high-performance dense vegetation

#### Unable to specialize model optimization strategies, and not the most performance-optimal model optimization processing method

There are usually two ways to optimize models:

- **Reduce**:删减 the geometric data of the source model to get a simplified model.
- **Remesh**: Approximate the source model with a certain voxel precision through voxelization model algorithms to get a simplified model.

These two strategies have different application scenarios:

- Reduce: Suitable for planes, usually used for models with high requirements for geometric edges and corners, such as terrain, buildings, plants, water planes...
- Remesh: Suitable for closed models with relatively rounded geometric shapes, which can usually ensure the geometric shape of the source model with very few vertices, such as stones, buildings, props...

For trees, if we use these two strategies to generate simplified models with the same number of triangles:

![image-20240809151946858](../../../04-UnrealEngine/Resources/image-20240809151946858.png)

> Nanite uses the Reduce algorithm. It can be understood that the reduced model will be a certain precision gradient of Nanite. The Nanite strategy is to prioritize ensuring that the画面 is not distorted. If this tree uses Nanite directly, how far do you think it needs to be to display such precision? Obviously, it has to be very far, and there are still many vertices at this time.

Both strategies have their own problems:

- Remesh: The model becomes fluffy, and black blocks appear where UV mapping is abnormal. (In fact, to generate a good Remesh model, the parameters of the voxel algorithm need a lot of fine-tuning and specialization)
- Reduce: A lot of leaf details are lost.

In this regard, I have done many attempts and can clearly say that it is difficult to get excellent plant LOD through automated model processing algorithms with unified strategies.

Why is vegetation optimization so difficult? Because many times people treat it as a regular model in the engine's rendering mechanism for optimization, but the most critical part of making good vegetation in games is the production skills.

For manually making LOD, art students can use as few main branches as possible to create a larger coverage area, use secondary branches to add local details to the main branches, and when making low-level LOD, only need to cut off a certain number of secondary branches.

You can also adjust the vertex color to distinguish between main and secondary branches, and finally use the vertex color weight-based reduction method for plants.

> Usually, vertex colors are painted on trees as weights for the vertex offset amplitude during plant wind calculation. This weight factor can also be used as the weight for regional simplification.

This method can be used to generate several high-precision LODs of plant models, but unfortunately, the simplified models generated in this way still often have a high number of vertices (when simplified to more than 1500 vertices, the model is already unrecognizable). To further reduce the number of vertices significantly (without cutting the main branches, otherwise there will be great visual defects) while ensuring the model's performance effect, it is obvious that the simplification method cannot do this. We must break the original geometric structure of the model. However, the Remesh method often makes a tree very fluffy and has UV mapping abnormalities. Its performance effect is not good. Is there any other way to solve this problem?

The answer is yes. Our ultimate goal is to ensure the display effect of the model, not the geometric structure. This also leads to another strategy for model optimization - **Impostor**.

> Impostor is my own translation. Translating it as "proxy" is easy to confuse with Proxy, and translating it as "impostor" is not very nice.

We usually use Impostor as the last level LOD of vegetation models. Common Impostor strategies include the following:

- **Billboard**: Draw the model from a specific angle onto a texture.
- **Flipbook**: Draw the model from multiple angles onto a texture, and finally switch the displayed texture according to the player's perspective in the material.
- **Billboard Cloud/ Mesh Card Cloud**: Draw the model on many mesh cards to stack up the perspective effect similar to the source model.
- **Octahedron**: Draw the model with a certain perspective distribution onto a texture, and finally interpolate images from multiple angles in the material to present a reliable perspective transition effect.

The above LOD chain also leads us to think about another problem:

- For the problem of multi-quality compatibility, in the traditional LOD strategy, we usually adjust the **Bias** of LOD to do compatibility for different qualities. For example, in high quality, the LOD chain starts from `LOD0`, and in low quality, the LOD chain can start from `LOD1` or LOD, which can greatly reduce the number of vertices, thereby improving scene performance. But in Nanite, what should we do?

The LOD of a model is usually manually supervised, which needs to ensure **clear optimization range** and **smooth transition effect**. To achieve this, each model's LOD usually needs to be **manually** made or use **non-unified parameter** model simplification strategies.

Nanite is different. Nanite uses a unified reduction strategy for all models. This strategy optimizes vertices as much as possible while ensuring the visual effect. This strategy will lead to some models having high degradation efficiency and some having low degradation efficiency due to different model characteristics.

Although Nanite can also adjust the offset and degradation multiplier, using unified parameters will definitely break the above strategy, leading to the visual effect of the model not being guaranteed, and some abnormalities or even broken faces that users cannot accept.

This is not just for vegetation, but for all models using Nanite.

#### Static data with fixed precision gradients is easier to organize into high-performance dense vegetation

My understanding of Nanite has gone through several stages:

1. "Use it as much as possible": Turn on Nanite for everything.
2. Encountered a pitfall: Grass should not use Nanite. There are some bugs when using Nanite for objects with dense instanced rendering.
3. Encountered another pitfall: The characteristics of Nanite cannot fit the HISM mechanism. Theoretically, objects that need HISM for efficient rendering cannot use Nanite.
4. After in-depth understanding of the production methods of some projects - who uses Nanite for vegetation seriously?

Let's talk about the first pitfall. Nanite's reduction is friendly to individual instances. It can easily reduce a model with millions of triangles and a relatively rounded geometry to empty pixels and finally be culled. However, for grass or trees that have tens of thousands of instances through instancing, the degradation of Nanite cannot efficiently reduce instances, and a large number of vertices will undoubtedly generate huge overhead for Nanite's scheduling calculation, further occupying the computing resources of other GPU tasks. This is especially obvious on some mid-to-low-end models.

> When the number of Nanite instances in the current画面 exceeds a certain threshold, it may even cause画面 abnormalities, although there are some engine commands that help improve this phenomenon.

The second pitfall should be discussed in combination with the HLOD of world partitioning. HLOD is a **distant proxy** used to display outside the streaming loading range in the open world. Ordinary models can generate distant HLOD through **Merge** + **Remesh** in the partition. However, for vegetation, using the voxelized Remesh algorithm for objects with many fragmented planes will generate marshmallows. The **Merge** + **Reduce** method cannot guarantee the画面 quality of distant vegetation while greatly reducing the number of vertices and DrawCall. Therefore, the HLOD of vegetation can only use **Instancing**. The instancing optimization in world partitioning, in addition to **regional切块** for instanced vegetation, also needs to use **Hierarchical Instanced Static Mesh (HISM)**, which is different from **Instanced Static Mesh (ISM)**. Hierarchical instanced meshes allow switching LOD inside the instanced mesh. For example, all the trees below are drawn with one HISM:

![image-20240809135411348](../../../04-UnrealEngine/Resources/image-20240809135411348.png)

HISM essentially divides the instanced mesh into ClusterTree, each Cluster has its own independent LOD level, and finally generates multiple levels of ISM. Through some engine commands, we can control the division strategy of HISM. For specific implementation details, you can refer to:

- [UHierarchicalInstancedStaticMesh (HISM) Principle Analysis - CSDN Blog](https://blog.csdn.net/qq_29523119/article/details/123932029)
- [HISM Large-scale Vegetation Rendering Solution - CSDN Blog](https://blog.csdn.net/ZJU_fish1996/article/details/108806360)

Unlike traditional LOD schemes, Nanite does not have a few models with fixed precision gradients. Its LOD gradient is not at the model level, but at the cluster level. Therefore, the HISM mechanism cannot work normally on models using Nanite.

### Summary

I have said a lot of trivial information above, and here is a unified summary:

- For plants with the same lushness, using the model tree method will generate a large number of vertices, and the performance and memory consumption it brings are much higher than those of the card tree method.
- The current reduction strategy of Nanite has low degradation efficiency for leaves, while manually controlling the LOD precision gradient and using Impostor can usually produce vegetation with better performance.

Scene models are generally placed in `Main Grid`, but considering that the cell size (CellSize) will also affect the distance of HLOD batching, I recommend putting vegetation in `AdvanceGrid`.

Unlike other regular static models, vegetation cannot generate a high-quality distant proxy by Merge+Remesh in open world scenes. But vegetation cannot be Merge into a Mesh, or after Merge into a Mesh, there is no good strategy to ensure the effect of vegetation while greatly reducing its vertices and optimizing its materials. Therefore, if you want to make a large range of vegetation, you can only use the instanced way to lay it. To ensure the load balance of performance between the world partition units, we must strictly control the number of plant types. There will definitely be some compromises in the art effect.

> Distance culling usually causes serious visual defects. If we can use some means (such as fog, corners) to block the vegetation at a distance, we do not need to consider the problem of distant proxies in this case. In this case, treat the plant as a regular Mesh, turn on Nanite, and combine with the unloading or distance culling of world partitioning to achieve good performance effects.

Usually, vegetation uses HISM for organization at close range. After exceeding the loading range:

- For small vegetation, you can directly not display the distant proxy. If you use terrain grass, you usually need to ensure that the color of the grass is basically the same as the terrain color, so that there will be no particularly obvious visual defects at a distance. If you do not use terrain grass but use procedural grass, you can bake a color texture from the top view in the procedural blueprint in the editor and render it as a decal as the distant proxy of the grass.
- For large vegetation, usually referring to trees, after exceeding the loading range, HISM can be degraded to ISM using the lowest level LOD as HLOD (HISM has the overhead of cluster division and LOD switching scheduling), like this:

![image-20240809173840266](../../../04-UnrealEngine/Resources/image-20240809173840266.png)

> The LOD of vegetation needs to be able to transition smoothly. Since HISM will become ISM when exceeding the loading range, it is necessary to ensure that the LOD levels on the left and right sides of the loading distance are consistent, which means that the LOD gradient of the model is distributed within the loading distance. Since UE currently uses the screen space size as the basis for model LOD switching, it needs to be converted to the corresponding distance during production.

Although with the blessing of world partitioning, it does not mean that we can build an infinitely large scene. Its advantage is more about seamless loading. The real-time computing resources of the computer are limited. Although this batching mechanism can further expand the distance, the larger the range, the greater the performance overhead, and the less budget left for gameplay. Therefore, the distance that the character can see should still be maintained within a certain distance, such as 768 m:

![image-20240809174827247](../../../04-UnrealEngine/Resources/image-20240809174827247.png)

> Not only trees, but also other models, particles, dynamic material effects, etc. are recommended to follow this rule.

## Shadow Optimization

The shadow consumption of vegetation is often a large part of the entire scene, because it has a large number of dense and overlapping triangles.

So how to optimize shadows?

First, we need to think about a question: Why do we need shadows? If we turn off the shadows, we will see:

![image-20240809193856172](../../../04-UnrealEngine/Resources/image-20240809193856172.png)

If players are asked after watching the above comparison画面: Do you like the画面 with shadows or the one without shadows?

Most players will probably answer: I choose the画面 with shadows.

Further question: Why do you like the画面 with shadows?

## Collision and Interaction Optimization

For the collision production of trees, it depends on the project's requirements for the scene. After being familiar with some of the mesh processing algorithms mentioned earlier, we can also easily build a generation pipeline for tree collision bodies. For example, using the fluffy characteristics of Remesh can easily generate a collision body with a small number of vertices like a marshmallow, or generate a collision only for the trunk part according to the distribution of vertex colors...

For interaction, since we use HISM at close range, which is not a real individual, it usually cannot interact normally.

If we need interaction, we need to do some special processing on HISM. For example, the engine extends **UFoliageInstancedStaticMeshComponent**, which can be used to handle the damage calculation of instances:

![image-20240809223452013](../../../04-UnrealEngine/Resources/image-20240809223452013.png)

If there is a demand, you can also derive HISM yourself to make close-range instances degrade into actual Actors. Here, I do not recommend using the world partitioning method to manage this degradation.
