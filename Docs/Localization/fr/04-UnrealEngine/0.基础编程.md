# Documentation de programmation C++ pour Unreal Engine

## Préface

**Unreal Engine** est un moteur puissant écrit en C++, mais la présence de **Unreal Build Tool (UBT)** et de **Unreal Header Tool (UHT)** lui confère une syntaxe indépendante de la norme C++. C'est pourquoi les internautes l'appellent souvent **U++**.

Non seulement la syntaxe diffère, mais le flux de développement sous Unreal Engine est également très différent de celui du développement C++ classique. Par exemple, la bibliothèque standard STL ressemble à une boîte à outils (Toolkit) **que nous utilisons pour développer**, tandis qu'Unreal Engine est plutôt une plateforme de développement (Platform) **sur laquelle nous développons**.

Actuellement, les tutoriels et livres sur U++ sont peu nombreux. Parmi ceux qui sont utiles aux développeurs, on peut citer :

- [大象无形：虚幻引擎程序设计浅析 (L'Invisibilité de l'Éléphant : Analyse approfondie de la conception de programmes pour Unreal Engine)](https://book.douban.com/subject/27033749/)
- [UE4开发指南 - Gamedev Guide (Guide de développement UE4 - Gamedev Guide)](https://ikrima.dev/ue4guide/)
- [循迹研究室 - 查利鹏 (Laboratoire de Recherche sur les Traces - Zha Lipeng)](https://imzlp.com/)
- [剖析虚幻渲染体系 - 向往 (Analyse du système de rendu Unreal - Xiang Wang)](https://www.cnblogs.com/timlly/p/13512787.html)
- [InsideUE - 大钊 (InsideUE - Da Zhao)](https://zhuanlan.zhihu.com/p/22813908)

La documentation limitée et le code obscur d'Unreal Engine représentent un obstacle presque infranchissable pour les débutants en C++. En effet, Unreal Engine est un projet industriel développé par de nombreux ingénieurs, avec un codebase volumineux et une itération rapide. Il est donc très difficile de documenter et de synthétiser son évolution.

J'ai consulté certaines vidéos tutoriels sur U++, mais elles sont fragmentées. La plupart sont des tutoriels de base sur le C++ déguisés en cours sur UE, avec un contenu limité et de nombreuses lacunes. Les gains d'apprentissage ne sont pas très importants.

> Si vous découvrez de bons tutoriels, n'hésitez pas à les recommander dans les commentaires !

Pour maîtriser Unreal Engine, il faut souvent avoir la capacité de travailler sur des projets C++ de grande taille. Je peux dire clairement que **ce n'est pas adapté aux débutants en C++**.

Si vous êtes un étudiant qui a découvert Unreal Engine par hasard, été captivé par ses effets visuels spectaculaires et avez envie d'apprendre le développement U++ sur un coup de tête, vous devriez vous demander si, outre résoudre des exercices et écrire des dissertations, vous possédez les compétences suivantes :

- Maîtrise de la construction de projets C++
- Connaissance des différents sous-modules du moteur et capacité à lire le code source de projets de grande taille

Si ce n'est pas le cas, je vous conseille de prendre le temps de renforcer vos bases plutôt que de vous lancer tête baissée.

Les bases ne deviennent solides qu'après des années de pratique, et la technologie s'accumule progressivement pour s'élever niveau par niveau. Il ne faut pas chercher à "dépasser les autres en coup de volant" ou écouter les histoires sur quelqu'un qui aurait acquis une grande expertise en peu de temps. En réalité, **dans l'industrie, il n'y a pas de génie qui ne travaille pas**. Du moins, parmi les personnes que je respecte, c'est le cas pour tous. De plus, la technologie n'a pas de hiérarchie de force ; la plupart du temps, c'est simplement une question de **"qui a appris en premier" et "spécialisation dans un domaine"**.

## Structure du projet

La structure de fichiers d'un projet UE standard est la suivante :

![image-20230517115452232](../../../04-UnrealEngine/Resources/image-20230517115452232-16848129576282.png)

- `Config` : Contient divers fichiers de configuration du projet (GameConfig, EngineConfig, EditorConfig, PluginConfig...)
- `Content` : Contient les fichiers de ressources du projet
- `Saved` : Répertoire temporaire où sont stockés les fichiers générés pendant le développement du projet, y compris les journaux, les enregistrements de crash, les données de cuisson et les configurations locales de l'éditeur
- `Source` : Contient les fichiers de code source du projet
- `MyProj.uproject` : Fichier de projet

### uproject

`*.uproject` stocke des informations de base sur le projet. Sa structure initiale est la suivante :

```json
{
	"FileVersion": 3,
	"EngineAssociation": "5.2",		
	"Category": "",
	"Description": "",
	"Modules": [					
		{
			"Name": "MyProj",
			"Type": "Runtime",
			"LoadingPhase": "Default"
		}
	],
	"Plugins": [
		{
			"Name": "ModelingToolsEditorMode",
			"Enabled": true,
			"TargetAllowList": [
				"Editor"
			]
		}
	]
}
```

Les paramètres clés de ce fichier sont :

- `EngineAssociation` : Version du moteur
- `Modules` : Modules de code du projet
- `Plugins` : Plugins intégrés activés pour le projet

Ces paramètres peuvent être modifiés manuellement, mais il est plus sûr et plus pratique de le faire via l'éditeur UE.

#### Ajouter des modules au projet

Les **modules** sont les blocs de construction fondamentaux de l'architecture logicielle d'**Unreal Engine (UE)**. Ils encapsulent des outils de programmation, des fonctionnalités runtime, des bibliothèques ou d'autres fonctionnalités dans des unités de code indépendantes.

L'utilisation de la programmation modulaire offre les avantages suivants :

- Les modules imposent une bonne séparation du code, qui peut être utilisé pour encapsuler des fonctionnalités et cacher les composants internes du code.
- Les modules sont compilés en unités de compilation séparées. Cela signifie que seul le module modifié doit être recompilé, ce qui réduit considérablement le temps de compilation pour les grands projets.
- Les modules sont liés dans un graphe de dépendances et ne permettent aux paquets de code réellement utilisés d'inclure des fichiers d'en-tête, conformément à la norme [Include What You Use (IWYU)](https://docs.unrealengine.com/5.2/zh-CN/include-what-you-use-iwyu-for-unreal-engine-programming). Cela signifie que les modules non utilisés dans votre projet seront exclus en toute sécurité de l'édition.
- Vous pouvez contrôler le chargement et le déchargement des modules à n'importe quel moment pendant l'exécution. Ainsi, vous pouvez gérer quels systèmes sont disponibles et actifs, optimisant ainsi les performances du projet.
- Vous pouvez inclure ou exclure des modules dans votre projet en fonction de conditions spécifiques (par exemple, la plateforme pour laquelle le projet est développé).

Tous les projets et plugins ont par défaut leur propre **module principal**.

Dans le panneau principal de l'éditeur UE - `Outils (Tools)` - `Débogage (Debug)` - `Modules (Modules)`, vous pouvez voir tous les modules activés pour le projet actuel :

![image-20230523115940276](../../../04-UnrealEngine/Resources/image-20230523115940276.png)

Pour plus d'informations sur la création de modules, consultez :

- Modules Unreal Engine : https://docs.unrealengine.com/5.2/zh-CN/unreal-engine-modules/
- Créer un module Gameplay : https://docs.unrealengine.com/5.2/zh-CN/how-to-make-a-gameplay-module-in-unreal-engine/

En plus de lire la documentation, vous devez également comprendre les concepts de base de la construction de projets C++ :

- `*.Build.cs` est le fichier de construction du module UE. Il définit les règles de construction du module, y compris les chemins d'inclusion, les bibliothèques dépendantes, les options de compilation, etc. (similaire à CMakeLists.txt pour CMake).

La structure d'un `*.Build.cs` de base est la suivante :

```C#
using UnrealBuildTool;
using System.IO; // for Path
public class ModuleName : ModuleRules
{
	public ModuleName(ReadOnlyTargetRules Target) : base(Target)
	{
		PCHUsage = ModuleRules.PCHUsageMode.UseExplicitOrSharedPCHs;

		PublicIncludePaths.AddRange(
			new string[] {
				// ... ajouter ici les chemins d'inclusion publics nécessaires ...
			}
		);


		PrivateIncludePaths.AddRange(
			new string[] {
				// ... ajouter ici les autres chemins d'inclusion privés nécessaires ...
			}
		);


		PublicDependencyModuleNames.AddRange(
			new string[]
			{
				"Core",
				"CoreUObject",
				"Engine",
				// ... ajouter ici les autres dépendances publiques avec lesquelles vous liez statiquement ...
			}
		);

		PrivateDependencyModuleNames.AddRange(
			new string[]
			{
				// ... ajouter ici les autres dépendances privées avec lesquelles vous liez statiquement ...	
			}
		);
	}
}
```

- L'outil de construction UE (UBT) génère le **fichier de projet** (fichier `*.sln` pour les projets VS) en fonction de `*.Build.cs`. Par conséquent, si vous modifiez le contenu de `*.Build.cs` ou la structure des fichiers de code du module, vous devez régénérer le fichier de projet avec UBT pour que l'IDE puisse analyser les modifications du code et des relations de dépendance.
- Les chemins d'inclusion et les bibliothèques dépendantes sont des concepts de base de la construction de projets C++.
  - Les chemins d'inclusion sont utilisés pour ajouter des chemins de recherche pour les définitions des fichiers d'en-tête.
  - Les bibliothèques dépendantes sont utilisées pour **lier (Link)** l'implémentation de modules externes au module actuel.

Supposons qu'il existe un fichier d'en-tête C++ `D:/Unreal Projects/MyProj/Source/MyProj/MyHeader.h` dans le projet. Pour utiliser les définitions de code qu'il contient, vous pouvez directement écrire :

```c++
#include "D:/Unreal Projects/MyProj/Source/MyProj/MyHeader.h"
```

Si vous ajoutez `"D:/Unreal Projects/MyProj/Source/MyProj"` à `IncludePaths` dans `*.Build.cs`, vous pouvez remplacer par :

``` c++
#include "MyHeader.h"
```

Si vous voulez utiliser le code d'un autre module dans le module actuel, il suffit d'ajouter le nom du module cible à `DependencyModuleNames` dans `*.Build.cs`.

> Si vous ne faites pas cela, une erreur de liaison (Link Error) se produira lors de la compilation. Dans ce cas, il suffit de trouver le fichier de code de la structure utilisée, de déterminer quel `*.Build.cs` il appartient à via l'IDE, et d'ajouter son nom de module à `DependencyModuleNames` pour résoudre le problème.

#### Différence entre Public et Private

En bref, Public signifie transférable, Private signifie utilisé uniquement par soi-même.

Supposons qu'il y ait trois modules A, B, C, avec la structure de fichiers suivante :

- Dossier A
  - A.Build.cs
  - Dossier Public
    - a.h
  - Dossier Private
    - A.h
- Dossier B
  - B.Build.cs
  - Dossier Public
    - b.h
  - Dossier Private
    - B.h
- Dossier C
  - C.Build.cs
  - Dossier Public
    - c.h
  - Dossier Private
    - C.h

Le pseudo-code de `*.Build.cs` est le suivant :

```C#
public class A(ReadOnlyTargetRules Target) : base(Target){
}

public class B(ReadOnlyTargetRules Target) : base(Target){
    PrivateDependencyModuleNames.AddRange( new string[] { "A"});
}

public class C(ReadOnlyTargetRules Target) : base(Target){
    PublicDependencyModuleNames.AddRange( new string[] { "B"});
}
```

Si vous utilisez les fichiers des modules A et B dans **c.h**, les résultats suivants se produiront :

```c++
#include "C.h"
//【Erreur de compilation 0】, le dossier Private n'est pas un chemin de recherche pour le module C.

#include "b.h"
// Compilation normale. UE ajoute automatiquement le répertoire Public du module lui-même à PublicIncludePaths dans Build.cs. De plus, comme le module C a ajouté le module B en dépendance publique,
// le PublicIncludePaths du module B est également transmis au module C. Par conséquent, le module C peut accéder normalement au répertoire Public de B.


#include "B.h"	
//【Erreur de compilation 1】, le module C ne peut pas accéder au répertoire Private du module B.

#include "A.h"			
//【Erreur de compilation 2】, comme le module C a ajouté le module B en dépendance publique, mais le module B a ajouté le module A en dépendance privée,
// B peut utiliser normalement le contenu Public de A, mais C ne peut pas utiliser A.

#include "a.h"			
//【Erreur de compilation 3】, le module C ne peut pas accéder à aucun contenu du module A.

```

Pour corriger ces erreurs, vous pouvez modifier la structure de `*.Build.cs` comme suit :

``` C#
public class A(ReadOnlyTargetRules Target) : base(Target){
    PublicIncludePaths.AddRange( new string[] { "Private"});	// Corrige【Erreur de compilation 3】, ajoute le dossier Private du module A au chemin d'inclusion public.
}

public class B(ReadOnlyTargetRules Target) : base(Target){
    PublicDependencyModuleNames.AddRange( new string[] { "A"});	// Corrige【Erreurs de compilation 2 et 3】, ajoute le module A en dépendance publique du module B, ce qui signifie une dépendance transférable.
    PublicIncludePaths.AddRange( new string[] { "Private"});	// Corrige【Erreur de compilation 1】, ajoute le dossier Private du module B au chemin d'inclusion public.
}

public class C(ReadOnlyTargetRules Target) : base(Target){		
    PublicDependencyModuleNames.AddRange( new string[] { "B"});
    PublicIncludePaths.AddRange( new string[] { "Private"});	// Corrige【Erreur de compilation 0】, ajoute le dossier Private du module C au chemin d'inclusion public.
}
```

Après avoir vu l'exemple ci-dessus, il n'est pas difficile de comprendre la différence entre Public et Private :

- Public signifie transférable
- Private signifie utilisé uniquement par le module actuel

Vous vous demandez peut-être pourquoi ne pas utiliser Public uniformément, ce qui éviterait beaucoup d'opérations. La raison est qu'il y a des problèmes :

- Conflits de définitions : Lorsque des modules introduits ont des définitions chevauchantes (classes, fonctions, variables globales), des erreurs de compilation se produisent.
- Compilation lente : Si le module B introduit le module A, toute modification du code du module A déclenchera une recompilation du module B. Ainsi, de nombreuses dépendances non nécessaires ralentiront considérablement la compilation, comme `#include "CoreMinimal.h"`.

Pour éviter les risques de conflits de compilation et la lenteur, il faut utiliser Private autant que possible et ne considérer Public que lorsque le module doit être transmis à l'extérieur.

## Système d'objets

Le corps logique d'Unreal Engine adopte un paradigme de conception orienté objet. Pour que toutes les **classes (Class)** puissent être gérées de manière uniforme, Unreal fournit, comme d'autres frameworks orientés objet, sa propre classe de base — **UObject**.

### Structure

Sa hiérarchie de structure est la suivante :

![image-20220622175331091](../../../04-UnrealEngine/Resources/image-20220622175331091-1740212922378-1.png)

Elle est principalement composée de trois niveaux, chacun ayant des responsabilités différentes :

- **UObjectBase** : Couche de données, définit toutes les données de base de UObject, y compris :
  - **ObjectFlags** : Divers identifiants de l'Object
  - **InternalIndex** : Tous les pointeurs d'Object dans UE sont stockés dans un tableau. Cet index permet une localisation rapide dans le tableau, principalement utilisé pour le GC.
  - **ClassPrivate** : Type méta de l'Object — UClass : stocke les données de réflexion de la classe.
  - **NamePrivate** : Nom de l'Object
  - **OuterPrivate** : Objet qui détient cet Object (lié à la sérialisation, **pas à la durée de vie**)
- **UObjectBaseUtility** : Couche d'interface de données, fournit de nombreuses interfaces de traitement pour la couche de données.

![image-20220622180328342](../../../04-UnrealEngine/Resources/image-20220622180328342-1740212957319-4.png)

- **UObject** : Couche fonctionnelle, fournit de nombreuses interfaces de fonctions de base pour le système d'objets.

Dans le constructeur de **UObjectBase**, il y a le code suivant :

```c++
UObjectBase::UObjectBase(UClass* InClass, EObjectFlags InFlags, EInternalObjectFlags InInternalFlags, UObject *InOuter, FName InName)
:   ObjectFlags         (InFlags)
,   InternalIndex       (INDEX_NONE)
,   ClassPrivate        (InClass)
,   OuterPrivate        (InOuter)
{
    check(ClassPrivate);
    // Ajouter au tableau global.
    AddObject(InName, InInternalFlags);
}
```

AddObject stocke l'adresse du nouveau UObject dans la variable globale **GUObjectArray**, qui se trouve dans : `Runtime\CoreUObject\Private\UObject\UObjectHash.cpp`

```c++
// Instance globale du tableau UObject
FUObjectArray GUObjectArray;
```

La définition de **FUObjectArray** se trouve dans `Runtime\CoreUObject\Public\UObject\UObjectArray.h`. Elle est principalement utilisée pour gérer tous les objets, les clusters et le GC. Ses membres de données principaux sont :

```c++
class FUObjectArray{
    //typedef TStaticIndirectArrayThreadSafeRead<UObjectBase, 8 * 1024 * 1024 /* Max 8M UObjects */, 16384 /* alloué en blocs de 64K/128K */ > TUObjectArray;
    typedef FChunkedFixedUObjectArray TUObjectArray;

    // Note : ces variables conservent le préfixe Obj pour pouvoir être liées aux versions historiques de GObj.

    /** Premier index dans le tableau des objets pris en compte pour le GC.                           */
    int32 ObjFirstGCIndex;
    /** Index pointant au dernier objet créé dans la plage ignorée par le GC.                  */
    int32 ObjLastNonGCIndex;
    /** Nombre maximum d'objets dans la plage ignorée par le GC */
    int32 MaxObjectsNotConsideredByGC;

    /** Si vrai, c'est le chargement initial et nous devons charger les objets dans la plage ignorée par le GC.    */
    bool OpenForDisregardForGC;
    /** Tableau de tous les objets actifs.                                          */
    TUObjectArray ObjObjects;
    /** Objet de synchronisation pour tous les objets actifs.                                            */
    mutable FCriticalSection ObjObjectsCritical;
    /** Indices d'objets disponibles.                                           */
    TArray<int32> ObjAvailableList;

    /**
     * Tableau des éléments à notifier lors de la création d'un UObjectBase
     */
    TArray<FUObjectCreateListener* > UObjectCreateListeners;
    /**
     * Tableau des éléments à notifier lors de la destruction d'un UObjectBase
     */
    TArray<FUObjectDeleteListener* > UObjectDeleteListeners;

### Création

La définition d'une classe UObject simple est la suivante :

``` c++

#include "UObject/Object.h"

UCLASS()
class UCustomObject :public UObject {

Pour créer une instance d'objet UObject, on utilise généralement la fonction `NewObject<>()`, par exemple `NewObject<UCustomObject>()`. Sa définition complète est :

```c++
/**
 * Modèle de commodité pour construire un objet gameplay
 *
 * @param	Outer		l'outer pour le nouvel objet. Si non spécifié, l'objet sera créé dans le package transitoire.
 * @param	Class		la classe de l'objet à construire
 * @param	Name		le nom du nouvel objet. Si non spécifié, l'objet recevra un nom transitoire via MakeUniqueObjectName
 * @param	Flags		les flags de l'objet à appliquer au nouvel objet
 * @param	Template	l'objet à utiliser pour initialiser le nouvel objet. Si non spécifié, l'objet par défaut de la classe sera utilisé
 * @param	bCopyTransientsFromClassDefaults	si vrai, copier les transitoires depuis les valeurs par défaut de la classe au lieu du pointeur d'archétype passé (souvent les mêmes)
 * @param	InInstanceGraph						contient les mappings des objets et composants instanciés à leurs templates
 * @param	ExternalPackage						Attribuer un Package externe à l'objet créé si non null
 *
 * @return	un pointeur de type T vers un nouvel objet de la classe spécifiée
 */
template< class T >
FUNCTION_NON_NULL_RETURN_START
	T* NewObject(UObject* Outer,
                 const UClass* Class, 
                 FName Name = NAME_None,
                 EObjectFlags Flags = RF_NoFlags,
                 UObject* Template = nullptr, 
                 bool bCopyTransientsFromClassDefaults = false,
                 FObjectInstancingGraph* InInstanceGraph = nullptr,
                 UPackage* ExternalPackage = nullptr)
{
	if (Name == NAME_None)
	{
		FObjectInitializer::AssertIfInConstructor(Outer, TEXT("NewObject avec un nom vide ne peut pas être utilisé pour créer des sous-objets par défaut (dans le constructeur d'une classe dérivée de UObject) car cela produit des noms d'objets incohérents. Utilisez ObjectInitializer.CreateDefaultSubobject<> à la place."));
	}

#if DO_CHECK
	// La classe a été spécifiée explicitement, donc elle doit être validée
	CheckIsClassChildOf_Internal(T::StaticClass(), Class);
#endif

	FStaticConstructObjectParameters Params(Class);
	Params.Outer = Outer;
	Params.Name = Name;
	Params.SetFlags = Flags;
	Params.Template = Template;
	Params.bCopyTransientsFromClassDefaults = bCopyTransientsFromClassDefaults;
	Params.InstanceGraph = InInstanceGraph;
	Params.ExternalPackage = ExternalPackage;
	return static_cast<T*>(StaticConstructObject_Internal(Params));
}
```

Concernant la création d'Object, il faut noter几点 :

- **Outer n'a aucun lien avec la durée de vie de l'Object** : Le paramètre Outer indique à quel objet parent l'objet actuel appartient **sur le plan du stockage**. Il est lié à la sérialisation des assets.

- **On peut créer un objet via UClass** : `NewObject<UCustomObject>()` est équivalent à `NewObject<UObject>(GetTransientPackage(), UCustomObject::StaticClass())`

En général, la plupart des objets que nous rencontrons dans Unreal Engine sont des **UObject**. Au niveau du code, pour créer n'importe quel UObject, on utilise généralement cette méthode :

``` c++
UObject* MyObject = NewObject<UObject>();

UTexture2D* MyTexture = NewObject<UTexture2D>();

UBlueprint* MyBlueprint = NewObject<UBlueprint>();

UStaticMesh* MyStaticMesh = NewObject<UStaticMesh>();

UNiagaraSystem* MyNiagaraSystem = NewObject<UNiagaraSystem>();

AActor* MyActor = NewObject<AActor>();

UStaticMeshComponent* MyStaticMeshComponent = NewObject<StaticMeshComponent>();

UWorld* World = NewObject<UWorld>();

...
```

Ces instructions n'ont pas d'erreur syntaxique dans Unreal et peuvent être compilées.

Mais les utilisateurs expérimentés d'Unreal savent que si on crée des objets directement de cette façon, bien qu'ils soient créés avec succès, certains de leurs mécanismes peuvent ne pas fonctionner correctement. Parce que ces types sont accompagnés de données et de logiques de construction spécifiques, et le moteur les encapsule souvent dans de nouvelles interfaces, par exemple :

- Utiliser `UWorld::CreateWorld(...)` pour construire UWorld
- Utiliser `UWorld::SpawnActor( ... )` pour créer un Actor dans le monde correspondant
- Utiliser `FKismetEditorUtilities::CreateBlueprint(...)` pour créer un Blueprint (UBlueprint) dans l'éditeur
- Utiliser `UObject::CreateDefaultSubobject(...)` dans le constructeur d'un Actor pour créer la structure de composants appartenant à cet Actor
- ...

Donc, si un objet créé avec `NewObject()` a des mécanismes qui ne fonctionnent pas correctement, il est probable que le moteur ait encapsulé une logique de construction spécifique. Si vous ne la trouvez pas, essayez de rechercher les logiques d'initialisation et d'enregistrement, puis exécutez-les manuellement.

### Destruction

Outre la création d'objets UObject, leur destruction, c'est-à-dire la gestion de leur durée de vie, est également très importante.

Comme on le sait, Unreal possède un mécanisme de garbage collection automatique, qui est un mode de récupération **basé sur les références d'objets,定时定量**.

Pour les développeurs, il n'est généralement pas nécessaire d'analyser en profondeur le principe d'exécution de ce mécanisme, mais de maîtriser son utilisation de base. Les points clés de l'utilisation sont :

- Comment le moteur détermine si un objet est un garbage ?
- Comment configurer et utiliser le GC ?

Dans UE, il y a **quatre voies directes** pour qu'un objet ne soit pas considéré comme garbage :

- Lors de `NewObject`, utiliser l'identifiant `EObjectFlags::RF_Standalone`. Cet identifiant garantit que l'objet créé ne sera jamais récupéré par le GC **dans l'éditeur** (voir `GarbageCollection.h ligne 28`).

- Utiliser la fonction `void UObject::AddToRoot()` pour ajouter l'objet à l'ensemble des objets racine, afin qu'il ne soit pas libéré. Utiliser `void UObject::RemoveFromRoot()` pour le retirer de l'ensemble des objets racine.

- Dériver la **classe FGCObject**, qui est largement utilisée pour la gestion de la durée de vie des objets dans les différents modules d'UE : [![image-20230523170954045](../../../04-UnrealEngine/Resources/image-20230523170954045-1740213062865-7.png)](https://italink.github.io/ModernGraphicsEngineGuide/04-UnrealEngine/Resources/image-20230523170954045.png)

    Lorsque UE exécute le GC, il appelle la fonction `virtual void AddReferencedObjects( FReferenceCollector& Collector )` de **tous les objets FGCObject**. **Collector** est une entrée d'opération. Les objets ajoutés à **Collector** ne seront pas libérés lors de ce GC.

    Le constructeur de **FGCObject** ajoute cet objet à la liste globale des objets FGCObject d'UE, ce qui signifie qu'un objet dérivé de la classe FGCObject peut être utilisé comme objet racine.

    Donc, les développeurs n'ont qu'à ajouter `public FGCObject` à la définition de leur structure native, puis dériver ses fonctions associées :

    ```
    class FMyManager : public FGCObject {
        virtual void AddReferencedObjects(FReferenceCollector& Collector) override {
            //Collector.AddReferencedObject(...)
            //..
        }
        virtual FString GetReferencerName() const override{ return TEXT("FMyManager"); }   
    };
    ```

- Utiliser le pointeur intelligent **TStrongObjectPtr** pour stocker l'objet. En réalité, il utilise toujours **FGCObject**, mais cette structure est très lourde et son utilisation à grande échelle n'est pas recommandée. Voir :

    - [Pointeurs intelligents d'UE4 liés à UObject](https://zhuanlan.zhihu.com/p/371851019)

La **voie indirecte** est :

- Lorsqu'un objet n'est pas garbage actuellement, les objets qu'il référence ne sont pas non plus garbage.

UE construit et analyse les références entre objets principalement via la réflexion. Par exemple, ce code :

```c++
UCLASS()
class UCustomObject :public UObject {
public:
    UCustomObject() {}

    UPROPERTY()         
    UObject* Prop = nullptr;
};

int main() {
    auto A = NewObject<UCustomObject>();
    auto B = NewObject<UCustomObject>();
    A->Prop = B;        
    A->AddToRoot();
    // Boucle du moteur
    return 0;
}
```

- Comme `objet A` est ajouté à l'ensemble des objets racine, il ne sera pas libéré. De plus, UE détermine via la réflexion que la `propriété Prop` de `objet A` référence `objet B`, donc B ne sera pas non plus libéré.

Concernant l'utilisation, on peut détruire manuellement un objet avec les fonctions suivantes :

- `bool UObject::ConditionalBeginDestroy()` : Détruit directement l'objet sans attendre le GC
- `void UObject::MarkAsGarbage()` : Marque l'objet comme garbage, il sera libéré lors du prochain GC

On peut aussi exécuter manuellement le GC dans la frame actuelle avec ce code :

```
bool bForceGarbageCollectionPurge = true;   // Si true, GC complet
GEngine->ForceGarbageCollection(bForceGarbageCollectionPurge);
```

De plus, il faut noter que le **système d'objets** et le **système de réflexion** d'UE sont complémentaires. Pour certaines raisons, les objets UObject **n'utilisent pas de destructeur** pour libérer les ressources. Donc, si vous avez besoin d'implémenter une logique de destructeur, surchargez la fonction virtuelle de UObject :

- `virtual void BeginDestroy()`

## Système de réflexion

La réflexion est un concept émergent dans le développement de programmes modernes. Elle vise à examiner le code sous l'angle Meta, en considérant les énumérations, classes, structures, fonctions... du code comme des assets accessibles et même manipulables à l'exécution. **En essence, c'est l'introspection du code C++.**

Pour plus d'informations sur le concept de réflexion et son implémentation de base, consultez :

- [Guide de démarrage sur les moteurs graphiques modernes (cinq) — Macro, Template, Réflexion](https://zhuanlan.zhihu.com/p/600456225)

### Structure

Dans UE, un exemple de marqueur de réflexion relativement complet est le suivant :

```c++
/*CustomStruct.h*/
#pragma once        
#include "UObject/Object.h"
#include "CustomStruct.generated.h"

UCLASS()
class UCustomClass :public UObject {
    GENERATED_BODY()
public:
    UCustomClass() {}
public:
    UFUNCTION()
    static int Add(int a, int b) {
        UE_LOG(LogTemp, Warning, TEXT("Hello World"));
        return a + b;
    }

private:
    UPROPERTY(meta = (Keywords = "This is keywords"))
    int SimpleValue = 123;

    UPROPERTY()
    TMap<FString, int> ComplexValue = { {"Key0",0},{"Key1",1} };
};
```

UENUM()
enum class ECustomEnum : uint8 {
    One UMETA(DisplayName = "This is 0"),
    Two UMETA(DisplayName = "This is 1"),
    Tree UMETA(DisplayName = "This is 2")
};

USTRUCT()
struct FCustomStruct
{
    GENERATED_BODY()

    UPROPERTY()
    int Value = 123;
};

//Définition de la structure fixe de l'Interface
UINTERFACE()
class UCustomInterface :public UInterface {
    GENERATED_BODY()
};
class ICustomInterface
{
    GENERATED_BODY()
public:
    UFUNCTION()
    virtual void SayHello() {}
};
```

Pour les structures marquées par les macros ci-dessus, UE crée une structure de données correspondante pour stocker leurs métadonnées.

-   **UCLASS()** : UClass, stocke les informations de description de la classe
-   **USTRUCT()** : UScriptStruct, stocke les informations de description de la structure
-   **UENUM()** : UEnum, stocke les informations de description de l'énumération
-   **UPROPERTY()** : FProperty, stocke les informations de description de la propriété
-   **UFUNCTION()** : UFunction, stocke les informations de description de la fonction
-   **UINTERFACE()** : Aucune

Dans les parenthèses de ces macros, vous pouvez ajouter des paramètres pour être utilisés par les systèmes associés. Pour les configurations spécifiques, veuillez consulter :

### CDO (Class Default Object)

Le système de réflexion d'UE fournit à UObject un mécanisme appelé **Class Default Object**, c'est-à-dire : chaque classe possède un objet par défaut.

Grâce à l'existence du CDO, chaque Class dispose d'un **singleton global**.

Vous pouvez obtenir le CDO via la fonction suivante :

``` c++
UObject* UClass::GetDefaultObject(bool bCreateIfNeeded = true) const
{
    if (ClassDefaultObject == nullptr && bCreateIfNeeded)   //Créer si non existant
    {
        UE_TRACK_REFERENCING_PACKAGE_SCOPED((GetOutermost()), PackageAccessTrackingOps::NAME_CreateDefaultObject);
        const_cast<UClass*>(this)->CreateDefaultObject();
    }
    return ClassDefaultObject;
}
```

UE fournit également des méthodes pratiques pour l'obtention :

```c++
const UObject* ConstCDO = GetDefault<UObject>();		 //Obtenir le pointeur Const du CDO
UObject* MutableCDO = GetMutableDefault<UObject>(); 	 //Obtenir le pointeur modifiable du CDO
```

UE utilise le CDO comme modèle lors de l'appel de `NewObject`, donc vous pouvez modifier les valeurs des propriétés du CDO pour ajuster les valeurs initiales des propriétés des nouveaux objets.

Le panneau Détails d'UE utilise également le CDO comme référence pour vérifier quelles propriétés de l'objet courant diffèrent du CDO :

![image-20230523200403812](../../../04-UnrealEngine/Resources/image-20230523200403812.png)

De plus, le CDO est étroitement lié au mécanisme Config d'UE :

```c++
UCLASS(config = CustomSettings, defaultconfig)
class UCustomSettings : public UObject {
	GENERATED_BODY()
public:
	UPROPERTY(EditAnywhere, Config)
	FString ConfigValue;
};
```

Grâce à la caractéristique de singleton global du CDO, il peut être utilisé pour stocker des configurations. En ajoutant des identifiants liés à Config dans `UCLASS` et `UPROPERTY`, le code suivant permet de stocker les configurations associées dans le répertoire du projet :

```c++
CDO->SaveConfig();
//Instance->LoadConfig();
//Instance->TryUpdateDefaultConfigFile();
```

Si vous souhaitez que le fichier de configuration s'affiche davantage dans les paramètres du projet de l'éditeur, vous pouvez enregistrer le fichier de configuration lors du démarrage du plugin avec le code suivant :

```c++
ISettingsModule* SettingsModule = FModuleManager::GetModulePtr<ISettingsModule>("Settings");
if (SettingsModule) {
    auto Settings = GetMutableDefault<UCustomSettings>();
    SettingsModule->RegisterSettings("Project", 
                                     TEXT("CustomSection"),
                                     TEXT("CustomSettingsName"),
                                     LOCTEXT("CustomSettingsName", "CustomSettingsName"),
                                     LOCTEXT("CCustomSettingsTooltip", "Custom Settings Tooltip"),
                                     Settings);
}
```

Il est également important de noter que le CDO exécute également le constructeur de UObject. Par conséquent, lors de l'exécution d'opérations à haut coût, il faut考虑si le CDO doit également l'exécuter :

``` c++
UCustomObject::UCustomObject(const FObjectInitializer& ObjectInitializer){
    if (HasAnyFlags(EObjectFlags::RF_ClassDefaultObject)) {		//Vérifier si l'objet courant est un CDO
	}
}
```

### Sérialisation (Serialize)

UObject prend en charge la sérialisation et la désérialisation, donc n'importe quel UObject peut être utilisé comme asset.

L'interface de sérialisation d'UE est la suivante :

``` c++
class UObject{
    /** 
     * Gère la lecture, l'écriture et la collecte de références à l'aide de FArchive.
     * Cette implémentation gère la sérialisation de toutes les FProperty, mais peut être surchargée pour les variables natives.
     */
    virtual void Serialize(FArchive& Ar);
};
```

UObject sérialise automatiquement les **propriétés de réflexion non Transient**. Il est également possible de surcharger la fonction `Serialize` et d'utiliser `FArchive` pour ajouter des données non réfléchies.

L'utilisation de **FObjectReader** et **FObjectWriter** permet de convertir UObject en ByteArray et vice versa.

Si seule la sérialisation des propriétés de réflexion est nécessaire, vous pouvez utiliser le code suivant :

``` c++
TArray<uint8> Buffer;
FMemoryWriter PropertiesAr(Buffer, true);
CustomObject->SerializeScriptProperties(PropertiesAr);
```

### Blueprint

Le point le plus puissant de la réflexion d'Unreal Engine est que les développeurs peuvent non seulement générer des données de réflexion par le scan du code, mais aussi **créer et organiser des structures de données de réflexion par eux-mêmes**.

Voici un exemple de construction d'une UClass à l'aide de code :

```c++
DEFINE_FUNCTION(execIntToString)                //Fonction native personnalisée
{
    P_GET_PROPERTY(FIntProperty, IntVar);       //Obtenir le paramètre
    P_FINISH;                                   //Fin de l'obtention
    *((FString*)RESULT_PARAM) = FString::FromInt(IntVar);       //Définir la valeur de retour
}
```

``` c++
UClass* CustomClass = NewObject<UClass>(GetTransientPackage(),"CustomClass");       //Classe personnalisée
CustomClass->ClassFlags |= CLASS_EditInlineNew;         //Définir les identifiants de la classe
CustomClass->SetSuperStruct(UObject::StaticClass());    //Définir la classe parent

FIntProperty* IntProp = new FIntProperty(CustomClass, TEXT("IntProp"), EObjectFlags::RF_NoFlags);//Créer une propriété Int
FStrProperty* StringProp = new FStrProperty(CustomClass, TEXT("StringProp"), EObjectFlags::RF_NoFlags);

UPackage* CoreUObjectPkg = FindObjectChecked<UPackage>(nullptr, TEXT("/Script/CoreUObject"));   //Créer une propriété de structure Vector
UScriptStruct* VectorStruct = FindObjectChecked<UScriptStruct>(CoreUObjectPkg, TEXT("Vector"));
FStructProperty* VectorProp = new FStructProperty(CustomClass, "VectorProp", RF_NoFlags);
VectorProp->Struct = VectorStruct;

CustomClass->ChildProperties = IntProp;                 //CustomClass->ChildProperties est un nœud de liste chaînée, les propriétés sont liées via la liste chaînée
IntProp->Next = StringProp;                 
StringProp->Next = VectorProp;

UFunction* CustomFucntion = NewObject<UFunction>(CustomClass, "IntToString", RF_Public);
CustomFucntion->FunctionFlags = FUNC_Public | FUNC_Native;  //Une fonction native fait référence à une fonction C++ native, sinon à du code de fonction dans un script Blueprint

FIntProperty* IntParam = new FIntProperty(CustomFucntion, "IntParam", EObjectFlags::RF_NoFlags);
IntParam->PropertyFlags = CPF_Parm;                         //Utilisé comme paramètre de fonction

FStrProperty* StringReturnParam = new FStrProperty(CustomFucntion, "StringReturnParam", EObjectFlags::RF_NoFlags);
StringReturnParam->PropertyFlags = CPF_Parm | CPF_ReturnParm;       //Utilisé comme valeur de retour de la fonction (doit inclure CPF_Parm)

CustomFucntion->ChildProperties = IntParam;                         //La valeur de retour de la fonction doit être le dernier nœud pour calculer le décalage des paramètres suivants
IntParam->Next = StringReturnParam;

CustomFucntion->SetNativeFunc(execIntToString);                     //Définir la fonction native
CustomFucntion->Bind();                                                 
CustomFucntion->StaticLink(true);                                   //Lier toutes les propriétés, cette opération génère la taille mémoire et le décalage de la Property..
CustomFucntion->Next = CustomClass->Children;                       //Ajouter la Function en tête de la liste chaînée Children de la Class pour l'accès Field
CustomClass->Children = CustomFucntion;

CustomClass->AddFunctionToFunctionMap(CustomFucntion, CustomFucntion->GetFName());  //Ajouter la fonction personnalisée à la table de fonctions de la classe personnalisée

CustomClass->Bind();
CustomClass->StaticLink(true);                          //Lier toutes les propriétés
CustomClass->AssembleReferenceTokenStream();            //Associer le GC de la propriété, terminer la construction de la classe personnalisée

UObject* CDO = CustomClass->GetDefaultObject();         

//Affecter des valeurs aux propriétés dans le CDO
void* IntPropPtr = IntProp->ContainerPtrToValuePtr<void*>(CDO);
IntProp->SetPropertyValue(IntPropPtr, 789);

FVector Vector(1, 2, 3);
void* VectorPropPtr = VectorProp->ContainerPtrToValuePtr<void>(CDO);
VectorProp->CopyValuesInternal(VectorPropPtr, &Vector, 1);

//Appeler la fonction personnalisée
int InputParam = 12345;
UFunction* Func = CustomClass->FindFunctionByName("IntToString");
uint8* Params = (uint8*)FMemory::Malloc(Func->ReturnValueOffset);		//Allouer un tampon de paramètres
FMemory::Memcpy((void*)Params, (void*)&InputParam, sizeof(int));
FFrame Frame(CDO, Func, Params, 0, Func->ChildProperties);
FString ReturnParam;
Func->Invoke(CDO, Frame, &ReturnParam);
```

Après cela, nous pouvons même utiliser la UClass que nous avons créée pour créer un UObject :

```c++
UObject* CustomObject = NewObject<UObject>(GetTransientPackage(), CustomClass);
```

La structure de données correspondant au Blueprint d'UE est **UBlueprint**. La plupart des opérations que nous effectuons sur l'éditeur Blueprint (gestion des propriétés et des fonctions, édition des nœuds, paramètres de classe...) consistent essentiellement à modifier les paramètres de **UBlueprint** :

![img](../../../04-UnrealEngine/Resources/image-20220928175121797-16735895312067.png)

L'interface suivante permet de créer un Blueprint :

```c++
static UBlueprint* FKismetEditorUtilities::CreateBlueprint(
    UClass* ParentClass,
    UObject* Outer, 
    const FName NewBPName,
    enum EBlueprintType BlueprintType,
    TSubclassOf<UBlueprint> BlueprintClassType,
    TSubclassOf<UBlueprintGeneratedClass> BlueprintGeneratedClassType, 
    FName CallingContext = NAME_None);
```

La signification des paramètres est la suivante :

- **ParentClass** : Classe parent, le Blueprint généré héritera des propriétés et des méthodes de cette Class
- **Outer** : Outer (propriétaire) du Blueprint généré
- **NewBPname** : Nom du Blueprint généré
- **BlueprintType** : Type de Blueprint, peut prendre les valeurs suivantes :

    ``` c++
    enum EBlueprintType
    {
        /** Blueprint normal. */
        BPTYPE_Normal               UMETA(DisplayName="Blueprint Class"),
        /** Blueprint constant pendant l'exécution (pas de graphe d'état et les méthodes ne peuvent pas modifier les variables membres). */
        BPTYPE_Const                UMETA(DisplayName="Const Blueprint Class"),
        /** Blueprint servant de conteneur pour des macros à utiliser dans d'autres Blueprints. */
        BPTYPE_MacroLibrary         UMETA(DisplayName="Blueprint Macro Library"),
        /** Blueprint servant d'interface à implémenter par d'autres Blueprints. */
        BPTYPE_Interface            UMETA(DisplayName="Blueprint Interface"),
        /** Blueprint gérant le scripting de niveau. */
        BPTYPE_LevelScript          UMETA(DisplayName="Level Blueprint"),
        /** Blueprint servant de conteneur pour des fonctions à utiliser dans d'autres Blueprints. */
        BPTYPE_FunctionLibrary      UMETA(DisplayName="Blueprint Function Library"),
    
        BPTYPE_MAX,
    };
    ```

- **BlueprintClassType** : Modèle de base de la classe Blueprint, par défaut `UBlueprint::StaticClass()` peut être utilisé, il permet de personnaliser la configuration du Blueprint
- **BlueprintGeneratedClassType** : Modèle de base de la classe générée par le Blueprint, par défaut `UBlueprintGeneratedClass::StaticClass()` peut être utilisé, il permet de personnaliser la stratégie de génération
- **CallingContext** : Contexte d'appel, vide par défaut

La logique de création d'un Blueprint peut être simplement considérée comme :

``` c++
UBlueprint* FKismetEditorUtilities::CreateBlueprint(
    UClass* ParentClass,
    UObject* Outer,
    TSubclassOf<UBlueprint> BlueprintClassType,
    TSubclassOf<UBlueprintGeneratedClass> BlueprintGeneratedClassType)
{
    UBlueprint* NewBP = NewObject<UBlueprint>(Outer,*BlueprintClassType);   //Créer une instance selon BlueprintClassType
    NewBP->ParentClass = ParentClass;

    UBlueprintGeneratedClass* NewGenClass =                                 //Créer une instance selon BlueprintGeneratedClassType
        NewObject<BlueprintGeneratedClassType>(NewBP->GetOutermost(),*BlueprintGeneratedClassType);

    NewGenClass->SetSuperStruct(ParentClass)            //Définir la classe parent de NewGenClass comme ParentClass pour accéder à ses propriétés et méthodes

    NewBP->GeneratedClass = NewGenClass;            	//Affecter la nouvelle UClass générée à NewBP->GeneratedClass 
}
```

La fonction suivante est réellement appelée :

L'objectif de cette fonction est de générer la **variable membre GeneratedClass** de UBlueprint en se basant sur la `liste des propriétés` et le `graphe logique` de l'éditeur Blueprint ainsi que la `ParentClass`.

En général, les étapes pour utiliser un Blueprint côté C++ sont les suivantes :

``` c++

FProperty* Prop = FindFProperty<FProperty>(Blueprint->GeneratedClass, "IntProp");//Rechercher la propriété nommée [IntProp] dans les données de réflexion de la classe

L'utilisation de `/Game/NewBlueprint.NewBlueprint_C` permet justement d'obtenir la **variable membre GeneratedClass** de UBlueprint, où `/Game/NewBlueprint` est le chemin du Package et `NewBlueprint_C` est le nom de l'objet de la **variable membre GeneratedClass**.

Pour la **UClass** générée par **UBlueprint**, vous pouvez accéder à la variable membre `ClassGeneratedBy` de **UClass** pour obtenir le **UBlueprint** qui l'a générée, ou utiliser la fonction :

```c++
static UBlueprint* UBlueprint::GetBlueprintFromClass(const UClass* InClass);
```

## Système d'Assets

Un prototype de fonction de NewObject est le suivant :

``` c++
template< class T >
T* NewObject(UObject* Outer = (UObject*)GetTransientPackage());
```

Où Outer peut être simplement compris comme l'objet parent. Il est important de noter que **Outer** n'est pas lié au GC d'UObject, son rôle est de spécifier la relation de structure de stockage des assets.

Les objets assets dans UE ne sont pas équivalents aux fichiers physiques. En fait, un fichier `*.uasset` et `*.umap` sur le disque peut être considéré comme correspondant à un objet **UPackage**.

Lors de la création d'un asset dans UE, on crée d'abord un `UPackage` comme mappage du fichier physique réel, puis on utilise `NewObject` pour créer l'asset réel. À ce moment, on spécifie son `Outer` comme le `Package`. Lors de la sauvegarde du `Package`, tous les `UObject` détenus par ce `Package` sont sérialisés dans le fichier physique. Ce processus ressemble à :

``` c++
// Créer un nouveau Package, /Game/CustomPackage est le chemin du package, où /Game représente le répertoire Content du projet
UPackage* CustomPackage = CreatePackage(nullptr, TEXT("/Game/CustomPackage"));

// Créer un nouvel asset, peut être n'importe quel UObject (ici UObject est une classe abstraite, il y aura un avertissement)
UObject* CustomInstance = NewObject<UObject>(CustomPackage, UObject::StaticClass(),
                                             TEXT("CustomInstance"), 
                                             EObjectFlags::RF_Public | EObjectFlags::RF_Standalone);	

// Obtenir le chemin du disque local du Package
FPackagePath PackagePath = FPackagePath::FromPackageNameChecked(CustomPackage->GetName());
const FString PackageFileName = PackagePath.GetLocalFullPath();

// Stocker le package sur le disque
const bool bSuccess = UPackage::SavePackage(CustomPackage,
                                            CustomInstance, 
                                            RF_Public | RF_Standalone,
                                            *PackageFileName,
                                            GError, nullptr, false, true, SAVE_NoError);
```

Cette opération créera un fichier `CustomPackage.uasset` dans le répertoire Content du projet.

![image-20230524105904811](../../../04-UnrealEngine/Resources/image-20230524105904811.png)

Nous pouvons charger le package et l'objet asset sur le disque avec le code suivant :

``` C++
UPackage* LoadedPackage = LoadPackage(nullptr, TEXT("/Game/CustomPackage"), LOAD_None);
UObject* LoadedAsset = LoadObject<UObject>(nullptr,TEXT("/Game/CustomPackage.CustomInstance"));
```

Si vous souhaitez que l'asset puisse être créé et prévisualisé dans l'éditeur UE, vous devez :

-   Dériver **UFactory** pour définir la fabrique de génération de l'objet asset
-   Dériver **FAssetTypeActions_Base** pour définir la prévisualisation de l'asset dans l'éditeur, le menu, etc.

        if (FSceneInterface* Scene = InWorld->Scene) {

                GFrameNumberRenderThread++;

    }

    FTaskGraphInterface::Get().ProcessThreadUntilIdle(ENamedThreads::GameThread);

    FSlateApplication::Get().GetRenderer()->Sync();

    FTSTicker::GetCoreTicker().Tick(InDelta);

    FAssetCompilingManager::Get().FinishAllCompilation();
}

## Autres

### Délegate

UE utilise le concept de **Delegate** pour la communication entre objets, qui permet d'appeler des fonctions C++ d'une manière générique et sécurisée en termes de type.

> Si vous connaissez bien Qt, Delegate correspond en fait au Signal dans le système Signal-Slot de Qt. Cependant, Delegate est plus puissant que Signal et devient plus complexe dans son utilisation.
>
> Son principal défaut est le nommage. Si il s'appelait également Signal, il serait probablement plus facile de susciter l'association des développeurs et de les amener à utiliser la bonne méthode.

Voici un scénario d'utilisation de Delegate (pseudocode nommé avec Signal) :

```C++
class Student{
    Signal nameChanged(string OldName, string NewName);
public:
	void setName(string inName){
       	string oldName = mName;
    	mName = inName;
        nameChanged.Emit(oldName,mName);
    }
private:
    string mName;
};

class Tearcher{
public:
    void OnStudentNameChanged(string OldName, string NewName){
        // faire quelque chose
    }
};

class Class{
protected:    
    void connectEveryone(){
      	 for(auto Student:mStudents){		
             Student.nameChanged.Connect(mTeacher,&Tearcher::OnStudentNameChanged);
         }
    }
private:
   	Teacher mTeacher;
    TArray<Student> mStudents;
};
```

La fonction `connectEveryone` dans cet exemple réalise la fonction suivante : "Le professeur dit aux élèves dans la classe : si vous changez de nom, veuillez me notifier."

Ici, on ne modifie pas directement la structure de Teacher et Student, mais on lie leur relation dans un tiers (la classe), ce qui permet de découpler le code.

Sans utiliser de Delegate, pour réaliser la même fonction, on pourrait écrire un code aussi laid que celui-ci :

``` c++
class Student{
public:
    Student(Class* InClass)		//Besoin de transmettre le pointeur du domaine logique de niveau supérieur
        : mClass(InClass){}
    
	void setName(string inName){
        string oldName = mName;
    	mName = inName;
        
        //Appel en chaîne non sécurisé, et un appel avec une portée de contexte large rendra la maintenance et l'itération ultérieures difficiles
        mClass->mTeacher->OnStudentNameChanged(OldName,mName);	
    }
private:
    string mName;
    Class* mClass
};

class Tearcher{
public:
    void OnStudentNameChanged(string OldName, string NewName){
        // faire quelque chose
    }
};

class Class{
    friend class Student;
private:
   	Teacher mTeacher;
    TArray<Student> mStudents;
};
```
