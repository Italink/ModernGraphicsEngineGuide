# GUI

> L'Interface Utilisateur Graphique (Graphical User Interface, abrégée GUI) est une interface utilisateur pour les ordinateurs qui utilise des éléments graphiques.
>
> L'interface utilisateur graphique est un format d'affichage d'interface de communication entre l'homme et l'[ordinateur](https://baike.baidu.com/item/计算机通信/8082711?fromModule=lemma_inlink), qui permet à l'utilisateur d'utiliser des périphériques d'entrée tels que la [souris](https://baike.baidu.com/item/鼠标/122323?fromModule=lemma_inlink) pour manipuler des [icônes](https://baike.baidu.com/item/图标/3823326?fromModule=lemma_inlink) ou des options de menu sur l'[écran](https://baike.baidu.com/item/屏幕/3750314?fromModule=lemma_inlink), afin de sélectionner des commandes, appeler des fichiers, lancer des programmes ou exécuter d'autres [tâches quotidiennes](https://baike.baidu.com/item/日常任务/10744783?fromModule=lemma_inlink). Par rapport à l'interface en caractères qui utilise des commandes textuelles ou de caractères entrées via le clavier pour accomplir des tâches routinières, l'interface utilisateur graphique présente de nombreux avantages. L'interface utilisateur graphique est composée de fenêtres, de menus déroulants, de boîtes de dialogue et de leurs mécanismes de contrôle correspondants. Elle est standardisée dans toutes les nouvelles applications, c'est-à-dire que les mêmes opérations sont toujours accomplies de la même manière. Dans l'interface utilisateur graphique, ce que l'utilisateur voit et manipule sont des objets graphiques, et elle utilise la technologie de l'infographie.
>
> ——《[Baidu Encyclopedia](https://baike.baidu.com/item/GUI/479966)》

Si vous êtes fatigué des jours passés à lutter avec la console, cet article pourrait vous être utile.

## Vue d'ensemble

La GUI se divise principalement en deux catégories :

- **Native UI** : Mode de développement traditionnel des applications natives, utilisant les interfaces du système d'exploitation pour le développement
- **Web UI** : Applications web spécifiques fonctionnant dans un navigateur

Voici une présentation plus détaillée :

- [Zhihu : Qu'est-ce que Native, Web App, Hybrid ?](https://zhuanlan.zhihu.com/p/40705635)

Pour les débats sur elles, vous pouvez consulter :

- [Zhihu : Web App et Native App, laquelle est la tendance ?](https://www.zhihu.com/question/19558750)

Web UI domine le marché internet en raison de son faible coût et de son développement rapide, tandis que les raisons d'utiliser Native UI ne sont rien d'autre que : haute performance, personnalisation, interaction avec le matériel.

Bien que [Web GPU](https://www.zhihu.com/question/315103318) soit maintenant stable et offre plus de potentiel aux développeurs web, pour les étudiants orientés graphiques ou moteurs, l'auteur suggère de préférer la direction Native, car elle offre plus d'espace de contrôle.

Après utilisation, l'auteur a constaté que la GUI ne consiste essentiellement qu'à :

- Traiter les événements d'interaction (clavier/souris) du système
- Remplir des pixels sur l'écran pour dessiner quelques graphiques

C'est une fonctionnalité que chaque système d'exploitation ou framework GUI offre au minimum. Imaginez : avec ces deux fonctionnalités, il suffit de lier une fonction de rappel aux opérations clavier/souris et d'utiliser une boucle pour remplir les pixels de l'écran avec des valeurs RGB. Quel type d'interface graphique impressionnante ne pourrait-on pas créer ? Par exemple, un programme comme celui-ci :

``` c++
#include <conio.h>		// E/S console
#include <iostream>

int main() {
	char currentChar = '\0';
	const int width = 20;
	const int height = 20;
	while (true) {
		if (kbhit()) {				// kbhit permet de vérifier s'il y a une entrée clavier
			currentChar = getch();	// getch est une fonction d'entrée sans écho ; contrairement à getchar, la touche entrée n'est pas affichée sur la console
		}
		system("cls");				// Effacer la console
		std::cout << "Veuillez entrer une touche:" << std::endl;
		for (int y = 0; y < height; y++) {
			for (int x = 0; x < width; x++) {
				std::cout << currentChar;
			}
			std::cout << std::endl;
		}
	}
    return 0;
}
```

Par rapport au programme console ci-dessus, la GUI ne consiste essentiellement qu'à encapsuler l'entrée clavier/souris dans une interface, `width` et `height` étant les dimensions de la fenêtre, et à remplir les pixels aux coordonnées correspondantes avec des couleurs.

Ce qui détermine réellement le choix du framework, c'est avant tout l'écosystème, qui se manifeste par :

- Beaucoup d'utilisateurs, beaucoup de collègues, facilité de recrutement
- Large couverture du framework, nombreuses bibliothèques d'outils, documentation complète
- Maintenance à long terme par l'éditeur, fréquence d'itération élevée, peu de problèmes

Parmi les frameworks mentionnés ci-dessus, celui qui fait le mieux le travail, sans aucun doute, est Qt.

La plupart des modules de Qt suivent la licence LGPL, ce qui nous permet de les utiliser sous forme de liens dynamiques et de publier des logiciels commerciaux. Pour la licence open source de chaque module, veuillez consulter :

- https://doc.qt.io/qt-6/licenses-used-in-qt.html

Si vous souhaitez modifier le code source de Qt ou utiliser certains modules commerciaux, vous devez acheter une licence commerciale Qt. Pour plus de détails, veuillez consulter :

- https://www.qt.io/licensing/open-source-lgpl-obligations

En raison de la licence open source stricte de Qt, son indépendance par rapport à la norme C++ et sa taille importante, de nombreuses équipes peuvent choisir des frameworks comme WxWidget, C++ Builder, duilib ou GTK. Même si MFC, FLTK et EasyX sont de bons frameworks GUI, leur écosystème de développement n'est pas optimiste. Si vous avez le choix, l'auteur suggère de ne pas les utiliser.

Dear ImGUI et Nuklear sont des kits d'outils GUI légers, portables et suivant le **Immediate Mode**. Essentiellement, ils fournissent des interfaces de contrôles aux développeurs pour réaliser le rendu d'une image. Par exemple, avec ImGUI, le code suivant :

``` c++
ImGui::Text("Hello Dear ImGUI");
static bool CheckState;
ImGui::Checkbox("CheckBox ", &CheckState);
```

Permet de générer une interface comme celle-ci :

![image-20230210205746160](../../../00-C++/Resources/image-20230210205746160.png)

Le **Immediate Mode (mode immédiat)** se manifeste principalement par le fait qu'il transmet un pointeur vers la variable `CheckState` au "contrôle", tandis que le **Retained Mode (mode conservé)** traditionnel, par exemple dans Qt, pourrait avoir un code comme celui-ci :

``` c++
static bool CheckState;
QCheckBox* CheckBox = new QCheckBox;
CheckBox->setCheckState( CheckState? Qt::Checked : Qt::Unchecked);		// Initialisation
QObject::connect(CheckBox,&QCheckBox::stateChanged,[&](int state){		// Liaison signal-slot
    CheckState = state == Qt::Checked;
});
```

On peut voir que **QCheckBox** n'utilise pas de pointeur vers `CheckState`, mais définit l'état initial du contrôle via `CheckState`. Lorsque le contrôle déclenche `stateChanged`, il définit ensuite la valeur de `CheckState`. Autrement dit, le contrôle lui-même détient son propre état, tandis que le **Immediate Mode insiste sur l'absence d'état**, l'état étant intégré au contrôle.

Pendant le développement, stocker trop d'états locaux nécessite beaucoup de code pour maintenir la synchronisation, ce qui peut facilement entraîner des bugs, par exemple des événements exécutés plusieurs fois ou même des boucles infinies.

Prendre l'exemple de la modification d'une couleur :

![](../../../00-C++/Resources/image-20230210212343936.png)

En utilisant une palette de couleurs, en faisant glisser la souris, en entrant des valeurs de canaux, en entrant un code hexadécimal ou en prenant une couleur à l'écran, on peut ajuster la même valeur de couleur de plusieurs manières. Avec le mode conservé, après avoir modifié la couleur d'une manière, il faut ajuster manuellement les autres contrôles pour garantir la synchronisation. Bien que certains modèles de conception puissent résoudre ce problème, le mode immédiat a un avantage naturel dans ce scénario d'application. Pour les débats sur leurs différences, veuillez consulter :

- [Zhihu : Quels sont les liens et les différences entre Retained et IMGUI ?](https://www.zhihu.com/question/39093254/answer/1351958747)

Cela signifie-t-il que Dear ImGUI est mieux que Qt ? Pas nécessairement. Les points de vue de l'auteur sont les suivants :

- **Le Immediate Mode est plus adapté aux moteurs de jeu, mais Dear ImGUI n'est pas suffisant.** C'est seulement un petit kit d'outils GUI. Bien qu'il soit facile à prendre en main et capable de produire des interfaces agréables, le développement de systèmes logiciels grands est un art de l'ingénierie. Un seuil d'entrée bas peut entraîner plus de problèmes. À moins d'avoir assez de personnel et d'énergie pour itérer constamment, utiliser Dear ImGUI natif pour le développement est un véritable désastre...

  > Voici une réponse qui, bien qu'elle ne parle pas de Dear ImGUI, expose bien les problèmes de ce type de frameworks : https://www.zhihu.com/question/66934513/answer/248036488

- **Le Retained Mode n'est qu'une façon d'architecturer les contrôles, Qt != Retained Mode.** Bien que la plupart des contrôles officiels des frameworks Native UI utilisent le Retained Mode, vous pouvez utiliser le Immediate Mode sur ces frameworks si vous le souhaitez.

  > [Why Qt and not IMGUI?](https://deplinenoise.wordpress.com/2017/03/05/why-qt-and-not-imgui/)

Cela signifie-t-il que Qt est mieux ? Pas nécessairement. Utiliser Qt implique d'intégrer ses modules Core, Widget et moc. De plus, en raison de la licence open source, nous ne pouvons pas modifier son code source. C'est pourquoi, dans les moteurs de jeu, il est principalement utilisé comme éditeur, par exemple :

- [O3DE](https://www.o3de.org/) : https://github.com/o3de/o3de

Actuellement, il n'est pas adapté aux solutions UI dans les jeux :

- Blog de Yunfeng — Choix du module UI pour les jeux : https://blog.codingnow.com/2020/07/game_ui.html

Slate dans UE est un excellent framework UI de bas niveau :

- https://docs.unrealengine.com/5.1/en-US/understanding-the-slate-ui-architecture-in-unreal-engine/

Mais dans les tutoriels sur les graphiques suivants de cette série, Qt sera utilisé comme éditeur principal, avec ImGUI intégré pour l'édition de scènes. Les raisons principales sont les suivantes :

- Qt possède un encapsulation cross-platform de Window, permettant d'obtenir un Handle pour effectuer des traitements spécifiques avec les API natives
- Qt possède un système de réflexion élégant, facilitant la construction d'éditeurs. L'utilisation de Signal-Slot permet de découpler bien la logique et d'augmenter la lisibilité
- Qt possède une bibliothèque de conteneurs indépendante, permettant de s'affranchir des problèmes de la STL
- Qt possède de nombreuses bibliothèques d'extensions avec une interface uniforme, comme une bibliothèque mathématique de base, une bibliothèque de codage/décodage d'images, une bibliothèque multimédia, permettant de rendre les résultats de l'apprentissage plus facilement exploitables
- Depuis Qt 6.0, un RHI (Render Hardware Interface) supportant OpenGL, DX11, Vulkan et Metal a été introduit. Son utilisation est bien plus facile qu'OpenGL, et son architecture utilise glsl dans le style Vulkan et des API graphiques modernes, sans modification comme bgfx. Le plus important est que l'utilisation du RHI de Qt permet une bonne compatibilité avec les API natives, facilitant l'utilisation d'API graphiques ou de fonctionnalités avancées fournies par le matériel

## Base de la plateforme

Les programmes GUI s'affichent sur l'écran. Pour pouvoir gérer systématiquement les pixels sur l'écran, le système d'exploitation fournit une structure appelée Window. Sur Windows 10, une fenêtre standard est comme celle-ci, avec une barre de titre (icône, texte de titre, bouton de réduction, bouton d'agrandissement, bouton de fermeture) :

![](../../../00-C++/Resources/image-20230210223818978.png)

Vous pouvez créer une Window comme suit :

- Créer un fichier `CMakeLists.txt` et un fichier `main.cpp`

- Dans `CMakeLists.txt`, ajouter :

  ``` cmake
  cmake_minimum_required(VERSION 3.12)
  project(Window)
  add_executable(Window WIN32 main.cpp)
  ```

  > WIN32 indique que l'exécutable est une fenêtre Win32, correspondant à `Paramètres du projet` - `Editeur de liens` - `Système` - `Sous-système` - `Fenêtre` dans Visual Studio
  >
  > ![image-20230210225528304](../../../00-C++/Resources/image-20230210225528304.png)

- Dans `main.cpp`, ajouter :

  ``` c++
  #ifndef UNICODE
  #define UNICODE
  #endif 
  
  #include <windows.h>
  
  LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam);
  
  int WINAPI wWinMain(HINSTANCE hInstance, HINSTANCE hPrevInstance, PWSTR pCmdLine, int nCmdShow)
  {
      // Enregistrer la classe de fenêtre
      const wchar_t CLASS_NAME[]  = L"Sample Window Class";
      
      WNDCLASS wc = { };
  
      wc.lpfnWndProc   = WindowProc;
      wc.hInstance     = hInstance;
      wc.lpszClassName = CLASS_NAME;
  
      RegisterClass(&wc);
  
      // Créer la fenêtre
  
      HWND hwnd = CreateWindowEx(
          0,                              // Styles de fenêtre optionnels
          CLASS_NAME,                     // Classe de fenêtre
          L"Apprendre à programmer Windows",    // Texte de la fenêtre
          WS_OVERLAPPEDWINDOW,            // Style de fenêtre
  
          // Taille et position
          CW_USEDEFAULT, CW_USEDEFAULT, CW_USEDEFAULT, CW_USEDEFAULT,
  
          NULL,       // Fenêtre parente    
          NULL,       // Menu
          hInstance,  // Handle de l'instance
          NULL        // Données supplémentaires de l'application
          );
  
      if (hwnd == NULL)
      {
          return 0;
      }
  
      Afficher la fenêtre
  
      ShowWindow(hwnd, nCmdShow);
  
      // Exécuter la boucle de messages
  
      MSG msg = { };
      while (GetMessage(&msg, NULL, 0, 0) > 0)
      {
          TranslateMessage(&msg);
          DispatchMessage(&msg);
      }
  
      return 0;
  }
  
  LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
  {
      switch (uMsg)
      {
      case WM_DESTROY:
          PostQuitMessage(0);
          return 0;
  
      case WM_PAINT:
          {
              PAINTSTRUCT ps;
              HDC hdc = BeginPaint(hwnd, &ps);
  
              // Tous les dessins se produisent ici, entre BeginPaint et EndPaint
  
              FillRect(hdc, &ps.rcPaint, (HBRUSH) (COLOR_WINDOW+1));
  
              EndPaint(hwnd, &ps);
          }
          return 0;
  
      }
      return DefWindowProc(hwnd, uMsg, wParam, lParam);
  }
  ```

### Double buffering

Dans le programme console précédent, la page clignote furieusement. C'est parce que nous ajoutons progressivement des éléments à un tampon, et la fenêtre console prévisualise ce processus. En raison de la vitesse de rafraîchissement rapide, cela cause un clignotement. Pour résoudre ce type de problème, en informatique, le concept de **Double buffering (double tampon)** a été proposé :

- Le tampon utilisé pour la prévisualisation de la console est appelé **tampon frontal**. Le cœur du double tampon est que nous n'opérons pas directement sur le tampon frontal, mais traitons d'abord le **tampon arrière** avant de le **soumettre en bloc** au tampon frontal. Cela permet d'éviter efficacement le clignotement et le déchirement.

> En parlant de soumission en bloc, pensez-vous à **for copy** et **memcpy** de la section précédente ?
>
> Pour mettre toutes les oranges d'un panier dans un autre panier, est-ce plus rapide de les mettre une par une ou de lever le panier et de le vider directement ? C'est évident.
>
> Les fournisseurs de matériel et d'interfaces comprennent aussi ce principe. Dans la plupart des cas, ils supportent des opérations comme Map, Blit, etc.

Un exemple d'utilisation du double tampon dans la console est le suivant :

``` c++
#include <conio.h>		// E/S console
#include <iostream>
#include <Windows.h>

const int width = 20;
const int height = 20;
const int MaxBufferSize = width * height * 10;

void UseSingleBuffer() {
	char currentChar = '*';
	while (true) {
		if (kbhit()) {				// kbhit permet de vérifier s'il y a une entrée clavier
			currentChar = getch();	// getch est une fonction d'entrée sans écho ; contrairement à getchar, la touche entrée n'est pas affichée sur la console
		}
		system("cls");				// Effacer la console
		for (int y = 0; y < height; y++) {
			for (int x = 0; x < width; x++) {
				std::cout << currentChar;
			}
			std::cout << std::endl;
		}
	}
}

void UseDoubleBuffer() {
	HANDLE frontendBuffer = GetStdHandle(STD_OUTPUT_HANDLE);		// Obtenir le tampon par défaut

	HANDLE backendBuffer = CreateConsoleScreenBuffer(				// Créer un nouveau tampon comme tampon arrière
		GENERIC_READ | GENERIC_WRITE,
		FILE_SHARE_READ | FILE_SHARE_WRITE,
		NULL,
		CONSOLE_TEXTMODE_BUFFER,
		NULL
	);

	// Cacher les curseurs des deux tampons
	CONSOLE_CURSOR_INFO cci;
	cci.bVisible = 0;
	cci.dwSize = 1;
	SetConsoleCursorInfo(frontendBuffer, &cci);
	SetConsoleCursorInfo(backendBuffer, &cci);


	char bufferData[MaxBufferSize];		// Zone de stockage temporaire des données du tampon
	DWORD bufferLength = 0;
	COORD zeroCoord = { 0,0 };
	char currentChar = '*';

	while (true) {
		if (kbhit()) {				
			currentChar = getch();	
		}
		bufferLength = 0;

		CONSOLE_SCREEN_BUFFER_INFO backendBufferInfo; 		// Obtenir le nombre de caractères par ligne du backendBuffer
		GetConsoleScreenBufferInfo(backendBuffer, &backendBufferInfo);
		int lineWidth = backendBufferInfo.srWindow.Right - backendBufferInfo.srWindow.Left + 1;		

		for (int y = 0; y < height; y++) {
			for (int x = 0; x < width; x++) {
				bufferData[bufferLength++] = currentChar;
			}
			while (bufferLength % lineWidth != 0) {				// Remplir des caractères pour obtenir un retour à la ligne
				bufferData[bufferLength++] = ' ';
			}
		}
        
        // Écrire bufferData de longueur bufferLength à partir de zeroCoord dans backendBuffer
		WriteConsoleOutputCharacterA(backendBuffer, bufferData, bufferLength, zeroCoord, &bufferLength);	
		SetConsoleActiveScreenBuffer(backendBuffer);			// Afficher backendBuffer
		std::swap(backendBuffer, frontendBuffer);				// Échanger les handles d'opération des tampons avant et arrière ; frontendBuffer deviendra le backendBuffer de la prochaine boucle
	}
}

int main() {
	//UseSingleBuffer();
    UseDoubleBuffer();
	return 0;
}
```

La plupart des frameworks GUI utilisent la méthode du double tampon, tandis que les jeux utilisent même un triple tampon. Généralement, on appelle cette structure une [chaîne d'échange](https://en.wikipedia.org/wiki/Swap_chain).

Pour plus de détails sur le double buffering, vous pouvez consulter :

- https://en.wikipedia.org/wiki/Multiple_buffering

### DPI

> Le nombre de points par pouce de longueur dans une image numérique matricielle.
>
> DPI (Dots Per Inch, points par pouce) est une unité de mesure utilisée pour les images numériques matricielles, indiquant le nombre de points échantillonnés, affichables ou sortis par pouce de longueur.

Sous Windows, vous pouvez ajuster le DPI du système via les paramètres **Mise à l'échelle et disposition**.

Le système d'exploitation ajustera la taille et le contenu de la fenêtre selon une certaine mécanique configurable en fonction de la variation du DPI. Pour plus de détails sur la perception du DPI, veuillez consulter :

Pendant le développement GUI, le support de la prévisualisation multi-DPI est toujours un problème délicat, car il est difficile d'ajuster l'effet et la disposition de l'ensemble de l'interface via quelques paramètres.

- Window Size != Buffer Size. Beaucoup de personnes créent un Frame Buffer en utilisant la taille de la fenêtre. Cela fonctionne normalement sur un ordinateur avec un zoom de 100%, mais pose des problèmes dans d'autres cas.

  ``` c++
#include <QApplication>
#include <QWindow>

int main(int argc, char* argv[]) {
  ```

### Object

La plupart des classes dans Qt dérivent de [QObject](https://doc.qt.io/qt-6/qobject.html), ce qui facilite la gestion de tous leurs sous-objets et fournit des mécanismes comme la réflexion, Signal-Slot, le garbage collection, les événements, etc. Un exemple de définition d'une sous-classe de QObject est le suivant :

``` c++
class QExmapleClass : public QObject {
```

#### Système de méta-objets

Le système de méta-objets de Qt fournit des mécanismes comme Signal-Slot, des informations sur le type à l'exécution et un système de propriétés dynamiques.

Pour les `Q_OBJECT` écrits dans `*.cpp`, vous devez inclure manuellement `*.moc` à la fin pour déclencher l'exécution de moc. Par exemple :

```c++
/* main.cpp
*/

#include <QApplication>
#include <QMetaType>
#include <QMetaProperty>

class QExmapleClass : public QObject {
	Q_OBJECT
	Q_PROPERTY(int Var READ getVar WRITE setVar)				// Déclarer une MetaProperty via Getter et Setter
public:
	int getVar() {
		return mVar;
	}
	void setVar(int inVar) {
		mVar = inVar;
	}

	Q_INVOKABLE void sayHello(const QString& inName) {			// Déclarer une MetaMethod
		qDebug() << "Hello " << inName.toLatin1().data();
	}

	enum Number {
		Zero, One, Two, Three
	};
	Q_ENUM(Number)												// Déclarer une MetaEnum
protected:
	int mVar= 5;
};

int main(int argc, char* argv[]) {
	QApplication a(argc, argv);

	QExmapleClass obj;		

	// Obtenir le MetaObject
	const QMetaObject* metaObjectFromStatic = &QExmapleClass::staticMetaObject;	
	const QMetaObject* metaObjectFromVirtual = obj.metaObject();

	// Lire et écrire la propriété
	obj.setProperty("Var", QVariant::fromValue<int>(10));						
	QVariant var = obj.property("Var");
	qDebug() << "Property : " << var.value<int>();

	// Appeler la fonction
	qDebug() << "Invoke Method Begin:";
	metaObjectFromStatic->invokeMethod(&obj, "sayHello",Q_ARG(QString,"Boy"));
	qDebug() << "Invoke Method End";

	// Opération sur MetaType
	QMetaType metaType = var.metaType();
	qDebug() << "Meta Type : " << metaType.name() <<" ID: " << metaType.id();

	// Parcourir et lire/écrire les propriétés dans MetaObject, et afficher le type de propriété
	for (int i = metaObjectFromStatic->propertyOffset() ; i < metaObjectFromStatic->propertyCount(); i++) {
		const QMetaProperty& metaProperty = metaObjectFromStatic->property(i);
		metaProperty.write(&obj, QVariant::fromValue<int>(15));
		QVariant varFromMetaObject = metaProperty.read(&obj);
		qDebug() << "Meta Property : " << metaProperty.name() << varFromMetaObject;
	}

	// Parcourir les fonctions dans MetaObject et afficher les informations sur les paramètres
	for (int i = metaObjectFromStatic->methodOffset(); i < metaObjectFromStatic->methodCount(); i++) {
		const QMetaMethod& metaMethod = metaObjectFromStatic->method(i);
		QByteArrayList paramNames = metaMethod.parameterNames();
		QStringList paramsDefineList;
		for (int j = 0; j < metaMethod.parameterCount(); j++) {
			paramsDefineList << metaMethod.parameterTypeName(j) +" " + paramNames[j];
		}
		qDebug() << QString("Meta Method : %1 %2(%3)")
			.arg(metaMethod.typeName())
			.arg(metaMethod.name())
			.arg(paramsDefineList.join(',')).toLatin1().data();
	}

	// Parcourir les énumérations dans MetaObject et afficher les informations sur les énumérations
	for (int i = metaObjectFromStatic->enumeratorOffset(); i < metaObjectFromStatic->enumeratorCount(); i++) {
		const QMetaEnum& metaEnum = metaObjectFromStatic->enumerator(i);
		qDebug()<< "Meta Enum : " << metaEnum.name();
		for (int j = 0; j < metaEnum.keyCount(); j++) {
			qDebug() << "-- " << metaEnum.key(j) << " : " << metaEnum.value(j);
		}
	}
	return a.exec();
}

#include "main.moc"		// Il faut inclure main.moc pour déclencher la compilation moc
```

#### Signal-Slot

Le mécanisme Signal-Slot est utilisé pour la communication entre objets. C'est une caractéristique centrale de Qt. Concernant son rôle, un exemple de pseudo-code est le suivant :

``` c++
class Student{
    Signal nameChanged(string OldName, string NewName);
public:
    void setName(string inName){
        nameChanged.Emit(mName，inName);
        mName = inName;
    }
private:
    string mName;
};

class Tearcher{
public:
    void OnStudentNameChanged(string OldName, string NewName){
        // faire quelque chose
    }
};

class Class{
protected:    
    void connectEveryone(){
         for(auto Student:mStudents){       
             Student.nameChanged.Connect(mTeacher,&Tearcher::OnStudentNameChanged);
         }
    }
private:
    Teacher mTeacher;
    TArray<Student> mStudents;
};
```

Via la fonction connectEveryone, on peut dire que : "Le professeur" dit aux étudiants dans la classe : si vous changez de nom, veuillez me notifier.

Ici, on ne modifie pas directement la structure de Teacher et Student, mais on lie la relation entre les deux dans un ensemble tiers (la classe), permettant une bonne découplage.

> Ce mécanisme correspond aux délégués (Delegate) dans UE. Ils sont plus détaillés que les Signal-Slot de Qt, mais la traduction a quelques points faibles. Si on l'appelait aussi Signal, on croit que cela permettrait aux développeurs de s'associer plus facilement et d'adopter la bonne façon de l'utiliser.

Pour des explications plus détaillées, veuillez consulter :

- https://doc.qt.io/qt-6/signalsandslots.html

#### Système d'événements

Dans Qt, un événement est une instance d'une sous-classe de la classe abstraite [QEvent](https://doc.qt.io/qt-6/qevent.html). Il est utilisé pour décrire le résultat d'une activité interne ou externe de l'application. En termes de rôle, il peut être considéré comme un Signal-Slot de poids lourd. Le mécanisme d'interaction dans QWigdet est implémenté via des événements.

Lorsqu'un événement se produit, Qt le représente en construisant une instance appropriée d'une sous-classe de QEvent et appelle :

- [static bool QCoreApplication::sendEvent(QObject* *receiver*, QEvent event)](https://doc.qt.io/qt-6/qcoreapplication.html#sendEvent)

Pour envoyer l'événement au `QObject` correspondant. QObject possède une fonction virtuelle :

- [virtual bool QObject::event( QEvent* *e* )](https://doc.qt.io/qt-6/qobject.html#event)

Via la redéfinition de `event`, on peut traiter l'événement ou le distribuer davantage à d'autres fonctions.

De plus, Qt supporte le mécanisme d'écouteur d'événements. On peut redéfinir la fonction virtuelle de QObject :

- [bool QObject:: eventFilter ( QObject * *watched* , QEvent* *event* )](https://doc.qt.io/qt-6/qobject.html#eventFilter)

Pour qu'elle puisse être utilisée comme `filterObj`, puis appeler :

- [void QObject:: installEventFilter ( QObject* *filterObj* )](https://doc.qt.io/qt-6/qobject.html#installEventFilter)

Ainsi, l'objet peut être utilisé comme écouteur d'événements pour d'autres objets.

Concernant le système d'événements, voir en détail :

- https://doc.qt.io/qt-6/eventsandfilters.html

#### Garbage Collection

Dans la section précédente sur la gestion de la mémoire, on a déjà mentionné le GC de Qt. Sa méthode de GC est simple : QObject peut spécifier un parent unique. Lorsque le parent est libéré, les enfants sont aussi libérés. De plus, on peut utiliser [QObject::deleteLater](https://doc.qt.io/qt-6/qobject.html#deleteLater) pour retarder la libération de QObject.

Dans QWidget, l'ajout d'un sous-contrôle définit implicitement le parent. Dans la plupart des cas, il n'est pas nécessaire de supprimer manuellement, mais il faut faire attention à contrôler le cycle de vie du parent. Si un nœud dans l'arbre d'objets a un problème, tous les objets du sous-arbre ne peuvent pas être libérés.

#### WindowOption

Dans la plupart des cas, les développeurs n'ont même pas besoin de toucher à `QWindow`, car le `QWidget` le plus externe (ou le plus haut niveau) générera automatiquement `QWindow`. On peut faire quelques paramètres sur ce QWidget pour influencer la génération de Window :

- [WindowFlag](https://doc.qt.io/qt-6/qt.html#WindowType-enum) : Ajuster l'identifiant de Window, comme une fenêtre contextuelle, une boîte de dialogue, une boîte d'information, sans bordure...

- [WindowModality](https://doc.qt.io/qt-6/qt.html#WindowModality-enum) : Définir une fenêtre modale. Une fenêtre modale bloque l'entrée d'autres fenêtres. Elle est généralement utilisée pour forcer l'utilisateur à choisir certaines options avant de continuer l'exécution.

- [WindowState](https://doc.qt.io/qt-6/qt.html#WindowState-enum) : L'état de Window inclut : `par défaut`, `réduit`, `agrandit`, `plein écran (sans bordure)`, `activé`. On peut appeler `setWindowState`. Qt fournit aussi des API pratiques, comme [activateWindow()](https://doc.qt.io/qt-6/qwidget.html#activateWindow).

Par exemple, avec ce code :

```c++
QWidget widget;
widget.setWindowFlags(Qt::FramelessWindowHint|Qt::Tool);
widget.resize(200,200);
widget.show();
```

Vous verrez un carré gris de 200*200 sur l'écran, et son icône est aussi cachée dans la barre des tâches en bas.

Il faut noter que lors de la création d'un Widget, on ne crée pas de Window. La plupart du temps, les paramètres que l'on définit sur le Widget ne font que régler sa machine à états de paramètres. Seul lors de l'exécution de l'événement, on effectue des opérations réelles en fonction de ces états. Par exemple, vous devez appeler show avant de pouvoir obtenir le handle de Window.

Vous pouvez définir beaucoup de propriétés utiles pour QWidget, dont les plus courantes sont :

- Qt::WA_TranslucentBackground : Rendre l'arrière-plan de la fenêtre transparent

#### Event

L'affichage de GUI dépend de [paintEvent](https://doc.qt.io/qt-6/qwidget.html#paintEvent) de QWidget. On peut redéfinir paintEvent et utiliser [QPainter](https://doc.qt.io/qt-6/qpainter.html) pour dessiner n'importe quel graphique que l'on souhaite.

L'essence de GUI est simplement d'utiliser divers événements d'interaction pour ajuster la machine à états de propriétés et changer le résultat du dessin de paintEvent.

Voici un bon exemple :

```c++
#include <QApplication>
#include <QWidget>
#include <QMouseEvent>
#include <QPainter>

class QExmapleWidget:public QWidget {
	Q_OBJECT
private:
	QPoint mMousePressPos;
	bool bIsHovered = false;
protected:
	void mousePressEvent(QMouseEvent* event) override {
		if (event->button() == Qt::LeftButton)		// Enregistrer la position lorsque le bouton gauche de la souris est pressé
			mMousePressPos = event->pos();			
	}
	void mouseMoveEvent(QMouseEvent* event) override {
		if (event->buttons() & Qt::LeftButton)		// Lorsque le bouton gauche de la souris est pressé et déplacé, ajuster la position du Widget
			move(event->pos() + this->pos() - mMousePressPos);
	}

	void enterEvent(QEnterEvent* event) override {
		bIsHovered = true;							// La souris entre dans le Widget
		setCursor(Qt::ClosedHandCursor);			// Définir la forme du curseur de la souris
		update();									// Demander un rafraîchissement de l'interface
	}

	void leaveEvent(QEvent* event) override {
		bIsHovered = false;							// La souris quitte le Widget
		setCursor(Qt::ArrowCursor);					// Définir la forme du curseur de la souris
		update();									// Demander un rafraîchissement de l'interface
	}

	void paintEvent(QPaintEvent* event) override {
		QPainter painter(this);

		painter.fillRect(this->rect(),bIsHovered ? Qt::green : QColor(0,100,200));	// Remplir la zone avec une couleur

		painter.setPen(QPen(Qt::white));
		painter.setFont(QFont("",20,90));											// Utiliser une police par défaut et définir la taille et le poids
		painter.drawText(this->rect(), Qt::AlignCenter, "Hello Qt");				// Dessiner du texte
	}
};

int main(int argc, char* argv[]) {
	QApplication a(argc, argv);
	QExmapleWidget widget;
	widget.setWindowFlags(Qt::FramelessWindowHint);			// Sans bordure
	widget.setAttribute(Qt::WA_TranslucentBackground);		// Arrière-plan transparent		
	widget.setAttribute(Qt::WA_AlwaysStackOnTop);			// Toujours au premier plan
	widget.resize(200,200);
	widget.show();
	return a.exec();
}

#include "main.moc"
```

#### Layout

Dans un programme, il y a souvent plus d'un QWidget. Donc, on a aussi besoin d'organiser la disposition de ces Widgets. La disposition la plus courante dans Qt est BoxLayout. Voici un exemple simple :

``` c++
#include <QApplication>
#include <QWidget>
#include <QHBoxLayout>
#include <QPushButton>

class QMainWidget :public QWidget {
	Q_OBJECT
public:
	QMainWidget() {
		createUI();
	}
private:
	void createUI() {
		QHBoxLayout* hLayout = new QHBoxLayout(this);
		// QHBoxLayout* hLayout = new QHBoxLayout();			// Équivalent
		//setLayout(hLayout);

		hLayout->setContentsMargins(5, 5, 5, 5);				// Définir les marges externes
		hLayout->setSpacing(10);								// Définir l'espacement entre les éléments internes
		hLayout->setAlignment(Qt::AlignLeft|Qt::AlignVCenter);	// Définir l'alignement à gauche et centré verticalement
		hLayout->addWidget(new QPushButton("A"));
		hLayout->addSpacing(20);								// Ajouter un remplissage vide
		hLayout->addWidget(new QPushButton("B"));
		hLayout->addWidget(new QPushButton("C"));
	}
};

int main(int argc, char* argv[]) {
	QApplication a(argc, argv);
	QMainWidget widget;
	widget.resize(300, 300);
	widget.show();
	return a.exec();
}
```
