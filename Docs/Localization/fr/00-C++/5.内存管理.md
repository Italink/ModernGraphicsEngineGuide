## Concepts de base

Les différentes données d'un ordinateur sont généralement **stockées** sur un **disque**. En cliquant avec le bouton droit sur l'icône "Ce PC" du bureau, puis en sélectionnant "Gérer" → "Stockage" → "Gestion des disques", vous pouvez parcourir et manipuler les disques :

Dans le **Gestionnaire des tâches** et le **Moniteur des ressources**, vous pouvez également voir l'état d'exécution actuel du disque :

![image-20230203202516951](../../../00-C++/Resources/image-20230203202516951.png)

Lorsque les données du disque sont utilisées, le système d'exploitation les charge en mémoire. Concernant la mémoire, [Baidu Baike](https://baike.baidu.com/item/%E5%86%85%E5%AD%98/103614) donne la définition suivante :

> La mémoire est un composant important de l'ordinateur, également appelé **mémoire interne** et **mémoire principale**. Elle est utilisée pour stocker temporairement les données de calcul de l'CPU ainsi que les données échangées avec des **mémoires externes** telles que le disque dur. C'est le pont de communication entre la mémoire externe et l'CPU. Tous les programmes de l'ordinateur s'exécutent en mémoire, et les performances de la mémoire influencent le niveau global de l'ordinateur. Dès que l'ordinateur démarre, le système d'exploitation transfère les données nécessaires au calcul de la mémoire vers l'CPU pour traitement. Une fois le calcul terminé, l'CPU transmet les résultats.

### Pile (Stack) et Tas (Heap)

Un programme (fichier `.exe` sous Windows) est également un type de données. Lors de son lancement, le système d'exploitation lui alloue deux blocs de mémoire de **taille fixe**, respectivement utilisés comme :

- **Pile (Stack)** : Principalement pour l'appel et l'exécution des piles de fonctions
- **Tas (Heap)** : Pour stocker les adresses des mémoires allouées dynamiquement pendant l'exécution du programme

> La taille de la pile est fixe, tandis que celle du tas dépend de l'implémentation et du compilateur utilisé. Le tas peut être considéré comme un stockage chaîné des adresses des mémoires allouées dynamiquement. Bien que la taille par défaut **préallouée** du tas dans MSVC soit de 1MB, l'espace utilisé pendant l'exécution peut dépasser 1MB.

Les compilateurs et les plateformes différents ont des tailles par défaut différentes. Prenons MSVC sous Windows comme exemple et exécutons le programme suivant :

``` c++
int main() {
	char arr[10000000];
	return 0;
}
```

Étant donné que nous créons ou utilisons une mémoire en pile dépassant la taille préallouée du programme, une erreur **Stack Overflow** sera signalée :

![image-20230203205039824](../../../00-C++/Resources/image-20230203205039824.png)

Exécutons ensuite le programme suivant :

``` c++
int main() {
	for (int i = 0; i < 100000000; i++) {
		new int;
	}
	return 0;
}
```

Lorsqu'il n'y a pas de bloc de mémoire libre correspondant, l'allocation dynamique échoue :

![image-20230203210759623](../../../00-C++/Resources/image-20230203210759623.png)

Vous pouvez définir manuellement la taille de la pile et du tas préalloués par le programme via le compilateur. Dans Visual Studio, vous pouvez modifier cela dans la configuration du projet :

### Fragmentation de la mémoire

En C++, nous utilisons généralement `new`/`delete` pour créer et détruire des mémoires dynamiques. En réalité, les interfaces d'allocation de mémoire des différents systèmes d'exploitation sont différentes. Par exemple, Windows utilise en fait `VirtualAlloc`/`VirtualFree`, tandis que Unix et Mac utilisent `mmap`/`munmap`.

Pendant l'exécution du programme, des allocations et des récupérations fréquentes de mémoire entraînent de nombreuses petites mémoires continues夹杂ées entre les mémoires déjà allouées. Étant donné que l'algorithme d'allocation de mémoire du système d'exploitation n'est pas parfait, ces **mémoires libres ne peuvent pas être réutilisées**. Ces mémoires sont appelées **fragments de mémoire**.

### Alignement de la mémoire

La plupart des CPU ne lisent ou n'écrivent pas la mémoire par octet. Ils utilisent généralement 2, 4, 6 ou 8 octets comme granularité d'accès à la mémoire, ce qui améliore l'efficacité d'E/S de la mémoire. Pour plus de détails, vous pouvez consulter :

- https://zhuanlan.zhihu.com/p/83449008

L'alignement de la mémoire varie selon les opérations, le matériel et la plateforme. Pour les développeurs, s'ils ne connaissent pas les termes techniques, il est facile de tomber dans des pièges, par exemple :

- L'utilisation de SIMD nécessite un alignement de 16 octets.
- Il existe une limite de décalage minimal d'alignement entre les buffers alloués sur le GPU.
- Les modes d'alignement des vecteurs diffèrent également selon les API de rendu.

### Cache高速 (Cache)

La vitesse de lecture/écriture de la mémoire est réellement rapide, mais celle de l'CPU est encore plus élevée, ce qui fait que l'CPU doit attendre longtemps pour la venue (lecture) et l'envoi (écriture) des données. Pour réduire le temps moyen d'accès de l'CPU à la mémoire, le système de stockage de l'ordinateur a introduit le composant **Cache CPU**. Dans [Baidu Baike](https://baike.baidu.com/item/CPU%E7%BC%93%E5%AD%98), on trouve la définition suivante :

> Dans un système informatique, le **Cache CPU** (en anglais : CPU Cache) est un composant utilisé pour réduire le temps moyen nécessaire à un processeur pour accéder à la mémoire.
>
> Dans le système de stockage pyramidal, il se trouve au deuxième niveau du haut vers le bas, juste après les registres CPU. Sa capacité est bien inférieure à celle de la mémoire, mais sa vitesse peut approcher celle du processeur.
>
> Lorsque le processeur envoie une demande d'accès à la mémoire, il vérifie d'abord si les données demandées sont dans le cache. Si elles y sont (cache hit), il retourne directement les données sans accéder à la mémoire. Si elles n'y sont pas (cache miss), il charge d'abord les données correspondantes de la mémoire dans le cache, puis les retourne au processeur.
>
> Le cache est efficace principalement parce que l'accès à la mémoire pendant l'exécution du programme présente une caractéristique de localité (Locality), incluant à la fois la localité spatiale (Spatial Locality) et la localité temporelle (Temporal Locality). En utilisant efficacement cette localité, le cache peut atteindre un taux de réussite très élevé.
>
> Pour le processeur, le cache est un composant transparent. Par conséquent, les programmeurs ne peuvent généralement pas intervenir directement sur les opérations du cache. Cependant, il est possible d'optimiser spécifiquement le code du programme selon les caractéristiques du cache pour l'utiliser mieux.

Sous Windows, vous pouvez ouvrir le Gestionnaire des tâches pour consulter les informations sur le Cache de votre ordinateur :

![image-20230203213134642](../../../00-C++/Resources/image-20230203213134642.png)

Lorsqu'un programme accède à un bloc de mémoire, il peut charger sa zone environnante dans le cache (car le chargement supplémentaire d'une partie du contenu n'entraîne pas beaucoup de surcoût). Si la mémoire que nous devons accéder ensuite a déjà été chargée dans le cache (appelé cache hit), l'CPU n'a pas besoin d'accéder à la mémoire, ce qui améliore la vitesse.

Ce code exemple vous permet de comprendre l'importance du cache :

``` c++
#include <iostream>
#include <chrono>
#include <vector>

class ClockGuard {			//Permet d'afficher le temps d'exécution d'un scope
public:
	ClockGuard(const std::string& inDest)
		:mDesc(inDest)
	{
		mStartTime = std::chrono::steady_clock::now();
	}
	~ClockGuard() {
		std::chrono::steady_clock::time_point currentTime = std::chrono::steady_clock::now();
		double durationNs = std::chrono::duration<double, std::nano>(currentTime - mStartTime).count();
		std::cout << mDesc << " Cost: " << durationNs << " Ns" << std::endl;
	}
private:
	std::string mDesc;
	std::chrono::steady_clock::time_point mStartTime;
};

const size_t bigger_than_cachesize = 10 * 1024 * 1024;
long* ptr = new long[bigger_than_cachesize];
void ClearCPUCache() {				//Tente de vider le cache
	for (int i = 0; i < bigger_than_cachesize; i++){
		ptr[i] = rand();
	}
}

int main(int argc,char** argv) {
	std::vector<int*> continuous(1000);		//Tableau de mémoire continue
	std::vector<int*> dispersive(1000);		//Tableau de mémoire dispersée

	for (int*& item : continuous) {		
		item = new int;
	}

	const int spacing = 10000;	   		//Espacement de la mémoire, ajustez ce nombre pour voir l'impact du cache
	for (int*& item : dispersive) {	   		
		item = new int[spacing];
	}

	ClearCPUCache();
	{
		ClockGuard guard("continuous");		//Affectation à la mémoire continue, taux de cache hit élevé
		for (int*& item : continuous) {
			*item = 1;
		}
	}
    
	ClearCPUCache();
	{
		ClockGuard guard("dispersive");		//Affectation à la mémoire dispersée, taux de cache hit bas 
		for (int*& item : dispersive) {
			*item = 1;
		}
	}

	return 0;
}
```

Éviter de modifier le contexte de la mémoire peut efficacement augmenter le taux de cache hit. Le cerveau humain a en fait un mécanisme similaire, ne croyez-vous pas ?

### Accélération matérielle

En plus du mécanisme de cache, la mémoire présente également des **"magies noires"** dans son utilisation, par exemple le code suivant :

``` C++
#include <iostream>
#include <chrono>
#include <vector>

class ClockGuard {
public:
	ClockGuard(const std::string& inDest)
		:mDesc(inDest) {
		mStartTime = std::chrono::steady_clock::now();
	}
	~ClockGuard() {
		std::chrono::steady_clock::time_point currentTime = std::chrono::steady_clock::now();
		double durationNs = std::chrono::duration<double, std::nano>(currentTime - mStartTime).count();
		std::cout << mDesc << " Cost: " << durationNs << " Ns" << std::endl;
	}
private:
	std::string mDesc;
	std::chrono::steady_clock::time_point mStartTime;
};

const size_t bigger_than_cachesize = 10 * 1024 * 1024;
long* ptr = new long[bigger_than_cachesize];
void ClearCPUCache() {
	for (int i = 0; i < bigger_than_cachesize; i++) {
		ptr[i] = rand();
	}
}

int main(int argc, char** argv) {
	std::vector<int> src(100000);
	std::vector<int> dst(100000);

	ClearCPUCache();
	{
		ClockGuard guard("Copy");		//Copie C++ normale
		for (int i = 0; i < src.size(); ++i) {
			dst[i] = src[i];
		}
	}
	ClearCPUCache();
	{
		ClockGuard guard("Map");		//Copie de mémoire
		memcpy(dst.data(), src.data(), src.size());
	}

	return 0;
}
```

En syntaxe C++, on ne peut pas écrire de code plus simple que `for (int i = 0; i < src.size(); ++i) { dst[i] = src[i]; }`, mais l'utilisation de `memcpy` pour faire la même chose améliore considérablement les performances. Cela est principalement dû au fait que `memcpy` utilise une optimisation au niveau de l'assembleur et est fortement lié aux caractéristiques matérielles :

- Principe de fonctionnement de memcpy sur architecture ARM64 : https://blog.csdn.net/m0_46250244/article/details/115055101

Dans votre parcours d'apprentissage de la graphique, vous rencontrerez également de nombreuses opérations similaires sur le GPU. Par conséquent, les lecteurs doivent approfondir leur connaissance de l'architecture matérielle.

### Directions d'optimisation

En résumé, les principales stratégies d'optimisation de la mémoire sont principalement axées sur les points suivants :

- **Réduire les fragments de mémoire et augmenter le taux de cache hit**
- **Utiliser des méthodes d'opération de mémoire efficaces en combinant le scénario d'application et les caractéristiques matérielles**

## Gestion du cycle de vie des objets

Dans le développement de programmes modernes, il y a une multitude d'objets. Pour les objets alloués sur la pile, ils sont automatiquement libérés lorsqu'ils quittent leur scope. Mais pour les objets alloués sur le tas, nous devons gérer manuellement leur cycle de vie. En C++, cela signifie que nous devons garantir que `new` et `delete` correspondent l'un à l'autre. Idéalement, c'est comme ça :

``` c++
void Func(){
    Object* object = new Object;
    //...
    delete object;
}
```

Mais la réalité est cruelle. Lorsque des branches logiques ou des fonctions imbriquées apparaissent dans le code, et que le cycle de vie de l'objet est transféré, il devient difficile de contrôler manuellement son `delete` :

``` c++
void Func(){
    Object* object = new Object;
    if(...){
        //Faire quelque chose 
        delete object;
        return;
    }
    else if(...){
        //Faire quelque chose 
        delete object;
        return;
    }
    else if(...){
        //Faire quelque chose 
        delete object;
        return;
    }
}
```

À cet égard, nous avons souvent besoin d'une stratégie de gestion automatique du cycle de vie des objets. Actuellement, il existe deux principales méthodes :

- Pointeurs intelligents
- Récupération de garbage (Garbage Collection)

### Pointeurs intelligents

Dans les différentes bibliothèques C++, on trouve souvent le concept de pointeur partagé. Son idée centrale est :

- Utiliser un objet externe pour envelopper le pointeur de l'objet réel. En surveillant la construction, la destruction et la copie de l'objet externe, utiliser une mémoire publique pour enregistrer la référence du pointeur. Lorsque la référence atteint 0, l'objet est détruit.

Une imitation simplifiée est la suivante :

```c++
struct SharedPtrRefData{
    uint refCount = 0; 
};

template<Typename _Ty>
class SharedPtr{
public:
	SharedPtr(_Ty* rawPtr)						//Constructeur
    	: mRawPtr(rawPtr)
        , mRefData(new SharedPtrRefData)		//Nouvelle mémoire publique
    {
        mRefData->refCount++;					//Compteur de référence +1
	}
    
    SharedPtr(const SharedPtr<_Ty>& other){		//Constructeur de copie
        mRefData = other.mRefData;				//Transmettre la mémoire publique
        mRefData->refCount++;					//Compteur de référence +1
    }
    
    ~SharedPtr(){								//Destructeur
        mRefData->refCount--;					//Compteur de référence -1
        if(mRefData->refCount == 0){	
            delete mRawPtr;						//Détruire l'objet
            delete mRefData;					//Détruire la mémoire publique
        }
    }
private:
    _Ty* mRawPtr;
    SharedPtrRefData* mRefData;
};
```

Cette structure est implémentée dans les frameworks suivants :

- Bibliothèque standard C++ : **std::shared_ptr**
- Unreal Engine : **TSharedPtr**
- Qt : **QSharedPointer**

L'utilisation de `SharedPtr` garantit que l'objet pointé n'a pas été libéré lors de l'accès. Mais parfois, nous souhaitons que le **pointeur partagé** **ne prolonge plus le cycle de vie de l'objet, mais puisse déterminer ultérieurement si l'objet a été détruit**. Les frameworks appellent généralement cette structure **WeakPtr**, correspondant à :

- Bibliothèque standard C++ : **std::weak_ptr**
- Unreal Engine : **TWeakPtr**
- Qt : **QWeakPointer**

Prenons `std` comme exemple :

```c++
#include <iostream>

int main() {
	std::shared_ptr<int> sptr(new int);
	std::weak_ptr<int> wptr(sptr);
	if (const std::shared_ptr<int>& lock = wptr.lock()) {
		std::cout << "exist !!!" << std::endl;
	}
	else {
		std::cout << "not exist" << std::endl;
	}
	sptr.reset();
	if (const std::shared_ptr<int>& lock = wptr.lock()) {
		std::cout << "exist !!!" << std::endl;
	}
	else {
		std::cout << "not exist !" << std::endl;
	}
	return 0;
}

/*
exist !!!
not exist !
*/
```

Dans le code simplifié de `SharePtr` ci-dessus, lorsque `refCount` est 0, l'objet et la mémoire publique sont détruits simultanément. En réalité, `SharedPtrRefData` contient deux compteurs : `refCount` et `weakCount`. Lorsque `refCount` est 0, seul l'objet est détruit, pas la mémoire publique. Cela permet à `WeakPtr` d'accéder toujours à la mémoire partagée pour vérifier si l'objet existe encore. La mémoire publique n'est détruite que lorsque `weakCount` est également 0.

Pour un pointeur nu, `delete` ne détruit que la mémoire de l'objet, et l'adresse pointée par le pointeur existe toujours. Si la gestion est incorrecte, un pointeur sauvage (wild pointer) peut apparaître,导致内存泄漏. `WeakPtr` résout ce problème.

Il existe également un cas où nous souhaitons qu'un objet créé avec `new` soit détruit lorsqu'il quitte son scope, comme un objet normal, par exemple :

``` c++
class Example{
public:
    Example()
   		: mObject(new Object)	//Erreur de syntaxe : virgule manquante après mObject(new Object)
    {}
    ~Example(){
        delete mObject;
    } 
private:
    Object* mObject;
};
```

Dans ce cas, nous pouvons utiliser :

- Bibliothèque standard C++ : **std::unique_ptr**
- Unreal Engine : **TUniquePtr**
- Qt : **QScopedPointer**

> Le nommage de Qt semble mieux refléter son rôle.

Le code ci-dessus peut être réécrit avec `UniquePtr` comme suit :

``` c++
class Example{
public:
    Example()
   		: mObject(new Object)
    {}
private:
    std::unique_ptr<Object> mObject;
};
```

Les pointeurs intelligents peuvent résoudre la plupart des problèmes lors du développement, mais ils ne sont pas parfaits. Voici quelques **points à noter** :

- Lors de l'utilisation de pointeurs intelligents, il est préférable de créer l'objet dans le constructeur ou la fonction `reset`, et de ne pas manipuler le pointeur nu en dehors du pointeur intelligent.

  ``` c++
  //Exemple de mauvaise pratique :
  Object* raw = new Object;
  std::shared_ptr<Object> sptr(raw);
  delete raw; //Erreur : double libération
  ```
  
- On ne peut pas utiliser `std::shared<int> sptr(this)`. Si on souhaite créer un pointeur partagé avec `this`, la classe de `this` doit hériter du modèle `enable_shared_from_this`.

- L'utilisation excessive de `SharedPtr` inutile entraînera un certain gaspillage. L'intention de l'utilisation de `SharedPtr` est de maintenir le cycle de vie de l'objet. Si vous n'avez pas besoin de transmettre le cycle de vie de l'objet via une interface lors de son encapsulation, vous ne devriez pas exposer `SharedPtr`, mais plutôt `WeakPtr` ou `RawPtr`.

- Lors de l'utilisation dans un environnement multithread, assurez-vous que le `SharedPtr` utilisé est thread-safe, pour garantir le bon fonctionnement du compteur de référence.

De plus, il existe quelques **risques** :

- Lors de l'utilisation de pointeurs partagés, il est facile de négliger le cycle de vie des paramètres capturés. Si un pointeur partagé est présent à l'intérieur, cela entraînera une fuite de mémoire :

  ``` c++
  #include <iostream>
  #include <functional>
  
  class Example { //Erreur de typo : Exmaple → Example
  public:
  	Example() {
  		std::cout << "Create" << std::endl;
  	}
  	~Example() {
  		std::cout << "Destroy" << std::endl;
  	}
  };
  
  int main(int argc, char** argv) {
  	{
  		std::function<void()> func0;
  		{
  			std::shared_ptr<Example> sptr(new Example);
  			std::function<void()> func1 = [sptr]() {};	//Capturer le pointeur partagé
  			std::cout << "---------0" << std::endl;
  			//func0 = func1;		//Décommenter pour que Example soit libéré entre 1 et 2
  		}
  		std::cout << "---------1" << std::endl;
  	}
  	std::cout << "---------2" << std::endl;
  	return 0;
  }
  /*
  Les paramètres capturés par lambda ne sont libérés que lorsqu'ils quittent leur scope et qu'aucune fonction ne les référence.
  Si la fonction n'est pas détruite ou réinitialisée à temps, les paramètres capturés existeront toujours,导致内存泄漏.
  */
  ```

- `SharedPtr` présente un problème de référence circulaire :

  ```c++
  #include <iostream>
  #include <memory> //Manquant : nécessaire pour std::shared_ptr
  
  struct B;
  
  struct A {
  	~A() {
  		std::cout << "destruct A" << std::endl;
  	}
  	std::shared_ptr<B> mB;
  };
  
  struct B {
  	~B() {
  		std::cout << "destruct B" << std::endl;
  	}
  	std::shared_ptr<A> mA;
  };
  
  int main() {
  	{
  		std::shared_ptr<A> a(new A);
  		std::shared_ptr<B> b(new B); 
  		a->mB = b;
  		b->mA = a;
  	}
  	return 0;	//Les objets ne sont pas libérés
  }
  ```

- La destruction de `SharedPtr` est immédiate. Dans un système de grande taille, la destruction d'un grand nombre d'objets en une fois peut causer des ralentissements.

### Récupération de garbage (Garbage Collection)

Pour résoudre les défauts des pointeurs partagés, certains langages de haut niveau et grands frameworks fournissent un mécanisme de récupération de garbage (Garbage Collection), visant à résoudre le problème de référence circulaire et à implémenter la destruction différée.

> En raison des caractéristiques de C++ (raisons historiques), si un mécanisme de récupération de garbage médiocre était intégré dans la norme C++, cela ne ferait qu'ajouter de la confusion. Par conséquent, la récupération de garbage en C++ est souvent personnalisée par le framework, comme UE et Qt, qui sont sortis du cadre de la norme C++. Les internautes les appellent souvent U++ et Q++.

Actuellement, les mécanismes GC que l'auteur connaît bien sont :

- Unreal Engine
- Qt, FBX SDK
- Lua

Pour les développeurs, il faut principalement comprendre deux points sur le GC :

- Comment marquer les relations de référence entre les objets
- Comment effectuer la récupération de garbage

Pour certains langages de haut niveau comme Java, C# et Python, grâce à la machine virtuelle, il est facile de surveiller les relations de référence entre les objets. En C++, les relations de référence entre les objets ne peuvent être établies que par configuration manuelle ou analyse par réflexion.

Qt utilise `QObject` comme classe de base. Sa récupération de mémoire est très simple, comme suit :

```cpp
class QObject{
public:
    QObject(QObject * parent = nullptr);
private:
    QVector<QObject*> children; //Erreur de typo : QObejct → QObject
    QObject *parent;
};
```

- `QObject` contient un pointeur `parent` et une liste `children`. Lorsque `QObject` est détruit, ses `children` sont également détruits.
- `QObject` fournit également une fonction `deleteLater()`, qui ajoute l'objet à un tableau. La destruction n'a lieu qu'après la fin de la boucle de traitement des événements.

FBX SDK utilise `FbxObject` comme classe de base. Lors de la création d'une instance, il faut spécifier son objet parent, comme suit :

```cpp
FbxManager* lManager = FbxManager::Create();
FbxIOSettings* lIOSettings = FbxIOSettings::Create(lManager, "");
FbxScene* scene = FbxScene::Create(lManager,"");
FbxSkeleton* skeletonNode = FbxSkeleton::Create(scene,"SkeletonRoot");
FbxCluster* rootCluster = FbxCluster::Create(skeletonNode, "");
```

- Lorsque l'objet parent est libéré, les objets enfants sont libérés.

La structure principale de la récupération de mémoire des deux frameworks ci-dessus est très simple. Pour le problème de cycle, ils détectent lors de la spécification du parent et signalent une erreur directement en cas de cycle.

Le mécanisme GC d'UE est beaucoup plus complexe. Dans UE, les références sont principalement établies de deux manières :

- `UProperty` (Réflexion) : UE détermine les relations de référence entre deux objets en analysant les propriétés de `UObject`.
- `FGCObject` : Classe d'interface pour établir manuellement des relations de référence. La plupart des frameworks d'UE, comme UMG, Editor, Niagara..., dérivent de `FGCObject` pour implémenter un mécanisme de gestion des références GC, de sorte que les développeurs établissent implicitement des relations de référence entre les objets lors de l'appel de certaines interfaces.

La méthode de récupération d'UE est assez complexe et ne sera pas développée ici. Il suffit de savoir qu'elle est récupérée定时定量 (à intervalles réguliers et en quantités fixes).

Voici une présentation d'un algorithme simple de marquage et nettoyage (Mark-and-Sweep), dont le cœur est :

- Stocker tous les objets récupérables dans un tableau.
- Stocker les relations de référence entre les objets.
- Posséder un nœud racine global. Si un autre nœud a une relation de référence pour atteindre ce nœud, cela signifie que le nœud est accessible.
- Lors de la récupération de garbage, il faut suspendre le thread du jeu pour garantir que tous les objets ne sont pas utilisés.
- Parcourir depuis le nœud racine et marquer tous les nœuds accessibles.
- Parcourir le tableau d'objets et détruire les nœuds non accessibles.

Une implémentation simplifiée est la suivante (pour plus de détails, consultez : [Mark-and-Sweep：垃圾收集算法](https://link.zhihu.com/?target=https%3A//www.geeksforgeeks.org/mark-and-sweep-garbage-collection-algorithm/)) :

```cpp
class ObjectBase{
public:
    typedef short ID;
public:
    ObjectBase();
    virtual ~ObjectBase();
    void addRefrence(ObjectBase * ref);     //Ajouter une référence à l'objet
    void removeRefrence(ObjectBase* ref);   //Supprimer une référence à l'objet
private:
    friend class ObjectManagement;
    ID id;                      //Attribuer un ID unique à l'objet
    std::list<ID> refrence;     //Liste des IDs des objets référencés
};
```

> Ici, `short` est utilisé car il ne fait que 2 octets et peut représenter 2^15 (32767) nombres, ce qui est suffisant pour les IDs.

Pour pouvoir gérer tous les objets `ObjectBase`, un objet de gestion global **GObjectManagement** est créé. Lors de la construction, l'objet est ajouté à celui-ci, et lors de la destruction, il est supprimé :

```cpp
ObjectBase::ObjectBase(){
    GObjectManagement.AddObject(this);
}

ObjectBase::~ObjectBase(){
    GObjectManagement.RemoveObject(this);
}
```

La définition de `ObjectManagement` est la suivante :

```cpp
class ObjectManagement {
public:
    ObjectManagement() {
        for (int i = 0; i < mObjects.size(); i++) {     //Initialiser la pile d'IDs
            mObjects[i].object = nullptr;
            mIdStack[i] = i;
        }
    }
    void AddObject(ObjectBase* obj) {       //Ajouter un objet
        if (obj != nullptr) {
            obj->id = allocId();
            mObjects[obj->id].object = obj;
            ++mCurrentNumberOfObject;
            mMaxIdOfObject = std::max(mMaxIdOfObject, obj->id);
        }
    }
    void RemoveObject(ObjectBase* obj) {    //Supprimer un objet
        if (obj != nullptr) {
            mObjects[obj->id].object = nullptr;
            freeId(obj->id);
            --mCurrentNumberOfObject;
        }
    }
    void GarbageCollection() {              //Récupération de garbage
        MarkObjects(0);        //Ici, on suppose que le nœud 0 est le nœud racine global du jeu. On commence par lui pour parcourir et marquer les objets accessibles.
        for (int i = 0; i <= mMaxIdOfObject; i++) {     //Parcourir simplement tous les objets et détruire ceux non accessibles
            if (!mObjects[i].reachable) {
                delete mObjects[i].object;
            }
            else {      //Réinitialiser l'état pour la prochaine traversée d'accessibilité
                mObjects[i].reachable = false;
            }
        }
    }

    void MarkObjects(const ObjectBase::ID& Id) {                //Parcourir tous les nœuds en profondeur
        ObjectBase* obj = mObjects[Id].object;
        if (obj != nullptr && !mObjects[Id].reachable) {        //Le nœud doit être inaccessible pour éviter les cycles
            mObjects[Id].reachable = true;
            for (auto& subId : obj->refrence) {
                MarkObjects(subId);
            }
        }
    }

private:
    ObjectBase::ID allocId() {                  //Allouer un ID depuis le sommet de la pile
        assert(mIdStackTop < mIdStack.size());
        return mIdStack[mIdStackTop++];
    }
    
    void freeId(ObjectBase::ID id) {            //Récupérer un ID
        assert(mIdStackTop > 0);
        mIdStack[--mIdStackTop] = id;
    }

public:
    struct ObjectItem{
        ObjectBase* object;
        bool reachable = false;
    };

    static const int MAX_NUMBER_OF_OBJECT = std::numeric_limits<ObjectBase::ID>().max();

    std::array<ObjectItem, MAX_NUMBER_OF_OBJECT> mObjects;      //Ici, un tableau de taille fixe de 32767 éléments est créé pour stocker tous les objets
    
    std::array<ObjectBase::ID, MAX_NUMBER_OF_OBJECT> mIdStack;  //Ce tableau de taille fixe simule une pile pour allouer et récupérer des IDs, garantissant que les IDs ne se développent pas rapidement
    ObjectBase::ID mIdStackTop = 0;                             //Index du sommet de la pile

    ObjectBase::ID mCurrentNumberOfObject = 0;                  //Nombre actuel d'objets existants
    ObjectBase::ID mMaxIdOfObject = 0;                          //ID maximum utilisé dans le programme, pour réduire le nombre de traversées
};

//Objet statique global
static ObjectManagement GObjectManagement;
```

## Frameworks de planification de mémoire

La communauté open source a vu émerger de nombreux frameworks de planification de mémoire visant à réduire les fragments de mémoire et à augmenter le taux de cache hit. Parmi les plus connus, on trouve :

### [mimalloc](https://github.com/microsoft/mimalloc)

mimalloc est un allocateur généraliste avec des caractéristiques de [performance](https://github.com/microsoft/mimalloc#performance) exceptionnelles. Initialement développé par Daan Leijen pour les systèmes d'exploitation des langages [Koka](https://koka-lang.github.io/) et [Lean](https://github.com/leanprover/lean).

- **Petit et cohérent** : La bibliothèque utilise des structures de données simples et cohérentes, d'environ 8k LOC. Cela la rend très adaptée à l'intégration et à l'adaptation à d'autres projets. Pour les systèmes d'exploitation, elle fournit des crochets pour les *heartbeats* monotones et les libérations différées (pour un temps d'exécution maximal borné avec comptage de références).
- **Fragmentation des listes libres** : Chaque "page mimalloc" a de nombreuses listes plus petites au lieu d'une grande liste libre (par classe de taille), ce qui réduit la fragmentation et augmente la localité — les éléments alloués à peu de间隔 sont alloués près les uns des autres en mémoire. (Une page mimalloc contient un bloc de taille fixe, généralement 64KiB sur les systèmes 64 bits).
- **Multi-fragmentation des listes libres** : Bonne idée ! Nous ne fragmentons pas seulement les listes libres de chaque page mimalloc, mais pour chaque page, nous avons plusieurs listes libres. En particulier, il y a une liste pour les opérations `free` locales au thread, et une autre pour les opérations `free` concurrentes. La libération depuis un autre thread peut maintenant être une simple opération CAS, sans coordination complexe entre les threads. Comme il y aura des milliers de listes libres individuelles, la contention est naturellement distribuée sur le tas, et les chances de contention sur un seul emplacement seront faibles — cela ressemble beaucoup à des algorithmes aléatoires comme les listes sautantes (skip lists), où l'ajout d'une machine à sous aléatoire élimine le besoin d'algorithmes plus complexes.
- **Réinitialisation proactive des pages** : Lorsqu'une "page" devient vide (grâce à l'augmentation des chances de fragmentation des listes libres), la mémoire est marquée comme non utilisée par le système d'exploitation ("réinitialisée" ou "nettoyée") pour réduire la pression (réelle) sur la mémoire et la fragmentation, notamment dans les programmes longs.
- **Sécurité** : *mimalloc* peut être construit en mode sécurisé, ajoutant des pages de protection, des allocations aléatoires, des listes libres cryptées, etc., pour prévenir diverses vulnérabilités du tas. La perte de performance est généralement d'environ 10% en moyenne sur nos benchmarks.
- **Tas de première classe** : Créer et utiliser efficacement plusieurs tas pour des allocations dans différentes zones. Les tas peuvent être détruits en une fois, au lieu de libérer chaque objet individuellement.
- **Borné** : Il n'est pas affecté par l'*expansion*, avec un temps d'allocation maximal borné ( *wcat* ), un surcoût spatial borné (environ 0.2% de métadonnées, avec un gaspillage maximal de 12.5% sur la taille de l'allocation), et aucun point interne de contention grâce à l'utilisation d'opérations atomiques.
- **Rapide** : Dans nos benchmarks, *mimalloc* surpasse les autres allocateurs leaders ( *jemalloc* , *tcmalloc* , *Hoard* , etc.) et utilise généralement moins de mémoire. Une bonne caractéristique est qu'il fonctionne toujours bien sur une large gamme de benchmarks. Pour les grands programmes serveurs, il y a également un bon support pour les grandes pages du système d'exploitation.

### [oneTBB](https://www.intel.com/content/www/us/en/developer/tools/oneapi/onetbb.html)

Intel® oneAPI Threading Building Blocks (oneTBB) est une bibliothèque de performance flexible qui simplifie l'ajout de parallélisme aux applications complexes sur des architectures accélérées, même si vous n'êtes pas un expert en threads.

- **Spécifier la performance logique, pas les threads**
  La bibliothèque d'exécution mappe automatiquement le parallélisme logique sur les threads, permettant une utilisation la plus efficace des ressources du processeur.
- **Cibler les threads pour améliorer la performance**
  Se concentrer sur la parallélisation de tâches spécifiques à haute intensité calculatoire, fournissant des solutions plus haut niveau et plus simples.
- **Coexister avec d'autres paquets de threads**
  Il peut être intégré de manière transparente avec d'autres threads, vous donnant la flexibilité de conserver votre ancien code inchangé et d'utiliser oneTBB pour de nouvelles implémentations.
- **Mettre l'accent sur la programmation parallèle des données extensible** oneTBB met l'accent sur la programmation parallèle des données, plutôt que de décomposer le programme en blocs fonctionnels et d'attribuer un thread séparé à chaque bloc, permettant à plusieurs threads de travailler sur différentes parties d'un ensemble. En divisant l'ensemble en parties plus petites, cela s'étend bien à un plus grand nombre de processeurs. À mesure que vous ajoutez des processeurs et des accélérateurs, les performances du programme s'améliorent.

### [jemalloc](https://github.com/jemalloc/jemalloc)

jemalloc est une implémentation personnalisée de `malloc(3)` pour C, conçue pour éviter la fragmentation et offrir un support de concurrence extensible. Elle est destinée à être utilisée comme allocateur de mémoire fourni par le système, comme dans la bibliothèque libc de FreeBSD, ainsi que pour être liée à des applications C/C++. jemalloc offre de nombreuses fonctionnalités d'introspection, de gestion de mémoire et de réglage au-delà des capacités des allocateurs standard.

### [tcmalloc](https://github.com/google/tcmalloc)

TCMalloc est une implémentation personnalisée de `malloc()` pour C et `operator new` pour C++ par Google, utilisée pour allouer de la mémoire dans le code C et C++. Ce framework d'allocation de mémoire personnalisé est une alternative à ceux fournis par la bibliothèque standard C (généralement via `glibc` sur Linux) et la bibliothèque standard C++.

- Les performances augmentent avec le degré de parallélisme de l'application
- Optimisé pour C++14 et C++17, et légèrement différent de la norme tout en garantissant un avantage en performance (ces différences sont indiquées dans la [référence TCMalloc](https://github.com/google/tcmalloc/blob/master/docs/reference.md))
- Permet des extensions pour améliorer les performances sur certaines architectures, ainsi que d'autres comportements, comme la collecte de métriques

- Effectue des allocations depuis le système d'exploitation en gérant des blocs de mémoire de taille fixe (appelés "pages").
- Utilise des pages individuelles (ou des séquences de pages appelées "spans" dans TCMalloc) pour des tailles d'objets spécifiques. Par exemple, tous les objets de 16 octets sont placés dans des "spans"专门分配 pour cette taille d'objet. Dans ce cas, les opérations d'obtention ou de libération de mémoire sont beaucoup plus simples.
- Conserve la mémoire dans un *cache* pour accélérer l'accès aux objets fréquemment utilisés. La conservation d'un tel cache, même après la libération, peut aider à éviter des appels système coûteux si la mémoire est réallouée ultérieurement.

## Optimisation des bibliothèques de base

Au niveau de l'application de la mémoire, les conteneurs et algorithmes de base de C++ ont beaucoup de potentiel d'optimisation. Il faut parler de la bibliothèque STL C++, qui a de nombreux défauts :

- Certaines implémentations STL (notamment Microsoft STL) ont des caractéristiques de performance médiocres, ce qui les rend inadaptées au développement de jeux.
- STL est parfois difficile à déboguer, car la plupart des implémentations STL utilisent des noms de variables mystérieux et des structures de données inhabituelles.
- Les allocateurs STL sont parfois douloureux à utiliser, car ils ont beaucoup de exigences et ne peuvent pas être modifiés une fois liés à un conteneur.
- STL contient trop de fonctionnalités qui peuvent faire dépasser le code les attentes. Il n'est pas facile de dire aux programmeurs qu'ils ne devraient pas utiliser une fonctionnalité.
- STL est implémenté par des appels de fonction très profonds. Cela entraîne des performances inacceptables dans les builds non optimisés, et parfois aussi dans les builds optimisés.
- STL ne prend pas en charge l'alignement des objets contenus.
- Les conteneurs STL ne vous permettent pas d'insérer des entrées sans fournir l'entrée à copier. Cela peut être inefficace.
- Les extensions STL utiles trouvées dans des implémentations STL existantes comme STLPort (par exemple slist, hash_map, shared_ptr) ne sont pas portables, car elles n'existent pas dans d'autres versions STL ou sont inconsistantes entre les versions STL.
- STL manque d'extensions utiles que les développeurs de jeux considèrent comme utiles (par exemple intrusive_list), mais qui peuvent être optimisées de manière optimale dans un environnement STL portable.
- La spécification de STL limite notre capacité à l'utiliser efficacement. Par exemple, un vecteur STL ne garantit pas l'utilisation de mémoire continue, donc il ne peut pas être utilisé en toute sécurité comme un tableau.
- STL met l'accent sur la correction avant la performance, et parfois vous pouvez obtenir des gains de performance significatifs en réduisant la pureté académique.
- Les conteneurs STL ont une implémentation privée, qui ne vous permet pas de manipuler leurs données de manière portable, mais parfois c'est important (par exemple le pool de nœuds).
- Toutes les versions existantes de STL allouent de la mémoire dans au moins certaines versions vides de leurs conteneurs. Ce n'est pas idéal et empêche des optimisations comme la réinitialisation de la mémoire du conteneur, qui peut améliorer considérablement les performances dans certains cas.
- La compilation de STL est lente, car la plupart des implémentations STL modernes sont très volumineuses.

> Extrait de https://github.com/electronicarts/EASTL/blob/master/doc/Design.md

Son principal défaut est :

- **STL met l'accent sur la correction avant la performance. Pour追求 l'exactitude académique, il n'a pas pris de risques pour la performance.**

Par exemple, beaucoup d'entre vous savent qu'il faut utiliser `reserve` pour allouer à l'avance et éviter les réallocations de mémoire dues à l'extension lors de l'utilisation de `std::vector`. Pour des conteneurs comme `set` et `map`, on peut également allouer à l'avance la mémoire des nœuds. Cela réduit non seulement le nombre d'allocations de mémoire, mais aussi garantit que les éléments du conteneur sont continus en mémoire, ce qui peut augmenter considérablement le taux de cache hit lors de l'accès.

Si vous comparez l'allocateur de mémoire de STL et celui d'UE, vous pouvez constater une différence évidente :

- STL utilise un allocateur pour allouer de la mémoire pour les nouveaux éléments du conteneur.
- L'allocateur d'UE réalloue de la mémoire pour l'ensemble du conteneur, et les conteneurs d'UE prennent en charge un mécanisme d'extension comme `std::vector`.

Pour résoudre les problèmes mentionnés ci-dessus, de nombreux moteurs maintiennent leur propre bibliothèque de base. Parmi les solutions open source, on trouve principalement les suivantes :

### [EASTL](https://github.com/electronicarts/EASTL)

EASTL est une bibliothèque de modèles C++ contenant des conteneurs, des algorithmes et des itérateurs, utilisable pour le développement d'exécution et d'outils跨多个平台. Son implémentation est assez étendue et robuste, et met l'accent sur la performance avant toutes autres considérations.

- EASTL a un schéma d'allocation personnalisé simplifié et plus flexible.
- Le code d'EASTL est plus facile à lire.
- EASTL a des conteneurs et des algorithmes étendus.
- EASTL a des optimisations专为 le développement de jeux.

Parmi les points ci-dessus, la seule différence incompatible avec STL est le cas de l'allocation de mémoire.

### [foonathan](https://github.com/foonathan/memory)

foonathan a également été créé pour résoudre les défauts de STL, mais contrairement à EASTL, il n'a pas tenté de modifier STL.

### [STL C++17 polymorphic memory source](https://www.rkaiser.de/wp-content/uploads/2021/03/embo2021-pmr-STL-for-Embedded-Applications-en.pdf)

Avant C++17, l'allocation de mémoire des conteneurs STL nécessitait l'aide d'un allocateur, qui présentait principalement les défauts suivants :

- L'allocateur fait partie de la signature du modèle. Les conteneurs avec des allocateurs différents ne peuvent pas être mélangés.

  ```c++
  vector<int,allocator0> v0;
  vector<int,allocator1> v1;
  v0 = v1;  //Erreur
  ```

- L'alignement de la mémoire de l'allocateur ne peut pas être contrôlé, il faut passer un allocateur personnalisé.
- L'allocateur n'a pas d'état interne.

C++17 a introduit une nouvelle méthode d'allocation de mémoire pour les conteneurs — ` <memory_resource>`.

Son utilisation est comme suit :

```C++
#include <memory_resource>
#include <vector>
#include <string>            
#include <iostream>

class CustomMemoryResource :public std::pmr::memory_resource{   //Source de mémoire personnalisée
public:
    CustomMemoryResource() {}
private:
    virtual void* do_allocate(const size_t _Bytes, const size_t _Align) override {
        return ::operator new(_Bytes,std::align_val_t(_Align));
    }                                                                                                                                             
    virtual void do_deallocate(void* _Ptr, size_t _Bytes, size_t _Align){
        ::operator delete(_Ptr,_Bytes, std::align_val_t(_Align));
    };
    virtual bool do_is_equal(const memory_resource& _That) const noexcept {
        return this==&_That;
    };
};
int main() {
    std::pmr::unsynchronized_pool_resource ms1; //Allocateur de pool non thread-safe
    std::pmr::synchronized_pool_resource ms2;   //Allocateur de pool synchronisé
    CustomMemoryResource custom_memory_source;  //Allocateur personnalisé
    char buffer[20];
    std::pmr::monotonic_buffer_resource mbr(std::data(buffer),std::size(buffer),&custom_memory_source);   //Allocateur de buffer monotone, allouant de la mémoire depuis le buffer jusqu'à ce que mbr.release() soit appelé. Si le buffer est dépassé, l'allocateur parent est utilisé.
    {
        std::pmr::vector<std::pmr::string> vec{ &mbr };
        vec.push_back("Hello World");
        vec.push_back("One Two Three");
    }   //La mémoire de vec n'est pas libérée
    mbr.release();  //La mémoire de mbr est libérée à ce moment
}
```

À partir du code ci-dessus, on voit que **MemoryResouce** résout parfaitement les problèmes de **allocator**. Nous n'avons qu'à utiliser les conteneurs du namespace `std::pmr`.

Comment fait-il cela ?

Prenons `std::pmr::vector` comme exemple et trouvons sa définition :

```C++
namespace pmr {
    template <class _Ty>
    using vector = std::vector<_Ty, polymorphic_allocator<_Ty>>;
} // namespace pmr
```

Très simple, c'est juste un `std::vector` utilisant `polymorphic_allocator`. En trouvant sa définition, on peut voir le code suivant :

```C++
template <class _Ty>
class polymorphic_allocator {
public:
    //...
    _NODISCARD __declspec(allocator) _Ty* allocate(_CRT_GUARDOVERFLOW const size_t _Count) {
        // Obtenir de l'espace pour _Count objets de type _Ty depuis _Resource
        void* const _Vp = _Resource->allocate(_Get_size_of_n<sizeof(_Ty)>(_Count), alignof(_Ty));
        return static_cast<_Ty*>(_Vp);
    }

    void deallocate(_Ty* const _Ptr, const size_t _Count) noexcept /* strengthened */ {
        // Retourner de l'espace pour _Count objets de type _Ty à _Resource
        // Pas besoin de vérifier que size_t peut représenter la taille de _Ty[_Count].
        _Resource->deallocate(_Ptr, _Count * sizeof(_Ty), alignof(_Ty));
        
private:
    memory_resource* _Resource = _STD pmr::get_default_resource();    
};
```

Il est facile de voir qu'il ne fait que appeler la méthode de `memory_resource` sur l'interface de l'Allocator original.
