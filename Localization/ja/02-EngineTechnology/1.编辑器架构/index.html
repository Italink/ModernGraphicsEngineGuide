    エディタアーキテクチャ¶

    筆者が近年の開発で積み重ねたコードの大部分はエンジンエディタに費やされてきました。ここではいくつかの心得を羅列し、参考にしていただければと思います。記事では以下の側面からエディタの設計をどのように行うかを分析します：

    • デザインの美感
    • ユーザーエクスペリエンス
    • リフレクションに基づくエディタアーキテクチャ
    • パフォーマンス最適化

    デザインの美感¶

    デザインの美感は大多数の開発者が欠けている要素です。彼らはコードに非常に多くの時間と労力を費やすため、美しいインターフェースを作成する方法を知恵を絞って考える人は少ないです。

    もちろん、彼らはデザインを理解する頭脳を持っていないかもしれませんが、美しいものを鑑賞する目は持っています。適切な参考があれば、開発者はすぐに対応する効果を再現できます。

    大多数のソフトウェア開発チームには専門のUIデザイナーがいます。彼らは主にUIの以下の点に注目します：

    • タイポグラフィ
    • カラートーン
    • アイコン
    • レイアウト

    筆者が使用したいくつかのソフトウェアシステムの中には、上記の点を確かに考慮し、美しいインターフェース効果を作成しているものもありますが、多くの場合 コンポーネント化設計 を無視しており、その結果以下の問題が発生します：

    • ユーザーがソフトウェアの使用ルールを迅速に理解できず、大きな認知負担が生じる。
    • ソフトウェアコードの組織構造が破壊される。コンポーネント化設計が優れたUIは、インターフェースからコードの階層構造を読み取ることができますが、規則が混乱したインターフェースは、そのコードも大抵混乱しています。

    Unreal Engineを例に挙げると、そのコンポーネント化設計は非常に直感的です：

    ユーザーはインターフェース上の各コンポーネント要素の責任を理解し掌握するだけで、多くの場合チュートリアルやドキュメントを借りることなく、類推して操作を行うことができます。

    UIデザイナーは主にUI効果に注力するため、コードアーキテクチャに適したコンポーネント化設計を作成することは彼らにとって比較的困難です。したがって、この方面の内容は開発者が考え、討論し、誘導し、"ノー"と言うことを学ぶ必要があります。

    UIデザインに関するいくつかの概念とスタイルについては、ここにより詳細な参考資料があります：

    • All Time Design - UI Style Guide

    ユーザーエクスペリエンス¶

    ユーザーエクスペリエンスは主に以下の点を中心に展開されます：

    • ユーザーの認知負担を軽減する：インターフェースレイアウト、ラベル命名、操作において常識と規範に従う
    • 元に戻す（Undo）、やり直す（Redo）をサポートする：誤操作を迅速に修正できるようにする
    • 適切な操作フィードバック：操作を実行する際、ログ、ダイアログボックス、プログレスバー、通知バブル、ステータスバーなどを使用して、操作の実行状態をユーザーに通知する
    • タイムリーな状態バックアップまたは保存：予期せぬクラッシュによる大量の作業データの損失を回避する
    • 設定可能な操作方式：ユーザーがショートカットキー、レイアウト方式、操作スタイルなどをカスタマイズできるようにする

    ユーザーの認知負担を軽減するには、ここに非常に完備したドキュメントがあります：

    • O3DE - Component Card UX Pattern
    • O3DE - Component Card Error Handling

    元に戻す・やり直すについては、コード設計の問題です。通常、デザインパターンレベルでメモパターンとコマンドパターンを使用して元に戻す・やり直す機能を実現します。Qtではこれに対応する構造が QUndoCommand と QUndoStack です。其中 QUndoCommand の核心定義は以下の通りです：

    class QUndoCommand
{
    virtual void undo();
    virtual void redo();
    virtual int id() const;
    virtual bool mergeWith(const QUndoCommand *other);
}；

    使用時には、QUndoCommandを派生させ、undoとredoの操作行為を実現するために関数をオーバーライドし、その後具体的なCommandをUndoStackにプッシュします。

    ここに簡単なコード例があります：

    #include <QUndoCommand>
#include <QUndoStack>
#include <QDebug>

class QAssignCommand : public QUndoCommand {
public:
    QAssignCommand(int* ptr, int dstValue)
        : mValuePtr(ptr)
        , mSrcValue(*ptr)
        , mDstValue(dstValue) {}
protected:
    virtual void undo() override {
        *mValuePtr = mSrcValue;
    }
    virtual void redo() override {
        *mValuePtr = mDstValue;
    }
private:
    int* mValuePtr = nullptr;
    int mSrcValue;
    int mDstValue;
};

int main(int argc, char** argv) {
    QUndoStack stack;
    int value = 0;
    stack.push(new QAssignCommand(&value, 1));
    qDebug() << value;      //1

    stack.undo();
    qDebug() << value;      //0

    stack.redo();
    qDebug() << value;      //1

    stack.beginMacro("Merge");  
    stack.push(new QAssignCommand(&value, 2));
    stack.push(new QAssignCommand(&value, 3));
    stack.endMacro();
    qDebug() << value;      //3

    stack.undo();
    qDebug() << value;      //1

    return 0;
}

    その実現アイデアは比較的簡単ですが、処理が難しい点もあります：

    • Command内の操作対象が他の場所で破棄されたが、Commandが依然としてStackに存在する場合、この時元に戻す・やり直すを実行すると、プログラムのクラッシュを引き起こす可能性がある

    このような問題に対して、主に以下のいくつかの方案で解決できます：

    • 元に戻す・やり直す操作の指令が操作対象のライフサイクルを完全にカバーしていないのかを検討する
    • Commandに有効性検証を追加する
    • シリアライゼーションを使用してオブジェクトの保存と再構築を行う

    Unreal Engineでは、オブジェクトシステムに基づく元に戻す・やり直すメカニズム —— Transactional が提供されています。

    RF_Transactional 識別子を持つ任意のUObjectインスタンスについては、以下のコードを使用して元に戻す・やり直すを実現できます：

    GEditor->BeginTransaction(FText::FromString("Assign Value"));   //トランザクション開始

MyObject->Modify();                                             //初期状態を保存
MyObject->ValueProperty = 123;                                  //属性を修改

GEditor->EndTransaction();                                      //トランザクション終了

    UObjectのGCがオブジェクトの遅延回収を可能にするため、操作対象のライフサイクルを考慮する必要がなくなります。その実現原理については、以下を参照してください：

    • CSDN - UE4 编辑器(UObject)的Undo撤回系统Transactional

    状態保存については、プログラムが突然クラッシュしたり、コンピュータが突然シャットダウンしたりする状況に遭遇したことがあると思います。この時作業データがタイムリーに保存されていないと、数時間の作業成果が水の泡になってしまいます。この時、プログラムが保存またはバックアップの補助手段を提供していれば、意外が発生した時に自分を救うことができます。

    このような手段は一般的に自動保存を指します。ユーザーが手動でクリックして作業データを保存する以外に、特定のタイミングで自動的に保存またはバックアップすることもできます。例えば：

    • ユーザーが某个界面を閉じる時に保存する
    • 定期的に自動保存する
    • プログラムがクラッシュした時に保存する（SetUnhandledExceptionFilter関数を使用してプログラムクラッシュ時のシステムコールバックを設定できる）

    上記の手段は作業データの損失リスクを可能な限り減らすことができます。もちろん、保存性能の損耗が少ないデータ（例えば小型の設定ファイル）については、操作実行後すぐに保存することができます。

    Meta思维¶

    Meta思维は現代工業ソフトウェア開発プロセスにおいて極めて大きな利便性を提供します。一労永逸のコード拡張方式を提供できます。

    Meta思维に関する連想語には：微分、高次次元、神の視点、...があります。

    詳細は： [ 知乎 ] bus waiter- 谈meta を参照してください。

    コードを書くことを家を建てることに例えると、私たちが考えるのは家をどのように建てるかですが、Metaレベルでは自動的に家を建てる機械を構築する方法を考えます。Meta思维により、工程問題を別の問題に変換します。難易度は上昇しますが、方法が適切であれば比類のない利益をもたらすことができます。

    筆者はいくつかの自研エンジンとソフトウェアに接触しました。自研エンジンエディタ に関する話題になると、基本的に批判ばかりです。

    その原因は外乎以下の点です：

    • インターフェースが簡素すぎる
    • ユーザーエクスペリエンスが悪い

    大多数の開発者の考えは：

    • "できないわけではないが、よくするには多くの時間がかかり、面倒です。時間を浪費する必要はなく、使えれば良いと思っています。"

    もちろん、このような考えは一些の小さなツールにとっては問題ありませんが、高頻度で使用されるツールに対して依然としてこのような態度で対応すると、使用者にとっては苦痛な拷問になります。

    筆者はQtで数十万行のコードを積み重ねましたが、Unreal Engineでは数万行のコードしか使用していませんが、より多くの完備した機能を実現しています。また、Unreal Engineではインターフェーススタイルとユーザーエクスペリエンスの需求を非常に容易に満たすことができます。これは主にUnreal Engineの インフラストラクチャ によるものです。

    ゲームエンジンでは、Meta理念に基づくアーキテクチャが到処に見られます。その中で最も有用で強力なのは間違いなく —— リフレクションに基づくエディタアーキテクチャ です。

    大家は一些のパラメータ調整パネルを見たことがあると思います。例えば：

    コードレベルでは、これらの設定可能なパラメータは通常具体的なデータ構造に対応します。以下のようになる可能性があります：

    struct Options{
    bool            Option0;
    int             Option1;
    string          Option2;
    vector<string>  Option3;
};

    大多数の開発者はデータ構造Optionsに対して手動でコードを記述して編集パネルを作成しますが、Metaレベルではこのような複雑な構造をさらに分解します。C++の基本型は有限であり、開発者が作成する型はそれらの基本型を一定の階層で組織化したものに過ぎないため、メンバー変数の型に基づいてコントロールを作成し、Optionsの構造に基づいてコントロールのレイアウトを組織化することが完全に可能です。簡単に言えば、型に基づくコントロール、構造に基づくパネル です。

    実行時にデータ構造の関連情報を取得する必要があるため、リフレクション に依存する必要があります。此外、データ構造の組織は往往にしてツリー状であるため、GUIフレームワークのTreeViewコントロールを使用してコントロールパネルを組織化します。

    ここに簡単な擬似コードがあります：

    class Options: public Object{       //データ構造、Objectはオブジェクトシステムの基類
    OBJECT_ENTRY()                  //OBJECT_ENTRYはリフレクションシステムの入口マクロ

    PROPERTY()  bool            Option0;    //PROPERTYマクロを使用して属性をリフレクション
    PROPERTY()  int             Option1;
    PROPERTY()  string          Option2;
    PROPERTY()  vector<string>  Option3;
};

class DetailView: public TreeView{
public:
    void setObject(Object* object){                                         
        clearTreeView();
        for(auto metaProperty: object->metaObject()){                       //MetaObjectに基づいてオブジェクトの所有属性を遍历
            Widget* widget = generateWidgetForType(metaProperty.type());    //型に基づいてコントロールを生成
            widget->bind(Object,metaProperty);                              //コントロールをリフレクションされた属性にバインド
            this->addRow(widget);                                           //コントロールをTreeViewに追加
        }
    }
};

    型については、以下の分類に基づいて归纳します：

    • 基本型：論理、数値、列挙、文字列
    • 複合型：クラス、構造体
    • 容器型：
      • 連続（sequential）容器：list、array、vector、set、queue...
      • 組合（associative）容器：map、hashmap...

    このような分類により、開発者は基本型に対してコントロールを制作し、複合型に対して属性パネルのレイアウトを組織化するだけで済みます。容器型の編集パネルは往往にして内部要素の型に基づいて自動的に生成および組合わされます。此外、開発者が自由に基本属性を拡張し、オブジェクトのパネルとレイアウトを覆盖できるように、一般的に以下の2つの構造を提供します：

    class IDetailCustomization{
public:
    virtual void CustomizeDetails(DetailsBuilder* builder) = 0;     //オブジェクトの調整パネルをカスタマイズするために使用
};

class IPropertyTypeCustomization{
public:
    virtual void CustomizeHeader(RowBuilder* builder) = 0;      //属性型のHeader Rowをカスタマイズするために使用
    virtual void CustomizeChildren(DetailsBuilder* builder) {}  //该属性型のChild Rowを附加するために使用
};

    属性を管理するために、IPropertyHandleを派生させます。主に以下の用途で使用されます：

    • 多態を使用して階層関係の組織を処理する。
    • 属性の設定と取得の唯一の入口として、元に戻す・やり直す、変動通知、エディタ同期などの関連機能を追加する。
    class IPropertyHandle{
    void SetValue(Variant var);
    Variant GetValue();
    virtual Widget* GenerateNameWidget();       //属性の名称コントロールを生成
    virtual Widget* GenerateValueWidget();      //属性の値コントロールを生成
    virtual void GenerateChildrenRow(DetailsBuilder* builder);  //属性の子行を生成
};

    上記の構造のサポートがあれば、DetailsViewの作成過程は簡単に以下のように看作すことができます：

    map<typeid,IDetailCustomization*> GloabalDetailCustomizationMap;
map<typeid,IPropertyTypeCustomization*> GloabalPropertyTypeCustomizationMap;

class DetailView: public TreeView{
public:
    void setObject(Object* object){                                         
        clearTreeView();

        auto DetailCustomization = GloabalDetailCustomizationMap[object->metaObject()->type()]; 
        DetailsBuilder builder(this);
        DetailCustomization->CustomizeDetails(&builder);
        /* オブジェクト型に対応するDetailCustomizationを取得し、CustomizeDetailsを呼び出すと所有のPropertyを遍历し、
        IPropertyHandleを创建します。IPropertyHandleは又属性型に対応するIPropertyTypeCustomizationに基づいて、
        具体的な属性調整コントロールを创建します。
        */
    }
};

    実際のアーキテクチャは上記の構造より複雑ですが、核心アイデアを掌握すれば実現は困難ではありません。ここに簡単なバージョンのQt実現（Unreal EngineのDetailsViewを参考）があります：

    • コード：https://github.com/Italink/QEngineUtilities/tree/main/Source/Editor/Source/Public/DetailView
    • 示例工程：https://github.com/Italink/QEngineUtilities/tree/main/Samples/DetailViewExample

    パフォーマンス最適化¶

    コンピュータの計算資源は始终にして有限です。ゲームエンジンでは、パフォーマンス消耗の大头は毫无疑问Gameです。因此、エディタのパフォーマンス消耗を可能な限り降低してGame実行への影響を減らす必要があります。

    一般的に、以下の手段を通じてエディタのパフォーマンスを最適化できます（ゲーム内UIにも適用されます）：

    • 美观を追求するために高消耗のインターフェース効果を使用しない ：

    • 可能な限りインターフェースアニメーションとフィルタ（模糊、阴影、拟态、毛玻璃、投影变换...）を使用しない

    • 高解像度の画像リソースを使用しない

    • 静态のUIについては、可能な限り既に制作された画像を使用するか、事前にRT（Bitmap）を绘制する。GUIフレームワークで毎フレームリアルタイムに绘制するのではなく、例えばカラーピッカーのカラーパレット：

    • インターフェースの再绘制タイミングを管理する ：某个操作Aがインターフェース更新を触发する場合がありますが、一帧で複数回操作Aを実行することが往往にしてあります。很显然一帧で複数回インターフェースを再绘制する必要はないため、往往にして操作A中で直接UIを更新するのではなく、标识を设置し、UIのTick事件中で标识に基づいてインターフェースを再绘制します。以下のようになります（擬似コード）：

    class MyWidget : public Widget{
private:
    bool bNeedRepaint = false;
public:
    void setFont(...){                //フォントを设置し、インターフェース再绘制を触发
      bNeedRepaint = true;
    }

    void tick() override{         //UIのTick事件をオーバーライドし、Tick時にUIを再绘制する必要があるかを检查
        if(bNeedRepaint){
            repaintUI();          //UIの再绘制インターフェース
            bNeedRepaint = false;
        }
    }  
};

    • 离屏绘制缓存と局部刷新を使用する ：上帧画像の复用性が非常に高いUIについては、先にUIを一张のRT（Bitmap）に绘制し、毎フレーム必要に応じて部分区域のUIを更新するだけで済みます。这种做法は图表、画布相关のUIで较为常见です。

    • 主线程中で高消耗の逻辑操作を执行してUIを阻塞することを避免する ：UIの処理は往往にして主线程に位于します。主线程の逻辑操作の执行時間が比较的长いと、UIの阻塞を导致します。この問題を解决する主な方法は2つあります：

    • 逻辑操作中にUIシステムの更新操作を插入してUIの刷新を强制する。

    • 逻辑操作を异步线程に移して执行し、逻辑执行が完了した後、主线程でUI相关の更新を执行する。
