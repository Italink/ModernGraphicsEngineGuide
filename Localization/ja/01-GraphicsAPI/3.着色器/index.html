    シェーダー基礎¶

    前節では主にQRhiを使用して基本的なグラフィックスレンダリングパイプラインを構築する方法について説明しました。おそらく気づかないかもしれませんが、実は既にGPUを使って任意のグラフィックスを描画できるようになっています！必要なのは頂点データを埋めるだけです～

    そうなると、後の内容は学ぶ必要がないのかと思うかもしれません。

    現代のグラフィックスAPIでは、単に何かを実現するだけでなく、実現できることをより多くし、不可能なことを可能にすることを追求しています。

    そのため、グラフィックスAPIシリーズの次の記事では、主にハードウェア特性に適合した操作を使用してグラフィックスの描画を高速化する方法を中心に説明します。

    歴史¶

    GPUの登場は、当時のグラフィックスレンダリングシステムに信頼できるハードウェアアクセラレーションデバイスを提供するためでした。そのため、GPUの発展初期には、グラフィックスAPIはCPU上の固定レンダリングフローをGPUに移行するための単純で汎用的なインターフェースを提供することを目的としていました。

    早期のOpenGLに接触したことがある方は、次のようなコードに馴染みがあるかもしれません：

    void init(void)
{
    glMatrixMode(GL_MODELVIEW);                             //モデルビュー行列を単位行列に設定
    glLoadIdentity();
}
void display(void)
{
    glClear(GL_COLOR_BUFFER_BIT);                           //画面をクリア
    glBegin(GL_TRIANGLES);                                  //三角形プリミティブの書き込み開始
    glColor3f(1.0, 0.0, 0.0); glVertex3f(-1.0, -1.0, 0.0);  //頂点データ0を書き込み
    glColor3f(0.0, 1.0, 0.0); glVertex3f( 0.0,  1.0, 0.0);  //頂点データ1を書き込み
    glColor3f(0.0, 0.0, 1.0); glVertex3f( 1.0, -1.0, 0.0);  //頂点データ2を書き込み
    glEnd();                                                //終了    
    glutSwapBuffers();                                      //スワップチェーンを更新
}
void reshape(int w, int h)
{
    glViewport(0, 0, (GLsizei) w, (GLsizei) h);             //ビューポートサイズを調整
    glMatrixMode(GL_PROJECTION);                            //クリッピング行列を単位行列に設定
    glLoadIdentity();
}

    この段階のグラフィックスAPIでは、レンダリングパイプラインの各フローの処理ロジックは固定されており、開発者は頂点データ、テクスチャ、行列、光源などの情報をグラフィックスAPIに提供するだけで、GPUアクセラレーションによって3Dシーンのレンダリングを完了できました。

    グラフィックスAPIは、少数のパラメータと識別子を通じてグラフィックスレンダリングパイプライン内のフローを設定することを許可していましたが、グラフィックス学の急速な発展に伴い、様々なレンダリング理論が次々と登場しました。明らかに、公式が提供するインターフェースは学術界と産業界の発展に追いつけなくなり、さらに開発者と研究者の更なる探索を制約するようになりました。そのため、**プログラマブルパイプライン（Programmable Pipeline）**が誕生しました。

    現在では、旧来の使用方法を**固定機能パイプライン（Fixed Function Pipeline）**と呼んでいます。

    プログラマブルパイプラインでは、開発者が**シェーダー（Shader）**を記述してパイプラインの特定の段階の処理ロジックをカスタマイズすることができます。

    各グラフィックスAPIには独自の**シェーダー言語（Shader Language）**があります。例えば：

    • OpenGL、VulkanはGLSLを使用
    • Direct3DはHLSLを使用
    • MetalはMSLを使用

    これらのシェーダー言語の全体的な作業フローはほぼ同じですが、主な違いは自身のAPIスタイルに合わせた（独自性のある）構文です。

    次は、機能が同じフラグメントシェーダー（Fragment Shader）を異なるシェーダー言語で実装した例です：

    早期のゲーム開発会社は、多くの場合、一種類のグラフィックスAPIを自身のゲームエンジンのレンダリングバックエンドとして使用していました。しかし、各操作プラットフォームのユーザー数が次第に増加するにつれ、クロスプラットフォームも大手メーカーの注意を引くようになりました。毕竟、多くのプラットフォームをサポートすることは、多くの市場を意味するからです。

    そのため、現在のほとんどのゲームエンジンはこれらのグラフィックスAPIを統一されたインターフェースにカプセル化し、異なるプラットフォームで切り替えてより良いグラフィックス性能を追求しています。このインターフェースを一般的に**RHI（Rendering Hardware Interface）**と呼びます。

    カプセル化の過程では、グラフィックスAPIの命令とリソースに注意するだけでなく、クロスプラットフォームのシェーダーも非常に頭痛の種です。

    現在、ほとんどのエンジンは一種類のシェーダー言語で開発を行い、他のグラフィックスAPIで使用可能なシェーダー言語に変換しています。例えば：

    • UEはHLSLで開発を行い、オープンソースライブラリGlslangとSpirv-Crossを利用してクロスプラットフォームのシェーダー変換を実現
    • Unity、O3DE、Godot、Bgfxなどのエンジンは新しいシェーダー言語をカスタマイズして開発を行い、組み込みコンパイラとオープンソースライブラリを組み合わせてクロスプラットフォームのシェーダー変換を実現

    関連する読み物は以下の通りです：

    • [知乎-unwind] クロスプラットフォームエンジンShaderコンパイルフロー分析

    • [知乎-ウェブゲーム雷火事業群] ゲームシェーダー（Shader）基礎紹介

    シェーダー変換¶

    QRhiのクロスプラットフォームシェーダー方案はUEと似ていますが、QRhiはHLSLではなくVulkanスタイルのGLSLで開発を行います。その変換フローは以下の通りです：

    前節では、次のようなコードを使用してシェーダーを作成しました：

    QShader vs = mRhi->newShaderFromCode(QShader::VertexStage, R"(#version 440
    layout(location = 0) in vec2 position;      //ここは上記のinputLayoutと対応する必要がある
    layout(location = 1) in vec4 color;

    layout (location = 0) out vec4 vColor;      //出力変数、ここのlocationはoutであり、inではない

    out gl_PerVertex {                          //Vulkan GLSLで固定された定義
        vec4 gl_Position;                       
    };

    void main(){
        gl_Position = vec4(position,0.0f,1.0f); //入力されたpositionに基づいて、実際の頂点出力を設定
        vColor = color;                         //入力されたcolorをfragment shaderに渡す
    }
)");
Q_ASSERT(vs.isValid());

QShader fs = mRhi->newShaderFromCode(QShader::FragmentStage, R"(#version 440
    layout (location = 0) in vec4 vColor;       //前の段階のoutがこの段階のinになる
    layout (location = 0) out vec4 fragColor;   //フラグメントシェーダーの出力、locationが0はrender targetの最初のカラーアタッチメントに出力することを意味する
    void main(){
        fragColor = vColor;
    }
)");
Q_ASSERT(fs.isValid());

    ここでのnewShaderFromCode()はQRhiが提供する原生関数ではなく、筆者が**QtShaderTools**モジュール内のインターフェースを呼び出して簡単にカプセル化したものです。その真のロジックは以下の通りです：

    #include "private/qshaderbaker_p.h"

QShader newShaderFromCode(QShader::Stage stage, const char* code) {
    QShaderBaker baker;                     //シェーダーベイカー
    baker.setGeneratedShaderVariants({ QShader::StandardShader });
    baker.setGeneratedShaders({
        QShaderBaker::GeneratedShader{QShader::Source::SpirvShader,QShaderVersion(100)},
        QShaderBaker::GeneratedShader{QShader::Source::GlslShader,QShaderVersion(430)},
        QShaderBaker::GeneratedShader{QShader::Source::MslShader,QShaderVersion(12)},
        QShaderBaker::GeneratedShader{QShader::Source::HlslShader,QShaderVersion(60)},
    });
    baker.setSourceString(code, stage);     //GLSLソースコードをアセンブル
    QShader shader = baker.bake();          //ベイクを実行し、各グラフィックスAPIのシェーダーコードに変換

    if (!shader.isValid()) {                //コンパイルエラーを出力
        QStringList codelist = QString(code).split('\n');
        for (int i = 0; i < codelist.size(); i++) {
            qWarning() << i + 1 << codelist[i].toLocal8Bit().data();
        }
        qWarning(baker.errorMessage().toLocal8Bit());
    }
    return shader;
}

    QShaderBakerは**Qt Shader Tools**のプライベートモジュールから来ています。CMakeでビルドする場合、自身のビルドターゲットにQt::ShaderToolsPrivateをリンクする必要があります。これを使用すると、VulkanスタイルのGLSLをQShaderオブジェクト（各バージョンのグラフィックスAPIのシェーダーコードを含む）にコンパイルできます。これは**実行時にシェーダーコードを変換**する方法です。

    さらに、Qtが提供する**qsb**コマンドラインツールを利用して**オフラインでシェーダーコードを変換**することもできます。このツールは次のディレクトリにあります：

    ウィンドウのアドレスバーにcmdを入力してEnterキーを押すと、コマンドラインウィンドウが開きます。そこでqsb.exe -hを入力すると、このコマンドラインツールの使用説明を見ることができます：

    例えば、qsb.exe -c color.frag -o color.frag.qsb --glsl 430 --msl 12 --hlsl 60というコマンドを使用すると、現在のディレクトリのcolor.fragファイルを変換してcolor.frag.qsbファイルを生成できます。このファイルには430バージョンのGLSL、12バージョンのMSL、60バージョンのHLSLが含まれています。

    Qtでは、次の方法で*.qsbファイルを使用できます：

    QShader newShaderFromQSBFile(const char* filename) {
    QFile file(filename);
    if (file.open(QIODevice::ReadOnly))
        return QShader::fromSerialized(file.readAll());
    return QShader();
}

    CMakeでは、さらに便利な機能が提供されています：特定のファイルが変更された場合に、いくつかの操作を実行することができます。

    この機能を利用して、**コンパイル時にシェーダーを変換**することもできます。

    この機能はCMake指令add_custom_commandを通じて実現されます。CMakeに次の関数を追加してShaderを追加することができます：

    function(add_shader TARGET_NAME SHADER_PATH)
    set(OUTPUT_SHADER_PATH ${SHADER_PATH}.qsb)  #出力ファイルパス
    add_custom_command(
        OUTPUT ${OUTPUT_SHADER_PATH}        #出力ファイルを指定
        COMMAND qsb.exe -c ${SHADER_PATH} -o ${OUTPUT_SHADER_PATH} --glsl 430 --msl 12 --hlsl 60    #QSBツールを実行
        MAIN_DEPENDENCY ${SHADER_PATH}      #依存ファイルを指定、即ちこのファイルが変更された場合、上記のコマンドをトリガー
    )  
    set_property(TARGET ${TARGET_NAME} APPEND PROPERTY SOURCES ${OUTPUT_SHADER_PATH})               #出力ファイルをビルドターゲットに追加する必要があり、そうしてこそCustomCommandがトリガーされる
    source_group("Shader Files" FILES ${SHADER_PATH} ${OUTPUT_SHADER_PATH})                         #シェーダーファイルを分類
endfunction()

    これにより、毎回TARGET_NAMEをビルドするとき、CMakeはSHADER_PATHが変更されたかどうかを検出します。変更された場合は、カスタム指令を呼び出します。ここではQSBツールを呼び出して*.qsbファイルを生成し、エラー情報もIDEのエラーパネルに表示されます：

    シェーダーの記述¶

    基本タイプ¶

    GLSLの一般的な基本タイプは以下の通りです：

    Type Meaning
    void 値を返さない関数用
    bool 条件型、trueまたはfalseの値を取る
    int 符号付き整数
    uint 符号なし整数
    float 単精度浮動小数点スカラー
    double 倍精度浮動小数点スカラー
    vec2 2成分の単精度浮動小数点ベクトル
    vec3 3成分の単精度浮動小数点ベクトル
    vec4 4成分の単精度浮動小数点ベクトル
    mat2 2×2の単精度浮動小数点行列
    mat3 3×3の単精度浮動小数点行列
    mat4 4×4の単精度浮動小数点行列
    sampler1D texture1D image1D 1Dテクスチャにアクセスするためのハンドル
    sampler1DArray texture1DArray image1DArray 1D配列テクスチャにアクセスするためのハンドル
    sampler2D texture2D image2D 2Dテクスチャにアクセスするためのハンドル
    sampler2DArray texture2DArray image2DArray 2D配列テクスチャにアクセスするためのハンドル
    sampler2DRect texture2DRect image2DRect 矩形テクスチャにアクセスするためのハンドル
    sampler3D texture3D image3D 3Dテクスチャにアクセスするためのハンドル
    samplerCube textureCube imageCube キューブマップテクスチャにアクセスするためのハンドル
    samplerCubeArray textureCubeArray imageCubeArray キューブマップ配列テクスチャにアクセスするためのハンドル
    samplerBuffer textureBuffer imageBuffer バッファテクスチャにアクセスするためのハンドル

    完全なタイプリストは以下を参照してください：

    • https://www.khronos.org/registry/OpenGL/specs/gl/GLSLangSpec.4.60.html#basic-types

    ここで主に注意が必要なのは**vec（ベクトル）**と**mat（行列）**です。ここではそれらの幾何学的意味については議論しません。これらに不慣れな場合は、『3D数学基礎：グラフィックスとゲーム開発』を読むことを推奨します。

    ベクトル¶

    数学において、ベクトル（ユークリッドベクトル、幾何学的ベクトル、ベクトルとも呼ばれる）は大きさ（magnitude）と方向を持つ量を指します。コンピュータにおいては、ベクトルは単に連続したいくつかの数字です。GLSLは2次元（vec2）、3次元（vec3）、4次元（vec4）のベクトルをサポートしています。

    ベクトルの基本的な使用方法について、vec4を例に説明します：

    vec4 mVector = vec4(1,2,3,4);
float x   = mVector.x;      //1
vec2  xy  = mVector.xy;     //[1,2]
vec3  xzy = mVector.xzy;    //[1,3,2]
vec2  xxw = mVector.xxw;    //[1,1,4]
vec4  newVecotr = vec4(mVector.xx,-1,-2);   //[1,1,-1,-2]

    ここではxyzwを使用してベクトルの成分にアクセスしています。GLSLは他のキーワードセットrgbaとpqstもサポートしています。どのキーワードセットを使用するかは、使用シーンと個人の好みによります。

    GLSLは当然、ベクトルの加算、減算、乗算、除算、ドット積などもサポートしています。

    行列¶

    数学において、行列（Matrix）は長方形の配列に並べられた複素数または実数の集合です。コンピュータにおいても、同様に単に連続した数字の集まりです。GLSLは最大4x4の行列サイズをサポートしています（mat4x4、ここではxは乗算記号を表す）。正方行列であるため、mat4と略記することができます。

    特に注意が必要なのは、GLSLが行列を列優先で格納することです：

    mat3 mMatrix = mat4(0,1,2,
                    3,4,5,
                    6,7,8);

    行優先で格納する場合、その表現は次のようになります：

    {
  0,3,6,
  1,4,7,
  2,5,8
}

    格納方式の違いは、行列のアクセス方式に影響するだけでなく、より重要なのは行列の演算順序に影響することです。次の図は、異なる格納方式で3次元行列と3次元ベクトルを乗算した結果がどのようなタイプになるかを示しています：

    GLSLでは、通常、ベクトルを変換するために行列を使用するため、演算は右から左に行うのが一般的です。次のように示されます：

    vec3 pos    = vec3(0.5,1.0,0);
mat3 model  = mat3(...);
vec3 newPos = mat * pos;

    さらに、行列とベクトルの演算を逆にするだけでなく、行列の内部演算の一部も逆にする必要があることに注意する必要があります。例えば、クライアントでQMatrix4x4を使用してグラフィックスを先に回転させ、次に平行移動させる場合、次のように使用する必要があります：

    QMatrix4x4 mat4;
mat4.translate(0,1);                    //先に実行する操作を後で呼び出す
mat4.rotate(60,QVector3D(0,0,1));       //ここでは先に回転してから平行移動する

    さらに注意が必要なのは、QMatrix4x4のメモリサイズは16 * sizeof(float)ではなく、4バイトの識別子ビットも含んでいることです。QMatrix4x4をGPUにアップロードする必要がある場合は、mat.toGenericMatrix<4,4>()を呼び出して**QGenericMatrix**タイプに変換してください。

    修飾子¶

    GLSLでは、変数の関連情報を記述するためにいくつかの修飾子を使用します。常見的な修飾子タイプは以下の通りです：

    • ストレージ修飾子：変数のストレージ位置を記述
    • レイアウト修飾子：変数のレイアウトを記述

    常見的なストレージ修飾子は以下の通りです：

    Storage Qualifier Meaning
    なし 読み書き可能なローカル変数
    const 定数
    in この変数が入力変数であり、前の段階の出力から来ることを示す
    out この変数が出力変数であり、次の段階の入力となることを示す
    uniform この変数がUniformデータであることを示す

    in、out、uniformの間の違いに注意する必要があります：

    レイアウト修飾子の形式は以下の通りです：

    • layout( layout-qualifier-id-list )

    ここでlayout-qualifier-id-listは特徴の配列であり、その要素は識別子であっても、キーバリューペア（Key-Value）であってもよい。他の常見的なレイアウト修飾子の特徴は以下の通りです：

    レイアウト修飾子の特徴 説明
    binding = uniformデータが記述子セットバインディングレイアウトのindexに対応するために使用
    location = すべての入力出力変数の位置を確定するために使用。シェーダーの前の段階の入力変数と後の段階の出力変数は、変数名ではなくlocationによって接続を確定する
    shared , packed , std140 , std430 Blockが採用する構造体内存アライメント方式を宣言するために使用
    local_size_x = , local_size_y = , local_size_z = 計算シェーダーにおいて、計算ユニットのサイズを示す
    max_vertices = ジオメトリシェーダーにおいて、最大の頂点数を定義する
    rgba32f rgba16f rg32f rg16f r11f_g11f_b10f r32f r16f rgba16 rgb10_a2 rgba8 rg16 rg8 r16 r8 rgba16_snorm rgba8_snorm rg16_snorm rg8_snorm r16_snorm r8_snorm rgba32i rgba16i rgba8i rg32i rg16i rg8i r32i r16i r8i rgba32ui rgba16ui rgb10_a2ui rgba8ui rg32ui rg16ui rg8ui r32ui r16ui r8ui 計算シェーダーにおいて、Image変数の画像フォーマットを示す

    VulkanスタイルのGLSLでは、次の点に注意する必要があります：

    • 任意のinまたはout変数はlayout(location = ${index})で修飾する必要があります。これは、この段階のin変数が前の段階の対応するout変数をLocation Indexによって探すためです
    • 頂点シェーダーの場合、そのin変数はLocation Indexによってパイプライン作成時の頂点入力レイアウトから探します
    • フラグメントシェーダーの場合、そのout変数はLocation Indexによってレンダーターゲットの対応するインデックスのカラーアタッチメントに出力されます
    • 任意のuniform変数はlayout(binding = ${index})で修飾する必要があります。Binding Indexはパイプラインで使用される記述子セットレイアウト（QRhiShaderResourceBindings）に対応する必要があります

    修飾子の完全なドキュメントは以下を参照してください：

    • https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.60.html#storage-qualifiers

    基礎段階¶

    完全なグラフィックスレンダリングパイプラインの実行フローは以下の通りです：

    • 赤色部分の**Vertex Shader**と**Fragment Shader**はグラフィックスレンダリングパイプラインの**必須項目**です

    • 黄色部分の**Tesselation Control Shader**、Tesselation Evaluation Shader、**Geometry Shader**はグラフィックスレンダリングパイプラインの**任意項目**です

    • 緑色部分の**Primitive Setup**、Clipping、**Rasterization**は**プログラマブルできない段階**ですが、グラフィックスAPIはそれらの動作を調整するためのいくつかのパラメータを提供しています

    シェーダーを記述するには、まずグラフィックスレンダリングパイプラインの各段階の仕事内容を理解する必要があります。ここでは主に頂点シェーダーとフラグメントシェーダーについて説明します。グラフィックスAPIには他の処理段階とパイプラインもありますが、早く展開すると読者に多くの認知負担を与えるため、興味がある場合は先に了解してみることができます。これらの内容も後の記事でさらに深く説明されます。

    頂点シェーダー（Vertex Shader）¶

    **頂点シェーダー（Vertex Shader）**の仕事は、入力された頂点データとUniformデータ（ある場合）に基づいて、現在の頂点の**組み込み出力変数**を記入し、有用なデータを次の段階に渡すことです。

    核心的な頂点シェーダーのテンプレートは以下の通りです：

    layout(location = 0) in vec2 position;      

out gl_PerVertex {                          
    vec4 gl_Position;
};

void main(){
    gl_Position = vec4(position,0.0f,1.0f); 
}

    解釈：

    • layout(location = 0)は、パイプライン作成時の頂点入力レイアウトのインデックス0の頂点属性に対応することを意味します
    • inは入力変数であることを意味します
    • vec2はこの変数のタイプが2次元ベクトルであることを示し、頂点入力レイアウトのフォーマット（Float2）に対応する必要があります
    • positionは入力変数の名前であり、任意の名前を使用できます
    • out gl_PerVertex { vec4 gl_Position; };は頂点シェーダーの固定出力定義です
    • gl_Position = vec4(position,0.0f,1.0f);は入力された頂点位置に基づいて、頂点シェーダーの実際の頂点データ出力を埋めることです

    注意が必要なのは、固定概念の影響を受けて、ここで必ずpositionを入力する必要があると思わないことです。実際には任意の頂点データを入力でき、頂点位置を含まなくても、頂点シェーダーでgl_PerVertex内のgl_Positionの値を確定するだけです。例えば次のように：

    layout(location = 0) in vec2 anyVertexData;

out gl_PerVertex {              
    vec4 gl_Position;
};

vec1 calcPosition(vec2 vertexData){
    // do something
    return position;
}

void main(){
    gl_Position = calcPosition(anyVertexData)
}

    この段階のデータを次の段階に渡したい場合は、outで修飾され且つレイアウト（layout）記述を持つ変数を定義するだけです：

    layout(location = 0) in vec2 position;      
layout(location = 0) out vec4 color;        //出力変数を定義、inとoutのlocationは分離されている

out gl_PerVertex {                          
    vec4 gl_Position;
};

void main(){
    gl_Position = vec4(position,0.0f,1.0f); 
    color = vec4(position.xy,0.0f,1.0f);
}

    パイプラインに頂点シェーダーのUniformデータがある場合、uniformで修飾され且つバインディング（binding）記述を持つ変数を定義するだけです：

    layout(location = 0) in vec2 position;      
layout(location = 0) out vec4 color;    

layout(binding = 0) uniform UniformBlock {  //ここのbinding=0はパイプライン作成時の記述子セットレイアウトバインディングの設定に対応する
    vec4 color;                             //UniformBlockはこのデータ構造ブロックの名前であり、任意の名前を使用できる
} ubo;


out gl_PerVertex {                          
    vec4 gl_Position;
};

void main(){
    gl_Position = vec4(position,0.0f,1.0f); 
    color = ubo.Color;                      //Uniformデータを通じて色を設定
}

    フラグメントシェーダー（Fragment Shader）¶

    **フラグメントシェーダー（Fragment Shader）**の仕事は、前の段階の入力データとUniformデータ（ある場合）に基づいて、レンダーターゲット（Render Target）のカラーアタッチメントに書き込むことです。

    核心的なフラグメントシェーダーのテンプレートは以下の通りです：

    layout(location = 0) out vec4 fragColor;    
void main(){
    fragColor = vec4(1,1,1,1);
}

    解釈の内容：

    • layout(location = 0) outは、このフラグメントがレンダーターゲットのインデックス0のカラーアタッチメントに出力されることを示します。レンダーターゲットは通常少なくとも1つのカラーアタッチメントを含み、スワップチェーンのレンダーターゲットには4チャンネルのカラーアタッチメントが1つだけあります。
    • vec4はカラーアタッチメントが4つのカラーチャンネルを持つことを意味し、例えばRGBA8888です。
    • fragColorは出力変数の名前であり、任意の名前を使用できます。
    • fragColor = vec4(1,1,1,1)は最終的なフラグメントが不透明な白色（R=1、G=1、B=1、A=1）であることを示します。

    フラグメントシェーダーも頂点シェーダーのようにUniform入力を追加できます。

    論理分岐¶

    開発者にとって、シェーダー言語を単に異なる構文のプログラミング言語と見なすことはできません。最も特殊な点はGPU上で実行されることであり、その組み込み関数の実装はすべてGPUハードウェア特性に基づいています。

    GPUは大量の計算ユニットを積み重ねて構成されているため、論理の実行に不向きな欠点も生まれました。

    GLSLを記述する際には、可能な限りGLSLに**分岐命令**が出現しないようにする必要があり、別の戦略から問題を考える必要があります：

    • まず明確にできること：シェーダーでreturnを呼び出しても、後の段階に影響を与えません。必要なパラメータが記入されていない場合は、デフォルト値が使用される可能性があります。
    • 論理分岐を実現したい主な目標は、一般的に一部の場合にAを出力し、別の一部の場合にBを出力し、他の場合に...を出力することです。

    GPUは数学演算に友好的であるため、論理条件から出力結果までの関数式を確定できれば、数値計算の方式で論理分岐を回避できます。ここでは重要な関数が関係します：

    • step（ステップ）関数

    一般的に、数学関数の画像は連続的で緩やかですが、ステップ関数の特殊な点は値の跳び変わりが存在することです。その関数画像は次のようになります：

    この跳び変わりの特徴は数値上の論理分岐に非常に適していますが、その使用は人の直感に合わないため、GLSLでは条件演算子を使用して関連する論理を完成させることができます。例えば：(a < b) ? a : b

    GLSLのいくつかの組み込み関数（例えばmin、maxなど）はGPU固有の実装であるため、論理分岐の問題を気にする必要はありません。ifの使用に注意するだけで、ifは分岐と等価ではなく、真正に重要なのはコンパイラが**分岐命令**を生成するかどうかです。

    これらの問題の詳細と注意点については、非常に良い説明がある記事があります：

    パイプラインキャッシュ（Pipeline Cache）¶

    前文で述べたように、ゲームエンジンでは通常一種類のシェーダー言語で開発を行い、各グラフィックスAPIのシェーダーコードに変換します。この変換で一般的に得られるのは具体的なグラフィックスAPIのソースコードまたはバイトコード（中間）ファイルです。

    GPUがシェーダーを使用する場合、実際にはソースコードまたはバイトコード（中間）ファイルを機械で実行可能なバイナリコードにコンパイルする必要があります。このコンパイル過程はグラフィックスドライバに依存しており、各ユーザーのグラフィックスドライバのバージョンが異なる可能性があるため、開発会社はすべてのグラフィックスドライバをカバーすることは困難です。これは、ユーザーのコンピュータでシェーダーのバイナリコードをコンパイルしなければならないことを意味します。

    プログラムの実行過程でシェーダーのコンパイルによるカクツキを回避するため、現代のグラフィックスAPIはすべてパイプラインキャッシュ（Pipeline Cache）機能を提供しています。この機能により、プログラムは初回起動時にすべてのパイプラインをコンパイルしてディスクに保存することができ、プログラムの実行時または次回起動時にシェーダーのコンパイルによるカクツキが発生しなくなります。

    Unreal Engineではこの技術をPSOキャッシュ（Pipeline State Object Cache）と呼んでいます。

    PSOキャッシュに関する知識を説明する非常に良い記事があります：

    • [知乎-mike] UE4 PSOキャッシュ

    QRhiでは、QRhiを作成する際にパイプラインキャッシュ機能を有効にすることができます：

    関数QByteArray QRhi::pipelineCacheData()を使用して、現在のプログラムで既にコンパイルされたパイプラインキャッシュデータを取得できます。

    関数void QRhi::setPipelineCacheData(const QByteArray &data)を使用して、パイプラインキャッシュデータを設定できます。

    プログラムがQRhiGraphicsPipeline::create()を呼び出すと、現在のパイプラインパラメータの状態に基づいて、ストリームライン状態が存在するかどうかをクエリします。存在する場合は直接再利用され、再コンパイルされません。

    学習プラットフォーム¶

    海外には非常に面白い2つのプラットフォームがあります。固定フローのパイプラインを通じて、一部の外部入力変数を提供しフラグメントシェーダーコードを変更するだけで、多くの非常にクールなグラフィックス効果を作成することができます：

    • Shadertoy：https://www.shadertoy.com/

    • Glsl Sandbox：http://glslsandbox.com/

    これら2つのプラットフォームはどちらも完備されたオンラインShaderエディタを搭載しており、簡単な効果を模倣してシェーダーの基本的な構文に慣れることができます。
