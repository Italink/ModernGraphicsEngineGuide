    GUI¶

    グラフィカルユーザーインターフェース（Graphical User Interface、略してGUI、グラフィカルユーザーインターフェースとも呼ばれる）は、グラフィック方式で表示されるコンピュータ操作のユーザーインターフェースを指す。

    グラフィカルユーザーインターフェースは人とコンピュータ通信を行うためのインターフェース表示形式であり、ユーザーがマウスなどの入力デバイスを使って画面上のアイコンやメニューオプションを操作し、コマンドの選択、ファイルの呼び出し、プログラムの起動、その他の日常的なタスクを実行できるようにする。キーボードからテキストや文字コマンドを入力して日常的なタスクを完了する文字インターフェースと比較して、グラフィカルユーザーインターフェースには多くの利点がある。グラフィカルユーザーインターフェースはウィンドウ、ドロップダウンメニュー、ダイアログボックスおよびそれに対応する制御メカニズムで構成されており、様々な新しいアプリケーションで標準化されている。つまり、同じ操作は常に同じ方法で完了し、グラフィカルユーザーインターフェースではユーザーが見て操作するのはすべてグラフィックオブジェクトであり、コンピュータグラフィックス技術が応用されている。

    ——《百度百科》

    コンソールと知恵比べをする日々に疲れたら、この記事が役に立つかもしれません。

    概要¶

    GUIの分類は主に2つの大きなカテゴリに分かれている。

    • Native UI：伝統的なネイティブアプリ開発モデルで、システムプラットフォーム上のインターフェースを使用して開発する
    • Web UI：ブラウザ上で特定的に動作するウェブアプリケーション

    こちらに更に詳しい紹介があります：

    • 知乎：Native、Web App、Hybridとは何か？

    HybridとはNative UIとWeb UIを混合して開発することを指す

    それらに関する議論はこちらを参照してください：

    • 知乎：Web AppとNative App、どちらがトレンドか？

    Web UIはコストが低く開発が速いため、インターネット市場で主導的地位を占めていますが、Native UIを使用する理由は主に高性能、カスタマイズ性、ハードウェアとのインタラクションです。

    Web GPUが現在安定しつつあり、Webプログラマーにとっては更なる向上の余地がありますが、グラフィックスやエンジン分野の方には、Native方向を進むことを推奨します。これにより、より多くの制御可能な空間が得られます。

    Native UIの方案は、言語によって主に以下のように分類されます：

    C/C++: Qt、WxWidget、GTK、FLTK、DearImGUI、Nuklear、duilib、C++ Builder、MFC、EasyX

    Python: PyQt、WxPython、PyGTK、PyFLTK、DearPyGUI、Tkinter、PyGame

    C#：WPF、WinForm

    Java：Swing、JavaFx

    上記のフレームワークの中で、C/C++を使用すると天然の優位性があります。もしPythonやC#の開発者で、強制的な業務要件がない場合は、GUIのために大掛かりなC++の学習をする必要はありません。

    • 知乎：どの言語がGUI作成に最も適しているか？

    これらのC++ GUIフレームワークの中で、どのように選択すれば良いのでしょうか？

    筆者は順番にEasyX - Tkinter - PyGame - JavaFx - FLTK - Qt - ImGUI - UE Slateを学びました。

    全体的に使ってみると、GUIは結局以下のことであることが分かりました：

    • システムの（キーボード・マウス）インタラクションイベントを処理する
    • 画面上にピクセルを埋めていくつかのグラフィックスを描画する

    これはオペレーティングシステムまたは各GUIフレームワークが少なくとも提供する機能であり、この2つの機能があれば、キーボード・マウス操作にコールバック関数をバインドし、ループで画面ピクセルにRGBを埋めるだけで、どんなクールなグラフィカルインターフェースでも作れませんか？例えば以下のようなプログラムです。

    #include <conio.h>      //コンソールIO
#include <iostream>

int main() {
    char currentChar = '\0';
    const int width = 20;
    const int height = 20;
    while (true) {
        if (kbhit()) {              //kbhitは現在キー入力があるかどうかを判断できる
            currentChar = getch();  //getchはエコーなし入力関数で、getcharと異なり、入力したキーがコンソールに表示されない
        }
        system("cls");              //コンソールをクリアする
        std::cout << "Please enter key:" << std::endl;
        for (int y = 0; y < height; y++) {
            for (int x = 0; x < width; x++) {
                std::cout << currentChar;
            }
            std::cout << std::endl;
        }
    }
    return 0;
}

    コンソールプログラムは実行中に激しく点滅します。この点については後述で解決します。

    GUIは上記のコンソールプログラムと比較して、結局キーボード・マウス入力を一層のインターフェースにカプセル化し、widthとheightをウィンドウサイズとし、対応する座標のピクセルに色を埋めるだけです。

    実際にどのフレームワークを選択するかを決定する最も重要な点は生態系であり、具体的には以下の点に現れます：

    • 使用する人が多く、チームメンバーが多く、採用が容易である
    • フレームワークのカバレッジが広く、ツールライブラリが多く、ドキュメントが充実している
    • 公式が長期的に維持し、迭代頻度が高く、不具合が少ない

    上記のフレームワークの中で、最も良くできているのは間違いなくQtです。

    Qtの大部分のモジュールはLGPLライセンスに従っており、動的リンクの形式でモジュールを使用し、商用ソフトウェアをリリースすることが許可されています。各モジュールのオープンソースライセンスについては以下を参照してください：

    • https://doc.qt.io/qt-6/licenses-used-in-qt.html

    Qtのソースコードを変更したり、一部の商用モジュールを使用したりする場合は、Qtの商用ライセンスを購入する必要があります。具体的には以下を参照してください：

    • https://www.qt.io/licensing/open-source-lgpl-obligations

    Qtのオープンソースライセンスが比較的厳しく、C++標準とは独立しており、体量が膨大であるため、多くのチームは依然としてWxWidget、C++ Builder、duilib、GTKなどのフレームワークを選択する可能性があります。MFC、FLTK、EasyXは良いGUIフレームワークかもしれませんが、開発生態系は楽観的ではないため、選択肢がある場合は触れないことを推奨します。

    Dear ImGUIとNuklearは軽量、ポータブルで**Immediate Mode**に従うGUIツールキットであり、本質的には開発者にいくつかのコントロールインターフェースを提供して一フレームのグラフィックスの描画を完了させるものです。ImGUIを例にとると、以下のコードを使用します：

    ImGui::Text("Hello Dear ImGUI");
static bool CheckState;
ImGui::Checkbox("CheckBox ", &CheckState);

    以下のようなインターフェースを生成できます：

    Immediate Mode（即時モード） は主に変数CheckStateのポインタを「コントロール」に渡す点に現れます。一方、伝統的な**Retained Mode（保持モード）** 、例えばQtでは、コードは以下のようになる可能性があります：

    static bool CheckState;
QCheckBox* CheckBox = new QCheckBox;
CheckBox->setCheckState( CheckState? Qt::Checked : Qt::Unchecked);      //初期化
QObject::connect(CheckBox,&QCheckBox::stateChanged,[&](int state){      //signal-slotをバインド
    CheckState = state == Qt::Checked;
});

    QCheckBox がCheckStateのポインタを使用していないことがわかります。代わりにCheckStateを使用してコントロールの初期状態を設定し、コントロールのstateChanged時にCheckStateの値を設定します。つまり、コントロール自体が自身のStateを保持しているのに対し、**Immediate Modeは無状態を強調**し、状態をコントロールに埋め込んでいます。

    開発過程で、过多の局部状態を保存すると同期を保持するために多くのコードを記述する必要があり、不注意でバグを引き起こす可能性があります。例えば、一部のイベントが複数回実行されたり、無限ループに陥ったりしやすくなります。

    例えば、Colorを調整する場合：

    カラーパレットを使用し、ドラッグまたはチャネル値の入力、16進数入力、画面からの色取得など、複数の方式で同じ色値を調整できます。保持モードを使用する場合、ある方式で色を変更した後、他のコントロールを手動で調整して色の同期を保証する必要があります。いくつかのデザインパターンに従うことでこの問題を解決できますが、即時モードはこのようなアプリケーションシナリオで天然の優位性を持っています。それらの違いに関する議論は以下を参照してください：

    • 知乎：RetainedとIMGUIの関係と違いは何か？

    では、これはDear ImGUIがQtより優れていることを意味するのでしょうか？必ずしもそうではありません。筆者の観点は以下の通りです：

    • Immediate Modeはゲームエンジンにより適しているが、Dear ImGUIはまだ不十分である。 それは単なる小さなGUIツールキットであり、確かに使いやすく、良いインターフェース効果を作り出すことができますが、大規模なソフトウェアシステムの開発はエンジニアリングアートであり、低い門檻はより多くの問題を引き起こす可能性があります。十分な人手と精力で不断に迭代できない限り、ネイティブのDear ImGUIを使用して開発することは災難になります...

    ここに回答があります。Dear ImGUIについて言及していませんが、この種のフレームワークの問題をよく暴露しています：https://www.zhihu.com/question/66934513/answer/248036488

    • Retained Modeはコントロールアーキテクチャの一種の方式に過ぎず、Qt != Retained Modeである。 基本的にネイティブUIフレームワークの公式コントロールはRetained Modeを使用していますが、希望する場合はこれらのフレームワーク上でImmediate Modeを使用することもできます。

    Why Qt and not IMGUI?

    では、Qtの方が良いという意味でしょうか？必ずしもそうではありません。筆者の観点は以下の通りです：

    • Qtはエディタとして主に使用されるため、ゲームエンジン内では多くの場合、以下の例のようになります：
    • O3DE：https://github.com/o3de/o3de

    現在、ゲーム内のUI方案には適していません：

    • 云风のBLOG — ゲームUIモジュールの選択：https://blog.codingnow.com/2020/07/game_ui.html

    UEのSlateは非常に優れた基盤UIフレームワークです：

    • https://docs.unrealengine.com/5.1/en-US/understanding-the-slate-ui-architecture-in-unreal-engine/

    しかし、本シリーズ記事の次のグラフィックス関連のチュートリアルでは、Qtを主エディタとして使用し、ImGUIをシーン編集のために埋め込む予定です。主な理由は以下の通りです：

    • QtはクロスプラットフォームのWindowカプセル化を持ち、Handleを取得してNative APIを使用して特殊な処理を行うことができる
    • Qtはエレガントなリフレクションシステムを持ち、エディタの構築に便利であり、Signal-Slotを使用してロジックを良好にデカップリングし、可読性を高めることができる
    • Qtは独立したコンテナライブラリを持ち、STLの苦しみから免れることができる
    • Qtはインターフェーススタイルが統一された多くの拡張ライブラリを持ち、例えば基礎数学ライブラリ、画像エンコーディング・デコーディングライブラリ、マルチメディアライブラリなどがあり、学習成果をより容易に実用化することができる
    • Qt 6.0以降、OpenGL、DX11、Vulkan、MetalをサポートするRHI（Render Hardware Interface）が導入され、OpenGLより使用が容易であり、アーキテクチャ上はVulkanスタイルのglslと現代的なグラフィックスAPIを使用し、bgfxのような魔改造を行っていません。最も重要なのは、QtのRHIを使用してNative APIと良好に互換性を持たせることができ、これによりグラフィックスAPIまたはハードウェアが提供する高級機能を使用しやすくなります
    • Qtの多くの体系構造はUnreal Engineにマッピングすることができ、目標がUnreal Engineである場合は、Qtは最良の跳板であり、Qtの公式コードの可読性が高く、大量のドキュメント、Demo、チュートリアルがあるためです

    プラットフォーム基礎¶

    GUIプログラムは画面に表示され、画面上のピクセルをシステム的に管理するために、オペレーティングシステムはWindowという構造を提供します。Windows10では、標準的なWindowは以下のようになり、タイトルバー（アイコン、タイトルテキスト、最小化ボタン、最大化ボタン、閉じるボタン）を持っています：

    以下の方法でWindowを作成することができます：

    • CMakeLists.txtとmain.cppファイルを新規作成する

    • CMakeLists.txtに以下を記入する：

    cmake_minimum_required(VERSION 3.12)
project(Window)
add_executable(Window WIN32 main.cpp)

    Win32はこのexecutableがWin32ウィンドウであることを示し、具体的にはVisual Studioのプロジェクト設定 - リンカ - システム - サブシステム - ウィンドウに対応する

    • main.cppに以下を記入する：
    #ifndef UNICODE
#define UNICODE
#endif 

#include <windows.h>

LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam);

int WINAPI wWinMain(HINSTANCE hInstance, HINSTANCE hPrevInstance, PWSTR pCmdLine, int nCmdShow)
{
    // ウィンドウクラスを登録する
    const wchar_t CLASS_NAME[]  = L"Sample Window Class";

    WNDCLASS wc = { };

    wc.lpfnWndProc   = WindowProc;
    wc.hInstance     = hInstance;
    wc.lpszClassName = CLASS_NAME;

    RegisterClass(&wc);

    // ウィンドウを作成する

    HWND hwnd = CreateWindowEx(
        0,                              // オプションのウィンドウスタイル
        CLASS_NAME,                     // ウィンドウクラス
        L"Learn to Program Windows",    // ウィンドウテキスト
        WS_OVERLAPPEDWINDOW,            // ウィンドウスタイル

        // サイズと位置
        CW_USEDEFAULT, CW_USEDEFAULT, CW_USEDEFAULT, CW_USEDEFAULT,

        NULL,       // 親ウィンドウ    
        NULL,       // メニュー
        hInstance,  // インスタンスハンドル
        NULL        // 追加のアプリケーションデータ
        );

    if (hwnd == NULL)
    {
        return 0;
    }

    ShowWindow(hwnd, nCmdShow);

    // メッセージループを実行する

    MSG msg = { };
    while (GetMessage(&msg, NULL, 0, 0) > 0)
    {
        TranslateMessage(&msg);
        DispatchMessage(&msg);
    }

    return 0;
}

LRESULT CALLBACK WindowProc(HWND hwnd, UINT uMsg, WPARAM wParam, LPARAM lParam)
{
    switch (uMsg)
    {
    case WM_DESTROY:
        PostQuitMessage(0);
        return 0;

    case WM_PAINT:
        {
            PAINTSTRUCT ps;
            HDC hdc = BeginPaint(hwnd, &ps);

            // すべての描画はここで行われ、BeginPaintとEndPaintの間である

            FillRect(hdc, &ps.rcPaint, (HBRUSH) (COLOR_WINDOW+1));

            EndPaint(hwnd, &ps);
        }
        return 0;

    }
    return DefWindowProc(hwnd, uMsg, wParam, lParam);
}

    上記のコードはマイクロソフトの公式チュートリアルからのもので、興味のある読者は自分で一通り見ることができます：

    • https://learn.microsoft.com/en-us/windows/win32/learnwin32/your-first-windows-program

    Spy++¶

    ここまでで、Windowとは何だと思いますか？最大化、最小化、閉じるボタンの付いた枠ですか？

    必ずしもそうではありません。Visual Studioで**Spy++**を見つけることができます：メニューバー—ツール—Spy++

    これを使用してシステム内のすべてのWindowを表示することができます：

    Spy++は自底向上で階層的にすべてのウィンドウを表示します。つまり、ディスプレイに表示されるものはすべて痕跡があり、例えば最下層はデスクトップ（壁紙）です。

    そのウィンドウ検索ツール（メニューバー—検索—ウィンドウを検索—ドラッグ下図の照準を任意のウィンドウに）を使用して、Spy++で具体的なItemを定位することができます。これはUEのコントロールリフレクターに類似しています。

    上記のツールを通じて、ウィンドウには階層があり、必ずしも閉じるボタンがあるわけではなく、枠さえない可能性があることがわかります。

    Windowsでは、枠とタイトルバーの部分はシステムによって制御され、プログラム自体に属さないため、**Non-Client Area（非クライアント領域）**と呼ばれます。

    枠内部の領域はプログラムが自由に描画できる領域であり、この部分は**Client Area（クライアント領域）**と呼ばれます。

    • What is windows client and non-client area?

    マイクロソフトはタイトルバーがUIの美化を制限していることに気づいた可能性があるため、ウィンドウは**枠なし且つ背景透明**の属性を設定することをサポートしています。多くのソフトウェアはこの方式で**異形ウィンドウ**を描画しています。例えばQQ音楽のプレーヤー：

    システムインタラクションイベントは現在のActivated（アクティブな）ウィンドウに伝達され、Unactivated状態にあるウィンドウはシステムが一般的にグレーのスタイルで表示します：

    一般的に、アクティブなウィンドウは1つだけであり、これは現在キーボードの入力イベントを受け入れるウィンドウが1つだけであることを意味します。ただし、フックなどの方法で規則を打破することもできます。

    Multiple buffering¶

    以前のコンソールプログラムでは、ページが激しく点滅します。これは1つのバッファに少しずつものを追加し、コンソールウィンドウがこの過程をプレビューしているため、リフレッシュ速度が速いため点滅が発生するからです。このような問題を解決するために、コンピュータ科学では**Multiple buffering（多バッファ）**の概念が提唱されました：

    • コンソールプレビューに供給するバッファを**前台バッファ**と呼び、多バッファの核心は前台バッファを直接操作するのではなく、**后台バッファ**を処理した後、**一括して**前台バッファに**提交**することで、点滅と撕裂を効果的に回避できます。

    一括提交といえば、前節の**for copy**と**memcpy**を思い出しませんか？

    ハードウェアとインターフェースの提供者も明らかにこの道理を理解しており、大多数の場合、Map、Blitのような操作をサポートしています。

    コンソールで双バッファを使用する例は以下の通りです：

    #include <conio.h>      //コンソールIO
#include <iostream>
#include <Windows.h>

const int width = 20;
const int height = 20;
const int MaxBufferSize = width * height * 10;

void UseSingleBuffer() {
    char currentChar = '*';
    while (true) {
        if (kbhit()) {              //kbhitは現在キー入力があるかどうかを判断できる
            currentChar = getch();  //getchはエコーなし入力関数で、getcharと異なり、入力したキーがコンソールに表示されない
        }
        system("cls");              //コンソールをクリアする
        for (int y = 0; y < height; y++) {
            for (int x = 0; x < width; x++) {
                std::cout << currentChar;
            }
            std::cout << std::endl;
        }
    }
}

void UseDoubleBuffer() {
    HANDLE frontendBuffer = GetStdHandle(STD_OUTPUT_HANDLE);        //デフォルトのバッファを取得する

    HANDLE backendBuffer = CreateConsoleScreenBuffer(               //新しいバッファを作成して后台バッファとする
        GENERIC_READ | GENERIC_WRITE,
        FILE_SHARE_READ | FILE_SHARE_WRITE,
        NULL,
        CONSOLE_TEXTMODE_BUFFER,
        NULL
    );

    //2つのバッファのカーソルを隠す
    CONSOLE_CURSOR_INFO cci;
    cci.bVisible = 0;
    cci.dwSize = 1;
    SetConsoleCursorInfo(frontendBuffer, &cci);
    SetConsoleCursorInfo(backendBuffer, &cci);


    char bufferData[MaxBufferSize];     //キャッシュデータ一時保存領域
    DWORD bufferLength = 0;
    COORD zeroCoord = { 0,0 };
    char currentChar = '*';

    while (true) {
        if (kbhit()) {              
            currentChar = getch();  
        }
        bufferLength = 0;

        CONSOLE_SCREEN_BUFFER_INFO backendBufferInfo;       //backendBufferの每行の文字数を取得する
        GetConsoleScreenBufferInfo(backendBuffer, &backendBufferInfo);
        int lineWidth = backendBufferInfo.srWindow.Right - backendBufferInfo.srWindow.Left + 1;     

        for (int y = 0; y < height; y++) {
            for (int x = 0; x < width; x++) {
                bufferData[bufferLength++] = currentChar;
            }
            while (bufferLength % lineWidth != 0) {             //改行の効果を達成するために文字を埋める
                bufferData[bufferLength++] = ' ';
            }
        }

        //backendBufferのzeroCoordから始めてbufferLength長のbufferDataを書き込む
        WriteConsoleOutputCharacterA(backendBuffer, bufferData, bufferLength, zeroCoord, &bufferLength);    
        SetConsoleActiveScreenBuffer(backendBuffer);            //backendBufferを表示する
        std::swap(backendBuffer, frontendBuffer);               //前后バッファ操作ハンドルを交換し、frontendBufferが次のループのbackendBufferとなる
    }
}

int main() {
    //UseSingleBuffer();
    UseDoubleBuffer();
    return 0;
}

    *.cppに記述されたQ_OBJECTについては、末尾で手動で*.mocをincludeする必要があり、これによりmocの実行がトリガーされます。例えば：

    /* main.cpp
*/

#include <QApplication>
#include <QMetaType>
#include <QMetaProperty>

class QExmapleClass : public QObject {
    Q_OBJECT
    Q_PROPERTY(int Var READ getVar WRITE setVar)                //Getter、Setterを通じてMetaPropertyを宣言する
public:
    int getVar() {
        return mVar;
    }
    void setVar(int inVar) {
        mVar = inVar;
    }

    Q_INVOKABLE void sayHello(const QString& inName) {          //MetaMethodを宣言する
        qDebug() << "Hello " << inName.toLatin1().data();
    }

    enum Number {
        Zero, One, Two, Three
    };
    Q_ENUM(Number)                                              //MetaEnumを宣言する
protected:
    int mVar= 5;
};

int main(int argc, char* argv[]) {
    QApplication a(argc, argv);

    QExmapleClass obj;      

    //MetaObjectを取得する
    const QMetaObject* metaObjectFromStatic = &QExmapleClass::staticMetaObject; 
    const QMetaObject* metaObjectFromVirtual = obj.metaObject();

    //プロパティを読み書きする
    obj.setProperty("Var", QVariant::fromValue<int>(10));                       
    QVariant var = obj.property("Var");
    qDebug() << "Property : " << var.value<int>();

    //関数を呼び出す
    qDebug() << "Invoke Method Begin:";
    metaObjectFromStatic->invokeMethod(&obj, "sayHello",Q_ARG(QString,"Boy"));
    qDebug() << "Invoke Method End";

    //MetaType操作
    QMetaType metaType = var.metaType();
    qDebug() << "Meta Type : " << metaType.name() <<" ID: " << metaType.id();

    //MetaObject内でプロパティを走査して読み書きし、プロパティタイプを出力する
    for (int i = metaObjectFromStatic->propertyOffset() ; i < metaObjectFromStatic->propertyCount(); i++) {
        const QMetaProperty& metaProperty = metaObjectFromStatic->property(i);
        metaProperty.write(&obj, QVariant::fromValue<int>(15));
        QVariant varFromMetaObject = metaProperty.read(&obj);
        qDebug() << "Meta Property : " << metaProperty.name() << varFromMetaObject;
    }

    //MetaObject内で関数を走査し、パラメータ情報を出力する
    for (int i = metaObjectFromStatic->methodOffset(); i < metaObjectFromStatic->methodCount(); i++) {  
        const QMetaMethod& metaMethod = metaObjectFromStatic->method(i);
        QByteArrayList paramNames = metaMethod.parameterNames();
        QStringList paramsDefineList;
        for (int j = 0; j < metaMethod.parameterCount(); j++) {
            paramsDefineList << metaMethod.parameterTypeName(j) +" " + paramNames[j];
        }
        qDebug() << QString("Meta Method : %1 %2(%3)")
            .arg(metaMethod.typeName())
            .arg(metaMethod.name())
            .arg(paramsDefineList.join(',')).toLatin1().data();
    }

    //MetaObject内で列挙型を走査し、列挙型情報を出力する
    for (int i = metaObjectFromStatic->enumeratorOffset(); i < metaObjectFromStatic->enumeratorCount(); i++) {
        const QMetaEnum& metaEnum = metaObjectFromStatic->enumerator(i);
        qDebug()<< "Meta Enum : " << metaEnum.name();
        for (int j = 0; j < metaEnum.keyCount(); j++) {
            qDebug() << "-- " << metaEnum.key(j) << " : " << metaEnum.value(j);
        }
    }
    return a.exec();
}

    Signal-Slot¶

    信号スロットメカニズムはオブジェクト間の通信に使用され、Qtの核心的な特性です。その作用について、疑似コードの例は以下の通りです：

    class Student{
    Signal nameChanged(string OldName, string NewName);
public:
    void setName(string inName){
        nameChanged.Emit(mName，inName);
        mName = inName;
    }
private:
    string mName;
};

class Tearcher{
public:
    void OnStudentNameChanged(string OldName, string NewName){
        //do something
    }
};

class Class{
protected:    
    void connectEveryone(){
         for(auto Student:mStudents){       
             Student.nameChanged.Connect(mTeacher,&Tearcher::OnStudentNameChanged);
         }
    }
private:
    Teacher mTeacher;
    TArray<Student> mStudents;
};

    connectEveryone関数を通じて、「先生」がクラスで生徒に「名前を変更したら通知してください」と伝えることができます。

    ここではTeacherとStudentの構造を直接変更するのではなく、第三者の集合（クラス）で二者の関係をバインドすることで、良好なデカップリングを実現しています。

    このメカニズムはUEのデリゲート（Delegate）に対応し、Qtの信号スロットより細かいですが、訳文にはいくつかの欠点があります。Signalとも呼ばれると、開発者の連想を引き起こして正しい使用方法を採用することが容易になると信じています。

    更に詳細な説明については以下を参照してください：

    • https://doc.qt.io/qt-6/signalsandslots.html

    Event System¶

    Qtでは、イベントは抽象クラスQEventサブクラスのインスタンスオブジェクトを指し、アプリケーション内部または外部の活動の結果を記述するために使用されます。作用上、重いSingle-Slotと見なすことができ、QWigdetのインタラクションメカニズムはすべてイベントを通じて実現されます。

    イベントが発生すると、Qtは適切なQEventサブクラスのインスタンスを構築してそれを表し、以下を呼び出します：

    • static bool QCoreApplication::sendEvent(QObject* receiver, QEvent event)

    対応するQObjectにイベントを送信し、QObjectは虚関数を持っています：

    • virtual bool QObject::event( QEvent* e )

    eventをオーバーライドすることで、イベントを処理したり、更に他の関数に分散させたりすることができます。

    此外、Qtはイベントリスナーメカニズムをサポートし、QObjectの虚関数をオーバーライドすることができます：

    • bool QObject:: eventFilter ( QObject * watched , QEvent* event )

    これをfilterObjとし、以下を呼び出します：

    • void QObject:: installEventFilter ( QObject* filterObj )

    これにより、該当オブジェクトを他のオブジェクトのイベントリスナーとすることができます。

    イベントシステムについて詳しくは以下を参照してください：

    • https://doc.qt.io/qt-6/eventsandfilters.html

    Garbage Collection¶

    前節のメモリ管理でQtのGCについて触れました。QtのGC方式は非常にシンプルで、QObjectは唯一のparentを指定することができ、parentが解放されるとchildrenも解放されます。此外、QObject::deleteLaterを使用してQObjectの解放を遅延させることもできます。

    QWidgetでは、子コントロールを追加すると暗黙的にparentが設定され、大多数の場合手動でdeleteする必要はありません。但しparentのライフサイクルを制御する必要があり、オブジェクトツリーの某个ノードに不備があると、サブツリー全体のオブジェクトが解放されなくなります。

    WindowOption¶

    一般的に、開発者はQWindowに接触することさえないことが多いです。最外层（または最上位）のQWidgetが自動的にQWindowを生成するため、このQWidgetにいくつかの設定を行うことでWindowの生成に影響を与えることができます：

    • WindowFlag：Windowの标识を調整し、例えばポップアップ、ダイアログ、提示框、无边框など...
    • WindowModality：モーダルウィンドウを設定し、モーダルウィンドウは他のウィンドウの入力をブロックし、一般的にユーザーに現在のオプションを強制的に選択させてから続行するために使用されます。
    • WindowState：Windowの状態には默认、最小化、最大化、全屏（无边框）、激活があり、setWindowStateを呼び出すことができます。Qtはいくつかの便利なAPIも提供しており、例えばactivateWindow()などです。

    例えば以下のコード：

    QWidget widget;
widget.setWindowFlags(Qt::FramelessWindowHint|Qt::Tool);
widget.resize(200,200);
widget.show();

    スクリーンに200*200の灰色の正方形が表示され、下方のタスクバーでそのアイコンも隠されます。

    注意すべき点は、Widgetを作成する時にWindowは作成されておらず、Widgetの設定の大多数はそのパラメータ状態機械を調整しているだけであり、イベント実行時にこれらの状態に基づいて実際の操作を行うことです。例えば、showした後でWindowのハンドルを取得することができます。

    Event¶

    GUIの表示はQWidgetのpaintEventにあり、これをオーバーライドすることで、QPainterを使用して任意のグラフィックスを描画することができます。

    #include <QApplication>
#include <QWidget>
#include <QMouseEvent>
#include <QPainter>

class QExmapleWidget:public QWidget {
    Q_OBJECT
private:
    QPoint mMousePressPos;
    bool bIsHovered = false;
protected:
    void mousePressEvent(QMouseEvent* event) override {
        if (event->button() == Qt::LeftButton)      //マウス左ボタンが押された時の位置を記録する
            mMousePressPos = event->pos();          
    }
    void mouseMoveEvent(QMouseEvent* event) override {
        if (event->buttons() & Qt::LeftButton)      //マウス左ボタンを押しながらドラッグする時、Widgetの位置を調整する
            move(event->pos() + this->pos() - mMousePressPos);
    }

    void enterEvent(QEnterEvent* event) override {
        bIsHovered = true;                          //マウスがWidgetに入る
        setCursor(Qt::ClosedHandCursor);            //マウスカーソルの形状を設定する
        update();                                   //インターフェースのリフレッシュをリクエストする
    }

    void leaveEvent(QEvent* event) override {
        bIsHovered = false;                         //マウスがWidgetから離れる
        setCursor(Qt::ArrowCursor);                 //マウスカーソルの形状を設定する
        update();                                   //インターフェースのリフレッシュをリクエストする
    }

    void paintEvent(QPaintEvent* event) override {
        QPainter painter(this);

        painter.fillRect(this->rect(),bIsHovered ? Qt::green : QColor(0,100,200));  //領域内に色を埋める

        painter.setPen(QPen(Qt::white));
        painter.setFont(QFont("",20,90));                                           //デフォルトフォントを使用し、フォントサイズとウェイトを設定する
        painter.drawText(this->rect(), Qt::AlignCenter, "Hello Qt");                //文字を描画する
    }
};

int main(int argc, char* argv[]) {
    QApplication a(argc, argv);
    QExmapleWidget widget;
    widget.setWindowFlags(Qt::FramelessWindowHint);         //无边框
    widget.setAttribute(Qt::WA_TranslucentBackground);      //背景透明      
    widget.setAttribute(Qt::WA_AlwaysStackOnTop);           //置顶
    widget.resize(200,200);
    widget.show();
    return a.exec();
}

    Layout¶

    プログラムには往往にしてQWidgetが1つだけではないため、これらのWidgetのレイアウトを組織する必要があります。Qtで常用されるレイアウトはBoxLayoutであり、簡単な例は以下の通りです：

    #include <QApplication>
#include <QWidget>
#include <QHBoxLayout>
#include <QPushButton>

class QMainWidget :public QWidget {
    Q_OBJECT
public:
    QMainWidget() {
        createUI();
    }
private:
    void createUI() {
        QHBoxLayout* hLayout = new QHBoxLayout(this);
        // QHBoxLayout* hLayout = new QHBoxLayout();            //等价
        //setLayout(hLayout);

        hLayout->setContentsMargins(5, 5, 5, 5);                //外边距を設定する
        hLayout->setSpacing(10);                                //内部要素の間隔を設定する
        hLayout->setAlignment(Qt::AlignLeft|Qt::AlignVCenter);  //左对齐且垂直居中を設定する
        hLayout->addWidget(new QPushButton("A"));
        hLayout->addSpacing(20);                                //空白填充を加入する
        hLayout->addWidget(new QPushButton("B"));
        hLayout->addWidget(new QPushButton("C"));
    }
};

int main(int argc, char* argv[]) {
    QApplication a(argc, argv);
    QMainWidget widget;
    widget.resize(300, 300);
    widget.show();
    return a.exec();
}
