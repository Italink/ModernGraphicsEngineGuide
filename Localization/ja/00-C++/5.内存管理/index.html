    メモリ管理¶

    メモリに関する注意点を詳しく解説した優れた記事がこちらです：

    • https://blog.csdn.net/zju_fish1996/article/details/108858577

    すでに優れた記事が存在するため、本節では補足的な内容を説明します。

    基礎概念¶

    コンピュータ上の様々なデータは、一般的に**ディスク**に**格納**されています。デスクトップアイコンの「このPC」を右クリック→「管理」→「ストレージ」→「ディスクの管理」を選択することで、ディスクを閲覧および操作できます：

    **タスクマネージャー**と**リソースモニター**では、ディスクの現在の動作状況を確認できます：

    ディスク内のデータが使用される際、オペレーティングシステムはそれをメモリにロードします。メモリについては、百度百科に以下の説明があります：

    メモリはコンピュータの重要な部品であり、内部メモリおよび主記憶装置とも呼ばれます。CPU内の演算データを一時的に格納し、ハードディスクなどの外部記憶装置との間でデータを交換するために使用されます。外付けストレージとCPU間の通信の架け橋であり、コンピュータ内のすべてのプログラムはメモリ上で実行されます。メモリ性能の強弱はコンピュータ全体の性能に影響を与えます。コンピュータが起動すると、オペレーティングシステムは演算が必要なデータをメモリからCPUに転送して演算を実行し、演算が完了するとCPUは結果を出力します。

    ヒープ、スタック¶

    プログラム（Windowsのexe）も一種のデータであり、起動時にオペレーティングシステムによって**固定サイズ**の2つのメモリブロックが事前に割り当てられます。それぞれ以下の用途に使用されます：

    • スタック（Stack）：主に関数スタックの呼び出し実行に使用
    • ヒープ（Memory）：プログラム実行時に動的に申請されたメモリアドレスの格納に使用

    スタックのサイズは固定ですが、ヒープのサイズは実装に依存し、使用されるコンパイラによって異なります。ヒープは動的に割り当てられたメモリアドレスを連鎖的に格納するものと見なすことができます。MSVCにおけるヒープの**事前割り当て**のデフォルトサイズは1MBですが、実行時に使用される空間は1MBを超えることが許可されています。

    コンパイラとプラットフォームによってデフォルトサイズは異なります。WindowsのMSVCを例に、以下のプログラムを実行してみましょう：

    int main() {
    char arr[10000000];
    return 0;
}

    スタック内でプログラムの事前割り当てサイズを超えるメモリを作成または使用したため、Stack Overflowが発生します：

    次に以下のプログラムを実行します：

    int main() {
    for (int i = 0; i < 100000000; i++) {
        new int;
    }
    return 0;
}

    対応する空きメモリブロックがない場合、動的割り当ては失敗します：

    コンパイラを使用してプログラムの事前割り当てスタックおよびヒープの空間サイズを手動で設定できます。Visual Studioでは、プロジェクト設定から変更できます：

    筆者が使用しているVS2022には**漢字化異常**があり、Stackが誤って「スタック」に翻訳されています。

    • 命令：https://learn.microsoft.com/en-us/cpp/build/reference/stack-stack-allocations

    メモリフラグメンテーション¶

    C++では、一般的にnew/deleteを使用して動的メモリを作成および破棄します。実際には、オペレーティングシステムごとにメモリ割り当てインターフェースが異なります。例えば、Windowsでは実際にVirtualAlloc/VirtualFreeを使用し、UnixおよびMacではmmap/munmapを使用します。

    プログラムの実行中に、メモリの割り当てと解放が頻繁に行われると、大量の連続した小さなメモリが割り当て済みメモリの間に挟まるようになります。オペレーティングシステムのメモリ割り当てアルゴリズムは完全ではないため、これらの**空きメモリを継続的に使用できなくなり**ます。このようなメモリを**メモリフラグメント**と呼びます。

    メモリアライメント¶

    ほとんどのCPUはバイト単位でメモリを読み書きするのではなく、一般的に2、4、6、8バイトをメモリアクセス粒度として使用します。これによりメモリのIO効率が向上します。詳細は以下を参照してください：

    • https://zhuanlan.zhihu.com/p/83449008

    操作、ハードウェア、プラットフォームが異なると、メモリアライメントにも若干の差異があります。開発者が専門用語を理解していない場合、容易にトラブルに陥る可能性があります。例えば：

    • SIMDを使用する場合は16バイトアライメントを保証する必要がある
    • GPU上で申請されたBuffer間に最小アライメントオフセットの制限がある
    • 異なるレンダリングAPIではベクトルのアライメント方式にも差異が存在する
    D3D9:{
    {  4,  4,  4,  4 }, // Uint8
    {  4,  4,  4,  4 }, // Uint10
    {  4,  4,  8,  8 }, // Int16
    {  4,  4,  8,  8 }, // Half
    {  4,  8, 12, 16 }, // Float
};

D3D11:{
    {  1,  2,  4,  4 }, // Uint8
    {  4,  4,  4,  4 }, // Uint10
    {  2,  4,  8,  8 }, // Int16
    {  2,  4,  8,  8 }, // Half
    {  4,  8, 12, 16 }, // Float
};

GL、Vulkan、Metal: {
    {  1,  2,  4,  4 }, // Uint8
    {  4,  4,  4,  4 }, // Uint10
    {  2,  4,  6,  8 }, // Int16
    {  2,  4,  6,  8 }, // Half
    {  4,  8, 12, 16 }, // Float
};

    高速キャッシュ¶

    メモリの読み書き速度は確かに速いですが、CPUの演算速度はさらに速いため、CPUはデータの到着（読み取り）と送信（格納）を待つために長時間を費やす必要があります。CPUのメモリアクセス平均時間を短縮するため、コンピュータのストレージシステムに**CPU高速キャッシュ**が導入されました。百度百科には以下の定義があります：

    コンピュータシステムにおいて、CPU高速キャッシュ（英語：CPU Cache）はプロセッサがメモリにアクセスする平均時間を短縮するための部品です。

    ピラミッド型ストレージシステムでは、CPUレジスタに次いで2番目に上位に位置します。その容量はメモリよりはるかに小さいですが、速度はプロセッサの周波数に近づくことができます。

    プロセッサがメモリアクセス要求を発行すると、まずキャッシュ内に要求されたデータが存在するかどうかを確認します。存在する場合（ヒット）、メモリにアクセスすることなく直接データを返します；存在しない場合（ミス）、まずメモリ内の対応するデータをキャッシュにロードしてからプロセッサに返します。

    キャッシュが効果的である主な理由は、プログラム実行時のメモリアクセスが局所性（Locality）の特徴を示すためです。この局所性には空間局所性（Spatial Locality）と時間局所性（Temporal Locality）の両方が含まれます。この局所性を効果的に利用することで、キャッシュは非常に高いヒット率を達成できます。

    プロセッサから見ると、キャッシュは透明な部品です。したがって、プログラマは通常キャッシュの操作を直接介入することはできません。ただし、キャッシュの特徴に基づいてプログラムコードに特定の最適化を実施することで、キャッシュをより良く利用することは確かに可能です。

    Windowsでは、タスクマネージャーを開いてコンピュータのCache情報を確認できます：

    プログラムがあるメモリブロックにアクセスすると、周辺領域も一緒にキャッシュにロードされる可能性があります（追加で一部の内容をロードしてもオーバーヘッドが少ないため）。次回アクセスするメモリが既にキャッシュにロードされている場合（キャッシュヒットと呼ばれる）、CPUは再びメモリにアクセスする必要がなくなり、速度が向上します。

    このサンプルコードはキャッシュの重要性を理解するのに役立ちます：

    #include <iostream>
#include <chrono>
#include <vector>

class ClockGuard {          //あるスコープの実行時間を出力するためのクラス
public:
    ClockGuard(const std::string& inDest)
        :mDesc(inDest)
    {
        mStartTime = std::chrono::steady_clock::now();
    }
    ~ClockGuard() {
        std::chrono::steady_clock::time_point currentTime = std::chrono::steady_clock::now();
        double durationNs = std::chrono::duration<double, std::nano>(currentTime - mStartTime).count();
        std::cout << mDesc << " Cost: " << durationNs << " Ns" << std::endl;
    }
private:
    std::string mDesc;
    std::chrono::steady_clock::time_point mStartTime;
};

const size_t bigger_than_cachesize = 10 * 1024 * 1024;
long* ptr = new long[bigger_than_cachesize];
void ClearCPUCache() {              //キャッシュをクリアしようとする
    for (int i = 0; i < bigger_than_cachesize; i++){
        ptr[i] = rand();
    }
}

int main(int argc,char** argv) {
    std::vector<int*> continuous(1000);     //メモリ連続な配列
    std::vector<int*> dispersive(1000);     //メモリ分散な配列

    for (int*& item : continuous) {     
        item = new int;
    }

    const int spacing = 10000;          //メモリ間隔、この値を調整してcacheの影響を確認
    for (int*& item : dispersive) {         
        item = new int[spacing];
    }

    ClearCPUCache();
    {
        ClockGuard guard("continuous");     //連続したメモリに値を代入、キャッシュヒット率が高い
        for (int*& item : continuous) {
            *item = 1;
        }
    }

    ClearCPUCache();
    {
        ClockGuard guard("dispersive");     //離散したメモリに値を代入、キャッシュヒット率が低い 
        for (int*& item : dispersive) {
            *item = 1;
        }
    }

    return 0;
}

    メモリコンテキストの調整を避けることで、キャッシュのヒット率を効果的に高めることができます。人間の脳にも同様のメカニズムが存在します。不信なら以下をご覧ください：

    ハードウェアアクセラレーション¶

    メモリにはキャッシュメカニズムだけでなく、使用上もいくつかの**黒魔術**が存在します。例えば以下のコード：

    #include <iostream>
#include <chrono>
#include <vector>

class ClockGuard {
public:
    ClockGuard(const std::string& inDest)
        :mDesc(inDest) {
        mStartTime = std::chrono::steady_clock::now();
    }
    ~ClockGuard() {
        std::chrono::steady_clock::time_point currentTime = std::chrono::steady_clock::now();
        double durationNs = std::chrono::duration<double, std::nano>(currentTime - mStartTime).count();
        std::cout << mDesc << " Cost: " << durationNs << " Ns" << std::endl;
    }
private:
    std::string mDesc;
    std::chrono::steady_clock::time_point mStartTime;
};

const size_t bigger_than_cachesize = 10 * 1024 * 1024;
long* ptr = new long[bigger_than_cachesize];
void ClearCPUCache() {
    for (int i = 0; i < bigger_than_cachesize; i++) {
        ptr[i] = rand();
    }
}

int main(int argc, char** argv) {
    std::vector<int> src(100000);
    std::vector<int> dst(100000);

    ClearCPUCache();
    {
        ClockGuard guard("Copy");       //普通のC++コピー
        for (int i = 0; i < src.size(); ++i) {
            dst[i] = src[i];
        }
    }
    ClearCPUCache();
    {
        ClockGuard guard("Map");        //メモリコピー
        memcpy(dst.data(), src.data(), src.size());
    }

    return 0;
}

    C++構文では、for (int i = 0; i < src.size(); ++i) { dst[i] = src[i]; }より簡単なコードを書くことはできませんが、memcpyを使用して同じことを行うと、性能が大幅に向上します。これは主にmemoryがアセンブリレベルの最適化を使用しており、ハードウェア特性と強い関連性があるためです：

    • ARM64アーキテクチャ下のmemcpy実装原理：https://blog.csdn.net/m0_46250244/article/details/115055101

    今後グラフィックスを学ぶ過程で、GPU上でも同様の操作に多く接触することになるため、読者はハードウェアの体系構造をより深く理解する必要があります。

    最適化方向¶

    以上から、メモリ最適化の主な戦略は主に以下の点に焦点を当てていることがわかります：

    • メモリフラグメンテーションを減らし、キャッシュのヒット率を高める
    • アプリケーションシナリオとハードウェア特性を組み合わせ、効率的なメモリ操作方法を使用する

    オブジェクトライフサイクル管理¶

    現代のプログラム開発過程では、大量のオブジェクトが存在します。スタック上で申請されたオブジェクトは、そのスコープを離れると自動的に解放されますが、ヒープ上で申請されたオブジェクトは、手動でそのライフサイクルを管理する必要があります。c++では、newとdeleteが一対一に対応することを保証する必要があります。理想的な場合、以下のようになります：

    void Func(){
    Object* object = new Object;
    //...
    delete object;
}

    しかし現実は残酷で、コードに論理分岐やネストされた関数が存在する場合、オブジェクトのライフサイクルが移行し、手動でdeleteを制御することが困難になることがあります：

    void Func(){
    Object* object = new Object;
    if(...){
        //Do something 
        delete object;
        return;
    }
    else if(...){
        //Do something 
        delete object;
        return;
    }
    else if(...){
        //Do something 
        delete object;
        return;
    }
}

    これに対し、オブジェクトのライフサイクルを自動的に管理する戦略が必要となります。現在主に使用されている方式は以下の2つです：

    • スマートポインタ
    • ガベージコレクション

    スマートポインタ¶

    c++の様々なライブラリでは、共有ポインタの概念が提供されています。その核心思想は以下の通りです：

    • 実際のオブジェクトポインタを外部オブジェクトでラップし、外部オブジェクトの構築、破棄、コピーを監視することで、ポインタの参照を記録するための共通メモリを使用し、参照が0になった時にオブジェクトを破棄する

    簡易的な模倣は以下の通りです：

    struct SharedPtrRefData{
    uint refCount = 0; 
};

template<Typename _Ty>
class SharedPtr{
public:
    SharedPtr(_Ty* rawPtr)                      //コンストラクタ
        : mRawPtr(rawPtr)
        : mRefData(new SharedPtrRefData);       //共通メモリを新規作成
    {
        mRefData->refCount++;                   //参照カウント+1
    }

    SharedPtr(const SharedPtr<_Ty>& other){     //コピーコンストラクタ
        mRefData = other.mRefData;              //共通メモリを伝達
        mRefData->refCount++;                   //参照カウント+1
    }

    ~SharedPtr(){                               //デストラクタ
        mRefData->refCount--;                   //参照カウント-1
        if(SharedPtrRefData->refCount == 0){    
            delete mRawPtr;                     //オブジェクトを破棄
            delete mRefData;                    //共通メモリを破棄
        }
    }
private:
    _Ty* mRawPtr;
    SharedPtrRefData* mRefData;
};

    この構造は以下のフレームワークで実装されています：

    • C++標準ライブラリ： std::shared_ptr
    • Unreal Engine： TSharedPtr
    • Qt： QSharedPointer

    SharedPtrを使用することで、指針オブジェクトにアクセスする際に、それが解放されていないことを保証できます。しかし時には「共有ポインタ」が**オブジェクトのライフサイクルを延長しないが、後でオブジェクトが破棄されたかどうかを判断できる**ことを希望する場合があります。フレームワークでは一般的にこの構造を**WeakPtr**と呼び、以下のように対応しています：

    • C++標準ライブラリ： std::weak_ptr
    • Unreal Engine： TWeakPtr
    • Qt： QWeakPointer

    stdを例にとると：

    #include <iostream>

int main() {
    std::shared_ptr<int> sptr(new int);
    std::weak_ptr<int> wptr(sptr);
    if (const std::shared_ptr<int>& lock = wptr.lock()) {
        std::cout << "exist !!!" << std::endl;
    }
    else {
        std::cout << "not exist" << std::endl;
    }
    sptr.reset();
    if (const std::shared_ptr<int>& lock = wptr.lock()) {
        std::cout << "exist !!!" << std::endl;
    }
    else {
        std::cout << "not exist !" << std::endl;
    }
    return 0;
}

/*
exist !!!
not exist !
*/

    上記のSharePtrの簡易コードでは、refCountが0になった時にオブジェクトと共通メモリの両方が破棄されますが、実際にはSharedPtrRefDataにはrefCountとweakCountの2つのカウンタが存在します。refCountが0になった時にはオブジェクトのみが破棄され、共通メモリは破棄されません。これによりWeakPtrは依然として共有メモリにアクセスしてオブジェクトが存在するかどうかをクエリできます。weakCountも0になった時に初めて共通メモリが破棄されます。

    裸のポインタの場合、deleteはオブジェクトのメモリを破棄するだけで、ポインタが指すアドレスは依然として存在します。管理が不適切な場合、ダングリングポインタが出現し、メモリリークが発生します。WeakPtrはこの問題を解決します。

    また別の場合として、newで作成されたオブジェクトが、通常のオブジェクトのようにスコープを離れた後に破棄されることを希望する場合があります。例えば：

    class Example{
public:
    Example()
        : mObject(new Object)
    {}
    ~Example(){
        delete mObject;
    } 
private:
    Object* mObject;
}

    この場合、以下を使用できます：

    • C++標準ライブラリ： std::unique_ptr
    • Unreal Engine： TUniquePtr
    • Qt： QScopedPointer

    Qtの命名はその役割をよりよく反映しているようです。

    上記のコードをUniquePtrを使用して書き換えると以下のようになります：

    class Example{
public:
    Example()
        : mObject(new Object)
    {}
private:
    std::unique_ptr<Object> mObject;
};

    スマートポインタは開発過程の大部分の問題を解決できますが、完璧ではありません。以下に**注意点**があります：

    • スマートポインタを使用する場合は、できるだけコンストラクタまたはreset関数内でnewオブジェクトを行い、スマートポインタの外部で裸のポインタを操作しないようにする
    • std::shared<int> sptr(this)を使用してはならない。thisを使用して共有ポインタを作成したい場合は、thisのクラスをテンプレートenable_shared_from_thisから継承する必要がある
    • 不必要なSharedPtrを大量に使用すると一定の浪費が発生する。SharedPtrを使用する本意はオブジェクトのライフサイクルを維持することであり、インターフェースをカプセル化する際にオブジェクトのライフサイクルをインターフェースに伝達する必要がない場合は、SharedPtrを公開すべきではなく、WeakPtrまたはRawPtrを使用する
    • マルチスレッド環境で使用する場合は、使用するSharedPtrがスレッドセーフであることを確認し、参照カウントが正常に動作することを保証する

    さらに、以下の**潜在的な問題**があります：

    • 共有ポインタを使用する際、キャプチャパラメータのライフサイクルを無視しやすく、内部に共有ポインタが存在する場合、メモリリークが発生する：
    #include <iostream>
#include <functional>

class Exmaple {
public:
  Exmaple() {
      std::cout << "Create" << std::endl;
  }
  ~Exmaple() {
      std::cout << "Destroy" << std::endl;
  }
};

int main(int argc, char** argv) {
  {
      std::function<void()> func0;
      {
          std::shared_ptr<Exmaple> sptr(new Exmaple);
          std::function<void()> func1 = [sptr]() {};  //共有ポインタをキャプチャパラメータとして使用
          std::cout << "---------0" << std::endl;
          //func0 = func1;        //コメントを解除すると、Exampleは1と2の間で解放される

      std::cout << "---------1" << std::endl;

    • SharedPtrには循環参照の問題が存在する

    ガベージコレクション¶

    共有ポインタの欠点を解決するため、一部の高級言語や大型フレームワークではガベージコレクション（Garbage Collection）メカニズムが提供されています。循環参照の問題を解決し、遅延破棄を実現することを目的としています。

    C++の特性（歴史的な理由）により、不十分なガベージコレクションメカニズムがC++標準に導入されると、より混乱するだけであるため、C++におけるガベージコレクションは通常フレームワーク自身がカスタマイズするものです。UEやQtのように、C++標準の範囲を超えているため、ネットユーザーはU++やQ++と戏称しています。

    現在、筆者が多く了解しているGCメカニズムは以下の通りです：

    • Unreal Engine
    • Qt、FBX SDK
    • Lua

    開発者にとって、GCに関して主に了解する必要がある点は以下の2つです：

    • オブジェクト間の参照関係をどのようにマークするか
    • ガベージコレクションをどのように実行するか

    Java、C#、Python、Luaのような高級言語では、仮想マシンのため、オブジェクト間の参照を監視することが容易です。一方C++では、オブジェクト間の参照は手動で設定するか、リフレクションを通じて分析する必要があります。

    QtはQObjectを基底クラスとして使用し、そのメモリ回収は非常に簡単で、以下のようになります：

    class QObject{
public:
    QObject(QObject * parent = nullptr);
private:
    QVector<QObejct*> children;
    QObject *parent;
}
    • QObjectにはparentポインタとchildrenリストが存在し、QObjectを破棄すると同時にchildrenも破棄される
    • QObjectはdeleteLater()関数を提供し、オブジェクトを配列に追加し、イベント処理ループが終了した後に破棄を行います。

    FBX SDKはFbxObjectを基底クラスとして使用し、インスタンスを作成する際に必ず親オブジェクトを指定する必要があります。以下のようになります：

    FbxManager* lManager = FbxManager::Create();
FbxIOSettings* lIOSettings = FbxIOSettings::Create(lManager, "");
FbxScene* scene = FbxScene::Create(lManager,"");
FbxSkeleton* skeletonNode = FbxSkeleton::Create(scene,"SkeletonRoot");
FbxCluster* rootCluster = FbxCluster::Create(skeletonNode, "");
    • 親オブジェクトが解放されると、子オブジェクトも解放される

    上記2つのフレームワークのメモリ回収の主体構造は非常に簡単で、ループ問題に対してはparentを指定する際に検出を行い、ループが出現した場合は直接エラーを出力します。

    一方UEのGCメカニズムははるかに複雑です。UEでは、参照の構築は主に以下の2つの方式によって行われます：

    • UProperty（リフレクション）：UEはUObjectのPropertyを分析して、2つのオブジェクト間の参照を確定します
    • FGCObject：参照関係を手動で構築するためのインターフェースクラス。UEにおける大多数のフレームワーク（UMG、Editor、Niagaraなど）はFGCObjectを派生させてGC参照の管理メカニズムを実装しており、開発者が特定のインターフェースを呼び出す際に、暗黙的にオブジェクト間の参照が構築されるようになっています。

    UEの回収方式は比較的複雑で、ここでは展開しません。一般的には定期的かつ定量的に回収されることを了解するだけで十分です。

    ここで簡単なマークアンドスイープアルゴリズムを紹介します。その核心は以下の通りです：

    • すべての回収可能なオブジェクトを配列に格納する
    • オブジェクト間の参照関係を格納する
    • グローバルなルートノードを持ち、他のノードがこのノードに到達する参照関係を持つ場合、そのノードは到達可能であると判断する
    • ガベージコレクションを行う際には、ゲームスレッドを一時停止し、すべてのオブジェクトが使用されていないことを保証する
    • ルートノードからトラバースし、すべての到達可能なノードをマークする
    • オブジェクト配列をトラバースし、到達不可能なノードを破棄する

    簡易版の実装は以下の通りです（詳細はMark-and-Sweep：ガベージコレクションアルゴリズムを参照してください）：

    class ObjectBase{
public:
    typedef short ID;
public:
    ObjectBase();
    virtual ~ObjectBase();
    void addRefrence(ObjectBase * ref);     //オブジェクト参照を追加
    void removeRefrence(ObjectBase* ref);   //オブジェクト参照を削除
private:
    friend class ObjectManagement;
    ID id;                      //このオブジェクトに唯一のidを割り当てる
    std::list<ID> refrence;     //参照オブジェクトのidリスト
};

    ここでshortを使用するのは、2バイトで2^15（32767）個の数値を表現でき、IDとして十分であるためです。

    すべてのObjectBaseオブジェクトを管理するため、ここではグローバルな管理オブジェクト**GObjectManagement**を作成し、構築時にこのオブジェクトを追加し、破棄時に削除します：

    ObjectBase::ObjectBase(){
    GObjectManagement.AddObject(this);
}

ObjectBase::~ObjectBase(){
    GObjectManagement.RemoveObject(this);
}

    ObjectManagementの定義は以下の通りです：

    class ObjectManagement {
public:
    ObjectManagement() {
        for (int i = 0; i < mObjects.size(); i++) {     //Idスタックを初期化
            mObjects[i].object = nullptr;
            mIdStack[i] = i;
        }
    }
    void AddObject(ObjectBase* obj) {       //オブジェクトを追加
        if (obj != nullptr) {
            obj->id = allocId();
            mObjects[obj->id].object = obj;
            ++mCurrentNumberOfObject;
            mMaxIdOfObject = std::max(mMaxIdOfObject, obj->id);
        }
    }
    void RemoveObject(ObjectBase* obj) {    //オブジェクトを削除
        if (obj != nullptr) {
            mObjects[obj->id].object = nullptr;
            freeId(obj->id);
            --mCurrentNumberOfObject;
        }
    }
    void GarbageCollection() {              //ガベージコレクション
        MarkObjects(0);        //ここでは0番ノードをゲームグローバルのルートノードと仮定し、そこからトラバースして到達可能なオブジェクトをマークする
        for (int i = 0; i <= mMaxIdOfObject; i++) {     //すべてのオブジェクトを簡単にトラバースし、到達不可能なオブジェクトを破棄する
            if (!mObjects[i].reachable) {
                delete mObjects[i].object;
            }
            else {      //状態をリセットし、次の到達可能性トラバースの準備をする
                mObjects[i].reachable = false;
            }
        }
    }

    void MarkObjects(const ObjectBase::ID& Id) {                //すべてのノードを深さ優先でトラバース
        ObjectBase* obj = mObjects[Id].object;
        if (obj != nullptr && !mObjects[Id].reachable) {        //ノードが到達不可能であることを要求し、ループの出現を回避する
            mObjects[Id].reachable = true;
            for (auto& subId : obj->refrence) {
                MarkObjects(subId);
            }
        }
    }

private:
    ObjectBase::ID allocId() {                  //スタックトップからIdを割り当てる
        assert(mIdStackTop < mIdStack.size());
        return mIdStack[mIdStackTop++];
    }

    void freeId(ObjectBase::ID id) {            //Idを回収する
        assert(mIdStackTop > 0);
        mIdStack[--mIdStackTop] = id;
    }

public:
    struct ObjectItem{
        ObjectBase* object;
        bool reachable = false;
    };

    static const int MAX_NUMBER_OF_OBJECT = std::numeric_limits<ObjectBase::ID>().max();

    std::array<ObjectItem, MAX_NUMBER_OF_OBJECT> mObjects;      //ここで32767サイズの固定長配列を作成し、すべてのObjectを格納する

    std::array<ObjectBase::ID, MAX_NUMBER_OF_OBJECT> mIdStack;  //この固定長配列を使用してスタックを模擬し、Idの割り当てと回収を行い、Idが急速に膨張することを防止する
    ObjectBase::ID mIdStackTop = 0;                             //スタックトップインデックス

    ObjectBase::ID mCurrentNumberOfObject = 0;                  //現在存在するObjectの数
    ObjectBase::ID mMaxIdOfObject = 0;                          //プログラム全体で使用された最大ID、トラバース数を減らすために使用
};

//グローバル静的オブジェクト
static ObjectManagement GObjectManagement;

    メモリスケジューリングフレームワーク¶

    オープンソースコミュニティには、メモリフラグメンテーションを減らし、キャッシュのヒット率を高めることを目的とした多くのメモリスケジューリングフレームワークが登場しています。比較的有名なものは以下の通りです：

    mimalloc¶

    mimallocは優れた性能特性を持つ汎用アロケータです。当初Daan LeijenによってKokaおよびLean言語のランタイムシステムのために開発されました。

    • 小さく一貫性がある：このライブラリは単純で一貫性のあるデータ構造を使用し、約8k LOCです。これにより他のプロジェクトに統合および適応するのに非常に適しています。ランタイムシステムに対しては、単調な*ハートビート*および遅延解放のためのフックを提供します（参照カウントを持つ有界最悪ケース時間のため）。
    • 空きリストのシャーディング：各「mimallocページ」には、1つの大きな空きリスト（各サイズクラス）ではなく、多くの小さなリストがあります。これによりフラグメンテーションが減少し、局所性が向上します——タイムリーに割り当てられたものはメモリ内で近くに割り当てられます。（mimallocページは64ビットシステムで通常64KiBのサイズクラスのブロックを含みます）。
    • 空きリストのマルチシャーディング：良いアイデアです！各mimallocページの空きリストをシャーディングするだけでなく、各ページに複数の空きリストを持っています。特に、スレッドローカルのfree操作のためのリストと、並行free操作のための別のリストがあります。別のスレッドから解放する場合、スレッド間の複雑な調整を必要とせずに単一のCASで可能になります。数千の個別の空きリストが存在するため、競合は自然にヒープ全体に分散され、単一の位置で競合する機会は低くなります——スキップリストなどのランダムアルゴリズムと非常に似ており、ランダムオラクルを追加することでより複雑なアルゴリズムの必要性を排除します。
    • 急切なページリセット：「ページ」が空になった場合（空きリストシャーディングにより機会が増える）、メモリはオペレーティングシステムによって未使用としてマークされ（「リセット」または「クリア」）、特に長時間実行されるプログラムで（実際の）メモリプレッシャーとフラグメンテーションが減少します。
    • 安全：*mimalloc*は安全モードで構築でき、保護ページ、ランダム割り当て、暗号化された空きリストなどを追加して、さまざまなヒープの脆弱性を防止します。性能損失は通常、ベンチマークの平均で約10%程度です。
    • 一流のヒープ：効率的に複数のヒープを作成および使用し、異なる領域で割り当てを行います。ヒープは個々のオブジェクトを解放する代わりに一度に破棄できます。
    • 有界：膨張*の影響を受けず、有界の最悪ケース割り当て時間（*wcat）、有界の空間オーバーヘッド（約0.2%のメタデータ、割り当てサイズの最大12.5%の浪費）、および原子操作のみを使用する内部ポイントの競合はありません。
    • 高速：ベンチマークでは、mimalloc*は他の主要なアロケータ（*jemalloc、tcmalloc、*Hoard*など）より優れており、通常はより少ないメモリを使用します。優れた特性は、広範なベンチマークで一貫して良好な性能を発揮することです。大きなサーバープログラムには、巨大なオペレーティングシステムページのサポートもあります。

    oneTBB¶

    インテル® oneAPIスレッドビルディングブロック（oneTBB）は、スレッドの専門家でなくても、アクセラレーションアーキテクチャ間で複雑なアプリケーションに並列性を追加する作業を簡素化する柔軟な性能ライブラリです。

    • 論理性能を指定し、スレッドではない：ランタイムライブラリは自動的に論理並列をスレッドにマッピングし、プロセッサリソースを最も効率的に利用します。
    • スレッドをターゲットにして性能を向上：計算集約的な作業の特定のターゲットを並列化することに焦点を当て、より高レベルで簡単なソリューションを提供します。
    • 他のスレッドパッケージと共存：他のスレッドとシームレスに互換性があり、古いコードを変更せずに保持し、新しい実装にoneTBBを使用する柔軟性を提供します。
    • スケーラブルなデータ並列プログラミングを強調：oneTBBはデータ並列プログラミングを強調し、プログラムを機能ブロックに分解して各機能ブロックに個別のスレッドを割り当てるのではなく、複数のスレッドがコレクションの異なる部分で作業できるようにします。コレクションをより小さな部分に分割することで、より多くのプロセッサにスケーラブルになります。プロセッサとアクセラレータを追加すると、プログラムの性能が向上します。

    jemalloc¶

    jemallocは、フラグメンテーションの回避とスケーラブルな並行サポートを強調する汎用的なmalloc(3)実装です。FreeBSDのlibcライブラリのようにシステム提供のメモリアロケータとして、またC/C++アプリケーションにリンクするために使用することを目的としています。jemallocは標準的なアロケータの機能を超える多くのイントロスペクション、メモリ管理、および調整機能を提供します。

    tcmalloc¶

    TCMallocは、Cmalloc()およびC++のoperator newのGoogleのカスタム実装であり、CおよびC++コードでメモリを割り当てるために使用されます。このカスタムメモリ割り当てフレームワークは、C標準ライブラリ（Linuxでは通常glibcを介して）およびC++標準ライブラリが提供するフレームワークの代替手段です。

    • 性能はアプリケーションの並列度に応じて向上する
    • C++14およびC++17に最適化されており、性能上の利点を保証しながら標準とは若干異なります（これらはTCMallocリファレンスで注記されています）

    • 特定のアーキテクチャ下で性能を向上させる拡張機能や、指標収集などの他の動作を許可します

    • オペレーティングシステムから特定のサイズのメモリブロック（「ページ」と呼ばれる）を管理することで割り当てを実行します。

    • 特定のオブジェクトサイズのために個々のページ（またはTCMallocで「スパン」と呼ばれるページの実行）を使用します。例えば、すべての16バイトのオブジェクトは、そのサイズのオブジェクトのために専用に割り当てられた「スパン」に配置されます。この場合、メモリを取得または解放する操作ははるかに簡単になります。
    • 一般的なオブジェクトへのアクセスを高速化するために*キャッシュ*にメモリを保持します。解放後もこのようなキャッシュを保持することで、後で同様のメモリを再割り当てする場合、高コストのシステムコールを回避するのに役立ちます。

    使用方法¶

    これらのフレームワークの使用方法は簡単で、独自のメモリ割り当ておよび解放インターフェースを提供しています。C++のoperatorをオーバーライドし、これらのメモリインターフェースを使用してメモリを操作するだけです：

    mimallocを例に、以下のコードを使用してC++の new と delete をオーバーライドできます。

    #include <vcruntime_new.h>

_NODISCARD _Ret_notnull_ _Post_writable_byte_size_(_Size) _VCRT_ALLOCATOR
void* __CRTDECL  operator new  (size_t Size) { return mi_malloc(Size ? Size : 1); }

_NODISCARD _Ret_notnull_ _Post_writable_byte_size_(_Size) _VCRT_ALLOCATOR
void* __CRTDECL operator new[](size_t Size) { return mi_malloc(Size ? Size : 1); }

_NODISCARD _Ret_maybenull_ _Success_(return != NULL) _Post_writable_byte_size_(_Size) _VCRT_ALLOCATOR
void* __CRTDECL operator new  (size_t Size, const std::nothrow_t&) { return mi_malloc(Size ? Size : 1); }

_NODISCARD _Ret_maybenull_ _Success_(return != NULL) _Post_writable_byte_size_(_Size) _VCRT_ALLOCATOR

    Unreal Engineでは、メモリアロケータの基底クラス**FMalloc**を実装し、以下のサブクラスを派生させています。FMemory::Malloc / FMemory::Freeを使用してメモリアロケータのインターフェースを呼び出すことで、異なるメモリアロケータ間で切り替えることができます：

    • Ansi：標準的なcアロケータで、直接malloc、free、reallocを呼び出します。

    • Stomp：割り当て過程での読み書きによる問題（ダングリングポインタ、メモリ越界など）を追跡するのに役立ちます。

    • TBB：Thread Building Blocks、Intelが提供する64ビットスケーラブルメモリアロケータ

    • Jemalloc：主にUnix用のメモリアロケータです。

    • Binned：ビン分割メモリアロケータで、主にIOSに使用されます。

    • Binned：ビン分割アロケータは1つのメモリブロック（Pool）を多くの異なるサイズのスロットに分割します。例えばBinnedはPC上で64KBを41個の異なるスロットに分割し、尾部から空きスロットを割り当てます：

    • Binned2：Binned2アロケータはスレッドローカルメモリ割り当てをサポートし、毎回ロックする必要がありません。これにより、頻繁な小さなメモリ割り当てと解放時に性能が大幅に向上する可能性があります。

    • Binned3：仮想メモリアドレス（論理メモリアドレス）を使用し、それを並べ替えることでPoolのIndex検索を高速に実行できるようにし、メモリのポインタから目標サイズのPoolを計算できるようにします。

    • Mimalloc：tcmallocやjemallocより優れた汎用メモリアロケータ

    基礎ライブラリの最適化¶

    メモリのアプリケーションレベルでは、C++の基礎的なコンテナとアルゴリズムには大きな最適化の余地があります。ここでC++ STLライブラリについて言及する必要があります。その欠点は非常に多く、以下の通りです：

    • 一部のSTL実装（特にMicrosoft STL）は性能特性が悪く、ゲーム開発には不適切です。
    • STLは時々デバッグが難しく、ほとんどのSTL実装は神秘的な変数名と珍しいデータ構造を使用しています。
    • STLアロケータは時々使用が苦痛で、多くの要求があり、コンテナにバインドされた後は変更できません。
    • STLには過剰な機能が含まれており、コードが予期せずに超過する可能性があります。プログラマーにその機能を使用すべきではないと伝えることは容易ではありません。
    • STLは非常に深い関数呼び出しを介して実装されています。これにより、最適化されていないビルドでの性能が許容できなくなり、時には最適化されたビルドでも同様です。
    • STLはオブジェクトのアライメントをサポートしていません。
    • STLコンテナは、コピー元のエントリを提供せずにコンテナにエントリを挿入することを許可しません。これは非効率的です。
    • slist、hash_map、shared_ptrなどの既存のSTL実装（STLPortなど）で見られる有用なSTL拡張機能は、他のSTLバージョンで存在しないか、STLバージョン間で一貫性がないため、移植性がありません。
    • STLにはゲームプログラマーが有用と考える有用な拡張機能（intrusive_listなど）が欠けていますが、移植可能なSTL環境で最適に最適化することができます。
    • STLの仕様はそれを効率的に使用する能力を制限します。例えば、STLベクターは連続メモリを保証しないため、配列として安全に使用することはできません。
    • STLは性能よりも正確性を重視し、学術的な純粋性を追求するため、性能のために危険な道を進んだり、予想外の方法を取ったりすることはありません。
    • STLコンテナはプライベートな実装を持ち、移植可能な方法でそのデータを処理することを許可しませんが、時にはこれが重要です（例えばノードプール）。
    • すべての既存のSTLバージョンは、少なくともその一部のコンテナの空のバージョンでメモリを割り当てます。これは理想的ではなく、コンテナメモリのリセットなど、特定の状況で性能を大幅に向上させることができる最適化を阻止します。
    • STLのコンパイル速度は遅く、ほとんどの現代のSTL実装は非常に大きいためです。

    出典：https://github.com/electronicarts/EASTL/blob/master/doc/Design.md

    最大の欠点は以下の通りです：

    • STLは性能よりも正確性を重視し、学術的な純粋性を追求するため、性能のために危険な道を進んだり、予想外の方法を取ったりすることはありません。

    例えば、多くの方がstd::vectorを使用する際に、reserveを使用して事前に割り当てを行い、拡張によるメモリ再割り当てを回避することを知っていると思います。set、mapのようなコンテナについても、ノードのメモリを事前に割り当てることができます。これによりメモリの割り当て回数を減らすだけでなく、コンテナ要素がメモリ内で連続していることを保証し、アクセス時のキャッシュのヒット率を大幅に向上させることができます。

    STLとUEのメモリアロケータを比較すると、明確な違いが見られます：

    • STLはAllocatorを使用してコンテナに新しい要素を割り当てる
    • UEのAllocatorは整个コンテナのメモリを再割り当てし、UEのコンテナはstd::vectorのような拡張メカニズムをサポートしています

    上記の問題を解決するため、多くのエンジンは独自の基礎ライブラリを維持しています。オープンソースの主な解決策は以下の通りです：

    EASTL¶

    EASTLは、複数のプラットフォームでのランタイムおよびツール開発に使用できるC++テンプレートライブラリで、コンテナ、アルゴリズム、イテレータを含みます。その実装は非常に広範かつ堅牢で、すべての他の考慮事項よりも性能を重視しています。

    • EASTLは簡素化され、より柔軟なカスタム割り当て方案を持っています。
    • EASTLのコードは読みやすさが向上しています。
    • EASTLには拡張されたコンテナとアルゴリズムがあります。
    • EASTLにはゲーム開発のために設計された最適化があります。

    上記の項目の中で、STLと互換性のない唯一の違いはメモリ割り当ての状況です。

    foonathan¶

    foonathanもSTLの存在する欠点を解決するために開発されましたが、EASTLとは異なり、STLを変更しようとはしていません。

    STL C++17 polymorphic memory source¶

    C++17以前は、STLコンテナのメモリ割り当てを完了するためにallocatorを使用する必要がありました。主な欠点は以下の通りです：

    • allocatorはテンプレートシグネチャの一部であり、異なるallocatorのコンテナは混在して使用できません
    vector<int,allocator0> v0;
vector<int,allocator1> v1;
v0 = v1;  //エラー
    • allocatorのメモリアライメントは制御できず、カスタムallocatorを渡す必要があります
    • allocatorに内部状態がありません

    C++17では、コンテナに新しいメモリ割り当て方法——<memory_resource>が提供されました。

    その使用方法は以下の通りです：

    #include <memory_resource>
#include <vector>
#include <string>            
#include <iostream>

class CustomMemoryResource :public std::pmr::memory_resource{   //カスタムmemory_source
public:
    CustomMemoryResource() {}
private:
    virtual void* do_allocate(const size_t _Bytes, const size_t _Align) override {
        return ::operator new(_Bytes,std::align_val_t(_Align));
    }                                                                                                                                             
    virtual void do_deallocate(void* _Ptr, size_t _Bytes, size_t _Align){
        ::operator delete(_Ptr,_Bytes, std::align_val_t(_Align));
    };
    virtual bool do_is_equal(const memory_resource& _That) const noexcept {
        return this==&_That;
    };
};
int main() {
    std::pmr::unsynchronized_pool_resource ms1; //スレッド非安全なプールアロケータ
    std::pmr::synchronized_pool_resource ms2;   //同期プールアロケータ
    CustomMemoryResource custom_memory_source;  //カスタムアロケータ
    char buffer[20];
    std::pmr::monotonic_buffer_resource mbr(std::data(buffer),std::size(buffer),&custom_memory_source);   //単調キャッシュアロケータ、bufferからメモリを割り当て、mbr.release()が呼び出されるまでメモリは解放されず、キャッシュを超える場合は上位アロケータを使用して割り当てる
    {
        std::pmr::vector<std::pmr::string> vec{ &mbr };
        vec.push_back("Hello World");
        vec.push_back("One Two Three");
    }   //vecのメモリは解放されない
    mbr.release();  //この時点でmbr内のメモリが解放される
}

    上記のコードから、**MemoryResouce**が**allocator**の存在する問題を完璧に解決していることがわかります。名前空間std::pmrからのコンテナを使用するだけです。

    どのように実現されているのでしょうか？

    std::pmr::vectorを例に、その定義を見つけると：

    namespace pmr {
    template <class _Ty>
    using vector = std::vector<_Ty, polymorphic_allocator<_Ty>>;
} // namespace pmr

    非常に簡単で、polymorphic_allocatorを使用したstd::vectorです。その定義を見つけると、以下のコードが見られます：

    template <class _Ty>
class polymorphic_allocator {
public:
    //...
    _NODISCARD __declspec(allocator) _Ty* allocate(_CRT_GUARDOVERFLOW const size_t _Count) {
        // _Resourceから_Count個の_Ty型オブジェクトのスペースを取得
        void* const _Vp = _Resource->allocate(_Get_size_of_n<sizeof(_Ty)>(_Count), alignof(_Ty));
        return static_cast<_Ty*>(_Vp);
    }

    void deallocate(_Ty* const _Ptr, const size_t _Count) noexcept /* strengthened */ {
        // _Resourceに_Count個の_Ty型オブジェクトのスペースを返す
        // size_tが_Ty[_Count]のサイズを表現できることを検証する必要はない
        _Resource->deallocate(_Ptr, _Count * sizeof(_Ty), alignof(_Ty));

private:
    memory_resource* _Resource = _STD pmr::get_default_resource();    
};

    明らかに、元のAllocatorインターフェースでmemory_resourceのメソッドを呼び出しているだけです。
