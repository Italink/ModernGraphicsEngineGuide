    C++基礎¶

    学習経路¶

    C++の初心者にとって、最も良い学習方法は間違いなく各種の問題解決プラットフォームに浸ることです：

    • LeetCode：https://leetcode-cn.com/
    • 牛客網（Nowcoder）：https://www.nowcoder.com
    • Virtual Judge：https://link.zhihu.com/?target=https%3A//vjudge.net/
    • 杭電HDUOJ：https://link.zhihu.com/?target=http%3A//acm.hdu.edu.cn/
    • PTA | プログラム設計クラス実験補助教育プラットフォーム：(https://pintia.cn/problem-sets/dashboard)
    • ...

    プログラミングトレーニングを通じて、C++の基本構文や各種データ構造・アルゴリズムを迅速に掌握し、自身のプログラミング思考を形成できます。また、問題解決は資料を読むほど退屈ではありません。

    筆者は強く**初心者がこの段階で1～2年間磨きをかけることを推奨**します。

    『C++ Primer Plus』『C++ Templates』などのツールブックについては、大まかに読んでC++に何があるかを知っておき、対応する問題に遭遇した際に再び詳細に読めば十分です。

    『STLソースコード剖析』のようなソースコード剖析やエンジニアリング実践クラスの書籍については、深く読むことを推奨しません。これらの書籍は大量の特定のエンジニアリング実践経験に基づいているため、関連するエンジニアリング経験のない方にとっては収穫が少ないからです。人の生命と精力は限られており、現代社会が高度に発展しているのはまさに巨人の肩の上に立っているからです。

    学習過程では、仲間と討論できるフォーラムもあります：

    • Stack Over Flow：https://stackoverflow.com/
    • CSDN：https://www.csdn.net/
    • 掘金（Juejin）：https://juejin.cn/
    • 知乎（Zhihu）：https://www.zhihu.com/hot
    • 牛客（Nowcoder）：https://www.nowcoder.com/discuss

    ここに非常に良いC++チュートリアルがあります：

    • https://www.bilibili.com/video/BV1Wd4y1t7fZ/

    また、完全なC++リソースコレクションもあります：

    • https://github.com/fffaraz/awesome-cpp

    入門段階を過ぎたら、エンジニアリング実践に接触し始めることができます。この段階では**質の高い**プロジェクトを参考に**不断に試行**する必要があります。

    ここで筆者はQtを学ぶことを推奨します。Qtのコードは数十年間イテレーションされており、コード品質が非常に高い上に、最も重要なのは**ドキュメントが充実している**ことです！Qtを単なるGUIフレームワークと見なさないでください。個人の見解として、Qtは現在学習効率が最も高いC++フレームワークと言えます（後の章で詳しく説明します）。

    Qt Creatorには多くの公式サンプルが提供されており、Githubにも大量の高品質なプロジェクトが存在します。

    どのフレームワークを学ぶ場合でも、**必ず必ず必ず**最初にフレームワークの公式ドキュメントを一通り読んでください。一般的に、公式ドキュメントは情報が最も完全な場所です。

    学習過程では、そのエンジニアリングアーキテクチャやデザインパターンなどを多く思考してください。

    ここで幾つかの書籍を推薦します：

    • 《C++コード整洁之道》
    • 《リファクタリング：既存コードの設計を改善する》
    • 《デザインパターン》
    • 《Effective C++》《More Effective C++》

    発展ルート¶

    学部生に対して、筆者が推奨する発展ルートは以下の通りです：

    • 1～2年間をかけて、熱狂的に問題を解き、ACM、蓝桥杯、PATなどの各種プログラミングコンテストに参加します。
    • 1～2年間をかけて、熱狂的にエンジニアリングを行い、不断に試行錯誤し、多くの参考例を探し、コードをリファクタリングし、自身のアーキテクチャ能力を磨きます。

    ここで筆者は参考指標を提示します：4年間で300問以上の問題を解き、総コード量が20万行以上に達すること。

    • 3年生になったら、履歴書を提出してインターンシップを探し始め、コミュニケーション能力を鍛えることに注意します。

    一定の段階に達すると、自身の技術を制限するのは能力ではなく時間と精力になることに気づくでしょう。学習過程で孤独に感じるかもしれませんが、最終的には集団に回帰する必要があります。

    安心してください、彼らはあなたに共感できます。

    • 4年生になったら、卒業設計と答弁をしっかり準備し、成績に関係なく、自身に対して後悔のないようにします。

    誤解¶

    国内のC++技術環境はあまり友好的ではなく、特に一部の大学では多くの人が**C++の難易度を過度に誇張**する傾向があります。C++について言及すると、以下のような考えが浮かび上がることがあります：

    • C++はバックエンド開発に使われる
    • C++はすでに時代遅れで、Python、Go、Rust...が未来的にそれを置き換えるだろう
    • ...

    これに対して、筆者も無知な者は恐れないとしか言えません...

    彼らを責めることもできません。国内ではインターネット企業が盛んで、主に業務ロジックを導向とし、開発効率と維持コストをより重視するからです。

    C++は業務のために生まれたものではなく、コンピュータ技術により注力しています。多くのものは存在即合理ですが、確かに一部の歴史的な負担もあります...

    一方、後発の言語は一部の応用シーンに対して大幅な最適化を行っており、それらを使用すると開発体験が大幅に向上することは事実です。

    前の章の言葉を引用すると：「道生一、一生二、二生三、三生万物」。道に近づけば近づくほど、掌握する必要のあるものは少なくなり、掌握した後に派生できる「物」はより多くなります。しかし、万千の事物の中からいわゆる**道**を探すことは、はるかに難しくなります。あなたは自身の人間的な思考を矯正し、思考方式をよりコンピュータや機械のようにする必要があるかもしれません。そうすれば、C++がどれほどエレガントかを発見できるでしょう～

    トレーニングクラスの罠に陥らないように注意してください。トレーニングクラスのコース品質がどれほど高いかを論じるまでもなく、学習自体は情報の収集と整理能力を鍛えるものです。常に近道を探そうとすると、他人にだまされやすくなります。欲しいものがなければ強くなれます～

    コンパイル¶

    統合開発環境（IDE: Integrated Development Environment）をコンパイラと見なすのは、多くの初心者の誤りです。コンパイラについて言及すると、最初に思い浮かぶのはVisual Studio、Visual Studio Code、Clion、XCode、Dev、VC...かもしれません。

    現代の開発過程では開発者が直接コンパイラを操作することは少ないですが、少なくともこのものが存在すること、そして存在意義を理解する必要があります。自身の知識体系に曖昧な部分が存在しないようにしましょう。

    後続のリフレクション章では、コンパイラの実装に直接接触します。

    コンパイラについて、百度百科には以下の定義があります：

    c++コンパイラ

    コンパイラとは、「高級言語」を「機械語（低級言語）」に翻訳するプログラムです。

    現代のコンパイラの主な作業フロー：ソースコード → プリプロセッサ → コンパイラ → アセンブラ → オブジェクトコード → リンカ → 実行可能プログラム。

    ウィキペディア：https://en.wikipedia.org/wiki/C%2B%2B

    一般的なC++コンパイラにはGCC/G++、ICC、Clang、MSVC、BCCがあります。

    プログラム開発者にとって、これらのコンパイラの詳細を深く理解する必要は通常なく、それらが存在することと存在意義を知っておけば十分です。

    それらに関する討論は、知乎の各C/C++コンパイラの特長と不足点は何ですか？を参照してください。

    まだC++のコンパイラを使用したことがない場合は、UP主と一緒に使用してみましょう～

    これらのパラメータを見て、見覚えがありませんか？ああ、これはVSのプロジェクト設定ではないですか？

    cl.exeはコマンドラインプログラムです。以下でこのコマンドラインプログラムを使用して自身のコマンドラインプログラムを生成します。

    まず、任意のパスで新しいファイルを作成し、名前を**main.cpp**とします。コードは以下の通りです：

    #include <iostream>

/**
* argc はパラメータの個数
* argv はパラメータ文字列配列
*/

int main(int argc,char** argv) {
    std::cout << "argc: " << argc << std::endl;
    for (int i = 0; i < argc; i++) {
        std::cout << i <<": " << argv[i] << std::endl;
    }
    return 0;
}

    コンパイルに成功すると、以下の2つのファイルが生成されます：

    • main.obj：コンパイル時の中間ファイルであるオブジェクトファイル
    • main.exe：Windows下の実行可能ファイル

    実際、cl.exeは以下の複数のステップを実行しています：

    • プリコンパイル：ソースファイル（*.c、*.cpp）を*.iファイルに出力し、ソースコード内の#define、#include、#ifなどのプリプロセッサ指令をコンパイルします。
    • コンパイル：*.iを*.sファイルにコンパイルし、高級言語をアセンブリ言語に変換します。
    • アセンブル：*.sを*.oファイルにアセンブルし、アセンブリ言語を機械指令に変換します。
    • リンク：*.oファイルをリンクし、最終的に実行可能ファイル（Windows下では*.exe）に統合します。

    今後の開発過程では、以下のような大量のコマンドラインプログラムに遭遇する可能性があります：

    • グラフィカルインターフェースがなく、パラメータを解析することで各種作業を完了するプログラム。複雑なパラメータについては、QtのQCommandLineParserやGithub上の多くのオープンソース**CommandLine解析ライブラリ**が利用可能です。
    • グラフィカルインターフェースプログラムでも、このパラメータを利用して他の機能を実現できます。例えば、レジストリに起動パラメータを追加することで、プログラム実行時に起動が自動かどうかを判断できます。
    • cmdでwhere 指令名を入力すると、対応するコマンドラインプログラムの保存位置を見つけることができます。例えばwhere wingetを入力すると、wingetのパスが取得できます。

    ライブラリ¶

    現実生活では、あらゆる場所に見られる各種デバイスが、一つ一つの部品で組み立てられていることに気づくでしょう。例えば一般的なスマートフォンは、バッテリー、画面、センサーなどで構成されています....

    スマートフォンが部品ではなく一体型である場合、以下のようなシナリオが発生する可能性があります：

    • ユーザーにとって、明明は画面だけが壊れたのに、スマートフォン全体を交換する必要があります...
    • スマートフォンメーカーにとって、より多くの方向を把握する必要があり、研究開発圧力が倍増し、投入を拡大せざるを得ません。会社のアーキテクチャが適切でなく、決定権が過度に中央に集まっている場合、研究開発部門の発展を阻害することになります。

    コンピュータは現実世界の映射と見なすことができ、C++にも必然的にこのような問題が存在します。そのため、エンジニアは常にプログラムを**モジュール化**し、特定の機能の集合を**ライブラリ（Library）**にカプセル化します。これによるメリットは以下の通りです：

    • エンジニアリングの開発と維持の圧力を各ライブラリに分散させ、開発チームの各人の負担を大幅に軽減できます。
    • 超大規模なエンジニアリングでは、ライブラリの依存関係を分析することでコンパイル時間を大幅に短縮できます。
    • ライブラリを使用してプログラムにプラグインを拡張することもできます。

    ライブラリについては、筆者の経験が浅く、使い方しか知らないため明確に説明できません。しかしここに非常に良いリポジトリがあり、必ず助けになるでしょう：

    • https://github.com/robotology/how-to-export-cpp-library

    コーディング規範¶

    チーム協力では、相互の認知負担を軽減するため、チームメンバーに特定のコーディング規範に従うことを要求することが多いです。例えば：

    • Googleコーディング規範：https://google.github.io/styleguide/cppguide.html
    • GNUコーディング規範：https://www.gnu.org/prep/standards/standards.html
    • LLVMコーディング規範：https://llvm.org/docs/CodingStandards.html
    • Linuxカーネルコーディング規範：https://www.kernel.org/doc/Documentation/process/coding-style.rst
    • Qt APIスタイル：https://doc.qt.io/archives/qq/qq13-apis.html

    各チームのコーディングスタイルの要求は異なる可能性があるため、読者は「入乡随俗」する必要があります。丑いコードには以下の2種類があります：

    • 規範に従わないコード
    • 規範が統一されていないコード
