    パーティクルシステム（Particle System）¶

    パーティクルシステム（Particle System）とは、3Dコンピュータグラフィックスにおいて特定の曖昧な現象をシミュレートする技術であり、他の伝統的なレンダリング技術ではリアルな物理運動法則を実現しにくい現象を対象とする。パーティクルシステムでよくシミュレートされる現象には、火、爆発、煙、水流、火花、落葉、雲、霧、雪、塵、流星の尾跡、あるいは発光軌跡のような抽象的な視覚効果などがある。

    《百度百科》— 粒子系统

    原理¶

    パーティクルシステムは主に 大量の運動する オブジェクトをレンダリングするために使用され、その核心的なワークフローは複雑ではない。グラフィックスAPIに慣れている方なら、GPUでオブジェクトを描画するにはDrawCallを呼び出す必要があることを知っているだろう。パーティクルシステムには非常に多くの微小なパーティクルが存在するため、通常の方法は次のようになる：

    for(int i = 0; i < particles.num(); i++){
    drawParticle(particles[i]);
}

    この方法で確かに効果は得られるが、大量のDrawCallが呼び出され、かつパーティクル間に多くの重複データが存在するため、パーティクルシステムのレンダリングコストが非常に高くなり、描画可能なパーティクル数が非常に限られてしまう。

    パーティクルデータを最大限に再利用し、DrawCallを削減するために、多くの人が思いつくだろう—— インスタンシング（Instancing）

    インスタンシングの概念と使用方法については、以下を参照：

    • Learn OpenGL - Instancing

    インスタンシングにより、パーティクルシステムのDrawCallを統合し、パーティクル間の同じデータを再利用することができる。

    上記の概念を理解することで、パーティクルシステムは単に インスタンシングレンダリングを使用するワークフロー であることがわかる。この視点からパーティクル効果を制作する方法を考えると、次の点に注目する必要がある：

    • パーティクルシステムに必要なインスタンスデータ（Instance Data）を如何に構築するか。
    • インスタンスデータを如何に利用してパーティクル効果をレンダリングするか。

    この2つの角度から考えると、パーティクルシステムのワークパイプラインを容易に構築できるはずだ。以下では主にアーキテクチャの観点から、パーティクルシステムの詳細について説明する：

    単純なパーティクルは、次のようなデータ構造を使用する可能性がある：

    struct Particle{        //パーティクルの属性構造 
    vec3 position;
    vec3 rotation;
    float size;
    float age;
    //...
}

    ほとんどのパーティクルシステムのアーキテクチャでは、 パーティクルエミッタ（Particle Emitter） と呼ばれる構造が使用される。これはデータを格納する パーティクルプール（Particle Pool） を維持し、パーティクルの 生成（Spawn） 、 更新（Update） 、 回収（Recycle） を担当する。 パーティクルレンダラー（Particle Renderer） を使用してパーティクルプール内のデータをレンダリングすることで、パーティクル効果が得られる。このプロセスは次のように表現できる：

    class ParticleEmitter{
protected:
    void Tick() override{
        Spawn();                //生成段階:新しいパーティクルを作成
        UpdateAndRecycle();     //更新段階:各パーティクルの状態データを更新し、死亡したパーティクルを回収
        Render();               //レンダリング段階:パーティクルレンダラーを使用してパーティクル効果をレンダリング
    }
private:
    vector<Particle> mParticlePool;
    ParticleRenderer mParticleRenderer;
};

    パーティクルプール¶

    コンピュータのメモリリソースは有限であるため、パーティクルシステムは プログラムの実行中にパーティクルプールが占めるメモリが常に膨張し続けない ことを保証する必要がある。この問題を回避するため、パーティクルシステムは通常次の手段を講じる：

    • パーティクルの発射数を制限する。
    • パーティクルにライフサイクルを持たせ、ライフサイクルを超えたパーティクルを及时に回収する。

    これにより、パーティクルプールのメモリ最適化の基礎が提供される：

    • パーティクルの発射数とライフサイクルが既知であれば、現在のコンピュータの最大フレームレートを考慮することで、当該エミッタの最大パーティクル数を容易に推定できる。この数のメモリは通常、エミッタの初期化時にパーティクルプールに割り当てられ、パーティクルプールのメモリ再割り当てによるオーバーヘッドを回避する。
    • パーティクルプールが並列回収を可能にするため（配列から要素を削除する際に後方の要素を移動して埋める必要を回避する）、通常は同じサイズの2つのパーティクルプールを交互に反復処理する。

    パーティクルを更新し回収する場合、次のようなコードを記述する可能性がある：

    vector<Particle> ParticlePool;
ParticlePool.reserve(10000);            //10000個のパーティクルデータを格納できるメモリを事前に割り当てる

int index = -1;
for(int i = 0; i < ParticlePool.size(); i++){
    if(ParticlePool[i].isAlive()){
        index++;
        ParticlePool[index] = ParticlePool[i];
        ParticlePool[index].position = ...;
        ParticlePool[index].size = ...;
        ...;
    }
}
ParticlePool.reseize(index);

    このロジックの時間複雑度はO(n)である。さらに最適化するためにforループを並列処理しようとしても、上記のコード構造では不可能である。その理由は次の通り：

    • 内部のループロジックが外部の共有変数indexに対して読み書きを行う。
    • ParticlePoolの異なる領域に同時に読み書きを行うため、並列処理では実行順序が乱れてデータが混乱する可能性がある。

    この問題を解決するため、通常は2つのParticlePoolを交互に使用し、ローカルスレッド内で原子操作を使用してindexを読み書きする。そのため、ParticleEmitterの構造コードは次のように変更される：

    class ParticleEmitter{
protected:
    void InitPool(){
        mParticlePool[0].reserve(...);
        mParticlePool[1].reserve(...);
        mCurrentPoolIndex = 0;
        mNextPoolIndex = 1;
        mCurrentNumOfParticle = 0;
    }
    void Tick() override{
        Spawn();                
        UpdateAndRecycle();     
        Render();               
    }
private:
    vector<Particle> mParticlePool[2];
    int mCurrentPoolIndex;
    int mNextPoolIndex;
    int mCurrentNumOfParticle;

    ParticleRenderer mParticleRenderer;
};

    生成段階¶

    パーティクルの生成段階では主に、新しいパーティクルを生成してパーティクルプールに格納し、初期化する。このプロセスは次のように表現できる：

    void Spwan(){ 
    SpwanPerFrame(mParticlePool[mCurrentPoolIndex],mCurrentNumOfParticle,100);          //毎フレーム100個のパーティクルを生成
}

// 発射メカニズム カスタマイズ可能
void SpwanPerFrame(vector<Particle>& ParticlePool,int& NumOfParticle, int NumOfNewParticle){
    for(int i = 0; i < NumOfNewParticle ; i++ ){            //NumOfNewParticleは新規パーティクルの数
        Particle& NewParticle =  ParticlePool[NumOfParticle];   
        NumOfParticle++;
        InitializeParticle(NewParticle);
    }
}

// 初期化メカニズム カスタマイズ可能
void InitializeParticle(Particle& particle){
    particle.position = vec3(0.0f,0.0f,0.0f);
    //particle...
}

    ここで注意が必要なのは、Spawn関数は毎フレーム呼び出されることである。エミッタには 毎フレーム 固定数を発射するメカニズムだけでなく、 毎秒 「固定」数を発射するメカニズムも存在する。しかし、システム環境によってゲームの毎秒のフレーム数は予測不可能であるため、このような 時間帯に基づいて発射数を決定するメカニズム では、パーティクル数を正確に制御することは困難である。

    更新回収段階¶

    この段階の疑似コードは次のように表現できる：

    void UpdateAndRecycle(){    
    int IndexOfNextBuffer = -1;             //初期インデックス
    for_each_thread(int i = 0 ; i < mCurrentNumOfParticle ; i++){       //並列for
        const Particle& CurrentParticle = mParticlePool[mCurrentPoolIndex][i];
        if(CurrentParticle.isActive()){ 
            int CurrentIndex = atomicAdd(IndexOfNextPool,1);            //原子操作を使用して外部共有変数を読み書き
            Particle& NextParticle = mParticlePool[mNextPoolIndex][CurrentIndex];
            UpdateParticleStatus(CurrentParticle,NextParticle);
        }
    }
    CurrentParticlesBufferSize = IndexOfNextBuffer; //現在生存しているパーティクル数を更新
    swap(mCurrentPoolIndex,mNextPoolIndex);         //現在のパーティクルプールのインデックスを交換
}

// パーティクル状態更新メカニズム カスタマイズ可能
void UpdateParticleStatus(const Particle& CurrentParticle, Particle& NextParticle){
    NextParticle.position = CurrentParticle.position;
    //NextParticle...
}

    描画段階¶

    描画自体はパーティクルのデータを利用してレンダリングするだけであり、その基本的なプロセスは次のように表現できる：

    void Render(){
    mParticleRenderer.BindAttribute("position",mParticlePool[mCurrentPoolIndex],offset0,stride0);
    mParticleRenderer.BindAttribute("color",mParticlePool[mCurrentPoolIndex],offset1,stride1);
    ...;
    mParticleRenderer.drawInstancing();
}

    この段階はパーティクルの本質を体現している：パーティクルは単なるデータの集合であり、パーティクルシステム（エミッタ）はこれらのデータを一括処理し、パーティクルレンダラーの 属性スロット にデータをバインドすることで、パーティクル効果のレンダリングを完了する。

    CPU VS GPU¶

    上記で述べたように、パーティクルシステムの本質はすべてパーティクルデータの集合を中心に処理することであり、主に次の2つに分類される：

    • 生成段階 と 更新回収段階 ：これらの段階は主にパーティクルデータを処理する。Niagaraは 視覚化スクリプト を提供してこれらの段階にカスタム操作を提供し、最終的にスクリプトは次のように実行される：
    • CPU：ノードを接続して生成されたC++コードは、Niagaraの仮想マシンで実行される。
    • GPU：Niagaraはノードグラフに基づいて、 NiagaraHlslTranslator を使用して対応する HLSL コードに翻訳し、 ComputerShader から呼び出す。
    • 描画段階 ：CPUパーティクルであれGPUパーティクルであれ、同じレンダラーを使用できる。違いは CPUパーティクルはデータをGPUにアップロードする必要があるのに対し、GPUパーティクルのデータは元々GPUに存在するため、転送が不要 であることである。

    上記のプロセスは論理的に大きな違いはないが、GPUパーティクルの回収には注意が必要である。GPUパーティクルはComputeShaderを呼び出して 並列 に各パーティクルを処理するが、更新回収段階ではデータの再配置が必要になる。GPUが効率的に並列処理できるのは、各ブランチのデータが互いに独立して影響し合わないためである。しかし、GPUパーティクルの回収を実現するには、この規則を「打破」する必要がある。現在、この効果を達成する主な方法は次の2つである：

    • グラフィックスレンダリングパイプライン：ラスタライゼーションを無効にし、TransformFeedback（OpenGL）/ Stream Output（DX）、Geometry Shaderで死亡したパーティクルを回収（提交しない）する。

    Geometry Shader自体は線形操作を伴う。このプロセスで不定数の新しい頂点が生成されるため、GPUがデータをメモリに書き込む際には必ずロックと再配置が行われる。これが、TransformFeedbackやStream Outputを使用してGPUパーティクルを制作する人がいる理由であり、当然ながらゲームでGSをできるだけ回避する必要がある理由でもある。ちなみに、Stream OutputはDXの正規の機能であるが、TransformFeedbackはKhronosでの待遇はあまり良くない。Vulkanには公式のサポートさえ提供されておらず、Metalには対応する機能のAPIすら存在しない。

    • 汎用計算パイプライン：SSBO Atomic：ハードウェアの更新に伴い、現在の高バージョンのレンダリングドライバはSSBO（Shader Storage Buffer Object）をサポートするようになっている。ここで注目すべき点は、SSBOがAtomic操作をサポートすることである。これにより、CSでパーティクルを並列処理し、Atomic操作を使用してパーティクルデータを再配置（上記の疑似コードのNewIndex）することができる。新しいパーティクルデータについては、別の特性である間接レンダリング（Indirect Draw）を使用することで、GPU上のデータを直接使用してDrawCallを呼び出すことができる。これにより、CPUとGPU間のパーティクル転送を完全に回避できる。以下に簡易的なGLSLコードを提供する：
    layout (local_size_x = LOCAL_SIZE) in;
struct Particle {
    vec3 position;
    vec3 rotation;
    vec3 scaling;
    vec3 velocity;
    float life;
};
layout(std140,binding = 0) buffer InputParticlesBuffer{
    Particle inputParticles[PARTICLE_MAX_SIZE];
};
layout(std140,binding = 1) buffer OutputParticlesBuffer{
    Particle outputParticles[PARTICLE_MAX_SIZE];
};
layout(std140,binding = 2) buffer ParticleRunContext{
  int inputCounter;           //初期値は現在のパーティクル数
  int outputCounter;          //初期値は-1
  float duration;
  float lifetime;
};

#define inID  gl_GlobalInvocationID.x
#define inParticle inputParticles[inID]

void main(){                                              //注意：GPUの並列処理は無秩序である
    if(inID >= inputCounter||inParticle.life>lifetime)        //ここではステップ関数stepを使用して最適化可能
        return;
    uint outID = atomicAdd(outputCounter,1);              //atomicAddはGLSLの原生関数だが、操作対象はSSBOから取得する必要がある
    outputParticles[outID].life = inParticle.life + duration;
}

    シェーダーストレージバッファオブジェクト（ Shader Storage Buffer Object ） は、読み書き可能なバッファデータを提供するために使用される。

    その使用方法はUniformBufferとほぼ同じであるが、主な違いは次の通りである：

    • Storage Bufferは非常に大きなビデオメモリを申請できる ： OpenGL規格はUniform Bufferのサイズが 16KB に達することを保証するが、Storage Bufferは 128MB に達することができる。
    • Storage Bufferは書き込み可能で、原子（Atomic）操作をサポートする ：Storage Bufferの読み書きは順序が乱れる可能性があるため、同期を保証するためにメモリバリアを追加する必要があることが多い。
    • Storage Bufferは可変ストレージをサポートする ：これは、Storage Buffer内のブロックで無境界配列（int arr[];のような）を定義できることを意味する。シェーダー内でarr.lengthを使用して配列の長さを取得できる。一方、Uniform Buffer内のブロックで配列を定義する場合は、配列のサイズを明確に指定する必要がある。
    • 同じ条件下で、SSBOのアクセスはUniform Bufferより遅い ：Storage Bufferは通常、バッファテクスチャと同様にアクセスされるのに対し、Uniform Bufferデータは内部のシェーダーアクセス可能なメモリを介して読み取られる。

    機能的には、Image Load Storeを介してアクセスする場合、SSBOはバッファテクスチャのより良いインターフェースと見なすことができる。

    OpenGLはAtomicCounter機能を提供しており、その本質はこの特性である。

    上記によりGPUパーティクルの回収は完了するが、実は深刻な問題も引き起こす——回収のたびにパーティクル数が変化するが、データはGPUに存在するため、CPUがDrawCallを呼び出す際にこのパラメータを知る必要がある。

    GPUからデータを読み戻すことは当然不可である。なぜなら、現代のグラフィックスAPIは命令キャッシュを使用してレンダリングを加速するため、ある時点でGPUの命令キャッシュには2フレーム以上の未処理命令が存在する可能性があるからである。データを読み戻す場合、現在の命令が即座に実行されることを保証する必要があり、つまりレンダリングスレッドをブロックしてデータの返却を待つ必要がある。この操作はエンジン全体にとって致命的な打撃であるが、幸いにも解決策が存在する。

    OpenGL4.0の更新では、新しい特性——Indirect Rendering（間接レンダリング、 Indirect Draw とも呼ばれる）が提供された。これにより、GPU上のデータを直接使用してDrawCallを呼び出すことができる。以下に公式の定義を示す：

    Indirect Rendering

    間接レンダリングでは、GPU上のデータを直接DrawCallのパラメータとして使用することができる。例えば、glDrawArraysのパラメータにはプリミティブタイプ、頂点数、開始頂点が含まれる。間接描画命令glDrawArraysIndirectを使用する場合、対応するパラメータはバッファオブジェクトから取得される。

    この機能はGPU->CPU->GPUの往復を回避するために設計された。GPUがレンダリングするパラメータを決定し、CPUが行うのはいつ描画命令を発行するか、およびその命令がどのPrimitiveを使用するかを決定するだけである。

    NiagaraのソースコードでIndirectを検索すると、関連する使用方法の定義を見つけることができる。その主な構造は以下に位置する：

    • NiagaraVertexFactories\Public\NiagaraDrawIndirect.h
    • Niagara\Private\NiagaraGPUInstanceCountManager.cpp

    优缺点¶

    • CPU パーティクル

    • 优点

      • CPU側で完全なゲーム環境にアクセスでき、他のパーティクルやゲームロジックとインタラクションを行うことができる。
      • 高いハードウェア構成を必要とせず、グラフィックスカードがプログラマブルパイプラインとインスタンシングレンダリングをサポートしていれば良い。

    • 缺点

      • CPU側でパーティクルデータを線形に反復処理する必要があり、CPUの性能消費が深刻である。
      • パーティクルデータはCPU側のメモリに存在するため、レンダリング時にパーティクルデータを一括してGPUにアップロードする必要がある。この転送プロセスの消費は極めて深刻である。

    • GPU パーティクル

    • 优点

      • パーティクルデータは全程GPU側で生成および処理され、CPUとGPU間のデータ転送が回避される。
      • GPU内の並列ユニットに依存してパーティクルデータを処理するため、パーティクル処理に必要な時間が大幅に短縮される。

    • 缺点

      • GPUパーティクルのデータはビデオメモリに存在するため、バウンディングボックスの境界をリアルタイムに計算することができない。そのため、GPUパーティクルには手動で固定境界を指定する必要がある。
      • ゲーム環境と良好にインタラクションすることができないが、深度、Scene Capture、距離場を使用して効果を近似することは可能である。
      • ハードウェア構成に一定の要求があり、CS、SSBO Atomic、Indirect Drawをサポートする必要がある（PC端末では独立したグラフィックスカードがあれば基本的に問題ないが、モバイル端末でのサポートは特に完善していない）。

    Niagara¶

    Unreal EngineのNiagaraシステムは非常に強力であり、その本質は プログラマブルなデータプロセッサ（CPUまたはGPU）とインスタンシングレンダラー を提供することである。このレベルから考えると、非常に多くの驚くべき効果を実現することができる。

    作用域¶

    大多数の記事ではここの作用域を「名前空間」と呼んでいる。確かに変数名を区別する役割を果たすが、開発者にとって更に重要なのはこれらの変数作用域が代表するライフサイクルである。

    Niagaraエディタでは、パラメータパネルを通じてこれらの作用域の変数に対して追加、削除、変更を行うことができる：

    • EngineProvided ：この作用域を使用する主な目的はエンジンから変数を読み取ることであり、常見的なものにDeltaTimeがある。

    • System Attribute ：単一のパーティクルシステムが持つ属性変数。

    • Emitter Attribute ：単一のパーティクルエミッタが持つ属性変数。

    底層核心—FNiagaraDataSet¶

    Niagara属性自体は単なるデータの集合であり、コード上で対応する構造は FNiagaraDataSet である（ User Expose を除く）。その簡易的な構造は以下の通りである：

    class FNiagaraDataSet{
    /** 次のTickで割り当て可能な空きIDのテーブル。 */
    TArray<int32> FreeIDsTable;

    /** FreeIDTable内の空きIDの数。 */
    int32 NumFreeIDs;

    /** 最後の実行で見られた最大ID。IDTableを縮小することを可能にする。 */
    int32 MaxUsedID;

    /** 新しいIDが取得されるときに使用するタグ。Tickごとに一意である必要がある。 */
    int32 IDAcquireTag;

    /** 最後のTickで生成されたIDのテーブル（インデックス部分のみ、取得タグはすべてIDAcquireTagである）。 */
    TArray<int32> SpawnedIDsTable;

    /** 次のTickで使用可能な空きIDのGPUバッファ。 */
    FRWBuffer GPUFreeIDs;

    /** GPUシミュレーションのために割り当てられたIDの数。 */
    uint32 GPUNumAllocatedIDs;

    /**
    実際のデータストレージ。これらはRTに直接渡され、読み取られる。
    これは事実上、このシミュレーションのためのバッファプールである。
    通常、これは2つまたは3つのエントリだけであり、BeginSimulate()で書き込み先の空きバッファを検索する。

    追加のバッファは、現在レンダリングスレッドによって使用されている場合、ここに存在する可能性がある。

        /** 現在のシミュレーション状態を含むバッファ。 */
    FNiagaraDataBuffer* CurrentData;

    /** 現在シミュレート中のバッファ。シミュレート中（PrepareForSimulateとEndSimulate呼び出しの間）にのみ有効である。*/
    FNiagaraDataBuffer* DestinationData;

    /* 最大インスタンス数は許可される最大インスタンス数である。 */
    uint32 MaxInstanceCount;
    /* 最大割り当て数は、丸めによりMaxInstanceCountより大きくなる可能性のある、割り当て可能な最大インスタンス数である。 */

    void FNiagaraEmitterInstance::Init(int32 InEmitterIdx, FNiagaraSystemInstanceID InSystemInstanceID){
    const int32 UpdateEventGeneratorCount = CachedEmitter->UpdateScriptProps.EventGenerators.Num();
    const int32 SpawnEventGeneratorCount = CachedEmitter->SpawnScriptProps.EventGenerators.Num();
    const int32 NumEvents = CachedEmitter->GetEventHandlers().Num();

    if (UpdateEventGeneratorCount || SpawnEventGeneratorCount || NumEvents)
    {
        EventInstanceData = MakeUnique<FEventInstanceData>();
        EventInstanceData->UpdateScriptEventDataSets.Empty(UpdateEventGeneratorCount);
        EventInstanceData->UpdateEventGeneratorIsSharedByIndex.SetNumZeroed(UpdateEventGeneratorCount);
        int32 UpdateEventGeneratorIndex = 0;
        for (const FNiagaraEventGeneratorProperties &GeneratorProps : CachedEmitter->UpdateScriptProps.EventGenerators)
        {
            FNiagaraDataSet *Set = ParentSystemInstance->CreateEventDataSet(EmitterHandle.GetIdName(), GeneratorProps.ID);
            Set->Init(&GeneratorProps.DataSetCompiledData);

            EventInstanceData->UpdateScriptEventDataSets.Add(Set);
            EventInstanceData->UpdateEventGeneratorIsSharedByIndex[UpdateEventGeneratorIndex] = CachedEmitter->IsEventGeneratorShared(GeneratorProps.ID);
            ++UpdateEventGeneratorIndex;
        }

        EventInstanceData->SpawnScriptEventDataSets.Empty(SpawnEventGeneratorCount);
        EventInstanceData->SpawnEventGeneratorIsSharedByIndex.SetNumZeroed(SpawnEventGeneratorCount);
        int32 SpawnEventGeneratorIndex = 0;
        for (const FNiagaraEventGeneratorProperties &GeneratorProps : CachedEmitter->SpawnScriptProps.EventGenerators)
        {
            FNiagaraDataSet *Set = ParentSystemInstance->CreateEventDataSet(EmitterHandle.GetIdName(), GeneratorProps.ID);
            Set->Init(&GeneratorProps.DataSetCompiledData);

            EventInstanceData->SpawnScriptEventDataSets.Add(Set);
            EventInstanceData->SpawnEventGeneratorIsSharedByIndex[SpawnEventGeneratorIndex] = CachedEmitter->IsEventGeneratorShared(GeneratorProps.ID);
            ++SpawnEventGeneratorIndex;
        }

        EventInstanceData->EventExecContexts.SetNum(NumEvents);
        EventInstanceData->EventExecCountBindings.SetNum(NumEvents);

        for (int32 i = 0; i < NumEvents; i++)
        {
            ensure(CachedEmitter->GetEventHandlers()[i].DataSetAccessSynchronized());

            UNiagaraScript* EventScript = CachedEmitter->GetEventHandlers()[i].Script;

            //This is cpu explicitly? Are we doing event handlers on GPU?
            EventInstanceData->EventExecContexts[i].Init(EventScript, ENiagaraSimTarget::CPUSim);
            EventInstanceData->EventExecCountBindings[i].Init(EventInstanceData->EventExecContexts[i].Parameters, SYS_PARAM_ENGINE_EXEC_COUNT);
        }
    }
}

    事件的处理时机¶

    在FNiagaraEmitterInstance::Tick中，有如下代码：

    void FNiagaraEmitterInstance::Tick(float DeltaSeconds)
{
    //...
    if (EventInstanceData.IsValid())
    {
        // イベントのための生成数とソースデータセットを設定する。システムは、受信元のエミッタの後に実行されることを保証するため、ソースがこのTickで計算したデータバッファを使用することができる。
        const int32 NumEventHandlers = CachedEmitter->GetEventHandlers().Num();
        EventInstanceData->EventSpawnTotal = 0;
        for (int32 i = 0; i < NumEventHandlers; i++)
        {
            const FNiagaraEventScriptProperties& EventHandlerProps = CachedEmitter->GetEventHandlers()[i];
            FNiagaraEventHandlingInfo& Info = EventInstanceData->EventHandlingInfo[i];

            Info.TotalSpawnCount = 0;//This was being done every frame but should be done in init?
            Info.SpawnCounts.Reset();

            //TODO: We can move this lookup into the init and just store a ptr to the other set?
            if (FNiagaraDataSet* EventSet = ParentSystemInstance->GetEventDataSet(Info.SourceEmitterName, EventHandlerProps.SourceEventName))
            {
                Info.SetEventData(&EventSet->GetCurrentDataChecked());
                uint32 EventSpawnNum = CalculateEventSpawnCount(EventHandlerProps, Info.SpawnCounts, EventSet);

    使用建议¶

    特效在中追求艺术效果的同时，还必须保证：

    • 粒子系统设置正确的包围盒和可延展性，否则在场景中可能就会出现 粒子莫名其妙消失 的问题
    • 严格管控Spawn特效的生命周期，避免Pool Method 与生命周期处理操作（预裁剪，可延展性剔除，AutoDestroy）出现冲突。

    关于优化，需要了解：

    • 如何缩减粒子发射器的数量？

    理想的情况是：只要两个发射器所使用的渲染器参数是完全一致的，那么它们就应该使用同一个发射器

    因为发射器中的一个渲染器对应一条图形渲染管线，粒子系统本质上是处理图形渲染管线所需的实例化数据

    多一个发射器就会多一份渲染数据，并且要多维护一个粒子缓冲区

    如果只是想调整粒子的运动机制，可以通过自定义Module的方式进行扩展

    • 如何界定该使用CPU粒子还是GPU粒子？

    CPU粒子可以动态地计算包围盒边界，但它只适用于少量的粒子渲染，

    GPU粒子可用来渲染大量的粒子数据，但必须为其设置 准确的包围盒边界

    界定的分割线主要是粒子数量，如果在千、万级别的粒子数量，必须使用GPU粒子

    少量粒子，比如几个，建议使用CPU粒子

    • 为了追求效果，不得以使用CPU粒子时，主要需要考虑两点：

    • CPU粒子的执行是串行的，随着粒子系统复杂度的增加，其性能损耗会成倍增加。

    • CPU粒子在渲染线程中的性能瓶颈，主要是粒子数据的传输（带宽有限），这也是为什么它并不适用于大量粒子的绘制。

    • 粒子系统的工作方式不同于常规的Pipeline，如果是放置在场景中的单个物件，你需要考虑使用Actor（Game Object），而不是粒子系统。

    • 除了控制粒子系统的复杂度和数量，还可以通过其他手段来降低粒子的性能消耗：
    • 避免粒子拥挤，减少Overdraw
    • 限制透明度
