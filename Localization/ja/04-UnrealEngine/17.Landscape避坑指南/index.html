    Landscape 落とし穴回避ガイド¶

    概要¶

    地形（Landscape）は現代ゲームにおける基礎的なグラフィック要素であるが、グラフィックエンジンの複雑さが高まり、開発チームがますます「若年化」する中で、効果の実装とエディタレベルの使用にのみ焦点を当て、重要な細部を無視すると、大きな問題を引き起こす可能性がある。そこで本記事ではこれらの点について紹介する。

    ほとんどのグラフィックエンジンにおいて、最も多く使用されるグラフィック要素は間違いなく —— スタティックメッシュ（Static Mesh）である。スタティックメッシュは頂点ジオメトリデータ（空間座標、UV、法線...）とマテリアルテクスチャを組み合わせてグラフィック効果を表現する：

    スタティックメッシュは現代ゲーム開発において極めて重要な地位を占め、既にゲーム世界のジオメトリを構築する基礎ユニットとなっている。専門的なモデリングソフト（3dsMax、Maya、Blender、Zbrushなど）はデザイナーに大きな利便性と自由度を提供し、想定したグラフィック効果を迅速にデザインできるようにしている。

    これに対し、地形は比較的特殊なグラフィック要素であり、スタティックメッシュのように直接三角形頂点データを使用して表現するのではなく、ハイトマップに依存している：

    この画像は https://manticorp.github.io/unrealheightmap で生成されたものである。

    ハイトマップの各ピクセルは実際の頂点座標に対応し、マッピング関係は以下の通り：

    • ピクセル座標（XY）> 頂点水平座標（XY）
    • ピクセルグレースケール値（Grayscale） > 頂点高さ（Z）

    ハイトマップは2次元数値配列と見なすことができ、基本要素の型は通常16ビット符号なし整数であり、対応するC++構造体は以下の通り：

    uint16_t HeightMap[Height][Width];

    実際の変換規則はソフトウェアによって微妙な差異が存在する可能性がある。Unreal Engineが採用する基本単位は センチメートル（cm） であり、その変換規則は以下の通り：

    • 頂点水平座標は直接ピクセル座標から変換される。何もスケーリングを行わない場合、UE地形の水平方向の最小表現精度は 1 cm である。
    • ピクセルグレースケールは16ビット符号なし整数として格納される。これは65536個の異なる高さレベルを区別できることを意味する。UEはこれを直接cmにマッピングするのではなく、 [-256.0, 255.992] の浮動小数点範囲に再マッピング する。つまり、何もスケーリングを行わない場合、UE地形の垂直方向が表現できる高さ範囲は -256.0 cm ~ 255.992 cm であり、高さが表現できる最小精度は 0.0078125 cm である。

    以上を踏まえ、一部の方は以下のような疑問を抱くのではないだろうか：

    • 同じグラフィック効果を実現するために、スタティックメッシュは非常に高い精度と自由度を持つのに、地形を使用すると非常に多くの制限が存在するのに、なぜ地形を使用する必要があるのか？

    実際、地形の使用は本質的に シーン規模 と 高精度 のトレードオフである。

    まず地形の欠点について説明する：

    • 水平方向の精度が限られる ：例えば、UE5 非WPマップ がサポートするハイトマップの最大サイズは 8129 である。何もスケーリングを行わない場合、これは水平幅 81.29 m を表現できることを意味する。より大きな領域範囲を表現したい場合、例えば100倍にストレッチすると 66.08km の領域を表現できるが、この時水平方向の最小表現精度は 1m になる。つまり 1m 未満のジオメトリ詳細はすべて失われる。
    • 高さの表現範囲が限られる ：何もスケーリングを行わない場合、高さの表現範囲は -256.0 cm ~ 255.992 cm である。 2000m の高山を表現したい場合、高さを元の1000倍にストレッチする必要がある。これは高さの最小表現精度が 7.8125cm になることを意味し、地形の衝突計算に少なくとも7cmの計算誤差が生じる。
    • トポロジ構造の単一性 ：地形は本質的に「連続的な高さ場グリッド」であり、「単一層面の起伏」のみをサポートし、スタティックメッシュの複雑なトポロジ（空中プラットフォーム、地形交差、地下洞窟など）を実現することはできない。
    • 編集粒度が粗い ：地形編集は「ブラシ描画」（抬升、降低、平滑など）に依存するため、スタティックメッシュのように「頂点レベル編集」で各凸凹を精密に制御することは困難である。
    • 協働開発の複雑さ ：ハイトマップ、ウェイトマップは単一ファイルであり、複数人が同時に編集するとデータ上書きが発生するため、バージョン管理ツールで厳密に管理する必要がある。

    しかしこれらの欠点が存在するにもかかわらず、 地形は現在のハードウェアレベルにおいて、大規模シーンの唯一の解決策 である。

    例えば、 1km² のシーンを構築したい場合、グリッド平面で敷設し、平均ジオメトリ精度を 10cm × 10cm に保つとする。これは既に低い精度であるが、依然として 1億（10000×10000） の三角形頂点が必要である。UE5スタティックメッシュの1頂点の占有容量は通常 28バイト（位置 : 12 + 接線X : 4 + 接線Z : 4 + UV : 8）であるため、地形グリッド全体の未圧縮空間占有容量は約以下の通り：

    • 28 x 10000 x 10000 ÷ 1024³ ≈ 2.61 GB

    これはジオメトリデータのみである。 平铺贴图（Tiled Texture） を使用しない場合、 10cm のテクセル精度では画面効果を保証できず、ボケやモザイクが必然的に発生する。「近距離視覚の鮮明さ」を保証したい場合（例えば 1cm×1cm の地面が1つのテクセルに対応する）、テクセルの総量は 100億 に達する。4つのチャンネル（ARGB_8888）で色を表現する場合、未圧縮空間占有容量は約以下の通り：

    • 4 x 100000 x 100000 ÷ 1024³ ≈ 37.25 GB

    これはたった 1km² のシーンに過ぎない。

    実際、筆者が近年接触した多くのチーム（ゲーム業界に限らない）は、グラフィックシーンのデータ規模に深い認識がない。特にプランナー/プロダクトの視点では、オープンシーンは単に十分な要素でシーンを大きくするだけのものと考えている。

    このような背景下で、少し大きなシーンを構築したい場合、地形はほぼ必然的な選択である。上記の欠点に加え、地形には無視できない多くの長所が存在する：

    • メモリ ：地形の各頂点は4バイト（RGチャンネルが高さを格納、BAチャンネルが圧縮された法線を格納）のみで済むが、スタティックメッシュのメモリ占有容量は通常地形の6～7倍である。
    • テクスチャ ：地形は「高さに依存しないワールド空間マッピング」であり、地形の起伏（高くする、平らにする、山を作るなど）をどのように変更しても、テクスチャの平铺贴り精度は常に変わらない。そのため平铺贴图の使用が非常に便利であるが、スタティックメッシュは困難である。なぜならモデル形状を変更する（例えば平坦な地面を斜面に変更する）と、テクスチャがモデルに伴ってストレッチ変形するからである。此外、スタティックメッシュの詳細は主にテクスチャとUV精度に依存するが、地形は平铺贴图に複数のテクスチャ（詳細テクスチャ、傾斜テクスチャなど）を重ねて階層効果を改善することができる。
    • LOD ：地形の LOD は「高さ場に基づく動的簡略化」であり、GPUは自動的にMipmapを通じて低解像度のテクスチャMip層に切り替える。遠くのレンダリング効率を保証すると同時に、テクスチャのストレッチを回避する。スタティックメッシュのLODは各レベルに独立した低精度モデルを制作する必要がある。
    • 衝突 ：地形は高さ場衝突体（Heightfield Collider）を生成して使用し、破壊可能をサポートする。そのデータ構造の特性により、衝突計算効率はグリッド体衝突よりはるかに高く、隙間が存在しないため、衝突貫通問題における防護安全性はスタティックメッシュよりはるかに優れている。
    • ワークフロー ：ゲームエンジンにおいて、地形は基本的なグラフィックキャリアと見なされ、エンジン内には地形を中心に非常に多くのツールとプロセス（植生システム、地形附着物のプロシージャル生成、光影ベイクなど）が構築されている。

    Landscapeの使用については、公式ドキュメントに詳細な紹介があり、地形の概念、LODと衝突の管理がよく説明されている：

    • https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-outdoor-terrain-in-unreal-engine

    地形の原理については、以下の非常に詳細な分析記事がある：

    • 虚幻引擎地形系统原理机制源码剖析 - MarsZhou：https://zhuanlan.zhihu.com/p/668278748

    計画¶

    実際のゲームプロジェクトにとって、地形の実装原理とツールの使用方法を知るだけでは往往にして不十分であり、早期設計段階でいくつかの計画を策定する必要がある。

    シーン規模を明確にする¶

    シーンの大きさはゲーム内容の体量を一定程度決定する。UE標準の小白人を例にとると、そのデフォルト移動速度は 600cm/s であり、 1000m の距離を移動するには2分46秒かかる。これに実際のゲーム内容を組み合わせて、おおよそ必要なシーン規模を評価する。

    シーンサイズが 1km² を超え、大量のGameObjectを持つ場合、 World Partition を使用してシーンのSteamingを組織することを検討すべきである。

    注意が必要なのは、遊技可能な領域が非常に大きいシーン（例えば 64km²）を構築したい場合、決して1つの地形で entire シーンを構築しないことである。過大なシーン規模はアセット管理、マップ編集、玩法と关卡設計の複雑さを大幅に高め、プロジェクトのイテレーション速度を深刻に低下させる。

    UE WP マップが現在サポートする最大地形サイズは 65281 であるが、個人の提案としては単一地形のサイズを 4km² を超えないようにする。独立したサブ关卡でゲーム内容のイテレーションを行い、海面、河川または山脈などの要素を通じてサブマップを拼接する主マップを専門に設置する。具体的には以下のように：

    解像度を確定する¶

    単一地形の規模を確定した後、地形が表現する最小ジオメトリ精度を確定する必要がある。水平方向は通常 1m の精度でRPGプロジェクトのニーズを満たすことができる。地表詳細を増やしたい場合、以下の方案を通じて実現することができる：

    • 法線贴图（Normal Map） ：表面法線方向を修改して光照反射に影響を与え、平坦な地形に凹凸の詳細を持たせる。
    • 視差遮蔽映射（Parallax Occlusion Mapping） ：ピクセルの「仮想深度オフセット」を計算することで、テクスチャに実際の厚みを持たせ、法線贴图よりも立体感に優れる。
    • 位移贴图（Displacement Mapping） ：Naniteと细分曲面技術を借りて、位移贴图を通じて真正のジオメトリ凸起（ピクセルレベルの高さを修改）を実現する。
    • 地表附着物 ：地形表面にスタティックメッシュと贴花を放置して詳細を補充する。衝突体が性能に与える影響に注意が必要である。

    垂直方向の纵深は最初から確定する必要がある。大量の内容をイテレーションした後にこの問題に気づき、修改するのは少し面倒である。此外、衝突精度を保証するため、Z軸を過度にストレッチしてはならない。高い山脈については、スタティックメッシュを使用して填充することを考慮すべきである。

    ストリーミングプロキシ、コンポーネントとセクションの数量のバランスを取る¶

    UE地形が実際に対応する核心構造は ALandscape であり、整个地形の全局データとコンポーネント階層構造を管理する責任を負う。ハイトマップ、ウェイトマップなどの基礎アセットを保有し、地形の整体属性（物理设置、LOD全局参数など）を控制する。

    ALandscape の職責を划分し、より小さな粒度のLOD管理、可视性判断、DrawCall、衝突検出とマテリアル管理を持たせるため、地形システムは 地形コンポーネント（ULandscapeComponent） と セクション（Section） の概念を提出した。

    仮に現在すべての小粒度機能を地形コンポーネントに託し、暂时セクション機制を導入せず、 2017×2017 解像度のハイトマップで 4km² のシーンを構築する場合、コンポーネント划分はジレンマに直面する：

    • コンポーネント数量が少ない場合（例えば1つのコンポーネントが4km²を覆盖する）：単一コンポーネントの頂点データ量が大きく、視錐台カリング時に「不可视区域」を精確にカリングできない。LOD切り替えは「整体切り替え」しかできず（例えば遠くの整体コンポーネントがLOD0からLOD3に切り替わり、詳細が明らかに失われる）、衝突計算も全量データを処理する必要があり、効率が低い。
    • コンポーネント数量が多い場合（例えば100個のコンポーネントが4km²を覆盖する）：精確なカリングとLOD切り替えは可能だが、各コンポーネントの调度（加载/卸载）、DrawCall提交、衝突体筛选に追加オーバーヘッドが発生し、逆にフレームレートを低下させる。

    この矛盾を解決するため、UE地形システムは セクション（Section） 概念を導入した。その位置付けはコンポーネントの更なる划分ではなく、コンポーネント内部で 細粒度のDrawCall、LOD、カリング、衝突 機能を承担し、コンポーネント職責の合併を許可することで、 コンポーネント数量の削減 と 細粒度管理 のバランスを実現する。

    ストリーミングプロキシ（ALandscapeStreamingProxy） はUE5 World Partitionが導入した新概念である。World Partitionのストリーミングの最小単位はActorであり、Componentではないため、ストリーミングプロキシの目的は元々ALandscapeに掛かっていた一連のULandscapeComponentを、区域划分に応じて不同のストリーミングプロキシに划分することである。1つのストリーミングプロキシは1つまたは複数の地形コンポーネントを包含することができ、ストリーミングプロキシの划分はプロジェクト自身が望むストリーミング粒度に依存する。

    注目すべき点は、ストリーミングプロキシの出現によりセクションの地位が少し揺らいだことである。なぜなら早期プロジェクトで地形を使用する場合、地形コンポーネントは一般的に完全に加载され、カリングを通じて最適化を行うため、セクションを使用してコンポーネントを削減することができたからである。

    しかし現在World PartitionのStreamingがあり、HLODの合併を組み合わせることで、地形コンポーネント数量を大幅に削減できるだけでなく、合併後のジオメトリとテクスチャデータを大幅に最適化することができる。そのためWPマップにおいて、地形セクションの価値は微々たるものと言える。

    以上を踏まえ、地形に関連するいくつかの構造の関係は主に以下の通り：

    階層オブジェクト 核心職責 依存関係
    地形（ALandscape） 全局データ（ハイトマップ/ウェイトマップ）の管理、统一调度 1つまたは複数のストリーミングプロキシを包含する（WPマップ）
    ストリーミングプロキシ（StreamingProxy） WPストリーミングの最小単位、地形コンポーネントを承载する 1つまたは複数の地形コンポーネントを包含する
    地形コンポーネント（LandscapeComponent） 局部データ副本（例えば某块100m×100mの区域）とマテリアル（图层解析、物理マテリアル、挖孔）を管理する 内部に複数のセクションを划分可能
    セクション（Section） DrawCall、LOD、精细カリング、衝突計算を承担する 単一地形コンポーネントに隷属する

    シーン生態構造を確定する¶

    地形はハイトマップとウェイトマップの組み合わせからなる。ハイトマップは地形のジオメトリ形状を描述する責任を負い、ウェイトマップは地形のマテリアル表現に使用される。

    大多数の美术人员は图层の管理についていくつかの誤解を抱いている：

    • マテリアル効果と图层を一対一で绑定する

    実際のワークフローにおいて、美术人员は通常効果のニーズに応じて图层を追加する。例えば一片の草地が欲しい場合、Grass图层を追加し、一片の雪地が欲しい場合、Snow图层を追加する。その後Gravel（砾石）、Dirt（泥土）、Rock（岩石）、Mud（泥浆）、Water（水）、Path（道路）...と続く。

    別のスタイルのシーンに过渡するために、素材と图层を继续追加する...

    この誤った做法は以下の問題に直面する：

    • 効果が制限される ：地形ウェイト图层の数量に上限が存在する。UE4では上限が8であり、UE5では上限が16になった。
    • 性能が悪い ：过多のウェイトマップサンプリングは地形マテリアルの描画性能を严重に低下させる。

    正しい做法はウェイト图层と地形マテリアルの関係を理清することである：

    • ウェイト图层とマテリアルは一対一の関係ではない。地形マテリアルは本質的にウェイトデータの解析器（Resolver）として機能する。1つの地形（ALandscape）は1つのマテリアルのみを許可するのではなく、マテリアル管理の最小粒度は地形コンポーネント（ULandscapeComponent）である。

    例えばこのような効果を実現する場合、各数字区域に特定の色、植生および物理マテリアルがある。以前の誤った做法ではこの効果に4つの地形图层が必要であるが、ここでは実際に1つしか使用されていない。ただし各地形コンポーネントが自身のマテリアルを持っている：

    UE5の非WPマップは地形コンポーネントの編集入口を暴露していない。編集したい場合はC++から入手する必要がある。WPマップのALandscapeStreamingProxyも特化属性パネルを通じて、批量的にコンポーネント属性を管理する。これが误用を生じやすい部分的な原因でもある。

    そのため、地形图层管理時にはマテリアル効果に基づいて图层を划分すべきではなく、地形の生態構造から划分すべきである。不同の生態群落は不同のマテリアルを使用して图层を解析することで、图层数量の泛滥を回避すると同時に、地形マテリアルの渲染オーバーヘッドを最適化することができる。

    このプロセスは使用門檻が高いため、エンジンに相应的なツールチェーンを開発してイテレーションプロセスを簡素化する必要がある。

    LOD、Nanite、RVT、HLOD¶

    地形のLOD策略はALandscapeの属性パネルで调整することができる。

    目前UE5はNanite地形をサポートしており、より高いカリング効率とジオメトリ詳細を持つ。VSMを組み合わせると、中高端ハードウェアにおける描画性能は通常Naniteの方がLODより優れている。

    Naniteのジオメトリ処理パスとRVTのサンプリングパスは互換性がないため、通常NaniteグリッドはRVTの書き込みをサポートしない。しかし地形は依然として原始的なハイトマップとウェイトマップデータを保持しているため、エンジンは非Naniteの補助チャンネルを通じてRVT描画データを提交する：

    • https://dev.epicgames.com/documentation/en-us/unreal-engine/using-nanite-with-landscapes-in-unreal-engine

    UE5最新の版本は地形HLODの生成策略を调整し、逻辑は ULandscapeHLODBuilder に位于する。具体的な做法は以下の通り：

    • ALandscapeStreamingProxyが包含する所有の地形コンポーネントから、其中の1つのLODレベルを選択し、1つのULandscapeMeshProxyComponent（UStaticMeshComponentを継承）に合并する。

    个人的にはこの做法はあまり効率的ではないと感じる。なぜならストリーミングの粒度と合批の粒度を等しくするからである。例えば1つの地形コンポーネントブロックのサイズが100Mである場合、HLODがコンポーネントを合并できるようにするため、ストリーミングプロキシの範囲を200Mに設定する必要がある（つまり4つの地形コンポーネントを包含する）。これは地形ストリーミングのコストを显著に増加させる。1つのストリーミングプロキシが1つのコンポーネントのみを包含するように改修し、実際の合批をグリッド划分の粒度に基づいて行う方がよいはずである。

    地形のHLODマテリアルについては、テクスチャを重新烘培する必要はない。なぜなら実際のプロジェクトにおいて、通常地形にRVTを使用し、地形のRVTにSVTを开启して低レベルのMipLevelを存储するため、地形HLODマテリアルは直接ALandscapeで HLOD Material Override を指定することができるからである。

    そのため地形HLODのマテリアルはテクスチャ入力が不要で、直接RVTのSVTをサンプリングすればよい：

    RVTは地形に広く応用されている。例えば遠くの地表詳細（贴花、草皮...など）をRVTのSVTに烘培することで、HLODの远景マテリアル効果を保証することができる。

    高度をRVTに書き込むことは、一些特效を実現する際に非常に有用である。例えば：

    • 雨、積雪、水流：地形高度（海抜）と法線方向（傾斜）に基づいて、自然現象の効果分布を動的に控制する。
    • 足迹/踩踏效果：キャラクターが移動する際、接触点の地形位置に地形起伏に匹配する足迹を生成する。
    • 爆炸/冲击痕迹：爆炸冲击点が地形表面に地形輪郭に匹配する凹痕または焦痕を生成する。
    • 雾气/烟尘分布：地形高度と傾斜を利用して雾气濃度を控制し、山谷雾、爬坡雾などの効果を模拟する。
    • 地面湿润/干燥过渡：地形排水能力（傾斜）に基づいて雨后地面の干燥過程を模拟する。

    地形RVTにSVTを开启する步骤については、以下を参照することができる：

    • https://dev.epicgames.com/documentation/zh-cn/unreal-engine/runtime-virtual-texturing-in-unreal-engine

    注意が必要なのは、記事でRVT体积 细节（Details） 面板で 在编辑器中使用流送低mip（Use Streaming Low Mips in Editor） 属性を選択することが提到されているが、最新版本のエンジンではこの属性の名称が View In Editor に改修されている。必ずこれを勾选してください。否则编辑器下でRVTはSVTのデータを读取しない。

    底层接口¶

    これらを見て、「わお、地形にはこんなに多くの注意事项があるのか」と感じた方もいるだろう。しかし現在プロジェクトが既に落とし穴にハマっている場合、どうすればよいのか？慌てないで、救いの手はある！

    UE地形システムの调度と管理は複雑に見えるが、本質的には底层の数枚の贴图を处理するものである。UEのエディタを迂回して、直接相应的な图像を处理することができれば、自由度は非常に高くなる。

    ハイトマップとウェイトマップの管理は统一的に ULandscapeInfo に配置されており、以下のように获取することができる：

    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();

    UEにおけるハイトマップに対応する構造は EditLayers であり、UEは複数のハイトマップの叠加をサポートする。その导入导出操作は以下の通り：

    void ExportAllEditLayers(ALandscape* LandscapeActor, FString OutputDir){
    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();
    for (int i = 0; i < LandscapeActor->GetLayerCount(); i++) {
        const FLandscapeLayer* Layer = LandscapeActor->GetLayerConst(i);
        FString ExportFilename = FString::Printf(
            TEXT("%s_%s.%s"),
            *Filename,
            *Layer->Name.ToString().Replace(TEXT(" "), TEXT("_")),
            *Extension
        );
        FScopedSetLandscapeEditingLayer Scope(LandscapeActor, Layer->Guid);             // 上下文中で当前编辑する高さ图层を设置する
        LandscapeInfo->ExportHeightmap(FPaths::Combine(OutputDir, ExportFilename));     // 当前高さ图层を导出する
    }
}

void ImportSingleEditLayer(ALandscape* LandscapeActor, int LayerIndex, FString ImportFilename){
    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();
    const FLandscapeLayer* Layer = LandscapeActor->GetLayerConst(LayerIndex);
    FImage Image;
    FImageUtils::LoadImage(*ImportFilename, Image);
    if (Image.Format != ERawImageFormat::Type::G16) {                                   // G16格式のみをサポートする
        return;
    }
    FIntRect TargetResolution;
    LandscapeInfo->GetLandscapeExtent(TargetResolution);
    if (Image.SizeX != TargetResolution.Width() + 1 || Image.SizeY != TargetResolution.Height() + 1) {
        FImage ScaledImage;                                                             // 导入图像を地形の解像度に缩放する
        Image.ResizeTo(ScaledImage, 
                       TargetResolution.Width() + 1,
                       TargetResolution.Height() + 1, 
                       ERawImageFormat::Type::G16, 
                       Image.GammaSpace);
        Image = ScaledImage;
    }
    FScopedSetLandscapeEditingLayer Scope(LandscapeActor, Layer->Guid, [&] {
        LandscapeActor->RequestLayersContentUpdate(ELandscapeLayerUpdateMode::Update_Heightmap_All);
    });
    FHeightmapAccessor<false> HeightmapAccessor(LandscapeInfo);
    HeightmapAccessor.SetData(TargetResolution.Min.X,
                              TargetResolution.Min.Y, 
                              TargetResolution.Max.X, 
                              TargetResolution.Max.Y, 
                              (uint16*)Image.RawData.GetData());
}

    ウェイトマップに対応する構造は TargetLayers であり、その操作はハイトマップに比べてはるかに容易である。ここで伪代码を提供する：
