    LOD不完全ガイド¶

    電子計算機の発明は第二次世界大戦中に起源し、当時砲兵と弾道計算がますます複雑になり、既存の計算ツールではニーズを満たせなくなったため、科学者やエンジニアが電子計算機の開発を開始しました。

    電子計算機の登場に伴い、電子ゲームも生まれました。

    電子ゲームの発展プロセスには、常に独創的なアイデアと技術が存在し、ハードウェア開発者の思考の限界を突破し、ハードウェア性能を極限まで活用し、コンピュータを驚くべき方向に発展させてきました：

    • 知乎 | 電子ゲームの前世、今生と未来 - 麥片

    そして LOD（Level of Detail） は、この発展プロセスで登場し、現在まで使用され続けている技術であり、その目的は：

    • 異なる 重要性（Significance） の場面で、異なる精度の戦略を採用することで、リソースの浪費を可能な限り減らし、システム全体の上限を引き上げること。

    このような思想戦略はゲーム制作のあらゆる面に現れています。

    モデル¶

    モデルにおけるLODの応用は主に、モデルに複数の精度レベルの低ポリゴンモデル（低模）を作成することで、近距離では高精度モデルを使用し、遠距離では低精度モデルを使用することです。

    リアルタイムレンダリング分野で使用され、一定規模を持つ3Dシーンでは、プログラムのフレームレートを保証するため、モデルLODの制作は通常開発チームが回避できない難題です。

    高額な時間と人的コストにより、多くのインディー開発者や小規模チームが複雑なシーンを構築する際に非常に多くの困難に直面する必要があります。

    UEの仮想ジオメトリ技術—— Nanite が登場するまで、シーン制作の門戸が大幅に低下しました。

    Naniteはモデルジオメトリの重要性情報を分析し、自動的に高品質なLODを生成します。ストレージスペースをより少なく占めるだけでなく、非常に高い性能で描画できるため、間違いなくジオメトリレンダリングの未来です。

    しかし現在のところ、特定のシーンではまだ完全にLODを放棄することはできません：

    • 現代のPCのGPU算力は通常冗長であり、大部分の中端GPUでは一般的な複雑なシーンレンダリングに対応できますが、モバイルデバイス、X Box、Switchなどの他のプラットフォームでは、高い画質要求のあるプロジェクトに対して、現在の算力は多くの場合やっと足りる程度であり、より良い視覚効果を追求するためには、しばしば極限的な最適化を行うためのHack的なレンダリングメカニズムをカスタマイズする必要があり、割り当てられた残りの算力ではNaniteの動作をサポートすることが難しい。
    • Naniteのモデル簡略化アルゴリズムは、植生などの特殊なモデルタイプではまだ大きな最適化の余地があります。植生の密度が高く範囲が広い複雑なシーンでは、LODを使用することで性能をより大きく圧縮できます。これは以前の記事で言及されています。

    以前の大部分のゲームプロジェクトでは、通常美術スタッフがDDCソフトウェアでLODを制作し、美術スタッフはモデルソースファイルを提供すると同時に、一定の規範に従ってモデルに対応するLODを生成していました。

    この方法は現在のところ一定の限界が存在します：

    • 初期のモデル制作プロセスは比較的「実務的」であり、大部分の場合依然として人工建模の方式に依存する必要がありましたが、現在多くのメッシュ処理SDKが登場し、これらは通常効果的なモデル簡略化アルゴリズムを提供し、再建模することなく高品質なLODを生成できます。
    • 人工でLODを制作するには通常高額なコストが必要で、チーム自身に十分な人的・物的資源があればまだ良いですが、アウトソーシングチームに委託する場合は、間違いなく巨額な費用になります。
    • どの方法论にも一定の適用条件があり、モデル制作も同様です。一部の老舗制作メーカーを除いて、大部分のチームはゲーム制作の初期に、尽善尽美的な制作規範を制定することが難しいはずです。多くの隠れた問題が開発進捗に伴って次第に浮上し、美術制作はプロジェクト全体で費用消費の大きな部分を占めます。LOD制作については、ソースモデルや規範が変更された場合、以前制作した「製品」は無駄になるため、具体的なLOD制作から、反復可能なLOD生産パイプラインの構築に関心を移す必要があります。
    • ソースモデルは美術スタッフによって制作されますが、彼らは通常性能に敏感ではなく、LODに対する認識も深くないため、どのように制作しても規範を満たすことが難しいモデルに直面した場合、ただ困惑するだけです。

    この時、ジオメトリ処理、グラフィックスレンダリング、エディタ方向に深い理解を持つ人がいて、プログラマティックな方式でこれらの事務を引き受けると、チームの制作コストを大幅に節約できます。この種の専門家は一般的に パイプラインTA / エンジンパイプラインエンジニア と定義されます。

    制作プロセス¶

    LODを制作する前に、簡単なプレビューレベルを構築することをお勧めします。簡単なエディタツールで自動的に配置し、次の目的を達成します：

    • アセットリストまたはアセットパスに基づいて、プレビューするすべてのアセットを確定する。
    • モデルのバウンディングスフィア半径を間隔として横方向に配置する。
    • LODのスクリーンサイズを距離に変換し、すべてのLODを縦方向に配置する。
    • 生成されたモデルに、スクリーンサイズ、距離、頂点数、面数などの重要な情報を表示する。

    このようなビューでは、モデルの規格をより直感的に確認および管理できます：

    初期のLOD制作プロセスでは、一般的に モデルとカメラの距離 をLOD切り替えの判断基準とし、一定の距離ごとに精度の異なる簡略化モデルを切り替えていました。この方式では、次のような LODチェーン を制作する可能性があります：

    しかしすぐに、距離を使用するとLOD間の距離間隔を直感的に確立できないことが発見されました。モデルの大きさが異なるため、各モデルに適切な精度分布を保証するには、異なる距離間隔を評価する必要があります。この問題を解決するため、別のパラメータ—— スクリーンサイズ（Screen Size） を導入しました：これは カメラ距離、カメラの透視行列 およびモデルの バウンディングスフィア半径 を総合的に評価して得られる数値で、モデルの画面占有率と大まかに見なすことができます。以下にその計算式を示します：

    float ConvertDistanceToScreenSize(float ObjectSphereRadius, float Distance)
{
    const float FOV = 90.0f;                                // カメラパラメータは統一して確認可能
    const float FOVRad = FOV * (float)UE_PI / 360.0f;
    const FMatrix ProjectionMatrix = FPerspectiveMatrix(FOVRad, 1920, 1080, 0.01f);     
    const float ScreenMultiple = FMath::Max(0.5f * ProjectionMatrix.M[0][0], 0.5f * ProjectionMatrix.M[1][1]);
    return 2.0f * ScreenMultiple * ObjectSphereRadius / FMath::Max(1.0f, Distance);
}

    スクリーンサイズを一定の割合で縮小するたびにLOD間の間隔を確定することで、直接距離を使用するよりも容易になります：

    しかし、スクリーンサイズを使用することでLOD間の間隔を直感的に設定できるものの、異なるサイズのモデルに対してLODチェーンの距離間隔を統一しないと、視覚上の瑕疵がより明らかになります。

    スクリーンサイズを固定割合で減少させる方式でLODを生成すると、異なるモデルのLODチェーンの距離が不一致であることがわかります（瑕疵を確認しやすくするため、意図的にLODの簡略化幅度を大きく調整しています）：

    スクリーンサイズを使用することで単一モデルのLODチェーンをより合理的に組織できますが、エンジンでは 距離 を使用してシャドウ、距離場照明などの視覚効果を制限することが多いため、視覚効果をよりスムーズに遷移させるには、次の戦略でLODを生成することを推奨します：

    • 固定LOD距離グラデーションを使用する
    • バウンディングスフィア半径に基づいてLODの数を確定する
    • スクリーンサイズ、頂点密度およびモデル特徴に基づいて簡略化幅度を確定する

    上記の重要なパラメータは、プロジェクトの反復、複雑さの向上およびプラットフォームの性能要求に伴って変化するため、直接手動でLODを生成するのではなく、LOD生成パイプラインを構築する必要があります。これにより、パイプラインを不断に反復および最適化できます。

    一般的な簡略化モデル生成戦略には3つの種類があります：

    • 減面（Reduce）：重要性に基づいて一定の 簡略化幅度 で元のモデルの頂点データを削除し、簡略化モデルを生成する。
    • 重构（Remesh）：ボクセル化されたモデルアルゴリズムを通じて、一定の ボクセル精度 でソースモデルに近似し、簡略化モデルを得る。
    • 替身（Impostor）：モデルの視覚効果を保証するための取り巧な方式で、通常元のモデルのジオメトリ構造を打破する。

    現在大部分のチームはこのパイプラインをDDCとエンジンの間に構築していますが、現在のところUnreal Engineは非常に優れたモデル処理インターフェースを提供しているため、直接エンジン側にパイプラインを構築すると、実際のゲームシーン環境とより良く結合して、より良い効果を生成できます。

    例えば以前の植生章で言及された 八面体替身（Octahedron Impostor）：

    • https://shaderbits.com/blog/octahedral-impostors

    UEエンジンはネイティブでいくつかのモデル簡略化アルゴリズムを提供していますが、一部のジオメトリ処理SDKは、視覚効果を保証した前提下で、モデルレンダリングのオーバーヘッドを大幅に削減できます：

    • Simplygon - 3Dゲームコンテンツ最適化の標準を樹立
    • InstaLOD - 3Dコンテンツの生産と自動最適化に必要なすべて

    これらのSDKが提供するインターフェースを使用すると、容易にLODチェーン生成パイプラインを構築できます。

    カスタムメッシュの作成¶

    UPackage* NewPackage = CreatePackage(TEXT("/Game/NewStaticMesh"));                                              // 新しいパッケージを作成
UStaticMesh* NewStaticMesh = NewObject<UStaticMesh>(NewPackage, "NewStaticMesh",  RF_Public | RF_Standalone);   // 新しいメッシュを作成、Outerを新しいパッケージに指定することで、新しいパッケージを保存する時にこのオブジェクトをシリアル化して保存する
{   // LOD0
    FStaticMeshSourceModel& NewSourceModel = NewStaticMesh->AddSourceModel();                                   // 新しいソースモデルを作成 
    FMeshDescription& NewMeshDescription = *NewStaticMesh->CreateMeshDescription(0);                            // このソースモデルのためにメッシュ記述を作成
    FStaticMeshAttributes AttributeGetter = FStaticMeshAttributes(NewMeshDescription);                          // メッシュ記述の属性取得器を作成
    AttributeGetter.Register();

    TPolygonGroupAttributesRef<FName> PolygonGroupNames = AttributeGetter.GetPolygonGroupMaterialSlotNames();   // ジオメトリグループ名リスト、対応するMeshsSection
    TVertexAttributesRef<FVector3f> VertexPositions = AttributeGetter.GetVertexPositions();                     // 頂点配列
    TVertexInstanceAttributesRef<FVector3f> Normals = AttributeGetter.GetVertexInstanceNormals();               // 法線配列
    TVertexInstanceAttributesRef<FVector3f> Tangents = AttributeGetter.GetVertexInstanceTangents();             // 接線配列
    TVertexInstanceAttributesRef<float> BinormalSigns = AttributeGetter.GetVertexInstanceBinormalSigns();       
    TVertexInstanceAttributesRef<FVector4f> Colors = AttributeGetter.GetVertexInstanceColors();                 // 頂点色配列
    TVertexInstanceAttributesRef<FVector2f> UVs = AttributeGetter.GetVertexInstanceUVs();                       // テクスチャ座標配列

    int32 VertexCount = 4;
    int32 VertexInstanceCount = 6;
    int32 PolygonCount = 2;
    NewMeshDescription.ReserveNewVertices(VertexCount);                                                         // メモリを事前に割り当て
    NewMeshDescription.ReserveNewVertexInstances(VertexInstanceCount);
    NewMeshDescription.ReserveNewPolygons(PolygonCount);
    NewMeshDescription.ReserveNewEdges(PolygonCount * 2);
    UVs.SetNumChannels(PolygonCount);
    {
        const FVertexID VertexID0 = NewMeshDescription.CreateVertex();
        const FVertexID VertexID1 = NewMeshDescription.CreateVertex();
        const FVertexID VertexID2 = NewMeshDescription.CreateVertex();
        const FVertexID VertexID3 = NewMeshDescription.CreateVertex();

        VertexPositions[VertexID0] = FVector3f(0.0f, 0.0f, 0.0f);
        VertexPositions[VertexID1] = FVector3f(100.0f, 0.0f, 0.0f);
        VertexPositions[VertexID2] = FVector3f(100.0f, 0.0f, 100.0f);
        VertexPositions[VertexID3] = FVector3f(0.0f, 0.0f, 100.0f);

        const FVertexInstanceID VertexInstanceID0 = NewMeshDescription.CreateVertexInstance(VertexID0);
        const FVertexInstanceID VertexInstanceID1 = NewMeshDescription.CreateVertexInstance(VertexID1);
        const FVertexInstanceID VertexInstanceID2 = NewMeshDescription.CreateVertexInstance(VertexID2);

        const FVertexInstanceID VertexInstanceID3 = NewMeshDescription.CreateVertexInstance(VertexID0);
        const FVertexInstanceID VertexInstanceID4 = NewMeshDescription.CreateVertexInstance(VertexID2);
        const FVertexInstanceID VertexInstanceID5 = NewMeshDescription.CreateVertexInstance(VertexID3);

        UVs[VertexInstanceID0] = FVector2f(0.0f, 0.0f);
        UVs[VertexInstanceID1] = FVector2f(1.0f, 0.0f);
        UVs[VertexInstanceID2] = FVector2f(1.0f, 1.0f);
        UVs[VertexInstanceID3] = FVector2f(0.0f, 0.0f);
        UVs[VertexInstanceID4] = FVector2f(1.0f, 1.0f);
        UVs[VertexInstanceID5] = FVector2f(0.0f, 1.0f);

        Normals[VertexInstanceID0] 
            = Normals[VertexInstanceID1] 
            = Normals[VertexInstanceID2] 
            = Normals[VertexInstanceID3] 
            = Normals[VertexInstanceID4] 
            = Normals[VertexInstanceID5] 
            = FVector3f(0.0f, 1.0f, 0.0f);

        UMaterialInterface* Material = UMaterial::GetDefaultMaterial(MD_Surface);

        {   // Mesh Section 0
            FPolygonGroupID PolygonGroup0 = NewMeshDescription.CreatePolygonGroup();
            PolygonGroupNames[PolygonGroup0] = "LOD0_Section0";
            NewMeshDescription.CreatePolygon(PolygonGroup0,
                {
                    VertexInstanceID0,
                    VertexInstanceID1,
                    VertexInstanceID2,
                });
            NewStaticMesh->GetStaticMaterials().Add(FStaticMaterial(Material));
        }

        {   // Mesh Section 1
            FPolygonGroupID PolygonGroup1 = NewMeshDescription.CreatePolygonGroup();
            PolygonGroupNames[PolygonGroup1] = "LOD0_Section1";
            NewMeshDescription.CreatePolygon(PolygonGroup1,
                {
                    VertexInstanceID3,
                    VertexInstanceID4,
                    VertexInstanceID5
                });
            NewStaticMesh->GetStaticMaterials().Add(FStaticMaterial(Material));
        }
    }
    NewSourceModel.ScreenSize = 1;                                                      // スクリーンサイズを設定
    NewStaticMesh->CommitMeshDescription(0);                                            // メッシュ記述を提交
}

{
    FStaticMeshSourceModel& NewSourceModel = NewStaticMesh->AddSourceModel();
    FMeshDescription& NewMeshDescription = *NewStaticMesh->CreateMeshDescription(1);
    FStaticMeshAttributes AttributeGetter = FStaticMeshAttributes(NewMeshDescription);
    AttributeGetter.Register();

    TPolygonGroupAttributesRef<FName> PolygonGroupNames = AttributeGetter.GetPolygonGroupMaterialSlotNames();
    TVertexAttributesRef<FVector3f> VertexPositions = AttributeGetter.GetVertexPositions();
    TVertexInstanceAttributesRef<FVector3f> Tangents = AttributeGetter.GetVertexInstanceTangents();
    TVertexInstanceAttributesRef<float> BinormalSigns = AttributeGetter.GetVertexInstanceBinormalSigns();
    TVertexInstanceAttributesRef<FVector3f> Normals = AttributeGetter.GetVertexInstanceNormals();
    TVertexInstanceAttributesRef<FVector4f> Colors = AttributeGetter.GetVertexInstanceColors();
    TVertexInstanceAttributesRef<FVector2f> UVs = AttributeGetter.GetVertexInstanceUVs();

    int32 VertexCount = 3;
    int32 VertexInstanceCount = 3;
    int32 PolygonCount = 1;
    NewMeshDescription.ReserveNewVertices(VertexCount);
    NewMeshDescription.ReserveNewVertexInstances(VertexInstanceCount);
    NewMeshDescription.ReserveNewPolygons(PolygonCount);
    NewMeshDescription.ReserveNewEdges(PolygonCount * 2);
    UVs.SetNumChannels(1);
    {
        const FVertexID VertexID0 = NewMeshDescription.CreateVertex();
        const FVertexID VertexID1 = NewMeshDescription.CreateVertex();
        const FVertexID VertexID2 = NewMeshDescription.CreateVertex();

        VertexPositions[VertexID0] = FVector3f(0.0f, 0.0f, 0.0f);
        VertexPositions[VertexID1] = FVector3f(100.0f, 0.0f, 0.0f);
        VertexPositions[VertexID2] = FVector3f(50.0f, 0.0f, 100.0f);

        const FVertexInstanceID VertexInstanceID0 = NewMeshDescription.CreateVertexInstance(VertexID0);
        const FVertexInstanceID VertexInstanceID1 = NewMeshDescription.CreateVertexInstance(VertexID1);
        const FVertexInstanceID VertexInstanceID2 = NewMeshDescription.CreateVertexInstance(VertexID2);

        UVs[VertexInstanceID0] = FVector2f(0.0f, 0.0f);
        UVs[VertexInstanceID1] = FVector2f(1.0f, 0.0f);
        UVs[VertexInstanceID2] = FVector2f(0.5f, 1.0f);

        Normals[VertexInstanceID0]
            = Normals[VertexInstanceID1]
            = Normals[VertexInstanceID2]
            = FVector3f(0.0f, 1.0f, 0.0f);

        UMaterialInterface* Material = UMaterial::GetDefaultMaterial(MD_Surface);

        {
            FPolygonGroupID PolygonGroup0 = NewMeshDescription.CreatePolygonGroup();
            PolygonGroupNames[PolygonGroup0] = "LOD1_Section0";
            NewMeshDescription.CreatePolygon(PolygonGroup0,
                {
                    VertexInstanceID0,
                    VertexInstanceID1,
                    VertexInstanceID2,
                });
            NewStaticMesh->GetStaticMaterials().Add(FStaticMaterial(Material));
        }
    }
    NewSourceModel.ScreenSize = 0.5f;
    NewStaticMesh->CommitMeshDescription(1);
}

    マテリアルテクスチャ¶

    マテリアルについては、初期のいくつかのプロジェクトでは、モデルLODを生成すると同時に、対応するマテリアルのLODも生成していました。理論的にはマテリアルのロジックを簡略化することで性能オーバーヘッドを減らすことができますが、マテリアルLODは無疑にマテリアルセットのサイズを増加させ、もたらされる性能向上は特に明らかではなく、複雑な管理方式により実際のプロジェクトで普及しにくいものになっています。

    現在はより多くの関心がテクスチャに向けられており、LODの応用は主にテクスチャに Mipmap を生成することです。

    Mipmap（多段階漸遠テクスチャ） については、モアレ現象を解決するものとしてより多く認識されているはずです：

    • 知乎 | コンピュータグラフィックス七：テクスチャマッピング(Texture Mapping)及びMipmap技術 - 孫小磊

    モアレ現象を解決する以外に、Mipmapは現在UEでは他の用途もあります：

    • テクスチャストリーミング（Texture Streaming）：ビデオメモリ占有の圧力を緩和するため、UEはデフォルトで一定サイズのテクスチャストリーミングプールを割り当てます（r.Streaming.PoolSizeで設定）。テクスチャの重要性（カメラ距離とテクスチャグループの優先度）に基づいてテクスチャの特定の MipLevel を流入させ、全体的なビデオメモリ占有を可能な限り低下させます。ここにテクスチャストリーミングに関する非常に価値のある記事があります：
      • 知乎 | UE4 Texture Streaming - mike
      • 知乎 | Unreal Engine（UE4）によるモバイル端末テクスチャリソース（ASTC）の極限的な圧縮処理まとめ - Sparrowfc
    • UIアダプテーション（UI Adaptation）：ゲームは異なる解像度の実行環境に直面する可能性があるため、UIテクスチャを縮小する時、ダウンサンプリング（Downsampling） のテクセルステップが大きすぎると、テクスチャにジャギーエッジが出現します。位置を動的に調整するUIの場合、明らかな点滅も出現します。この時UIテクスチャにMipmapを生成することができます。エンジンは DDX(UV)、DDY(UV) に基づいてUIテクスチャのどの MipLevel を使用するかを確定するためです。

    地形¶

    UE5の地形実行メカニズムは非常に完善であり、地形のLODは曲面細分化の精度を調整することで実現されます。現在デフォルトでは8レベルのLODを使用しており、LODを変更するにはこれらのパラメータを調整するだけです：

    UE5.1以降はNanite地形をサポートしています。地形は非常に標準化されたモデルデータを取得するため、Naniteを有効にするとより合理的なジオメトリ組織を持ち、LODと比較して通常より少ない三角形とより忠実な視覚効果を持ちます：

    Naniteのスケジューリングアルゴリズムは曲面細分化より複雑で、メッシュデータも1つ多くなりますが、カメラが静止している時、Naniteのレンダリング消費は明らかにLODより低く、かつNaniteは仮想シャドウに友好的です。プラットフォームの制限がない場合、Nanite地形はより良い選択になります。

    現在のいくつかのプロジェクトでは静的メッシュを地形として使用し、ワールドパーティションのストリーミングとHLODを借りて性能をより良く平衡させ、地形編集の制限もないですが、地形の主な利点は高解像度のいくつかのTileテクスチャ（テクスチャの解像度は地形解像度よりはるかに小さい）を使用して大きな領域をタイリングできることで、同じ視覚精度の地形をモデルでタイリングする場合より占めるディスクサイズがはるかに小さいです。

    HLOD¶

    上記で言及したいくつかのLODタイプは主に単一アセットを対象としていますが、HLODはアセットをバッチ処理した後にLODを制作するものです。

    現在HLODはUEで2つの使用方式が存在します：

    • 普通のマップに対しては、このドキュメントに従ってツールを利用してメッシュをマージしHLODを生成できます：
      • Epic Games | HLODの構築
    • オープンワールドマップに対しては、シーンオブジェクトを分類し HLODLayer を設定し、ワールドパーティションの メッシュセル（Grid Cell） のために自動的にHLODを生成する必要があります：
      • Epic Games | ワールドパーティションのためのHLOD構築

    ここで後者の方式について展開して説明します。

    ワールドパーティション（World Partition） はシーンメッシュを多くのセルに分割し、ストリーミング（Streaming） によって重要な一部の領域（例えばプレイヤー周辺）のみをロードするため、プログラム実行の圧力を効果的に緩和できます：

    しかし既にアンロードされたセルについても、依然として表示されることを希望しますが、大きな性能オーバーヘッドを増やしたくないため、セル内のオブジェクトに対してHLODを生成します。これによりストリーミングのロード範囲をさらに縮小できます。HLODは以下のことができるためです：

    • Draw Callを減らす
    • プリミティブコンポーネントの数を減らし、カリング効率を向上させる
    • 遠景のジオメトリとテクスチャの精度を減らし、レンダリング効率を向上させメモリ圧力を低下させる

    しかし同様に問題も存在します：

    • 一定の表示範囲しか拡大できない
    • ディスクスペースのサイズを増加させる

    現在UEは4つの基礎的なHLOD生成戦略を提供しており、これらは 静的メッシュアセットにのみ対応 しています。それぞれ：

    • インスタンス化：セル内のオブジェクトをISMにマージする
    • マージ：セル内のオブジェクトを1つのメッシュにマージする
    • 簡略化：セル内のオブジェクトをマージした後にメッシュを簡略化する
    • 近似：セル内のオブジェクトをマージした後にメッシュを近似する

    これらは異なるメッシュカテゴリに適用されます。例えば次のようなパーティションメッシュを使用した場合：

    GirdName Cell Size Loading Range Priority BlockOnSlowStreaming
    MainGrid（Default） 12800 25600 0 false
    DeferGrid 25600 25600 -9 true
    AdvanceGrid 51200 51200 9 true
    SmallGrid 6400 19200 -9 false

    これに基づいて次のいくつかの大分類に分けることができます：

    • 地形面片：主に地表を補充するための静的メッシュ面片（地形コンポーネントではない）で、AdvanceGridに分布しています。地形ブロックのサイズは通常25600にすることができ、地形面片は51200のCellに配置され、ジオメトリをマージしてHLODを生成し、DrawCallとプリミティブコンポーネントの数を減らします。
    • 普通モデル：MainGridに分布し、12800のCellに配置されます。HLODの生成方式は小物をカリングし、マージ後に簡略化または近似してHLOD簡略化モデルを生成し、複数のHLODレベルを持つことができます。
    • 植生：AdvanceGridに分布し、25600のHISMを使用してPartitionを組織し、51200のCellに配置されます。HLOD戦略はHISMをマージし51200のISMに退化させることです。
    • その他：いくつかのカスタムまたは動的なレンダリングコンポーネント（パーティクル、水体など）は、遠くで表示されることを可能な限り回避します。通常この種のアイテムは遠くで表示するためにロード距離を拡大し、LODを適切に設定するか、専用のHLOD生成戦略をカスタマイズする必要があります。

    エフェクト¶

    エフェクト（Niagara） は非常に特殊なレンダリングコンポーネントで、GPUパーティクルは Computer Shader を使用してパーティクルの運動をシミュレートし、シミュレートされたデータはパーティクルレンダラーによって 間接レンダリング（Indirect Rendering） を実行されます。

    パーティクルの最適化は主にシミュレーションロジックの複雑さを減らし、エミッターを減らし、カリングし、マテリアルとOverDrawを最適化することにあります。
