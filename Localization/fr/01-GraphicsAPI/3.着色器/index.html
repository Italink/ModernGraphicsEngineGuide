    Bases des shaders¶

    Dans la section précédente, nous avons principalement expliqué comment utiliser QRhi pour construire un pipeline de rendu graphique de base. Vous n'avez peut-être pas remarqué que vous pouvez déjà dessiner n'importe quel graphique avec le GPU ! Il suffit de remplir les données des sommets~

    Si c'était le cas, il ne serait pas nécessaire d'apprendre les choses suivantes.

    Dans les API graphiques modernes, nous cherchons non seulement à accomplir certaines tâches, mais aussi à augmenter le nombre de choses faisables et à rendre possibles les impossibilités.

    Par conséquent, les articles suivants de la série sur les API graphiques se concentreront sur la façon d'utiliser des opérations conformes aux caractéristiques du matériel pour accélérer le rendu graphique.

    Historique¶

    L'apparition du GPU visait à fournir un périphérique d'accélération matérielle fiable pour le système de rendu graphique de l'époque. Ainsi, au début du développement du GPU, les API graphiques avaient pour but de fournir des interfaces simples et génériques pour transférer le flux de rendu fixe précédemment exécuté sur le CPU vers le GPU.

    Si vous avez déjà utilisé OpenGL ancien, vous ne devriez pas être étranger à ce genre de code :

    void init(void)
{
    glMatrixMode(GL_MODELVIEW);                             // Définir la matrice de vue du modèle comme matrice identité
    glLoadIdentity();
}
void display(void)
{
    glClear(GL_COLOR_BUFFER_BIT);                           // Effacer l'écran
    glBegin(GL_TRIANGLES);                                  // Commencer à écrire le primitives de triangle
    glColor3f(1.0, 0.0, 0.0); glVertex3f(-1.0, -1.0, 0.0);  // Écrire les données du sommet 0
    glColor3f(0.0, 1.0, 0.0); glVertex3f( 0.0,  1.0, 0.0);  // Écrire les données du sommet 1
    glColor3f(0.0, 0.0, 1.0); glVertex3f( 1.0, -1.0, 0.0);  // Écrire les données du sommet 2
    glEnd();                                                // Terminer 
    glutSwapBuffers();                                      // Rafraîchir la chaîne d'échange
}
void reshape(int w, int h)
{
    glViewport(0, 0, (GLsizei) w, (GLsizei) h);             // Ajuster la taille de la fenêtre de visualisation
    glMatrixMode(GL_PROJECTION);                            // Définir la matrice de découpage comme matrice identité
    glLoadIdentity();
}

    À cette étape, la logique de traitement de chaque étape du pipeline de rendu de l'API graphique était fixe. Les développeurs n'avaient qu'à fournir à l'API graphique des informations telles que les données des sommets, les textures, les matrices et les sources de lumière pour accomplir le rendu d'une scène 3D via l'accélération GPU.

    Bien que l'API graphique permette de configurer les étapes du pipeline de rendu graphique via quelques paramètres et identifiants, avec le développement rapide de la graphique, diverses théories de rendu ont émergé. Il est évident que les interfaces officielles ne peuvent pas suivre le développement du milieu académique et industriel, et limitent même l'exploration approfondie des développeurs et chercheurs. Par conséquent, le pipeline programmable (Programmable Pipeline) est apparu.

    Aujourd'hui, nous appelons l'ancienne méthode d'utilisation le pipeline à fonctionnalités fixes (Fixed Function Pipeline).

    Le pipeline programmable permet aux développeurs d'écrire des shaders pour personnaliser la logique de traitement d'une étape du pipeline.

    Chaque API graphique a sa propre langage de shader, par exemple :

    • OpenGL et Vulkan utilisent GLSL
    • Direct3D utilise HLSL
    • Metal utilise MSL

    Le flux de travail global de ces langages de shader est similaire, la différence principale résidant dans leur syntaxe qui suit le style de leur API (innovation).

    Voici une implémentation d'un fragment shader (shader de fragment) avec la même fonctionnalité dans différents langages de shader :

    Les éditeurs de jeux anciens utilisaient souvent une seule API graphique comme backend de rendu de leur moteur de jeu. Mais avec l'augmentation du nombre d'utilisateurs sur différentes plateformes, le cross-platform a attiré l'attention des grands éditeurs, car supporter une plateforme supplémentaire signifie un marché supplémentaire.

    Par conséquent, la plupart des moteurs de jeu modernes encapsulent ces API graphiques dans une interface unifiée, qui peut être basculée sur différentes plateformes pour obtenir de meilleures performances graphiques. Nous appelons généralement cet ensemble d'interfaces RHI (Rendering Hardware Interface).

    Pendant le processus d'encapsulation, outre les instructions et ressources de l'API graphique, les shaders cross-platform constituent également un problème très délicat.

    Actuellement, la plupart des moteurs développent dans un langage de shader et le transforment ensuite en langages de shader utilisables par d'autres API graphiques, par exemple :

    • UE utilise HLSL pour le développement et s'appuie sur les bibliothèques open source Glslang et Spirv-Cross pour implémenter la transformation cross-platform des shaders
    • Des moteurs comme Unity, O3DE, Godot et Bgfx ont défini un nouveau langage de shader pour le développement, et utilisent un compilateur intégré associé à des bibliothèques open source pour implémenter la transformation cross-platform des shaders

    Voici quelques lectures pertinentes :

    • [Zhihu-Groupe d'affaires Leihuo pour les jeux web] Introduction de base aux shaders de jeu

    Transformation des shaders¶

    La solution de shaders cross-platform de QRhi est similaire à celle d'UE, sauf que QRhi utilise GLSL dans le style Vulkan pour le développement au lieu de HLSL. Son flux de transformation est le suivant :

    Dans la section précédente, nous avons utilisé ce code pour créer des shaders :

    QShader vs = mRhi->newShaderFromCode(QShader::VertexStage, R"(#version 440
    layout(location = 0) in vec2 position;      // Doit correspondre à inputLayout ci-dessus
    layout(location = 1) in vec4 color;

    layout (location = 0) out vec4 vColor;      // Variable de sortie, ici location est out, pas in

    out gl_PerVertex {                          // Définition fixe dans GLSL Vulkan
        vec4 gl_Position;                       
    };

    void main(){
        gl_Position = vec4(position,0.0f,1.0f); // Définir la sortie de sommet réelle selon la position d'entrée
        vColor = color;                         // Transmettre la couleur d'entrée au fragment shader
    }
)");
Q_ASSERT(vs.isValid());

QShader fs = mRhi->newShaderFromCode(QShader::FragmentStage, R"(#version 440
    layout (location = 0) in vec4 vColor;       // Le out de l'étape précédente devient le in de cette étape
    layout (location = 0) out vec4 fragColor;   // Sortie du fragment shader, location 0 signifie sortie vers le premier attachement de couleur du render target
    void main(){
        fragColor = vColor;
    }
)");
Q_ASSERT(fs.isValid());

    Ici, newShaderFromCode() n'est pas une fonction native fournie par QRhi, mais une encapsulation simple que l'auteur a effectuée en appelant l'interface du module QtShaderTools. Sa logique réelle est la suivante :

    #include "private/qshaderbaker_p.h"

QShader newShaderFromCode(QShader::Stage stage, const char* code) {
    QShaderBaker baker;                     // Four à shaders
    baker.setGeneratedShaderVariants({ QShader::StandardShader });
    baker.setGeneratedShaders({
        QShaderBaker::GeneratedShader{QShader::Source::SpirvShader,QShaderVersion(100)},
        QShaderBaker::GeneratedShader{QShader::Source::GlslShader,QShaderVersion(430)},
        QShaderBaker::GeneratedShader{QShader::Source::MslShader,QShaderVersion(12)},
        QShaderBaker::GeneratedShader{QShader::Source::HlslShader,QShaderVersion(60)},
    });
    baker.setSourceString(code, stage);     // Assembler le code source GLSL
    QShader shader = baker.bake();          // Exécuter le baking pour transformer en code shader des différentes API graphiques

    if (!shader.isValid()) {                // Afficher les erreurs de compilation
        QStringList codelist = QString(code).split('\n');
        for (int i = 0; i < codelist.size(); i++) {
            qWarning() << i + 1 << codelist[i].toLocal8Bit().data();
        }
        qWarning(baker.errorMessage().toLocal8Bit());
    }
    return shader;
}

    QShaderBaker provient du module privé Qt Shader Tools. Lors de la construction avec CMake, vous devez lier votre cible de construction à Qt::ShaderToolsPrivate. Il permet de compiler GLSL dans le style Vulkan en un objet QShader (qui contient le code shader des différentes versions d'API graphiques). C'est une méthode de transformation des shaders à l'exécution.

    De plus, nous pouvons utiliser l'outil en ligne de commande qsb fourni par Qt pour transformer des shaders hors ligne. Cet outil se trouve dans le répertoire suivant :

    Vous pouvez ajouter ce répertoire à la variable d'environnement système pour accéder à l'outil qsb globalement.

    Dans la barre d'adresse de la fenêtre, entrez cmd et appuyez sur Entrée pour ouvrir une fenêtre de ligne de commande. Entrez qsb.exe -h pour voir les instructions d'utilisation de cet outil en ligne de commande :

    Par exemple, la commande qsb.exe -c color.frag -o color.frag.qsb --glsl 430 --msl 12 --hlsl 60 peut transformer le fichier color.frag du répertoire courant en un fichier color.frag.qsb, qui contient GLSL version 430, MSL version 12 et HLSL version 60.

    Dans Qt, vous pouvez utiliser les fichiers *.qsb de la manière suivante :

    QShader newShaderFromQSBFile(const char* filename) {
    QFile file(filename);
    if (file.open(QIODevice::ReadOnly))
        return QShader::fromSerialized(file.readAll());
    return QShader();
}

    CMake fournit également une fonction utile : exécuter certaines opérations lorsque certains fichiers changent.

    Grâce à cette fonction, nous pouvons également implémenter la transformation des shaders à la compilation.

    Cette fonction est réalisée via l'instruction CMake add_custom_command. Nous pouvons ajouter la fonction suivante dans CMake pour ajouter des shaders :

    function(add_shader TARGET_NAME SHADER_PATH)
    set(OUTPUT_SHADER_PATH ${SHADER_PATH}.qsb)  # Chemin du fichier de sortie
    add_custom_command(
        OUTPUT ${OUTPUT_SHADER_PATH}        # Spécifier le fichier de sortie
        COMMAND qsb.exe -c ${SHADER_PATH} -o ${OUTPUT_SHADER_PATH} --glsl 430 --msl 12 --hlsl 60    # Exécuter l'outil QSB
        MAIN_DEPENDENCY ${SHADER_PATH}      # Spécifier le fichier de dépendance, c'est-à-dire que la commande ci-dessus est déclenchée lorsque ce fichier change
    )  
    set_property(TARGET ${TARGET_NAME} APPEND PROPERTY SOURCES ${OUTPUT_SHADER_PATH})               # Il faut ajouter le fichier de sortie à une cible de construction pour déclencher CustomCommand
    source_group("Shader Files" FILES ${SHADER_PATH} ${OUTPUT_SHADER_PATH})                         # Classer les fichiers de shader
endfunction()

    Ainsi, lors de chaque construction de TARGET_NAME, CMake détectera si SHADER_PATH a changé. Si c'est le cas, il appellera l'instruction personnalisée, ici l'outil QSB pour générer le fichier *.qsb. Les messages d'erreur apparaîtront également dans le panneau d'erreurs de l'IDE :

    Concernant les outils de shader de Qt, vous pouvez trouver des exemples de test ici :

    • https://www.khronos.org/registry/OpenGL/specs/gl/GLSLangSpec.4.60.html#basic-types

    Les principaux éléments à noter sont vec (vecteur) et mat (matrice). Nous ne discutons pas ici de leur signification géométrique. Si vous n'êtes pas familiarisé avec ces concepts, je vous recommande de lire Fondements des mathématiques 3D : graphiques et développement de jeux.

    Vecteur¶

    En mathématiques, un vecteur (également appelé vecteur euclidien, vecteur géométrique, vecteur) désigne une quantité ayant une magnitude et une direction. En informatique, un vecteur n'est que plusieurs nombres consécutifs. GLSL prend en charge les vecteurs bidimensionnels (vec2), tridimensionnels (vec3) et quadridimensionnels (vec4).

    Voici quelques utilisations de base du vecteur, en prenant vec4 comme exemple :

    vec4 mVector = vec4(1,2,3,4);
float x   = mVector.x;      // 1
vec2  xy  = mVector.xy;     // [1,2]
vec3  xzy = mVector.xzy;    // [1,3,2]
vec2  xxw = mVector.xxw;    // [1,1,4]
vec4  newVecotr = vec4(mVector.xx,-1,-2);   // [1,1,-1,-2]

    Ici, nous utilisons xyzw pour accéder aux composantes du vecteur. GLSL prend également en charge d'autres groupes de mots-clés : rgba et pqst. Le choix du groupe dépend du contexte d'utilisation et des préférences personnelles.

    GLSL prend bien sûr en charge l'addition, la soustraction, la multiplication, la division et le produit scalaire des vecteurs.

    Matrice¶

    En mathématiques, une matrice est un ensemble de nombres complexes ou réels disposés en une grille rectangulaire. En informatique, ce n'est également qu'un tas de nombres consécutifs. GLSL prend en charge des matrices de taille maximale 4x4, c'est-à-dire mat4x4 (ici, la lettre x représente le signe multiplication), et comme c'est une matrice carrée, elle peut être abrégée en mat4.

    Il faut particulièrement noter que les matrices utilisées dans GLSL sont stockées par colonnes :

    mat3 mMatrix = mat4(0,1,2,
                    3,4,5,
                    6,7,8);

    Si on la stocke par lignes, sa représentation devient :

    {
  0,3,6,
  1,4,7,
  2,5,8
}

    Le mode de stockage affecte non seulement la manière d'accéder à la matrice, mais surtout l'ordre des opérations matricielles. La figure ci-dessous décrit le type de résultat de la multiplication d'une matrice 3D par un vecteur 3D selon le mode de stockage :

    Nous utilisons généralement les matrices dans GLSL pour transformer des vecteurs, donc nous effectuons les opérations de droite à gauche. Par exemple :

    vec3 pos    = vec3(0.5,1.0,0);
mat3 model  = mat3(...);
vec3 newPos = mat * pos;

    De plus, nous devons noter que, outre l'inversion de l'ordre des opérations entre matrices et vecteurs, certaines opérations internes des matrices doivent également être inversées. Par exemple, si nous voulons faire tourner d'abord un graphique puis le translater en utilisant QMatrix4x4 sur le client, nous devons l'utiliser comme ceci :

    QMatrix4x4 mat4;
mat4.translate(0,1);                    // L'opération exécutée en premier est appelée en dernier
mat4.rotate(60,QVector3D(0,0,1));       // Donc ici, c'est d'abord rotation puis translation

    Il faut également noter que la taille mémoire de QMatrix4x4 n'est pas 16 * sizeof(float), elle comporte également un bit d'identification de quatre octets. Lorsque vous avez besoin de télécharger QMatrix4x4 sur le GPU, veuillez appeler mat.toGenericMatrix<4,4>() pour le convertir en type QGenericMatrix.

    Qualificateurs¶

    Dans GLSL, nous utilisons des qualificateurs pour décrire certaines informations sur les variables. Les types de qualificateurs courants sont :

    • Qualificateurs de stockage : décrivent l'emplacement de stockage de la variable
    • Qualificateurs de layout : décrivent le layout de la variable

    Les qualificateurs de stockage courants sont :

    Qualificateur de stockage Signification
    Aucun Variable locale accessible en lecture-écriture
    const Constante
    in Indique que la variable est une variable d'entrée, provenant de la sortie de l'étape précédente
    out Indique que la variable est une variable de sortie, qui sera utilisée comme entrée de l'étape suivante
    uniform Indique que la variable est des données Uniform

    Il faut noter la différence entre in, out et uniform :

    Le format du qualificateur de layout est :

    • layout( liste d'identifiants de qualificateurs de layout )

    Où liste d'identifiants de qualificateurs de layout est un tableau de caractéristiques, dont les éléments peuvent être un identifiant ou une paire clé-valeur. D'autres caractéristiques courantes des qualificateurs de layout sont :

    Caractéristique du qualificateur de layout Description
    binding = Utilisé pour correspondre à l'index de la variable uniform dans le layout de liaison de l'ensemble de descripteurs
    location = Utilisé pour déterminer la position de toutes les variables d'entrée et de sortie. La variable d'entrée de l'étape précédente du shader et la variable de sortie de l'étape suivante sont connectées via location, pas via le nom de la variable
    shared , packed , std140 , std430 Utilisé pour déclarer le mode d'alignement de la mémoire structurale adopté par le Block
    local_size_x = , local_size_y = , local_size_z = Dans le compute shader, indique la taille de l'unité de calcul
    max_vertices = Dans le geometry shader, définit le nombre maximum de sommets
    rgba32f rgba16f rg32f rg16f r11f_g11f_b10f r32f r16f rgba16 rgb10_a2 rgba8 rg16 rg8 r16 r8 rgba16_snorm rgba8_snorm rg16_snorm rg8_snorm r16_snorm r8_snorm rgba32i rgba16i rgba8i rg32i rg16i rg8i r32i r16i r8i rgba32ui rgba16ui rgb10_a2ui rgba8ui rg32ui rg16ui rg8ui r32ui r16ui r8ui Dans le compute shader, indique le format d'image de la variable Image

    Dans GLSL dans le style Vulkan, nous devons noter :

    • Toute variable in ou out doit être modifiée avec layout(location = ${index}), car la variable in de cette étape cherchera la variable out correspondante de l'étape précédente selon Location Index
    • Pour le vertex shader, sa variable in cherchera dans le layout d'entrée des sommets du pipeline selon Location Index
    • Pour le fragment shader, sa variable out sera sortie vers l'attachement de couleur correspondant à l'index du render target selon Location Index
    • Toute variable uniform doit être modifiée avec layout(binding = ${index}), et Binding Index doit correspondre au layout de l'ensemble de descripteurs (QRhiShaderResourceBindings) utilisé dans le pipeline

    La documentation complète sur les qualificateurs peut être consultée ici :

    • https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.4.60.html#storage-qualifiers

    Étapes de base¶

    Le flux d'exécution complet d'un pipeline de rendu graphique est le suivant :

    • Les parties rouges Vertex Shader et Fragment Shader sont des éléments obligatoires du pipeline de rendu graphique.

    • Les parties jaunes Tesselation Control Shader, Tesselation Evaluation Shader et Geometry Shader sont des éléments facultatifs du pipeline de rendu graphique.

    • Les parties vertes Primitive Setup, Clipping et Rasterization sont des étapes non programmables, mais les API graphiques fournissent des paramètres pour ajuster leur comportement.

    Pour écrire des shaders, nous devons d'abord comprendre les responsabilités de chaque étape du pipeline de rendu graphique. Ici, je vais principalement expliquer le vertex shader et le fragment shader. Il existe d'autres étapes de traitement et pipelines dans les API graphiques, et leur présentation précoce imposerait une charge cognitive importante aux lecteurs. Si vous êtes intéressé, vous pouvez essayer de les découvrir d'abord, et ces contenus seront approfondis dans les articles suivants.

    Vertex Shader (Shader de sommet)¶

    La responsabilité du Vertex Shader est de remplir les variables de sortie intégrées du sommet courant et de transmettre des données utiles à l'étape suivante, en fonction des données de sommet d'entrée et des données Uniform (si elles existent).

    Un modèle de vertex shader essentiel est le suivant :

    layout(location = 0) in vec2 position;      

out gl_PerVertex {                          
    vec4 gl_Position;
};

void main(){
    gl_Position = vec4(position,0.0f,1.0f); 
}

    Interprétation :

    • layout(location = 0) représente la propriété de sommet à l'index 0 dans le layout d'entrée des sommets lors de la création du pipeline.
    • in indique qu'il s'agit d'une variable d'entrée.
    • vec2 indique que le type de la variable est un vecteur bidimensionnel, qui doit correspondre au format (Float2) dans le layout d'entrée des sommets.
    • position est le nom de la variable d'entrée, qui peut être arbitraire.
    • out gl_PerVertex { vec4 gl_Position; }; est la définition de sortie fixe du vertex shader.
    • gl_Position = vec4(position,0.0f,1.0f); remplit la sortie de sommet réelle du vertex shader selon la position de sommet d'entrée.

    Il faut noter : ne pas être influencé par la pensée定式, pensant qu'il faut absolument entrer une position ici. En réalité, nous pouvons entrer n'importe quelle donnée de sommet, même sans inclure la position du sommet, à condition de déterminer la valeur de gl_Position dans gl_PerVertex dans le vertex shader. Par exemple :

    layout(location = 0) in vec2 anyVertexData;

out gl_PerVertex {              
    vec4 gl_Position;
};

vec1 calcPosition(vec2 vertexData){
    // Faire quelque chose
    return position;
}

void main(){
    gl_Position = calcPosition(anyVertexData)
}

    Si nous voulons transmettre certaines données de cette étape à l'étape suivante, nous devons simplement définir une variable modifiée par out et avec une description de layout :

    layout(location = 0) in vec2 position;      
layout(location = 0) out vec4 color;        // Définir la variable de sortie, les locations de in et out sont séparées

out gl_PerVertex {                          
    vec4 gl_Position;
};

void main(){
    gl_Position = vec4(position,0.0f,1.0f); 
    color = vec4(position.xy,0.0f,1.0f);
}

    Si le pipeline contient des données Uniform pour le vertex shader, il suffit de définir une variable modifiée par uniform et avec une description de binding :

    layout(location = 0) in vec2 position;      
layout(location = 0) out vec4 color;    

layout(binding = 0) uniform UniformBlock {  // Ici, binding=0 correspond à la configuration de liaison du layout de l'ensemble de descripteurs lors de la création du pipeline
    vec4 color;                             // UniformBlock est le nom de ce bloc de structure de données, il peut être arbitraire
} ubo;


out gl_PerVertex {                          
    vec4 gl_Position;
};

void main(){
    gl_Position = vec4(position,0.0f,1.0f); 
    color = ubo.Color;                      // Définir la couleur via les données Uniform
}

    Fragment Shader (Shader de fragment)¶

    La responsabilité du Fragment Shader est d'écrire sur l'attachement de couleur du render target, en fonction des données d'entrée de l'étape précédente et des données Uniform (si elles existent).

    Un modèle de fragment shader essentiel est le suivant :

    layout(location = 0) out vec4 fragColor;    
void main(){
    fragColor = vec4(1,1,1,1);
}

    Interprétation :

    • layout(location = 0) out indique que le fragment sera sorti vers l'attachement de couleur à l'index 0 du render target. Un render target contient généralement au moins un attachement de couleur, et le render target de la chaîne d'échange n'a qu'un seul attachement de couleur à quatre canaux.
    • vec4 indique que l'attachement de couleur a quatre canaux de couleur, par exemple RGBA8888.
    • fragColor est le nom de la variable de sortie, qui peut être arbitraire.
    • fragColor = vec4(1,1,1,1) indique que le fragment final est blanc opaque (R=1, G=1, B=1, A=1).

    Le fragment shader peut également ajouter des entrées Uniform comme le vertex shader.

    Au début de mon apprentissage, j'ai considéré le vertex shader et le fragment shader comme étant en correspondance biunivoque parce que la variable de sortie du vertex shader correspond à la variable d'entrée du fragment shader. Mais en réalité, c'est une erreur. Rappelez-vous le programme de la section précédente ?

    Branches logiques¶

    Pour les développeurs, le langage de shader ne peut pas être simplement considéré comme un langage de programmation avec une syntaxe différente. Son point le plus particulier est qu'il s'exécute sur le GPU, et l'implémentation de ses fonctions intégrées est basée sur les caractéristiques matérielles du GPU.

    Comme le GPU est constitué d'un grand nombre d'unités de calcul empilées, cela entraîne son inconvénient d'être peu performant pour l'exécution de logiques.

    Lors de l'écriture de GLSL, nous devons éviter autant que possible les instructions de branchement dans GLSL et réfléchir au problème d'une autre stratégie :

    • D'abord, il est clair que l'appel de return dans le shader n'affectera pas les étapes suivantes. Si des paramètres nécessaires ne sont pas remplis, des valeurs par défaut peuvent être utilisées.
    • L'objectif principal de l'utilisation de branches logiques est généralement de faire en sorte que certaines situations sortent A, d'autres sortent B, et d'autres sortent...

    Le GPU est performant pour les opérations mathématiques. Si nous pouvons déterminer la fonctionnalité de la condition logique à résultat de sortie, nous pouvons éviter les branches logiques par le biais de calculs numériques. Cela implique une fonction clé :

    • Fonction step (étape).

    Généralement, l'image des fonctions mathématiques est continue et douce. Le point particulier de la fonction step est qu'elle présente un saut de valeur. Son image est la suivante :

    Cette caractéristique de saut est très adaptée aux branches logiques sur les valeurs numériques, mais son utilisation n'est pas très intuitive pour l'homme. Ainsi, dans GLSL, nous sommes autorisés à utiliser des opérateurs conditionnels pour accomplir la logique correspondante, par exemple : (a < b) ? a : b.

    Certaines fonctions intégrées de GLSL, comme min, max, sont implémentées spécifiquement pour le GPU, donc nous n'avons pas à nous soucier des problèmes de branches logiques. Nous devons seulement prêter attention à l'utilisation de if, et if n'est pas équivalent à un branchement. Ce qui compte vraiment, c'est si le compilateur génère une instruction de branchement.

    Cache de pipeline (Pipeline Cache)¶

    Comme mentionné précédemment, dans les moteurs de jeu, le développement est généralement effectué dans un langage de shader, puis transformé en code shader des différentes API graphiques. Cette transformation nous donne généralement le code source ou le fichier de bytecode (intermédiaire) de l'API graphique spécifique.

    Lorsque le GPU utilise le shader, il faut en réalité compiler le code source ou le fichier de bytecode (intermédiaire) en code binaire exécutable par la machine. Ce processus de compilation dépend du pilote graphique. Comme la version du pilote graphique de chaque utilisateur peut être différente, il est difficile pour les éditeurs de couvrir tous les pilotes graphiques. Cela signifie que nous devons compiler le code binaire du shader sur l'ordinateur de l'utilisateur.

    Afin d'éviter les ralentissements causés par la compilation du shader pendant l'exécution du programme, les API graphiques modernes fournissent la fonction de cache de pipeline (Pipeline Cache). Cette fonction permet au programme de compiler tous les pipelines lors du premier démarrage et de les stocker sur le disque, de sorte que le programme ne subira pas de ralentissement dû à la compilation du shader pendant son exécution ou au prochain démarrage.

    Dans Unreal Engine, cette technique est appelée Cache PSO (Pipeline State Object Cache)

    Voici un excellent article expliquant les connaissances relatives à la cache PSO :

    • [Zhihu-mike] Cache PSO d'UE4

    Dans QRhi, nous pouvons activer la fonction de cache de pipeline lors de la création de QRhi :

    La fonction QByteArray QRhi::pipelineCacheData() permet d'obtenir les données de cache de pipeline déjà compilées par le programme courant.

    La fonction void QRhi::setPipelineCacheData(const QByteArray &data) permet de définir les données de cache de pipeline.

    Lorsque le programme appelle QRhiGraphicsPipeline::create(), il vérifiera si l'état du pipeline existe en fonction de l'état des paramètres du pipeline courant. Si c'est le cas, il le réutilisera directement sans recompiler.
