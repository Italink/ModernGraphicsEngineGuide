    Bases de l'API graphique¶

    Concepts fondamentaux¶

    Pour les débutants, les API graphiques modernes présentent initialement de nombreuses structures incompréhensibles. Il n'est pas nécessaire de s'inquiéter excessivement : ces termes ne sont que des noms courts attribués à des structures et processus spécifiques. Une fois que vous comprendrez leurs cas d'usage et maîtriserez leur flux d'utilisation, leur signification deviendra évidente.

    Périphérique physique (Physical Device)¶

    Dans les API graphiques, le GPU est généralement appelé périphérique physique.

    Avec le développement rapide des GPU, les fonctionnalités des API graphiques augmentent également au fil du temps. Afin de garantir la compatibilité descendante des API graphiques avec les périphériques GPU, ces API fournissent souvent des interfaces pour interroger si un périphérique physique prend en charge certaines fonctionnalités et les limites des ressources.

    Prenons Vulkan comme exemple : VkPhysicalDeviceFeatures permet d'interroger si un périphérique physique prend en charge une fonctionnalité donnée :

    struct VkPhysicalDeviceFeatures {
    VkBool32    robustBufferAccess;
    VkBool32    fullDrawIndexUint32;
    VkBool32    imageCubeArray;
    VkBool32    independentBlend;
    VkBool32    geometryShader;
    VkBool32    tessellationShader;
    VkBool32    sampleRateShading;
    VkBool32    dualSrcBlend;
    VkBool32    logicOp;
    VkBool32    multiDrawIndirect;
    VkBool32    drawIndirectFirstInstance;
    VkBool32    depthClamp;
    VkBool32    depthBiasClamp;
    VkBool32    fillModeNonSolid;
    VkBool32    depthBounds;
    VkBool32    wideLines;
    //...
}

    VkPhysicalDeviceLimits permet d'interroger les limites des ressources du périphérique physique :

    struct VkPhysicalDeviceLimits {
    uint32_t              maxImageDimension1D;
    uint32_t              maxImageDimension2D;
    uint32_t              maxImageDimension3D;
    uint32_t              maxImageDimensionCube;
    uint32_t              maxImageArrayLayers;
    uint32_t              maxTexelBufferElements;
    uint32_t              maxUniformBufferRange;
    uint32_t              maxStorageBufferRange;
    uint32_t              maxPushConstantsSize;
    uint32_t              maxMemoryAllocationCount;
    //...
}

    Lors de l'utilisation d'une API graphique, le développeur doit connaître l'existence de ces limites. En plus de sélectionner un périphérique physique qui répond aux exigences fonctionnelles, il doit également implémenter des traitements de compatibilité logiques pour les utilisateurs dont les périphériques ne prennent pas en charge certaines fonctionnalités.

    Périphérique logique (Device)¶

    Le périphérique logique est le "agent" qui permet au développeur de communiquer avec le périphérique physique.

    Puisque le CPU et le GPU s'exécutent indépendamment l'un de l'autre sans attente mutuelle, afin de réduire la charge de communication entre eux et d'éviter que le développeur ne harcèle le GPU pour des détails insignifiants ("Hé ! Tu ne peux pas partir avant d'avoir fini ce travail !"), les API graphiques modernes introduisent le concept de périphérique logique. Le développeur transmet ses demandes à l'agent, qui regroupe un ensemble de tâches avant de les transmettre uniformément au périphérique physique pour exécution.

    Lors de la création d'un périphérique logique, il est nécessaire de spécifier les extensions du périphérique physique à activer.

    Tampon de commandes (Command Buffer)¶

    Le tampon de commandes, également appelé Command List, est le "petit papier" du développeur.

    En plus de remettre des "marchandises" à l'agent (périphérique logique), le développeur enregistre les tâches à accomplir sur un petit papier et le remet à l'agent pour transmission au périphérique physique.

    Dans QRhi, il n'est pas possible de créer directement un CommandBuffer. Il existe deux manières de l'obtenir :

    • Via SwapChain pour récupérer le CommandBuffer actuel
    • rhi->beginOffscreenFrame crée un nouveau CommandBuffer

    File d'attente du périphérique (Device Queue)¶

    La file d'attente du périphérique est le seul "pont" de communication entre l'agent (périphérique logique) et le périphérique physique.

    Une fois que l'agent a reçu les marchandises et le petit papier du développeur, il se précipite à travers le pont vers le périphérique physique.

    Synchronisation¶

    Pourquoi le GPU est-il si puissant ? Parce qu'il dispose d'une équipe de subordonnés. Imaginez la scène suivante :

    Un jour, le chef GPU reçoit le petit papier envoyé par l'agent et convoque immédiatement ses subordonnés pour leur donner des ordres :

    "Hmm... Première instruction : déchirer toutes les publicités illégales de la rue Fandou. Zhang San, c'est à toi !"

    "Reçu !" répond Zhang San, qui s'enfuit immédiatement vers la rue Fandou.

    "Deuxième instruction : coller les publicités du développeur sur toute la rue Fandou. Li Si, c'est à toi !"

    "Compris !" dit Li Si, qui monte sur sa petite moto et s'élance vers la rue Fandou.

    Le lendemain, le développeur arrive avec une équipe et interroge le chef GPU sur le fait que les publicités n'ont pas été collées, menaçant même de renverser la table.

    Le chef GPU vérifie le petit papier : rien ne cloche. Il interroge Zhang San et Li Si : Zhang San a bien déchiré les publicités, Li Si a bien collé les siennes. En creusant davantage, il s'avère que Li Si est arrivé trop tôt : il a d'abord collé les publicités, qui ont ensuite été toutes déchirées par Zhang San.

    En résumé, le développeur n'ayant pas fourni d'instructions claires et le chef GPU ayant mal interprété la demande, une erreur d'organisation a provoqué cet incident.

    Dans le GPU, de nombreuses tâches s'exécutent en parallèle, ce qui signifie qu'il peut y avoir des opérations lancées dans un ordre séquentiel mais exécutées en désordre.

    De plus, le CPU et le GPU ne s'attendent pas mutuellement, mais dans certains cas, nous souhaitons attendre la fin de certaines opérations ou la déclenchement d'événements.

    C'est pourquoi les API graphiques modernes fournissent des structures pour contrôler la synchronisation entre CPU, GPU, instructions et files d'attente. Prenons Vulkan comme exemple : il propose plusieurs structures de contrôle de synchronisation :

    • Barrière (Fence)
    • Sémaphore
    • Barrière (Barrier)
    • Événement (Event)

    Pour plus de détails, vous pouvez lire :

    • Synchronisation et contrôle de cache dans Vulkan (I) : Fence et Semaphore
    • Synchronisation et contrôle de cache dans Vulkan (II) : Barrier et Event
    • Comprendre la synchronisation dans Vulkan

    Surface de fenêtre (Window Surface)¶

    Afin d'afficher les résultats du rendu à l'écran, le développeur doit souvent créer une connexion entre l'API graphique et le système de fenêtrage. Dans Vulkan, cela se fait en créant une surface de fenêtre (Window Surface) pour la fenêtre de la plateforme correspondante, qui sert de pont d'interaction entre l'API graphique et le système de fenêtrage.

    Étant donné que les systèmes de fenêtrage des différents systèmes d'exploitation (Windows, Linux, Mac...) ne sont pas uniformes, la création d'une Window Surface nécessite certaines configurations spécifiques à la plateforme.

    Certaines bibliothèques open source visent à éviter ces configurations fastidieuses, comme GLFW :

    GLFW est une bibliothèque open source multi-plateforme pour le développement d'applications OpenGL, OpenGL ES et Vulkan.

    Elle fournit une API simple, légère et indépendante de la plateforme pour créer des fenêtres, des contextes et des surfaces, lire les entrées, gérer les événements, etc.

    La plupart des frameworks GUI fournissent également une gestion des Window Surface. Notre tâche consiste à consulter la documentation et à explorer le code source.

    Pipeline¶

    Le pipeline, également appelé pipeline graphique, est le flux de tâches exécuté sur le GPU. Dans les API graphiques modernes, il existe trois types de pipelines courants :

    • Pipeline de rendu graphique (Graphics Pipeline) : utilisé pour dessiner des images sur une cible de rendu (RenderTarget)
    • Pipeline de calcul (Compute Pipeline) : utilisé pour traiter des données dans des tampons (Buffer) ou des images (Image)
    • Pipeline de ray tracing (Ray Tracing Pipeline) : utilisé pour les processus de ray tracing

    Dans la section précédente, nous avons découvert le pipeline de rendu graphique via un programme console. Voici un diagramme plus complet :

    Source : https://graphicscompendium.com/intro/01-graphics-pipeline

    Son flux de travail peut être résumé comme suit :

    • Le développeur charge les données de vertex sur le GPU
    • Chaque donnée de vertex est traitée par le shader de vertex (Vertex Shader)
    • (Si présent) Après traitement par le shader de contrôle de tessellation (Tessellation Control Shader), le shader d'évaluation de tessellation (Tessellation Evaluation Shader) et le shader de géométrie (Geometry Shader), les données de triangle sont assemblées avec succès.
    • Ensuite, le moteur de rastérisation mappe (rastérise) les données de triangle pour obtenir des fragments (Fragment)
    • Chaque donnée de fragment est traitée par le shader de fragment (Fragment Shader)
    • Les fragments chevauchants sont traités lors de l'étape de test et de mélange
    • Une valeur unique est obtenue pour chaque pixel de coordonnées correspondantes, qui est ensuite dessinée sur la cible de rendu (RenderTarget)

    Shader (Shader)¶

    Un shader est un petit programme exécuté sur le GPU, principalement utilisé pour étendre les fonctionnalités du pipeline. Par exemple, dans le pipeline de rendu graphique ci-dessus :

    • Le tableau de vertex en entrée est traité par le shader de vertex (Vertex Shader)
    • Après rastérisation, chaque pixel est traité par le shader de fragment (Fragment Shader)

    Un pipeline de rendu graphique nécessite au minimum un shader de vertex et un shader de fragment. Cependant, les API graphiques modernes prennent également en charge des shaders supplémentaires :

    • Shader de contrôle de tessellation (Tessellation Control Shader)
    • Shader d'évaluation de tessellation (Tessellation Evaluation Shader)
    • Shader de géométrie (Geometry Shader)
    • Shader de calcul (Compute Shader)

    Ces shaders sont écrits dans un langage de shader spécifique à l'API, comme :

    • GLSL : utilisé pour OpenGL et Vulkan
    • HLSL : utilisé pour Direct3D
    • MSL : utilisé pour Metal

    Dans les RHI (Rendering Hardware Interface) génériques des moteurs graphiques modernes, afin de prendre en charge plusieurs API graphiques, un langage de shader est souvent utilisé pour le développement, puis transcrit en code shader pour d'autres API.

    Dans QRhi, le développement utilise un GLSL de style Vulkan. Qt compile le GLSL en code shader au format SPIR-V via glslang, puis utilise la bibliothèque open source SPIRV-Cross pour le transcrire en code shader compatible avec chaque API. Le flux est le suivant :

    QRhi utilise un GLSL de style Vulkan, donc cette documentation est très importante :

    Tampon (Buffer)¶

    Ici, "Buffer" ne désigne pas seulement un segment de mémoire (Memory) sur le GPU.

    Plus précisément, un Buffer contient non seulement un segment de mémoire, mais aussi son propre type (Type) et usage (Usage).

    En ce qui concerne le type (Type), les API graphiques le divisent généralement en :

    • Mémoire locale à l'hôte (Host Local Memory) : mémoire visible uniquement par l'hôte, généralement appelée mémoire ordinaire
    • Mémoire locale au périphérique (Device Local Memory) : mémoire visible uniquement par le périphérique, généralement appelée mémoire vidéo
    • Mémoire locale à l'hôte et visible par le périphérique (Host Local Device Memory) : mémoire gérée par l'hôte et visible par le périphérique
    • Mémoire locale au périphérique et visible par l'hôte (Device Local Host Memory) : mémoire gérée par le périphérique et visible par l'hôte

    L'hôte désigne généralement le côté CPU, tandis que le périphérique désigne le GPU.

    Pour plus de détails, consultez :

    • Gestion de la mémoire dans Vulkan

    L'utilisation du bon type de mémoire peut considérablement améliorer l'efficacité de lecture/écriture. Dans le pipeline des moteurs graphiques modernes, on utilise autant que possible la mémoire du périphérique (Device Memory). Lorsque nous devons soumettre des données depuis le CPU, étant donné que l'hôte ne peut pas y accéder directement, nous chargeons généralement les données sur une mémoire visible par l'hôte, puis les copions via une instruction vers la mémoire du périphérique correspondante. Ce Buffer contenant la mémoire visible par l'hôte est généralement appelé Tampon de staging (Staging Buffer).

    QRhi encapsule ces types davantage, en les classant selon l'intention d'utilisation :

    • Immutable : utilisé pour stocker des données qui ne devraient jamais changer. Il offre des performances de lecture/écriture très efficaces sur le GPU. Il est généralement placé dans la mémoire GPU locale au périphérique (Device Local) et ne peut pas être lu/écrit directement par le CPU. Cependant, QRhi prend en charge son chargement : chaque chargement de données crée un nouveau tampon de staging (Staging Buffer) avec mémoire locale à l'hôte (Host Local) comme intermédiaire pour charger de nouvelles données. Cette opération est très coûteuse.
    • Static : également stocké dans la mémoire GPU locale au périphérique (Device Local). Contrairement à Immutable, le tampon de staging (Staging Buffer) créé lors du premier chargement de données est conservé.
    • Dynamic : utilisé pour stocker des données qui changent fréquemment. Il est placé dans la mémoire GPU locale à l'hôte (Host Local). Afin de ne pas retarder le pipeline de rendu graphique, il utilise généralement un mécanisme de double buffering.

    En ce qui concerne l'usage (Usage), il peut généralement avoir les indicateurs (Flag) suivants :

    • VertexBuffer : utilisé pour stocker des données de vertex
    • IndexBuffer : utilisé pour stocker des données d'index
    • UniformBuffer : utilisé pour stocker des données constantes
    • StorageBuffer : utilisé pour le calcul de données dans le pipeline de calcul
    • IndirectDrawBuffer : utilisé pour fournir des paramètres de rendu pour le rendu indirect

    Descripteur (Descriptor)¶

    Comme mentionné dans le pipeline de rendu graphique ci-dessus, chaque vertex est traité par le shader de vertex et chaque fragment par le shader de fragment. "Chaque" se traduit par "Per" en anglais. Dans le pipeline, outre ce type de données "Per", il existe souvent des données communes et partagées entre les shaders. Ces données sont généralement appelées données Uniform dans les API graphiques et peuvent être considérées comme des entrées publiques des shaders.

    Lors de la création de la structure du pipeline, il est nécessaire d'utiliser un descripteur (Descriptor) pour décrire les informations de structure de base des données Uniform. Les types de descripteurs courants incluent :

    • UniformBuffer : entrée de Buffer en lecture seule pour les shaders
    • Sampler : entrée d'échantillonnage de texture en lecture seule pour les shaders
    • StorageBuffer : Buffer accessible en lecture/écriture pour les calculs dans le pipeline de calcul
    • StorageImage : Image accessible en lecture/écriture pour les calculs dans le pipeline de calcul

    Cela correspond à QRhiShaderResourceBinding dans QRhi :

    Liaison de layout de jeu de descripteurs (DescriptorSetLayoutBinding)¶

    Un shader n'a pas souvent qu'un seul type d'entrée Uniform. La liaison de layout de jeu de descripteurs (DescriptorSetLayoutBinding) est un ensemble de descripteurs qui définit le layout de structure Uniform du shader. Dans les API graphiques, après la création du pipeline, la plupart de ses paramètres ne peuvent pas être modifiés. Cependant, la liaison de layout de jeu de descripteurs peut être remplacée dynamiquement sans reconstruire le pipeline.

    Cela correspond à QRhiShaderResourceBindings dans QRhi. Sa création est très simple :

    mShaderBindings.reset(mRhi->newShaderResourceBindings());
mShaderBindings->setBindings({
      QRhiShaderResourceBinding::bufferLoadStore(0, QRhiShaderResourceBinding::ComputeStage, mStorageBuffer.get()),
      QRhiShaderResourceBinding::imageLoadStore(1, QRhiShaderResourceBinding::ComputeStage, mTexture.get(), 0),
});
mShaderBindings->create();

    Cible de rendu (RenderTarget)¶

    Elle équivaut à l'Objet Frame Buffer (Frame Buffer Object) dans OpenGL. Elle est composée d'un ou plusieurs attachements de couleur (Color Attachment) et peut inclure des attachements de profondeur et de stencil.

    Généralement, notre dessin consiste à remplir des données de couleur sur la RenderTarget. Pour les données de profondeur et de stencil, le GPU les traite automatiquement ; nous n'avons qu'à configurer certaines règles de traitement.

    Cela correspond à QRhiRenderTarget dans QRhi. Créer une RenderTarget avec QRhi est très facile :

    /*Créer une RT avec un attachement de couleur*/
QSharedPointer<QRhiTexture> colorAttachment;
colorAttachment.reset(rhi->newTexture(QRhiTexture::RGBA32F, QSize(800, 600), 1, QRhiTexture::RenderTarget | QRhiTexture::UsedAsTransferSource));
colorAttachment->create();
QSharedPointer<QRhiTextureRenderTarget> renderTarget;
QSharedPointer<QRhiRenderPassDescriptor> renderPassDesc;
renderTarget.reset(rhi->newTextureRenderTarget({ colorAttachment.get() }));
renderPassDesc.reset(renderTarget->newCompatibleRenderPassDescriptor());
renderTarget->setRenderPassDescriptor(renderPassDesc.get());
renderTarget->create();

    QRhi¶

    Si vous êtes un débutant, après avoir lu les concepts fondamentaux ci-dessus, vous êtes probablement un peu déconcerté. Mais restez assuré : une fois que vous commencerez à coder, ces concepts deviendront des "papiers tigres". Dans les sections suivantes de ce chapitre, nous expliquerons systématiquement la structure et l'utilisation des bases de l'API graphique.

    Tout d'abord, vous avez besoin de Qt. Vous pouvez télécharger le programme d'installation en ligne de Qt depuis ce miroir :

    QRhiWindow¶

    Les fenêtres fournies par le système d'exploitation offrent un contrôle très fin. Lorsque le développeur souhaite ajuster un effet de fenêtre, il peut être nécessaire de modifier plusieurs propriétés et événements de la fenêtre. Lorsque de nombreux effets sont empilés, des conflits peuvent facilement survenir. Par exemple :

    Supposons que l'effet A nécessite l'activation des propriétés a et b, et que l'effet B nécessite l'activation des propriétés b et c. Si la fenêtre active les effets A et B (c'est-à-dire les propriétés a, b et c), puis que l'on souhaite désactiver l'effet B, si l'on ne vérifie pas attentivement et que l'on désactive directement les propriétés b et c associées, les seules propriétés restantes seront a, et l'affichage de l'effet A présentera des problèmes.

    Le développeur souhaite généralement se concentrer sur l'effet d'affichage de la fenêtre plutôt que sur les propriétés et événements de fenêtre au niveau du système d'exploitation. Par conséquent, la configuration des effets dans la gestion de la fenêtre implique un chevauchement important des propriétés et événements.

    Si l'on ajoute une vérification d'association à chaque configuration de propriété, le code deviendra verbeux, difficile à maintenir et plus susceptible de contenir des bugs.

    C'est pourquoi Qt utilise une machine à états pour gérer les fenêtres natives :

    • Les différentes configurations de la fenêtre au niveau de Qt ne prennent pas effet immédiatement ; elles sont stockées et, à un moment donné (par exemple, lors de l'appel de show), Qt crée la fenêtre du système d'exploitation réel en fonction de la configuration du contexte actuel.

    En d'autres termes, pour une fenêtre Qt, la fenêtre réelle du système d'exploitation n'est créée et son handle n'est disponible qu'après l'appel de la fonction show.

    Pendant le développement, on rencontre souvent ce type de code, qui organise efficacement la logique complexe, notamment dans les projets graphiques. On voit fréquemment des fonctions commençant par ensure, qui effectuent des opérations en fonction du contexte de propriétés actuel.

    Si nous voulons créer la structure de rendu graphique de la fenêtre, nous avons besoin du handle de fenêtre réel, donc l'initialisation doit être effectuée après l'appel de show. Heureusement, Qt fournit un événement correspondant :

    • void QWindow:: exposeEvent (QExposeEvent* ev )
    • Cet événement est déclenché lorsque la fenêtre passe de l'état non exposé à exposé.
    • Lors du premier affichage de la fenêtre, resizeEvent est déclenché avant cet événement.

    Il est important de noter que pour une fenêtre, exposeEvent peut être déclenché plusieurs fois, mais l'initialisation n'est nécessaire qu'une seule fois. Par conséquent, des vérifications logiques doivent être ajoutées.

    Les structures de rendu graphique de la fenêtre incluent principalement :

    • QScopedPointer<QRhiEx> mRhi
    • QScopedPointer<QRhiSwapChain> mSwapChain : Chaîne d'échange
    • QScopedPointer<QRhiRenderBuffer> mDSBuffer : Tampon de profondeur et stencil
    • QScopedPointer<QRhiRenderPassDescriptor> mSwapChainPassDesc : Descripteur de RenderPass pour la chaîne d'échange

    Après une initialisation réussie, nous n'avons qu'à ajouter la logique de rendu et de redimensionnement à la fenêtre. Voici un exemple d'implémentation standard de fenêtre :

    • https://github.com/qt/qtbase/blob/dev/tests/manual/rhi/shared/examplefw.h

    Il est également important de noter que les ressources créées avec QRhi doivent être nettoyées avant la destruction de QRhi. L'utilisation de pointeurs intelligents permet de gérer efficacement le cycle de vie de ces ressources.

    QRhiWidget¶

    La principale différence entre Widget et Window est :

    • Widget déclenche le redessin de l'interface via certains événements, tandis que Window redessine à chaque frame.

    L'utilisation de Widget permet de mieux économiser les performances et d'éviter des rafraîchissements inutiles, mais pour les interfaces nécessitant un rafraîchissement en temps réel (comme les jeux et les applications graphiques), l'utilisation de Window permet de mieux répartir la charge de rendu.

    QEngineUtilities¶

    Afin de simplifier l'utilisation de certaines structures, j'ai encapsulé des structures génériques dans QEngineUtilities, qui contient trois cibles de construction :

    • QEngineCore : Architecture de rendu, incluant des encapsulations simplifiées de RHI, FrameGraph, RenderPass, RenderComponent et Asset.
    • QEngineEditor : Suite d'édition, incluant de nombreux contrôles de réglage de propriétés de base (régulateur de valeur, sélecteur de couleur, bulle de notification, DetailView basé sur QObject, éditeur de code GLSL, etc.).
    • QEngineUtilities : Couche de lancement, qui assemble les deux modules ci-dessus selon différentes configurations de construction. Par exemple, en configuration DebugEditor, l'interface d'édition est intégrée ; en configuration Debug, seul le module Core est présent.

    Vous pouvez cloner ce dépôt :

    • Dans le fichier CMakeLists.txt de votre projet, utilisez add_subdirectory pour ajouter QEngineUtilities
    • Liez votre Target à QEngineUtilities
    • Dans cmake, utilisez la fonction qengine_setup_env pour configurer les variables d'environnement de votre Target (ajouter le chemin de recherche des DLL)

    Il est principalement utilisé pour l'enseignement et les essais :

    • La lisibilité est la priorité absolue.
    • Les performances ne sont pas optimisées en détail (il y a quelques défauts dans les détails du code, que j'ai remarqués trop tard. En raison de contraintes de temps, je dois妥协 pour l'instant. Désolé... Mais restez assuré : ces impacts sont minimes).
    • Centré sur le rendu, incluant une architecture d'édition basique, sans modules qui gonfleraient le code (gestion des assets, réseau, asynchrone, ECS, etc.).

    Si tout se passe bien, vous pouvez utiliser le code suivant pour créer un Widget et une Window :

    #include <QApplication>
#include "Render/RHI/QRhiWidget.h"
#include "Render/RHI/QRhiWindow.h"

class ExampleRhiWindow : public QRhiWindow {
public:
    ExampleRhiWindow(QRhiWindow::InitParams inInitParams) : QRhiWindow(inInitParams) {}
protected:
    virtual void onRenderTick() override {
        QRhiRenderTarget* renderTarget = mSwapChain->currentFrameRenderTarget();
        QRhiCommandBuffer* cmdBuffer = mSwapChain->currentFrameCommandBuffer();

        const QColor clearColor = QColor::fromRgbF(0.0f, 0.0f, 1.0f, 1.0f);         // Effacer l'écran en bleu
        const QRhiDepthStencilClearValue dsClearValue = { 1.0f, 0 };

        cmdBuffer->beginPass(renderTarget, clearColor, dsClearValue);
        cmdBuffer->endPass();
    }
};

class ExampleRhiWidget : public QRhiWidget {
public:
    ExampleRhiWidget() {
        setDebugLayer(true);        // Activer la couche de vérification
    }
    void render(QRhiCommandBuffer* inCmdBuffer) override {
        const QColor clearColor = QColor::fromRgbF(1.0f, 0.0f, 0.0f, 1.0f);         // Effacer l'écran en rouge
        const QRhiDepthStencilClearValue dsClearValue = { 1.0f, 0 };
        inCmdBuffer->beginPass(mRenderTarget.data(), clearColor, dsClearValue);
        inCmdBuffer->endPass();
    }
};

int main(int argc, char **argv){
    QApplication app(argc, argv);

    QRhiWindow::InitParams initParams;
    ExampleRhiWindow window(initParams);
    window.setTitle("01-RhiWindow");
    window.resize({ 400, 400 });
    window.show();

    ExampleRhiWidget widget;
    widget.setWindowTitle("01-RhiWidget");
    widget.setApi(QRhiWidget::Vulkan);
    widget.resize({ 400, 400 });
    widget.show();

    return app.exec();
}
