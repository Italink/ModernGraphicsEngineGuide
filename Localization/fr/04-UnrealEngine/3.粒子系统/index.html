    Système de particules (Particle System)¶

    Le système de particules (Particle System) représente une technique en infographie 3D pour simuler certains phénomènes flous, que d'autres techniques de rendu traditionnelles ont du mal à reproduire avec un mouvement physique réaliste. Les phénomènes souvent simulés avec des systèmes de particules incluent le feu, les explosions, la fumée, les flux d'eau, les étincelles, les feuilles mortes, les nuages, le brouillard, la neige, la poussière, les traînées de météores ou des effets visuels abstraits comme les traînées lumineuses, etc.

    《Baidu Baike》— Système de particules

    Principe¶

    Le système de particules est principalement utilisé pour rendre un grand nombre d'objets en mouvement. Son flux de travail central n'est pas compliqué : les développeurs familiarisés avec les API graphiques savent qu'il faut appeler DrawCall pour dessiner un objet avec le GPU. Comme un système de particules contient de très nombreuses petites particules, une approche classique pourrait être la suivante :

    for(int i = 0; i < particles.num(); i++){
    drawParticle(particles[i]);
}

    Cette méthode fonctionne bien, mais en raison de la multitude d'appels DrawCall et des nombreuses données redondantes entre les particules, le coût de rendu du système de particules devient très élevé, limitant ainsi le nombre de particules qu'il est possible de rendre.

    Pour réutiliser au maximum les données des particules et réduire les DrawCall, les développeurs pensent immédiatement à l'instanciation (Instancing).

    Pour en savoir plus sur le concept et l'utilisation de l'instanciation, consultez :

    • Learn OpenGL - Instancing

    Grâce à l'instanciation, les DrawCall du système de particules peuvent être fusionnés et les données identiques entre les particules peuvent être réutilisées.

    En comprenant ces concepts, on réalise que le système de particules n'est qu'un flux de travail utilisant le rendu instancié. En réfléchissant à la création d'effets de particules sous cet angle, on se concentre sur deux points :

    • Comment construire les données d'instanciation (Instance Data) nécessaires au système de particules.
    • Comment utiliser ces données d'instanciation pour rendre l'effet de particules.

    En partant de ces deux perspectives, il devient facile de mettre en place le pipeline de travail d'un système de particules. Les sections suivantes décriront principalement les détails d'un système de particules du point de vue de l'architecture :

    Pour une particule simple, on pourrait utiliser une structure de données comme celle-ci :

    struct Particle{        // Structure des propriétés d'une particule 
    vec3 position;
    vec3 rotation;
    float size;
    float age;
    //...
}

    Dans la plupart des architectures de systèmes de particules, on utilise une structure appelée émetteur de particules (Particle Emitter). Celui-ci gère un pool de particules (Particle Pool) contenant les données, et est responsable de la génération (Spawn), de la mise à jour (Update) et du recyclage (Recycle) des particules. En utilisant un renderer de particules (Particle Renderer) pour rendre les données du pool de particules, on obtient l'effet de particules. Ce processus peut être résumé comme suit :

    class ParticleEmitter{
protected:
    void Tick() override{
        Spawn();                // Phase de génération : création de nouvelles particules
        UpdateAndRecycle();     // Phase de mise à jour : mise à jour des données d'état de chaque particule et recyclage des particules mortes
        Render();               // Phase de rendu : utilisation du renderer de particules pour afficher l'effet de particules
    }
private:
    vector<Particle> mParticlePool;
    ParticleRenderer mParticleRenderer;
};

    Pool de particules¶

    Étant donné que les ressources mémoire de l'ordinateur sont limitées, le système de particules doit garantir que l'occupation mémoire du pool de particules ne continue pas de croître au fil du temps. Pour cela, le système de particules utilise souvent les moyens suivants :

    • Limiter le nombre de particules émises.
    • Les particules ont un cycle de vie ; celles qui dépassent ce cycle sont recyclées rapidement.

    Cela fournit également une base pour l'optimisation mémoire du pool de particules :

    • Connaissant le nombre de particules émises, leur cycle de vie et le nombre maximum de frames par seconde du système, il est facile d'estimer le nombre maximum de particules pour cet émetteur. La mémoire correspondant à ce nombre est généralement allouée dès le début au pool de particules, évitant ainsi les coûts liés à la réallocation mémoire du pool.
    • Pour permettre le recyclage parallèle du pool de particules (éviter de déplacer les éléments suivants pour remplir la position d'un élément supprimé dans un tableau), on utilise souvent deux pools de particules identiques qui s'itèrent alternativement.

    Si on voulait mettre à jour et recycler les particules, on pourrait écrire un code comme celui-ci :

    vector<Particle> ParticlePool;
ParticlePool.reserve(10000);            // Allocation préalable de mémoire pour 10000 particules

int index = -1;
for(int i = 0; i < ParticlePool.size(); i++){
    if(ParticlePool[i].isAlive()){
        index++;
        ParticlePool[index] = ParticlePool[i];
        ParticlePool[index].position = ...;
        ParticlePool[index].size = ...;
        ...;
    }
}
ParticlePool.resize(index);

    La complexité logique est O(n). Si on voulait optimiser davantage en parallélisant la boucle for, le code ci-dessus ne le permet pas pour deux raisons :

    • La logique interne de la boucle lit et écrit une variable publique externe index.
    • La lecture et l'écriture simultanées sur différentes zones de ParticlePool entraîneraient un désordre dans l'exécution parallèle et une confusion des données.

    Pour résoudre ce problème, on utilise généralement deux ParticlePool qui se traitent alternativement, et on utilise des opérations atomiques pour lire et écrire index dans les threads locaux. Ainsi, la structure de ParticleEmitter deviendrait :

    class ParticleEmitter{
protected:
    void InitPool(){
        mParticlePool[0].reserve(...);
        mParticlePool[1].reserve(...);
        mCurrentPoolIndex = 0;
        mNextPoolIndex = 1;
        mCurrentNumOfParticle = 0;
    }
    void Tick() override{
        Spawn();                
        UpdateAndRecycle();     
        Render();               
    }
private:
    vector<Particle> mParticlePool[2];
    int mCurrentPoolIndex;
    int mNextPoolIndex;
    int mCurrentNumOfParticle;

    ParticleRenderer mParticleRenderer;
};

    Phase de génération¶

    La phase de génération des particules consiste à créer de nouvelles particules, à les stocker dans le pool de particules et à les initialiser. Ce processus peut être résumé comme suit :

    void Spawn(){ 
    SpwanPerFrame(mParticlePool[mCurrentPoolIndex], mCurrentNumOfParticle, 100);        // Générer 100 particules par frame
}

// Mécanisme d'émission (personnalisable)
void SpwanPerFrame(vector<Particle>& ParticlePool, int& NumOfParticle, int NumOfNewParticle){
    for(int i = 0; i < NumOfNewParticle ; i++ ){            // NumOfNewParticle : nombre de particules à ajouter
        Particle& NewParticle =  ParticlePool[NumOfParticle];   
        NumOfParticle++;
        InitializeParticle(NewParticle);
    }
}

// Mécanisme d'initialisation (personnalisable)
void InitializeParticle(Particle& particle){
    particle.position = vec3(0.0f, 0.0f, 0.0f);
    //particle...
}

    Il est important de noter que la fonction Spawn est appelée à chaque frame. En plus du mécanisme d'émission qui génère un nombre fixe de particules par frame, l'émetteur peut également générer un nombre "fixe" de particules par seconde. Cependant, le nombre de frames par seconde du jeu étant imprévisible selon l'environnement du système, il est difficile de contrôler précisément le nombre de particules pour ce type de mécanisme où le nombre d'émissions dépend de la période.

    Phase de mise à jour et de recyclage¶

    Le pseudo-code de cette phase peut être résumé comme suit :

    void UpdateAndRecycle(){    
    int IndexOfNextBuffer = -1;             // Index initial
    for_each_thread(int i = 0 ; i < mCurrentNumOfParticle ; i++){       // Boucle parallèle
        const Particle& CurrentParticle = mParticlePool[mCurrentPoolIndex][i];
        if(CurrentParticle.isActive()){ 
            int CurrentIndex = atomicAdd(IndexOfNextPool, 1);           // Utiliser une opération atomique pour lire et écrire la variable publique externe
            Particle& NextParticle = mParticlePool[mNextPoolIndex][CurrentIndex];
            UpdateParticleStatus(CurrentParticle, NextParticle);
        }
    }
    CurrentParticlesBufferSize = IndexOfNextBuffer; // Mettre à jour le nombre de particules vivantes
    swap(mCurrentPoolIndex, mNextPoolIndex);            // Échanger les indices du pool de particules courant
}

// Mécanisme de mise à jour de l'état des particules (personnalisable)
void UpdateParticleStatus(const Particle& CurrentParticle, Particle& NextParticle){
    NextParticle.position = CurrentParticle.position;
    //NextParticle...
}

    Phase de rendu¶

    Le rendu lui-même consiste simplement à utiliser les données des particules pour effectuer le rendu. Son processus de base peut être résumé comme suit :

    void Render(){
    mParticleRenderer.BindAttribute("position", mParticlePool[mCurrentPoolIndex], offset0, stride0);
    mParticleRenderer.BindAttribute("color", mParticlePool[mCurrentPoolIndex], offset1, stride1);
    ...;
    mParticleRenderer.drawInstancing();
}

    Cette phase montre la nature essentielle des particules : une particule n'est qu'un ensemble de données, et le système de particules (émetteur) ne fait que traiter ces données en masse, en les liant aux emplacements d'attributs du renderer de particules, afin de réaliser le rendu de l'effet de particules.

    CPU VS GPU¶

    Comme mentionné précédemment, le système de particules consiste essentiellement à traiter un ensemble de données de particules, qui peuvent être divisées en :

    • Phase de génération et phase de mise à jour et de recyclage : ces deux phases traitent principalement les données des particules. Niagara propose des scripts visuels pour permettre des opérations personnalisées sur ces deux phases. En fin de compte, le script sera :
    • CPU : le code C++ assemblé via des nœuds est exécuté dans la machine virtuelle de Niagara.
    • GPU : Niagara traduit le graphe de nœuds en code HLSL correspondant via le NiagaraHlslTranslator, qui est ensuite appelé par le ComputeShader.
    • Phase de rendu : que ce soit pour les particules CPU ou GPU, on peut utiliser le même renderer. La différence réside dans le fait que les particules CPU nécessitent que leurs données soient envoyées au GPU, tandis que les données des particules GPU se trouvent déjà sur le GPU et n'ont pas besoin d'être transmises.

    Le processus est logiquement similaire, mais il est important de noter le recyclage des particules GPU. Le ComputeShader appelle les particules GPU pour les traiter en parallèle, mais lors de la phase de mise à jour et de recyclage, il faut réorienter les données. La raison pour laquelle le GPU peut traiter en parallèle de manière efficace est que les données de chaque branche ne communiquent pas entre elles et ne s'influencent pas mutuellement. Pour implémenter le recyclage des particules GPU, il faut "rompre" cette règle. Actuellement, il existe deux principales approches pour atteindre cet objectif :

    • Pipeline de rendu graphique : désactiver le rastérisation, utiliser TransformFeedback (OpenGL) / Stream Output (DX), et recycler (sans soumettre) les particules mortes dans le Geometry Shader.

    Le Geometry Shader lui-même effectue des opérations linéaires, car ce processus génère un nombre variable de nouveaux sommets. Le GPU doit certainement verrouiller et réorienter les données lors de leur écriture en mémoire, ce qui explique pourquoi certaines personnes utilisent TransformFeedback et Stream Output pour créer des particules GPU. C'est aussi la raison pour laquelle il faut essayer d'éviter le GS dans les jeux. Par ailleurs, Stream Output est une fonctionnalité正统e de DX, tandis que TransformFeedback n'est pas très bien pris en charge par Khronos : Vulkan n'offre même pas de support officiel, et Metal n'a pas d'API correspondante.

    • Pipeline de calcul général : SSBO Atomic. Avec la mise à jour du matériel, les pilotes de rendu des versions récentes prennent généralement en charge le SSBO (Shader Storage Buffer Object). Notre point de focalisation principal ici est que le SSBO prend en charge les opérations atomiques. Avec cette fonctionnalité, on peut traiter les particules en parallèle dans le CS et utiliser les opérations atomiques pour réorienter les données des particules (c'est-à-dire NewIndex dans le pseudo-code ci-dessus). Pour les nouvelles données de particules, on peut utiliser une autre fonctionnalité : le rendu indirect (Indirect Draw), qui appelle directement DrawCall en utilisant les données du GPU. Ainsi, la transmission des particules entre le CPU et le GPU est évitée tout au long du processus. Voici un exemple simple de code GLSL :
    layout (local_size_x = LOCAL_SIZE) in;
struct Particle {
    vec3 position;
    vec3 rotation;
    vec3 scaling;
    vec3 velocity;
    float life;
};
layout(std140, binding = 0) buffer InputParticlesBuffer{
    Particle inputParticles[PARTICLE_MAX_SIZE];
};
layout(std140, binding = 1) buffer OutputParticlesBuffer{
    Particle outputParticles[PARTICLE_MAX_SIZE];
};
layout(std140, binding = 2) buffer ParticleRunContext{
  int inputCounter;           // Valeur initiale : nombre actuel de particules
  int outputCounter;          // Valeur initiale : -1
  float duration;
  float lifetime;
};

#define inID  gl_GlobalInvocationID.x
#define inParticle inputParticles[inID]

void main(){                                              // Attention : la parallélisation du GPU est non ordonnée
    if(inID >= inputCounter || inParticle.life > lifetime)        // Ici, on peut optimiser avec la fonction step
        return;
    uint outID = atomicAdd(outputCounter, 1);             // atomicAdd est une fonction native de GLSL, mais l'objet à manipuler doit provenir du SSBO
    outputParticles[outID].life = inParticle.life + duration;
}

    Shader Storage Buffer Object (Shader Storage Buffer Object) est utilisé pour fournir des données de tampon lisibles et écrivables.

    Son utilisation est presque identique à celle de UniformBuffer. Les différences principales sont les suivantes :

    • Storage Buffer peut demander une très grande quantité de mémoire vidéo : la spécification OpenGL garantit que la taille de UniformBuffer peut atteindre 16KB, tandis que Storage Buffer peut atteindre 128MB.
    • Storage Buffer est écrivable et même compatible avec les opérations atomiques : la lecture et l'écriture de Storage Buffer peuvent être désordonnées, il faut donc souvent ajouter des barrières mémoire pour garantir la synchronisation.
    • Storage Buffer prend en charge le stockage variable : cela signifie que dans un bloc de Storage Buffer, on peut définir un tableau sans limite, comme int arr[];. Dans le shader, on peut obtenir la longueur du tableau avec arr.length, tandis que dans un bloc de UniformBuffer, il faut spécifier explicitement la taille du tableau lors de sa définition.
    • Dans les mêmes conditions, l'accès à SSBO est plus lent que celui à Uniform Buffer : Storage Buffer est généralement accédé comme une texture de tampon, tandis que les données de Uniform Buffer sont lues via la mémoire accessible par le shader interne.

    Fonctionnellement, SSBO peut être considéré comme une interface meilleure pour la texture de tampon lorsqu'il est accédé via Image Load Store.

    OpenGL fournit une fonctionnalité AtomicCounter, qui est essentiellement cette caractéristique.

    Le recyclage des particules GPU est ainsi réalisé, mais cela pose un problème sérieux : chaque fois que le recyclage est effectué, le nombre de particules change. Cependant, les données se trouvent sur le GPU, et l'appel de DrawCall par le CPU doit connaître ce paramètre.

    Il est certainement impossible de lire les données depuis le GPU, car les API graphiques modernes utilisent un cache d'instructions pour accélérer le rendu. En d'autres termes, à un moment donné, le cache d'instructions du GPU peut contenir des instructions de deux frames ou plus qui n'ont pas encore été traitées. Si on voulait lire les données, il faudrait garantir que l'instruction actuelle est exécutée immédiatement, ce qui bloquerait le thread de rendu et attendrait le retour des données. Cette opération est fatale pour tout le moteur, mais heureusement, il existe une solution.

    Dans la mise à jour d'OpenGL 4.0, une nouvelle fonctionnalité a été introduite : Indirect Rendering (rendu indirect, aussi appelé Indirect Draw), qui permet d'utiliser les données du GPU comme paramètres de DrawCall. Voici la définition officielle :

    Indirect Rendering

    Le rendu indirect permet d'utiliser directement les données du GPU comme paramètres de DrawCall. Par exemple, les paramètres de glDrawArrays incluent le type de primitive, le nombre de sommets et le sommet de départ. Lorsque l'on utilise la commande de dessin indirecte glDrawArraysIndirect, les paramètres correspondants sont obtenus depuis un objet tampon.

    Cette fonctionnalité évite le trajet GPU->CPU->GPU en permettant au GPU de déterminer les paramètres à rendre, tandis que le CPU ne décide que quand envoyer la commande de dessin et quel Primitive utiliser pour cette commande.

    En recherchant "Indirect" dans le code source de Niagara, on peut trouver la définition de son utilisation. Sa structure principale se trouve dans :

    • NiagaraVertexFactories\Public\NiagaraDrawIndirect.h
    • Niagara\Private\NiagaraGPUInstanceCountManager.cpp

    Avantages et inconvénients¶

    • Particules CPU

    • Avantages

      • Le CPU peut accéder à l'environnement de jeu complet et interagir avec d'autres particules ou la logique du jeu.
      • Pas besoin de configuration matérielle élevée ; il suffit que la carte graphique prenne en charge le pipeline programmable et le rendu instancié.

    • Inconvénients

      • On ne peut itérer les données des particules que de manière linéaire sur le CPU, ce qui consomme beaucoup de performances CPU.
      • Les données des particules se trouvent dans la mémoire du CPU ; lors du rendu, il faut envoyer toutes les données des particules au GPU, et ce processus de transmission est extrêmement coûteux.

    • Particules GPU

    • Avantages

      • Les données des particules sont générées et traitées全程 sur le GPU, évitant la transmission de données entre le CPU et le GPU.
      • Les données des particules sont traitées par les unités parallèles du GPU, réduisant considérablement le temps nécessaire au traitement des particules.

    • Inconvénients

      • Les données des particules GPU se trouvent dans la mémoire vidéo, et il est impossible de calculer en temps réel les limites de la boîte englobante. Il faut donc spécifier manuellement des limites fixes pour les particules GPU.
      • Elles ne peuvent pas interagir bien avec l'environnement de jeu, mais on peut approcher l'effet via la profondeur, la capture de scène (Scene Capture) ou le champ de distance.
      • Elles ont des exigences sur la configuration matérielle : il faut prendre en charge CS, SSBO Atomic et Indirect Draw (les cartes graphiques dédiées sur PC sont généralement compatibles, mais le support sur mobile n'est pas très完善).

    Niagara¶

    Le système Niagara d'Unreal Engine est très puissant. Il s'agit essentiellement d'un processeur de données programmable (CPU ou GPU) et d'un renderer instancié. En réfléchissant à partir de ce niveau, on peut réaliser de nombreux effets étonnants.

    Portée (Scope)¶

    La plupart des articles appellent cette portée "espace de noms". Bien qu'elle joue effectivement un rôle dans la distinction des noms de variables, ce qui est plus important pour les développeurs est le cycle de vie représenté par la portée de ces variables.

    Voici la structure générale de Niagara dans UE, où la partie jaune représente la portée des variables gérables dans Niagara :

    Dans l'éditeur Niagara, vous pouvez ajouter, supprimer ou modifier des variables de ces portées via le panneau des paramètres.

    • EngineProvided : Cette portée est principalement utilisée pour lire des variables depuis le moteur, comme DeltaTime.

    • System Attribute : Variable d'attribut détenue par un seul système de particules.

    • Emitter Attribute : Variable d'attribut détenue par un seul émetteur de particules.

    • Particle Attribute : Variable d'attribut détenue par une seule particule.

    • Module Inputs : Variable d'entrée du module, c'est-à-dire la variable que le module expose à l'extérieur pour la configuration. Elle s'affichera dans le panneau de configuration du module :

    • Static Switch Inputs : Variable d'entrée de branche statique du module, utilisée pour optimiser les branches logiques du script à la compilation.

    • Module Locals : Variable locale du module.

    • Module Outputs : Variable de sortie du module.

    • Stage Transients : Variable temporaire de phase.

    • User Expose : Variable exposée à l'utilisateur. Ces variables sont principalement destinées à être appelées par des modules externes à Niagara (C++ ou Blueprint). Au niveau du bas, elles sont本质iellement différentes des autres variables, comme expliqué ci-dessous.

    Pour plus de détails sur la signification de ces portées, vous pouvez consulter : UE4 : Variables de Niagara et HLSL - Zhihu (zhihu.com)

    Cœur du bas niveau — FNiagaraDataSet¶

    Les attributs de Niagara sont eux-mêmes un ensemble de données. La structure correspondante dans le code est FNiagaraDataSet (à l'exception de User Expose). Sa structure simplifiée est la suivante :

    class FNiagaraDataSet{
    /** Tableau des IDs libres disponibles pour l'allocation au prochain tick. */
    TArray<int32> FreeIDsTable;

    /** Nombre d'IDs libres dans FreeIDTable. */
    int32 NumFreeIDs;

    /** ID maximum vu lors de la dernière exécution. Permet de réduire la taille de IDTable. */
    int32 MaxUsedID;

    /** Tag à utiliser lors de l'acquisition de nouveaux IDs. Doit être unique par tick. */
    int32 IDAcquireTag;

    /** Tableau des IDs générés lors du dernier tick (seulement la partie index, le tag d'acquisition est IDAcquireTag pour tous). */
    TArray<int32> SpawnedIDsTable;

    /** Tampon GPU des IDs libres disponibles au prochain tick. */
    FRWBuffer GPUFreeIDs;

    /** Nombre d'IDs alloués pour la simulation GPU. */
    uint32 GPUNumAllocatedIDs;

    /**
    Stockage réel des données. Ces tampons sont passés et lus directement par le thread de rendu (RT).
    C'est effectivement un pool de tampons pour cette simulation.
    En général, il ne devrait y avoir que deux ou trois entrées, et on recherche un tampon libre pour écrire dedans lors de BeginSimulate().
    On garde une trace des tampons Current et Previous qui se déplacent à chaque simulation.
    D'autres tampons peuvent être présents ici s'ils sont actuellement utilisés par le thread de rendu.
    */
    TArray<FNiagaraDataBuffer*, TInlineAllocator<2>> Data;

        /** Tampon contenant l'état de simulation actuel. */
    FNiagaraDataBuffer* CurrentData;

    /** Tampon dans lequel on simule actuellement. Valide seulement pendant la simulation, c'est-à-dire entre les appels PrepareForSimulate et EndSimulate. */
    FNiagaraDataBuffer* DestinationData;

    /* Le nombre maximum d'instances est le nombre maximum d'instances autorisées. */
    uint32 MaxInstanceCount;
    /* Le nombre maximum d'allocation est le nombre maximum d'instances que l'on peut allouer, qui peut être supérieur à MaxInstanceCount en raison de l'arrondi. */
    uint32 MaxAllocationCount;
}

    De la structure ci-dessus, on peut voir que FNiagaraDataSet fournit la structure de données nécessaire au processus de base de l'émetteur de particules mentionné au début :

    • Valeur maximale de l'allocation de stockage (capacité, ID).
    • TArray<FNiagaraDataBuffer*, TInlineAllocator<2>> Data est un tampon itéré alternativement par deux, et FNiagaraDataBuffer* CurrentData et FNiagaraDataBuffer* DestinationData sont deux pointeurs vers le tampon, permettant un échange rapide (swap).

    void FNiagaraEmitterInstance::Init(int32 InEmitterIdx, FNiagaraSystemInstanceID InSystemInstanceID){
    const int32 UpdateEventGeneratorCount = CachedEmitter->UpdateScriptProps.EventGenerators.Num();
    const int32 SpawnEventGeneratorCount = CachedEmitter->SpawnScriptProps.EventGenerators.Num();
    const int32 NumEvents = CachedEmitter->GetEventHandlers().Num();

    if (UpdateEventGeneratorCount || SpawnEventGeneratorCount || NumEvents)
    {
        EventInstanceData = MakeUnique<FEventInstanceData>();
        EventInstanceData->UpdateScriptEventDataSets.Empty(UpdateEventGeneratorCount);
        EventInstanceData->UpdateEventGeneratorIsSharedByIndex.SetNumZeroed(UpdateEventGeneratorCount);
        int32 UpdateEventGeneratorIndex = 0;
        for (const FNiagaraEventGeneratorProperties &GeneratorProps : CachedEmitter->UpdateScriptProps.EventGenerators)
        {
            FNiagaraDataSet *Set = ParentSystemInstance->CreateEventDataSet(EmitterHandle.GetIdName(), GeneratorProps.ID);
            Set->Init(&GeneratorProps.DataSetCompiledData);

            EventInstanceData->UpdateScriptEventDataSets.Add(Set);
            EventInstanceData->UpdateEventGeneratorIsSharedByIndex[UpdateEventGeneratorIndex] = CachedEmitter->IsEventGeneratorShared(GeneratorProps.ID);
            ++UpdateEventGeneratorIndex;
        }

        EventInstanceData->SpawnScriptEventDataSets.Empty(SpawnEventGeneratorCount);
        EventInstanceData->SpawnEventGeneratorIsSharedByIndex.SetNumZeroed(SpawnEventGeneratorCount);
        int32 SpawnEventGeneratorIndex = 0;
        for (const FNiagaraEventGeneratorProperties &GeneratorProps : CachedEmitter->SpawnScriptProps.EventGenerators)
        {
            FNiagaraDataSet *Set = ParentSystemInstance->CreateEventDataSet(EmitterHandle.GetIdName(), GeneratorProps.ID);
            Set->Init(&GeneratorProps.DataSetCompiledData);

            EventInstanceData->SpawnScriptEventDataSets.Add(Set);
            EventInstanceData->SpawnEventGeneratorIsSharedByIndex[SpawnEventGeneratorIndex] = CachedEmitter->IsEventGeneratorShared(GeneratorProps.ID);
            ++SpawnEventGeneratorIndex;
        }

        EventInstanceData->EventExecContexts.SetNum(NumEvents);
        EventInstanceData->EventExecCountBindings.SetNum(NumEvents);

        for (int32 i = 0; i < NumEvents; i++)
        {
            ensure(CachedEmitter->GetEventHandlers()[i].DataSetAccessSynchronized());

            UNiagaraScript* EventScript = CachedEmitter->GetEventHandlers()[i].Script;

            //This is cpu explicitly? Are we doing event handlers on GPU?
            EventInstanceData->EventExecContexts[i].Init(EventScript, ENiagaraSimTarget::CPUSim);
            EventInstanceData->EventExecCountBindings[i].Init(EventInstanceData->EventExecContexts[i].Parameters, SYS_PARAM_ENGINE_EXEC_COUNT);
        }
    }
}

    Dans FNiagaraEmitterInstance::Tick, on trouve le code suivant :

    void FNiagaraEmitterInstance::Tick(float DeltaSeconds)
{
    //...
    if (EventInstanceData.IsValid())
    {
        // Set up the spawn counts and source datasets for the events. The system ensures that we will run after any emitters
        // we're receiving from, so we can use the data buffers that our sources have computed this tick.
        const int32 NumEventHandlers = CachedEmitter->GetEventHandlers().Num();
        EventInstanceData->EventSpawnTotal = 0;

        {

            FNiagaraEventHandlingInfo& Info = EventInstanceData->EventHandlingInfo[i];

            Info.TotalSpawnCount = 0;//This was being done every frame but should be done in init?
            Info.SpawnCounts.Reset();

            //TODO: We can move this lookup into the init and just store a ptr to the other set?

            {
                Info.SetEventData(&EventSet->GetCurrentDataChecked());
                uint32 EventSpawnNum = CalculateEventSpawnCount(EventHandlerProps, Info.SpawnCounts, EventSet);
                Info.TotalSpawnCount += EventSpawnNum;

    Conseils d'utilisation¶

    En plus de rechercher des effets artistiques, les effets spéciaux doivent également garantir :

    • Le système de particules a une boîte englobante et une extensibilité correctes, sinon des problèmes comme les particules disparaissant莫名其妙 peuvent survenir dans la scène.
    • Le cycle de vie des effets Spawn est strictement contrôlé, évitant les conflits entre la Pool Method et les opérations de traitement du cycle de vie (pré-cadrage, élimination par extensibilité, AutoDestroy).

    Concernant l'optimisation, il faut savoir :

    • Comment réduire le nombre d'émetteurs de particules ?

    Idéalement, si deux émetteurs utilisent exactement les mêmes paramètres de renderer, ils devraient utiliser le même émetteur.

    Parce qu'un renderer dans un émetteur correspond à un pipeline de rendu graphique, et le système de particules consiste essentiellement à traiter les données d'instanciation nécessaires au pipeline de rendu graphique.

    Chaque émetteur supplémentaire ajoute des données de rendu et nécessite de maintenir un tampon de particules supplémentaire.

    Si on veut seulement ajuster le mécanisme de mouvement des particules, on peut l'étendre via un module personnalisé.

    • Comment déterminer s'il faut utiliser des particules CPU ou GPU ?

    Les particules CPU peuvent calculer dynamiquement les limites de la boîte englobante, mais elles ne sont adaptées qu'au rendu de peu de particules.

    Les particules GPU peuvent être utilisées pour rendre un grand nombre de données de particules, mais il faut leur spécifier des limites de boîte englobante précises.

    La ligne de séparation principale est le nombre de particules. Si le nombre de particules est de l'ordre de mille ou de dix mille, il faut absolument utiliser des particules GPU.

    Pour peu de particules, par exemple quelques-unes, il est recommandé d'utiliser des particules CPU.

    • Si on est obligé d'utiliser des particules CPU pour des raisons d'effet, il faut principalement考虑 deux points :

    • L'exécution des particules CPU est sérielle, et avec l'augmentation de la complexité du système de particules, la consommation de performances augmente de manière exponentielle.

    • Le goulot d'étranglement des performances des particules CPU dans le thread de rendu est principalement la transmission des données des particules (bande passante limitée), ce qui explique pourquoi elles ne sont pas adaptées au rendu de beaucoup de particules.

    • Le fonctionnement du système de particules est différent de celui d'un Pipeline classique. Si c'est un objet unique placé dans la scène, il faut考虑 utiliser un Actor (Game Object) plutôt qu'un système de particules.

    • Outre le contrôle de la complexité et du nombre du système de particules, on peut également réduire la consommation de performances des particules par d'autres moyens :
    • Éviter l'encombrement des particules et réduire l'Overdraw.
    • Limiter la transparence.

    • ...

    • Générer les données nécessaires à la simulation Niagara hors ligne (lors de l'édition).
