    Editor Architecture¶

    Most of the code I've accumulated in development over the past few years has been spent on engine editors. Here, I'll list some insights for your reference. This article will analyze how to design a good editor from the following dimensions:

    • Design Aesthetics
    • User Experience
    • Reflection-Based Editor Architecture
    • Performance Optimization

    Design Aesthetics¶

    Design aesthetics is something most developers lack, as they spend a great deal of effort on code and rarely want to rack their brains figuring out how to create exquisite interfaces.

    Of course, although they don't have a design-oriented mind, they do have an eye for appreciating beautiful things. With suitable references, developers can quickly replicate corresponding effects.

    In most software development teams, there are usually professional UI designers who mainly focus on:

    • Typography
    • Color Palette
    • Icons
    • Layout

    Among some software systems I've used, some do consider the above points and create exquisite interface effects, but often overlook componentized design of the UI, leading to:

    • Users being unable to quickly establish usage patterns for the software, resulting in heavy cognitive load.
    • Disruption of the software's code structure. A well-componentized UI allows the code hierarchy to be seen from the interface, while a disorganized interface usually corresponds to messy code.

    Take Unreal Engine as an example; its componentized design is very intuitive:

    Users only need to understand and master the responsibilities of each component element on the interface. In many cases, they can operate by analogy without relying on tutorials or documentation.

    UI designers mostly focus on UI effects, so it's often difficult for them to create a componentized design suitable for the code architecture. Therefore, developers need to think about, discuss, guide, and learn to say "no" regarding this aspect.

    For more detailed references on UI design concepts and styles:

    • All Time Design - UI Style Guide

    User Experience¶

    User experience mainly revolves around:

    • Reducing users' cognitive load: Following common sense and norms in interface layout, label naming, and operations
    • Supporting undo and redo: Allowing quick correction of misoperations
    • Reasonable operation feedback: Using logs, dialog boxes, progress bars, notification bubbles, status bars, etc., to inform users of the execution status when operations are performed
    • Timely state backup or saving: Preventing loss of large amounts of work data due to unexpected crashes
    • Configurable operation methods: Allowing users to customize shortcuts, layout methods, operation styles, etc.

    For reducing users' cognitive load, here are very comprehensive documents:

    • O3DE - Component Card UX Pattern

    • O3DE - Component Card Error Handling

    Regarding undo and redo, it's a code design issue. Typically, we use the Memento pattern and Command pattern at the design pattern level to implement undo and redo functionality. In Qt, the corresponding structures are QUndoCommand and QUndoStack, where the core definition of QUndoCommand is as follows:

    class QUndoCommand
{
    virtual void undo();
    virtual void redo();
    virtual int id() const;
    virtual bool mergeWith(const QUndoCommand *other);
};

    When using it, we derive from QUndoCommand, override the functions to implement undo and redo behaviors, and then push the specific Command into the UndoStack.

    Here's a simple code example:

    #include <QUndoCommand>
#include <QUndoStack>
#include <QDebug>

class QAssignCommand : public QUndoCommand {
public:
    QAssignCommand(int* ptr, int dstValue)
        : mValuePtr(ptr)
        , mSrcValue(*ptr)
        , mDstValue(dstValue) {}
protected:
    virtual void undo() override {
        *mValuePtr = mSrcValue;
    }
    virtual void redo() override {
        *mValuePtr = mDstValue;
    }
private:
    int* mValuePtr = nullptr;
    int mSrcValue;
    int mDstValue;
};

int main(int argc, char** argv) {
    QUndoStack stack;
    int value = 0;
    stack.push(new QAssignCommand(&value, 1));
    qDebug() << value;        // 1

    stack.undo();
    qDebug() << value;        // 0

    stack.redo();
    qDebug() << value;        // 1

    stack.beginMacro("Merge");    
    stack.push(new QAssignCommand(&value, 2));
    stack.push(new QAssignCommand(&value, 3));
    stack.endMacro();
    qDebug() << value;        // 3

    stack.undo();
    qDebug() << value;        // 1

    return 0;
}

    Its implementation idea is relatively simple, but there are some tricky points:

    • If the operation object in the Command is destroyed elsewhere but the Command still exists in the Stack, executing undo or redo at this time may cause the program to crash.

    We can mainly solve this problem through the following solutions:

    • Check if the undo/redo command fully covers the lifecycle of the operation object.
    • Add validity verification to the Command.
    • Use serialization to save and reconstruct the object.

    In Unreal Engine, a undo/redo mechanism based on the object system is provided —— Transactional

    For any UObject instance with the RF_Transactional flag, you can use the following code to implement undo and redo:

    GEditor->BeginTransaction(FText::FromString("Assign Value"));    // Start transaction

MyObject->Modify();                                             // Save initial state
MyObject->ValueProperty = 123;                                  // Modify property

GEditor->EndTransaction();                                      // End transaction

    Since UObject's GC allows delayed object recycling, we don't need to consider the lifecycle of the operation object. For its implementation principle, see:

    • CSDN - UE4 Editor (UObject) Undo System Transactional

    Regarding state saving, I believe everyone has encountered sudden program crashes or computer shutdowns. Without timely saving of work data, hours of work成果 may be lost. At this time, if the program provides auxiliary means for saving or backup, it can save you when accidents occur.

    Such means usually refer to auto-save. In addition to letting users manually click to save work data, we can also automatically save or backup work data at specific times, such as:

    • Saving when the user closes an interface
    • Timed auto-save
    • Saving when the program crashes (using the SetUnhandledExceptionFilter function to set a system callback when the program crashes)

    The above methods can minimize the risk of work data loss. Of course, for data with low saving performance overhead, such as small configuration files, you can save immediately after performing operations.

    Meta Thinking¶

    Meta thinking can provide great convenience in modern industrial software development, as it offers a once-and-for-all way to extend code.

    Associated words for meta thinking: derivative, higher dimension, God's perspective, ...

    See details: [Zhihu] bus waiter - Talking about meta

    If writing code is compared to building a house, we usually think about how to build the house well. At the meta level, we think about how to build a machine that automatically builds houses. Meta thinking transforms one engineering problem into another. Although the difficulty increases, with proper methods, it can bring incomparable benefits.

    I have come into contact with some self-developed engines and software. Whenever the topic of self-developed engine editors is mentioned, there are basically complaints.

    The reasons are nothing more than:

    • Crude interface
    • Poor user experience

    Most developers think:

    • "It's not that we can't do it well, but it takes a lot of time and is very troublesome. There's no need to waste time; it's enough to make it usable."

    Of course, this idea is understandable for small tools, but if high-frequency tools are treated with this attitude, it will be a painful torture for users.

    I have accumulated hundreds of thousands of lines of code in Qt, but only tens of thousands of lines in Unreal Engine, yet I have created more complete functions. Moreover, in Unreal Engine, interface style and user experience requirements are very easy to meet, which largely benefits from Unreal Engine's " infrastructure ".

    In game engines, architectures based on the meta concept are everywhere, and among them, the most useful and powerful one is undoubtedly —— reflection-based editor architecture

    I believe everyone has seen some parameter adjustment panels, such as:

    At the code level, these configurable parameters usually correspond to specific data structures, which may look like this:

    struct Options{
    bool            Option0;
    int             Option1;
    string          Option2;
    vector<string>  Option3;
};

    Most developers manually write code to create an editing panel for the data structure Options. At the meta level, we further decompose such complex structures. Since basic types in C++ are limited, the types created by developers are just combinations of those basic types organized in a certain hierarchy. We can completely create controls based on the types of member variables and organize the layout of controls based on the structure of Options. In short, it is type-based controls and structure-based panels

    Since we need to obtain information about the data structure at runtime, we must rely on reflection. In addition, data structure organization is usually tree-like, so we use the TreeView control in the GUI framework to organize the control panel.

    Here's a simple pseudocode:

    class Options: public Object{        // Data structure, Object is the base class of the object system
    OBJECT_ENTRY()                   // OBJECT_ENTRY is the entry macro of the reflection system

    PROPERTY() bool            Option0;    // Use the PROPERTY macro to reflect properties
    PROPERTY() int             Option1;
    PROPERTY() string          Option2;
    PROPERTY() vector<string>  Option3;
};

class DetailView: public TreeView{
public:
    void setObject(Object* object){                                            
        clearTreeView();
        for(auto metaProperty: object->metaObject()){                        // Traverse all properties of the object according to MetaObject
            Widget* widget = generateWidgetForType(metaProperty.type());    // Create a control based on the type
            widget->bind(Object, metaProperty);                             // Bind the control to the reflected property
            this->addRow(widget);                                            // Add the control to the TreeView
        }
    }
};

    For types, we mainly classify them as follows:

    • Basic types: boolean, numeric, enumeration, string
    • Composite types: class, struct
    • Container types:
      • Sequential containers: list, array, vector, set, queue...
      • Associative containers: map, hashmap...

    Through this classification, developers only need to create controls for basic types and organize the property panel layout for composite types. The editing panels for container types are usually automatically generated and combined based on the internal element types. In addition, to allow developers to freely extend basic properties and override object panels and layouts, two structures are generally provided:

    class IDetailCustomization{
public:
    virtual void CustomizeDetails(DetailsBuilder* builder) = 0;        // Used to customize the object's adjustment panel
};

class IPropertyTypeCustomization{
public:
    virtual void CustomizeHeader(RowBuilder* builder) = 0;        // Used to customize the Header Row of the property type
    virtual void CustomizeChildren(DetailsBuilder* builder) {}    // Used to attach the Child Row of the property type
};

    To manage properties, IPropertyHandle is derived, which is mainly used for:

    • Using polymorphism to handle hierarchical organization.
    • Serving as the only entry for property setting and getting, incorporating functions such as undo/redo, change notification, and editor synchronization.
    class IPropertyHandle{
    void SetValue(Variant var);
    Variant GetValue();
    virtual Widget* GenerateNameWidget();        // Generate the name control of the property
    virtual Widget* GenerateValueWidget();        // Generate the value control of the property
    virtual void GenerateChildrenRow(DetailsBuilder* builder);    // Generate the child row of the property
};

    With the support of the above structures, the creation process of DetailsView can be simply regarded as:

    map<typeid, IDetailCustomization*> GloabalDetailCustomizationMap;
map<typeid, IPropertyTypeCustomization*> GloabalPropertyTypeCustomizationMap;

class DetailView: public TreeView{
public:
    void setObject(Object* object){                                            
        clearTreeView();

        auto DetailCustomization = GloabalDetailCustomizationMap[object->metaObject()->type()];    
        DetailsBuilder builder(this);
        DetailCustomization->CustomizeDetails(&builder);
        /* Get the DetailCustomization corresponding to the object type. Calling CustomizeDetails will traverse all its Properties,
        create IPropertyHandle, and IPropertyHandle will create specific property adjustment controls based on the IPropertyTypeCustomization corresponding to the property type.
        */
    }
};

    Performance Optimization¶

    Computing resources of computers are always limited, and in game engines, the main performance consumption is undoubtedly the Game. Therefore, we need to minimize the performance loss of the editor to reduce its impact on Game execution.

    Generally, we can optimize the performance of the editor through the following methods (also applicable to in-game UI):

    • Don't pursue beautiful but high-consumption interface effects:

    • Avoid using interface animations and filters as much as possible (blur, shadow, neumorphism, frosted glass, projection transformation...)

    • Don't use high-resolution image resources

    • For static UI, use pre-made images or pre-rendered RT (Bitmap) as much as possible instead of real-time rendering with the GUI framework every frame, such as the color palette of a color picker:

    • Control the timing of interface redrawing: If a certain operation A triggers an interface update, but sometimes we perform operation A multiple times in one frame, it's obviously unnecessary to redraw the interface multiple times in one frame. Therefore, we usually don't update the UI directly in operation A, but set a flag and redraw the UI according to the flag in the UI's Tick event, like this (pseudocode):

    class MyWidget : public Widget{
private:
    bool bNeedRepaint = false;
public:
    void setFont(...){             // Set font, trigger interface redrawing
        bNeedRepaint = true;
    }

    void tick() override{          // Override the UI's Tick event, check if redrawing is needed during Tick
        if(bNeedRepaint){
            repaintUI();           // UI redrawing interface
            bNeedRepaint = false;
        }
    }  
};

    • Use off-screen drawing cache and partial refresh: For UI with high reusability of the previous frame's image, you can first draw the UI onto an RT (Bitmap), and only update part of the UI as needed every frame. This method is more common in UI related to charts and canvases.

    • Avoid blocking the UI by executing high-consumption logical operations in the main thread: UI processing is usually in the main thread. If some logical operations in the main thread take a long time to execute, it will cause UI blocking. There are two main ways to solve this problem:

    • Insert UI system update operations in logical operations to force UI refresh.

    • Execute logical operations in an asynchronous thread, and then perform UI-related updates in the main thread after the logic is executed.
