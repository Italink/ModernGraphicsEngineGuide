    Landscape Pitfall Avoidance Guide¶

    Overview¶

    As a fundamental graphical element in modern games, Landscape has become increasingly complex with the growing sophistication of graphics engineering and the "younger" composition of R&D teams. Focusing solely on effect implementation and editor usage while ignoring critical details can埋下 significant hidden issues. This article aims to address these aspects.

    In most graphics projects, the most widely used graphical element is undoubtedly the Static Mesh, which uses vertex geometry data (spatial coordinates, UVs, normals...) combined with material textures to render graphical effects:

    Static Meshes play a pivotal role in modern game development, serving as the basic unit for constructing game world geometry. Professional modeling software (such as 3dsMax, Maya, Blender, Zbrush) provides designers with great convenience and freedom to quickly create their desired graphical effects.

    In contrast, Landscape is a more specialized graphical element that does not directly use triangular vertex data like Static Meshes. Instead, it relies on heightmaps:

    This image is generated by https://manticorp.github.io/unrealheightmap

    Each pixel in the heightmap corresponds to an actual vertex coordinate, with the following mapping relationship:

    • Pixel coordinates (XY) > Vertex horizontal coordinates (XY)
    • Pixel grayscale value > Vertex height (Z)

    A heightmap can be regarded as a 2D numerical array, where the basic element type is typically a 16-bit unsigned integer. The corresponding C++ structure is:

    uint16_t HeightMap[Height][Width];

    Actual conversion rules may vary slightly between software. Unreal Engine uses centimeters (cm) as its base unit, with the following conversion rules:

    • Vertex horizontal coordinates are directly converted from pixel coordinates. Without any scaling, the minimum horizontal precision of UE Landscape is 1 cm.
    • Pixel grayscale values are stored as 16-bit unsigned integers, meaning they can distinguish 65536 different height levels. UE does not directly map this to cm; instead, it remaps the values to the floating-point range [-256.0, 255.992]. This means that without any scaling, the vertical height range representable by UE Landscape is -256.0 cm ~ 255.992 cm, with a minimum height precision of 0.0078125 cm.

    Given the above, some readers may have the following question:

    • Static Meshes offer high precision and freedom for achieving the same graphical effects, while Landscape has many limitations. Why do we still use Landscape?

    In fact, the use of Landscape essentially involves a trade-off between scene scale and high precision.

    First, let's discuss the disadvantages of Landscape:

    • Limited horizontal precision: For example, the maximum heightmap size supported by UE5 non-WP maps is 8129. Without scaling, this means the horizontal width it can represent is 81.29 m. To represent a larger area (e.g., stretching by 100x to cover 66.08 km), the minimum horizontal precision becomes 1 m, meaning any geometric details smaller than 1 m will be lost.
    • Limited height range: Without scaling, the height range is -256.0 cm ~ 255.992 cm. To represent a 2000 m mountain, the height must be stretched by 1000x, reducing the minimum height precision to 7.8125 cm and introducing at least a 7 cm error in collision calculations.
    • Single topology: Landscape is essentially a "continuous heightfield grid" that only supports "single-layer undulations" and cannot achieve complex topologies like Static Meshes (e.g., floating platforms, intersecting terrain, underground caves).
    • Coarse editing granularity: Landscape editing relies on "brush painting" (e.g., raising, lowering, smoothing), making it difficult to precisely control individual bumps or depressions through "vertex-level editing" like Static Meshes.
    • Complex collaborative development: Heightmaps and weightmaps are single files, so simultaneous editing by multiple people can cause data overwrites, requiring strict management via version control tools.

    Despite these drawbacks, Landscape remains the only solution for large-scale scenes under current hardware constraints.

    For example, to build a 1 km² scene with a grid plane and ensure an average geometric precision of 10 cm × 10 cm (already a low precision), we would need 100 million (10000×10000) triangular vertices. A single vertex in UE5 Static Meshes typically occupies 28 bytes (position: 12 + tangent X: 4 + tangent Z: 4 + UV: 8), so the uncompressed space required for the entire terrain mesh would be approximately:

    • 28 x 10000 x 10000 ÷ 1024³ ≈ 2.61 GB

    This is just geometric data. Without using Tiled Textures, a 10 cm texel precision would clearly fail to ensure visual quality (resulting in blurriness or pixelation). To guarantee "close-up visual clarity" (e.g., 1 texel per 1 cm × 1 cm of ground), the total number of texture pixels would reach 10 billion. Using 4 channels (ARGB_8888) for color representation, the uncompressed space required would be approximately:

    • 4 x 100000 x 100000 ÷ 1024³ ≈ 37.25 GB

    And this is just for a 1 km² scene!

    In my recent experience, many teams (not just in the game industry) lack a deep understanding of the data scale of graphics scenes. Especially from the perspective of planners/product managers, open scenes are simply about "filling the scene with enough elements to make it larger."

    Against this backdrop, Landscape is almost an inevitable choice when building larger scenes. Beyond the disadvantages mentioned above, it also has several notable advantages:

    • Memory efficiency: Each Landscape vertex requires only 4 bytes (RG channels for height, BA channels for compressed normals), while Static Meshes typically consume 6 to 7 times more memory.
    • Textures: Landscape uses "world-space mapping independent of height." Regardless of how the terrain undulates (raised, flattened, or mountainous), the texture tiling precision remains unchanged, making it easy to use tiled textures. This is difficult for Static Meshes, as modifying the model shape (e.g., changing flat ground to a slope) stretches the texture with the model. Additionally, Static Mesh details rely heavily on texture and UV precision, while Landscape can overlay multiple texture layers (e.g., detail textures, slope textures) on tiled textures to improve depth.
    • LOD: Landscape LOD uses "dynamic simplification based on heightfields." The GPU automatically switches to lower-resolution texture Mip levels via Mipmaps, ensuring rendering efficiency at a distance while avoiding texture stretching. Static Mesh LOD requires creating independent low-precision models for each level.
    • Collision: Landscape uses generated Heightfield Colliders that support destructibility. Their data structure makes collision calculations far more efficient than mesh collision, and their gap-free nature provides better protection against collision penetration than Static Meshes.
    • Workflow: In game engines, Landscape is treated as a basic graphical carrier, with numerous tools and workflows built around it (e.g., vegetation systems, procedural generation of terrain attachments, light baking).

    The official documentation provides detailed instructions on using Landscape, covering concepts, LOD, and collision management:

    • https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-outdoor-terrain-in-unreal-engine

    For an in-depth analysis of Landscape principles, refer to this article:

    • Unreal Engine Landscape System Principle and Source Code Analysis - MarsZhou: https://zhuanlan.zhihu.com/p/668278748

    Planning¶

    For actual game projects, understanding Landscape implementation principles and tool usage is often insufficient. Planning should be established during early design.

    Define Scene Scale¶

    Scene size determines the volume of game content to some extent. Taking the UE standard character as an example (default movement speed: 600 cm/s), moving 1000 m takes 2 minutes and 46 seconds. Use this to estimate the required scene scale based on actual game content.

    When the scene size exceeds 1 km² and contains numerous GameObjects, consider using World Partition to organize scene streaming.

    Note that for very large playable areas (e.g., 64 km²), avoid using a single Landscape for the entire scene. Excessively large scenes significantly increase asset management, map editing, gameplay, and level design complexity, severely slowing project iteration.

    While UE WP maps currently support a maximum Landscape size of 65281, it is recommended that individual Landscape sizes do not exceed 4 km². Iterate on game content in independent sub-levels, with a main map responsible for connecting sub-maps via elements like oceans, rivers, or mountains:

    After UE 5.4, many issues with Level Instances have been effectively resolved, enabling this workflow. The following sections focus on individual Landscape tiles.

    Determine Resolution¶

    After defining the scale of a single Landscape, determine the minimum geometric precision. A horizontal precision of 1 m typically suffices for RPG projects. To add surface details, use the following methods:

    • Normal Map: Modify surface normal directions to affect light reflection, making flat terrain appear to have凹凸 details.
    • Parallax Occlusion Mapping: Calculate "virtual depth offsets" for pixels to give textures apparent thickness, creating a more three-dimensional effect than normal maps.
    • Displacement Mapping: Leverage Nanite and tessellation technology to achieve true geometric凸起 (modify pixel-level height) via displacement maps.
    • Terrain Attachments: Place Static Meshes and decals on the terrain surface to add details. Pay attention to collision performance impacts.

    Define the vertical depth early, as modifying it later after extensive content iteration is cumbersome. Additionally, avoid over-stretching the Z-axis to ensure collision precision. For tall mountains, consider using Static Meshes for filling.

    Balance Streaming Proxies, Components, and Sections¶

    The core structure corresponding to UE Landscape is ALandscape, which manages global data and component hierarchy, including holding basic resources like heightmaps and weightmaps, and controlling overall properties (e.g., physics settings, global LOD parameters).

    To divide ALandscape responsibilities and enable finer-grained LOD management, visibility checks, DrawCalls, collision detection, and material management, the Landscape system introduces Landscape Components (ULandscapeComponent) and Sections.

    Suppose we assign all fine-grained functions to Landscape Components without introducing Sections, using a 2017×2017 resolution heightmap to build a 4 km² scene. Component division faces a dilemma:

    • Few components (e.g., 1 component covering 4 km²): Large vertex data per component makes frustum culling unable to precisely exclude "invisible areas." LOD switching can only be done "globally" (e.g., switching the entire component from LOD0 to LOD3 at a distance, causing significant detail loss). Collision calculations must process full data, reducing efficiency.
    • Many components (e.g., 100 components covering 4 km²): While enabling precise culling and LOD switching, component scheduling (loading/unloading), DrawCall submission, and collider filtering introduce additional overhead, reducing frame rates.

    To resolve this, the UE Landscape system introduces Sections—not a further division of components, but a way to handle fine-grained DrawCalls, LOD, culling, and collision within components. This allows merging component responsibilities to balance reducing component count and fine-grained management.

    Streaming Proxies (ALandscapeStreamingProxy) are a new concept introduced in UE5 World Partition. Since World Partition streams at the Actor level (not Component), streaming proxies divide ULandscapeComponents originally attached to ALandscape into different streaming proxies. A streaming proxy can contain one or more Landscape Components, with division based on the project's desired streaming granularity.

    Notably, streaming proxies have reduced the importance of Sections. In early projects, Landscape Components were typically fully loaded, with optimization via culling, so Sections helped reduce components.

    With World Partition Streaming, combined with HLOD merging, component count can be reduced while significantly optimizing merged geometry and texture data. Thus, Sections have minimal value for WP maps.

    In summary, the relationships between Landscape-related structures are as follows:

    Hierarchical Object Core Responsibilities Dependencies
    Landscape (ALandscape) Manages global data (heightmaps/weightmaps) and unified scheduling Contains 1 or more streaming proxies (WP maps)
    Streaming Proxy Minimum streaming unit for WP,承载 Landscape Components Contains 1 or more Landscape Components
    Landscape Component Manages local data copies (e.g., 100 m×100 m areas) and materials (layer parsing, physical materials, holes) Can be divided into multiple Sections
    Section Handles DrawCalls, LOD, fine-grained culling, and collision calculations Belongs to a single Landscape Component

    Define Scene Ecological Structure¶

    Landscape consists of heightmaps and weightmaps. Heightmaps describe geometric shape, while weightmaps control material expression.

    Most artists have misunderstandings about layer management:

    • One-to-one binding of material effects to layers

    In practice, artists often add layers based on effect requirements (e.g., adding a Grass layer for grass, a Snow layer for snow, followed by Gravel, Dirt, Rock, Mud, Water, Path...). To transition to another scene style, they continue adding materials and layers...

    This incorrect approach leads to the following issues:

    • Limited effects: Landscape weight layers have a maximum count (8 in UE4, 16 in UE5).
    • Poor performance: Excessive weightmap sampling severely degrades Landscape material rendering performance.

    The correct approach is to clarify the relationship between weight layers and Landscape materials:

    • Weight layers are not one-to-one with materials. Landscape materials essentially act as resolvers for weight data. An ALandscape is not limited to one material; the minimum granularity for material management is the Landscape Component (ULandscapeComponent).

    For example, to achieve an effect where each numbered area has specific colors, vegetation, and physical materials, the incorrect approach would use 4 Landscape layers. However, the correct approach uses only 1 layer, with each Landscape Component having its own material:

    UE5 non-WP maps do not expose Landscape Component editing entries; editing requires C++ access. WP map ALandscapeStreamingProxies also manage component properties in batches via specialized property panels, which is why misuse is common.

    Thus, when managing Landscape layers, divide them based on ecological structure (not material effects). Use different materials to parse layers for different ecological communities, avoiding excessive layers and optimizing rendering overhead.

    Since this workflow has a high entry barrier, develop corresponding toolchains to simplify iteration.

    LOD, Nanite, RVT, HLOD¶

    Landscape LOD strategies can be adjusted in the ALandscape property panel.

    UE5 now supports Nanite Landscape, which offers higher culling efficiency and geometric detail. Combined with VSM, Nanite typically outperforms LOD in rendering performance on mid-to-high-end hardware.

    Since Nanite's geometry processing path is incompatible with RVT sampling, Nanite meshes usually do not support RVT writing. However, because Landscape retains original heightmap and weightmap data, the engine submits RVT rendering data via non-Nanite auxiliary channels:

    • https://dev.epicgames.com/documentation/en-us/unreal-engine/using-nanite-with-landscapes-in-unreal-engine

    The latest UE5 version has adjusted the Landscape HLOD generation strategy, implemented in ULandscapeHLODBuilder:

    • Merge all Landscape Components in an ALandscapeStreamingProxy (selecting one LOD level) into a ULandscapeMeshProxyComponent (inheriting from UStaticMeshComponent).

    This approach is inefficient, as it equates streaming granularity with batching granularity. For example, if a Landscape Component is 100 m in size, the streaming proxy range might need to be 200 m (containing 4 components) to allow HLOD merging, significantly increasing streaming costs. A better approach would be one streaming proxy per component, with actual batching based on mesh division granularity.

    Landscape HLOD materials do not require re-baking textures. In practice, projects often use RVT on Landscape and enable SVT for RVT to store low-level Mip levels. Thus, the HLOD material can be specified directly in ALandscape via HLOD Material Override.

    Therefore, Landscape HLOD materials do not need texture inputs; they can directly sample the RVT SVT:

    RVT is widely used in Landscape. For example, distant surface details (e.g., decals, grass) can be baked into the RVT SVT to ensure HLOD material quality at a distance.

    Writing height to RVT is useful for effects like:

    • Rain, snow, water flow: Dynamically control natural effect distribution based on terrain height (elevation) and normal direction (slope).
    • Footprints/stepping effects: Generate footprints matching terrain undulations at character contact points.
    • Explosion/impact marks: Generate dents or scorch marks matching the terrain contour at explosion points.
    • Fog/smoke distribution: Control fog density using terrain height and slope to simulate valley fog or climbing fog.
    • Ground wet/dry transitions: Simulate post-rain drying based on terrain drainage (slope).

    For steps to enable SVT for Landscape RVT, refer to:

    • https://dev.epicgames.com/documentation/zh-cn/unreal-engine/runtime-virtual-texturing-in-unreal-engine

    Note: The article mentions selecting the Use Streaming Low Mips in Editor property in the RVT volume Details panel. In the latest engine version, this property has been renamed to View In Editor. Ensure it is enabled; otherwise, RVT will not read SVT data in the editor.

    Underlying Interfaces¶

    After reading this, you might think, "Wow, Landscape has so many considerations! What if my project is already in trouble?" Don't worry—there's a solution!

    While UE Landscape scheduling and management seem complex, they essentially process underlying textures. Bypassing the UE editor to directly manipulate these images offers great freedom.

    Heightmap and weightmap management are unified in ULandscapeInfo, which can be obtained as follows:

    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();

    The UE heightmap structure is EditLayers, supporting multiple heightmap overlays. Import/export operations are as follows:

    void ExportAllEditLayers(ALandscape* LandscapeActor, FString OutputDir){
    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();
    for (int i = 0; i < LandscapeActor->GetLayerCount(); i++) {
        const FLandscapeLayer* Layer = LandscapeActor->GetLayerConst(i);
        FString ExportFilename = FString::Printf(
            TEXT("%s_%s.%s"),
            *Filename,
            *Layer->Name.ToString().Replace(TEXT(" "), TEXT("_")),
            *Extension
        );
        FScopedSetLandscapeEditingLayer Scope(LandscapeActor, Layer->Guid);             // Set the current editing height layer in context
        LandscapeInfo->ExportHeightmap(FPaths::Combine(OutputDir, ExportFilename));     // Export the current height layer
    }
}

void ImportSingleEditLayer(ALandscape* LandscapeActor, int LayerIndex, FString ImportFilename){
    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();
    const FLandscapeLayer* Layer = LandscapeActor->GetLayerConst(LayerIndex);
    FImage Image;
    FImageUtils::LoadImage(*ImportFilename, Image);
    if (Image.Format != ERawImageFormat::Type::G16) {                                   // Only G16 format is supported
        return;
    }
    FIntRect TargetResolution;
    LandscapeInfo->GetLandscapeExtent(TargetResolution);
    if (Image.SizeX != TargetResolution.Width() + 1 || Image.SizeY != TargetResolution.Height() + 1) {
        FImage ScaledImage;                                                             // Resize the imported image to the terrain resolution
        Image.ResizeTo(ScaledImage, 
                       TargetResolution.Width() + 1,
                       TargetResolution.Height() + 1, 
                       ERawImageFormat::Type::G16, 
                       Image.GammaSpace);
        Image = ScaledImage;
    }
    FScopedSetLandscapeEditingLayer Scope(LandscapeActor, Layer->Guid, [&] {
        LandscapeActor->RequestLayersContentUpdate(ELandscapeLayerUpdateMode::Update_Heightmap_All);
    });
    FHeightmapAccessor<false> HeightmapAccessor(LandscapeInfo);
    HeightmapAccessor.SetData(TargetResolution.Min.X,
                              TargetResolution.Min.Y, 
                              TargetResolution.Max.X, 
                              TargetResolution.Max.Y, 
                              (uint16*)Image.RawData.GetData());
}
