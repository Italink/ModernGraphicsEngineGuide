    Unreal Engine 5 Open World¶

    The author previously compiled a non-technical chat about open worlds:

    This article will explain in more detail what to pay attention to and what challenges you will face when creating an open world with UE5.

    Streaming¶

    By default, newly created Actors in the scene will participate in streaming, meaning they will be unloaded. You can adjust related settings in the Actor's Details panel:

    • Runtime Grid: Which World Partition grid the Actor belongs to. If set to None, it will be assigned to MainGrid.
    • Is Spatially Loaded: If checked, the Actor will participate in World Partition streaming. Unchecking it will keep the Actor permanently loaded in the scene and exclude it from streaming.

    World Partition streaming is triggered by Streaming Sources.

    Multiplayer¶

    In multiplayer, the server does not enable streaming by default; scene streaming is only a local behavior of players:

    Use the command wp.Runtime.EnableServerStreaming 1 to enable streaming on the server:

    Streaming Optimization¶

    World Partition enables streaming optimization by default, which means streaming status is not updated every frame. You can adjust the optimization strategy through the following configurations:

    • wp.Runtime.UpdateStreaming.EnableOptimization true: Defaults to true, enabling streaming optimization.
    • wp.Runtime.UpdateStreaming.ForceUpdateFrameCount 0: Defaults to 0, can set how many frames to fix for updating streaming status.
    • wp.Runtime.UpdateStreaming.LocationQuantization 400: Defaults to 400, triggers streaming status update when movement distance exceeds 400.
    • wp.Runtime.UpdateStreaming.RotationQuantization 10: Defaults to 10, triggers streaming status update when rotation angle exceeds 10.

    Partition¶

    The Actor partition strategy of UWorldPartition is implemented by RuntimeHash. In the editor, RuntimeHash re-partitions every time the map is started, and during packaging, the partition data is also baked:

    bool UWorldPartition::PrepareGeneratorPackageForCook(IWorldPartitionCookPackageContext& CookContext, TArray<UPackage*>& OutModifiedPackages)
{
    check(RuntimeHash);
    return RuntimeHash->PrepareGeneratorPackageForCook(OutModifiedPackages);
}

{
    check(RuntimeHash);
    return RuntimeHash->PopulateGeneratorPackageForCook(InPackagesToCook, OutModifiedPackages);
}

bool UWorldPartition::PopulateGeneratedPackageForCook(IWorldPartitionCookPackageContext& CookContext, const FWorldPartitionCookPackage& InPackagesToCook, TArray<UPackage*>& OutModifiedPackages)
{
    check(RuntimeHash);
    return RuntimeHash->PopulateGeneratedPackageForCook(InPackagesToCook, OutModifiedPackages);

UWorldPartitionRuntimeCell* UWorldPartition::GetCellForPackage(const FWorldPartitionCookPackage& PackageToCook) const
{
    check(RuntimeHash);
    return RuntimeHash->GetCellForPackage(PackageToCook);

    In the editor, when starting an open world map, UWorldPartition::OnBeginPlay is called:

    void UWorldPartition::OnBeginPlay()
{
    TArray<FString> OutGeneratedStreamingPackageNames;
    GenerateStreaming((bIsPIE || IsRunningGame()) ? &OutGeneratedStreamingPackageNames : nullptr);

    // Prepare GeneratedStreamingPackages
    check(GeneratedStreamingPackageNames.IsEmpty());
    for (const FString& PackageName : OutGeneratedStreamingPackageNames)
    {
        // Set as memory package to avoid wasting time in UWorldPartition::IsValidPackageName (GenerateStreaming for PIE runs on the editor world)
        FString Package = FPaths::RemoveDuplicateSlashes(FPackageName::IsMemoryPackage(PackageName) ? PackageName : TEXT("/Memory/") + PackageName);
        GeneratedStreamingPackageNames.Add(Package);
    }

    RuntimeHash->OnBeginPlay();
}

    The GenerateStreaming function further calls UWorldPartition::GenerateContainerStreaming, which recursively searches for all Containers and ActorDescs from the MainContainer.

    After collecting all Containers and ActorDescs, the following function is called:

    bool UWorldPartitionRuntimeSpatialHash::GenerateStreaming(UWorldPartitionStreamingPolicy* StreamingPolicy,
                                                          const IStreamingGenerationContext* StreamingGenerationContext,
                                                          TArray<FString>* OutPackagesToGenerate);

    The main flow of this function is:

    • Collect all grid configurations in the scene (not only WorldSettings contain grid configurations, some Actors also provide them, such as ASpatialHashRuntimeGridInfo, which is currently mainly used for HLOD).
    • Iterate through all ActorDescs and assign them to the corresponding Grid's FActorSetInstance based on the RuntimeGrid configuration in the ActorDesc.
    • For each Grid's FActorSetInstance, call:
    FSquare2DGridHelper GetPartitionedActors(const FBox& WorldBounds, 
                                         const FSpatialHashRuntimeGrid& Grid, 
                                         const TArray<const FActorSetInstance*>& ActorSetInstances)

    to assign all Actors in the Grid to specific Cells.

    Key Issues¶

    World Partition allows us to easily implement seamless loading of large worlds, but the streaming feature also brings many limitations. This often requires developers to have a more mature production team and a professional engine team, fully consider the characteristics of World Partition during design, and need professionals to supervise the streaming strategy of World Partition.

    Cross-Boundary¶

    Observe the previous object partitioning and streaming status:

    You can see some "strange" phenomena:

    • Because the bounding box of object E is on the axis of the World Partition, it is assigned to Level 3, which means it will always be loaded, even though its bounding box area is very small.

    This problem is very easy to occur:

    Solutions¶

    The engine provides some commands to help alleviate this phenomenon:

    • wp.Runtime.RuntimeSpatialHashUseAlignedGridLevels: Whether to enable upward alignment of grid levels.
    • wp.Runtime.RuntimeSpatialHashSnapNonAlignedGridLevelsToLowerLevels: Assign non-aligned objects to lower grid levels.
    • wp.Runtime.RuntimeSpatialHashPlaceSmallActorsUsingLocation: Objects with bounding boxes smaller than the cell size will be partitioned directly using their Location.
    • wp.Runtime.RuntimeSpatialHashPlacePartitionActorsUsingLocation: Partition objects (vegetation, water, and terrain) with bounding boxes smaller than the cell size will be partitioned directly using their Location.

    Loading Priority¶

    Due to World Partition streaming, some moving objects in the scene may behave abnormally. Gravity is one of the most common issues:

    The problems in the image above are:

    • Some cubes are assigned to one cell, while the ground is assigned to another cell due to limitations of the partitioning algorithm. If the cell containing the ground is outside the loading range, the objects will fall through the ground.

    Other situations can also trigger this problem:

    • World Partition streaming is performed per Cell, not per Actor. When a cell is within the loading range of the streaming source, all Actors in that cell are loaded asynchronously. The loading order is not guaranteed. If the cube is loaded before the ground and a physics tick occurs during this period, the object will fall through the ground. (This is more likely to happen when the scene is under heavy load.)
    Solutions¶

    The main ideas to solve this problem are:

    • Make the World Partition grid containing gravity-bearing objects have a larger loading range.
    • Move gravity objects to a World Partition grid with lower loading priority than gravity-bearing objects.

    Data Persistence¶

    Actors participating in World Partition do not have data persistence. When we modify a loaded object, the modified data will not be saved when the object is unloaded.

    For example: There are a group of floating cubes in the World Partition. After loading, they fall to the ground due to gravity. After unloading and reloading, you can see that the cubes have correctly saved their previous state and are on the ground:

    But when we enable the console command gc.ForceCollectGarbageEveryFrame 1 and look again:

    When reloading the cubes this time, they return to their starting position.

    The first example gives us the illusion that object modifications can be saved because cells outside the loading range are not immediately released but are in the Unloaded Still Around state. This ensures they can be reused immediately when loaded next time. The actual unloading of cells occurs during the next GC.

    Solutions¶

    This problem is caused by the characteristics of streaming:

    • Assets are loaded into memory when streaming in and unloaded (resources destroyed) when streaming out, without saving modifications to the assets.

    Does this mean we need to save asset modifications when streaming out?

    • Obviously not, unless you want to make permanent modifications—meaning the previous modifications remain even after restarting the game and cannot be reverted.

    Usually, such modifications only persist within a certain scope (lifecycle), such as after restarting the game, re-entering the level, or reloading a save, these modifications should be lost.

    But what we want now is that streaming does not cause data loss.

    In fact, we only need:

    • To prevent this part of the data from participating in streaming, i.e., store the data in a reasonable scope instead of in the Actor.

    UE5.3 provides an experimental plugin LevelStreamingPersistence to help developers solve this problem.

    This plugin uses ULevelStreamingPersistenceSettings to configure which properties in the engine require persistence:

    When World Partition streams cells, it saves the persistent properties of the outgoing cells according to the above configuration. For incoming cells, it assigns values using previous historical values:

    To solve the gravity problem above, we only need to add the following configuration to DefaultEngine.ini:

    [/Script/LevelStreamingPersistence.LevelStreamingPersistenceSettings]
Properties=(Path="/Script/Engine.SceneComponent:RelativeLocation",bIsPublic=False)
Properties=(Path="/Script/Engine.SceneComponent:RelativeRotation",bIsPublic=False)

    Using PropertyPath to determine which properties often results in a very broad scope. For example, the above configuration serializes the location and rotation of all Scene Components, but not all Scene Components need persistence. The plugin also provides some delegates to further filter which objects need serialization:

    bIsPublic determines whether the saved value of the property can be modified manually, not just automatically serialized based on streaming. The main operation interfaces are located in ULevelStreamingPersistenceManager:

    Runtime Spawning¶

    World Partition partitioning is performed in the editor. Any objects spawned at runtime will not participate in World Partition streaming. Consider this scenario:

    • A gravity-enabled ball is spawned in the scene and falls to the ground. When the character moves away from the area, causing the ground to stream out, the ball will fall through the ground.

    This is obviously not what we want. Generally, all persistent objects except the character should be placed in the map level from the beginning.

    But sometimes there are special requirements:

    • Some scene objects may have runtime event dependencies and must be spawned at runtime.
    Solutions¶
    • If the object's position is fixed, you can place a placeholder Actor in the scene in advance, making it configurable at runtime.
    • If the object is located in a certain area, you can place a Trigger Volume in that area and control the object's lifecycle through trigger logic. If the trigger area is larger than the World Partition loading range, the trigger volume should be placed in a grid with higher loading priority and a streaming source component added.

    Character Teleportation¶

    When teleporting a character in World Partition, since streaming takes time, directly moving the character to the target location may cause the character to fall through the ground due to unloaded surrounding objects.

    Solutions¶

    To solve this problem, we need to preload the target area and wait for loading to complete.

    • Solution 1: Disable the character's tick, teleport the character to the target point, use the character itself as a streaming source to trigger streaming of the surrounding area, and enable the tick when the target area finishes loading via polling (FTSTicker). There is a corresponding reference in the Matrix's Mass framework:

    HLOD¶

    Through World Partition streaming, we can reduce the performance pressure of the entire scene to only the area around the streaming source:

    For game logic, this streaming is certainly an optimization, but for the scene, we don't want distant scenes to be unloaded due to streaming. HLOD solves this problem.

    HLOD is used to display distant views in World Partition. Its usage in open world maps differs from HLOD in regular maps (UE4):

    • World Partition - Hierarchical Level of Detail in Unreal Engine | Unreal Engine 5.3 Documentation (unrealengine.com)

    The official documentation also lacks detailed descriptions of HLOD. For those unfamiliar with its positioning, it's easy to misuse HLOD. The original intention of using HLOD in World Partition is:

    • Merge all Actors in a Cell into a low-precision cell model proxy. When the cell is outside the loading range of the streaming source, this simplified model can be used for display. This reduces rendering costs (using low-precision models and materials) while optimizing occlusion culling calculations (reducing the number of Actors).

    You can set the default HLOD layer configuration for the entire map here:

    Its asset configuration panel is as follows:

    • Layer Type: The strategy used to generate HLOD.
    • Instanced: Uses the lowest LOD of the corresponding model (if it's a Nanite model, it will generate new Nanite data using that LOD).
    • Merged: Merges static meshes within the partition.
    • Simplified: Merges meshes within the partition and performs mesh simplification on the merged mesh. It is more suitable for objects with complex geometries, such as leafy trees.
    • Approximated: Merges meshes within the partition and performs mesh approximation on the merged mesh. It is more suitable for objects with rounded geometries, such as buildings and stones.

    • Custom: Custom HLOD generation strategy.

    • Is Spatially Loaded: Whether the generated HLOD needs to enable streaming. If enabled, an HLOD Grid will be created for this HLOD layer, and the generated HLODActors will be placed in this Grid.

    • Cell Size: Configures the cell size of the HLOD Grid. The value should preferably be an integer multiple of the Main Grid cell size.
    • Loading Range: Configures the loading range of the HLOD Grid. The value should preferably be an integer multiple of the Main Grid cell size.
    • Parent Layer: Uses the parent HLOD layer to process the generated HLOD simplified model again to generate an even more simplified HLOD model, which usually has a larger loading range.

    Notes:

    • The Matrix's scene objects are mostly angular buildings, which uniformly use a customized approximated mesh strategy. When the scene has more complex object types (such as trees, water, vegetation), more refined processing strategies need to be customized, which often requires very strict asset management strategies as support. Additionally, a deep understanding of the HLOD-related code flow and the mesh processing algorithms provided by UE is very valuable for performance optimization of open world projects.
    • HLOD merges the cells of a grid into a simplified model. However, if an area has multiple grids, multiple simplified models will be generated for that area, and models between different grids will not be merged. Therefore, usually, all scene objects should be placed in the MainGrid, and HLOD should be generated only for objects in the MainGrid. For small objects, they can be placed in a grid with a smaller loading range and excluded from HLOD generation.

    Data Layers¶

    Data Layers are a feature provided by UE5 for open worlds, and their usage is similar to Outliner folders:

    But unlike folders, it also provides two key features:

    • You can set default non-loading for this category of Layer when opening the map in the editor.
    • You can load and unload Layers at runtime through related interfaces.

    Why use Data Layers?

    • Data Layers can be used to layer scene objects by category and block by region, which can alleviate the pressure of full-scene loading in the editor. During multi-person editing, each person can selectively load the regions they care about, which is crucial for large scene management and multi-person collaboration. If not handled properly, it will be the beginning of chaotic scene production processes.
    • Editor classification can provide an effective basis for subsequent scene optimization.
    • Data Layers are sub-levels participating in World Partition streaming.

    Level Instances¶

    UE5 provides the Level Instancing feature to improve and simplify the editing experience of World Partition.

    • Level Instancing in Unreal Engine | Unreal Engine 5.3 Documentation (unrealengine.com)

    The original intention of Level Instances is to group a set of Actors so that Level Instances can be placed and reused throughout the world. However, since they can be embedded into the World Partition of the main level during packaging, and UE5's Data Layers are not yet widely adopted, many development teams accustomed to UE4 prefer to use them as sub-levels of open world maps.

    • Performance optimization for open world scenes is different from optimizing individual assets. Since there are a large number of assets to maintain, it is difficult to rely on manual maintenance. Therefore, you should seek unified management strategies from a macro perspective as much as possible, and abandon some minor optimization requirements in exchange for greater performance balance. Proper classification and isolation of scene assets is very, very, very important—it is an important basis for performance optimization. R&D teams can formulate corresponding LOD Groups, Texture Groups, and HLOD generation strategies based on different classifications. Additionally, for assets that do require special treatment, the basis for specialization (whitelist) should be retained.

    • The scene production process will not be chaotic only if every participant strictly follows the scene production specifications. Therefore, R&D teams need to establish a public document repository for publishing and iterating scene specifications. Use tools as much as possible instead of manual checks to minimize the probability of errors caused by human intervention. If manual workload must be increased for relevant personnel, the most streamlined data and processes should be evaluated as much as possible.

    • Open world scene specifications are highly dependent on game design. Only after clarifying the core character gameplay can the development team formulate corresponding scene specifications, establish performance optimization indicators, and create corresponding toolchains. Take The Legend of Zelda: Tears of the Kingdom as an example:

    • Customize terrain height, slope, and water body specifications based on the character's stamina (swimming, climbing, gliding) mechanics.

    • Customize terrain specifications based on the requirements of the Ascend skill.
    • Create interactive objects that meet the characteristics of abilities like Ultrahand, Fuse, and Recall.
    • Weapons (one-handed swords, two-handed swords, spears, shields, arrows) can be fused, and characteristics are bound to corresponding slots to formulate specifications for fuse items.
    • Based on known character state categories, create different scene effects such as lightning strikes, fire, cold, and heat, and provide corresponding solutions (clothing or food).
    • Create Zonai technology gameplay without conflicting with core gameplay design specifications.

    For these specifications, engine developers can carry out development work similar to the following:

    • Customize debug views for "terrain climbable height", "water traversable area", and "Ascend usable area" (it would be great if UE supports extending debug views via plugins without modifying source code).

    • Verify the performance indicators of various effects and scene effects, adjust the balance between effect and performance, and create corresponding management and acceptance tools.

    • Here are some small suggestions for editor tools:

    • Trace the origin of problems as much as possible. Solving problems at the source has the lowest cost, such as when an asset is created (AssetCreated) or when an asset is saved (AssetSaved), when an Actor is created (NewActorsPlaced), etc.
    • Use ignorable Notifications instead of Dialogs that forcefully block user input.
    • Provide a friendly user experience with support for undo, redo, batch processing, and customization.

    Gameplay Design¶

    Regarding open world level design, here are some related documents:

    • What Challenges Are There in Making an Open World Game? - TiMi Studios / Jiang Anxi

    • Game Development Chat - Open World - Zhihu / Italink

    The underlying gameplay design of an open world is very important. It should be complete and full of ingenuity. Forcing unreasonable modules to achieve a certain effect will only cause destructive blows to subsequent development work.

    • After clarifying the upper limits of various budgets (time, energy, money, computing power), formulate resource scheduling and allocation. Trade-offs are inevitable.
    • If the underlying gameplay design is not rigorous, the entire production process will become chaotic or even out of control. As gameplay stacks up, the production difficulty of open scenes will increase exponentially. If some ingenious designs are not used to converge gameplay content, production costs will easily soar.

    Here are two examples:

    • The Legend of Zelda uses underlying systematic gameplay to build the game's gameplay system, applying various templates to expand gameplay. Developers ensure that templates and systematic designs are within a manageable range. Artists and game creators derive game content within this limited range, which prevents project complexity from rising sharply as the scale increases.

    • In Black Myth: Wukong, Wukong can transform into various elite monsters through the 72 Transformations. This gameplay design allows the R&D team to invest more production costs into the design of elite monsters.
