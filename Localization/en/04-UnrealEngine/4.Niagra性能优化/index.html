    Niagara Performance Optimization¶

    Niagara is a nearly all-powerful particle system provided by Unreal Engine. There are numerous high-quality tutorials online about how to use it to create certain effects, but the usage management and performance optimization of Niagara are often overlooked by effect artists.

    Since the author has been plagued by these issues for a long time, this section will supplement relevant content, hoping that after understanding it, everyone can avoid such problems as much as possible =.=.

    Usage¶

    Particle System is an important means to enrich effects in 3D scenes. Unlike Mesh in scenes, its notable features are:

    • The quantity of particles is relatively large
    • Particles move over time

    If these two features are not met (i.e., small quantity and static), artists need to consider whether to use MeshActor or particles.

    In UE, effects can be mainly divided into two categories:

    • Spawned Effects: Effects dynamically spawned in the scene using SpawnSystemAtLocation and SpawnSystemAttached.
    • Scene Effects: Effects placed in the scene as Actors.

    These two types of effects have different focus points and corresponding management measures.

    Bounding Box¶

    In game engines, to reduce the rendering overhead of each frame, the engine culls some invisible objects so they do not participate in GPU rendering, as shown below:

    This image is from: 马克·加尔维斯 - Homepage (optus23.github.io)

    If you understand 3D View Transformation, you should know that you can determine whether an object is within the camera's range by calculating all vertices of the object using the camera matrix.

    However, obviously, an object may have thousands of vertices. If calculations are performed for each vertex, the game engine might turn into a PPT player~

    To simplify this process, game engines use a clever method: replacing the object's vertices with a simple box that can enclose the object for camera culling calculations. Although the box has fewer vertices and visibility judgment is less precise, the performance improvement it brings is very significant.

    Logically, it can be assumed that if this box is visible, the object must be visible.

    Show object bounding box: ShowFlag.Bounds 1

    So everyone should understand this: In the engine, to determine whether an object is within the camera's range or occluded, generally, the reference is not its own vertex information, but the object's bounding box.

    For StaticMesh, its vertices are static, so the engine automatically generates bounding box information when creating the asset.

    But for effects, since particles are dynamic, their bounding boxes cannot be generated statically.

    In UE, for CPU particles, the engine recalculates the Niagara bounding box boundaries every frame:

    However, due to the特殊性 of their implementation (all particle data is in the GPU, and the number of particles is often very large), GPU particles make it impossible for the CPU side to calculate the particle bounding box in real time. Developers must set a fixed boundary for them, i.e., manually set the size of the bounding box.

    GPU particles use a GPU-driven rendering pipeline, and the entire process has almost no interaction with the CPU. The data in the graphics rendering pipeline can often be seen as one-way: CPU->GPU. Although data can also be read back from the GPU, this process has a certain delay and high performance cost.

    In Niagara, you can set the bounding box of the particle emitter here:

    The simplest way is to set the bounding box for the entire particle system:

    Artists must ensure the correctness of the bounding box (the bounding box should cover the entire movement space of the effect with the smallest possible area), otherwise the following consequences will occur:

    • If the bounding box of the effect does not match the actual movement space, it will lead to incorrect visual culling:

    • If the bounding box of the effect is too large, it will cause effects that are clearly not within the field of view to fail to be culled and still be rendered, resulting in unnecessary overhead.

    Lifecycle¶

    For Scene Effects, their lifecycle is managed by the scene at the Actor level, so we generally don't need to care about it. For Spawned Effects, there are some details we must understand regarding lifecycle management:

    Spawned Effects refer to effects generated using several functions under UNiagaraFunctionLibrary:

    UNiagaraComponent* SpawnSystemAtLocation(const UObject* WorldContextObject,
                                         class UNiagaraSystem* SystemTemplate, 
                                         FVector Location, 
                                         FRotator Rotation = FRotator::ZeroRotator,
                                         FVector Scale = FVector(1.f), 
                                         bool bAutoDestroy = true,
                                         bool bAutoActivate = true, 
                                         ENCPoolMethod PoolingMethod = ENCPoolMethod::None,
                                         bool bPreCullCheck = true);

UNiagaraComponent* SpawnSystemAttached(UNiagaraSystem* SystemTemplate,
                                       USceneComponent* AttachToComponent,
                                       FName AttachPointName,
                                       FVector Location, 
                                       FRotator Rotation,
                                       FVector Scale, 
                                       EAttachLocation::Type LocationType, 
                                       bool bAutoDestroy, 
                                       ENCPoolMethod PoolingMethod, 
                                       bool bAutoActivate = true,
                                       bool bPreCullCheck = true);

    SpawnSystemAtLocation is used to spawn a particle component at a specified location, while SpawnSystemAttached is used to attach to another scene component. Regarding the lifecycle, we mainly need to pay attention to several parameters:

    • bAutoActivate: Whether to activate automatically. True means the particle effect will play immediately afterward.
    • bAutoDestroy: Whether to destroy automatically. True will destroy the component after the particle finishes playing.
    • bPreCullCheck: Pre-culling. If true, and the bounding box of the spawned particle system is not within the view frustum, the particle component will not be spawned, i.e., returns null.
    • PoolingMethod: Pool operation, a mechanism to reuse particle components. Its values can be:
    • None
    • AutoRelease: Auto-release. After playing ends, it will be automatically stored in the effect pool for reuse.
    • ManualRelease: Manual release. The particle component can only be reused by manually calling ReleaseToPool.
    • ManualRelease_OnComplete: Non-public option, used for internal state control of Niagara. Do not use it.
    • FreeInPool: Non-public option, used for internal state control of Niagara. Do not use it.

    Effect Pool¶

    For detailed mechanism, refer to the article: 【UE4】Effect Pool - Zhihu (zhihu.com)

    Caching Mechanism¶

    The main purpose of the effect pool is to reuse particle components. Its caching mechanism can be seen as:

    • If the spawn parameters include pool operation (i.e., PoolingMethod != ENCPoolMethod::None), Niagara will search the effect pool for reusable components of the same type. If found, it will use them; otherwise, it will create a new particle component and record its usage time.
    • Newly created particle components will not be released (meaning bAutoDestroy will be invalidated). They will be stored in the effect pool for management.
    • For AutoRelease particle components, when playback ends, the effect pool will mark them as reusable.
    • For ManualRelease particle components, when ReleaseToPool is called: if the particle has finished playing, it will be immediately marked as reusable; otherwise, the pool operation will be modified to ManualRelease_OnComplete, and it will also be marked as reusable when playback finishes.
    Cleaning Methods¶

    UNiagaraComponentPool has a scheduled cleaning mechanism. The two main key parameters are:

    • GNiagaraSystemPoolKillUnusedTime: Default is 180.
    • GNiagaraSystemPoolingCleanTime: Default is 30.

    The automatic cleaning mechanism corresponding to the above configuration can be roughly regarded as: UNiagaraComponentPool will clean up particle components that have not been reused for more than 180 seconds every 30 seconds.

    Actually, it is not cleaned on Tick, but during each reuse. So it may not be exactly 30 seconds, and the deviation may be large.

    When switching World, UNiagaraComponentPool will execute Cleanup.

    You can also manually call UNiagaraComponentPool::ClearPool(UNiagaraSystem* System) for cleaning.

    Pitfalls¶

    • If there is a pool operation (PoolingMethod), then bAutoDestroy will be invalidated.
    • The premise for the pool mechanism to work properly is that the particle system can finish playing. Please note:
    • Ensure there are no emitters with infinite lifecycle in the particle system.
    • Calling ResetParticles(true) will not reach Complete.
    • If the culling response is Dormant for scalability culling, the culled effect will not be reused, and OnSystemFinished will not trigger (strictly speaking, it is not completed).
    • For particle components with pool operations, do not call DestoryComponent. Particle components in the pool will be cleaned up when switching World or during scheduled cleaning.
    • If SpawnSystemAttached has a pool operation, the actual owner of the newly spawned particle component is the World, not the attached component. The particle component will not be destroyed when the attached component is destroyed.
    • Calling ReleaseToPool on an AutoRelease particle component will cause an error.
    • For particles with neither AutoRelease nor pool operation, their lifecycle must be strictly controlled.

    Scalability¶

    By setting the bounding box, particles can be culled visually, but it should be noted that unlike ordinary scene objects, particle systems also have simulation costs!

    This is a problem that many effect artists easily overlook when using Niagara. Many people think that particles stop when they are not visible, but in reality, they are still executing:

    For spawned effects, since they have a certain lifecycle, their simulation consumption is mostly negligible in most cases.

    However, for scene effects, if there are too many NiagaraActors placed in the scene, it will have a great impact on the entire program.

    To solve this problem, UE provides an asset called NiagaraEffectType to control the simulation optimization strategy of Niagara System.

    We can specify the effect type used by the NiagaraSystem here:

    Using it can fulfill the following requirements:

    • Limit the maximum display distance of the particle system
    • Limit the maximum number of particle system instances displayed in the current viewport
    • Adjust particle effects according to performance budget
    • Adjust the scaling factor of emitter spawn count

    Its configuration panel is as follows:

    We can add system and emitter scalability configurations. Each configuration corresponds to the scalability strategy adopted under different performance levels:

    The meanings of its parameters are as follows:

    • Culling applies to local player: Whether to allow culling effects generated, attached, or created by the local player.

    • Update frequency: Spawn Only, Low, Medium, High, Continuous.

    Both NiagaraEffectType and NiagaraComponent are managed by NiagaraWorldManager. NiagaraEffectType will Tick separately. The update frequency here refers to the frequency at which it detects the current state of NiagaraSystem. The higher the frequency, the more timely the culling response, but the higher the performance overhead.

    • Culling response: Destroy, Destroy and Clear, Dormant, Dormant and Clear.

    Clear will immediately kill all particles and then cull the NiagaraSystem. If not cleared, no new particles will be generated, and culling will be performed after all existing particles have finished their lifecycle.

    The difference between Destroy and Dormant is that Destroy directly destroys the particles, while Dormant can be regarded as just hiding the particles waiting for activation.

    For scene effects, since they are Actors placed in the scene and will not be regenerated after destruction, they are generally set to Dormant. The specific destruction and loading are managed by the large world.

    For spawned effects, they are generally spawned once. If set to Dormant, they will occupy memory all the time, so they are generally destroyed.

    • Importance processor: Age, Distance.

    The importance processor is mainly related to the Maximum System Instances below. The maximum system proxy determines how many instances of the same type of particle system are allowed to exist currently. The importance processor determines the priority of particle sorting. For example, if distance is the target, there are ten particle systems, and the maximum system instances is five, then NiagaraEffectType will only retain the five closest particle effects.

    • System scalability settings

    Setting List: Each added setting item can configure under which environments this item takes effect.

    • Maximum distance: Cull particles according to the distance between the effect and the current player.
    • Cull proxy mode: Instanced Rendering. If Instanced Rendering is enabled, an invisible particle system will be created, and all other culled particle systems of the same type will use it for rendering, which can avoid a lot of simulation costs.
    • Maximum system proxies: Maximum number of system proxies.
    • Budget adjustment: Adjust the scalability strategy of the particle system according to a certain budget.
    • Visibility culling: Cull according to visibility.

    For specific descriptions, refer to the Tooltip in the editor panel.

    Control Emitter Count¶

    Ideally, as long as two emitters use exactly the same renderer parameters, they should use the same emitter.

    Because one renderer in an emitter corresponds to one graphics rendering pipeline, and the particle system essentially processes the instanced data required by the graphics rendering pipeline.

    One more emitter means one more rendering data and one more particle buffer to maintain.

    If you just want to adjust the particle movement mechanism, you can extend it by customizing Modules.

    Distinguish Between CPU and GPU Particles¶

    CPU particles: Suitable for rendering a small number of particles. Since the data is located in the CPU, it can obtain information about the entire scene, easily interact with game logic, support event communication between particles, precise physical collisions, and dynamically calculate bounding box boundaries.

    GPU particles: Have very low performance consumption and are suitable for rendering a large number (100,000-level) of particles.

    When distinguishing, the first dimension to consider is the number of particles. If the number of particles is very small (such as a few or dozens), it is best to use CPU particles (because there is no need to increase GPU scheduling overhead for a few particles).

    When the number exceeds 1,000, we consider: Does the functional requirement need to use the features of CPU particles? If not, then GPU particles are preferred.

    When the number of particles is very large but the features of CPU particles are needed, the functionality of GPU particles needs to be extended at a lower code level.

    Issues and Suggestions¶

    • Before Unreal Engine 5.1, Niagara System had a recompilation BUG. Its manifestation is: when spawning particles in the game for the first time, the entire particle system will be recompiled. This is because saving resources in the Niagara System Editor stores some configurations different from those in the game mode, leading to inconsistent HashID of the particle system and thus invalidating the compilation cache. Therefore, if you need to evaluate the execution performance of the particle system in the game environment, the author recommends testing in the packaged environment.
    • Unreal Engine provides very complete supporting tools for Niagara, but for a large team, it is easy to use but not easy to manage. The author highly recommends further expanding on the basis of the above toolset and adding automated processes to complete macro particle system management.
    • For some常规 rendering optimizations, such as optimizing materials, simplifying models, and reducing Overdraw, they are also applicable to Niagara.

    Production Optimization¶

    The optimization experience summarized in the process of mending the fold after the sheep are lost is precious. It can gradually let artists understand how to create high-performance particle effects.

    The following are some insights that can help effect artists optimize production (mainly for GPU particles):

    Computing Power Awareness¶

    1920 x 1080 is a common resolution for computer monitors nowadays. This means there are nearly 2 million pixels on the screen, which also means the computer needs to perform nearly 2 million pixel-level numerical processes to draw one frame. Currently, some mid-range hardware devices can easily draw hundreds or thousands of images per second. This amazing computing power benefits from the rapid development of the Graphics Processing Unit (GPU). Unlike the Central Processing Unit (CPU), which is the scheduling center of the computer and whose architecture needs to take all aspects of the system into account, the GPU is a specialized approach. Its architecture is filled with a large number of computing units to meet the needs of graphics operations.

    Taking the current cutting-edge consumer graphics card GeForce RTX 4090 as an example, it has more than 76 billion transistors and more than 16,000 computing cores.

    After understanding this upper limit, we can simply correspond a single GPU particle to a pixel point. That is, under normal circumstances, mid-range graphics cards can easily simulate millions of particle effects.

    But it should be noted that the million-level is often the upper limit of the entire system. We usually cannot allocate all performance budgets to the particle system. So in general, if the total number of particles exceeds 100,000, it may cause performance pressure on the entire rendering system.

    If these 100,000 particles are converted into the corresponding number of 1x1 pixels for tiling, it roughly corresponds to an image of 300x300 size:

    The closer the screen occupation area of the particle system is to its tiling area, the better its performance (because there is less OverDraw).

    Sprite Sheet Baking¶

    Niagara Editor supports baking particle effects into sprite sheets. For some effects with fixed viewing angles, we can adopt this scheme to obtain a great degree of optimization.

    Procedural Content Generation¶

    Particle systems are mainly suitable for simulating a large number of dynamic objects, but only under some specific requirements do we have to use particle systems for real-time simulation:

    • Creating interactive dynamic effects
    • Need to create a 3D effect with no visual dead angles
    • Very large number of large-scale clusters

    Excluding the above usage scenarios, we can usually achieve the desired performance effect by baking static materials.

    So when creating particle effects, we need to carefully examine: Is it necessary to use the particle system for real-time simulation?

    If yes, then we further think: Can some real-time calculation stages in the particle system be replaced with pre-made static data?

    For example, when creating effects related to the scene, the simulation of particles may need some scene information as input. Most of the time, this scene data is static. We don't need to calculate the relevant information of the scene in real time at runtime. We can generate this data statically in the editor. This way, we can create effects highly integrated with the scene with less performance cost. This improvement is particularly obvious when the number of particle systems is large.

    We can also create Procedural Content Generation (PCG) assets on Niagara:

    • In the User Parameters of Niagara System, add the scene data required by the particle system (here, a variable named SpawnPositionArray is added):

    • Create a new Actor Blueprint, add NiagaraComponent, and specify Niagara System.

    • In the BeginPlay event of the blueprint, set the parameters we added in Niagara, and promote the parameter input to a variable (Partcile Spawn Position Array):

    • Add a function (e.g., named CalcParticleSpawnPositionArray) in the blueprint, check Call In Editor, and in this function, obtain scene information (no need to care about performance, you can scan Actors, cast rays...), and fill the blueprint variable value (Partcile Spawn Position Array):

    • Place the Actor blueprint in the scene, and you can find that the function we created earlier has become a clickable button in its details panel:

    • Clicking the button will execute the corresponding function logic, which will execute and fill the blueprint properties. These property values will be serialized when saved. When the game starts normally, BeginPlay will execute and submit this data to Niagara.

    • Then, we can write the corresponding Module in Niagara to use this part of the data.

    It should be noted that we cannot directly set the Niagara parameters in CalcParticleSpawnPositionArray, but use the blueprint variable property serialization to store the scene data.

    This is because the functions for setting Niagara parameters (starting with NiagaraSet...) directly upload the data to Niagara's data processor without storing it. Therefore, setting Niagara parameters through functions may not necessarily show parameter changes in the details panel of the NiagaraSystem (some property types do return synchronization of editor data, so changes can be seen in the details panel).
