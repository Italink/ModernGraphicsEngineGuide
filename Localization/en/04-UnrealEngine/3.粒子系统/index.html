    Particle System¶

    A Particle System refers to a technology in 3D computer graphics used to simulate specific fuzzy phenomena that are difficult to achieve realistic physical motion laws with other traditional rendering techniques. Phenomena often simulated using particle systems include fire, explosions, smoke, water flows, sparks, falling leaves, clouds, fog, snow, dust, meteor trails, or abstract visual effects like glowing trajectories.

    Baidu Encyclopedia (Baidu Encyclopedia) — Particle System

    Principles¶

    Particle systems are mainly used to render large numbers of moving objects. Their core workflow is not complex. Those familiar with graphics APIs know that rendering an object with the GPU requires calling DrawCall. Since particle systems contain a huge number of tiny particles, a conventional approach might look like this:

    for(int i = 0; i < particles.num(); i++){
    drawParticle(particles[i]);
}

    While this achieves the effect, the numerous DrawCall invocations and repeated data between particles lead to very high rendering costs for the particle system, limiting the number of particles that can be rendered.

    To maximize data reuse between particles and reduce DrawCall, the solution is Instancing.

    For details on the concept and usage of instancing, see:

    • Learn OpenGL - Instancing

    Instancing allows merging DrawCall operations for particle systems and reusing identical data between particles.

    Understanding the above concepts makes it clear that a particle system is essentially a workflow using instanced rendering. When considering how to create particle effects from this perspective, we focus on:

    • How to construct the instanced data (Instance Data) required by the particle system.
    • How to use the instanced data to render the particle effect.

    Starting from these two angles, it should be easy to build the workflow of a particle system. The following sections mainly explain the details of particle system architecture:

    For a simple particle, it might use a data structure like this:

    struct Particle{        // Particle attribute structure 
    vec3 position;
    vec3 rotation;
    float size;
    float age;
    //...
}

    In most particle system architectures, a structure called a Particle Emitter is used. It maintains a Particle Pool for storing data and is responsible for Spawning, Updating, and Recycling particles. Using a Particle Renderer to render the data in the particle pool produces the particle effect. This process can be visualized as:

    class ParticleEmitter{
protected:
    void Tick() override{
        Spawn();                // Spawn phase: Create new particles
        UpdateAndRecycle();     // Update phase: Update each particle's state data and recycle dead particles
        Render();               // Render phase: Use the particle renderer to render the particle effect
    }
private:
    vector<Particle> mParticlePool;
    ParticleRenderer mParticleRenderer;
};

    Particle Pool¶

    Since computer memory resources are limited, the particle system must ensure that the memory occupied by the particle pool does not keep expanding as the program runs. To this end, particle systems typically use the following methods to avoid this issue:

    • Limit the number of particles emitted.
    • Particles have a lifecycle; particles exceeding their lifecycle are promptly recycled.

    This also provides a foundation for memory optimization in the particle pool:

    • Knowing the number of particles emitted and their lifecycle, combined with the current maximum frame rate of the computer, it is easy to estimate the maximum number of particles for the emitter. The memory for this number is often allocated to the particle pool at the start, avoiding overhead from memory reallocation of the particle pool.
    • To allow parallel recycling of the particle pool (avoiding the need to shift subsequent elements to fill the position when removing an element from the array), two particle pools of the same size are often used for alternating iteration.

    If we want to update and recycle particles, we might write code like this:

    vector<Particle> ParticlePool;
ParticlePool.reserve(10000);            // Pre-allocate memory for 10000 particles

int index = -1;
for(int i = 0; i < ParticlePool.size(); i++){
    if(ParticlePool[i].isAlive()){
        index++;
        ParticlePool[index] = ParticlePool[i];
        ParticlePool[index].position = ...;
        ParticlePool[index].size = ...;
        ...;
    }
}
ParticlePool.resize(index);

    Its logical complexity is O(n). If further optimization is needed, we can process the for loop in parallel, but the above code structure cannot do this because:

    • The internal loop logic reads and writes the external shared variable index.
    • Reading and writing different regions of ParticlePool simultaneously can cause data chaos due to out-of-order execution in parallel.

    To solve this problem, we usually use two ParticlePool for alternating processing and use atomic operations to read and write index in local threads. Therefore, the structure code of ParticleEmitter might become:

    class ParticleEmitter{
protected:
    void InitPool(){
        mParticlePool[0].reserve(...);
        mParticlePool[1].reserve(...);
        mCurrentPoolIndex = 0;
        mNextPoolIndex = 1;
        mCurrentNumOfParticle = 0;
    }
    void Tick() override{
        Spawn();                
        UpdateAndRecycle();     
        Render();               
    }
private:
    vector<Particle> mParticlePool[2];
    int mCurrentPoolIndex;
    int mNextPoolIndex;
    int mCurrentNumOfParticle;

    ParticleRenderer mParticleRenderer;
};

    Spawn Phase¶

    The particle spawn phase mainly involves creating new particles, storing them in the particle pool, and initializing them. This process can be visualized as:

    void Spawn(){ 
    SpawnPerFrame(mParticlePool[mCurrentPoolIndex], mCurrentNumOfParticle, 100);        // Spawn 100 particles per frame
}

// Emission mechanism (customizable)
void SpawnPerFrame(vector<Particle>& ParticlePool, int& NumOfParticle, int NumOfNewParticle){
    for(int i = 0; i < NumOfNewParticle ; i++ ){            // NumOfNewParticle is the number of new particles
        Particle& NewParticle =  ParticlePool[NumOfParticle];   
        NumOfParticle++;
        InitializeParticle(NewParticle);
    }
}

// Initialization mechanism (customizable)
void InitializeParticle(Particle& particle){
    particle.position = vec3(0.0f, 0.0f, 0.0f);
    // particle...
}

    Note here that the Spawn function is called every frame. In addition to the emission mechanism of spawning a fixed number of particles per frame, the emitter may also spawn a "fixed" number per second. However, since the number of frames per second in the game is unpredictable under different system environments, the number of particles for such time-based emission mechanisms is difficult to control precisely.

    Update and Recycle Phase¶

    The pseudocode for this phase can be visualized as:

    void UpdateAndRecycle(){    
    int IndexOfNextBuffer = -1;             // Initial index
    for_each_thread(int i = 0 ; i < mCurrentNumOfParticle ; i++){       // Parallel for loop
        const Particle& CurrentParticle = mParticlePool[mCurrentPoolIndex][i];
        if(CurrentParticle.isActive()){ 
            int CurrentIndex = atomicAdd(IndexOfNextPool, 1);           // Use atomic operations to read/write external shared variables
            Particle& NextParticle = mParticlePool[mNextPoolIndex][CurrentIndex];
            UpdateParticleStatus(CurrentParticle, NextParticle);
        }
    }
    CurrentParticlesBufferSize = IndexOfNextBuffer; // Update the number of currently alive particles
    swap(mCurrentPoolIndex, mNextPoolIndex);            // Swap the indices of the current particle pools
}

// Particle state update mechanism (customizable)
void UpdateParticleStatus(const Particle& CurrentParticle, Particle& NextParticle){
    NextParticle.position = CurrentParticle.position;
    // NextParticle...
}

    Rendering Phase¶

    Rendering itself only uses particle data for rendering. Its basic process can be visualized as:

    void Render(){
    mParticleRenderer.BindAttribute("position", mParticlePool[mCurrentPoolIndex], offset0, stride0);
    mParticleRenderer.BindAttribute("color", mParticlePool[mCurrentPoolIndex], offset1, stride1);
    ...;
    mParticleRenderer.drawInstancing();
}

    This phase reflects the essence of particles: particles are just a collection of data, and the particle system (emitter) simply processes this data in batches and binds it to the attribute slots of the particle renderer to complete the rendering of the particle effect.

    CPU VS GPU¶

    As mentioned above, particle systems essentially revolve around processing a collection of particle data, which can be mainly divided into:

    • Spawn Phase and Update and Recycle Phase: These two phases mainly process particle data. Niagara provides visual scripting to enable custom operations for these two phases. The final script will:
    • CPU: C++ code generated by node concatenation runs in Niagara's virtual machine.
    • GPU: Niagara translates the node graph into corresponding HLSL code via NiagaraHlslTranslator for ComputeShader calls.
    • Rendering Phase: Both CPU and GPU particles can use the same renderer. The difference is that CPU particles need to upload data to the GPU, while GPU particle data resides on the GPU and requires no transfer.

    The logic of the above processes is largely similar. One thing to note is the recycling of GPU particles. GPU particles use ComputeShader to process each particle in parallel, but during the update and recycle phase, data relocation is involved. The reason GPU can achieve efficient parallelism is that data on each branch is independent and does not interfere with each other. To implement GPU particle recycling, we must "break" this rule. Currently, there are two main ways to achieve this effect:

    • Graphics Rendering Pipeline: Disable rasterization, use TransformFeedback (OpenGL)/Stream Output (DX), and recycle (not submit) dead particles in the Geometry Shader.

    The Geometry Shader itself has linear operations because this process generates an indefinite number of new vertices. The GPU must lock and relocate data when writing it to memory during execution. This is why some people use TransformFeedback and Stream Output to create GPU particles. Of course, this is also why GS should be avoided in games. Incidentally, Stream Output is an official feature of DX, while TransformFeedback is not well-supported by Khronos—Vulkan does not even provide official support, and Metal lacks corresponding API functions.

    • General Computing Pipeline: SSBO Atomic. With hardware updates, most modern rendering drivers support SSBO (Shader Storage Buffer Object). Our main focus here is that SSBO supports atomic operations. With this support, we can process particles in parallel in CS and use atomic operations to relocate particle data (i.e., NewIndex in the pseudocode above). For new particle data, another feature—indirect rendering (Indirect Draw)—can be used: directly call DrawCall using data on the GPU. This avoids particle data transfer between CPU and GPU throughout the process. Below is a simple GLSL code example:
    layout (local_size_x = LOCAL_SIZE) in;
struct Particle {
    vec3 position;
    vec3 rotation;
    vec3 scaling;
    vec3 velocity;
    float life;
};
layout(std140,binding = 0) buffer InputParticlesBuffer{
    Particle inputParticles[PARTICLE_MAX_SIZE];
};
layout(std140,binding = 1) buffer OutputParticlesBuffer{
    Particle outputParticles[PARTICLE_MAX_SIZE];
};
layout(std140,binding = 2) buffer ParticleRunContext{
  int inputCounter;           // Initial value is the current number of particles
  int outputCounter;          // Initialized to -1
  float duration;
  float lifetime;
};

#define inID  gl_GlobalInvocationID.x
#define inParticle inputParticles[inID]

void main(){                                              // Note: GPU parallelism is unordered
    if(inID >= inputCounter || inParticle.life > lifetime)        // Can be optimized using the step function
        return;
    uint outID = atomicAdd(outputCounter, 1);             // atomicAdd is a native GLSL function but requires the operand to come from SSBO
    outputParticles[outID].life = inParticle.life + duration;
}

    Shader Storage Buffer Object (Shader Storage Buffer Object) is used to provide readable and writable buffer data.

    Its usage is almost identical to UniformBuffer. The main differences are:

    • Storage Buffer can allocate very large video memory: The OpenGL specification guarantees that Uniform Buffer can be up to 16KB, while Storage Buffer can be up to 128MB.
    • Storage Buffer is writable and even supports atomic operations: Reads and writes to Storage Buffer may be out of order, so memory barriers are often needed to ensure synchronization.
    • Storage Buffer supports variable storage: This means that blocks in Storage Buffer can define unbounded arrays (like int arr[]), and the array length can be obtained using arr.length in the shader. In contrast, blocks in Uniform Buffer require explicitly specifying the array size when defining arrays.
    • SSBO access is slower than Uniform Buffer under the same conditions: Storage Buffer is usually accessed like a buffer texture, while Uniform Buffer data is read through internal shader-accessible memory.

    Functionally, SSBO can be considered a better interface for buffer textures when accessed via Image Load Store.

    OpenGL provides an AtomicCounter feature, which essentially leverages this characteristic.

    The above completes the recycling of GPU particles, but it actually introduces a serious problem—each time particles are recycled, the number of particles changes. However, since the data is located on the GPU, the CPU must know this parameter when calling DrawCall.

    Reading data back from the GPU is definitely not feasible because modern graphics APIs use command buffering to accelerate rendering. Simply put, at any moment, the GPU's command buffer may contain instructions from two or more frames that have not yet been processed. If we want to read data back, we must ensure that the current instructions are executed immediately, which means blocking the rendering thread and waiting for the data to return. This operation is fatal to the entire engine, but fortunately, there is a solution.

    In the OpenGL 4.0 update, a new feature called Indirect Rendering (also known as Indirect Draw) was introduced, which allows using data on the GPU as DrawCall parameters. Here is the official definition:

    Indirect Rendering

    Indirect rendering allows directly using data on the GPU as DrawCall parameters. For example, the parameters of glDrawArrays include primitive type, number of vertices, and starting vertex. When using the indirect drawing command glDrawArraysIndirect, the corresponding parameters are obtained from a buffer object.

    This feature avoids GPU->CPU->GPU round trips by letting the GPU determine the parameters to render, while the CPU only decides when to issue the drawing command and which Primitive the command uses.

    Searching for "Indirect" in the Niagara source code reveals definitions of related usage. The main structures are located in:

    • NiagaraVertexFactories\Public\NiagaraDrawIndirect.h
    • Niagara\Private\NiagaraGPUInstanceCountManager.cpp

    Advantages and Disadvantages¶

    • CPU Particles

    • Advantages

      • The CPU can access the complete game environment and interact with other particles or game logic.
      • No high hardware configuration is required; the graphics card only needs to support programmable pipelines and instanced rendering.

    • Disadvantages

      • Particle data can only be iterated linearly on the CPU, causing severe performance loss to the CPU.
      • Particle data resides in CPU memory and needs to be uniformly uploaded to the GPU during rendering. This transfer process is extremely costly.

    • GPU Particles

    • Advantages

      • Particle data is generated and processed on the GPU throughout, avoiding data transfer between CPU and GPU.
      • Leveraging parallel units in the GPU to process particle data greatly reduces the time required for particle processing.

    • Disadvantages

      • GPU particle data resides in video memory, making it impossible to calculate bounding box boundaries in real time. Therefore, we need to manually specify fixed boundaries for GPU particles.
      • Cannot interact well with the game environment, but effects can be approximated using depth, Scene Capture, or distance fields.
      • Requires certain hardware configurations, including support for CS, SSBO Atomic, and Indirect Draw (PCs with discrete graphics cards are generally fine, but mobile support is not particularly完善).

    Niagara¶

    Unreal Engine's Niagara system is very powerful. It essentially provides a programmable data processor (CPU or GPU) and instanced renderer. From this perspective, we can achieve many stunning effects.

    Scopes¶

    Most articles refer to these scopes as "namespaces." While they do serve to distinguish variable names, more importantly for developers, these variable scopes represent different lifecycles.

    The following is the general structure of Niagara in UE, where the yellow parts represent the scopes of manageable variables in Niagara:

    In the Niagara editor, you can add, delete, or modify variables in these scopes through the parameter panel:

    • EngineProvided: This scope is mainly used to read variables from the engine, such as DeltaTime.

    • System Attribute: Attribute variables held by a single particle system.

    • Emitter Attribute: Attribute variables held by a single particle emitter.

    • Particle Attribute: Attribute variables held by a single particle.

    • Module Inputs: Module input variables, i.e., variables exposed by the module for external settings. They will be displayed in the module's settings panel:

    • Static Switch Inputs: Module static branch input variables, used to optimize script logic branches during compilation.

    • Module Locals: Module local variables.

    • Module Outputs: Module output variables.

    • Stage Transients: Stage temporary variables.

    • User Expose: User-exposed variables, mainly for calling from modules outside Niagara (C++ or Blueprint). Fundamentally, they are different from other variables, which will be discussed in detail below.

    For the detailed meaning of these scopes, refer to: UE4: Niagara Variables and HLSL - Zhihu (zhihu.com)

    Underlying Core — FNiagaraDataSet¶

    Niagara attributes are essentially a collection of data. Their corresponding code structure is FNiagaraDataSet (except for User Expose). Its simplified structure is as follows:

    class FNiagaraDataSet{
    /** Table of free IDs available to allocate next tick. */
    TArray<int32> FreeIDsTable;

    /** Number of free IDs in FreeIDTable. */
    int32 NumFreeIDs;

    /** Max ID seen in last execution. Allows us to shrink the IDTable. */
    int32 MaxUsedID;

    /** Tag to use when new IDs are acquired. Should be unique per tick. */
    int32 IDAcquireTag;

    /** Table of IDs spawned in the last tick (just the index part, the acquire tag is IDAcquireTag for all of them). */
    TArray<int32> SpawnedIDsTable;

    /** GPU buffer of free IDs available on the next tick. */
    FRWBuffer GPUFreeIDs;

    /** Number of IDs allocated for the GPU simulation. */
    uint32 GPUNumAllocatedIDs;

    /**
    Actual data storage. These are passed to and read directly by the RT.
    This is effectively a pool of buffers for this simulation.
    Typically this should only be two or three entries and we search for a free buffer to write into on BeginSimulate();
    We keep track of the Current and Previous buffers which move with each simulate.
    Additional buffers may be in here if they are currently being used by the render thread.
    */
    TArray<FNiagaraDataBuffer*, TInlineAllocator<2>> Data;

        /** Buffer containing the current simulation state. */
    FNiagaraDataBuffer* CurrentData;

    /** Buffer we're currently simulating into. Only valid while we're simulating i.e between PrepareForSimulate and EndSimulate calls.*/
    FNiagaraDataBuffer* DestinationData;

    /* Max instance count is the maximum number of instances we allow. */
    uint32 MaxInstanceCount;
    /* Max allocation count is the maximum number of instances we can allocate which can be > MaxInstanceCount due to rounding. */
    uint32 MaxAllocationCount;
}

    From the above structure, FNiagaraDataSet provides the data structures needed for the basic processes of the particle emitter mentioned at the beginning:

    • Maximum allocated storage (capacity, ID).
    • TArray<FNiagaraDataBuffer*, TInlineAllocator<2>> Data are two buffers for alternating iteration. FNiagaraDataBuffer* CurrentData and FNiagaraDataBuffer* DestinationData are pointers to the buffers for quick swapping.

    The core storage structure is FNiagaraDataBuffer, whose focus is solely on memory data. Its simplified structure is as follows:

    When a Niagara emitter is initialized (possibly due to reset or recompilation), the following function is called:

    void FNiagaraEmitterInstance::Init(int32 InEmitterIdx, FNiagaraSystemInstanceID InSystemInstanceID){
    const int32 UpdateEventGeneratorCount = CachedEmitter->UpdateScriptProps.EventGenerators.Num();
    const int32 SpawnEventGeneratorCount = CachedEmitter->SpawnScriptProps.EventGenerators.Num();
    const int32 NumEvents = CachedEmitter->GetEventHandlers().Num();

    if (UpdateEventGeneratorCount || SpawnEventGeneratorCount || NumEvents)
    {
        EventInstanceData = MakeUnique<FEventInstanceData>();
        EventInstanceData->UpdateScriptEventDataSets.Empty(UpdateEventGeneratorCount);
        EventInstanceData->UpdateEventGeneratorIsSharedByIndex.SetNumZeroed(UpdateEventGeneratorCount);
        int32 UpdateEventGeneratorIndex = 0;
        for (const FNiagaraEventGeneratorProperties &GeneratorProps : CachedEmitter->UpdateScriptProps.EventGenerators)
        {
            FNiagaraDataSet *Set = ParentSystemInstance->CreateEventDataSet(EmitterHandle.GetIdName(), GeneratorProps.ID);
            Set->Init(&GeneratorProps.DataSetCompiledData);

            EventInstanceData->UpdateScriptEventDataSets.Add(Set);
            EventInstanceData->UpdateEventGeneratorIsSharedByIndex[UpdateEventGeneratorIndex] = CachedEmitter->IsEventGeneratorShared(GeneratorProps.ID);
            ++UpdateEventGeneratorIndex;
        }

        EventInstanceData->SpawnScriptEventDataSets.Empty(SpawnEventGeneratorCount);
        EventInstanceData->SpawnEventGeneratorIsSharedByIndex.SetNumZeroed(SpawnEventGeneratorCount);
        int32 SpawnEventGeneratorIndex = 0;
        for (const FNiagaraEventGeneratorProperties &GeneratorProps : CachedEmitter->SpawnScriptProps.EventGenerators)
        {
            FNiagaraDataSet *Set = ParentSystemInstance->CreateEventDataSet(EmitterHandle.GetIdName(), GeneratorProps.ID);
            Set->Init(&GeneratorProps.DataSetCompiledData);

            EventInstanceData->SpawnScriptEventDataSets.Add(Set);
            EventInstanceData->SpawnEventGeneratorIsSharedByIndex[SpawnEventGeneratorIndex] = CachedEmitter->IsEventGeneratorShared(GeneratorProps.ID);
            ++SpawnEventGeneratorIndex;
        }

        EventInstanceData->EventExecContexts.SetNum(NumEvents);
        EventInstanceData->EventExecCountBindings.SetNum(NumEvents);

        for (int32 i = 0; i < NumEvents; i++)
        {
            ensure(CachedEmitter->GetEventHandlers()[i].DataSetAccessSynchronized());

            UNiagaraScript* EventScript = CachedEmitter->GetEventHandlers()[i].Script;

            //This is cpu explicitly? Are we doing event handlers on GPU?
            EventInstanceData->EventExecContexts[i].Init(EventScript, ENiagaraSimTarget::CPUSim);
            EventInstanceData->EventExecCountBindings[i].Init(EventInstanceData->EventExecContexts[i].Parameters, SYS_PARAM_ENGINE_EXEC_COUNT);
        }
    }
}

    Timing of Event Processing¶

    In FNiagaraEmitterInstance::Tick, there is the following code:

    void FNiagaraEmitterInstance::Tick(float DeltaSeconds)
{
    //...
    if (EventInstanceData.IsValid())
    {
        // Set up the spawn counts and source datasets for the events. The system ensures that we will run after any emitters
        // we're receiving from, so we can use the data buffers that our sources have computed this tick.
        const int32 NumEventHandlers = CachedEmitter->GetEventHandlers().Num();
        EventInstanceData->EventSpawnTotal = 0;
        for (int32 i = 0; i < NumEventHandlers; i++)
        {
            const FNiagaraEventScriptProperties& EventHandlerProps = CachedEmitter->GetEventHandlers()[i];
            FNiagaraEventHandlingInfo& Info = EventInstanceData->EventHandlingInfo[i];

            Info.TotalSpawnCount = 0;//This was being done every frame but should be done in init?
            Info.SpawnCounts.Reset();

            //TODO: We can move this lookup into the init and just store a ptr to the other set?
            if (FNiagaraDataSet* EventSet = ParentSystemInstance->GetEventDataSet(Info.SourceEmitterName, EventHandlerProps.SourceEventName))
            {
                Info.SetEventData(&EventSet->GetCurrentDataChecked());
                uint32 EventSpawnNum = CalculateEventSpawnCount(EventHandlerProps, Info.SpawnCounts, EventSet);
                Info.TotalSpawnCount += EventSpawnNum;
                EventInstanceData->EventSpawnTotal += EventSpawnNum;
            }
        }
    }
}

    The above code shows the logic of event processing:

    • When the emitter ticks, it iterates over all event handlers, reads the event's DataSet from the system instance ParentSystemInstance, and writes it to FNiagaraEventHandlingInfo for the script to read.

    Usage Recommendations¶

    While pursuing artistic effects, special effects must also ensure:

    • The particle system has correct bounding boxes and scalability; otherwise, particles may disappear inexplicably in the scene.
    • Strictly control the lifecycle of spawned effects to avoid conflicts between the Pool Method and lifecycle processing operations (pre-culling, scalability culling, AutoDestroy).

    For optimization, you need to understand:

    • How to reduce the number of particle emitters?

    The ideal scenario is: as long as two emitters use exactly the same renderer parameters, they should use the same emitter.

    Because one renderer in an emitter corresponds to one graphics rendering pipeline, and the particle system essentially processes the instanced data required by the graphics rendering pipeline.

    One more emitter means one more set of rendering data and one more particle buffer to maintain.

    If you just want to adjust the particle movement mechanism, you can extend it by customizing modules.

    • How to decide whether to use CPU or GPU particles?

    CPU particles can dynamically calculate bounding box boundaries but are only suitable for rendering a small number of particles.

    GPU particles can be used to render a large number of particles but must have accurate bounding box boundaries set.

    The dividing line is mainly the number of particles. If the number is in the thousands or tens of thousands, GPU particles must be used.

    For a small number of particles (e.g., a few), CPU particles are recommended.

    • When CPU particles must be used for effect purposes, two main points need to be considered:

    • CPU particles are executed serially. As the complexity of the particle system increases, performance loss multiplies.

    • The performance bottleneck of CPU particles in the rendering thread is mainly the transfer of particle data (limited bandwidth), which is why they are not suitable for rendering a large number of particles.

    • The working method of particle systems is different from conventional pipelines. If it is a single object placed in the scene, you need to consider using an Actor (Game Object) instead of a particle system.

    • In addition to controlling the complexity and number of particle systems, other methods can be used to reduce the performance consumption of particles:
    • Avoid particle crowding and reduce Overdraw.
    • Limit transparency.

    • ...

    • Generate data required for Niagara simulation offline (during editing).

    • Make good use of the Niagara Debugger and Insight.
