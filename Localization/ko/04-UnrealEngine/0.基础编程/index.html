    Unreal Engine C++ 프로그래밍 문서¶

    서문¶

    **Unreal Engine**은 C++로 작성된 강력한 엔진이지만, **빌드 도구(UBT)**와 **리플렉션 컴파일러(UHT)**의 존재로 인해 C++ 표준과 독립적인 문법을 가지고 있어, 사용자들은 이를 **U++**라고戏称하기도 합니다.

    문법뿐만 아니라 Unreal Engine의 개발 흐름도 일반적인 C++ 개발 흐름과 크게 다릅니다. 예를 들어 STL 표준 라이브러리는 도구 상자(Toolkit)처럼 사용되지만, **Unreal Engine**은 개발 플랫폼(Platform)처럼 기반 위에서 개발을 진행한다고 할 수 있습니다.

    현재 U++ 튜토리얼과 책이 많지 않은데, 개발자에게 도움이 되는 시리즈 문서는 다음과 같습니다:

    • 大象无形：虚幻引擎程序设计浅析
    • UE4开发指南 - Gamedev Guide
    • 循迹研究室 - 查利鹏
    • 剖析虚幻渲染体系 - 向往
    • InsideUE - 大钊

    Unreal Engine의 부족한 문서와 어려운 코드는 C++ 초보자에게 거의 넘을 수 없는 장벽입니다. 이는 Unreal Engine이 많은 개발자들에 의해 개발된 대규모 프로젝트로, 코드량이 방대하고 빠르게 업데이트되기 때문에 그 발전 과정을整理하고归纳하는 것이 매우 어렵기 때문입니다.

    저자는 몇 가지 U++ 비디오 튜토리를 보았지만, 내용이 산발적이고 대부분 UE 외피를 쓴 C++ 기초 튜토리이며,介绍하는 내용이 제한적이고 많은盲区가存在하여 학습 효율이 크지 않았습니다.

    좋은 튜토리를 발견하신 경우, 댓글에서 추천해 주세요~

    Unreal Engine을 다루려면 대규모 C++ 프로젝트의 엔지니어링 능력이 필요하며, 명확히 말씀드리자면 C++ 초보자에게 적합하지 않습니다

    만약 학생으로서 우연히 Unreal Engine이라는神奇한 도구를 발견하고, 그 화려한 그래픽 효과에 매료되어心血来潮로 U++ 개발을 배우고 싶다면, 문제 풀이와 논문 작성 외에도 다음 기술들을具备하고 있는지 고민해 보셔야 합니다:

    • C++ 엔지니어링 빌드에 익숙한지
    • 엔진의 각 하위 모듈에 대한 기본적인 인식이 있고, 대규모 프로젝트 소스 코드의閱讀能力가 있는지

    만약具备하지 않는다면, 저자는 좀 더 가만히 자신을 다듬는 것을建议하며, 무리하게 직접 도전하기보다는 기초를 다지는 것이 좋습니다.

    기초는 장기간의 다듬어야 튼튼해지고, 기술도 조금씩积累해야 층층이 높아질 수 있습니다. 어떤彎道超车를 생각하거나, 누군가가 누군가를吹嘘하는 것을 듣고 쉽게 기술이 뛰어나다고 생각하지 마세요. 실제로 산업계에는 노력하지 않는 천재가 없습니다, 적어도 저자가 존경하는 사람들에게는 예외가 없으며, 기술에는 강약之分이 없고 대부분 **闻道有先后, 术业有专攻**일 뿐입니다.

    저자의 경험을 예로 들면, 3년 전 U++를 한동안 배웠을 때 공식 문서를 한 번 훑고 다음 튜토리얼을 따라 코드를 작성했습니다:

    • https://docs.unrealengine.com/5.2/zh-CN/unreal-engine-cpp-programming-tutorials/

    이를 마치고도 혼란스러웠고, 많은 코드가莫名其妙하게 느껴졌으며, 너무 많은 지식盲区가 있어干脆放弃했습니다. 대신 볼 수 있고 만질 수 있는 것들을 배우기로 결정하여 Qt, CMake, OpenGL, 그래픽스 지식과 디지털 신호 관련 내용을学习한 후 다음 프로젝트를 진행했습니다:

    • 音频可视化图形引擎—Specinker

    이러한 기술들을熟练掌握한 후 다시 Unreal Engine을 보니, 많은 부분이明朗해졌습니다~

    **UBT(Unreal Build Tool)**를 보면, CMake와 같은 역할로 프로젝트 빌드를管理하며 다음 작업들을 수행할 수 있음을 알았습니다:

    • 빌드 대상에 의존 라이브러리(Library)、包含目录(Include Directories)、宏定义(Definitions) 추가
    • 컴파일러 설정
    • 빌드 스크립트 실행

    **UHT(Unreal Header Tool)**를 보면 Qt의 Moc(Meta Object Compiler)를 떠올렸습니다. 작업 흐름은 코드 헤더 파일을扫描하여 정보를 얻고, 새 코드 파일을 생성하여 빌드 대상에 추가하는 방식으로 UE의 코드 리플렉션을实现합니다. 리플렉션을 통해 타입 기반 컨트롤, 객체 기반 패널을实现할 수 있으며, 리플렉션 데이터를自行组织하여 블루프린트와 같은 시각적 프로그래밍 스크립트를实现할 수 있습니다.

    **Slate**를 만나면 문서 없이도 다음 사실을 추측할 수 있었습니다:

    • **FSlateApplication**은 전역 싱글톤으로 모든 UI의调度中心이며, 애플리케이션의 상태를获取하고设置할 수 있는 유용한操作을提供합니다.
    • **SWindow**는 최상위 창으로, 크로스 플랫폼 창 인스턴스(FGenericWindow)를持有하며 창 관련 설정과操作을提供합니다.
    • **SWidget**은 창 영역을划分하고,自身 영역内의交互와绘制事件를处理합니다. 처음 보았을 때 설정 가능한属性、覆盖 가능한事件 가상 함수、PaintEvent를 어떻게处理하는지查阅하는 것이 첫 번째 반응이었습니다.

    또한 기본적인 GUI 개념을映射해 보았습니다:

    • 창의 기본 상태: 활성(Active), 포커스(Focus),可见(Visible), 모달(Modal),变换(Transform)
    • 布局策略及相关概念:
    • 박스 레이아웃(HBox, VBox),流式布局(Flow),网格布局(Grid),锚式布局(Anchors),重叠布局(Overlap),画布(Canvas)
    • 내边距(Margin),外边距(Padding),间距(Spacing),对齐方式(Alignment)
    • 样式管理: 아이콘(Icon),风格(Style),画刷(Brush)
    • 字体管理:字体类型(Font Family),文本宽度测量(Font Measure)
    • 尺寸计算:控件尺寸计算策略
    • 交互事件:鼠标,键盘,拖拽,焦点事件,事件处理机制,鼠标捕获
    • 绘制事件:绘制元素,区域裁剪
    • 基本控件:标签(Label),按钮(Button),复选框(Check),组合框(Combo),滑动条(Slider),滚动条(Scroll Bar),文本框(Text),对话框(Dialog),颜色选取(Color),菜单栏(Menu Bar),菜单(Menu),状态栏(Status Bar),滚动面板(Scroll),堆栈(切换)面板(Stack/Switcher),列表面板(List),树形面板(Tree),停靠窗口(Dock),...
    • 国际化:文本本地化翻译(Localization)

    Ok, Slate를 사용하여想象할 수 있는任何界面效果를实现할 수 있음을发现했습니다.

    **RHI(Rendering Hardware Interface)**를 보면 OpenGL/Vulkan의 어떤操作에对应하는지联想할 수 있으며,自定义扩展을 하려면猫을 본 모양대로 그리기만 하면 됩니다.

    **Niagara**를 만나면 GPU粒子가 Compute Pipeline을 통해交互链上에서粒子运动을模拟하고,原子操作과间接渲染을利用하여粒子回收를 수행하며,最终粒子数据를粒子 렌더러의 매개변수에实例化数据로绑定하여粒子特效를渲染하는 것임을知道했습니다. Niagara의 Module은 Compute Shader의 코드와流水线资源를组织하는 것일 뿐이며,粒子系统的实现原理을知道하기 때문에 Niagara의流程와性能에非常敏感했습니다.

    World, Actor, Component, Controller...를 보면 Gameplay 아키텍처가这么多结构를 사용하여 코드의职责를划分할 수 있음을恍然意识到했으며, 제 반쪽짜리 수준보다 훨씬 잘 되어 있음을 느꼈습니다~

    이와 같은 예로, 일부 문서와 튜토리얼을 따라随波逐流하는 것을放弃한 후,通用框架上建立起来的知识体系가 Unreal Engine을回头审视할 때 "不同寻常"的思考维度를 제공했습니다 —— 엔진에应该有什么东西이 있을까,哦, Unreal Engine에도 있고 매우 잘 되어 있습니다.

    因此, 만약 대규모 C++ 엔지니어링 능력을具备하지 않는다면, 저자는 Qt나 일부 오픈 소스,轻量级,基础文档齐全的 엔진을学习하는 것을建议하며,自己搭建해 볼 수 있다면 더욱 좋습니다~

    扎實한基础知识体系를建立한 후,后续学习的重点은 **思路**에 있습니다.

    本文旨在阐述基础开发的主干路线,仅仅只是一个开发者文档,并非教程입니다.

    프로젝트 구조¶

    표준 UE 프로젝트의 파일 구조는 다음과 같습니다:

    • Config: 프로젝트의各类配置文件(GameConfig, EngineConfig, EditorConfig, PluginConfig...)을存放합니다.
    • Content: 프로젝트의资源文件을存放합니다.
    • Saved:暂存目录로, 프로젝트开发过程中生成的文件(日志,崩溃记录,烘焙,本地编辑器配置等)이一般적으로 여기에位于합니다.
    • Source: 프로젝트의源码文件을存放합니다.
    • MyProj.uproject: 프로젝트工程文件입니다.

    uproject¶

    *.uproject는 프로젝트의一些基本信息를存储하며,初始结构는 다음과 같습니다:

    {
    "FileVersion": 3,
    "EngineAssociation": "5.2",     
    "Category": "",
    "Description": "",
    "Modules": [                    
        {
            "Name": "MyProj",
            "Type": "Runtime",
            "LoadingPhase": "Default"
        }
    ],
    "Plugins": [
        {
            "Name": "ModelingToolsEditorMode",
            "Enabled": true,
            "TargetAllowList": [
                "Editor"
            ]
        }
    ]
}

    该文件的关键参数는 다음과 같습니다:

    • EngineAssociation: 엔진의版本입니다.
    • Modules:该工程拥有的代码模块입니다.
    • Plugins:该工程开启的 内置 插件입니다.

    这些参数는手动修改할 수 있지만,大多时候 UE编辑器上에서变更하는 것이更加安全하고方便합니다.

    工程模块添加¶

    **模块(Modules)**은 **虚拟引擎(UE)**의软件架构的基础构建块입니다.它们은独立的代码单元中一体的编程工具,运行时功能,库或其他功能을封装합니다.

    模块化编程을使用하면 다음好处를带来할 수 있습니다:

    • 模块은良好的代码分离를强制实施하며,功能封装和代码内部成分隐藏에用于될 수 있습니다.
    • 模块은单独的编译元으로编译됩니다.这意味着,只有更改된模块才需要编译되어更大项目的编译时间을显著缩短할 수 있습니다.
    • 模块은依赖性图表中链接在一起,并且实际使用的代码包만头文件을包含하도록允许하여 Include What You Use (IWYU)标准을符合합니다.这意味着,项目中未使用的模块은编辑中之外으로安全地排除될 수 있습니다.
    • 运行时任何时候加载和卸载实体的模块을控制할 수 있습니다.这样一来,哪些系统可用并活跃한지管理하여项目的性能을优化할 수 있습니다.
    • 特定条件(例如,项目가哪个平台为目标으로编写되었는지)에基于하여项目中模块을纳入或排除할 수 있습니다.

    所有项目和插件은默认情况下自己的 **主模块**을拥有합니다.

    模块创建에 대한 내용은 다음을参阅하세요:

    • 虚幻引擎模块: https://docs.unrealengine.com/5.2/zh-CN/unreal-engine-modules/
    • 创建Gameplay模块: https://docs.unrealengine.com/5.2/zh-CN/how-to-make-a-gameplay-module-in-unreal-engine/

    文档阅读 외에도 C++项目构建的一些基础概念을了解해야 합니다:

    • *.Build.cs는 UE模块的构建文件로,该模块的构建规则(包含路径,依赖库,编译选项等)을定义합니다. (CMake的CMakeLists.txt와类似)

    基本的*.Build.cs结构는 다음과 같습니다:

    using UnrealBuildTool;
using System.IO; // for Path
public class ModuleName : ModuleRules
{
    public ModuleName(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = ModuleRules.PCHUsageMode.UseExplicitOrSharedPCHs;

        PublicIncludePaths.AddRange(
            new string[] {
                // ... add public include paths required here ...
            }
        );


        PrivateIncludePaths.AddRange(
            new string[] {
                // ... add other private include paths required here ...
            }
        );


        PublicDependencyModuleNames.AddRange(
            new string[]
            {
                "Core",
                "CoreUObject",
                "Engine",
                // ... add other public dependencies that you statically link with here ...
            }
        );

        PrivateDependencyModuleNames.AddRange(
            new string[]
            {
                // ... add private dependencies that you statically link with here ...  
            }
        );
    }
}
    • UE的构建工具(UBT)는*.Build.cs에基하여项目的 工程文件 (VS工程的*.sln文件)를生成합니다.因此*.Build.cs的内容或模块的代码文件结构를修改한 경우, UBT를使用하여工程文件을重新生成해야 IDE가变更된代码和依赖关系를分析할 수 있습니다.
    • 包含路径和依赖库는 C++工程构建的基本概念입니다.
    • 包含路径는头文件定义的搜索路径를增加하는데用于됩니다.
    • 依赖库는当前模块에 链接(Link) 外部模块的实现을提供하는데用于됩니다.

    假如项目中D:/Unreal Projects/MyProj/Source/MyProj/MyHeader.h라는 C++头文件이存在한다면,它里面的代码定义를使用하려면直接 다음을使用할 수 있습니다:

    #include "D:/Unreal Projects/MyProj/Source/MyProj/MyHeader.h"

    如果*.Build.cs的IncludePaths中"D:/Unreal Projects/MyProj/Source/MyProj"를添加했다면, 다음으로 변경할 수 있습니다:

    #include "MyHeader.h"

    当前模块中其他模块的代码를使用하려면*.Build.cs的DependencyModuleNames中目标模块을添加하면 됩니다.

    如果这一步를做하지 않으면,编译时链接错误(Link Error)가 발생합니다.此时使用한结构的代码文件을找到하고, IDE를通过하여该文件이哪个*.Build.cs下에位于하는지找到한 후,它的模块名字를 DependencyModuleNames中添加하면这个问题를解决할 수 있습니다.

    Public和Private的差异¶

    简单而言, Public은可传递를代表하고, Private은仅自己使用를代表합니다.

    三个模块A, B, C가存在하고,他们的代码文件结构가 다음과 같다고 가정합니다:

    • 文件夹A
    • A.Build.cs
    • Public文件夹
      • a.h
    • Private文件夹
      • A.h
    • 文件夹B
    • B.Build.cs
    • Public文件夹
      • b.h

    • Private文件夹

      • B.h

    • 文件夹C

    • C.Build.cs
    • Public文件夹
      • c.h
    • Private文件夹
      • C.h

    *.Build.cs的伪代码는 다음과 같습니다:

    public class A(ReadOnlyTargetRules Target) : base(Target){
}

public class B(ReadOnlyTargetRules Target) : base(Target){
    PrivateDependencyModuleNames.AddRange( new string[] { "A"});
}

public class C(ReadOnlyTargetRules Target) : base(Target){
    PublicDependencyModuleNames.AddRange( new string[] { "B"});
}

    如果 **c.h**中模块A和B的文件를使用하면, 다음结果를导致합니다:

    #include "C.h"
//【编译报错0】, Private文件夹는模块C的搜索路径가 아닙니다.

#include "b.h"
//编译正常, UE는模块自身的 Public目录를自动으로 Build.cs의 PublicIncludePaths에加入하며,模块C的公有依赖中模块B가加入되었기 때문에模块B的PublicIncludePaths도模块C에传递됩니다.因此模块C中B的Public目录에正常访问할 수 있습니다.


#include "B.h"  
//【编译报错1】,模块C는模块B的Private目录에访问할 수 없습니다.

#include "A.h"          
//【编译报错2】,模块C的公有依赖中模块B가加入되었지만,模块B는私有依赖中模块A가加入되었기 때문에模块C는 A를使用할 수 없습니다.

#include "a.h"          
//【编译报错3】,模块C는模块A的任何内容에访问할 수 없습니다.

    以上报错를去除하려면*.Build.cs的结构를 다음으로 변경하면 됩니다:

    public class A(ReadOnlyTargetRules Target) : base(Target){
    PublicIncludePaths.AddRange( new string[] { "Private"});    //【编译报错3】修复,模块A的Private文件夹를公有包含路径에添加합니다.
}

public class B(ReadOnlyTargetRules Target) : base(Target){
    PublicDependencyModuleNames.AddRange( new string[] { "A"}); //【编译报错2,3】修复,模块A를模块B的公用依赖로添加하여可传递依赖를表示합니다.
    PublicIncludePaths.AddRange( new string[] { "Private"});    //【编译报错1】修复,模块B的Private文件夹를公有包含路径에添加합니다.
}

public class C(ReadOnlyTargetRules Target) : base(Target){      
    PublicDependencyModuleNames.AddRange( new string[] { "B"});
    PublicIncludePaths.AddRange( new string[] { "Private"});    //【编译报错0】修复,模块C的Private文件夹를公有包含路径에添加합니다.
}

    위 예를 보면 Public和Private的区别를理解하기并不难합니다:

    • Public은可传递를表示합니다.
    • Private은仅当前使用를表示합니다.

    读者는好奇할 수 있지만,直接统一使用Public하면很多操作을省去할 수 있으므로为什么不全用Public呢?这是因为它也会带来问题하기 때문입니다:

    • 定义冲突:引入된模块中重叠的定义(类,函数,全局变量)이出现하면编译报错를导致합니다.
    • 编译缓慢:假如模块B가模块A를引入했을 때,模块A的代码가变动하면模块B的重编译도触发되므로大量的非必要依赖는编译速度를严重拖垮할 수 있습니다.例如#include "CoreMinimal.h"也这样的问题를导致합니다.

    模块이编译冲突的风险和编译缓慢的问题가出现하지 않도록 하려면,模块을编写할 때尽可能 Private을使用하고,模块이对外传递할 필요가 있는 경우才 Public을考虑해야 합니다.

    对象系统¶

    虚幻引擎的逻辑主体는面向对象的设计范式를采用하며,所有 类(Class)가统一的管理方式를拥有하도록 하기 위해其他面向对象框架처럼自己的基类 —— **UObject**를提供합니다.

    结构¶

    它的结构层次는 다음과 같습니다:

    它主要由三级结构构成하며,这三级结构는不同的职责를有着습니다:

    • UObjectBase:数据层로, UObject의全部基础数据를定义합니다.其中包括:
    • ObjectFlags: Object的各类标识
    • InternalIndex: UE中所有Object的指针가一个数组中存放되며,这里에 index를记录하여数组中快速定位에用于됩니다.主要用于GC.
    • ClassPrivate: Object的元类型 — UClass:该类的反射数据를存储합니다.
    • NamePrivate: Object的名称
    • OuterPrivate:该Object를持有하는对象(序列化과有关, 生命周期와无关)
    • UObjectBaseUtility:数据接口层로,很多数据层的处理接口를提供합니다.

    • UObject:功能层로,大量对象系统的基本函数接口를提供합니다.

    简单的UObject类定义는 다음과 같습니다:

    UObject的对象实例를创建할 때一般情况下函数NewObject<>()를使用합니다.例如NewObject<UCustomObject>()이며,它的完整函数定义는 다음과 같습니다:

    /**
 * Convenience template for constructing a gameplay object
 *
 * @param   Outer       the outer for the new object.  If not specified, object will be created in the transient package.
 * @param   Class       the class of object to construct
 * @param   Name        the name for the new object.  If not specified, the object will be given a transient name via MakeUniqueObjectName
 * @param   Flags       the object flags to apply to the new object
 * @param   Template    the object to use for initializing the new object.  If not specified, the class's default object will be used
 * @param   bCopyTransientsFromClassDefaults    if true, copy transient from the class defaults instead of the pass in archetype ptr (often these are the same)
 * @param   InInstanceGraph                     contains the mappings of instanced objects and components to their templates
 * @param   ExternalPackage                     Assign an external Package to the created object if non-null
 *
 * @return  a pointer of type T to a new object of the specified class
 */
template< class T >
FUNCTION_NON_NULL_RETURN_START
    T* NewObject(UObject* Outer,
                 const UClass* Class, 
                 FName Name = NAME_None,
                 EObjectFlags Flags = RF_NoFlags,
                 UObject* Template = nullptr, 
                 bool bCopyTransientsFromClassDefaults = false,
                 FObjectInstancingGraph* InInstanceGraph = nullptr,
                 UPackage* ExternalPackage = nullptr)
{
    if (Name == NAME_None)
    {
        FObjectInitializer::AssertIfInConstructor(Outer, TEXT("NewObject with empty name can't be used to create default subobjects (inside of UObject derived class constructor) as it produces inconsistent object names. Use ObjectInitializer.CreateDefaultSubobject<> instead."));
    }

#if DO_CHECK
    // Class was specified explicitly, so needs to be validated
    CheckIsClassChildOf_Internal(T::StaticClass(), Class);
#endif

    FStaticConstructObjectParameters Params(Class);
    Params.Outer = Outer;
    Params.Name = Name;
    Params.SetFlags = Flags;
    Params.Template = Template;
    Params.bCopyTransientsFromClassDefaults = bCopyTransientsFromClassDefaults;
    Params.InstanceGraph = InInstanceGraph;
    Params.ExternalPackage = ExternalPackage;
    return static_cast<T*>(StaticConstructObject_Internal(Params));
}

    Object的创建에 대해注意해야 할几点는 다음과 같습니다:

    • Outer 跟 Object 的生命周期没有任何关系: Outer 매개변수는当前对象 存储上 哪个父对象에隶属于하는지指明하기 위한 것이며,资产序列化과有关합니다.

    • UClass를通过하여对象를创建할 수 있습니다: NewObject<UCustomObject>()는NewObject<UObject>(GetTransientPackage(), UCustomObject::StaticClass())와等价합니다.

    通常,虚幻引擎中接触到的绝大部分对象는 **UObject**이며,代码层面에서任意的UObject를创建하려면一般적으로 다음方式를使用합니다:

    UObject* MyObject = NewObject<UObject>();

UTexture2D* MyTexture = NewObject<UTexture2D>();

UBlueprint* MyBlueprint = NewObject<UBlueprint>();

UStaticMesh* MyStaticMesh = NewObject<UStaticMesh>();

UNiagaraSystem* MyNiagaraSystem = NewObject<UNiagaraSystem>();

AActor* MyActor = NewObject<AActor>();

UStaticMeshComponent* MyStaticMeshComponent = NewObject<StaticMeshComponent>();

UWorld* World = NewObject<UWorld>();

...

    这些语句는虚幻中语法上错误가 없으며,编译通过할 수 있습니다.

    但虚幻에熟悉한小伙伴는比较清楚할 수 있지만,直接这样去创建对象하면虽然确实创建成功할 수 있지만,它的某些机制很有可能正常工作하지 않습니다.这是因为那些类型는特定的构造数据和逻辑를伴随着하며,引擎往往会它를新的接口로包裹하기 때문입니다.例如:

    • UWorld::CreateWorld(...)를使用하여 UWolrd를构造합니다.
    • UWorld::SpawnActor( ... )를使用하여对应世界中Actor를创建합니다.
    • FKismetEditorUtilities::CreateBlueprint(...)를使用하여编辑器下蓝图(UBlueprint)를创建합니다.
    • Actor的构造函数中UObject::CreateDefaultSubobject(...)를使用하여当前Actor에隶属于하는组件结构를创建합니다.
    • ...

    因此如果NewObject()를使用하여创建된对象의某些机制가正常工作하지 않는다면,很有可能引擎이特定的构造逻辑를封装했습니다.如果找到하지 못했다면,那些初始化和注册的逻辑를寻找하여手动执行해 보십시오.

    销毁¶

    UObject对象的创建 외에도,它的销毁 즉生命周期的管理도非常重要합니다.

    众所周知,虚幻은自动的垃圾回收机制를拥有하며,这는对象引用에基于한定时定量的回收方式입니다.

    开发者而言,通常我们不需要该机制的执行原理를深入剖析하며,它的基本使用를掌握하면够了입니다.基本使用主要有以下几点:

    • 引擎如何一个对象가垃圾인지界定하는가?
    • GC를如何配置和使用하는가?

    UE中一个对象가垃圾로视为되지 않도록 하는 **直接的途径**는四种가 있습니다:

    • NewObject时EObjectFlags::RF_Standalone标识를使用합니다.该标识는创建된对象가 **编辑器**中一直GC回收되지 않도록保证합니다(详见GarbageCollection.h line28).

    • 函数 void UObject::AddToRoot()를使用하여对象를根对象集合中加入할 수 있습니다.从而对象가释放되지 않도록 하며, void UObject::RemoveFromRoot()를使用하여对象를根对象集合中移除할 수 있습니다.

    • **FGCObject**类를派生합니다.它는UE中各个模块的对象生命周期管理에广泛用于됩니다:

      UE가 GC를执行할 때, **所有FGCObject对象**의 virtual void AddReferencedObjects( FReferenceCollector& Collector )函数를调用합니다. **Collector**는操作入口로, **Collector**中添加된对象는本次GC中释放되지 않습니다.

      而 **FGCObject**的构造函数中,该对象를UE全局的 FGCObject对象列表中注册합니다.相当于FGCObject类를派生한对象는一个根对象로作为될 수 있습니다.

      因此开发者는自己原生的结构定义上public FGCObject를增加하고,它的相关函数를派生하기만 하면 됩니다:

      class FMyManager : public FGCObject {
    virtual void AddReferencedObjects(FReferenceCollector& Collector) override {
        //Collector.AddReferencedObject(...)
        //..
    }
    virtual FString GetReferencerName() const override{ return TEXT("FMyManager"); }   
};

    • 智能指针 **TStrongObjectPtr**를使用하여对象를存储합니다.它的本质其实依旧是 **FGCObject**를使用하지만,这个结构는非常重因此大规模使用를推荐하지 않습니다.详见:

      • UE4的智能指针 UObject相关

    而 **间接的途径**는:

    • 一个对象가目前垃圾가 아닐 때,它所引用的对象도垃圾가 아닙니다.

    UE中主要是反射를通过하여对象间的引用를构建和分析합니다.例如这样的代码:

    UCLASS()
class UCustomObject :public UObject {
public:
    UCustomObject() {}

    UPROPERTY()         
    UObject* Prop = nullptr;
};

int main() {
    auto A = NewObject<UCustomObject>();
    auto B = NewObject<UCustomObject>();
    A->Prop = B;        
    A->AddToRoot();
    // Engine Loop
    return 0;
}
    • 对象A가根对象集合中添加되었기 때문에它가释放되지 않으며,又因为UE가反射에基하여对象A的Prop属性가对象B를引用하는 것을确定했기 때문에 B也释放되지 않습니다.

    使用에 대해,我们可以直接以下函数를使用하여手动对象를销毁할 수 있습니다:

    • bool UObject::ConditionalBeginDestroy(): GC를等待하지 않고直接对象를销毁합니다.
    • void UObject::MarkAsGarbage():垃圾로标记하며,下一次GC时释放될 수 있습니다.

    也可以如下代码를使用하여当前帧手动GC를执行할 수 있습니다:

    bool bForceGarbageCollectionPurge = true;   //是否为全量GC
GEngine->ForceGarbageCollection(bForceGarbageCollectionPurge);

    另外,需要特别注意的是, UE的 对象系统 和 反射系统 相辅相成하며,一些原因导致UObject对象 析构函数를没有使用 去资源的释放逻辑를完成하기 때문에,析构逻辑를实现해야 할 때 UObject的虚函数를覆写해야 합니다:

    • virtual void BeginDestroy()

-   **UCLASS()** ：UClass，클래스의 설명 정보를 저장
-   **USTRUCT()** ：UScriptStruct，구조체의 설명 정보를 저장
-   **UENUM()** ：UEnum，열거형의 설명 정보를 저장
-   **UPROPERTY()** ：FProperty，속성의 설명 정보를 저장
-   **UFUNCTION()** ：UFunction，함수의 설명 정보를 저장
-   **UINTERFACE()** ：없음

    CDO（Class Default Object）¶

    UE의 리플렉션 시스템은 UObject에 Class Default Object 라는 메커니즘을 제공합니다，즉：각 클래스에는 기본 객체가 있습니다.

    CDO의 존재로 인해 각 Class는 전역 싱글톤 을 가지게 됩니다.

    다음 함수를 통해 CDO를 가져올 수 있습니다：

    UObject* UClass::GetDefaultObject(bool bCreateIfNeeded = true) const
{
    if (ClassDefaultObject == nullptr && bCreateIfNeeded)   // 존재하지 않으면 새로 생성
    {
        UE_TRACK_REFERENCING_PACKAGE_SCOPED((GetOutermost()), PackageAccessTrackingOps::NAME_CreateDefaultObject);
        const_cast<UClass*>(this)->CreateDefaultObject();
    }
    return ClassDefaultObject;
}

    UE는 CDO를 가져오는 편리한 방법도 제공합니다：

    const UObject* ConstCDO = GetDefault<UObject>();         //CDO의 Const 포인터 가져오기

    직렬화（Serialize）¶

    UObject는 직렬화 및 역직렬화를 지원하므로，어떤 UObject도 자산（Asset）으로 사용할 수 있습니다.

    UE의 직렬화 인터페이스는 다음과 같습니다：

    class UObject{
    /** 
     * FArchive를 사용하여 읽기，쓰기 및 참조 수집을 처리합니다.

    블루프린트（Blueprint）¶

    Unreal Engine 리플렉션의 가장 강력한 점은 개발자가 코드를 스캔하여 리플렉션 데이터를 생성할 수 있을 뿐만 아니라 **리플렉션 데이터 구조를 직접 생성하고 조직할 수 있다**는 것입니다.

    다음은 코드를 사용하여 UClass를 구성하는 예시입니다：

    DEFINE_FUNCTION(execIntToString)                //사용자 정의 네이티브 함수

    P_FINISH;                                   //가져오기 완료
    *((FString*)RESULT_PARAM) = FString::FromInt(IntVar);       //반환 값 설정
}

    UClass* CustomClass = NewObject<UClass>(GetTransientPackage(),"CustomClass");       //사용자 정의 클래스

UFunction* CustomFucntion = NewObject<UFunction>(CustomClass, "IntToString", RF_Public);
CustomFucntion->FunctionFlags = FUNC_Public | FUNC_Native;  //네이티브 함수는 네이티브 C++ 함수를 의미하며，그렇지 않으면 블루프린트 스크립트의 함수 코드를 의미합니다.

FIntProperty* IntParam = new FIntProperty(CustomFucntion, "IntParam", EObjectFlags::RF_NoFlags);
IntParam->PropertyFlags = CPF_Parm;                         //함수 매개변수로 사용

FStrProperty* StringReturnParam = new FStrProperty(CustomFucntion, "StringReturnParam", EObjectFlags::RF_NoFlags);
StringReturnParam->PropertyFlags = CPF_Parm | CPF_ReturnParm;       // 함수 반환 값으로 사용（CPF_Parm을 포함해야 함）

CustomFucntion->ChildProperties = IntParam;                         // 함수 반환 값은 후속 매개변수 오프셋을 계산하기 위해 마지막 노드여야 합니다.
IntParam->Next = StringReturnParam;

CustomFucntion->SetNativeFunc(execIntToString);                     // 네이티브 함수 설정
CustomFucntion->Bind();                                                 
CustomFucntion->StaticLink(true);                                   // 모든 속성 연결，이 작업은 Property의 메모리 크기，오프셋 값 등을 생성합니다.
CustomFucntion->Next = CustomClass->Children;                       // Function을 Class Children 링크 리스트의 헤드에 추가하여 Field에 액세스할 수 있도록 합니다.
CustomClass->Children = CustomFucntion;

CustomClass->AddFunctionToFunctionMap(CustomFucntion, CustomFucntion->GetFName());  //사용자 정의 함수를 사용자 정의 클래스의 함수 테이블에 추가

CustomClass->Bind();
CustomClass->StaticLink(true);                          // 모든 속성 연결
CustomClass->AssembleReferenceTokenStream();            // 속성의 GC와 연결，사용자 정의 클래스 구성 완료

UObject* CDO = CustomClass->GetDefaultObject();         

// CDO의 속성에 값 할당
void* IntPropPtr = IntProp->ContainerPtrToValuePtr<void*>(CDO);
IntProp->SetPropertyValue(IntPropPtr, 789);

FVector Vector(1, 2, 3);
void* VectorPropPtr = VectorProp->ContainerPtrToValuePtr<void>(CDO);
VectorProp->CopyValuesInternal(VectorPropPtr, &Vector, 1);

// 사용자 정의 함수 호출
int InputParam = 12345;
UFunction* Func = CustomClass->FindFunctionByName("IntToString");
uint8* Params = (uint8*)FMemory::Malloc(Func->ReturnValueOffset);       //매개변수 버퍼 할당
FMemory::Memcpy((void*)Params, (void*)&InputParam, sizeof(int));
FFrame Frame(CDO, Func, Params, 0, Func->ChildProperties);
FString ReturnParam;
Func->Invoke(CDO, Frame, &ReturnParam);

    그 후，우리는 직접 생성한 UClass를 사용하여 UObject를 생성할 수도 있습니다：

    UObject* CustomObject = NewObject<UObject>(GetTransientPackage(), CustomClass);

    UE의 블루프린트는 위 작업을 일부 포장하고相应的 편집기를 제공한 것에 불과합니다.

    UE의 블루프린트에 해당하는 데이터 구조는 UBlueprint 이며，우리가 블루프린트 편집기에서 수행하는 대부분의 작업（속성，함수 작업，노드 편집，클래스 설정...）은 기본적으로 UBlueprint 의 매개변수를 수정하는 것입니다：

    다음 인터페이스를 사용하여 블루프린트를 생성할 수 있습니다：

    static UBlueprint* FKismetEditorUtilities::CreateBlueprint(
    UClass* ParentClass,
    UObject* Outer, 
    const FName NewBPName,
    enum EBlueprintType BlueprintType,
    TSubclassOf<UBlueprint> BlueprintClassType,
    TSubclassOf<UBlueprintGeneratedClass> BlueprintGeneratedClassType, 
    FName CallingContext = NAME_None);

    매개변수의 의미는 다음과 같습니다：

    • ParentClass ：부모 클래스，생성된 블루프린트는 해당 Class의 속성과 메서드를 상속합니다.

    • Outer ：생성된 블루프린트의 Outer（소유자）

    • NewBPname ：생성된 블루프린트의 이름

    • BlueprintType ：블루프린트의 타입，다음 값을 사용할 수 있습니다：

      enum EBlueprintType
{
    /** 일반 블루프린트 */
    BPTYPE_Normal               UMETA(DisplayName="Blueprint Class"),
    /** 실행 중에 const인 블루프린트（상태 그래프가 없고 메서드가 멤버 변수를 수정할 수 없음） */
    BPTYPE_Const                UMETA(DisplayName="Const Blueprint Class"),
    /** 다른 블루프린트에서 사용할 매크로를 포함하는 블루프린트 */
    BPTYPE_MacroLibrary         UMETA(DisplayName="Blueprint Macro Library"),
    /** 다른 블루프린트에서 구현할 인터페이스로 사용되는 블루프린트 */
    BPTYPE_Interface            UMETA(DisplayName="Blueprint Interface"),
    /** 레벨 스크립팅을 처리하는 블루프린트 */
    BPTYPE_LevelScript          UMETA(DisplayName="Level Blueprint"),
    /** 다른 블루프린트에서 사용할 함수를 포함하는 블루프린트 */
    BPTYPE_FunctionLibrary      UMETA(DisplayName="Blueprint Function Library"),

    BPTYPE_MAX,
};

    • BlueprintClassType ：블루프린트 클래스의 기본 템플릿，기본적으로 UBlueprint::StaticClass()를 사용할 수 있으며，사용자 정의 블루프린트 구성에 사용할 수 있습니다.

    • BlueprintGeneratedClassType ：블루프린트 생성 클래스의 기본 템플릿，기본적으로 UBlueprintGeneratedClass::StaticClass()를 사용할 수 있으며，사용자 정의 생성 전략에 사용할 수 있습니다.

    • CallingContext ：호출 컨텍스트，기본적으로 비어 있습니다.

    블루프린트 생성 로직은 간단히 다음과 같이 볼 수 있습니다：

    UBlueprint* FKismetEditorUtilities::CreateBlueprint(
    UClass* ParentClass,
    UObject* Outer,
    TSubclassOf<UBlueprint> BlueprintClassType,
    TSubclassOf<UBlueprintGeneratedClass> BlueprintGeneratedClassType)
{
    UBlueprint* NewBP = NewObject<UBlueprint>(Outer,*BlueprintClassType);   //BlueprintClassType에 따라 인스턴스 생성
    NewBP->ParentClass = ParentClass;

    UBlueprintGeneratedClass* NewGenClass =                                 //BlueprintGeneratedClassType에 따라 인스턴스 생성
        NewObject<BlueprintGeneratedClassType>(NewBP->GetOutermost(),*BlueprintGeneratedClassType);

    NewGenClass->SetSuperStruct(ParentClass)            //NewGenClass의 부모 클래스를 ParentClass로 설정，이렇게 하면 해당 속성과 메서드에 액세스할 수 있습니다.

    NewBP->GeneratedClass = NewGenClass;                //새로 생성된 UClass를 NewBP->GeneratedClass에 할당 
}

    블루프린트 편집기의 컴파일 버튼을 클릭하면

    실제로 다음 함수가 호출됩니다：

    static void FKismetEditorUtilities::CompileBlueprint(UBlueprint* BlueprintObj, 
                             EBlueprintCompileOptions CompileFlags = EBlueprintCompileOptions::None,
                             class FCompilerResultsLog* pResults = nullptr );

    이 함수의 목표는 블루프린트 편집기의 속성 목록 和 로직 다이어그램 에 ParentClass를 더하여 UBlueprint의 멤버 변수GeneratedClass 를 생성하는 것입니다.

    일반적으로 C++ 측에서 블루프린트를 사용하는 단계는 다음과 같습니다：

    UClass * BlueprintGenClass = LoadObject<UClass>(nullptr, "/Game/NewBlueprint.NewBlueprint_C");      //블루프린트의 생성 클래스 가져오기
UObject* Instance = NewObject<UObject>(GetTransientPackage(),Blueprint->GeneratedClass);            //클래스에 따라 객체 인스턴스 생성

UFunction* Func = Blueprint->GeneratedClass->FindFunctionByName("FuncName");     // 클래스 리플렉션 데이터에서 [FuncName]이라는 이름의 함수 찾기
Instance->ProcessEvent(Func, nullptr);                                           // 블루프린트에 정의된 함수 호출

FProperty* Prop = FindFProperty<FProperty>(Blueprint->GeneratedClass, "IntProp");// 클래스 리플렉션 데이터에서 [IntProp]이라는 이름의 속성 찾기
int value = 0;
Prop->GetValue_InContainer(Instance,&value);        //속성 가져오기
Prop->SetValue_InContainer(Instance,&value);        //속성 설정

    /Game/NewBlueprint.NewBlueprint_C 를 사용하면 정확히 UBlueprint의 멤버 변수GeneratedClass 를 얻을 수 있으며，여기서 /Game/NewBlueprint는 Package 경로，NewBlueprint_C는 멤버 변수GeneratedClass 의 객체 이름입니다.

    UBlueprint 가 생성한 UClass 에 대해，UClass 의 멤버 변수 ClassGeneratedBy에 액세스하여 해당 UBlueprint 를 가져올 수 있으며，다음 함수를 사용할 수도 있습니다：

    static UBlueprint* UBlueprint::GetBlueprintFromClass(const UClass* InClass);

    블루프린트의 원리를 이해한 후，사용하기 어렵지 않습니다. 다음은 코드를 사용하여 블루프린트를 생성하고 편집기를 열리는 예시입니다：

    자산 시스템¶

    NewObject의 함수 원형은 다음과 같습니다：

    template< class T >
T* NewObject(UObject* Outer = (UObject*)GetTransientPackage());

    여기서 Outer는 간단히 부모 객체로 이해할 수 있으며，Outer 는 UObject의 GC와 관련이 없으며，자산 저장 구조상의 관계를 지정하는 역할을 합니다.

    UE의 자산 객체는 물리 파일과 동일하지 않으며，실제로 디스크의 *.uasset和*.umap 파일은 해당 UPackage 객체에 해당하는 것으로 이해할 수 있습니다.

    UE에서 자산을 생성할 때，먼저 실제 물리 파일 매핑으로 UPackage를 생성한 다음 NewObject를 사용하여 실제 자산을 생성하며，이때 Outer를 Package로 지정합니다. Package를 저장할 때，해당 Package가 소유하는 모든 UObject를 물리 파일에 직렬화하며，이 과정은 다음과 같습니다：

    // 새 Package 생성，/Game/CustomPackage는 패키지 경로，여기서 /Game은 프로젝트의 Content 디렉토리를 의미합니다.
UPackage* CustomPackage = CreatePackage(nullptr, TEXT("/Game/CustomPackage"));

// 새 자산 생성，임의의 UObject를 사용할 수 있습니다（여기서는 UObject가 추상 클래스이므로 경고가 발생합니다）
UObject* CustomInstance = NewObject<UObject>(CustomPackage, UObject::StaticClass(),
                                             TEXT("CustomInstance"), 
                                             EObjectFlags::RF_Public | EObjectFlags::RF_Standalone);    

// Package의 로컬 디스크 경로 가져오기
FPackagePath PackagePath = FPackagePath::FromPackageNameChecked(CustomPackage->GetName());
const FString PackageFileName = PackagePath.GetLocalFullPath();

// 패키지를 디스크에 저장
const bool bSuccess = UPackage::SavePackage(CustomPackage,
                                            CustomInstance, 
                                            RF_Public | RF_Standalone,
                                            *PackageFileName,
                                            GError, nullptr, false, true, SAVE_NoError);

    이 작업은 프로젝트의 Content 디렉토리에 CustomPackage.uasset 파일을 생성합니다.

    다음 코드를 통해 디스크의 패키지와 자산 객체를 로드할 수 있습니다：

    UPackage* LoadedPackage = LoadPackage(nullptr, TEXT("/Game/CustomPackage"), LOAD_None);
UObject* LoadedAsset = LoadObject<UObject>(nullptr,TEXT("/Game/CustomPackage.CustomInstance"));

    해당 자산을 UE 편집기에서 생성하고 미리 볼 수 있도록 하려면：

    • UFactory 를 파생하여 자산 객체의 생성 공장 정의
    • FAssetTypeActions_Base 를 파생하여 자산의 편집기에서 미리 보기，메뉴 등의 행동 정의

// 수동으로 엔진의 Tick 업데이트 실행
static void FakeEngineTick(UWorld* InWorld, float InDelta = 0.03f)    
    FApp::SetDeltaTime(InDelta);

    GEngine->EmitDynamicResolutionEvent(EDynamicResolutionStateEvent::EndFrame);
    GEngine->Tick(InDelta, false);                                  // 여기에는 현재 World의 업데이트가 포함됩니다.

    FSlateApplication::Get().PumpMessages();
    FSlateApplication::Get().Tick();

    GFrameCounter++;

    bool bIsTicking = FSlateApplication::Get().IsTicking();
    if (!bIsTicking && GIsRHIInitialized) {
        if (FSceneInterface* Scene = InWorld->Scene) {
            ENQUEUE_RENDER_COMMAND(BeginFrame)([](FRHICommandListImmediate& RHICmdList) {
                GFrameNumberRenderThread++;
                GFrameCounterRenderThread++;
                FCoreDelegates::OnBeginFrameRT.Broadcast();
            });

            ENQUEUE_RENDER_COMMAND(EndFrame)([](FRHICommandListImmediate& RHICmdList) {
                FCoreDelegates::OnEndFrameRT.Broadcast();
                RHICmdList.EndFrame();
            });
            FlushRenderingCommands();
        }
        ENQUEUE_RENDER_COMMAND(VirtualTextureScalability_Release)([](FRHICommandList& RHICmdList) {
            GetRendererModule().ReleaseVirtualTexturePendingResources();
        });
    }

    FTaskGraphInterface::Get().ProcessThreadUntilIdle(ENamedThreads::GameThread);

    FSlateApplication::Get().GetRenderer()->Sync();

    FThreadManager::Get().Tick();

    FTSTicker::GetCoreTicker().Tick(InDelta);

    GEngine->TickDeferredCommands();

    GEngine->EmitDynamicResolutionEvent(EDynamicResolutionStateEvent::EndFrame);

    FAssetCompilingManager::Get().FinishAllCompilation();
}

    델리게이트¶

    UE에서는 객체 간 통신을 위해 델리게이트（Delegate） 개념을 사용하며，일반적이고 타입 안전한 방식으로 C++ 함수를 호출할 수 있습니다.

    Qt를 잘 알고 있다면，Delegate는 실제로 Qt의 신호 슬롯（Signal-Slot）의 Signal에 해당하며，Delegate는 Signal보다 더 강력하며 사용도 더 복잡해집니다.

    가장 큰 단점은 명명법인데，만약 Signal이라고 불렀다면 개발자가 더 쉽게 연상을 하여 올바른 사용 방식을 채택할 수 있었을 것입니다.

    다음은 Delegate를 사용하는 시나리오 예시입니다（Signal 명명법을 사용한 의사 코드）：

    class Student{
    Signal nameChanged(string OldName, string NewName);
public:
    void setName(string inName){
        string oldName = mName;
        mName = inName;
        nameChanged.Emit(oldName,mName);
    }
private:
    string mName;
};

class Tearcher{
public:
    void OnStudentNameChanged(string OldName, string NewName){
        // do something
    }
};

class Class{
protected:    
    void connectEveryone(){
         for(auto Student:mStudents){       
             Student.nameChanged.Connect(mTeacher,&Tearcher::OnStudentNameChanged);
         }
    }
private:
    Teacher mTeacher;
    TArray<Student> mStudents;
};

    이 예시에서 connectEveryone 함수가 완료하는 기능은："선생님"이 반에서 학생들에게 "만약 이름을 바꾸면 저에게 알려주세요"라고 말하는 것입니다.

    여기서는 Teacher와 Student의 구조를 직접 수정하지 않고，제3자（반）에서 두 관계를 바인딩하여 코드의 결합도를 낮춥니다.

    델리게이트를 사용하지 않고 동일한 기능을 구현하려면 다음과 같은 불편한 코드를 작성해야 할 수 있습니다：

    class Student{
public:
    Student(Class* InClass)     //상위 논리 영역의 포인터 전달 필요
        : mClass(InClass){}

    void setName(string inName){
        string oldName = mName;
        mName = inName;

        //안전하지 않은 연쇄 호출，상황이 큰 호출은 후속 유지 보수와 반복을 어렵게 만듭니다.
        mClass->mTeacher->OnStudentNameChanged(OldName,mName);  
    }
private:
    string mName;
    Class* mClass
};

class Tearcher{
public:
    void OnStudentNameChanged(string OldName, string NewName){
        // do something
    }
};

class Class{
    friend class Student;
private:
    Teacher mTeacher;
    TArray<Student> mStudents;
};
