    Landscape 함정 피하기 가이드¶

    개요¶

    지형（Landscape）은 현대 게임의 기본 그래픽 요소로, 그래픽 엔지니어링의 복잡성이 높아지고 개발 팀이 점점 '젊어짐'에 따라 효과 구현과 편집기 수준의 사용에만 집중하고 중요한 세부 사항을 무시하면 크고 작은隐患을 남길 수 있으므로 본 문서에서 이에 대해 소개합니다.

    대부분의 그래픽 엔지니어링에서 가장 많이 사용되는 그래픽 요소는 의심할 여지 없이 —— 정적 메시（Static Mesh）로, 공간 좌표, UV, 법선 등의 정점 기하 데이터와 재질 텍스처를 결합하여 그래픽 효과를 표현합니다:

    정적 메시는 현대 게임 개발에서 매우 중요한 위치를 차지하며 게임 세계 기하학을 구축하는 기본 단위가 되었고, 3dsMax、Maya、Blender、Zbrush 등의 전문 모델링 소프트웨어는 디자이너에게 큰 편의성과 자유도를 제공하여 빠르게 예상하는 그래픽 효과를 디자인할 수 있게 합니다.

    이와 비교하여 지형은 비교적 특수한 그래픽 요소로, 정적 메시처럼 직접 삼각형 정점 데이터를 사용하여 표현하지 않고 높이 맵（Heightmap）에 의존합니다:

    이 이미지는 https://manticorp.github.io/unrealheightmap 에서 생성되었습니다.

    높이 맵의 각 픽셀은 실제 정점 좌표에 대응하며 매핑 관계는 다음과 같습니다:

    • 픽셀 좌표（XY）> 정점 수평 좌표（XY）
    • 픽셀 그레이스케일 값（Grayscale）> 정점 높이（Z）

    높이 맵은 2차원 수치 배열로 간주할 수 있으며 기본 요소 타입은 일반적으로 16비트 무부호 정수로, 해당 C++ 구조는 다음과 같습니다:

    uint16_t HeightMap[Height][Width];

    실제 변환 규칙은 소프트웨어에 따라 미세한 차이가 있을 수 있으며, 언리얼 엔진이 사용하는 기본 단위는 센티미터（cm） 이고 변환 규칙은 다음과 같습니다:

    • 정점 수평 좌표는 픽셀 좌표에서 직접 변환되며, 어떠한 스케일링도 하지 않는 경우 UE 지형 수평 방향의 최소 표현 정밀도는 1 cm 입니다.
    • 픽셀 그레이스케일은 16비트 무부호 정수로 저장되므로 65536개의 다른 높이 레벨을 구분할 수 있으며, UE는 이를 직접 cm에 매핑하지 않고 [-256.0, 255.992]의 부동소수점 범위로 재매핑 합니다. 즉, 어떠한 스케일링도 하지 않는 경우 UE 지형 수직 방향이 표현할 수 있는 높이 범위는 -256.0 cm ~ 255.992 cm 이며, 높이가 표현할 수 있는 최소 정밀도는 0.0078125 cm 입니다.

    종합하면 일부 친구들은 다음과 같은 의문을 가질 수 있습니다:

    • 동일한 그래픽 효과를 구현하기 위해 정적 메시를 사용하면 매우 높은 정밀도와 자유도를 가지고 지형을 사용하면 많은 제한이 있는데, 왜 우리는 여전히 지형을 사용해야 할까요?

    실제로 지형 사용은 본질적으로 场景规模（Scene Scale）과 高精度（High Precision）의取舍（Trade-off）입니다.

    먼저 지형이 어떤 단점을 가지고 있는지 살펴보겠습니다:

    • 수평 방향 정밀도 제한 ：예를 들어 UE5 비WP 맵이 지원하는 높이 맵의 최대 크기는 8129로, 어떠한 스케일링도 하지 않는 경우 수평 너비는 81.29 m로 표현할 수 있습니다. 더 큰 영역 범위를 표현하려면 예를 들어 100배로 스트레치해야 66.08km의 영역을 표현할 수 있으며, 이때 수평 방향의 최소 표현 정밀도는 1m로 변하여 1m보다 작은 기하학적 세부 사항은 모두 손실됩니다.
    • 높이 표현 범위 제한 ：어떠한 스케일링도 하지 않는 경우 높이 표현 범위는 -256.0 cm ~ 255.992 cm로, 2000m의 높은 산을 표현하려면 높이를 원래의 1000배로 스트레치해야 하며, 이는 높이의 최소 표현 정밀도가 7.8125cm로 변하여 지형의 충돌 계산에 최소 7cm의 계산 오차가 발생하게 합니다.
    • 토폴로지 구조의 단일성 ：지형은 본질적으로 "연속적인 높이 필드 메시"로 "단일 층면의起伏"만 지원하며 정적 메시의 복잡한 토폴로지（예: 공중 플랫폼, 지형 교차, 지하 동굴 등）를 구현할 수 없습니다.
    • 비교적 거친 편집 입도 ：지형 편집은 "브러시 그리기"（예:抬升、降低、平滑）에 의존하며 정적 메시처럼 "정점 수준 편집"을 통해 각凸起或凹陷을 정확하게 제어하기 어렵습니다.
    • 협업 개발의 복잡성 ：높이 맵、가중치 맵은 단일 파일로 여러 사람이 동시에 편집하면 데이터가 덮어씌워지므로 버전 관리 도구를 통해 엄격하게 관리해야 합니다.

    하지만 이렇게 많은 단점이 있음에도 지형은 현재 하드웨어 수준에서 대규모 장면의 유일한 해결方案 입니다.

    예를 들어 1km²의 장면을 구축하려고 그리드 평면으로铺设하고 평균 기하학적 정밀도를 10cm×10cm로 보장한다고 가정하면, 이는 이미 낮은 정밀도임에도 불구하고 1억（10000×10000）개의 삼각형 정점이 필요하며 UE5 정적 메시 하나의 정점 점유 공간은 일반적으로 28바이트（위치:12 + 접선X:4 + 접선Z:4 + UV:8）이므로 전체 지형 메시가 점유하는 압축되지 않은 공간은 약 다음과 같습니다:

    • 28 x 10000 x 10000 ÷ 1024³ ≈ 2.61 GB

    이것은 기하학적 데이터일 뿐이며, 平铺贴图（Tiled Texture） 를 사용하지 않는 경우 10cm의 텍셀 정밀도는 화면 효과를 보장할 수 없어 흐릿함、모자이크가 발생할 것이며 "근거리 시각적 선명도"를 보장하려면（예:1cm×1cm의 지면이 1개의 텍셀에 대응）텍셀이 필요한 픽셀 총량은 100억에 달하며 4개의 채널（ARGB_8888）만 사용하여 색상을 표현하는 경우 압축되지 않은 공간은 약 다음과 같습니다:

    • 4 x 100000 x 100000 ÷ 1024³ ≈ 37.25 GB

    이것은 단지 1km²의 장면일 뿐입니다.

    실제로 저자가 최근 몇 년 동안 접한 바에 따르면 많은 팀（게임 산업에만 국한되지 않음）이 그래픽 장면의 데이터 규모에 대한 깊은 인식이 없으며 특히 기획/제품 관점에서 개방형 장면은 충분히 많은 요소로 장면을 크게铺设하는 것일 뿐이라고 생각합니다.

    이러한 배경下에서稍大一些的 장면을 구축하려면 지형이 거의 필연적인 선택이며 위에서 언급한 일부 단점 외에도 무시할 수 없는 여러 장점이 있습니다:

    • 메모리 ：지형의 각 정점은 4바이트（RG 채널은 높이 저장, BA 채널은 압축된 법선 저장）만 필요하며 정적 메시의 메모리 점유 공간은 일반적으로 지형의 6~7배입니다.
    • 텍스처 ：지형은 "높이와 무관한 월드 공간 매핑"으로 지형起伏（높이 올리기、평탄화、산 만들기）를 어떻게 수정하든 텍셀의平铺 정밀도는 항상 변하지 않으므로平铺贴图를 사용하기 매우 편리합니다. 정적 메시는 모델 형태를 수정하면（예: 평탄한 지면을 경사면으로 변경）텍스처가 모델과 함께 스트레치 변형되므로 매우 어렵습니다. 또한 정적 메시의 세부 사항은 주로 텍스처와 UV 정밀도에 의존하는 반면 지형은平铺贴图에 세부 텍스처、경사 텍스처 등 여러 층의 텍스처를叠加하여 계층 효과를 개선할 수 있습니다.
    • LOD ：지형의 LOD는 "높이 필드 기반 동적 단순화"로 GPU는 자동으로 Mipmap을 통해 저해상도 텍스처 Mip 레이어를 전환하여 원거리 렌더링 효율을 보장하면서 텍스처 스트레치를 방지합니다. 정적 메시의 LOD는 각 레벨에 대해 독립적인 저정밀 모델을制作해야 합니다.
    • 충돌 ：지형은 高度场碰撞体（Heightfield Collider）를生成하여 사용하며 파괴 가능을 지원하고 데이터 구조의 특성으로 인해 충돌 계산 효율이 메시 충돌보다 훨씬 높으며 간극이 존재하지 않아 충돌 관통 문제에 대한 방호 안전성이 정적 메시보다 훨씬 우수합니다.
    • 워크플로우 ：게임 엔진에서 지형은 기본 그래픽载体로视为되며 엔진은 지형을围绕하여 식생 시스템、지형附着物의程序化生成、광선烘焙等非常多的 도구와流程를搭建했습니다.

    Landscape 사용에 대한 공식 문서는 지형의 개념、LOD 및 충돌 관리에 대해 자세히介绍하고 있습니다:

    • https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-outdoor-terrain-in-unreal-engine

    지형의 원리에 대해 매우 자세히剖析한文章가 있습니다:

    • 언리얼 엔진 지형 시스템 원리 메커니즘 소스 코드剖析 - MarsZhou：https://zhuanlan.zhihu.com/p/668278748

    계획¶

    실제 게임 프로젝트의 경우 지형의 구현 원리와 도구 사용만 아는 것은 종종不够하며 초기 설계阶段에서一些规划을制定해야 합니다.

    场景规模明确¶

    场景의 크기는一定程度上游戏内容의体量를决定하며 UE 표준小白人（Standard Mannequin）을 예로 들면 기본 이동 속도는 600cm/s로 1000m 거리를 이동하는 데 2분 46초가 걸리므로 이를结合하여实际游戏内容에 따라大致所需的场景规模를评估할 수 있습니다.

    场景 크기가 1km²보다 크고大量의 GameObject를拥有하는 경우 World Partition을使用하여场景的 Steaming을组织해야 합니다.

    주의할 점은游玩区域가非常大的场景（예:64km²）을搭建하려면千万不要一个 지형으로整个场景搭建을完成해야 한다는 것입니다.过大的场景规模는资产管理、맵 편집、玩法 및关卡设计의复杂度를大幅提升시켜 프로젝트의迭代速度를严重拖垮할 수 있습니다.

    UE WP 맵이目前支持하는 높이 맵의最大 크기는 65281이지만个人建议는单个 지형의 크기를 4km²를超過하지 않는 것이며独立的子关卡에서游戏内容의迭代을进行하고 해면、강 또는 산脉等元素를通过하여子맵을拼接하는主맵을专门负责하는 것입니다. 다음과 같습니다:

    UE 5.4之后关卡实例의诸多问题이有效解决되었으므로 이를依靠하여这样的 워크플로우를推动할 수 있으며后文所述的目标는单个 지형块에만针对됩니다.

    分辨率确定¶

    单个 지형의规模确定之后 지형이表示하는最小 기하학적 정밀도를确定해야 합니다. 수평 방향은 일반적으로 1m의 정밀도가 RPG 프로젝트의需求을满足하기 충분하며地表 세부 사항을增加하려면 다음方案을通过하여完成할 수 있습니다:

    • 法线贴图（Normal Map） ：표면 법선 방향을修改하여光照 반사에影响을 주어 평탄한 지형에凹凸 세부 사항이 있는 것처럼 보이게 합니다.
    • 视差遮挡映射（Parallax Occlusion Mapping） ：픽셀의 "가상 깊이 오프셋"을计算하여 텍스처에实际 두께가 있는 것처럼 보이게 하며法线贴图보다 입체감이 더 뛰어납니다.
    • 位移贴图（Displacement Mapping） ：Nanite 및细分曲面技术를借助하여位移贴图을通过하여真正的 기하학적凸起（픽셀 수준 높이修改）을 구현할 수 있습니다.
    • 地表附着物 ：지형 표면에 정적 메시와贴花를放置하여 세부 사항을补充해야 하며 충돌体가 성능에 미치는影响에关注해야 합니다.

    수직 방향의纵深는一开始就要确定해야 하며后续大量内容를迭代之后才想起这个问题再修改하면有些麻烦합니다.此外 충돌 정밀도를保证해야 하므로 Z축을过渡 스트레치할 수 없으며高耸的山脉에 대해 정적 메시를使用하여填充해야 합니다.

    流送代理、组件和分段的数量平衡¶

    UE 지형이实际对应的核心结构는 ALandscape 로整个 지형의全局数据和组件层级结构를管理하며 높이 맵、가중치 맵等基础资源持有以及 지형의整体属性（예:物理设置、LOD全局参数等）控制를 포함합니다.

    ALandscape 의职责를划分하여更小粒度的 LOD管理、可视性判断、DrawCall、충돌检测 및 재질管理를拥有하기 위해 지형 시스템은 地形组件（ULandscapeComponent） 和 分段（Section） 의概念을提出했습니다.

    현재我们가所有小粒度功能을地形组件에托付하고暂时分段机制을引入하지 않고 2017×2017分辨率 높이 맵으로 4km²场景를搭建하는 경우组件划分은两难에面临합니다:

    • 组件数量少（예:1个组件가 4km²覆盖）：单个组件의 정점 데이터量이 크고视锥体剔除时 '不可见区域'를精准剔除할 수 없으며 LOD切换은 '整体切换'만 가능（예:원거리整个组件가 LOD0에서 LOD3으로切换되어 세부 사항明显丢失）하고 충돌计算也全量数据를处理해야 하므로效率低；
    • 组件数量多（예:100个组件가 4km²覆盖）：精准剔除和 LOD切换은 가능하지만每个组件的调度（加载/卸载）、DrawCall提交、충돌体筛选은额外开销를产生하여帧率을反而拖慢합니다.

    이矛盾를解决하기 위해 UE 지형 시스템은 分段（Section） 概念을引入했습니다 —— 它的定位은组件的进一步划分이 아니라组件内部에서 精细粒度的 DrawCall、LOD、剔除、충돌 功能을承担하여组件职责合并을允许함으로써 组件数量减少 와 细粒度管理 의平衡을实现합니다.

    流送代理（ALandscapeStreamingProxy） 是 UE5 World Partition이引入한新概念으로 World Partition流送的最小单位는 Actor이고 Component가 아니므로流送代理的目的는原先 ALandscape下에 모두挂在된一系列 ULandscapeComponent를区域划分에 따라不同的流送代理中에划分하는 것입니다.一个流送代理는一个或多个地形组件를包含할 수 있으며流送代理的划分은项目本身想要的流送粒度에取决于합니다.

    가치 있는 점은流送代理的出现이分段的地位产生一些动摇을 시켰다는 것입니다.因为早期项目在使用 지형时地形组件는一般完全加载然后剔除를通过하여优化를进行하므로分段使用은组件减少를可以합니다.

    但现在 World Partition의 Streaming이 있으므로 HLOD的合并을结合하여地形组件数量减少를不仅可以同时几何和纹理数据的低级别的 Mip层를存储하기 위해 SVT를开启하여地形的 RVT에 SVT를使用하며地形 HLOD 재질은重新烘培贴图을不需要합니다.因为实际项目中通常地形上에 RVT를使用하고地形的 RVT에 SVT를开启하여低级别的 Mip层를存储하기 때문입니다.因此地形 HLOD 재질은直接 ALandscape中에 HLOD Material Override를指定할 수 있습니다.

    因此地形 HLOD的 재질은纹理输入을不需要하며直接 RVT的 SVT를采样하면 됩니다:

    RVT는地形上的应用가非常广泛하며 예를 들어远处的地表 세부 사항（예:贴花、草皮...）을 RVT에烘培하여 HLOD的远景 재질效果를保证할 수 있습니다.

    높이를 RVT에写入하면一些特效实现时非常有用하며 예:

    • 下雨、积雪、水流：地形高度（海拔）和法线方向（坡度）에 따라自然现象的效果分布를动态控制합니다.
    • 足迹/踩踏效果：角色移动时接触点的地形位置에地形起伏와匹配的足迹를生成합니다.
    • 爆炸/冲击痕迹：爆炸冲击点在地形表面에地形轮廓와匹配的凹痕或焦痕를生成합니다.
    • 雾气/烟尘分布：地形高度和坡度를利用하여雾气浓度를控制하여山谷雾、爬坡雾等效果를模拟합니다.
    • 地面湿润/干燥过渡：地形排水能力（坡度）에 따라雨后地面干燥过程를模拟합니다.

    地形 RVT开启 SVT的步骤는查阅할 수 있습니다:

    • https://dev.epicgames.com/documentation/zh-cn/unreal-engine/runtime-virtual-texturing-in-unreal-engine

    需要注意的是文章里提到 RVT体积 细节（Details） 面板中 在编辑器中使用流送低mip（Use Streaming Low Mips in Editor） 属性를选择하는데最新版本的引擎中该属性的名称은 View In Editor로已经改为되었으므로务必勾选해야 합니다.否则编辑器下 RVT는 SVT的数据를读取하지 않습니다.

    UE 지형系统的调度和管理가比较复杂看起来지만它本质上还是底层的几张贴图进行处理하는 것입니다.如果 UE的编辑器를绕过하여对应的图像를直接处理하면自由度가可太高了.

    높이 맵和权重图的管理는统一 ULandscapeInfo 中에放到了我们可以这样获取到:

    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();

    UE中的高度图对应的结构는 EditLayers 로 UE는多个高度图叠加를支持하며导入导出操作는 다음과 같습니다:

    void ExportAllEditLayers(ALandscape* LandscapeActor, FString OutputDir){
    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();
    for (int i = 0; i < LandscapeActor->GetLayerCount(); i++) {
        const FLandscapeLayer* Layer = LandscapeActor->GetLayerConst(i);
        FString ExportFilename = FString::Printf(
            TEXT("%s_%s.%s"),
            *Filename,
            *Layer->Name.ToString().Replace(TEXT(" "), TEXT("_")),
            *Extension
        );
        FScopedSetLandscapeEditingLayer Scope(LandscapeActor, Layer->Guid);             // 上下文中当前编辑的高度图层设置
        LandscapeInfo->ExportHeightmap(FPaths::Combine(OutputDir, ExportFilename));     // 当前高度图层导出
    }
}

void ImportSingleEditLayer(ALandscape* LandscapeActor, int LayerIndex, FString ImportFilename){
    ULandscapeInfo* LandscapeInfo = LandscapeActor->GetLandscapeInfo();
    const FLandscapeLayer* Layer = LandscapeActor->GetLayerConst(LayerIndex);
    FImage Image;
    FImageUtils::LoadImage(*ImportFilename, Image);
    if (Image.Format != ERawImageFormat::Type::G16) {                                   // G16格式만支持
        return;
    }
    FIntRect TargetResolution;
    LandscapeInfo->GetLandscapeExtent(TargetResolution);
    if (Image.SizeX != TargetResolution.Width() + 1 || Image.SizeY != TargetResolution.Height() + 1) {
        FImage ScaledImage;                                                             // 导入图像를地形的分辨率로缩放
        Image.ResizeTo(ScaledImage, 
                       TargetResolution.Width() + 1,
                       TargetResolution.Height() + 1, 
                       ERawImageFormat::Type::G16, 
                       Image.GammaSpace);
        Image = ScaledImage;
    }
    FScopedSetLandscapeEditingLayer Scope(LandscapeActor, Layer->Guid, [&] {
        LandscapeActor->RequestLayersContentUpdate(ELandscapeLayerUpdateMode::Update_Heightmap_All);
    });
    FHeightmapAccessor<false> HeightmapAccessor(LandscapeInfo);
    HeightmapAccessor.SetData(TargetResolution.Min.X,
                              TargetResolution.Min.Y, 
                              TargetResolution.Max.X, 
                              TargetResolution.Max.Y, 
                              (uint16*)Image.RawData.GetData());
}
