    4.宏、模板、反射

    대부분의 동료들은 비법을 찾은 후, 이후 학습에 큰 어려움이 없을 것이라고 믿습니다. 그리고 이 이후의 단계는 실제로 '게으름'이라는 두 글자에 중점을 둡니다.

    매크로, 템플릿, 리플렉션은 개발의 필수 요소가 아닙니다. 이를 사용하면 많은 코드를 적게 쓸 수 있지만, 새로운 문제도 발생시킵니다.

    매크로（Macro）¶

    C++ 코드가 컴파일에 참여하기 전에 전처리 과정이 있으며, 이 과정에서 전처리기가 코드의 **전처리 지시문**을 처리합니다. 컴파일러마다 전처리 지시문이 다르며, 예를 들어 Microsoft C/C++ 전처리기는 다음 지시문을 인식할 수 있습니다:

    • #define：매크로 정의
    • #if：조건 로직 판단
    • #ifdef：if define 판단
    • #ifndef：if not define 판단
    • #elif：else if
    • #else
    • #endif：로직 판단 종료
    • #error：오류抛出
    • #include：헤더 파일 포함
    • #line：컴파일러에 제공되는 행 번호 수정
    • #pragma：Pragma 지시문은 기계 또는 운영 체제별 컴파일러 기능 지정
    • #undef：매크로 정의 취소
    • ...

    #define으로 매크로를 정의하고 #undef로 이전 매크로 정의를 취소할 수 있습니다. 매크로의 로직은 간단한 문자 대체로 볼 수 있으며, 기본 사용법은 다음과 같습니다:

    #define EMPTY_MACRO                         //빈 매크로
#define SRC Dst                             //대체

#define EMPTY_FUNC_MACRO()                  //빈 함수 매크로
#define F(Param) Param                      //함수 매크로
#define F_STR(Param) #Param                 //함수 매개변수를 문자열로 변환
#define F_MERGE(Param0,Param1) Param0##_##Param1    //함수 매개변수拼接
#define F_VARIADIC(...) __VA_ARGS__                 //가변 매개변수 전달

int main() {
    EMPTY_MACRO
    int SRC;
    EMPTY_FUNC_MACRO()
    F(const char*) F_MERGE(Const, Text) = F_STR(F_VARIADIC(A, B, C, D, E));
    return 0;
}

    위 코드는 전처리 단계 후 다음과 같이 변합니다:

    int main() {
    int Dst;
    const char* Const_Text = "ABCDE";
    return 0;
}

    일반적으로 C++ 프로그램의 매크로 정의는 다음에서 가져옵니다:

    • 컴파일러의 미리 정의된 매크로
    • 빌드 도구 추가 매크로
    • 코드에서 #define으로 정의된 매크로

    컴파일러의 미리 정의된 매크로는 MSVC를 예로 들어, 자세한 미리 정의된 매크로 목록은 다음과 같습니다:

    • https://learn.microsoft.com/en-us/cpp/preprocessor/predefined-macros?view=msvc-170

    cmake와 같은 빌드 도구는 target_compile_definitions 함수를 제공하여 빌드 대상에 매크로 정의를 추가합니다:

    target_compile_definitions(<target>
  <INTERFACE|PUBLIC|PRIVATE> [items1...]
  [<INTERFACE|PUBLIC|PRIVATE> [items2...] ...])

    코드 간소화¶

    • 일부 고정 단계의 코드를 매크로로 대체하여 코드를 간소화할 수 있습니다

    예:

#define MIN(a,b) ((a) < (b) ? (a) : (b))

#define M_PI 3.1415926535

    /*클래스의 관련 작업(예: 클래스를 스크립트에 등록...)을 생성하기 위해 이 그룹의 매크로 사용..*/
#define CLASS_BEGIN(ClassName) ...
#define CLASS_ADD_PROPERTY(PropertyName) ...
#define CLASS_ADD_FUNCTION(FunctionName) ...
#define CLASS_END() ...

    #define FOR_EACH_NUMBER_TYPE(FuncBegin,Func)\

    결점¶

    매크로는 만능이 아니며 심각한 문제도 수반합니다:

    • 기능이 단순하며 문자열 대체만 수행합니다. 매개변수에 대해 拼接**와 **문자열 변환 작업만 가능합니다
    • 매크로는 C++ 표준 외의 많은 마법 문법을 프로그램에 추가하며 과도한 사용은 개발자에게 인지 부담을 증가시켜 유지보수를 어렵게 합니다
    • 매크로 확장 코드는 컴파일러 디버깅을 사용할 수 없습니다

    템플릿（Template）¶

    대부분이 흔히 접하는 템플릿 예제는 std::vector, std::map, std::sort()와 같은 C++ 표준 라이브러리의 다양한 컨테이너와 알고리즘일 것입니다...

    현재笔者의 경험来看, 주로 컨테이너, 알고리즘, 직렬화, 리플렉션, 스크립트 바인딩 등 타입과 강하게 관련된 일부 도구 라이브러리에서 대량으로 사용됩니다.

    • 템플릿을 사용하여 일부 판단 수행: 예를 들어 특정 타입이 특정 조건을 충족하는지, 특정 구조가 존재하는지 판단...

int main() {

      • 타입이 시퀀스 컨테이너인지 어떻게 확인?
      • std::sort의 정렬 메커니즘을 구현해야 하므로 시퀀스 컨테이너를 허용하고 오직 시퀀스 컨테이너만 이 메커니즘을 통해 정렬하도록 고려해야 합니다:

      최종 코드는 다음과 같습니다:

      #include <iostream>
#include <algorithm>
#include <vector>
#include <list>

template<typename _Ty>
struct sequential_container {                   //타입이 시퀀스 컨테이너인지 판단하고 시퀀스 컨테이너의 크기를 얻기 위한 구조체, 기본적으로 false와 0
    static_assert(false,"Invalid Type")         //비 시퀀스 컨테이너 사용 시 오류
    static int size(const _Ty& containter){ return 0;}
    static const bool isVaild = false;
};


template<typename _Ty>
struct sequential_container<std::vector<_Ty>>{  //부분 특수화를 통해 std::vector를 시퀀스 컨테이너로 지정하고 size 함수 구현
    static int size(const std::vector<_Ty>& containter) { return containter.size(); }
    static const bool isVaild = true;
};

//std::enable_if를 통해 범위 제한
template<typename _ItemType, typename std::enable_if<sequential_container<_ItemType>::isVaild>::type* = nullptr>
void sequential_container_sort(std::vector<_ItemType>& vec) {
    std::sort(vec.begin(),vec.end(),[](const _ItemType& Lhs, const _ItemType& Rhs){
        return sequential_container<_ItemType>::size(Lhs) < sequential_container<_ItemType>::size(Rhs);
    });
}

int main() {
    std::vector<std::vector<int>> vec = {
        {0,1,2},
        {0,1},
        {0,1,2,3,4},
        {0,1,2,3},
        {0}
    };
    sequential_container_sort(vec);
    return 0;
}

      나중에 다른 시퀀스 컨테이너를 확장하려면 템플릿 특수화 또는 부분 특수화만 하면 됩니다:

      template<>                  //std::string 확장
struct sequential_container<std::string> {      
    static int size(const std::string& containter) { return containter.size(); }
    static const bool isVaild = true;
};

template<typename _Ty>      //std::list 확장
struct sequential_container<std::list<_Ty>> {
    static int size(const std::list<_Ty>& containter) { return containter.size(); }
    static const bool isVaild = true;
};

    리플렉션（Reflection）¶

    기본 개념¶

    **매크로**는 전처리 단계에서 코드 대체를 수행할 수 있습니다.

    **템플릿**은 C++의 클래스, 구조체, 함수가 타입에 따라 변할 수 있게 합니다.

    이들은 C++에 명확한 문법이 있지만, 리플렉션은 다릅니다. 리플렉션은 C++ 및 컴파일러 표준에 속하지 않으며, 기계 —— 코드의 열거형, 클래스, 구조체, 함수...을 런타임에 액세스하거나 조작할 수 있는 자산으로 만드는 메커니즘에 더 가깝습니다. 본질적으로 C++ 코드의 자가 진단입니다.

    이 중 완료할 수 있는 작업은 다음을 포함하지만 이에 제한되지 않습니다:

    1. 이름에 따라 객체의 속성 읽기/쓰기
    2. 이름에 따라 함수 호출
    3. 클래스 이름에 따라 인스턴스 생성
    4. 이름에 따라 타입 간 상속 관계 판단
    5. 객체의 모든 속성, 메서드 및 열거형 반복
    6. 다른 타입 간의 암시적 적응
    7. 타입, 속성, 함수, 매개변수에 메타데이터 추가

    RTTI¶

    C++에는 기본적으로 RTTI(런타임 타입 식별) 메커니즘이 있으며, RTTI는 다음 두 가지 매우 유용한 연산자를 제공합니다:

    • typeid 연산자: 포인터와 참조가 가리키는 실제 타입 반환.

    • dynamic_cast 연산자: 기본 클래스 타입의 포인터 또는 참조를 파생 클래스 타입의 포인터 또는 참조로 안전하게 변환.

    이를 사용하여 타입 정보를 얻을 수 있지만 RTTI를 활성화하면 전체 프로그램 실행 성능에 영향을 미치므로 엔진에서는 RTTI를 비활성화하고 리플렉션 프레임워크 대부분이 자체 Cast 함수를 구현합니다.

    자세한 내용은 https://baike.baidu.com/item/RTTI 참조

    리플렉션 원리¶

    현재 상대적으로 완벽한 리플렉션 프레임워크는 다음과 같습니다:

    • Unreal Engine："오픈 소스" 게임 엔진
    • Qt：오픈 소스 GUI 프레임워크
    • RTTR（Run Time Type Reflection）：오픈 소스 리플렉션 라이브러리

    이러한 리플렉션 프레임워크는 위 작업을 모두 지원하며 각 구현에는 일정한 "특색"이 있습니다. 예:

    • Unreal Engine은 리플렉션 컴파일러 UHT(Unreal Header Tool)를 구현하여 편집기의 자동 바인딩 및 생성, 객체의 직렬화, 블루프린트 스크립트, 참조 분석, 가비지 컬렉션, 네트워크 동기화...를 지원합니다.
    • Qt는 리플렉션 컴파일러 Moc(메타 객체 컴파일러)를 구현하여 신호 슬롯 메커니즘, 시각적 UI 편집, QML 스크립트를 지원합니다.
    • Github에는 일부 C++ 리플렉션 라이브러리가 더 있지만 대부분 libclang을 사용하여 코드를 분석합니다. UE4의 HeaderTool 및 Qt의 MOC와 비교하여 libclang은 너무 많은 분석 작업을 수행하여 효율성이 극도로 낮으며 대형 프로젝트에서는 컴파일 속도를 심각하게 저하시킵니다.

    위 작업 항목 1을 예로 들어, 리플렉션이 무엇인지 모르는 C++ 사용자가 속성 이름에 따라 읽기/쓰기를 수행하려면 다음 코드를 작성할 수 있습니다:

    class Example{
public:
    void setProperty(std::string name, int var){
        if(name == "a")
            a = var;
        else if(name == "b")
            b = var;
    }
private:
    int a;
    int b;
};

    위 코드는 간단하지만 요구 사항을 충족할 수 있습니다. 또는 일부 최적화를 수행할 수 있습니다:

    • if else가 너무 느리므로 매핑을 구축하여 속도를 높일 수 있습니다:
    class Example{
public:
    void setProperty(std::string name, int var) {
        *PropertyMap.at(name) = var;
    }
private:
    int a = 0;
    int b = 0;
    std::unordered_map<std::string, int* > PropertyMap = {
        {"a",&a},
        {"b",&b}
    };
};

    위에서는 각 Example 인스턴스에 변수 주소를 기록했지만 각 Example 객체에 PropertyMap을 생성하는 것은 약간 낭비일 수 있습니다. Example 클래스에 Property Map을 하나만 두도록 변경할 수 있습니까?

    물론 가능합니다. Example의 메모리 구조가 확정되었으므로 메모리의 오프셋 Offset을 기록하기만 하면 this의 주소 +Offset으로 변수 주소를 얻을 수 있습니다.

    class Example {
public:
    void setProperty(std::string name, int var) {
        int offset = PropertyMap[name];
        int* valuePtr = (int*)((char*)this + offset);  //포인터 +의 범위는 하나의 요소 길이이므로 여기서는 this를 char*로 변환한 후 +offset은 offset 바이트 +를 의미합니다
        *valuePtr = var;
    }
private:
    int a = 0;
    int b = 0;
    static std::unordered_map<std::string, int> PropertyMap;
};

std::unordered_map<std::string, int> Example::PropertyMap = {
    {"a", offsetof(Example, a)},
    {"b", offsetof(Example, b) }
};

    위 코드는 구조적으로 거의挑剔할 점이 없지만鸡肋합니다 —— setValue는 int 타입 변수만 설정할 수 있습니다. 다른 타입을 동일한 함수로 설정할 수 있습니까?大神们은 즉시 템플릿을 생각할 수 있으며 다음과 같은 코드를 작성할 수 있습니다:

    template<typename _Ty>
void setProperty(std::string name, _Ty var) {
    int offset = PropertyMap[name];
    _Ty* valuePtr = (_Ty*)((char*)this + offset);  //포인터 +의 범위는 하나의 요소 길이이므로 여기서는 this를 char*로 변환한 후 +offset은 offset 바이트 +를 의미합니다
    memcpy(valuePtr, &var, sizeof(_Ty));
}

    현재 코드는 기능적으로 매우 완벽하지만 여전히 일부 문제가 있습니다. setProperty를 호출할 때 속성의 타입을 명확하게 지정해야 하며, 속성이 복합 타입이고 내부에 포인터가 포함된 경우 memcpy는 단순히 얕은 복사를 수행하며 실제로 복합 구조의 깊은 복사 함수를 호출해야 할 수 있습니다. 많은 템플릿을 사용하면 코드가 급격히 팽창되므로 가벼우면서 검증 가능한 타입 소거 수단이 절실히 필요합니다.

    이 문제에 대해 해결方案을 쉽게 생각할 수 있습니다 —— void*로 데이터 주소를 기록하고 TypeID로 타입을 기록하기만 하면 됩니다.

    리플렉션 프레임워크에서 일반적으로 이 구조를 **Variant**라고 합니다.

    하지만 void*에 TypeID를 추가하여 타입을 소거하는 것으로 끝나는 것이 아닙니다. 다음을 주의해야 합니다:

    • Variant가 저장하는 데이터 타입은 다양하며 타입 소거 및 복원, 데이터 복사, 생성, 소멸에는 종종 일부 차이가 있습니다. 리플렉션 프레임워크는 일반적으로 이러한 차이에 따라 다음으로 분류합니다:
    • 기본 타입(int、double、char...)
    • Class/Struct
    • 포인터
    • 컨테이너(시퀀스, 해시)

    따라서 Variant에는 종종 타입의 특징을 식별하는 Flag가 있습니다.

    Property가 Variant 처리 지원을 위해 속성의 타입 ID를 저장해야 하므로 더 직관적으로 다음과 같은 구조를 사용합니다:

    struct MetaProperty{  //속성의 핵심 정보 저장
    variant read(void* ObjectPtr){
        return variant::readFromProperty(typeId,ObjectPtr,offset);
    }

    void write(void* ObjectPtr,variant var){
        if(var.canConvert(typeID)){
            var.writeToProperty(ObjectPtr,offset);
        }
    }

    std::string name;
    int offset;
    int typeID;
}

struct MetaClass{    //클래스의 모든 정보 저장
    std::unordered_map<std::string, MetaProperty> properties;
}

    MetaClass에는 MetaProperty 외에도 일반적으로 다음이 포함됩니다:

    MetaFunction：함수의 정보, 함수의 매개변수, ID(또는 주소)... 설명

    MetaEnum：열거형의 정보 설명

    의사 코드는 다음과 같습니다:

    class Example {
public:
    void setProperty(std::string name, variant var) {
        StaticMetaClass.Properties[name]->write(this,var);
    }
private:
    int a = 0;
    int b = 0;

    friend class MetaClass;
    static MetaClass StaticMetaClass;
};

MetaClass Example::staticMetaClass = {

    {       //properties 구성
    {"a",{"a",variant::GetType<int>(),offsetof(Example, a)}},   
    {"b",{"b",variant::GetType<int>(),offsetof(Example, b)}},
    }

};

    항목 2【함수 이름에 따라 함수 호출】의 경우 다음은 간단한 핵심 구조입니다:

    #include <iostream>
#include <string>

class Example {
public:
    void print(int a) {                 //함수 예제1
        std::cout << a << std::endl;
    }
    double add(double a, double b) {     //함수 예제2
        return a + b;
    }

    template<typename _TyParam0>
    bool invoke(std::string name, const _TyParam0& param0) {        //단일 매개변수만 있는 함수에 적응
        void* params[2] = { nullptr,(void*)&param0 };
        return invoke_internal(name, params);
    }

    template<typename _TyRet, typename _TyParam0,typename _TyParam1>
    bool invoke(std::string name, _TyRet& ret, const _TyParam0& param0, const  _TyParam1& param1) {     //두 개의 매개변수와 반환 값이 있는 함수에 적응
        void* params[3] = { (void*)&ret,(void*)&param0,(void*)&param1 };
        return invoke_internal(name, params);
    }
private:
    bool invoke_internal(std::string name, void** params) {         //핵심：매개변수 스택에 따라 해당 함수를 호출하며 index 0은 반환 값의 포인터 저장
        if (name == "print") {
            print((*reinterpret_cast<int(*)>(params[1])));
            return true;
        }
        else if (name == "add") {
            double ret = add((*reinterpret_cast<double(*)>(params[1])), (*reinterpret_cast<double(*)>(params[2])));
            if (params[0]) {
                *reinterpret_cast<double*>(params[0]) = std::move(ret);
                return true;
            }
        }
        return false;
    }
};

int main() {
    Example ex;
    ex.invoke("print", 5);
    double result;
    ex.invoke("add", result, 10.0, 5.0);
    std::cout << result << std::endl;
    return 0;
}

    리플렉션 호출의 핵심은 전환 함수 **invoke_internal**을 통해 함수 이름에 따라 해당 함수를 선택한 다음 void** params에서 매개변수를 읽고 호출을 복원한 후 템플릿을 통해 한 층 래핑하여 다른 매개변수 수에 적응하는 것입니다.

    종합적으로 두 가지 작은 기능을 구현했습니다:

    1. 이름에 따라 객체의 속성 읽기/쓰기
    2. 이름에 따라 함수 호출

    이 두 가지 작은 기능에서不知不觉 리플렉션을 구현했으며, 위 구현을 통해 변수 a、b，함수print、add를 프로그램 런타임에 액세스하거나 조작할 수 있는 자산으로 만들 수 있습니다.

    클래스가 리플렉션을 지원하려면 MetaProperty，MetaFunction，**MetaEnum**의 정보 구성, **invoke_internal**의 작성 등 많은 고정 구조의 하드 코딩 부분을 구현해야 한다는 점에 주목했을 수 있습니다. 이 부분을 간소화하기 위해 정상적으로 게으름을 피하는 방법은 다음 두 가지뿐입니다:

    • 매크로：매크로를 사용하여 고정 형식의 코드 생성 완료

    • 단점：단순한 텍스트 대체만 수행한다는 가장 큰 고통점이 있으므로 리플렉션에 사용할 때 기능이 매우 제한됩니다.

    • 템플릿：템플릿 메타는 최근 C++에서 가장狂战酷炫한 프로그래밍 패러다임이며, 이를 사용하여 많은 컴파일 시간 계산、로직 분기를 수행할 수 있습니다. 매크로와 비교하여 충분한 프로그래밍성과 완전한 C++ 환경을 갖추고 있습니다. 유명한 리플렉션 프레임워크(RTTR)는 템플릿을 통해 생성됩니다.

    • 단점：

      • 템플릿 사용门槛이 높습니다
      • 템플릿의 특성으로 인해 일부 문제가 발생합니다. 예를 들어 템플릿은 리플렉션 바인딩을 전달하기 위해 헤더 파일에 배치해야 합니다.
      • 가장 큰 단점은 여전히 일부 바인딩 함수를 수동으로 작성해야 한다는 것입니다.

    위 두 가지 방법을 결합하더라도 리플렉션 구현에는 여전히 일부 제한이 있으며 다른 방법이 있습니까? 답은 물론 있습니다.

    이러한 약간의 제한을 해결하기 위해 이这群丧心病狂的挂壁이 C++ 컴파일러에 주목했을지 상상하기 어려울 수 있습니다.

    그들의 목표도 매우 간단합니다. 코드 정보에 따라 마음대로 코드를 생성할 수 있도록 하는 것입니다.

    간단히 말해, 템플릿처럼 모든 코드 정보를 얻지만 템플릿 문법에 제한되지 않고, 매크로처럼 코드를 수정할 수 있지만 단순한 문자 대체만 하는 것이 아닌 프로그램을 만들려는 것입니다.

    이를 위해 리플렉션 컴파일러를 구현해야 하며, 이는 두 부분으로 구성됩니다:

    • Header Parser：코드에 정의된 정보(일반적으로 헤더 파일) 분석

    • Code Generator：기존 정보에 따라附加 코드生成

    이러한 방식을采用하는 것은 Qt（Moc）와 Unreal（UHT）이며, 그들의流程는 기본적으로相似합니다:

    • 약속된 마크：여기서 마크는 매크로를指하며, 마크를 사용하는 주요目的은 다음과 같습니다:

    • 코드 스캔 속도加快, 편집기는 기본적으로 거친 스캔을 사용하며 마크를 만나면 해당 세부 분석을触发

    • 리플렉션할 구조를 수동으로指定할 수 있습니다

    • UE를 예로 들어:

    UCLASS()                          //매크로를 사용하여 클래스 마크
class MyObject: public UObject{
    GENERATED_BODY()              //클래스 정의의 진입점 매크로
public: 
    UFUNCTION(BlueprintCall)      //매크로를 사용하여 함수 마크, 매개변수는 리플렉션 컴파일러에 전달됩니다
    void Func();
private:
      UPROPERTY(EditAnywhere , Meta = (DisaplayName = "Int"))         //매크로를 사용하여 속성 마크
    int Value
}

    마크 매크로의 사용법은 주로 다음 세 가지가 있습니다:

    • 매개변수가 없는 "빈 매크로"：마크 역할만 수행

      • 예: Qt의 Q_INVOKABLE

    • 매개변수가 있는 "빈 매크로"：마크 외에도 스캔 도구에 매개변수를 전달하여 개인화된 코드生成 가능

      • 예: UE의 UProperty(...) 、 UFunction(..) 등, Qt의 Q_PROPERTY(...)

    • 진입점 매크로：一部分定義附带

      • 예: UE의 **GENERATED_BODY()**는 UHT에 의해 gen.h에生成되는 정의이며, Qt의 **Q_OBJECT**는一部分定義를固定填充합니다. 예如下:
      #define Q_OBJECT \
static const QMetaObject staticMetaObject; \
virtual const QMetaObject *metaObject() const; \
...

    • 코드 분석&정보 수집

    • 이 과정은 주로 Header Parser(UE UHeaderTool | Qt MOC)에서 완료하며, 분석은 실제로 키워드를 스캔하고 클래스의 계층 구조를还原하는 것이며 문법 관련 내용은 포함되지 않습니다. QtMOC의 Parser는 가볍고高效하며 함수, 열거형, 타입, 클래스를轻松解析할 수 있으며 UE는其工程에许多扩展을提供합니다.

      완전한 C++ 컴파일러의 경우 코드의 어휘 분석, 구문 트리构建 등을 필요로 하며这些过程는非常缓慢합니다. Qt의 MOC에서는巧的方法을采用합니다.首先代码에 대해 전처리(예: #include, #define执行)하여真正的代码를得到한 후代码를分隔符(공백, 탭, 줄 바꿈)按划分하여 Symbol数组로 만듭니다.例如上方的代码는 다음과 같이划分됩니다:

      {"UCLASS()" ,"class", "MyObject", ":", "public", "UObject", "{", "GENERATED_BODY()", ...}

      리플렉션 컴파일러는只需快速匹配这些符号,我们的标记 매크로(예:GENERATED_BODY())를 만나면逐字符로我们想要的信息를解析합니다

    • 예:

      다음 마크를 약속했다고 가정합니다,

      AxPROPERTY(GET getX SET setX) 
int x = 0;

      其解析过程는 다음과 같이 보입니다:

      void Moc::parser(){
       //...
       case AX_PROPERTY_TOKEN: //这段代码会在扫描到 AxPROPERTY的symbol时触发
          parseAxProperty(&def);
       break;
       //...
}

void Moc::parseAxProperty(ClassDef *def)
{
       PropertyDef axVarDef;         //属性定义
       next(LPAREN);                 //判断下一个是不是左括号
       while (test(IDENTIFIER)) {        //判断是不是标识符（非关键字）
           QByteArray type = lexem();    //获取类型
           next();                       //扫描下一个关键字
           if (type == "GET") {      
               axVarDef.getter = lexem();//解析Get函数
           }
           else if (type == "SET") {
               axVarDef.setter = lexem();//解析Set函数
           }
       }
       next(RPAREN);                 //判断下一个是不是右括号
       axVarDef.type = parseType();  //解析类型
       next(IDENTIFIER);             //判断下一个是不是标识符
       axVarDef.name = lexem();      //存储函数名
       until(SEMIC);                 //一直往后扫描，直到分号
       def->propertyList << axVarDef;    //将该属性添加到类中
}

    • 충분한 코드 정보를 수집하면 **Code Generator**를 사용하여 코드를生成합니다.说白了就是Header Parser가搜集한信息에 따라代码文件을 write하는 것입니다.

    • Qt의 경우 moc_*.cpp를生成하며, 여기에之前手写이 필요한代码(예: property, function, enum의各类信息, invoke_internal函数等)이存放됩니다.

    • UE의 경우 _.generated.h _.gen.cpp를生成합니다: Qt와 비교하여 UE는 헤더 파일을 하나 더生成하며, 이 파일의主要目的는 **GENERATED_BODY**의定义를生成하는 것입니다. 이方法을 통해 UE는甚至 클래스의定义를自定义地修改할 수 있으며, Qt는只能已有的接口上扩展합니다.

    • 예

      现在Code Generator를使用하여属性信息에 따라代码를生成한다고 가정합니다

      c++ for(auto& property:def.propertyList){ fprintf(out," .property(\"%s\"",property.name.constData()); if (property.getter.isEmpty()) { fprintf(out, ",&%s::%s)\n", def.classname.constData(), property.name.constData()); continue; } fprintf(out, ",&%s::%s", def.classname.constData(), property.getter.constData()); if (!property.setter.isEmpty()) { fprintf(out, ",&%s::%s", def.classname.constData(), property.setter.constData()); } fprintf(out, ")\n"); }

      上面的代码는 다음과 같은代码를生成할 수 있습니다:

      c++ .property("x",&TestClass::getX,&TestClass::setX)

    • 上述步骤는代码的解析和生成만完成했으며,真正将UHT和MOC를项目上实装하려면构建工具에依靠해야 합니다:

    • UE는 **UBT（Unreal Build Tool）**를 통해 UHT를调用합니다

    • Qt는 QMake를 통해 MOC를调用합니다

    -此外, CMake는现在主流的构建工具로서相应的指令를提供하여这些操作을支持합니다.例如:

    ```cmake
//自定义命令，并指定依赖，当${INPUT_FILE_PATH})变动时，调用${CMD}，生成 ${OUTPUT_FILE} 
add_custom_command(OUTPUT ${OUTPUT_FILE}               
                   COMMAND ${CMD}
                   DEPENDS ${INPUT_FILE_PATH})   

//生成的代码文件을 target的sources中添加합니다
set_property(TARGET ${PROJECT_TARGET} APPEND PROPERTY SOURCES ${OUTPUT_FILE}) 
```

    这种 **Header Parser + Code Generator**的机制을拥有하면更高级别的리플렉션功能을做할 수 있습니다(我们可以自己的需求에 따라C++代码를魔改할 수 있습니다):

    • 编辑器的自动绑定
    • 自动序列化
    • 脚本的自动绑定
    • 引用分析、垃圾回收
    • 网络同步

    这些功能的实现에는太多的细节和难点가 있으며,个人认为它们的实现原理을深究하는 것은太多的意义가 없습니다.

    • 使用者来说,只需官方所制定的使用方式을了解하고,底层上,它们的工作流程를粗略了解하면即可.
    • 同样开发需求가 있는人来说, Code Generator는一般框架的核心机制과强关联되어 있으므로里面에非常多的黑话가 있으며,整体思路上借鉴할 수 있지만细节上盲目追求一致할必要가 없습니다.

    框架对比¶

    笔者는 UE, Qt, RTTR都有不少的使用经验이 있으며,整体使用下来的感受如下:

    • 反射信息的支持程度：UE > RTTR > Qt, UE和RTTR的反射信息는注册을 통해全部一起存储되므로全局에서统一所有的MetaClass, MetaFunction, MetaEnum을处理할 수 있으며, Qt는有些保守하여反射信息를 Class局部에存储하며甚至 MetaData를支持하지 않습니다. UE的反射는比较夸张하여甚至手动로 MetaClass를构造하여 Object를创建할 수 있습니다(블루프린트의原理).
    • 扩展性：UE > Qt > RTTR,这点主要是因为UE和Qt有反射编译器的加持입니다.
    • 易用性：Qt > RTTR > UE, Qt的反射는相对比较精炼합니다.
    • 轻量级的反射需求가 있는 경우 RTTR은非常不错的选择입니다.

    这里也有一些笔者的反射测试项目:

    • XObject : STD库를使用하여 Qt의 MOC를模仿하며, XObject의标记代码를扫描하여 Rttr的注册代码以及序列化方法를生成합니다.

    • QDetailWidget：Qt Moc的基础上, UE的DetailView를模仿하며,自定义属性编辑器,撤销重做를支持하며,序列容器,散列容器,共享指针的属性编辑를允许합니다(重构中...).
