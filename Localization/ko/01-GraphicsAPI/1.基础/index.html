    그래픽 API 기초¶

    기본 개념¶

    현대 그래픽 API는 초보자에게 처음에는 이해하기 어려운 많은 구조가 존재하지만, 너무 걱정할 필요 없다. 이 용어들은 특정 구조와 프로세스에 호칭을 붙인 짧은 별칭일 뿐이며, 응용 시나리오를 이해하고 사용 프로세스를 익히면 자연스럽게 그 의미를 알게 될 것이다.

    물리적 디바이스（Physical Device）¶

    그래픽 API에서 우리는 일반적으로 GPU를 **물리적 디바이스**라고 부른다.

    GPU의 빠른 발전에 따라 그래픽 API의 기능도 날로 증가하고 있는데, 그래픽 API의 사용이 GPU 디바이스와 하위 호환되도록 하기 위해 그래픽 API는 물리적 디바이스가 특정 기능을 지원하는지 여부와 리소스 제한을 쿼리하기 위한 인터페이스를 제공하는 경우가 많다.

    Vulkan을 예로 들어 **VkPhysicalDeviceFeatures**를 사용하면 물리적 디바이스가 특정 기능을 지원하는지 쿼리할 수 있다:

    struct VkPhysicalDeviceFeatures {
    VkBool32    robustBufferAccess;
    VkBool32    fullDrawIndexUint32;
    VkBool32    imageCubeArray;
    VkBool32    independentBlend;
    VkBool32    geometryShader;
    VkBool32    tessellationShader;
    VkBool32    sampleRateShading;
    VkBool32    dualSrcBlend;
    VkBool32    logicOp;
    VkBool32    multiDrawIndirect;
    VkBool32    drawIndirectFirstInstance;
    VkBool32    depthClamp;
    VkBool32    depthBiasClamp;
    VkBool32    fillModeNonSolid;
    VkBool32    depthBounds;
    VkBool32    wideLines;
    //...
}

    **VkPhysicalDeviceLimits**를 사용하면 물리적 디바이스의 리소스 제한을 쿼리할 수 있다:

    struct VkPhysicalDeviceLimits {
    uint32_t              maxImageDimension1D;
    uint32_t              maxImageDimension2D;
    uint32_t              maxImageDimension3D;
    uint32_t              maxImageDimensionCube;
    uint32_t              maxImageArrayLayers;
    uint32_t              maxTexelBufferElements;
    uint32_t              maxUniformBufferRange;
    uint32_t              maxStorageBufferRange;
    uint32_t              maxPushConstantsSize;
    uint32_t              maxMemoryAllocationCount;
    //...
}

    개발자는 그래픽 API를 사용할 때 이러한 제한이 존재함을 알아야 하며, 사용 시 기능 요구 사항에 맞는 물리적 디바이스를 찾는 것 외에도 일부 디바이스 기능을 지원하지 않는 사용자를 위해 개발 시 로직상의 호환성 처리도 해야 한다.

    논리적 디바이스（Device）¶

    논리적 디바이스는 개발자와 물리적 디바이스 간 통신의 **"대리점"**이다.

    CPU와 GPU는 각각 독립적으로 실행되어 서로 기다리지 않기 때문에, 이들 간 통신 부담을 줄이고 개발자가 사소한 일마다 GPU를 따라다니며 "이 작업을 끝내지 않고 어디 가려고?" 라고 외치지 않도록 하기 위해, 현대 그래픽 API는 논리적 디바이스라는 개념을 제공한다. 개발자는 대리점에게 할 일을 말하면, 대리점은 일을 모아서 물리적 디바이스에 통보하여 실행하도록 한다.

    논리적 디바이스를 생성할 때는 물리적 디바이스의哪些 확장을 활성화할지 지정해야 한다.

    명령 버퍼（Command Buffer）¶

    명령 버퍼는 Command List라고도 하며, 개발자의 **"메모장"**이다.

    개발자는 대리점（논리적 디바이스）에게 일부 물건을 건네는 것 외에도, 할 일을 메모장에 기록하여 대리점에게 전달하여 물리적 디바이스에 전달하도록 한다.

    QRhi에서는 CommandBuffer를 직접 생성할 수 없으며, 다음 두 가지 경로를 통해 얻을 수 있다:

    • SwapChain을 통해 현재 CommandBuffer를 가져올 수 있다.
    • rhi->beginOffscreenFrame은 새로운 CommandBuffer를 생성한다.

    디바이스 큐（Device Queue）¶

    디바이스 큐는 대리점（논리적 디바이스）와 물리적 디바이스 간 통신의 유일한 **"다리"**이다.

    대리점이 개발자로부터 받은 물건과 메모장을拿到하면, 다리를 건너 물리적 디바이스로 빠르게 향한다.

    동기화（Synchronization）¶

    GPU가 왜这么强할까? 그것은 GPU가 많은 부하를 맡고 있기 때문이다. 다음과 같은 상황을 상상해보자:

    어느 날, GPU 대장이 대리점으로부터送来的 메모장을收到하고 즉시 부하를召集하여 명령을 내린다.

    ："음~, 첫 번째는 팬도 대성가의 광고를 모두 떼어내는 것, 장삼아, 너가 가라!"

    "받았습니다!" 라고 말한 후 장삼은 즉시 팬도 대성가로 향한다.

    ："두 번째는~, 팬도 대성가에 개발자의 광고를 모두 붙이는 것, 리사야, 너가 해라!"

    "명령받았습니다!" 라고 말한 후 리사는 사랑하는 오토바이에 타고 팬도 대성가로 질주한다.

    이튿날, 개발자가 일군을 이끌고 와서 GPU 대장에게 광고가 왜 붙지 않았는지 질문하며 탁자를 치려고 한다.

    GPU 대장은 메모장을 확인했더니 문제가 없었고, 장삼도 떼었고 리사도 붙였다고 하니, 다시 물어보니 놀랍게도 리사가 너무 일찍 가서 먼저 광고를 붙였는데, 나중에 장삼이 모두 떼어버렸다는 사실이 밝혀졌다.

    돌이켜보면, 개발자가 명확한 설명을 하지 않았고 GPU 대장의 이해도 부족하여 잘못된安排을 하여 이 사고가 발생했다.

    GPU에서는 많은 작업이 병렬로 수행되기 때문에, 일부 작업이 순서대로 시작되지만乱序로 실행되는情况가 발생할 수 있다.

    또한 CPU와 GPU는 서로 기다리지 않지만,某些情况下我们又希望某些操作이 실행 완료되거나事件가触发될 때까지 기다리려고 한다.

    이를 위해 현대 그래픽 API는 CPU, GPU, 명령, 큐之间의 동기화를 제어하기 위한一些 구조를 제공한다. Vulkan을 예로 들어, 동기화 제어에 사용되는几种 구조를 제공한다:

    • 펜스（Fence）
    • 세마포어（semaphore）
    • 배리어（Barrier）
    • 이벤트（Event）

    이들의 세부 사항은 다음을 읽어볼 수 있다:

    • vulkan中的同步和缓存控制之一，fence和semaphore
    • vulkan中的同步和缓存控制之二，barrier和event
    • 理解Vulkan同步(Synchronization)

    창 표면(Window Surface)¶

    렌더링 결과를 화면에呈现하기 위해, 개발자는往往 그래픽 API와 창 시스템之间的 연결을创建해야 한다. Vulkan에서는 해당 플랫폼의 창에 대해 **창 표면（Window Surface）**를创建하여 그래픽 API와 창 시스템之间交互的桥梁로 사용할 수 있다.

    각 운영 체제（Windows, Linux, Mac...）의 창 시스템이 일치하지 않기 때문에, Window Surface的创建에는 플랫폼 특정 구성이一些 필요하다.

    一些 오픈 소스 라이브러리는这些繁琐的 구성을 피하기 위해致力于开发되었으며, GLFW가 그 예이다.

    **GLFW**는 OpenGL, OpenGL ES 및 Vulkan 애플리케이션 개발을 위한 오픈 소스, 다중 플랫폼 라이브러리이다.

    창, 컨텍스트 및 표면创建, 입력 읽기, 이벤트 처리等를 위한 간단하고 가벼운 플랫폼 독립적 API를 제공한다.

    GUI 프레임워크도大多 Window Surface的管理을 제공하므로,我们要做的就是文档를翻阅하고源码를深入研究하는 것이다.

    파이프라인（Pipeline）¶

    파이프라인은管线라고도 하며, GPU上에서执行되는任务流程이다. 현대 컴퓨터 그래픽 API中常见的 파이프라인은 다음 세 가지类型이 있다:

    • 그래픽 렌더링 파이프라인（Graphics Pipeline）：**렌더 타겟（RenderTarget）**上에图像를绘制하기 위해 사용된다.
    • 계산 파이프라인（Compute Pipeline）：**버퍼（Buffer）**或者 **图像（Image）**中的数据를处理하기 위해 사용된다.
    • 광선 추적 파이프라인（Ray Tracing Pipeline）：광선 추적流程를 위해 사용된다.

    이전一节에서는 콘솔 프로그램을 통해 그래픽 렌더링 파이프라인에 대해简单히了解했는데,这里有一个更完整的流程图가 있다:

    https://graphicscompendium.com/intro/01-graphics-pipeline

    它的工作流程는简单히 다음과 같이看作할 수 있다:

    • 개발자는顶点数据를 GPU에上传한다. -每个顶点的数据는 **顶点 셰이더（Vertex Shader）**에 의해处理된다.
    • （如果有的话）再经过 테슬레이션 제어 셰이더（Tessellation Control Shader）, 테슬레이션 평가 셰이더（Tessellation Evaluation Shader）, **지오메트리 셰이더（Geometry Shader）**处理后,三角形数据가成功组装된다. -之后光栅화引擎은三角形数据를映射（光栅化）하여一个个 **프래그먼트（Frament）**를得到한다. -每个 프래그먼트的数据는 **프래그먼트 셰이더（Fragment Shader）**에 의해处理된다.
    • **测试与混合阶段**를 통해重叠 프래그먼트를处理한다. -对应坐标像素的唯一值를得到하여 **렌더 타겟（RenderTarget）**上에绘制한다.

    셰이더（Shader）¶

    셰이더는 GPU上에서运行的微小程序로, 주로 파이프라인의功能扩展에用于된다.比如上面的 그래픽 렌더링 파이프라인中:

    -输入的顶点数组는 **顶点 셰이더（Vertex Shader）**에 의해处理된다. -光栅化之后,每个像素는 **프래그먼트 셰이더（Fragment Shader）**에 의해处理된다.

    一条 그래픽 렌더링 파이프라인은至少一个顶点 셰이더和 프래그먼트 셰이더를要求하지만,实际上 현대 그래픽 API는额外的 셰이더扩展을支持한다:

    • 테슬레이션 제어 셰이더（Tessellation Control Shader）
    • 테슬레이션 평가 셰이더（Tessellation Evaluation Shader）
    • 지오메트리 셰이더（Geometry Shader）
    • 컴퓨트 셰이더（Compute Shader）

    它们는其 API特有の **Shader Language**로编写된다.比如:

    • GLSL：OpenGL、Vulkan에用于된다.
    • HLSL：Direct3D에用于된다.
    • MSL：Metal에用于된다.

    현대 그래픽 엔진의通用 RHI中,多种 그래픽 API를支持하기 위해上面的一种 셰이더 언어로开发한 후其他 API의 셰이더代码로转译하는 경우가 많다.

    버퍼（Buffer）¶

    这里的 Buffer는 단순히 GPU上的一段内存（Memory）를指하는 것이 아니다.

    정확히说,一个 Buffer는一段内存를持有할 뿐만 아니라,自身의 **类型（Type）**和 **用途（Usage）**도包含한다.

    **类型（Type）**方面, 그래픽 API는一般 다음과 같이划分한다:

    • Host Local Memory ：Host만可见的内存,通常普通内存라고 부른다.
    • Device Local Memory ：Device만可见的内存,通常显存라고 부른다.
    • Host Local Device Memory ：Host가管理하며 Device가可见的内存.
    • Device Local Host Memory ：Device가管理하며 Host가可见的内存.

    Host는往往 CPU端를指하고, Device는 GPU端를指한다.

    세부 사항은 다음을查阅하라:

    • Vulkan 内存管理

    合适的内存类型를使用하면内存的读写效率를大幅提升할 수 있다. 현대 그래픽 엔진의 파이프라인中,尽可能 **Device Memory**를使用하는데, CPU에서数据를提交해야 할 경우 Host가访问할 수 없기 때문에,一般数据를 **Host可见的 Memory**上에上传한 후 명령을 통해对应的 **Device Memory**上에拷贝한다.我们一般这个主机可见内存를持有하는 Buffer를 Staging Buffer라고 부른다.

    QRhi는这些类型를进一步包装하여使用意图上进行分类한다:

    • Immutable ：永远改变하지 않을 데이터를存放하기 위해使用되며,非常高效的 GPU读写性能를具有한다.通常 **Devices Local**의 GPU内存上에放置되며, CPU가直接读写할 수 없지만 QRhi는它的上传을支持한다.其原理는:每次数据上传时 **Host Local**의 **Staging Buffer**를新建하여中转으로新数据를上传하는데,这样操作的代价는非常高昂하다.
    • Static ：同样 **Devices Local**의 GPU内存上에存储된다. Immutable과不同的是,首次数据上传时创建的 **Staging Buffer**가一直保留된다.
    • Dynamic ：频繁变化的数据를存放하기 위해使用되며, **Host Local**의 GPU内存中에放置된다. 그래픽 렌더링 파이프라인을拖延하지 않기 위해,通常双缓冲机制를使用한다.

    **用途（Usage）**方面,通常以下 **标识（Flag）**를具备할 수 있다:

    • VertexBuffer ：顶点数据를存放하기 위해使用된다.
    • IndexBuffer ：索引数据를存放하기 위해使用된다.
    • UniformBuffer ：常量数据를存储하기 위해使用된다.
    • StorageBuffer ：Compute 파이프라인中的数据计算에用于된다.
    • IndirectDrawBuffer ：间接 렌더링에 렌더링 매개변수를提供하기 위해使用된다.

    디스크립터（Descriptor）¶

    上面的 그래픽 렌더링 파이프라인中说到,每个顶点는顶点 셰이더에 의해处理되고,每个 프래그먼트는 프래그먼트 셰이더에 의해处理된다. 每个는 영어로 Per로译作되며, 파이프라인中这类 Per数据 외에도,往往相同 셰이더之间公共的、共享的 데이터가存在한다.这类 데이터를 그래픽 API中我们一般 Uniform 데이터라고 부르며,它는 셰이더의公共输入으로当作될 수 있다.

    파이프라인结构를创建할 때, Uniform 데이터의基本结构信息를描述하기 위해 디스크립터（Descriptor）를使用해야 한다.常见的 디스크립터类型有:

    • UniformBuffer ：셰이더只读的 Buffer输入.
    • Sampler ：셰이더只读的 텍스처采样输入.
    • StorageBuffer ：셰이더可读可写的 Buffer, Compute 파이프라인中使用.
    • StorageImage ：셰이더可读可写的 Image, Compute 파이프라인中使用.

    这里 QRhi的 **QRhiShaderResourceBinding**에对应한다:

    디스크립터 세트 레이아웃 바인딩（DescriptorSetLayoutBinding）¶

    一个 셰이더는往往一种类型의 Uniform输入만具有하지 않는다. 디스크립터 세트 레이아웃 바인딩（DescriptorSetLayoutBinding）은一个 디스크립터的集合으로, 셰이더上的 Uniform结构布局를定义한다. 그래픽 API中 파이프라인을创建한 후, 파이프라인的绝大部分 매개변수는改变할 수 없지만, 디스크립터 세트 레이아웃 바인딩은 파이프라인을 재생성하지 않고도动态으로替换할 수 있다.

    这里 QRhi的 **QRhiShaderResourceBindings**에对应하며,它的创建方式는非常简单하다:

    mShaderBindings.reset(mRhi->newShaderResourceBindings());
mShaderBindings->setBindings({
      QRhiShaderResourceBinding::bufferLoadStore(0,QRhiShaderResourceBinding::ComputeStage,mStorageBuffer.get()),
      QRhiShaderResourceBinding::imageLoadStore(1,QRhiShaderResourceBinding::ComputeStage,mTexture.get(),0),
});
mShaderBindings->create();

    렌더 타겟（RenderTarget）¶

    它는 OpenGL中的 Frame Buffer Object와等价하며,一个或多个 **颜色附件(Color Attachment)**로组成되고,深度附件和模板附件를包含할 수 있다.

    通常我们的绘制은其实 RenderTarget上에颜色数据를填充하는 것이며,深度和模板的数据에 대해 GPU가自动处理하므로,我们只需要一些处理规则를配置하면 된다.

    QRhiWindow¶

    운영 체제가提供하는 창은非常细粒度的控制가 가능하다.开发者가 창의某个效果를调整하려고 할 때, 창的多个属性和事件를改变해야 할可能가 있다.大量的效果가堆叠设置될 때,冲突가比较容易出现할 수 있다.比如:

    假如 **A**效果需要属性a和b를开启하고, **B**效果需要属性b和c를开启한다.如果 창에效果 **A**和 **B**를开启（即属性a、b、c를开启）한 후效果 **B**를关闭하려고 할 때, 관련属性b和c를直接关闭하면开启된属性는a만剩下되어效果 **A**的显示에问题가出现할 수 있다.

    开发者는往往 운영 체제级别的 창属性和事件보다는 창的表现效果에关注하고 싶을 뿐이므로, 창管理中效果间的设置에는大量属性和事件的重叠가存在한다.

    每个属性的设置에关联验证을加하면代码가臃肿해지고维护가困难해지며 Bug가更容易出现한다.

    因此 Qt는 상태 기계 방식을采用하여原生 창을管理한다:

    • Qt层面对 Window的各种设置은立即生效하지 않고,这些设置를存储해 두었다가 특정时机（比如 Show）에 Qt가当前上下文的配置에 따라实际的 운영 체제 창을创建한다.

    换而言之, Qt的 창은 show 함수를调用한 후才实际 Window를创建하고窗口句柄를拿到할 수 있다.

    程序开发过程中,这类代码를经常接触할 수 있다.它는复杂的代码逻辑를很好地组织할 수 있으며,尤其是 그래픽相关的工程代码中 ensure로开头的函数를经常看到할 수 있다.它所做的工作는当前属性上下文에 따라某些操作를进行하는 것이다.

    我们如果 창的 그래픽 렌더링结构를创建하려면,实际的窗口句柄가需要하기 때문에 show之后初始化를进行해야 한다.不过好在 Qt는相关的事件를提供한다:

    • void QWindow:: exposeEvent (QExposeEvent* ev )
    • 창이 un-exposed 상태에서 exposed 상태로切换될 때,此事件가执行된다. -第一次 창을显示할 때,此事件之前 resizeEvent가执行된다.

    需要注意的是,一个 창而言 exposeEvent가多次执行될 수 있지만初始化는一次만进行하면 되므로,一些逻辑验证을增加해야 한다.

    그래픽 렌더링结构主要指的是:

    • QScopedPointer<QRhiEx> mRhi
    • QScopedPointer<QRhiSwapChain> mSwapChain：스왑 체인
    • QScopedPointer<QRhiRenderBuffer> mDSBuffer：深度模板 버퍼
    • QScopedPointer<QRhiRenderPassDescriptor> mSwapChainPassDesc：스왑 체인的 RenderPass描述符

    成功初始化之后,我们只需要 창上에 렌더링和 Resize的逻辑를增加하면 된다.这里标准的 Window实现示例가 있다:

    • https://github.com/qt/qtbase/blob/dev/tests/manual/rhi/shared/examplefw.h

    还需要注意的是, QRhi를使用하여创建的资源는 QRhi를销毁하기 전에清理해야 한다.智能指针를使用하면这些资源的生命周期를很好地管理할 수 있다.

    QRhiWidget¶

    Widget与 Window最大的不同는:

    • Widget는某些事件를通过하여界面的重绘를触发하는 반면, Window는每帧都在重绘한다.

    Widget를使用하면性能를更好地节约하고不必要的刷新를避免할 수 있지만,游戏和 그래픽这种实时刷新가需要的界面时 Window를使用하면绘制性能를更好地分摊할 수 있다.

    这里标准的 Widget实现가 있다:

    QEngineUtilities¶

    一些结构的使用를简化하기 위해,笔者는一些通用的结构를 QEngineUtilities中封装했다.它는三个构建目标를包含한다:

    • QEngineCore ：렌더링 아키텍처, RHI、FrameGraph、RenderPass、RenderComponent、Asset的简易封装을包含한다.
    • QEngineEditor ：编辑器套件,数值调节器,调色器,通知气泡, QObject 기반의 DetailView, GLSL代码编辑器等许多基础属性调整控件를包含한다.
    • QEngineUtilities ：Lanuch层,不同构建配置下上面两个模块를组装한다.比如 DebugEditor配置下编辑器界面를嵌入하고, Debug配置下则 Core模块만具有한다.

    你可以这个仓库를 Pull下来:

    -自己工程的 CMakeLists.txt中 add_subdirectory를使用하여 **QEngineUtilities**를添加한다. -自己的Target에 **QEngineUtilities**를链接한다. -cmake中函数qengine_setup_env를使用하여自己的Target에环境变量를配置한다（dll搜索路径를添加）.

    它主要教学和尝试에用于된다:

    • 가독성을第一要素로强调한다. -性能를细致地追求하지 않는다（代码细节上一些瑕疵가存在하지만,笔者가察觉到的时候已经太晚了.精力有限으로目前笔者也只能选择妥协,非常抱歉...不过放心,这些影响는微乎其微하다）.
    • 렌더링을核心으로少量编辑器架构를包含하며,资产管理,网络,异步, ECS等代码膨胀을导致하는模块는引入하지 않는다.

    如果成功하면,如下代码를使用하여 Widget和 Window를创建할 수 있다:

    #include <QApplication>
#include "Render/RHI/QRhiWidget.h"
#include "Render/RHI/QRhiWindow.h"

class ExampleRhiWindow : public QRhiWindow {
public:
    ExampleRhiWindow(QRhiWindow::InitParams inInitParams) :QRhiWindow(inInitParams) {}
protected:
    virtual void onRenderTick() override {
        QRhiRenderTarget* renderTarget = mSwapChain->currentFrameRenderTarget();
        QRhiCommandBuffer* cmdBuffer = mSwapChain->currentFrameCommandBuffer();

        const QColor clearColor = QColor::fromRgbF(0.0f, 0.0f, 1.0f, 1.0f);         //蓝色로清屏
        const QRhiDepthStencilClearValue dsClearValue = { 1.0f,0 };

        cmdBuffer->beginPass(renderTarget, clearColor, dsClearValue);
        cmdBuffer->endPass();
    }
};

class ExampleRhiWidget : public QRhiWidget {
public:
    ExampleRhiWidget() {
        setDebugLayer(true);        //验证层를开启
    }
    void render(QRhiCommandBuffer* inCmdBuffer) override {
        const QColor clearColor = QColor::fromRgbF(1.0f, 0.0f, 0.0f, 1.0f);         //红色로清屏
        const QRhiDepthStencilClearValue dsClearValue = { 1.0f,0 };
        inCmdBuffer->beginPass(mRenderTarget.data(), clearColor, dsClearValue);
        inCmdBuffer->endPass();
    }
};

int main(int argc, char **argv){
    QApplication app(argc, argv);

    QRhiWindow::InitParams initParams;
    ExampleRhiWindow window(initParams);
    window.setTitle("01-RhiWindow");
    window.resize({ 400,400 });
    window.show();

    ExampleRhiWidget widget;
    widget.setWindowTitle("01-RhiWidget");
    widget.setApi(QRhiWidget::Vulkan);
    widget.resize({ 400,400 });
    widget.show();

    return app.exec();
}
